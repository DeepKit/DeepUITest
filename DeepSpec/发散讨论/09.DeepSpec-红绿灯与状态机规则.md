# DeepSpec 深范｜红绿灯与状态机规则

## 1. 文档状态

DeepSpec 第一版使用以下状态：

| 状态 | 含义 |
|---|---|
| empty | 空文档 |
| draft | 草稿 |
| reviewing | 待审阅 |
| frozen | 已冻结 |
| changing | 变更中 |
| deprecated | 已废弃 |
| conflict | 有冲突 |
| error | 校验失败 |

---

## 2. 核心流转

```text
empty → draft
draft → reviewing
reviewing → frozen
reviewing → draft
frozen → changing
changing → reviewing
reviewing → frozen
frozen → deprecated
```

---

## 3. 禁止流转

```text
draft → frozen
empty → frozen
frozen → draft
conflict → frozen
error → frozen
```

原因：

- 必须经过人类审阅；
- 不能绕过状态机；
- 冲突和错误必须先解决；
- AI 不能直接冻结文档。

---

## 4. AI 权限

AI 可以：

- `empty → draft`
- `draft → reviewing`
- 给出建议；
- 生成候选内容；
- 生成 Context Pack；
- 生成 Review Pack；
- 生成 Handoff Pack。

AI 不可以：

- `reviewing → frozen`
- 直接修改 frozen 文档；
- 忽略红灯；
- 删除已确认决定；
- 直接写入最终变更日志。

---

## 5. 红绿灯定义

| 灯色 | 状态 | 含义 |
|---|---|---|
| 灰灯 | empty | 未开始 |
| 绿灯 | pass | 结构完整，可以冻结 |
| 黄灯 | warning | 有缺项，但不一定阻塞 |
| 红灯 | blocker | 关键字段缺失，不能冻结 |
| 蓝灯 | ai_pending | AI 建议待确认 |
| 紫灯 | changing | 冻结后变更中 |
| 黑灯 | conflict | 冻结内容被异常修改或冲突 |

---

## 6. 红灯规则

出现以下情况时为红灯：

1. 缺少必填字段；
2. 文档结构无法解析；
3. 当前 Schema 校验失败；
4. 状态机流转非法；
5. frozen 文档被静默修改；
6. 接口变更但接口定义未更新；
7. 功能变更但功能树缺失；
8. 状态流变更但状态机未更新；
9. 缺少必要验收标准；
10. 必须确认的决定仍处于 pending。

红灯文档不能冻结。

---

## 7. 黄灯规则

出现以下情况时为黄灯：

1. 缺少非目标说明；
2. 缺少风险说明；
3. 缺少关联文档；
4. 缺少测试建议；
5. 缺少变更影响说明；
6. 文档内容过于抽象；
7. 缺少例子或反例；
8. 可能需要补充决定，但不是阻塞项。

---

## 8. 蓝灯规则

蓝灯表示 AI 或规则引擎提出建议，但人类尚未确认。

例如：

- AI 建议拆分功能；
- AI 建议补充验收标准；
- AI 建议转为决定；
- AI 建议更新技术方案；
- AI 建议生成测试规格。

蓝灯不等于错误，但应进入人类审查。

---

## 9. 黑灯规则

黑灯表示冲突或异常。

常见情况：

1. frozen 文档内容 Hash 改变；
2. YAML 与 HTML 不一致；
3. Git Diff 修改了规格文件但没有变更日志；
4. 文档状态与文件实际内容不一致；
5. 同一决定被不同文件记录为不同结果。

黑灯优先级高于红灯。

---

## 10. 冻结规则

文档可冻结条件：

```text
无黑灯
无红灯
Schema 通过
必填字段完整
必要决定已确认
当前 Hash 已计算
人类确认
```

冻结后写入：

- `status: frozen`
- `frozen_at`
- `frozen_hash`
- `reviewer`
- `reviewed_at`
- `review_result`

---

## 11. 解冻规则

frozen 文档需要修改时，必须进入：

```text
changing
```

并记录：

- change_reason；
- requested_by；
- requested_at；
- affected_specs；
- expected_result。

---

## 12. 问题转决定规则

当问题涉及工程取舍时，应转为决定。

例如：

- 是否放入 MVP；
- 是否使用某技术；
- 是否修改文档结构；
- 是否调整状态机；
- 是否改变主窗体布局。

转为决定后：

- 原问题关联 Decision ID；
- 决定进入 pending；
- 人类确认后写入 discussion-log；
- 必要时写入 change-log。

---

## 13. 状态机的产品意义

DeepSpec 的状态机不是形式主义。  
它的作用是让文档成为工程对象：

```text
可生成
可审查
可冻结
可变更
可追踪
可交接
```
