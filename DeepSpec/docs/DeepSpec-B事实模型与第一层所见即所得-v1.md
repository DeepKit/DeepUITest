# DeepSpec B 事实模型与第一层所见即所得 v1

> 日期：2026-05-14  
> 状态：当前机制定稿  
> 主题：B 的事实颗粒度、第一层所见即所得定义、LLM 与 DeepSpec 的责任边界。

---

## 1. 核心结论

DeepSpec 的 B 不是 A 的摘要，也不是一组 Markdown 文档。

B 是 `.deepspec` 下的规格化需求事实层，最小颗粒度应是：

```text
需求节点 + 关系边 + 来源证据 + 状态 + 人类决策
```

第一层的“所见即所得”不是代码已经和需求一致，而是：

```text
用户在 DeepSpec 中看到的三棵树、图表、问题和节点详情，
就是 B 中当前规格事实的可视化表达；
用户在页面上做的需求决策会写回 B，
并驱动 HTML / 三树 / 图表重新渲染。
```

第二层的“需求所见即所得”才是：

```text
代码结果与 B 中的需求事实一致。
```

因此应区分两级：

| 层次 | 所见即所得含义 | 是否检查代码 |
|---|---|---|
| 第一层 | B 中需求事实与可视化界面一致 | 否 |
| 第二层 | 代码实现结果与 B 中需求事实一致 | 是 |

DeepSpec 的双界面原则：

```text
AI 读 YAML；
人类看 HTML；
交互可以通过 Prompt / LLM 任务，也可以通过 HTML 页面点击；
但最终必须写回 B 中的 YAML 事实文件。
```

这意味着：

- YAML 是 AI 和 DeepSpec 的机器事实层；
- HTML 是人类的审阅、理解和决策层；
- Prompt / LLM 任务是 AI 交互入口；
- HTML 点击是人类交互入口；
- 两种交互都不能绕过 B，不能只改页面状态。

---

## 2. B 不是文档摘要

如果 B 只是文档摘要，会有三个问题：

1. 图表只能静态展示，不能可靠联动。
2. 用户决策无法精确写回某个需求事实。
3. 第二层无法用 B 作为代码一致性校正基准。

因此 B 应保存结构化事实，而不是保存给人看的长文本。

B 中长文本可以存在，但必须附着在结构化对象上：

- 功能节点；
- 模块节点；
- 视图节点；
- 角色；
- 权限；
- 场景；
- 状态；
- 规则；
- 来源证据；
- 问题；
- 决策。

---

## 3. B 的最小事实对象

### 3.1 需求节点

需求节点是三棵树和各种图表的共同对象。

最小字段：

```yaml
id:
tree: function | module | view
title:
summary:
kind:
status: candidate | confirmed | uncertain | rejected | superseded
confidence: low | medium | high
source_refs: []
decision_refs: []
issue_refs: []
```

注意：

- `status` 表示当前事实状态；
- `confidence` 表示来源和推断可靠性；
- `source_refs` 指向 A 或 B 中的证据；
- `decision_refs` 指向人类确认过的需求决策；
- `issue_refs` 指向缺口、冲突、歧义、低置信等问题。

### 3.2 关系边

三棵树不是孤立树，而是一个需求空间。

最小关系类型：

```yaml
- id:
  from:
  to:
  type: contains | depends_on | implements | presented_by | owned_by | constrained_by | conflicts_with | derived_from
  confidence:
  source_refs: []
  decision_refs: []
```

关键关系：

| 关系 | 含义 |
|---|---|
| `contains` | 树内父子关系。 |
| `presented_by` | 功能由哪个视图承载。 |
| `implements` | 功能挂接到哪个模块 / 能力域。 |
| `depends_on` | 节点依赖另一个节点。 |
| `constrained_by` | 功能受权限、规则、状态约束。 |
| `conflicts_with` | 两个事实互相冲突。 |
| `derived_from` | 事实从某个来源或推断生成。 |

功能-视图映射和功能-模块映射不必默认做成独立 P0 大图，但必须作为关系边存在。这样用户点击功能时，能看到相关视图、模块、规则、来源和问题。

### 3.3 来源证据

所有重要事实都应尽量能追溯来源。

```yaml
- id:
  source_layer: A | B
  path:
  lines:
  excerpt:
  note:
  confidence:
```

来源层级：

```text
A:原文解析
B:人工决策
B:AI推断
B:生成摘要
```

来源证据的目标不是证明 AI 一定正确，而是让人能判断：

- 这个需求从哪里来；
- 是原文明确写了，还是 AI 推断；
- 是否被人类决策覆盖；
- 是否和旧文档冲突。

### 3.4 人类决策

页面决策不是 UI 状态，而是需求事实的一部分。

决策必须能：

- 覆盖 AI 推断；
- 覆盖 A 中旧描述；
- 影响三棵树和图表；
- 进入后续 LLM 任务上下文；
- 在第二层作为 A/B 校正和代码一致性校正基准。

最小字段沿用 `DeepSpec-人类决策写回与AI影响机制-v1.md`：

```text
decision + rationale + source_refs + ai_instruction
```

## 4. 第一层所见即所得

第一层所见即所得的对象是 B。

标准流程：

```text
A 原始项目材料
  ↓
扫描 / 分类 / 初步解析
  ↓
框架 LLM 模块生成候选 B
  ↓
DeepSpec 校验候选 B
  ↓
DeepSpec 合并候选 B 到当前 B
  ↓
从 B 渲染三棵树、图表、问题和 HTML
  ↓
用户在 HTML 页面上点击并生成候选 Decision Record
  ↓
用户确认 Decision Record
  ↓
决策写回 B
  ↓
B 重新计算当前规格判断
  ↓
界面重新渲染
```

用户看到的界面必须满足：

1. 图上的节点能对应到 B 中的事实对象。
2. 图上的线能对应到 B 中的关系边。
3. 问题清单能对应到 B 中的问题对象。
4. 来源证据能追溯到 A 或 B。
5. 用户决策能写回 B，并影响后续显示。
6. Prompt / LLM 任务生成的是候选 B，必须经过 Schema 校验、来源检查、冲突检查后合并进 B。
7. HTML 页面点击先产生候选 Decision Record，用户确认后写入 B 的 `decisions/`，不能只存在前端状态中。
8. HTML 通过 JS Bridge 把点击事件交给 DeepShell / DeepSpec，真正写 YAML 的责任在宿主侧，不在 HTML 页面内。

如果图表只是一张静态 HTML，不可追溯、不可决策、不可重新生成，就不符合第一层所见即所得。

## 5. 第二层所见即所得

第二层所见即所得的对象是代码结果。

它回答：

```text
实际代码、UI、配置、测试结果，
是否和 B 中用户看到并确认的需求事实一致？
```

第二层新增能力：

- A/B 需求校正；
- `A 未同步` 队列；
- B -> A 需求修订 Prompt / Patch；
- 代码与需求一致性校正；
- Git Diff / Review Pack；
- 漂移检测；
- 规则回流；
- Handoff。

第二层不能脱离 B 重新判断需求。B 是用户已经看见、审阅、决策过的规格事实源。

## 6. LLM 与 DeepSpec 的责任边界

### 6.1 LLM 负责什么

第一层默认直接调用成熟的框架 LLM 模块。

LLM 负责生成候选 B：

- 从 A 中提取候选功能、模块、视图；
- 补充节点摘要、验收点、关系候选；
- 标注来源；
- 标注不确定性；
- 根据人类决策完善 B；
- 按 DeepSpec Schema 输出结构化结果。

LLM 不允许直接覆盖 B 的事实文件。它输出的是候选结果：

```text
LLM 候选输出
  ↓
Schema 校验
  ↓
来源检查
  ↓
冲突检查
  ↓
DeepSpec 合并
  ↓
写入 B
```

### 6.2 DeepSpec 负责什么

DeepSpec 不承诺语义一定正确。

DeepSpec 负责：

- 构建 LLM 任务上下文；
- 提供 Prompt 模板；
- 提供 Schema；
- 校验 LLM 输出；
- 发现缺字段、无来源、冲突、低置信；
- 将 LLM 候选结果合并进 B；
- 拒绝直接覆盖 B 的高优先级人工决策；
- 管理 B 的事实文件；
- 渲染三棵树、图表和 HTML；
- 记录人类决策；
- 追踪 B 与 A 的来源关系；
- 为第二层代码一致性校正提供稳定规格入口。

一句话：

```text
LLM 产出候选理解；
DeepSpec 让候选理解可验证、可追溯、可决策、可视化。
```

## 7. 对 MVP 的约束

MVP 不应追求完整需求管理系统。

MVP 的图表交互定为：

```text
图上只做需求决策，不直接编辑树节点和关系边。
```

允许的操作：

- 点击节点；
- 查看来源、问题、关系、状态、置信度；
- 生成候选 Decision Record；
- 用户确认后执行确认、否定、澄清、补口、裁决冲突；
- 生成 B 内审阅 LLM 任务；
- 决策写回 B 后重新渲染。

暂不做：

- 拖拽改树结构；
- 直接改节点标题和层级；
- 手工连线；
- 完整画布编辑器。
- HTML 页面自行保存事实状态。

原因：

```text
第一层是审阅和决策面板，不是通用需求编辑器。
```

B 的文件组织定为：

```text
project-spec.yaml 只做总索引和摘要；
事实拆到 trees/ relations/ evidence/ issues/ decisions/ 等目录；
不把全部事实塞进一个巨大 YAML；
MVP 不以数据库作为主要事实源。
```

这样可以同时满足：

- 人类可查看；
- AI 可消费；
- Git diff 可读；
- 局部重生成；
- 第二层可引用稳定事实对象。

MVP 必须先做稳：

1. B 的最小事实对象；
2. 三棵树节点与 B 事实对象的一一对应；
3. 图表关系与 B 关系边的一一对应；
4. 来源证据；
5. 问题清单；
6. 人类决策写回 B；
7. B 变化后 HTML / 三树重新渲染；
8. LLM 任务记录和可导出 Prompt。
9. 节点点击后的来源、问题、关系和决策面板。
10. HTML JS Bridge 事件到 DeepShell / DeepSpec 写回 B 的链路。
11. LLM 候选输出的校验、合并和拒绝覆盖机制。

MVP 可以暂缓：

- 完整权限系统；
- 完整状态机；
- 全语言静态分析；
- 自动改 A；
- 代码一致性校正；
- CLI 调度开发。

---

## 8. 定稿表述

后续对外和内部文档统一使用：

```text
第一层：需求可视化（包括建议）
含义：把 A 中散乱线性的项目材料，通过框架 LLM 模块生成 B，再把 B 中规格化需求事实渲染成可审阅、可追溯、可决策的三树与图表界面。

第一层所见即所得：
用户看到的需求图表，就是 B 中当前规格事实的可视化表达；用户在图上做的需求决策会写回 B 并改变后续显示。

第二层：需求所见即所得（代码与需求一致）
含义：以 B 为基准，检查和校正代码结果、A 中底层文档与当前需求事实的一致性。
```
