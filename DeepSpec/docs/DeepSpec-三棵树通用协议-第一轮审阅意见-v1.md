## 一、通过的部分

### 专家一（数据建模）

- **§4 节点通用 Schema**：基础字段设计合理，`id` / `tree` / `title` / `kind` 四个必需字段最小但充分。
- **§7 来源证据**：`source_layer` 四级分类覆盖了全部溯源场景，`referenced_by` 反向索引有利于交叉查询。
- **§10 ID 命名规范**：前缀+slug 格式可 grep、可读、可排序。
- **§13 版本演进策略**："新增可选字段不升版本号"的前向兼容策略正确。

### 专家二（LLM 工程）

- **§12 LLM 输出约束**：10 条约束清晰无歧义，特别是"不得把推断写成 status: confirmed"和"输出必须是合法 YAML"。
- **§11.1 宽松模式**：允许缺省非必需字段 + 自动补默认值，对 LLM 首次生成非常友好。
- **§16 最小可用 B 示例**：对 LLM few-shot prompting 很有帮助。

### 专家三（Delphi 实现）

- **§2 文件组织**：拆分为多个小文件，对内存友好。
- **§10 ID 命名规范**：ASCII slug + 前缀，Delphi 字符串处理无障碍。
- **§11 校验规则**：两模式规则都可编程实现。

### 专家四（产品架构）

- **§1 设计原则**："AI 读 YAML，人类看 HTML"的双界面原则贯穿始终。
- **§15 协议使用场景**：四个场景覆盖了 MVP 全部交互路径。
- **§11 严格/宽松模式切换**：以"是否已有人类决策"作为切换条件合理。

## 二、必须修改（7 项）

| # | 章节 | 问题 | 影响 |
|---|------|------|------|
| 1 | §4.1 | kind 枚举缺少扩展机制（custom 值或命名空间前缀） | 非结构化项目无法使用 |
| 2 | §4 | 节点缺少 `created_at` / `updated_at` 时间戳 | 无法做增量更新和过期检测 |
| 3 | §4 | 节点缺少 `version` 或 `content_hash` 用于乐观并发控制 | 多次 LLM 调用可能静默覆盖 |
| 4 | §4 | `source_layer` 枚举值包含冒号和中文，不适合作为程序枚举 | 解析和比较不便 |
| 5 | §9 | 决策类型与写回文档不一致（5 种 vs 12 种） | 实现时产生歧义 |
| 6 | §11.2 | 严格模式应为节点级而非全局级 | 不必要的更新阻塞 |
| 7 | §4.1 | kind 枚举值需声明精确拼写，供 Delphi 枚举映射 | 实现一致性 |

协议的整体架构设计扎实，设计原则清晰，与 B 事实模型和旁路查阅规范的一致性好。主要改进方向集中在**可扩展性**（kind 枚举、source_layer 格式）和**增量更新支持**（时间戳、版本标识、增量输出模式）。建议在开发启动前完成 7 项必须修改，10 项建议修改可以在首批迭代中逐步纳入。
