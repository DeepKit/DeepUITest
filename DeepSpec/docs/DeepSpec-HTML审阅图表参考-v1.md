# DeepSpec HTML 审阅图表参考 v1

> 日期：2026-05-14  
> 来源参考：https://thariqs.github.io/html-effectiveness/#code-review  
> 目的：保存 HTML effectiveness 文章中对 DeepSpec 有启发的图表形态，后续用于设计 DeepSpec 的 HTML 审阅页。

---

## 1. 参考结论

HTML 的价值不只是“排版更漂亮”，而是能把线性文字表达不了的结构、关系、风险、路径和审阅重点做成可扫视、可跳转、可对照的图表。

对 DeepSpec 来说，这一点非常关键：

**DeepSpec 不是把 Markdown 渲染成 HTML，而是把项目中的开发材料读成立体需求图。**

---

## 2. 三类值得借鉴的 HTML 图表

### 2.1 Annotated PR

原文中的作用：

- 展示代码 diff；
- 标注风险；
- 做行级批注；
- 给 reviewer 指出重点位置；
- 让审查者不用从大段文字里找问题。

DeepSpec 后续可借鉴为：

**Annotated Spec Review / Annotated Requirement Review**

用于展示：

- 某个需求节点来自哪些文档；
- 哪些描述有冲突；
- 哪些字段缺失；
- 哪些部分是 AI 推断；
- 哪些地方需要用户确认；
- 可复制给原 AI 工具的修正 Prompt。

### 2.2 PR Writeup

原文中的作用：

- 给 reviewer 一份结构化说明；
- 说明为什么改；
- 改了哪些文件；
- Before / After；
- 重点审查区域；
- 测试计划。

DeepSpec 后续可借鉴为：

**Requirement Writeup / Spec Review Pack**

用于展示：

- 当前项目的需求总览；
- 人类想法被整理成了哪些主题；
- 哪些是 P0/P1；
- 哪些需求已经有来源；
- 哪些需求仍然缺少上下文；
- 下一步应该让原 AI 工具补什么文档。

### 2.3 Module Map

原文中的作用：

- 用盒子和箭头展示模块；
- 展示依赖、入口、调用路径、热点路径；
- 把代码结构从文字变成空间结构。

DeepSpec 后续可借鉴为：

**Requirement Map / Feature-View Map / Concept Map**

用于展示：

- 用户目标；
- 业务能力；
- 功能分组；
- 页面/界面区域；
- 角色与使用场景；
- 需求之间的依赖；
- 需求到界面的映射。

## 3. 当前暂不讨论的部分

以下内容重要，但不是当前优先讨论点：

- AI 生成代码后的实现差异；
- Git Diff；
- Review Pack；
- 设计-实现一致性检查；
- CLI 调度开发；
- 自动测试和回滚。

这些属于第二层和第三层能力。

当前优先讨论第一层：

**人类脑中的想法已经通过其他 AI 对话沉淀在项目材料里，DeepSpec 如何把它读出来，变成图表化、可审阅、可理解的需求表达。**

---

## 4. 对 DeepSpec 第一层的启发

第一层不应只是：

```text
文件树 + Markdown 预览
```

而应该是：

```text
项目材料
  ↓
需求理解
  ↓
需求图表
  ↓
人类审阅
  ↓
提示词回到原 AI 工具补文档
```

核心不是代码审查，而是需求表达审查。

---

## 5. 后续要设计的图表

本节是 HTML 表现形态参考，第一层图表优先级以 `DeepSpec-第一层图表体系定稿-v2.md` 为准。

按 v2 修正后，当前第一层优先表达为：

1. 三棵树：功能树、模块树 / 系统结构树、视图树 / UI 界面树；
2. 需求总览图；
3. 来源证据图；
4. 需求健康图；
5. 当前文档状态总览图；
6. 用户路径 / 场景流图；
7. 角色权限矩阵；
8. 术语与对象关系图。

功能-视图、功能-模块关系优先作为三棵树节点的挂接和联动能力，不默认作为独立 P0 大图。

这些图表的目标是：

**把人类需求从线性文字变成立体图表，让用户看见“自己到底让 AI 理解成了什么”。**
