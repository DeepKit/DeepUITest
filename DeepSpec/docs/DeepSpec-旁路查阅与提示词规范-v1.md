# DeepSpec 旁路查阅、LLM 上下文与提示词规范 v1

> 日期：2026-05-14  
> 目标：明确 DeepSpec 如何在不替代用户原 AI/IDE 工具的前提下，提供更好的查阅界面、框架 LLM 调用上下文和提示词导出。

---

## 1. 核心原则

**DeepSpec 只做旁路查阅、LLM 上下文增强和提示词导出，不接管主开发链路。**

双界面原则：

```text
AI 读 YAML；
人类看 HTML；
交互可以通过 Prompt / LLM 任务，也可以通过 HTML 页面点击；
所有交互结果最终写回 B 中的 YAML 事实文件。
```

用户原工作流保持不变：

```text
IDE / Claude Code / Cursor / Codex / 终端 / Git
        ↓
继续讨论、写代码、改文档、提交
```

DeepSpec 旁路工作流：

```text
读取同一个项目目录
        ↓
组织文件、三树、问题、证据
        ↓
生成 HTML/VCL 查阅界面
        ↓
用户通过 HTML 页面点击生成候选 Decision Record
        ↓
用户确认后写入需求决策文档和 AI 上下文
        ↓
生成 B 生成 / 审阅任务上下文
        ↓
调用框架 LLM 模块生成候选 B
        ↓
DeepSpec 校验并合并候选 B
        ↓
保留可复制 Prompt 作为导出和兜底
```

## 2. DeepSpec 提供的查阅界面

| 界面 | 用途 |
|---|---|
| 文件分类页 | 看项目里有哪些文档、代码、UI、配置、AI 规则文件。 |
| 扫描报告页 | 看项目类型、文件数量、解析结果、警告。 |
| 功能树 | 看 AI/规则理解出的产品能力。 |
| 模块树 | 看代码和目录结构。 |
| 视图树 | 看 UI/窗体/页面/控件层级。 |
| 节点详情页 | 看来源、属性、关联、置信度、问题。 |
| 问题页 | 看文档缺口、歧义、冲突、无证据节点。 |
| LLM 任务页 / 提示词导出页 | 调用框架 LLM 模块执行 A -> B 生成 / 审阅任务；必要时复制 Prompt 给外部 AI。 |

## 3. LLM 任务与提示词类型

### 3.1 Context Pack

用于让框架 LLM 模块或外部 AI 工具理解当前项目材料。

回答：

```text
这个项目是什么？
当前看到的结构是什么？
三棵树分别说明了什么？
哪些内容是确定的？
哪些内容不确定？
这次请 AI 做什么？
不要做什么？
完成后需要汇报什么？
```

Context Pack 的来源优先级：

```text
以 B 为主，按需引用 A。
```

其中：

- B 是 `.deepspec` 下的规格化事实源，包括 `project-spec.yaml`、三棵树、问题、决策和 AI 上下文；
- A 是用户原有需求文档目录 / 原始项目材料；
- Prompt 模板应要求 AI 优先遵守 B 中的 accepted decisions 和三棵树；
- 只有需要证据、原文语境或冲突说明时，才引用 A 中的来源片段。

### 3.2 A -> B 生成 / 审阅任务

用于通过框架 LLM 模块调用用户配置或已有的 AI 能力，根据 A 生成或完善候选 B，而不是直接修改 A 或直接覆盖 B。Prompt 是该任务的模板和可导出形态。

回答：

```text
当前 A 中哪些内容支撑 B？
B 中哪些节点低置信、缺来源或需要人工确认？
应如何重新生成或完善 B 中的功能、模块、视图、验收标准？
输出必须作为候选结果，等待 DeepSpec 校验和合并。
不要直接修改 A，除非用户进入第二层校正流程。
```

### 3.3 节点审阅任务

用于针对某个功能、模块、视图节点，让框架 LLM 模块完善 B 中的节点表达。

回答：

```text
当前节点是什么？
DeepSpec 从哪里推断出来？
为什么置信度低或有冲突？
请在 B 中补充什么？若要改 A，进入第二层代码与需求校正流程。
```

### 3.4 AI 规则草稿

用于生成或优化：

- `AGENTS.md`
- `CLAUDE.md`
- Cursor Rules
- Handoff
- 任务说明草稿

### 3.5 决策写回任务

用于把用户在 DeepSpec 页面上的决策，交给框架 LLM 模块完善 B。若要修改 A，属于第二层代码与需求校正能力。Prompt 仍可导出给外部 AI。

回答：

```text
用户做了什么需求决策？
该决策覆盖哪些旧描述？
涉及哪些功能树、模块树、视图树节点？
应该如何更新 B 中的规格化事实？
该更新必须作为候选结果，等待 DeepSpec 校验和合并。
若进入第二层，才判断应修改哪些 README / 需求 / 设计 / 规则文件。
后续 AI 撰写需求时必须遵守什么？
```

## 4. Context Pack 模板

```markdown
# Context Pack

## 1. 项目

项目名称：
项目路径：
项目类型：
扫描时间：

## 2. 当前 DeepSpec 理解

### 功能树摘要

### 模块树摘要

### 视图树摘要

## 3. 来源材料

### 关键文档

### 关键代码

### 关键 UI 文件

### AI 规则文件

## 4. 当前问题

### 高风险

### 中风险

### 低置信度

### 无来源证据

## 5. 本次任务

请根据以上信息生成或审阅 DeepSpec 的规格化需求目录 B，使功能、模块、视图、问题和来源证据更清楚。

## 6. 只允许修改

- `.deepspec/trees` 中的功能树、模块树、视图树；
- `.deepspec/issues` 中的问题记录；
- `.deepspec/decisions` 中由用户确认的决策上下文；
- `.deepspec/prompts` 和 `.deepspec/llm` 中的 AI 消费层记录；
- 用户明确允许的其他 B 内文件。

## 7. 不要修改

- 不要修改 A 中的 README / 需求文档 / 设计文档 / AI 规则文件；
- 不要修改 `.deepspec/html` 下生成的 HTML；
- 不要直接改业务代码，除非用户另行要求；
- 不要推翻已明确写入文档的决定。

## 8. 完成后请输出

- 修改文件列表；
- 每个文件改了什么；
- 哪些问题被解决；
- 哪些问题仍然需要用户确认；
- 是否影响功能树、模块树、视图树。
```

## 5. B 生成 / 审阅 Prompt 模板

```markdown
# B 生成 / 审阅任务

你正在帮助我根据项目原始材料 A 生成或完善 DeepSpec 的规格化需求目录 B。不要直接修改 A 中的 README、需求文档、设计文档或代码；目标是让 B 中的功能树、模块树、视图树、问题和来源证据更清楚。

## 当前问题

{{doc_issues}}

## 相关来源

{{source_refs}}

## 请执行

1. 根据 A 的来源材料，完善 B 中的功能、模块、视图、来源和问题。
2. 补充缺失的功能说明、模块职责、界面层级、验收标准或不做事项。
3. 对冲突描述给出候选判断，但不要把推断写成用户已确认事实。
4. 对不确定内容标注为“待确认”，不要编造已确认事实。
5. 输出符合 DeepSpec Schema 的内容。

## 不要做

- 不要修改 A 中的原始 README、需求文档、设计文档或代码。
- 不要修改生成的 `.deepspec/html` 文件。
- 不要大规模重构代码。
- 不要删除历史决定。
- 不要把推断内容写成已确认事实。

## 输出

请列出：

- 建议更新或已更新哪些 B 内文件 / 记录；
- 每个 B 内文件 / 记录解决了哪些问题；
- 仍需用户确认的问题；
- 建议重新运行 DeepSpec 扫描的理由。
```

```markdown
# 节点审阅任务

DeepSpec 在项目中识别出以下节点，但该节点存在低置信度、来源不足或描述不完整的问题。

## 节点

类型：{{tree_type}}
名称：{{node_title}}
摘要：{{node_summary}}
状态：{{status}}
置信度：{{confidence}}

## 来源

{{source_refs}}

## 问题

{{issues}}

## 请帮助优化 B 中的节点表达

请根据 A 中来源材料，在 B 的功能树、模块树、视图树或问题记录中补充该节点的明确说明，包括：

- 它是什么；
- 为什么需要它；
- 它和哪些模块或界面有关；
- 它的边界和不做事项；
- 如果是功能，请补充验收标准；
- 如果是模块，请补充职责边界；
- 如果是视图，请补充用户看到的界面结构。

不要直接修改 A 中的原始文档，也不要直接修改生成的 HTML。
```

## 9. LLM 任务和提示词生成规则

1. 必须引用来源文件，不要只给抽象建议。
2. 必须区分“已确认事实”和“DeepSpec 推断”。
3. 必须提醒 AI 完善 B，不直接修改 A 或生成视图。
4. 必须列出不允许修改的文件范围。
5. 必须要求 AI 输出修改摘要和仍需确认的问题。
6. 对低置信度节点，必须要求 AI 不要把推断写成事实。
7. 如果包含人类 accepted decision，必须要求 AI 以该 decision 为准；当旧文档冲突时，以 decision 为准并说明被覆盖的旧描述。

## 10. 决策写回 Prompt 模板

```markdown
# B 决策写回任务

你正在根据 DeepSpec 中的人类决策完善 B 中的规格化需求事实。请注意：这些 accepted decision 是用户确认过的需求事实，优先级高于 A 中旧文档的冲突描述。不要直接修改 A，除非用户进入第二层代码与需求校正流程。

## 人类决策

{{requirement_decisions}}

## 涉及节点

{{target_nodes}}

## 来源与旧描述

{{source_refs}}

## DeepSpec 判断

{{issues_and_rationale}}

## 请执行

1. 找到 B 中应更新的树节点、决策记录、AI 上下文或审阅摘要。
2. 将 accepted decision 写入 B 的合适位置。
3. 如果 A 的旧文档与 accepted decision 冲突，在 B 中标记 A 未同步 / A 有旧描述。
4. 保留决策理由、范围、优先级、影响节点。
5. 不要把 rejected、superseded 或待确认内容写成当前事实。
6. 不要直接修改业务代码，除非用户另行要求。

## 输出

请列出：

- 修改了哪些文件；
- 每个文件写入了哪些决策；
- 覆盖了哪些旧描述；
- 仍需用户确认的问题；
- 是否需要重新运行 DeepSpec 扫描。
```

## 11. 结论

DeepSpec 的 LLM 任务不是聊天入口，而是旁路查阅界面的自然延伸：

```text
看见问题
  ↓
用户决策
  ↓
写入决策文档和 AI 上下文
  ↓
调用框架 LLM 模块
  ↓
生成 / 完善 B
  ↓
重新渲染三树和 HTML 审阅界面
  ↓
必要时导出 Prompt 给外部 AI
```
