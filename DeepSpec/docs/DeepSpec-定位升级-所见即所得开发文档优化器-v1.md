# DeepSpec 定位升级：所见即所得的开发文档优化器 v1

> 日期：2026-05-14  
> 状态：定位升级讨论稿  
> 上一版定位：AI 开发前的规格审阅器  
> 新定位：所见即所得的开发文档优化器  
> 产品形态补充：DeepSpec 是用户原有 AI/IDE 工作流旁边的旁路工具，不接管主开发链路。

---

## 1. 新的一句话定位

**DeepSpec 是一个所见即所得的开发文档优化器：它作为用户原有 AI/IDE 工作流旁边的旁路工具，读取项目中的开发文档、代码、配置和 UI 文件，提供更好的查阅界面和相关提示词，帮助用户用自己的 AI 生成结构化规格、发现文档缺口、歧义和不一致，并回到底层文件持续优化。**

更短表达：

**DeepSpec 在不替代原有工具的前提下，让开发文档从“写给人看的文本”，升级为“人能审阅、AI 能执行的规格界面”。**

---

## 1.1 旁路工具原则

DeepSpec 不应该成为用户开发工作流中的强制入口，而应该作为旁路增强层存在：

```text
用户原工作流：
IDE / Claude Code / Cursor / Codex / 终端 / Git
        ↓
继续讨论、写代码、改文档、提交

DeepSpec 旁路：
读取同一个项目目录
        ↓
提供更好的查阅界面
        ↓
生成上下文包和提示词
        ↓
用户把提示词交给原来的 AI 工具
        ↓
AI 帮用户优化底层文件
```

旁路意味着：

- 不要求用户迁移到 DeepSpec；
- 不要求用户在 DeepSpec 里聊天；
- 不要求用户在 DeepSpec 里写代码；
- 不要求用户把项目托管到 DeepSpec 平台；
- DeepSpec 只读取项目材料、组织信息、渲染视图、生成提示词；
- 真正的修改仍发生在用户原来的 IDE、AI CLI、Cursor、Claude Code、Codex 或 Git 工作流中。

---

## 2. 为什么要从“规格审阅器”升级

“规格审阅器”描述了 DeepSpec 的一个动作：把 AI 理解结果拿出来审阅。

但它还不够完整，因为 DeepSpec 的真正闭环不是停在审阅，而是：

```text
旁路读取底层开发文档
        ↓
提供上下文包和提示词
        ↓
用户原 AI 工具生成结构化规格
        ↓
渲染所见即所得审阅界面
        ↓
暴露文档缺口、歧义、冲突
        ↓
用户用自己的 AI 优化底层文件
        ↓
重新生成规格界面
```

所以 DeepSpec 的价值不是“看一眼规格”，而是**持续优化开发文档质量**。

---

## 3. 产品本质

DeepSpec 不是：

- PRD 生成器；
- AI IDE；
- 代码生成器；
- 在线协作需求管理系统；
- 树结构编辑器。

DeepSpec 是：

- 开发文档质量检查器；
- AI 理解结果可视化器；
- 结构化规格生成器；
- HTML/VCL 审阅界面生成器；
- 原 AI/IDE 工作流旁边的查阅与提示词增强器；
- AI 开发前的文档优化闭环工具。

---

## 4. “所见即所得”具体指什么

这里的“所见即所得”不是传统 Word/WYSIWYG 编辑器含义，而是开发流程含义：

| 用户看到的 | 实际得到的 |
|---|---|
| 功能树 | AI 对产品意图的结构化理解 |
| 模块树 | AI 对系统拆分和职责边界的理解 |
| 视图树 | AI 对界面、窗体、页面、控件层级的理解 |
| HTML 审阅页 | 人类可快速检查的产品规格界面 |
| YAML 规格 | AI 后续开发可消费的机器事实源 |
| 问题列表 | 底层文档需要优化的地方 |

用户看到的不再是一堆 Markdown 段落，而是 AI 将要据此开发的软件规格轮廓。

如果界面上看到的功能、模块、视图是错的，说明底层文档需要修正；如果看到的是对的，AI 后续开发才有更稳定的输入。

---

## 5. 新核心痛点

旧表述：

**开发文档非所见即所得。**

升级后表述：

**开发文档不是可执行规格，AI 读完以后到底理解成什么，用户看不见。**

DeepSpec 要解决的是：

1. 文档散乱，用户不知道 AI 会抓住哪些信息；
2. 文档有歧义，AI 理解错了但用户事前看不出来；
3. 文档和代码/UI 不一致，AI 会把冲突继续放大；
4. Markdown 太线性，不适合审阅功能、模块、视图这种结构信息；
5. AI 编码太快，缺少一个“开发前确认 AI 理解”的中间层。

## 7. MVP 定义调整

### 7.1 旧 MVP 核心

读取项目材料，生成三棵树 YAML，渲染 HTML 审阅页。

### 7.2 新 MVP 核心

读取项目材料，生成三棵树 YAML 和文档问题清单，渲染成所见即所得审阅界面，并输出可交给用户 AI 的文档优化 Prompt。

新增重点：

| 能力 | 说明 |
|---|---|
| 文档问题清单 | 标记缺失、冲突、歧义、低置信度、无来源证据。 |
| 优化 Prompt | 根据问题清单生成给 Claude/Codex/Cursor/用户 CLI 的修正文档 Prompt。 |
| 前后对比 | 重新生成后对比三棵树变化和问题减少情况。 |
| 来源证据 | 每个节点尽量关联到原文件路径和片段摘要。 |
| 文档健康度 | 用简单指标表达当前开发文档是否足够支撑 AI 开发。 |
| Fog 探索 | 承认需求终点可能在"雾里"：节点 `fog_state`（clear→misty→foggy→unknown_unknowns 单向收敛）+ 探索 ticket（research/prototype/grilling）+ problems 页 Fog Map 可视化。一次只解一个 ticket 以保护 AI context。详见协议 §Fog 探索模型。 |

## 8. YAML Schema 需要增加的问题层

除了三棵树，MVP 应增加 `doc_issues`：

```yaml
doc_issues:
  - id: issue.auth.001
    severity: high
    type: missing_requirement # missing_requirement | conflict | ambiguity | stale_doc | no_source | low_confidence | research_ticket | prototype_ticket | grilling_ticket | fog_unknown
    title: 登录失败后的处理规则缺失
    description: 文档提到用户登录，但未说明密码错误、账号不存在、网络失败时的交互。
    affected_nodes:
      - feature.auth.login
      - view.login_form
    source_refs:
      - path: README.md
        note: 只描述了登录入口，没有描述失败分支
    suggested_fix_prompt: |
      请补充登录失败场景的需求说明，包括错误类型、用户提示、重试策略和验收标准。
```

这让 DeepSpec 从“规格展示”升级为“文档优化器”。

## 9. HTML 审阅界面升级

原来页面：

- 总览页；
- 功能树页；
- 模块树页；
- 视图树页；
- 对照页；
- 问题页。

升级后，首页应围绕“文档优化”组织：

| 区域 | 作用 |
|---|---|
| 文档健康度 | 当前材料是否足够让 AI 开发。 |
| 高风险问题 | 影响开发正确性的缺失、冲突、歧义。 |
| 三树预览 | AI 当前理解出的产品、模块、视图轮廓。 |
| 无证据节点 | AI 推断出来但底层文件没有明确支撑的内容。 |
| 冲突来源 | 不同文件中互相矛盾的描述。 |
| 优化 Prompt | 一键复制给用户 AI，让它修底层文件。 |
| 前后变化 | 文档优化后，规格结构发生了什么变化。 |

## 10. 产品口号

候选口号：

1. **让开发文档所见即所得。**
2. **先看清 AI 理解了什么，再让 AI 写代码。**
3. **把散乱开发文档，优化成 AI 可执行规格。**
4. **让文档从文本，变成规格界面。**
5. **开发前，先优化 AI 能读懂的文档。**

推荐主口号：

**让开发文档所见即所得。**

推荐副口号：

**先看清 AI 理解了什么，再让 AI 写代码。**

## 11. 与蓝海判断的关系

这个升级会让 DeepSpec 的差异更清楚。

如果定位是“AI 开发前的规格审阅器”，容易被理解成 Kiro / Spec Kit / PRD 生成器的附属功能。

如果定位是“所见即所得的开发文档优化器”，差异会更明显：

- 它优化的是用户已有开发文档；
- 它不替代用户原来的 AI 工具；
- 它用 HTML/VCL 把 AI 理解变成可见界面；
- 它用问题清单和优化 Prompt 驱动底层文件改进；
- 它让开发文档成为 AI 开发前的稳定输入层。

新的蓝海楔子是：

```text
开发文档质量优化
    ×
AI 理解可视化
    ×
所见即所得规格界面
    ×
用户原 AI 工作流
```

---

## 12. 当前结论

DeepSpec 的定位应升级为：

**所见即所得的开发文档优化器。**

它的第一性价值是：

**让用户在 AI 写代码前，看见并优化 AI 将要依据的开发文档。**

三棵树、YAML、HTML、VCL TreeView、Prompt、CLI/API key 都是实现这个目标的手段。
