# DeepSpec 第一层图表体系定稿 v2

> 日期：2026-05-14  
> 状态：替代 v1，作为当前第一层图表体系权威版本  
> 修正来源：继续讨论后确认，功能-视图、功能-模块关系优先由三棵树本身表达，不应为了“画图”额外制造独立图表。  
> 二次修正：第一层首页不是判断“闭环与否”，而是呈现当下项目文档被 DeepSpec 读出的可视化状态，并给出文档优化建议和提示词要点。  
> 当前范围：只讨论“人类需求如何从项目材料中被图表化表达”，暂不讨论 AI 生成代码后的实现一致性。

---

## 1. 核心修正

v1 的问题是把两类关系图升得过高：

- 功能-视图映射图；
- 功能-模块映射图。

现在修正为：

```text
功能-视图关系 = 视图树天然挂在功能树上的关系
功能-模块关系 = 模块树天然挂在功能树上的关系
```

因此它们不再作为默认 P0 独立大图，而是三棵树节点的关联属性、筛选条件和局部联动视图。

只有当项目很复杂、树形联动已经看不清关系时，才按需生成局部关系图或覆盖检查表。

---

## 2. 三棵树不是普通图表

DeepSpec 第一层的骨架是三棵树：

```text
功能树 = 需求本体
模块树 = 功能树中“实现组织/系统结构”部分的简化表达
视图树 = 功能树中“交付界面/UI 意图”部分的简化表达
```

三棵树不是额外图表，而是需求空间的主结构。

其中：

- 功能树回答：这个软件要做什么？
- 模块树回答：这些能力准备由哪些系统模块、服务、能力域承接？
- 视图树回答：用户会在哪些界面、页面、区域、入口中感知和使用这些能力？

视图树和模块树都不是第四套模型，它们是功能树的两个投影。

---

## 3. 第一层图表的新原则

第一层图表只解决三棵树本身不擅长表达的问题：

```text
来源证据
问题健康
时间顺序
角色权限
状态变化
术语对象
规则约束
```

不再为已经挂在树上的关系额外做固定大图。

判断标准：

| 类型 | 是否应固定成独立图 | 原因 |
|---|---|---|
| 功能树本体 | 是 | 需求本体需要一屏总览。 |
| 模块树 / 系统结构树 | 否，作为第二棵树 | 它本身就是主结构。 |
| 视图树 / UI 界面树 | 否，作为第三棵树 | 它本身就是主结构。 |
| 功能-视图映射 | 默认否 | 关系已挂在视图树和功能节点上。 |
| 功能-模块映射 | 默认否 | 关系已挂在模块树和功能节点上。 |
| 来源证据 | 是 | 树本身不能说明 AI 为什么这样理解。 |
| 需求健康 / 问题 | 是 | 树本身不能聚合风险、冲突和缺口。 |
| 用户路径 / 场景流 | 是 | 树表达层级，不表达时间顺序。 |
| 角色权限矩阵 | 条件必需 | 多角色、多权限项目必须有。 |
| 状态转换图 | 条件必需 | 有生命周期、任务状态、审批状态时必须有。 |
| 术语与对象关系图 | 条件必需 | 概念密集项目必须有。 |

## 4. 当前定稿：三树 + 四类固定图 + 三类条件图

### 4.1 P0 结构骨架

P0 结构骨架是三棵树：

| 结构 | 定位 | 说明 |
|---|---|---|
| 功能树 | 需求本体 | 所有需求节点的主事实树。 |
| 模块树 / 系统结构树 | 实现组织投影 | 功能挂在模块、服务、能力域、数据对象上。 |
| 视图树 / UI 界面树 | 交付界面投影 | 功能挂在页面、窗口、区域、组件意图、入口上。 |

注意：

模块树和视图树要能反查功能，但反查不等于必须另画“功能-模块映射图”或“功能-视图映射图”。

### 4.2 P0 固定图表

第一层固定图表收敛为四类：

| 优先级 | 图表 | 挂载位置 | 定位 |
|---|---|---|---|
| P0 | 需求总览图 | 功能树 | 功能树的图表化表达，一屏看懂需求本体。 |
| P0 | 来源证据图 | 三棵树节点 | 说明每个节点从哪些材料、片段、AI 规则中来。 |
| P0 | 需求健康图 | 三棵树问题聚合 | 聚合缺失、冲突、模糊、低置信度、无来源、孤岛。 |
| P0 | 当前文档状态总览图 | 功能树 + 模块树 + 视图树 + 来源 + 问题 + 建议 | 项目首页总控，呈现当下文档状态、问题类型、修改建议和提示词要点。 |

### 4.3 P1 条件必需图表

这些图不是每个项目都必须固定出现，但一旦材料中存在对应复杂度，就应该生成：

| 优先级 | 图表 | 触发条件 | 定位 |
|---|---|---|---|
| P1 | 用户路径 / 场景流图 | 有明确用户任务、操作流程、业务路径 | 表达时间顺序、任务路径和断点。 |
| P1 | 角色权限矩阵 | 有角色、权限、只读/可写/审批/配置差异 | 表达谁能看、谁能做、谁能批准。 |
| P1 | 术语与对象关系图 | 有大量业务对象、术语、别名、概念关系 | 统一概念，避免同词异义和多词同义。 |

### 4.4 P2 条件扩展图表

这些图很重要，但不应压到第一版固定入口：

| 优先级 | 图表 | 触发条件 | 定位 |
|---|---|---|---|
| P2 | 状态转换图 | 有订单、任务、工单、审批、连接、同步等状态生命周期 | 表达状态、事件、条件、异常出口。 |
| P2 | 规则 / 决策表 | 有价格、校验、准入、策略、条件分支 | 表达复杂规则，避免散落在长文本里。 |
| P2 | 接口 / 集成关系图 | 有外部系统、API、插件、文件交换 | 表达系统边界和集成点。 |
| P2 | 变更影响图 | 用户准备修改某个需求节点时 | 表达该修改会影响哪些功能、模块、视图和文档。 |

## 5. 每张固定图的定义

### 5.1 需求总览图

本质：

```text
需求总览图 = 功能树的图表化表达
```

它和功能树是同一批内容，不是第四棵树，也不是三棵树汇总。

应显示：

- 产品目标；
- 核心用户；
- 功能域；
- 子功能；
- 叶子需求；
- 业务规则；
- 异常和边界；
- 关键未决问题；
- 低置信度区域；
- 缺来源区域。

核心交互：

- 按层级折叠；
- 只看问题节点；
- 点击节点打开详情；
- 查看来源片段；
- 查看相关模块树节点和视图树节点；
- 生成“补充/澄清/拆分该功能”的 B 内审阅提示词要点。

### 5.2 来源证据图

回答：

```text
这些需求是从哪里来的？
哪些材料被有效吸收？
哪些节点没有明确来源？
```

应显示：

- 文件列表；
- 每份材料贡献的节点数量；
- 来源片段；
- 来源覆盖率；
- 未被吸收的材料；
- 无来源节点；
- 同一来源被多个节点复用的情况。

核心交互：

- 点击材料，过滤相关树节点；
- 点击来源片段，定位到节点；
- 标记“无来源推断”；
- 生成“重新阅读某材料 / 补齐遗漏 / 移除无依据推断”的 B 内审阅提示词要点。

### 5.3 需求健康图

回答：

```text
当前需求表达哪里不健康？
哪些地方最需要用户和 AI 回去修文档？
```

它合并以下审阅价值：

- 缺来源；
- 表述模糊；
- 需求冲突；
- 颗粒度不一致；
- 业务规则缺失；
- 异常流程缺失；
- 模块归属不清；
- 界面承载不清；
- 孤岛节点；
- 低置信度节点。

注意：

“模块归属不清”和“界面承载不清”先作为健康问题出现，不默认画成功能-模块或功能-视图大图。

核心交互：

- 按严重程度筛选；
- 点击问题进入对应树节点；
- 查看问题原因和来源证据；
- 生成“修复该类问题 / 修复单个问题”的 B 内审阅提示词要点。

### 5.4 当前文档状态总览图

定位：

**第一层项目首页总控图。**

它不是需求总览图，也不是验收矩阵。

需求总览图回答：

```text
当前项目文档被 DeepSpec 理解成了哪些需求？
```

当前文档状态总览图回答：

```text
这些需求在当下文档中表达得怎么样？
哪里不清晰？
哪里有缺口？
哪里互相冲突？
用户应该怎么让自己的 AI 完善 B？如果要修改 A，则进入第二层代码与需求校正流程。
```

它的重点不是判断“闭环 / 不闭环”，而是呈现当前文档状态，并把问题转成用户可以带回 Claude / Cursor / Codex / IDE AI 的沟通要点。

建议形态：

| 功能域 / 功能点 | 当前表达状态 | 来源依据 | 模块表达 | 视图表达 | 权限表达 | 问题类型 | 修改建议 | 提示词要点 |
|---|---|---|---|---|---|---|---|---|
| 项目导入 | 基本清楚 | README + 设计文档 | 有模块意图 | 有入口描述 | 未说明 | 权限缺口 | 补充谁能导入、失败后如何处理 | 请补充项目导入的角色权限、异常流程和来源依据 |
| 文档扫描 | 部分清楚 | 来源分散 | 有模块意图 | 视图入口不完整 | 管理员/开发者 | 表达缺口 | 说明扫描入口、扫描结果展示和异常反馈 | 请把文档扫描的 UI 入口、结果区、失败提示写入设计文档 |
| 报告导出 | 不清楚 | 无明确来源 | 有模块意图 | 缺界面入口 | 未说明 | 无来源 + UI 缺口 | 确认是否是有效需求；若有效，补来源和界面说明 | 请确认报告导出是否属于 P0 功能，并补充来源、界面入口和导出格式 |

核心交互：

- 点击单元格跳到对应树节点或问题；
- 筛选需求不清晰；
- 筛选表达缺口；
- 筛选表达冲突；
- 筛选权限未说明需求；
- 查看 DeepSpec 的建议理由；
- 复制单个问题的提示词要点；
- 生成某个功能域的一揽子 B 内审阅提示词。

行粒度：

- 默认按功能域汇总，保证首页可扫视；
- 展开后显示功能点；
- 继续展开后进入具体树节点和问题详情；
- 不默认按所有叶子节点铺满首页，避免第一屏信息过碎。

提示词显示策略：

- 首页显示结构化提示词要点；
- 要点至少包括节点路径、当前表达、问题判断、来源依据、建议修改方向；
- 点击后展开完整 Prompt；
- 完整 Prompt 面向用户自己的 Claude / Cursor / Codex / IDE AI，不要求用户迁移到 DeepSpec 内聊天。

人类决策：

- 用户可以在页面上对问题做决策，而不只是查看问题；
- 页面决策包括确认、否定、澄清、补口、冲突裁决、范围裁剪、优先级、术语归一、视图归属、模块归属、权限决策；
- 决策不是临时 UI 状态，必须写入 `.deepspec` 下可追溯的规格化需求文档和结构化 Decision Log；
- accepted decision 在后续 AI 需求撰写时优先于旧文档；
- 第一层可生成 B 内审阅提示词、规则草稿和文档片段；
- 让用户自己的 AI 按决策修改 README、需求文档、设计文档或 AI 规则文件属于第二层代码与需求校正能力；
- DeepSpec 不未经用户确认直接覆盖原始开发文档。
- 树节点应显示来源层级标签：`A:原文解析`、`B:人工决策`、`B:AI推断`、`B:生成摘要`；
- A 与 B 冲突时，主视图显示 B 的当前规格判断，同时标记 A 未同步或 A 有旧描述。
- 来源层级标签必须参与筛选；
- `B:AI推断` 可以进入图表，但必须低置信 / 待确认，不能覆盖人工决策；
- `A 未同步` 在第一层作为状态标签显示；专门待办队列、Prompt / Patch 属于第二层代码与需求校正能力。

状态表达：

- 状态以文字为主，颜色只做轻量辅助；
- 不使用单纯红黄绿替代判断，避免把第一层误解成验收打分；
- 建议状态包括：清楚、部分清楚、不清楚、表达冲突、表达缺口、无来源、待确认。

问题暴露层级：

- 首页只显示问题大类，保持可扫视；
- 展开后再拆到需求、视图、模块、权限、来源、术语等具体维度；
- 首页问题大类建议包括：需求不清晰、表达缺口、表达冲突、无来源、权限未说明、待用户确认；
- 详情层再说明是功能描述缺失、UI 入口缺失、模块归属不清、权限规则缺失、术语歧义，还是来源证据不足。

## 6. 角色权限矩阵为什么要升到 P1 条件必需

角色和权限不适合只塞进功能树备注里。

原因：

```text
功能树表达“做什么”
视图树表达“在哪里做”
模块树表达“由谁承接”
角色权限矩阵表达“谁能做、谁能看、谁能改、谁能批准”
```

它是一种天然的二维关系，树形结构表达不清。

建议最小矩阵：

| 角色 / 功能 | 可见 | 可执行 | 可编辑 | 可配置 | 可审批 | 备注 |
|---|---|---|---|---|---|---|
| 普通用户 | 是 | 是 | 自己的数据 | 否 | 否 | 条件权限需说明来源 |
| 管理员 | 是 | 是 | 全部 | 是 | 是 | 需标注来源 |
| 访客 | 部分 | 否 | 否 | 否 | 否 | 只读入口 |

矩阵单元格必须能回跳到：

- 角色定义来源；
- 功能树节点；
- 视图树入口；
- 相关规则或约束；
- B 内审阅提示词。

## 7. 软件设计过程里的必需图

如果不限定 DeepSpec，而问“一个软件设计过程中哪些图是必须的”，建议这样分：

### 7.1 任何项目都应有

1. 功能结构图：DeepSpec 中是功能树 / 需求总览图。
2. 系统结构图：DeepSpec 中是模块树 / 系统结构树。
3. 界面结构图：DeepSpec 中是视图树 / UI 界面树。
4. 来源与依据图：DeepSpec 中是来源证据图。
5. 问题与缺口图：DeepSpec 中是需求健康图。

### 7.2 交互型软件通常应有

1. 用户路径 / 场景流图。
2. 角色权限矩阵。
3. 术语与对象关系图。

### 7.3 复杂业务软件按条件必须有

1. 状态转换图。
2. 规则 / 决策表。
3. 接口 / 集成关系图。
4. 变更影响图。

## 8. 首页建议

第一层首页不要平铺很多独立图。建议：

```text
左侧：三棵树导航
中间：需求总览图 / 当前文档状态总览图切换
右侧：节点详情 + 来源证据 + 提示词要点
底部：需求健康问题列表
```

P1 图表作为二级 Tab 或条件入口：

- 用户路径 / 场景流；
- 角色权限矩阵；
- 术语与对象关系。

P2 图表由具体节点触发：

- 状态转换图；
- 规则 / 决策表；
- 接口 / 集成关系图；
- 变更影响图。

---

## 9. 通用交互标准

所有图表和树节点必须支持：

- 点击节点：打开详情面板；
- 查看来源：显示原文片段、文件名、位置；
- 查看问题：显示问题类型、严重程度、原因；
- 跳转关联：功能树、模块树、视图树之间互跳；
- 状态过滤：只看缺失、冲突、无来源、低置信度、权限未说明；
- 用户确认：标记正确 / 错误 / 待确认；
- 生成提示词要点：指导用户原有 AI 完善 B；修改 A 属于第二层能力。

Prompt 不能只复制节点文本，必须带：

- 节点路径；
- 问题类型；
- 当前描述；
- 来源证据；
- DeepSpec 判断；
- 期望修改方向；
- 受影响节点；
- 禁止直接改代码的约束。

---

## 10. 定稿结论

当前第一层不再是“6 个 P0 + 2 个 P1”，而是：

```text
P0 结构骨架：
1. 功能树
2. 模块树 / 系统结构树
3. 视图树 / UI 界面树

P0 固定图表：
4. 需求总览图
5. 来源证据图
6. 需求健康图
7. 当前文档状态总览图

P1 条件必需：
8. 用户路径 / 场景流图
9. 角色权限矩阵
10. 术语与对象关系图

P2 条件扩展：
11. 状态转换图
12. 规则 / 决策表
13. 接口 / 集成关系图
14. 变更影响图
```

一句话：

**DeepSpec 第一层不是把所有关系都画成独立图，也不是判断需求是否已经闭环；它用三棵树承载需求结构，再用证据、健康、当前文档状态、流程、权限和术语图，让用户看清当下文档表达了什么、哪里表达不好、该如何让自己的 AI 完善 B。B -> A 的需求校正属于第二层能力。**
