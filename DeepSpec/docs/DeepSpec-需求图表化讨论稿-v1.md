# DeepSpec 需求图表化讨论稿 v1

> 日期：2026-05-14  
> 当前讨论焦点：人类需求如何从项目材料中被读出，并转化为人类看得懂的图片/图表。  
> 暂不讨论：AI 生成代码之后，开发结果和设计文档如何做一致性对照。
> 说明：本文件保留讨论过程。第一层图表优先级和“功能-视图/功能-模块是否独立成图”的最终判断，以 `DeepSpec-第一层图表体系定稿-v2.md` 为准。

---

## 1. 当前前提

用户的真实需求并不是从空白开始录入 DeepSpec。

更真实的情况是：

```text
人类脑中的想法
  ↓
已经先和 Claude / Cursor / Codex / IDE AI 沟通过
  ↓
沉淀在项目目录里
  ↓
README / 需求文档 / 设计文档 / 代码注释 / CLAUDE.md / AGENTS.md / TODO / 配置 / UI 文件
```

DeepSpec 第一层要做的不是重新采访用户，而是：

**从项目里已经存在的材料中，把人类需求读出来。**

---

## 2. 这一层的核心问题

传统开发文档是线性的：

```text
一段文字
另一段文字
一个标题
一个列表
一段 AI 对话总结
```

但人类真正想看的需求不是线性的，而是立体的：

```text
谁在用？
为什么用？
要完成什么目标？
有哪些核心功能？
功能之间有什么关系？
用户看到哪些界面？
每个界面承载哪些需求？
哪些需求已经明确？
哪些需求只是 AI 推断？
哪些地方还缺上下文？
```

所以 DeepSpec 的第一层目标是：

**把平面线性的开发文字，转化为立体的需求图表。**

更完整地说：

**原来的平面开发文档无法表达立体需求。DeepSpec 要通过三棵树挂接各种图表，把人类需求变成可视化、易理解、可交互、可指导 AI 修改的需求表达系统。**

这里的关键不是“多生成几个图”，而是形成一个新表达层：

```text
平面文档
  ↓
三棵树结构骨架
  ↓
挂接多种需求图表
  ↓
HTML 交互审阅
  ↓
提示词指导原 AI 工具修改底层文件
```

---

## 3. 所见即所得在第一层的定义

第一层的“所见即所得”不是：

- Markdown 预览；
- HTML 排版；
- 代码实现结果；
- UI 像素还原。

第一层的“所见即所得”是：

**用户看到的需求图表，就是项目材料当前表达出来的需求结构。**

也就是：

```text
项目材料里怎么描述需求
        ↓
DeepSpec 就把它读成什么需求图
        ↓
用户通过图表判断：这是不是我脑子里的产品？
```

如果图表不对，说明底层文档没有表达清楚；用户应回到原 AI 工具中补 README、需求文档、设计文档或 AI 规则文件。

HTML 在这里不是静态报告，而是交互审阅层：

- 用户在 HTML 中点击图表节点；
- 查看来源证据；
- 查看不确定点；
- 查看问题说明；
- 复制修正 Prompt；
- 回到原来的 Claude / Cursor / Codex / IDE AI 中修改底层文档；
- 重新扫描后图表更新。

因此第一层闭环是：

```text
看图
  ↓
发现需求表达问题
  ↓
复制 Prompt
  ↓
让原 AI 工具修改项目文档
  ↓
重新生成图
```

---

## 4. 需求图表的主对象

当前优先讨论的不是“代码实现”，而是“需求表达”。

DeepSpec 要先把以下对象图表化：

| 对象 | 用户要看懂的问题 |
|---|---|
| 用户/角色 | 谁会用这个软件？ |
| 场景/目标 | 用户为什么用？要完成什么？ |
| 功能 | 软件应该做什么？ |
| 功能分组 | 哪些功能属于同一类能力？ |
| 用户旅程 | 用户从进入软件到完成目标，经过哪些步骤？ |
| 界面/视图 | 用户应该看到哪些界面？ |
| 功能-界面映射 | 每个功能在哪里被用户触发或看见？ |
| 需求问题 | 哪些需求缺失、冲突、模糊、低置信度？ |
| 来源证据 | 这些需求从哪些文件、标题、片段里读出来？ |

---

## 5. 第一批需求图表

重要原则：

**需求总览图不是脱离三棵树的独立模型，而是挂在功能树上的图表视图。功能-视图、功能-模块关系优先作为三棵树的节点挂接和联动能力，不默认作为独立 P0 大图。**

三棵树仍然是结构骨架：

```text
功能树：需求要做什么
模块树：系统如何组织能力
视图树：功能树中“交付界面”部分的简化表达
```

需求总览图不是新的模型，也不是三棵树的混合图。它和功能树表达的是同一批内容，只是表现方式不同：

```text
功能树 = 树形结构表达
需求总览图 = 图表化总览表达
```

功能-视图关系是功能树与视图树之间的关系。后续如果树形联动已经看不清复杂关系，可以按需生成局部覆盖检查图，但不再默认作为固定 P0 大图。

这里还需要明确：

**第一层的视图树不是代码实现层的控件树，而是需求侧的界面交付树。**

它来自功能树中所有和“用户可见界面、页面、窗口、区域、操作入口、信息展示”有关的部分，是功能树的一个简化投影：

```text
功能树
  ├─ 业务能力
  ├─ 用户流程
  ├─ 数据/规则
  └─ 交付界面
        ↓
      视图树
```

因此第一层里的 UI 图表/视图树，重点不是“代码里有哪些控件”，而是：

```text
用户需要看到哪些界面？
每个界面承载哪些功能？
每个界面的主要区域是什么？
用户在界面上完成什么目标？
```

代码、DFM、前端文件可以作为辅助证据，但不能把第一层视图树降级为纯实现控件树。

图表挂载关系：

| 图表 | 挂在哪些树上 | 作用 |
|---|---|---|
| 需求总览图 | 功能树 | 把功能树换一种图表方式表达成一屏需求轮廓。 |
| 用户目标图 | 功能树 | 解释功能背后的用户目标和场景。 |
| 功能分组图 | 功能树 | 把散乱功能整理成能力域。 |
| 用户旅程图 | 功能树 + 视图树 | 展示用户完成目标的步骤和界面路径。 |
| 界面意图图 | 视图树 | 展示每个界面区域承载的需求意图。 |
| 功能-视图联动 / 局部覆盖检查 | 功能树 + 视图树 | 默认作为树节点联动能力；复杂项目按需生成局部图。 |
| 需求问题图 | 三棵树 | 聚合缺失、冲突、模糊、低置信度问题。 |
| 来源证据图 | 三棵树 | 展示需求节点来自哪些项目文件和片段。 |

### 5.1 需求总览图

用途：

一屏看清项目需求轮廓。

挂载方式：

需求总览图挂在功能树之上，作为功能树的图表化首页或总览 Tab。它不是新的第四棵树，也不是三棵树汇总，而是把功能树换成一张可扫视的需求图。

应显示：

- 产品目标；
- 核心用户；
- 核心场景；
- P0 功能；
- 主要界面；
- 高风险缺口；
- AI 推断比例。

与三棵树的关系：

| 总览图元素 | 来自哪里 |
|---|---|
| 核心功能 / P0 功能 | 功能树 |
| 功能域 / 能力分组 | 功能树 |
| 用户目标 / 场景 | 功能树节点摘要或来源文档 |
| 验收点 / 未决问题 | 功能树节点字段 |
| 风险 / 缺口 / 低置信度 | 功能树节点问题聚合 |

视图树和模块树可以在总览图中作为辅助提示出现，但不应改变需求总览图的本质：它是功能树的另一种表现方式。

### 5.2 用户目标图

用途：

把“谁为什么用”从文字里提取出来。

应显示：

```text
用户角色 → 目标 → 痛点 → 期望结果
```

### 5.3 功能分组图

用途：

把散落在文档、按钮、标题、TODO 中的功能组织成结构。

应显示：

```text
功能域
  ├─ 功能
  ├─ 子功能
  └─ 验收点 / 未决问题
```

### 5.4 用户旅程图

用途：

让用户看到需求是否形成完整流程。

应显示：

```text
进入软件 → 选择任务 → 执行操作 → 查看结果 → 导出/保存/交接
```

每一步关联功能、视图和问题。

### 5.5 界面意图图

用途：

把 UI 需求表达为“用户应该看到什么”，不是代码层面的控件解析。

它本质上是视图树的图表化表达，而视图树又是功能树中“交付界面”部分的简化表达。

应显示：

- 主界面；
- 关键区域；
- 主要操作；
- 信息展示区；
- 反馈/状态区；
- 用户在每个区域想完成什么。

### 5.6 功能-视图联动 / 局部覆盖检查

用途：

这是第一层里最接近“需求和 UI 比较”的能力。

挂载方式：

功能-视图关系挂在功能树和视图树之间，优先通过节点详情、筛选、反查和局部高亮表达。

用户可以从功能树选中一个功能，看到它映射到哪些视图；也可以从视图树选中一个界面，反查它承载哪些功能。

应显示：

```text
功能需求 → 用户在哪个界面看到/触发 → 界面承担什么意图
```

重点不是代码实现，而是：

**人类需求有没有被表达成可见的界面意图。**

这里的“视图”不是最终代码控件，而是功能树中交付界面的需求表达。

最小图形结构：

```text
功能节点
  ├─ 触发视图
  ├─ 展示视图
  ├─ 输入区域
  ├─ 输出区域
  └─ 状态反馈区域
```

反向视角：

```text
视图节点
  ├─ 承载功能
  ├─ 支持的用户目标
  ├─ 关键操作
  └─ 未覆盖需求
```

后续扩展：

```text
功能 → 视图 → 模块
```

第一层先重点做：

```text
功能 → 视图
```

### 5.7 需求问题图

用途：

让用户一眼知道文档哪里还不够清楚。

应显示：

- 缺失；
- 冲突；
- 模糊；
- 低置信度；
- 无来源证据；
- 需要用户确认。

### 5.8 来源证据图

用途：

防止 DeepSpec 看起来像在胡猜。

应显示：

```text
需求节点 → 来源文件 → 来源片段 → 置信度
```

## 6. 和 AI、UI 的关系

当前你指出的重点是对的：

**需求图表化应该优先和 AI 理解、UI/界面意图做比较。**

这里有两个比较：

### 6.1 人类需求 vs AI 理解

DeepSpec 读项目材料后生成需求图表。用户看图表时，本质是在判断：

```text
AI / DeepSpec 当前理解出来的需求
是不是我脑子里的需求？
```

如果不是，就通过提示词回到原 AI 工具补文档。

这里的 HTML 交互必须支持“指导 AI 修改”：

| 用户在图上看到 | DeepSpec 应提供 |
|---|---|
| 需求缺失 | 补充需求说明 Prompt |
| 功能模糊 | 澄清功能边界 Prompt |
| 缺少界面意图 | 补充 UI/视图说明 Prompt |
| 来源证据不足 | 要求 AI 回到指定文档补证据 Prompt |
| 功能和界面断开 | 让 AI 补充功能-界面关系 Prompt |
| 需求冲突 | 让 AI 整理冲突选项并请用户确认的 Prompt |

### 6.2 人类需求 vs UI 意图

需求最终必须能在界面上被用户感知。

所以第一层应该重点做：

```text
功能需求
  ↓
用户旅程
  ↓
界面意图
  ↓
视图树
```

这不是代码实现对照，而是需求表达是否已经足够支撑 UI 设计。

## 7. 第一层暂不做的对照

当前先不讨论：

```text
设计文档 vs 代码实现
设计文档 vs Git Diff
需求 vs 测试覆盖
AI 实现是否偏离需求
```

这些属于第二层：

**AI 开发旁路治理与需求校准器。**

第一层只讨论：

```text
人类想法
  ↓
项目材料
  ↓
需求图表
  ↓
用户确认图表是否符合脑中想法
```

---

## 8. 当前建议的讨论顺序

接下来应该一次两个问题讨论：

1. **需求总览图应该长什么样？**
2. **角色权限矩阵应该如何挂到三棵树上？**

原因：

- 需求总览图决定 DeepSpec 第一眼价值，本质上是功能树的图表化表达；
- 角色权限矩阵决定“谁能看、谁能做、谁能批准”是否能从线性文字中被清楚审阅。
- 两张图都挂在三棵树之上，不会破坏“三棵树是结构骨架”的产品模型。

这两张图定下来，DeepSpec 的第一层“所见即所得”才有形状。
