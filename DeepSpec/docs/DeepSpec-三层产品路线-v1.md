# DeepSpec 三层产品路线 v1

> 日期：2026-05-14  
> 来源：`发散讨论/01_产品定位与三阶段路线.md`、`09.DeepSpec-阶段二旁路治理路线.md`、`10.DeepSpec-阶段三CLI调度远景.md`  
> 当前总定位：先做需求可视化，再做需求所见即所得，最后调用用户 CLI 实现软件功能。

---

## 1. 三层总览

DeepSpec 的产品路线不是三个互斥产品，而是三层递进能力：

```text
第一层：需求可视化（包括建议）
        ↓
第二层：需求所见即所得（代码与需求一致）
        ↓
第三层：调用 CLI 实现软件功能
```

最短表达：

```text
先把需求可视化并给出建议，
再让代码与需求保持一致，做到需求所见即所得，
最后调用用户 CLI 实现软件功能。
```

产品一句话：

```text
DeepSpec 是软件开发的需求可视化审阅层：把项目材料转成可追溯的规格化需求 B，并用三棵树和 HTML 图表让人看清、确认和校准 AI 的理解。
```

---

## 2. 第一层：需求可视化（包括建议）

### 定位

**免费给开发者使用的需求可视化层。**

这一层是当前 MVP 主线。DeepSpec 作为用户原 AI/IDE 工作流旁边的旁路工具，读取已有项目目录，提供更好的查阅界面、LLM 调用上下文和提示词工程。默认路径是直接调用已经成熟的框架 LLM 模块，让用户配置或已有的 AI 能力生成 / 更新 B，再由 DeepSpec 校验、固化、可视化呈现；复制 Prompt 只是导出和兜底方式，不是主流程。

第一层必须是通用产品，不能绑定在 Delphi + VCL 上。它应服务所有有开发文档、代码、配置、UI 文件和 AI 规则文件的项目。

第一层的首批用户是 AI 重度独立开发者和小团队技术负责人：他们愿意审阅需求体系、做需求决策、校准 AI 理解；不是期待“给一个提示词就输出产品”的用户。

第一市场楔子是 AI 重度开发者的需求可视化审阅工具。Delphi/VCL 是强样板和差异化 Pack，不是第一层主定位。

第一层的事实源模型：

```text
A = 用户原始需求文档目录 / 原始项目材料
B = DeepSpec 生成的规格化需求目录，默认位于 .deepspec/
```

第一层不是 DeepSpec 自己负责“理解并生成需求”的 AI 引擎。B 的语义内容主要由框架 LLM 模块调用用户配置或已有的 AI 能力，根据 DeepSpec 提供的上下文包、Schema 和提示词模板生成。DeepSpec 的责任是 LLM 任务编排、提示词工程、上下文组织、Schema 校验、来源追溯、HTML/三树呈现和 B 的事实源管理。

B 是 DeepSpec 的规格化事实源，后续第二层 Review 和第三层 CLI 调度都应以 B 为统一规格入口。

B 不是文档摘要，而是由需求节点、关系边、来源证据、状态和人类决策组成的规格化事实层。第一层的所见即所得，是 B 中当前需求事实与三树 / 图表 / HTML 审阅界面一致；第二层的所见即所得，才是代码结果与 B 中需求事实一致。

### 做什么

- 扫描项目目录；
- 分类文档、代码、UI、配置、AI 规则文件；
- 生成扫描报告；
- 调用框架 LLM 模块，使用 A -> B 的上下文包、Schema 和提示词模板生成 / 更新 B；
- 保留可复制 Prompt 和上下文包导出，作为用户外部 AI 工具的兜底路径；
- 接收 LLM 生成的内容，并固化为 `.deepspec` 规格化需求目录 B；
- 生成 `project-spec.yaml` 作为 B 的总事实索引；
- 生成功能树、模块树、视图树；
- 以三棵树为骨架挂接图表：需求总览图是功能树的图表化表达，功能-视图和功能-模块关系优先作为树节点挂接与联动能力表达；
- 生成文档问题清单；
- 展示来源证据、当前文档状态、低置信、缺口和冲突；
- 支持人类在页面上做需求决策，并写入 B 的 Decision Log；
- 复用同事已经开发的 DeepShell，提供树控件 + WebView2/HTML 所见即所得查阅界面。

### 不做什么

- 不接管用户原来的 AI/IDE 主工作流；
- 不在 DeepSpec 里聊天；
- 不默认把 B 混写进 A；
- 不自动修改 A 中的 README / PRD / 设计文档；
- 不提供 A 的自动同步和需求校正工作流；
- 不自动修改代码；
- 不直接调用用户 CLI 执行开发；
- 不做代码实现与规格一致性检查；
- 不做完整 Git Diff 治理。
- 不把第一层绑定为 Delphi/VCL 专用工具。

### 解决的问题

**开发文档散乱、线性、不可审阅；人类需求没有被立体表达，AI 读完到底理解成什么，用户看不见。**

### 用户动作

用户发现问题后，先在 B 的页面上做需求决策。免费层的核心价值是让用户看清“当前需求体系是什么、哪里不清楚、哪里冲突、哪些内容来自人工决策或 AI 推断”，并给出审阅建议和 B 内提示词要点。

A 的自动同步、需求修订建议、Patch 生成和代码与需求校正属于第二层付费能力。

Delphi/VCL 能力在第一层中只作为增强能力或样例能力存在：

- 可以优先支持 `.dpr/.dproj/.pas/.dfm`；
- 可以作为商业差异化的 Delphi Pack；
- 但不能让用户误解 DeepSpec 第一层只适用于 Delphi/VCL 项目。

## 3. 第二层：需求所见即所得（代码与需求一致）

### 定位

历史讨论中的原名是：

**AI Agent 开发旁路治理系统。**

按当前产品语言，建议升级为：

**需求所见即所得：让代码与需求保持一致。**

这一层仍然不接管主线开发，但开始围绕 B 与 A、代码实现、Git Diff 和测试输出做校正。它回答：代码是否偏离需求、A 是否没有同步 B、需求是否需要回写、AI 是否把实现写偏了。它的核心目标是实现“需求所见即所得”：用户在 B 中看到的需求，应能和实际代码结果对齐。

第二层统一以第一层生成的 B 作为规格事实源，不重新从 A 建立另一套规格事实。

### 做什么

- 开发前生成 Context Pack；
- 以 B 的 accepted decisions、三棵树、问题和 A 未同步队列作为 Review 基准；
- 生成 `A 未同步` 待办队列；
- 生成面向 A 的需求校正 Prompt / Patch 建议；
- 验证用户 AI 或 Patch 是否把 B 的决策同步回 A；
- 生成 AGENTS.md / CLAUDE.md / Cursor Rules 等规则草稿；
- 用户仍在外部 AI / IDE / CLI 中开发；
- DeepSpec 旁路扫描文件变化、Git Diff、测试输出；
- 生成 Review Pack；
- 检测规格漂移；
- 发现代码实现与需求文档不一致；
- 发现需求变化是否需要回写文档；
- 问题转决定；
- 更新变更日志；
- 生成 Handoff；
- 将 AI 犯错沉淀为规则回流。

### 关键闭环

```text
Context Pack
  ↓
外部 AI / IDE / CLI 开发
  ↓
文件变化 / Git Diff / 测试输出
  ↓
Review Pack
  ↓
Spec Drift 检测
  ↓
问题转决定
  ↓
需求文档 / 规格 / 规则回流
  ↓
Handoff
```

### 解决的问题

**用户仍然用原 AI 工具开发，但 DeepSpec 能判断“代码是否偏离需求、A 是否偏离 B、需求是否需要回写”，并把偏差反馈回文档、规则和下一轮提示词。**

### 与第一层的区别

第一层免费呈现“开发前的可视化需求体系和建议”。  
第二层付费提供“需求所见即所得”，也就是代码与需求一致。

## 4. 第三层：调用 CLI 实现软件功能

### 定位

历史讨论中的原名是：

**规格驱动 CLI 开发工作台。**

按当前目标，建议升级为：

**调用用户 CLI 实现软件功能。**

这一层开始直接调用用户本机已有 CLI 和 Agent，在 B 的需求约束下实现软件功能。它仍然以用户授权、用户配置、用户环境为前提。

### 可调用对象

- Codex CLI；
- Claude Code；
- OpenCode；
- Cursor 相关命令；
- Git；
- 编译器；
- 测试命令；
- Lint；
- DeepUITest；
- 其他用户配置的 CLI 工具。

### 做什么

- 选择规格或需求问题；
- 从 B 中选择规格节点、问题、决策或 A 未同步待办；
- 生成开发任务；
- 选择用户 CLI / Agent；
- 生成上下文包；
- 调用外部工具；
- 监控输出；
- 扫描文件变化；
- 运行编译和测试；
- 生成 Review Pack；
- 校准需求与实现；
- 人类确认；
- 合并、回滚或继续下一轮。

### 关键闭环

```text
选择 Spec / 文档问题
  ↓
生成开发或校准任务
  ↓
选择用户 CLI / Agent
  ↓
生成上下文包
  ↓
调用外部工具
  ↓
监控输出和文件变化
  ↓
运行测试
  ↓
生成 Review Pack
  ↓
校准需求与实现
  ↓
人类确认
  ↓
合并 / 回滚 / 下一轮
```

### 解决的问题

**用户不只是复制提示词，而是让 DeepSpec 在规格约束下调用用户已有 CLI 完成软件功能实现、测试、审查和需求校准。**

第三层的调度入口仍然是 B，而不是直接从 A 临时拼 Prompt。A 作为原始材料和证据层存在，B 作为规格约束和任务生成入口存在。

### 与第二层的区别

第二层是旁路观察和校准，不直接启动开发工具。  
第三层是受控调用用户 CLI，把“提示词 + 规格 + 审查”变成可执行开发循环。

---

## 5. 三层关系表

| 层次 | 名称 | 主动作 | 是否调用用户 CLI | 核心产物 |
|---|---|---|---|---|
| 第一层 | 需求可视化（包括建议） | 框架 LLM 调用、提示词工程、B 生成 / 更新、三树、HTML、问题、人类决策、审阅建议 | 否 | `.deepspec` 规格化事实源、三棵树、问题清单、Decision Log、HTML |
| 第二层 | 需求所见即所得（代码与需求一致） | 以 B 为基准做 A 同步、代码/需求一致性校正、Review、漂移检测、规则回流 | 通常否 | A 未同步队列、需求校正 Prompt/Patch、Review Pack、Handoff、漂移报告 |
| 第三层 | 调用 CLI 实现软件功能 | 以 B 为任务入口调用用户 CLI 实现功能、测试、校准 | 是 | 任务执行记录、测试结果、Review Pack、合并/回滚建议 |

---

## 6. 为什么第二层不能跳过

如果从第一层直接跳到第三层，风险是 DeepSpec 过早变成“又一个 AI 开发器”。

第二层的价值是先建立：

- 规格漂移检测；
- Review Pack；
- 文件变化扫描；
- 规则回流；
- Handoff；
- 需求与实现的校准逻辑。

这些能力稳定后，第三层调用 CLI 才不会变成盲目自动开发。

---

## 7. 当前建议

当前阶段先锁定免费第一层：

**需求可视化（包括建议）。**

第一版发布策略：

```text
开源免费。
```

免费边界：

```text
需求可视化 + 建议 + B 内决策
```

不越过到 A/B 需求校正、代码与需求一致性、Review Pack、Git Diff、CLI 调度。

第二层作为付费中期路线：

**需求所见即所得（代码与需求一致）。**

第三层作为长期路线：

**调用 CLI 实现软件功能。**

进入第二层的门槛：

- 第一层能稳定生成候选 B；
- 能稳定校验、合并和渲染 B；
- 三棵树、HTML、来源证据、问题清单、决策写回稳定；
- 在 3-5 个真实项目上验证；
- 用户能在 10 分钟内看懂项目需求结构；
- 用户能用 DeepSpec 找出 AI 对需求的误解、缺口或冲突。

这三个层次共同构成 DeepSpec 的完整产品路线：

```text
需求可视化
  ↓
需求所见即所得
  ↓
CLI 实现功能
```
