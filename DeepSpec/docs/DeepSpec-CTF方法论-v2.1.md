> 版本：2.1
> 日期：2026-05-21

## 0. 一句话定义

> **需求的形式和粒度是人机协作的建构产物，必须可追溯，且始终可谬。底层约束（合规、安全、性能）可能是客观存在的——方法论管的是对这些约束的表达，而非约束本身。**
>
> 方法通过四层结构（认知-正确性-生态-工程）将这一信念嵌入工具和流程，使方法论成为工具的一部分而非人的记忆负担。

## 1. 哲学基础

### 1.1 本体论立场

> **软件需求的形式和粒度不是被直接发现的，而是在人类与 AI 的持续对话中被建构的。需求规���是对话的中间产物——一个可追溯、可质疑、可修正的结构化快照。**
>
> 但需求的底层约束可能是客观的：合规要求、安全边界、性能指标不以人的意志为转移。方法论管的是对这些约束的**表达方式**，而非约束的存在性。

### 1.2 三个哲学承诺

| 承诺 | 含义 | 对设计的意味 |
|------|------|-------------|
| **建构主义** | 需求的表达形式通过人机交互被建构，而非"等着被发现" | 每个节点记录建构过程（谁、用什么输入、用什么方法） |
| **可追溯性** | 每个建构产物必须追溯到建构过程 | 不存在"无来源"的节点 |
| **可谬性** | 每个建构产物都可能被推翻 | 不存在"一旦确认就永远正确"的节点 |

### 1.3 第零公理

> **工具不替代人类判断。它让人类判断更有分量。**

同构推论：**方法论不替代团队工程直觉。它让工程直觉更可靠。** 如果方法论本身变成了负担而非赋能，它就违背了自己的第零公理。

## 2. 七条公理

公理是不证自明的起点。所有具体实践从公理推导而来。

| 编号 | 名称 | 陈述 | 推翻条件 |
|------|------|------|----------|
| A1 | 建构性 | 每个规格节点都是建构行为的结果，不是对已有事实的转录 | 若工具能从源文件直接导出确定性映射（如编译器），A1 退��为"转录" |
| A2 | 可追溯性 | 每个建构行为记录输入（证据源）、过程（推理链）、产出（节点） | 若追溯成本超过其防止的错误成本，团队可降低追溯粒度 |
| A3 | 可谬性 | 每个节点都可能被后续信息推翻 | 若某类节点经 6 个月无修正记录，团队可将其标记为"稳定" |
| A4 | 正交性 | 不同维度（生成状态、审阅状态）用独立字段表达 | 无推翻条件——混用维度会导致语义歧义，这是逻辑错误而非经验判断 |
| A5 | 最小权限上下文 | 每次 AI 调用只获得恰好够用的信息 | 若 AI 产出质量持续因上下文不足而下降，应增加上下文而非坚持最小权限 |
| A6 | 问题优先 | 向人类呈现信息时，先呈现不确定性，再呈现确定性结论 | 无推翻条件——确认偏差是认知科学确立的系统性偏差，干预永远有价值 |
| A7 | 部分成功 | 系统在任何时刻都处于"部分可用"状态 | 无推翻条件——全有或全无的系统在 AI 调用不可靠时必然失败 |

### 公理依赖关系

```
A1 建构性 ──→ 需要追溯（A2）
  │              │
  └─→ 可能出错（A3）──→ 需要正交描述（A4）
                          │
       ┌──────────────────┘
       ↓
  AI 调用要克制（A5）
       │
       ↓
  人类审阅要触发深层思考（A6）
       │
       ↓
  系统永远部分可用（A7）
```

每条公理标注了**推翻条件**——这是方法论自身可谬性的具体机制。不能被质疑的方法论是教条，没有推翻条件的公理是信条。

## 3. 四层模型

> **核心原则：从 Layer D 向下推导，不从 Layer A 向上堆砌。**
> 先确定认知目标（为什么），再确定正确性标准（什么），再确定传播策略（怎么），最后确定具体材料（用什么）。

### Layer D：认知干预层

> **"人类的判断力怎样才更可靠？"**

| 维度 | 内容 |
|------|------|
| **目标** | 增强人类审阅判断力，对抗确认偏差 |
| **操作** | 问题优先呈现、信任信号体系、Accept 加摩擦 / Reject 减摩擦 |
| **迭代节奏** | 月级（按用户行为数据迭代） |
| **验证标准** | 三信号仪表盘（见第 5 节） |
| **失败隔离** | 本层失灵 → 系统降级为展示工具，底层仍然正确运行 |

### Layer C：正确性保证层

> **"系统状态怎样才是完备的？"**

| 维度 | 内容 |
|------|------|
| **目标** | 系统状态的数学完备性 |
| **操作** | 不变量声明（INV-1~INV-7）、节点状态机、语义束跨树校验、kind 受控词表 |
| **迭代节奏** | 季度级（按协议版本） |
| **验证标准** | 所有不变量有对应测试；状态机无死锁；每条 failure path 有恢复行为 |
| **失败隔离** | 本层违规 → 认知层仍展示信息（只是无法自动检测问题） |

### Layer B：生态集成层

> **"正确的东西如何进入世界？"**

| 维度 | 内容 |
|------|------|
| **目标** | 让协议被广泛采用 |
| **操作** | CLI-first 集成、DeepSpec Tool Protocol、x_ 扩展命名空间、local.yaml 本地覆盖 |
| **迭代节奏** | 月-季度级（按第三方反馈） |
| **验证标准** | 第三方能否在不读实现代码的情况下完成集成？新的语言 binding 能否在 1 天内完成？ |
| **失败隔离** | 本层断裂 → 正确性层仍然有效 |

### Layer A：工程实现层

> **"怎么可靠地造出来？"**

| 维度 | 内容 |
|------|------|
| **目标** | 可靠、可测试、可恢复的工程实现 |
| **操作** | 上下文组装管线、快照与回滚、部分成功模式、单元测试 |
| **迭代节奏** | 周级（持续迭代） |
| **验证标准** | 核心模块测试覆盖率 > 80%；LLM 调用失败后自动恢复；单棵树失败不阻塞其他树 |
| **失败隔离** | 本层崩溃 → 生态层仍可用（CLI 可独立运行） |

### 失败隔离原则

```
底层失败不向上传播：
  Layer A 崩溃 → Layer B 仍可用
  Layer B 断裂 → Layer C 仍有效
  Layer C 违规 → Layer D 仍提供价值
  Layer D 失灵 → 系统降级为展示工具

顶层设计决定底层价值：
  Layer D 目标错误 → 所有工程努力打折
```

## 4. 核心概念

### 4.1 语义束（Semantic Bundle）

四棵投影树中描述同一件事的节点集合。一个语义束跨越多棵树，提供一个需求概念的所有投影。

价值：按束审阅、按束一致性检查、按束增量生成。

### 4.2 正交状态维度

```
gen_status（生成维度）：pending | generated | failed
review_status（审阅维度）：pending | accepted | rejected | locked
```

组合语义：

| gen_status | review_status | 含义 |
|------------|---------------|------|
| generated | pending | AI 生成了，等人审 |
| generated | accepted | 已确认，可以作为基准 |
| generated | rejected | AI 生成了但被否决 |
| generated | locked | 人工锁定，AI 不自动覆盖 |
| failed | locked | 源文件已变更，等待解锁重生成 |
| pending | any | 还没生成 |

### 4.3 信任信号（Trust Signal）

每个节点向审阅者展示的结构化可信度证据：

```
信任信号 =
  证据源状态（有来源 / 来源缺失 / 来源冲突）
  + LLM 推理链条（可展开）
  + 跨树一致性（同一语义束内其他树的状态）
  + 冲突检测（是否与人工决策或其他节点矛盾）
  + 人工决策历史（accept/reject 记录）
```

### 4.4 不变量（INV-1~INV-7）

每个不变量必须有运行时断言和测试用例。

| ID | 陈述 | 验证时机 |
|----|------|----------|
| INV-1 | 节点 ID 在单棵树内唯一 | 写入时 |
| INV-2 | parent_id 指向同树内已存在节点或 null | 写入时 |
| INV-3 | relation 的 source 和 target 指向已存在节点 | 写入时 |
| INV-4 | status 迁移遵守状态机 | 状态变更时 |
| INV-5 | accepted 节点必须有至少一条 evidence | Accept 时 |
| INV-6 | content_hash 变更时 gen_status 降级 | 写入时 |
| INV-7 | 同一语义束内的节点状态不互相矛盾 | 语义束写入时 |

### 4.5 最小权限上下文

每次 LLM 调用只给恰好够用的文件：

```
生成 function-tree → 项目概览 + README + 需求文档（不给源代码）
生成 module-tree  → 项目概览 + function-tree + 源代码目录结构（不给完整源码内容）
生成 view-tree    → 项目概览 + function-tree + DFM/PAS 文件（不给业务逻辑代码）
生成 data-tree    → 项目概览 + module-tree + schema/migration 文件（不给无关 UI 细节）
```

### 4.6 Kind 受控词表

每棵树有独立的合法 kind 值，`x_` 前缀为扩展命名空间。

## 5. 三信号健康仪表盘

只监控三个信号，每个直接对应一条核心公理：

| 信号 | 对应公理 | 触发条件 | 含义 |
|------|---------|---------|------|
| 审阅积压 | A3 可谬性 | pending 节点占比 > 30% | 未审阅的节点可能是错的 |
| 置信度漂移 | A2 可追溯性 | 新产出 confidence 低于已审阅均值 | AI 可能在新领域表现不佳 |
| 确认偏差 | A6 问题优先 | accept:reject > 10:1 | 审阅者是否在认真拒绝 |

不设复合"健康指数"。每个信号独立说话，团队自行判断。

## 6. 实践载体

### 载体 1：自动化检查

可机器验证的公理（A2、A3、A5、A7）嵌入 `deepspec_validate`，不需要人工对照。

只有 A6（问题优先）需要人类判断——以非阻断性提示呈现，不阻断工作流。

### 载体 2：协议文件

公理的机器可执行形式：

```
protocol/
  invariants.md         → INV-1~7
  state-machine.md      → gen_status × review_status 状态机
  controlled-vocab.md   → kind 受控词表
  schemas/bundle.json   → 语义束 schema
```

### 载体 3：三级审阅仪式

```
轻量审阅（3 分钟）── 默认，单节点/小改动
  问题先行 + Accept/Reject

标准审阅（10 分钟）── 同一语义束有 3+ 节点变更时自动建议
  问题先行 → 选择性深入 → 生成指令

深度审阅（20 分钟）── 跨树影响或 confidence < 0.7 时自动建议
  Phase 1：问题先行（3 分钟）
    不看四投影树，只看系统标记的不一致和疑问
  Phase 2：选择性深入（10 分钟）
    展开信任信号，决定 Accept 或 Reject
  Phase 3：全局浏览（5 分钟）
    快速浏览四投影树，关注 confidence < 0.7 的节点
  Phase 4：生成指令（2 分钟）
    决定下一步：重生成 / 补充源文件 / 锁定已确认 / 冻结
```

### 载体 4：异常驱动决策日志

只记录以下情况（其余数据自动采集）：

- **Reject 决策**——必须记录理由
- **Accept 但 confidence < 0.7**——必须记录理由
- **偏离标准审阅流程**——记录原因

系统自动采集（无需人工输入）：

- 每节点审阅时长
- accept/reject 计数
- 平均 confidence
- 会话长度和节点数量

### 载体 5：问题驱动复盘

**删除固定月度复盘会议。**

复盘嵌入审阅流程：审阅结束时可选标记"本次审阅是否暴露了方法论问题？"。标记的问题自动记录到 `.deepspec/methodology-feedback.yaml`。

**仅在以下条件触发正式复盘**：累积 5+ 条方法论反馈时，召开 30 分钟回顾。否则跳过。

Week 4 的"质疑公理"环节保留——这是方法论内化的关键仪式。

## 7. 方法论内化路径

| 周 | 活动 | 认知阶段 | 负担 |
|----|------|----------|------|
| Week 1 | 只用自动化检查，正常工作前花 2 分钟看三信号仪表盘 | 跟随 | 极轻 |
| Week 2 | 解锁轻量审阅（问题先行 3 分钟），开始看信任信号 | 理解 | 轻 |
| Week 3 | 解锁标准审阅，开始记录异常驱动的决策日志 | 实践 | 中等 |
| Week 4 | 独立完成深度审阅 + 参与问题驱动复盘 + 提出一个"公理可能不对"的论点 | 质疑 | 中等 |

每周解锁一个新行为。习惯形成的核心是最小起步——先跑起来再加速。

## 8. DeepSpec Tool Protocol

```
Tool: deepspec_read
  Input:  { tree: "function"|"module"|"view"|"data"|"all",
           format: "yaml"|"summary",
           filter?: { status, kind, confidence_min } }
  Output: 对应树数据或摘要

Tool: deepspec_validate
  Input:  { scope: "all"|"tree"|"file", target?: string }
  Output: { valid: bool, issues: [...], invariants_broken: [...] }

Tool: deepspec_query
  Input:  { question: string, explain?: bool }
  Output: 基于四投影树的 RAG 回答 + 推理链

Tool: deepspec_update
  Input:  { tree: string, nodes: [...], decisions?: [...] }
  Output: { accepted: bool, conflicts: [...] }
```

第一天最低要求：`deepspec_read` + `deepspec_validate`。

所有 `.deepspec/` 内容为人类可读 YAML。即使所有 AI 工具消失，审阅者仍可打开文件手动操作。

## 9. 协议扩展约定

```
保留命名空间：
  x_     → 第三方扩展（任何实现必须忽略不认识的 x_ 字段）
  _      → 内部临时字段（不应持久化）
  无前缀  → 核心 spec 字段

保留文件：
  x-*.yaml   → 第三方扩展文件
  local.yaml → 用户本地覆盖（不提交到 git）

兼容性承诺：
  - 新版本必须能读取旧版本 .deepspec/ 目录
  - 字段标记 deprecated → 保留 2 个小版本 → 删除
  - 未知字段必须被忽略（向前兼容）
```

## 10. 方法论元规则

CTF 的第零公理和第三公理适用于方法论本身：

> **方法论不替代团队判断。它让团队判断更有分量。**

> **方法论本身可谬。每条公理标注了推翻条件。修改需要证据和团队共识。修改后更新所有载体。**

度量决策质量而非流程合规性：

| 指标 | 度量什么 | 好趋势 |
|------|---------|--------|
| 规格修正率 | Accept 后又被 Reject 的节点比例 | 下降 = 决策质量提升 |
| AI 首次准确率 | 首次 Accept（无需修改）的节点比例 | 上升 = AI 在学习团队偏好 |
| 信心校准度 | confidence_self 与实际被推翻率的对应 | 高置信度节点的推翻率低 = 校准良好 |

不度量审阅仪式完成率、决策日志填写率等合规性指标。Goodhart 定律：当一个指标变成目标，它就不再是一个好指标。

## 11. 增强层功能开关

以下功能存在但不默认启用。团队在感受到具体痛点后按需开启：

| 功能 | 启用条件 | 解决的痛点 |
|------|---------|-----------|
| Accept 时间门控摩擦 | 完成 4 周内化后可启用 | 确认偏差持续 > 10:1 |
| 审阅节律提醒 | 完成 4 周内化后可启用 | 审阅积压持续 > 30% |
| 信任信号趋势图 | 有 3 个月使用数据后可启用 | 需要观察 AI 产出质量变化 |
| 自适应摩擦力度 | 有 3 个月使用数据后可启用 | Accept/Reject 比率波动大 |
| 社区反馈集成 | 有外部用户后可启用 | 第三方集成需要协议扩展 |

**原则：每个功能的存在是为了解决一个已经确认的痛点，而非预防一个假想的痛点。**

## 附录：v1.0 → v2.1 变更记录

| 变更 | 理由 |
|------|------|
| 本体论立场增加"底层约束可能客观存在" | 避免建构主义的过度断言 |
| 每条公理增加推翻条件 | 方法论可谬性的具体机制 |
| INV-7 跨束一致性 | 原 INV-1~6 缺少跨树维度 |
| gen_status=failed + review_status=locked 组合语义 | 源文件变更后的常见状态需要明确展示 |
| 三信号健康仪表盘替代 v2.0 健康指数 | 不设复合指标，每个信号独立说话 |
| 三级审阅仪式替代固定四阶段 | 不同场景需要不同重量的流程 |
| 异常驱动决策日志替代全面记录 | 减少 90% 数据量，保留 100% 信号 |
| 自动化检查替代手动检查清单 | 机器可执行的交给机器 |
| 问题驱动复盘替代月度固定复盘 | 没有问题就不需要复盘 |
| 4 周内化路径改为渐进解锁 | 习惯形成的核心是最小起步 |
| 增强层功能开关 | 不预设解决方案，按需启用 |
| 度量决策质量而非流程合规 | 避免方法论从赋能工具变成监视工具 |
| 删除 v2.0 的热力图/趋势分析/自动触发器 | 归入增强层，不默认开启 |
