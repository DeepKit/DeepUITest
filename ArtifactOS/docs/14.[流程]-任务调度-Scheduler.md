# 14 任务调度系统

> 系统编号：★（中枢）
> 核心职责：状态机驱动案（Case）、今日子案（DaySubCase）、片场（Studio）、子片场（SubStudio）、产出物（Artifact）、认知轨迹、证据断言、自动重写、策略裁决、发布、抽检、降权和召回的全生命周期管理
> 设计来源：DeepStory「双状态字段状态机」、DeepStory「flags叠加机制」

---

## 一、设计理念

### 1.1 核心原则

1. **案是一等公民（Case First）**：所有日常运营先归入案（Case），再下沉到今日子案（DaySubCase）、片场（Studio）、子片场（SubStudio）和产出物（Artifact）
2. **日晨会按今日子案授权（DaySubCase Authorization）**：人类在日晨会中操作今日子案（DaySubCase），成熟案（Mature Case）在授权范围内自动运行
3. **双状态字段**：管线状态和质量状态独立演进，不互相阻塞
4. **Flags叠加**：额外标记叠加在状态之上，提供细粒度控制
5. **返工可追溯**：每次返工都有原因、上下文、版本变更记录
6. **演进非返工**：探索模式中契约演进是正常创作行为，不触发返工计数
7. **策略单元驱动**：任务必须绑定策略单元，继承自治等级、质量矩阵、重写上限和发布策略
8. **调度模式可切换**：支持单产出、片场、赛马、实验策略四种模式
9. **产出物可治理**：任务必须绑定契约成熟度、证据包、封存记录和召回路径
10. **认知事件可调度**：任务必须能绑定 `CognitionTrace`、`EvidenceClaim`、`CognitiveDisturbanceEvent`
11. **边界决策可终止流程**：`not_write` 和 `draft_only` 是合法终态/半终态，不是异常

### 1.1a 调度对象边界

`Task` 不再是产品层一级对象，而是子片场执行任务（SubStudioExecutionTask）。它只负责驱动一个子片场（SubStudio）生产一个产出物（Artifact）的状态流转。产品层的组织关系如下：

```text
年案（YearCase）
  -> 半年案（HalfYearCase）
    -> 季案（QuarterCase）
      -> 月案（MonthCase）
        -> 周案（WeekCase）
          -> 日案（DayCase）
            -> 今日子案（DaySubCase）
              -> 片场（Studio）
                -> 产出计划集（ArtifactPlanSet）
                  -> 产出计划（ArtifactPlan）
                    -> 子片场（SubStudio）
                      -> 子片场执行任务（SubStudioExecutionTask）
                        -> 产出物（Artifact）
```

上层案（Case）定义边界、授权和介入规则；子片场执行任务（SubStudioExecutionTask）只执行，不反向静默改写上层案（Case）。

### 1.2 与 DeepStory 的对应

| DeepStory 概念 | ArtifactOS 映射 |
|---------------|-------------------|
| design_status | contract_status（契约阶段） |
| text_status | draft_status（写作阶段） |
| seal_status | publish_status（发布阶段） |
| flags | checking / ai_working / human_override |
| rework_count | rework_count |

## 三、管线状态（pipeline_status）

### 3.1 状态定义

| 状态 | 说明 | 可转换到 |
|------|------|---------|
| `pending` | 任务已创建，等待开始 | `contracting` |
| `contracting` | 正在生成/审核写作契约 | `drafting`, `abandoned` |
| `drafting` | 正在写作或自动重写 | `reviewing` |
| `reviewing` | 正在质量门禁检查和策略裁决 | `drafting`（返工）, `approved`, `waiting_human`, `stored`, `abandoned` |
| `approved` | 质量门禁通过，待发布 | `publishing` |
| `publishing` | 正在发布 | `published`, `publish_failed` |
| `published` | 已发布 | `collecting` |
| `collecting` | 正在回收数据 | `completed` |
| `completed` | 全流程完成 | — |
| `abandoned` | 已废弃 | — |
| `publish_failed` | 发布失败 | `publishing`（重试）, `frozen`, `abandoned` |
| `frozen` | 自动流程冻结，等待人工裁决 | `contracting`, `drafting`, `reviewing`, `publishing`, `abandoned` |
| `waiting_human` | 策略要求人工处理或抽检 | `drafting`, `approved`, `stored`, `abandoned`, `frozen` |
| `stored` | 已存入草稿池，暂不发布 | `drafting`, `publishing`, `abandoned` |
| `draft_only` | 只生成草稿，不允许发布 | `stored`, `abandoned`, `waiting_human` |
| `not_writing` | 系统决定不写，并已记录理由 | — |

### 3.2 状态转换图

```
pending → contracting → drafting → reviewing → approved → publishing → published → collecting → completed
                            ↑          │                                  │
                            └──────────┘ (自动重写/返工)                  │
                            ↕                                            ▼
                        契约演进(不增加rework_count)              publish_failed
                                       │                                 │
                                       ▼                                 ▼
                                                        waiting_human / stored / draft_only / not_writing
```

## 四、质量状态（quality_status）

### 4.1 状态定义

| 状态 | 说明 | 可转换到 |
|------|------|---------|
| `pending` | 尚未进入质量门禁 | `structure_checking` |
| `structure_checking` | ODD结构门禁检查中 | `structure_passed`, `structure_blocked` |
| `structure_passed` | 需求/规格/契约/证据链可判定 | `es_checking` |
| `structure_blocked` | 规格缺失、过期、冲突或不可回滚 | `pending`（复审后）, `strategy_decision` |
| `es_checking` | ES机械合规检查中 | `es_passed`, `es_failed` |
| `es_passed` | ES通过，待半ES | `ses_checking` |
| `es_failed` | ES失败，需返工 | `pending`（返工后） |
| `ses_checking` | 半ES语义检查中 | `ses_passed`, `ses_warned` |
| `ses_passed` | 半ES通过，无警告 | `strategy_decision` |
| `ses_warned` | 半ES通过但有警告 | `strategy_decision` |
| `strategy_decision` | 策略矩阵裁决中 | `passed`, `rework`, `sample_review`, `waiting_human`, `stored`, `failed` |
| `sample_review` | 等待人工抽检 | `passed`, `rework`, `waiting_human`, `failed` |
| `passed` | 策略裁决或抽检通过 | — |
| `rework` | 系统或人类要求重写/返工 | `pending`（返工后） |

### 4.2 质量状态与管线状态的关系

```
pipeline_status: drafting → reviewing → approved
                                │
                                └── quality_status 在此期间演进：
                                    pending → structure_checking → structure_passed
                                    → es_checking → es_passed
                                    → ses_checking → ses_passed
                                    → strategy_decision
                                    → passed / rework / sample_review / waiting_human / stored
```

管线状态 `reviewing` 期间，质量状态独立演进。质量状态到达 `passed` 后，管线状态才能转换到 `approved`。

实际执行时，`pending` 会先进入 `structure_checking`；结构门禁通过后才进入 `es_checking`。若返回 `NEEDS_CTF_REVIEW`，任务不计入返工，先回到 RSC/CTF 复审。

## 六、认知状态（cognition_status）

### 6.1 状态定义

| 状态 | 说明 | 可转换到 |
|------|------|----------|
| `not_started` | 尚未形成认知轨迹 | `tracing` |
| `tracing` | 正在记录属性识别、趋势预测和边界判断 | `evidence_claiming` |
| `evidence_claiming` | 正在抽取候选 EvidenceClaim | `falsification_checking`, `evidence_gap` |
| `falsification_checking` | 正在做反证和证据风险检查 | `cognition_ready`, `boundary_required` |
| `cognition_ready` | 认知轨迹和断言检查达到当前阶段要求 | — |
| `evidence_gap` | 存在关键证据缺口 | `falsification_checking`, `boundary_required` |
| `boundary_required` | 需要边界决策：不写、只草稿、等人或冻结 | `cognition_ready` |

### 6.2 与任务流的关系

```text
pending/contracting
    -> cognition_status=tracing
    -> evidence_claiming
    -> falsification_checking
    -> cognition_ready
    -> drafting/reviewing/approved
```

发布级任务在 `approved` 前必须满足：

```text
cognition_status = cognition_ready
AND cognition_trace_ids 非空
AND 高风险 EvidenceClaim 已验证或被人类接受风险
```

若 `boundary_decision=not_write`，任务进入 `not_writing`，并生成证据和事件；若 `boundary_decision=draft_only`，任务可生成草稿但 `publish_status=skipped`。

## 七、Flags（叠加标记）

### 7.1 标记定义

| Flag | 含义 | 谁设置 | 谁清除 |
|------|------|--------|--------|
| `checking` | 正在进行自动检查 | 质量门禁系统 | 检查完成 |
| `ai_working` | AI正在生成内容 | 写作引擎 | 生成完成 |
| `human_override` | 需要人工介入 | 策略 fallback 要求人类 / 发布失败 / 红灯 | 人类处理完毕 |
| `drift_alert` | 内容偏离契约 | 质量门禁 | 人类确认 |
| `frozen` | ODD门禁返回FREEZE/CONFLICT | 质量门禁/任务调度/发布引擎 | 人类解封后 |
| `cognitive_disturbance` | 预测失准、理论漂移、证据过期、反证命中 | 进化控制台 | 扰动事件关闭 |
| `evidence_gap` | EvidenceClaim 缺少来源、保鲜期或验证方式 | ClaimGraph/质量门禁 | 补证据或人类接受风险 |
| `algorithm_noise` | 内部质量高但外部表现异常低，疑似平台算法或环境噪音 | 数据回收/发布引擎 | 观察窗口结束或人类裁决 |

### 7.2 Flags 与阻断

大多数 Flags 是信息性标记，不阻断状态转换；`human_override` 和 `frozen` 是例外，必须等待人类动作。例如：
- `ai_working=True` 时，pipeline_status 可以正常推进
- `drift_alert=True` 时，质量门禁仍然可以给出 `passed`（如果偏差是生产性的）
- `human_override=True` 时，需要人类动作后才能继续；但策略允许“人类无时间”时可按 fallback 存草稿或放弃
- `frozen=True` 时，自动推进必须停止，只允许人工解封后进入明确的后续状态
- `evidence_gap=True` 时，不允许自动发布，只能补证据、只存草稿或等待人类裁决
- `algorithm_noise=True` 时，不判定理论失败，不自动降权；任务可转常青维护、探索模式或延长观察

## 九、调度模式

### 9.1 四种模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **单产出模式（Single Artifact Mode）** | 一个子片场执行任务（SubStudioExecutionTask）走完全流程 | 临时内容、低复杂度内容 |
| **片场模式（Studio Mode）** | 一个片场（Studio）固定生成环境，开启多个子片场（SubStudio）并行产出 | 日常运营、专题运营、批量生产 |
| **赛马模式（Race Mode）** | 同一产出计划（ArtifactPlan）生成多个候选版本，选优后封存 | 高价值产出物、标题/开头/卡片对比 |
| **实验策略模式** | 使用实验策略小流量生成或发布 | 策略优化验证 |

### 9.2 片场模式

```
今日子案（DaySubCase）
  -> 片场（Studio）: 固定生成环境
      ├── 产出计划集（ArtifactPlanSet）
      │   ├── 产出计划（ArtifactPlan）: 知乎长文
      │   ├── 产出计划（ArtifactPlan）: 小红书图文
      │   └── 产出计划（ArtifactPlan）: 微博短帖
      └── 子片场（SubStudio）
          └── 子片场执行任务（SubStudioExecutionTask）
              -> 产出物（Artifact）

片场约束（Studio Constraints）：
- 片场（Studio）是固定生成环境，不等于“主题 × 多平台任务”的临时分组
- 同一片场内固定账号（Account）、平台（Platform）、受众状态（AudienceState）、内容形态（ArtifactType）、理论显性度（TheoryVisibility）和操作上下文包（OperationContextPack）
- 任一固定环境变量变化，必须建立新片场（Studio）
- 片场只负责生成环境和一致性；一个具体产出物由一个子片场（SubStudio）完成
- 子片场之间独立流转，互不阻塞；片场级门禁只检查环境一致、角度互补、重复与漂移
- 缓存复用只是实现收益，不是片场定义
```

**用户故事：片场模式端到端场景（2026年6月第二周）**

```
周一 08:00 — 周案（WeekCase）约束今日海域，日案（DayCase）列出三个主题（Theme）
周一 08:10 — 日案（DayCase）+ 主题A 形成今日子案（DaySubCase）
周一 08:20 — 秘书按账号、平台、受众状态和理论显性度建立知乎片场（Studio）
周一 08:30 — 片场内生成产出计划集（ArtifactPlanSet）：长文、问答、评论跟进
周一 08:40 — 每个产出计划（ArtifactPlan）开启一个子片场（SubStudio）
周一 10:00 — 子片场各自产出一个产出物（Artifact），再分别走部件门禁、组装门禁和产出物门禁
周一 20:00 — 授权策略（DelegationPolicy）允许的产出物自动打包为发布包（PublicationPackage）并发布
周二以后   — 信号事件（SignalEvent）进入事件账本（EventLedger），只形成策略提案、保留模式候选或反哺候选
```

### 9.3 赛马模式

```
Race（赛马）
  ├── candidate_001: ArtifactPlan × 模型A → ArtifactVersion
  ├── candidate_002: ArtifactPlan × 模型B → ArtifactVersion
  └── candidate_003: ArtifactPlan × 温度0.9 → ArtifactVersion

赛马约束：
- 同一产出计划（ArtifactPlan）、同一写作契约（ArtifactContract）和同一子片场（SubStudio）边界
- 候选版本是产出物版本（ArtifactVersion），不是多个独立产出物（Artifact）
- 生成后由策略裁决、秘书或人类选优；未选中版本进入 archived，不作为发布包
```

### 9.4 实验策略模式

```
Experiment
  ├── strategy_unit: su_zhihu_sub_hot_long_theory_high
  ├── base_strategy_version: v12
  ├── experiment_strategy_version: v13-exp
  ├── scope: draft_only | small_traffic_publish | sample_before_publish
  └── rollback_policy: revert_to_v12
```

实验策略不直接覆盖主策略。实验结果进入进化控制台，由蓝灯/黄灯提示是否晋升。
