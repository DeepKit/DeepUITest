# 07 Part A: 通用 SourcePack 装载契约

> 核心定位：SourcePack Loader Contract 定义任意源体系如何进入 ArtifactOS。它把“一元论 SourcePack”从首个样板提升为通用装载机制，避免系统只适配一个高度结构化理论仓库。

---

## 一、目标

通用 SourcePack 装载契约要回答：

1. 什么材料可以被装载为 SourcePack。
2. 装载前要诊断哪些结构缺口。
3. 冲突、过时、禁忌和边界如何表达。
4. 什么状态下可以进入产出流水线。
5. 什么状态下只能做整理，不能生成外发内容。

ArtifactOS 不能假设用户的源材料都像一元论一样结构化。商业客户的源体系通常来自访谈、PPT、课程、产品文档、文章、聊天记录、案例和零散笔记。装载契约必须先治理输入，再允许 AI 生成。

---

## 二、SourcePack 类型

| 中文类型 | English Type | 典型来源 | 主要风险 |
|---|---|---|---|
| 理论体系包 | `theory_system` | 母板、论文、解释稿、实践协议 | 主张强度越界、概念误用 |
| 创始人观点包 | `founder_voice` | 访谈、演讲、内部信、产品哲学 | 语气失真、战略误读 |
| 品牌主张包 | `brand_positioning` | 品牌手册、官网、案例、FAQ | 空泛营销化、禁忌遗漏 |
| 产品资料包 | `product_knowledge` | 产品文档、路线图、客户案例 | 功能过度承诺、版本过期 |
| 专业方法论包 | `service_methodology` | 咨询框架、交付模板、案例库 | 专业责任边界不清 |
| 课程体系包 | `course_system` | 课程大纲、讲义、作业、社群问答 | 知识层级混乱、片段化 |
| 研究材料包 | `research_corpus` | 论文、报告、数据、读书笔记 | 证据强度混淆、来源不明 |

一套 SourcePack 可以有多个类型标签，但必须有一个主类型（Primary Pack Type）。

---

## 三、装载成熟度

SourcePack 装载成熟度（SourcePack Loading Level, SPL）决定系统能做什么。

| 等级 | 中文 | English | 可用能力 |
|---|---|---|---|
| SPL0 | 原始材料 | Raw Corpus | 只能整理、摘要、诊断 |
| SPL1 | 已识别边界 | Boundary Identified | 可生成内部草稿，不可发布 |
| SPL2 | 已形成清单 | Manifest Ready | 可生成候选契约和试写稿 |
| SPL3 | 可产出 | Production Ready | 可进入质量门禁和前夜审阅 |
| SPL4 | 可运营 | Operating Ready | 可进入成熟策略单元和批量产出 |

SPL 不是质量评价，而是治理可用性。源材料再有价值，如果边界、版本、禁忌和主张强度不清，就不能直接进入发布流水线。

## 四、装载流程

```text
SourceImport
  -> SourceInventory
  -> SourceReadinessReport
  -> SourceConflictReport
  -> SourcePackManifest
  -> SourcePackSnapshot
  -> SourcePackLoadingDecision
```

### 4.1 SourceInventory

源材料清单（SourceInventory）记录所有导入材料：

| 字段 | English Field | 说明 |
|---|---|---|
| 文件路径 | `source_path` | 本地路径或外部引用 |
| 来源类型 | `source_origin` | 人工上传、仓库、访谈、网页、旧系统 |
| 内容类型 | `content_kind` | 文档、音频转写、PPT、代码、表格 |
| 估计权威性 | `authority_hint` | 用户声明或系统推断 |
| 时间信息 | `time_scope` | 创建时间、适用时间、过期风险 |
| 敏感性 | `sensitivity_level` | 公开、内部、敏感、禁止外发 |

### 4.2 SourceReadinessReport

源体系就绪报告（SourceReadinessReport）回答“能不能开始产出”：

| 维度 | English Metric | 检查内容 |
|---|---|---|
| 结构完整度 | `structure_coverage` | 是否有层级、模块、主题、边界 |
| 权威性清晰度 | `authority_clarity` | 哪些文件说了算 |
| 版本清晰度 | `version_clarity` | 是否存在过期或冲突版本 |
| 禁忌清晰度 | `boundary_clarity` | 哪些不能说、不能承诺 |
| 引用可追溯性 | `traceability` | 能否从产出反查源材料 |
| 产出可用性 | `production_readiness` | 是否能进入契约和门禁 |

### 4.3 SourceConflictReport

源体系冲突报告（SourceConflictReport）记录：

- 同一概念的不同定义。
- 新旧版本冲突。
- 创始人表达与品牌手册冲突。
- 对外公开口径与内部材料冲突。
- 专业判断与合规边界冲突。
- AI 推断与源材料原文冲突。

冲突不能由 AI 静默解决。只能形成：

```text
keep_primary
mark_as_historical
requires_human_decision
exclude_from_generation
split_by_context
```

## 六、层级模型

通用 SourcePack 至少支持以下层级：

| 层级 | English Layer | 作用 |
|---|---|---|
| 治理层 | `governance` | 命名、边界、使用规则 |
| 核心层 | `canonical` | 当前最高权威材料 |
| 解释层 | `explanation` | 面向公众或客户的解释材料 |
| 案例层 | `case` | 案例、故事、客户场景 |
| 证据层 | `evidence` | 数据、引用、报告、外部材料 |
| 表达层 | `expression` | 语气、风格、标题、句式样本 |
| 归档层 | `archive` | 历史材料，默认不进入当前口径 |

不同 pack type 可以扩展层级，但不能缺少 `canonical` 或等价权威层。商业客户若只有访谈、PPT、案例和零散笔记，可以先生成权威候选（CanonicalCandidate），但必须经人类确认后才可成为正式权威层。

权威模型（AuthorityModel）允许四种：

| authority_model | 说明 |
|---|---|
| `explicit_canonical` | 用户已经提供明确权威文件或母板 |
| `human_approved_synthesis` | Amy 从零散材料合成权威候选，人类批准后生效 |
| `latest_effective_version` | 以最新有效版本作为当前口径 |
| `source_priority_rule` | 按用户确认的来源优先级裁决冲突 |

若只有未批准的 `CanonicalCandidate`，装载成熟度最高只能到 SPL2；要进入 SPL3/SPL4，必须形成已批准的权威模型和当前口径。

---

## 七、装载决策

SourcePackLoadingDecision 决定下一步动作：

| 决策 | English Decision | 含义 |
|---|---|---|
| 继续整理 | `organize_only` | 材料不足，只做清单和诊断 |
| 等待人类裁决 | `wait_human_decision` | 存在关键冲突 |
| 允许试写 | `allow_trial_generation` | 可生成内部候选 |
| 允许影子运行 | `allow_shadow_run` | 可进入 7 天影子运行 |
| 允许正式产出 | `allow_production` | 可进入门禁和发布预案 |
| 冻结装载 | `freeze_loading` | 边界或敏感材料风险过高 |

---

## 八、失败边界

以下情况不得进入发布级生成：

1. 没有权威层或当前口径。
2. 禁忌和责任边界不清。
3. 大量材料版本冲突且无人裁决。
4. 高风险领域缺少专业审校规则。
5. 源材料中含有禁止外发或隐私信息但未标注。
6. 归档材料与当前口径混用。
7. 用户只提供少量营销口号，没有可治理源体系。

失败不是项目失败，而是装载阶段需要继续整理。

## 九、Phase 1A 最小实现

首版至少实现：

- `SourceInventory`
- `SourceReadinessReport`
- `SourceConflictReport`
- `SourcePackManifest`
- `SourcePackSnapshot`
- `SourcePackLoadingDecision`
- SPL0-SPL4 枚举
- `theory_system` 与 `founder_voice` 两类模板

一元论 SourcePack 使用 `theory_system` 模板；商业试点优先增加 `founder_voice` 或 `service_methodology` 模板，验证通用性。

---

## 十、硬约束

1. SourcePack 不能被当作普通 RAG 文件夹。
2. SourcePackSnapshot 必须冻结生成时刻使用的源体系版本。
3. 装载冲突不能由 AI 静默裁决。
4. SPL0/SPL1 不得进入发布级生成。
5. archive 默认排除，人工点名也必须标注历史口径。
6. SourcePack 的所有权属于用户或组织，不属于 ArtifactOS。
7. 任何源体系反补必须形成候选和人类裁决，不得自动改母板。

# 16 一元论 SourcePack 装载方案

> ArtifactOS 首个自用源体系样板：把 `D:\_Progs\一元论` 装载为可治理、可追溯、可外发、可反馈候选化的 `SourcePack`

---

## 一、定位

`一元论 SourcePack` 是 ArtifactOS 的第一套高复杂度源体系样板。

它不是把 `D:\_Progs\一元论` 当作普通 RAG 文件夹，也不是让 AI 随机读取理论材料后写文章。它要把一元论仓库中已经存在的层级、母板、解释稿、实践稿、发布记录、归档边界和 AI 协作规则，装载成 ArtifactOS 可运行的源体系契约。

首版目标：

```text
源体系装载 -> 场域定位 -> 产出契约 -> 媒体产出物 -> 发布痕迹 -> 反馈候选 -> 人类裁决
```

ArtifactOS 只负责媒体产出物系统，不负责接引、承接、咨询、治疗、成交或用户关系运营。

本文件只描述一元论样板的装载规则。通用 SourcePack 装载契约、SPL0-SPL4 装载成熟度、就绪报告和冲突报告见 `07.[模型]-SourcePack装载-Loading.md`。

---

## 二、为什么不能做成普通知识库

一元论仓库已经有强治理结构：

- `01-母板/` 是唯一真相源
- `02-学术/` 负责可审、可投稿、可引用
- `03-解释/` 负责对外理解
- `04-实践/` 负责低风险协议、检查表和停止条件
- `85-发布管理/` 负责 DOI、投稿、发布事实
- `90-跨层组合/` 只做组合解释，不产生新法源
- `99-归档/` 是历史材料，默认不进入当前口径
- `*-4AI.md` 是 AI 协作者入口，不等同于公开文章入口

如果把这些文件混在一个向量库里，会产生三类风险：

1. **母板被派生稿反向污染**：解释稿、传播稿、旧稿被误当成当前真相源。
2. **主张强度失控**：C2/C3 的解释框架被写成 C5 实证定论。
3. **旧口径复活**：归档中的历史强表述重新进入外发材料。

因此，`SourcePack` 的首要职责不是检索，而是源体系治理。

## 四、SourcePack 层级模型

### 4.1 源文件分层

每个源文件进入系统时必须标注 `source_layer`：

| source_layer | 含义 | 默认使用方式 |
|--------------|------|--------------|
| `governance` | 仓库级治理、命名、注册、边界 | 先读，约束所有产出 |
| `canonical` | 母板、唯一真相源 | 作为断言和边界的最高依据 |
| `academic` | 学术稿、spec、投稿、DOI 材料 | 学术型产出优先引用 |
| `explanation` | 面向公众的解释稿 | 面向知乎/公众号等公开文章优先引用 |
| `practice` | 实践协议、检查表、停止条件 | 仅在低风险、边界明确场景引用 |
| `tool_case` | 工具、案例、评审记录 | 作为示例和论证辅助 |
| `publication` | DOI、投稿、发布管理 | 作为发布事实和引用记录 |
| `cross_layer` | 跨层解释或实践组合 | 只做组合，不产生法源 |
| `archive` | 历史归档、旧口径 | 默认排除，人工点名才可引用 |

### 4.2 引用优先级

当同一概念在多个文件中出现时，默认引用顺序是：

```text
governance -> canonical -> academic -> explanation -> practice -> tool_case -> publication -> cross_layer -> archive
```

`archive` 不参与默认检索。若用户明确要求研究历史演化，系统必须在产出物中标注“历史口径 / 非当前法源”。

### 4.3 主张强度

SourcePack 必须继承一元论治理原则中的主张强度标签：

| 标签 | ArtifactOS 处理方式 |
|------|---------------------|
| C1 观察语言 | 可用于现象显影、经验描述、文章开头 |
| C2 分析框架 | 可用于组织问题、分类、比较 |
| C3 协议 / 假说 | 可用于方法说明、候选解释、行动前置 |
| C4 规范性边界 | 可用于禁止项、停止条件、责任边界 |
| C5 经验证实理论 | 默认禁止生成，除非源文件明确提供充分实证依据 |

默认规则：不把解释力写成实证定论，不把理论语言写成治疗、诊断、法律、投资或工程放行承诺。

## 五、PFM 灯塔策略在 ArtifactOS 中的产品化

用户当前确认的核心链路是：

```text
找场 -> 立灯塔 -> 发光 -> 吸引人
```

ArtifactOS 对应实现：

| PFM 概念 | ArtifactOS 对象 | 系统职责 |
|----------|----------------|----------|
| 找场 | `FieldMap` / `FieldHypothesis` | 识别知乎等平台上的问题场、话题场、误解场 |
| 立灯塔 | `StrategyUnit` / `AccountPosition` | 定义账号定位、平台、理论介入方式、表达高度 |
| 发光 | `ArtifactContract` / `Artifact` | 产出文章、图文、短稿、声明、FAQ、卡片等载体 |
| 吸引人 | `SignalLedger` | 记录阅读、收藏、转发、评论、引用、误读等场域信号 |

### 5.1 不做推销式漏斗

ArtifactOS 不把 S0-S7 理解为 CRM 销售漏斗。它只把 S0-S7 作为读者认知状态假设，用于决定内容形态和表达深度。

任何面向单个读者或读者群体的状态识别都只能形成受众状态假设（AudienceStateHypothesis），并记录 `evidence_refs / confidence / uncertainty / alternative_states`；系统不声称读取真实心理。

```text
S0 不知道你 -> 用问题场显影文章
S1 觉得有点像自己 -> 用经验共鸣文章
S2 愿意继续读 -> 用框架解释文章
S3 开始认可局部判断 -> 用案例/对照文章
S4 愿意转发给同类人 -> 用高共鸣观点稿或图文卡片
S5 认可方法论价值 -> 用体系入口文章
S6 主动收藏/引用/搜索更多 -> 用索引、系列文、FAQ
S7 成为信徒或传播种子 -> 用宣言、长文、公开法源、专题包
```

系统只负责让不同认知状态的人有机会被“光”照见，不负责私聊、催转化、成交、接引和承接。

### 5.2 首个平台

首版默认平台：

```text
platform: 知乎
mode: 公开文章 / 回答 / 系列长文
goal: 发光与显影，不做互动运营
handoff: 站点或小程序承接属于其他系统，不进入 ArtifactOS 当前范围
```

## 六、反补机制

ArtifactOS 可以收集反馈，但不能自动修改源体系。

### 6.1 反馈来源

允许进入 `SignalLedger` 的反馈包括：

- 阅读、点赞、收藏、转发等平台表现
- 评论中的误读、高共鸣、反对、追问
- 外部引用、二次传播、收藏夹命名
- 人类抽检意见、修改意见、发布后复盘
- 反证材料、证据过期、外部事件变化

### 6.2 反馈分流

反馈进入系统后分为四类：

| 类型 | 作用范围 | 是否反补源体系 |
|------|----------|----------------|
| `production_tuning` | 标题、结构、表达、平台适配 | 不反补，只改生产策略 |
| `audience_signal` | 场域、认知状态、共鸣点 | 不反补，只校准灯塔位置 |
| `misreading_record` | 高频误读、边界混淆 | 生成解释层或 FAQ 候选 |
| `backfeed_candidate` | 可能影响理论映射、案例、反例、边界 | 只生成候选，等待人类裁决 |

### 6.3 人类裁决

任何反补源体系的动作都必须经过 `HumanDecision`：

```text
SignalLedger
  -> BackfeedCandidate
  -> HumanDecision
  -> SourcePackPatch / TheoryRevisionProposal / Reject / Archive
```

ArtifactOS 不直接修改 `D:\_Progs\一元论` 的母板，也不把运营数据当作理论正确性的自动证据。

## 七、SourcePack 必须实现的门禁

| 门禁 | 检查内容 | 失败动作 |
|------|----------|----------|
| `CanonicalGate` | 是否引用了当前母板或治理入口 | 降级为草稿或要求补源 |
| `LayerGate` | 是否混淆母板、解释、实践、归档 | 阻断发布 |
| `ClaimStrengthGate` | 是否把 C1-C3 写成 C5 | 阻断或降级措辞 |
| `ArchiveExclusionGate` | 是否默认引用归档旧口径 | 阻断并要求人工确认 |
| `BoundaryGate` | 是否越过医疗、心理、法律、投资、工程放行等边界 | `freeze` / `wait_human` |
| `PFMNoSalesGate` | 是否把吸引式显影写成推销、催化、成交话术 | 返工 |
| `NoAutoTheoryMutationGate` | 是否试图自动改源体系核心原则 | 阻断 |
| `EvidenceGate` | 关键事实、引用、外部判断是否有证据 | 阻断或标注假设 |

这些门禁应优先进入 `05.[模型]-写作契约-Contract`、`12.[流程]-质量门禁-Quality-Gate` 和 `19.[认知]-证据认知与进化-Evidence-Evolution` 的后续实现。

## 九、首版验收标准

Phase 1 自用版必须能完成：

1. 从 `D:\_Progs\一元论` 建立 `SourcePackManifest`
2. 区分治理、母板、学术、解释、实践、发布、跨层、归档
3. 装载三链十一模块的身份、边界、最小输入输出和失败边界
4. 为知乎文章生成 `ArtifactContract`
5. 在契约中明确目标读者认知状态、场域、灯塔高度和表达方式
6. 在草稿生成时注入正确层级的源材料
7. 质量门禁能识别主张强度越界、归档误引、承接越界和推销化表达
8. 发布后反馈进入 `SignalLedger`
9. 反馈先进入 `EventLedger`，经遗忘系统提炼后只能形成 `RetainedPattern`、`RecallCard` 或 `BackfeedCandidate`
10. 任何源体系反补必须由人类确认

首版不要求：

```text
多租户商业化
完整图数据库
自动修改理论母板
接引/承接/咨询系统
私域互动运营
爆款预测
全平台全媒体覆盖
```

## 十、从 SPL2 到 SPL3 的差距与推进路径

一元论作为高结构化的理论仓库，SPL0-SPL2 天然满足：已有 README、7 个必读注��文件、母板和各级材料。从 SPL2（Manifest Ready，可生成候选契约和试写稿）到 SPL3（Production Ready，可进入质量门禁和前夜审阅），需解决三个关键差距：

### 10.1 主张强度标签的结构化映射

现有 C1-C5 主张强度以 Markdown 元信息存在。SPL3 要求将它们转为 `SourcePackManifest` 中结构化字段：

```yaml
claim_strength_map:
  - source_path: "01-母板/DM.md"
    claim_level: C5
    default_propagation_limit: theory
  - source_path: "03-解释/"
    default_claim_level: C2
    max_claim_level: C3
    rule: "不得把解释稿当成实证定论"
```

映射规则：母板保持 C5 但需人工确认 C5 证据充分性；解释稿默认 C2；实践稿最多 C3；归档材料自动 C0 进入排除区。

### 10.2 层级冲突检查

必须运行一次全量 SourceConflictReport，覆盖 4 对跨层对照：

| 对照对 | 检查项 |
|--------|--------|
| 母板 vs 解释稿 | 是否把强命题弱化或误写成其他口径 |
| 解释稿 vs 实践稿 | 低风险协议是否引用了过时口径 |
| 发布记录 vs 当前母板 | DOI/投稿中的表述是否仍与最新母板一致 |
| 归档 vs 当前口径 | 是否有机取回了已废弃表述 |

冲突不能由 AI 静默裁决，只能 `keep_primary / mark_as_historical / requires_human_decision / exclude`。

### 10.3 SourcePackSnapshot 生成时机

必须每次产出前冻结，而不是每日冻结。原因是同一日内母板、解释稿、实践稿和归档可能被人类修订，两次产出如果跨修订窗口，需要归属于不同快照。

```text
ArtifactPlan 生成前: take SourcePackSnapshot
Artifact 使用 snapshot_id
QualityRun 引用 snapshot_id
PublicationPackage 绑定 snapshot_id
```

### 10.4 非文字材料的处理

图表、PPT、视频等在 SourceInventory 中注册为 `content_kind=image/audio/video/presentation`，受约束：

- AI 不得将其中的图表语义解释为替代原文的法源
- 只能作为补充材料引用，或标注"人工可审"
- 敏感材料必须标注 `sensitivity_level` 和 `exclude_from_generation`

### 10.5 首版装载正确性的验证

没有旧系统对照时，依赖三个信号判断装载是否合格：

```text
1. 主张强度正确性 —— 人类抽检 SourcePackSnapshot 的 C 层级分布
2. 层级冲突已裁决 —— SourceConflictReport 中没有 requires_human_decision 为 open 的高风险项
3. 结构忠实度门禁通过 —— 首轮 S08 SourceMapping 验证 required_relations / forbidden_relations 无违例
```

## 十二、一元论 SourcePack 自动候选标注规则

`D:\_Progs\一元论` 的首次装载采用“自动候选标注 + 人类确认晋升”模式。系统可以扫描目录并提出 `SourceInventoryCandidate`，但不能把候选自动晋升为当前法源。

| 目录特征 | 默认 `source_layer` | 默认处理 |
|---|---|---|
| `母板` / `master` / `canonical` | `canonical_candidate` | 需要人类确认后才能成为 `canonical` |
| `学术` / `paper` / `academic` | `evidence` | 可进入证据层，但主张强度需确认 |
| `解释` / `explain` | `explanation` | 可用于对外解释，不得反向污染母板 |
| `实践` / `protocol` / `checklist` | `practice` | 可用于流程、检查表、停止条件 |
| `发布` / `article` / `public` | `published_expression` | 可作为表达样例，不等同理论法源 |
| `归档` / `archive` / `old` | `archive` | 默认排除生成，只可用于历史演化研究 |
| `4AI` / `AI` | `ai_collaboration_entry` | 可作为 AI 协作入口，不等同公开入口 |

自动扫描只能生成 `candidate_claim_strength`，不能生成最终 `claim_strength`。未经人类确认的 `canonical_candidate` 最高只能使 SourcePack 达到 SPL2；SPL3 必须有已确认当前母板、禁忌、边界和可外发策略。任何旧口径复活必须生成 `SourceConflictReport` 和 `HumanDecision`。
- 行业研究框架
- 专业服务案例库
- 组织价值观和表达禁忌

通用抽象是：

```text
有源体系的人，用 ArtifactOS 把源体系变成可治理的媒体产出物。
```

一元论样板的价值在于它复杂、分层严密、边界要求高。只要 ArtifactOS 能正确装载一元论，装载普通品牌、课程、产品资料和专业方法论会更容易。

这个判断仍需通过多 SourcePack 干跑验证，不能只从一元论样板推断商业通用性。Phase 1A 之后应至少用 `founder_voice`、`service_methodology` 或 `product_knowledge` 类型做 2-3 次干跑，再进入商业试点。
