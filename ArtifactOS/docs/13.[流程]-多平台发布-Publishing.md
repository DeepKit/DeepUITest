# 13 多平台适配发布引擎

> 系统编号：⑦
> 子品牌：行铸 PraxisForge
> 核心职责：将产出物（Artifact）适配为渲染版本（Rendition）和发布包（PublicationPackage），并按策略单元执行自动发布、抽检发布、暂存、召回、现实反馈回收和证据封存
> 设计来源：Adobe「内容供应链Activate阶段」、media_publish 现有架构

---

## 一、设计理念

### 1.1 核心问题

同一个源体系输入（SourcePack）可以产出不同媒体对象。平台适配不是“把一篇定稿改格式”，而是把产出物（Artifact）按产出物蓝图（ArtifactBlueprint）渲染为目标平台可提交的发布包（PublicationPackage）：

| 平台 | 内容形态 | 字数 | 格式 | 风格 |
|------|---------|------|------|------|
| 知乎 | 长文 | 2000-3500 | Markdown→富文本 | 深度、理性 |
| 公众号 | 推文 | 1500-3000 | 微信排版 | 精致、有温度 |
| 小红书 | 卡片 | 300-600 | 图文卡片 | 轻量、视觉 |
| 微博 | 帖子 | 140 | 文字+话题 | 精炼、话题化 |

### 1.2 核心原则

1. **产出物驱动发布**：发布引擎消费产出物（Artifact）和发布包（PublicationPackage），不直接消费散落草稿
2. **适配器解耦**：每个平台一个适配器，互不影响
3. **策略授权发布**：自动发布由策略单元授权、质量门禁、红线和封存证据共同决定
4. **发布后存证**：截图、URL、发布状态全部记录
5. **发布物可召回**：发布物必须记录封存版本、证据包和召回/下架路径
6. **人类可降权**：人类可随时暂停某个策略单元的自动发布能力
7. **发布是现实介入**：每次发布都要绑定 `CognitionTrace`，用于验证系统此前的趋势预测和边界判断
8. **反馈回流 ClaimGraph**：发布后的负反馈、纠错和反例评论要能影响 `EvidenceClaim` 的置信度
9. **发布包门禁前置**：发布包门禁（PackageGate）通过前，不调用任何平台发布适配器或旧版 `media_publish`

## 二、系统架构

### 2.1 三模块架构

```
产出物（Artifact）输入
    │
    ▼
产出物门禁（ArtifactGate）与封存检查（seal + evidence_bundle）
    │
    ▼
┌────────────────┐
│ A. 渲染适配器   │  Artifact + ArtifactBlueprint → Rendition
└───────┬────────┘
        │
        ▼
┌────────────────┐
│ B. 发布包构建器 │  Rendition + Account + Schedule → PublicationPackage
└───────┬────────┘
        │
        ▼
┌────────────────┐
│ C. 发布调度器   │  策略裁决、排期、执行发布
└───────┬────────┘
        │
        ▼
┌────────────────┐
│ D. 数据回收器   │  发布后数据采集、归因分析
└────────────────┘
```

### 2.2 发布对象模型

| 对象 | 英文名 | 职责 |
|------|--------|------|
| 产出物 | Artifact | 可治理、可封存、可发布的媒体对象 |
| 产出物部件 | ArtifactPart | 文案、图片、视频、音频、字幕、标签、链接等语义部件 |
| 资源文件 | AssetFile | 真实落盘文件，记录路径、MIME、大小、哈希和派生来源 |
| 渲染版本 | Rendition | 面向某平台/账号/规格渲染后的版本 |
| 发布包 | PublicationPackage | 交给发布适配器的最终提交材料 |

示例：小红书产出物（Artifact）可以包含多张图片、一个视频和一段文案；这些不是三个独立产出物，而是同一产出物下的多个产出物部件（ArtifactPart）和资源文件（AssetFile）。发布前会形成小红书发布包（PublicationPackage）。

平台适配不得默认“先写一篇长文，再改格式”。知乎长文、公众号文章、小红书轮播、短视频脚本都应由 `ArtifactBlueprint` 直接声明所需部件。长文拆卡只能作为 fallback，并必须记录转换证据和人工可审 diff。

```python
class ZhihuAdapter(PlatformAdapter):
    platform_id = "zhihu"

    def render(self, artifact, blueprint, contract):
        # Markdown → HTML（含结构增强）
        body_html = markdown_to_html(artifact.primary_text)

        # 应用Draft.js特殊格式（高亮等）
        # 注：实际注入在浏览器发布时执行

        return Rendition(
            platform="zhihu",
            artifact_id=artifact.id,
            title=artifact.title,
            body=artifact.primary_text,  # 原始Markdown
            body_html=body_html,     # 增强HTML
            tags=self._extract_tags(artifact),
            meta={
                "highlight_ranges": collect_short_bold_ranges(artifact.primary_text),
            }

```

知乎发布的特殊处理（复用 media_publish 现有能力）：
- `_markdown_to_html()`：Markdown→增强HTML（▣ H2标记、▸ H3标记、点分隔线）
- `_apply_draft_highlight()`：通过React Fiber注入蓝色高亮
- 完整的发布流程：打开编辑器 → 填充内容 → 预览确认 → 发布

### 3.3 小红书适配器

```python
class XiaohongshuAdapter(PlatformAdapter):
    platform_id = "xiaohongshu"

    def render(self, artifact, blueprint, contract):
        # ArtifactBlueprint 直接要求封面、轮播图、主文案、标签等部件。
        # 如果源产出物只有长文部件，拆卡只能作为 fallback，并必须留下转换证据。
        cards = artifact.parts_by_type("carousel_image")
        primary_text = artifact.part_text("primary_text")

        return Rendition(
            platform="xiaohongshu",
            artifact_id=artifact.id,
            title=self._shorten_title(artifact.part_text("title"), max_len=20),
            body=primary_text,
            tags=artifact.part_json("tag_set").get("tags", []),
            meta={
                "cards": cards,
                "cover": artifact.part("cover"),
                "video": artifact.optional_part("video"),
            }
        )

    def _split_to_cards(self, body: str) -> list[Card]:
        """Fallback：将长文拆分为候选卡片，并记录为转换证据，不作为默认路径。"""
        paragraphs = body.split("\n\n")
        cards = []
        current_card = ""
        for p in paragraphs:
            if len(current_card) + len(p) > 150 and current_card:
                cards.append(Card(content=current_card.strip()))
                current_card = p
            else:
                current_card += "\n\n" + p
        if current_card:
            cards.append(Card(content=current_card.strip()))
        return cards[:5]  # 最多5张
```

## 四、模块B：发布调度器

### 4.0 ArtifactOS 1.0 真实发布闭环

1.0 不再以 `result_url` 返回作为发布完成标准。真实发布必须形成完整闭环：

```text
PublicationPackage(status=ready, run_mode=real)
  -> RealPublishGate(L3 real_publish passed)
  -> media_publish task created
  -> task checkpoint/result_url 回写
  -> PublishedVerifier 访问 result_url
  -> published_confirmed / verify_unknown / failed
  -> Amy Desk 上报人类
```

职责边界固定：

| 系统 | 职责 |
|---|---|
| ArtifactOS | 计划、产出物、质量门禁、发布授权、状态回写、URL 自动确认、异常上报 |
| media_publish / PublishingRuntime | `(platform_id, account_id)` 常驻浏览器会话、填充内容、点击发布、发布失败重试、返回 task/result_url |

`publication_package.status` 表示流程状态，`run_mode` 表示运行级别：

```text
run_mode = shadow / simulation / parallel / real
status   = ready / queued / submitting / submitted / verify_unknown / published / failed / held / recalled
```

1.0 验收标准：

```text
published = PublishedVerifier 能访问 result_url，且页面不是登录页/404，并命中标题或正文证据。
result_unknown 不能算 1.0 发布成功，只能进入 Amy Desk 异常上报。
```

## 五、模块B：发布调度器

### 4.1 发布流程

```
发布包（PublicationPackage）
    │
    ▼
检查 Artifact.seal_id、QualitySnapshot.qualified_status、package_gate_result 与 evidence_bundle
    │
    ▼
检查 run_mode：若为 shadow/simulation → 只能执行 SimulatedPublicationAttempt（见 `docs/06.[模型]-状态机规范-State-Machine.md` §8.2、`docs/17.[交互]-前夜审阅与影子运行-Evening-Shadow.md` §八）
    │
    ▼
读取 strategy_unit.publish_permission 与 QualitySnapshot.publish_readiness
    │
        ├── auto_publish → 调用 media_publish 执行发布
    ├── sample_review → 进入人类抽检后发布
    ├── store_draft → 存入草稿池
    ├── downgrade → 生成低风险发布物或短内容
    └── wait_human → 等待人类处理
            │
            ▼
发布结果（成功/失败/需要人工）
            │
            ▼
存证（URL + 截图 + 状态 + 策略决策）
            │
            ▼
发布物封存（publication seal）
```

### 4.2 与 media_publish 的集成

```
ArtifactOS                     media_publish
┌──────────────┐                ┌──────────────────┐
│ 发布调度器    │ ──contract──→ │ publish-article   │
│              │                │ publish-answer    │
│              │ ←─result──── │ show-task         │
└──────────────┘                └──────────────────┘
```

ArtifactOS 管发布治理、门禁、调度、证据、封存和召回；`PublishingAdapter / media_publish` 只执行平台提交动作。适配器只能接收 `PublicationPackage / 发布包`，不得直接接收 `ArtifactPlan`、`SourcePack` 或 `QualityRun`，也不得自行决定是否可发布、是否高质量、是否应召回或是否改变策略。

PublishingRuntime 必须使用 `(platform_id, account_id)` 作为浏览器会话主键：

```text
zhihu/main         -> 独立常驻浏览器
wechat/main        -> 独立常驻浏览器
xiaohongshu/main   -> 独立常驻浏览器
```

禁止同一个浏览器/profile ���知乎、公众号、小红书、微博之间切换。平台切换必须切换到另一个 `PlatformAccountSession`。

ArtifactOS 调用 media_publish / PublishingRuntime 的 Python API（非CLI），传入：
- `platform_id`：目标平台，用于选择独立常驻浏览器
- `account_id`：目标账号，与 platform_id 共同构成浏览器会话主键
- `strategy_unit_id`：策略单元
- `publication_package_id`：发布包ID
- `idempotency_key`：发布幂等键
- `title`：标题
- `body`：正文（Markdown）
- `asset_files`：图片、视频、音频等资源文件
- `mode`：`manual_review` / `auto_publish` / `draft_only` / `dry_run`

media_publish 返回：
- `publisher_task_id`：发布适配器内部任务ID
- `external_draft_id`：平台草稿ID，如存在
- `status`：`not_started | submitted | draft_saved | published | failed_recoverable | failed_final | unknown | canceled`
- `finality`：结果是否最终确认
- `url`：发布后的URL（如成功）
- `evidence`：截图路径
- `error_code / error_message`：失败或未知原因

`unknown` 状态不得自动重试真实发布。系统必须先执行 `recover_status`：确认未发布才可重试，确认已发布则补写 PublicationRecord，无法确认则进入人工处理或 AdapterRecoveryAttempt。幂等键应由 tenant、publication_package_id、platform、account_id、target_publish_window 和 package_content_hash 生成；同一幂等键不得创建多个真实发布尝试。

### 6.1a 预测验证账本

发布后回收数据不是只看成败，而是验证 `CognitionTrace.trend_prediction`：

| 字段 | 含义 |
|------|------|
| `expected` | 发布前预测，如收藏高于评论、负反馈低、引流强 |
| `actual` | 发布后实际表现 |
| `calibration_delta` | 预期与实际偏差 |
| `delta_dimension` | reading / interaction / conversion / negative_feedback / theory_risk |
| `consecutive_miss_count` | 同一策略单元同一维度连续偏离次数 |
| `environment_noise_flag` | 是否疑似平台算法或外部环境噪音 |

处理规则：

- `calibration_delta` 单次严重偏离：生成 `CognitiveDisturbanceEvent(type=prediction_miss)`
- 同一维度连续 3 次偏离：生成 `StrategyChangeProposal`，挂到进化控制台黄灯或橙灯
- 内部质量分高、源体系忠实度高、证据无明显问题，但外部表现异常低：生成 `algorithm_noise_overload` 灰灯，延长观察窗口，不直接降权
- 灰灯期间默认转入常青内容维护、探索模式或小流量实验，不自动判定理论失败

### 6.2 召回与撤回

发布物满足任一条件时，进入召回评估：

| 条件 | 动作 |
|------|------|
| 发布证据损坏或不可核实 | `recall_status=pending`，暂停复用该发布物作为案例 |
| 被确认存在高风险事实错误 | 红线级风险可自动暂停/下架，事后通知人类；普通风险由人类确认 |
| 上游契约发生破坏性变更 | 下游发布物重新验证，必要时召回 |
| EvidenceClaim 被证伪 | 触发 ClaimGraph 影响分析，必要时召回 |
| 预测与反馈严重偏离 | 生成 CognitiveDisturbanceEvent，不一定召回 |
| 灰灯算法扰动 | 延长观察窗口，不召回，不降权，必要时暂停同类自动发布 |
| 平台规则变化导致内容违规 | 停止自动复发，相关策略单元降权并进入人工处理 |

## 八、media_publish 当前接入方式与 PG 化映射

当前旧发布能力位于：

```text
D:\_Progs\.BetterCiv\tools\media_publish
```

它是 Python 包，当前以 SQLite 存储任务和事件。ArtifactOS 首期不重写发布器，只通过适配层调用其手动审阅能力。

| 能力 | 当前入口 | ArtifactOS 用法 |
|---|---|---|
| 环境检查 | `media-publish doctor` | Day 0 检查 |
| 账号检查 | `media-publish check-account` | 账号 readiness |
| 文章 smoke | `media-publish smoke-article` | 影子运行预检 |
| 回答 smoke | `media-publish smoke-answer` | 影子运行预检 |
| 文章手动审阅 | `publish-article --mode manual-review` | PublicationPackage 人类确认后试提交 |
| 回答手动审阅 | `publish-answer --mode manual-review` | PublicationPackage 人类确认后试提交 |
| 启动账号浏览器 | `start-account-browser` | 账号准备与人工登录 |

Phase 1A 只允许 `manual-review`，不调用 `mode=publish`。`media_publish` 的成功状态不得直接解释为 ArtifactOS 发布成功，必须回写 `PublicationAttempt` 并经人工/证据确认。

未来 PG 化映射：`publication_tasks -> media_publish.publication_task`，`task_events -> media_publish.publication_task_event`，`account_events -> media_publish.account_event`。PG 化迁移不得破坏现有 SQLite 手动审阅路径。

多平台扩展采用统一 PublishingAdapter 接口 + 每平台 PlatformAdapter 实现模式，避免接口碎片化。

发布失败采用三级重试链路：

```text
即时重试 1 次（3 秒内同一 token）
-> 冷却后重试 1 次（变体指数退避，上限 10 分钟）
-> 超过上限或 finality=true 时进入人工接管（HumanTakeover）
-> 状态 unknown 时不允许自动重试，必须先确认发布状态后决定
```
