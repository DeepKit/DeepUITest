# 00 产品蓝图：演擎 ArtifactOS

> 源体系驱动的通用媒体产出物操作系统

## 0.1 一句话定义

演擎 ArtifactOS 是一个**源体系驱动的通用媒体产出物操作系统**：它把理论、品牌、产品资料、方法论、研究材料、个人观点库等可装载输入，与 AI 生成能力、产出契约、媒体发布、反馈信号和人类裁决连接成一条可追溯的产出链路。系统不只自动写内容，也不是为了让人类治理 AI，而是持续管理“源体系 -> 产出物 -> 发布痕迹 -> 反馈证据 -> 人类裁决”的闭环，让源体系稳定显影、形成合格产出物、获得传播放大并节省大量人工。

从产品类别看，ArtifactOS 是一种 **产出物操作系统（Artifact Operating System）**：文章、卡片、图文、视频脚本、研究札记和发布包都只是不同形态的 `Artifact`。系统通过契约、版本、证据、发布记录和反馈账本，保证产出物可生成、可校正、可封存、可召回，并允许使用者决定是否反哺源体系。

产品定位分三层，避免把首版楔子与长期愿景混在一起：

| 层级 | English Position | 定位 |
|---|---|---|
| 首个楔子 | Initial Wedge | 源体系驱动的媒体产出系统：一元论 SourcePack + 知乎 + 前夜审阅 + 影子运行 |
| 中期品类 | Product Category | 受治理的源体系到产出物流水线（Governed Source-to-Artifact Pipeline） |
| 长期愿景 | Long-Term Vision | 知识进化操作系统（Knowledge Evolution OS） |

当前冻结的内部核心命题是：

```text
Source-to-Artifact Production and Amplification Kernel
源体系到产出物生产与放大内核
```

它的主语是 `SourcePack` 和 `Artifact`，不是 AI。`CapabilityRegistry`、授权、门禁、状态机、事件账本和审计都是后台保障机制，只能服务于合格产出物生产、传播放大、源体系忠实度和人类省力，不能反客为主成为通用 AI 管理平台。

> 正式英文名：`ArtifactOS`
> 正式中文名：`演擎`
> 副标题：`源体系驱动的通用媒体产出物操作系统`

## 0.1.1 品牌架构

ArtifactOS 是总品牌，下面用四个子品牌承载完整的知识进化循环：

| 子品牌 | 英文名 | 核心职责 | 对应能力 |
|--------|--------|----------|----------|
| **观象** | `SignalScope` | 观察现实扰动、热点、异常和研究问题 | 信号采集、选题漏斗、趋势识别、写/不写判断 |
| **论演** | `TheoryWeave` | 将现象编织进理论体系并生成解释假设 | 理论映射、观点推导、理论介入度、假设契约 |
| **证链** | `ClaimGraph` | 让判断可证、可反证、可追溯、可召回 | 断言图谱、证据版本、认知轨迹、反证门禁 |
| **行铸** | `PraxisForge` | 把知识投入内容、研究和策略行动，再回收反馈 | 写作流水线、多平台发布、研究报告、策略动作 |

原先的内容生产能力不再是总产品，而是 `PraxisForge` 下的一条内容行动流水线。

## 0.1.2 五层产品模型

| 层次 | 名称 | 核心能力 | 独有价值 |
|------|------|---------|---------|
| `PL1` | 理论驱动内容流水线 | 按理论体系生成多平台内容，质量门禁把关 | 理论映射保证不失真（vs Jasper/Copy.ai 的模板填充） |
| `PL2` | 证据化认知运营 | 断言追踪、置信度校准、策略优化、AI自评降权 | EvidenceClaim 生命周期管理（无直接竞品） |
| `PL3` | 理论应用图谱引擎 | 因果原语积累、观点指纹去重、映射网络扩展 | 理论→现实的动态映射网络（vs Obsidian 等的静态连接） |
| `PL4` | 理论研究辅助 | 空缺检测、假设生成、反证检验、二级定理生长 | 面向人文社科的理论研究（vs AI Scientist-v2 面向自然科学） |
| `PL5` | 知识进化操作系统 | 个人/组织的知识体系持续进化，理论核心可被保护带生长 | 闭环进化而非静态存储（vs Second Brain/Zettelkasten） |

每层的关系：**PL1 是入口（用起来就有价值），PL2 是壁垒（用了就离不开），PL3 是积累（越用越厚），PL4 是愿景（理论开始生长），PL5 是终极形态（知识进化OS）。**

命名约束：产品层级使用 `PL1-PL5`，自治等级使用 `AL0-AL4`，RSC 澄清等级使用 `RL0-RL4`，旧系统迁移阶段使用 `LegacyStage L0-L5`，策略单元成熟度使用 `StrategyUnitMaturity M0-M4`。开发路线统一写 Phase，不使用 `M1/M2/M3` 表示里程碑；文档中不得裸写 `L3` 或 `M3` 作为跨域概念，避免“L3/M3 到底是什么”的歧义。

系统中有三条不同的"进化线"：
1. **理论体系（硬核）**：核心原则不可自动修改，只能通过人类裁决的 `TheoryRevisionProposal` 修订
2. **理论应用图谱（保护带）**：因果原语池 × 现实话题的映射网络，系统自动积累扩展
3. **写作策略（执行层）**：策略参数校准、风格优化、重写策略进化，系统自动调优

"知识进化"的精确定义：**理论应用图谱的扩展 + 写作策略的校准 + 保护带的生长**。理论核心是定海神针，不自动进化——它是被守护的。

### 0.1.2.1 竞争定位

```
         理论驱动程度 高
              |
              |         ★ ArtifactOS
              |         (PL3-PL5 证据化认知运营→理论研究→知识进化OS)
              |
              |    DeepStory
              |    (叙事驱动)
    ----------+----------→ 知识管理深度 高
              |
    Jasper /  |
    Copy.ai   |    ChatGPT 直接写
              |    (无状态生成)
              |
         理论驱动程度 低
```

ArtifactOS 独占右上象限。核心方法论：**证据化进化论**——每个判断都是可证伪的认知行动，内容不是产出终点而是知识投入现实的实践行动，反馈和反证推动系统持续进化。

护城河公式：**结构化理论资产 × 证据化运行时间 × 复水粒度 = 竞对复制成本**。系统运行越久，乘积越大。

当前开发路线从 `PL2` 起步，首期必须为 `PL3` 预埋证据化认知结构，长期向 `PL4/PL5` 演进。

## 0.1.3 知识进化闭环

ArtifactOS 的主循环是：

```text
现实扰动
-> 属性识别
-> 趋势预测
-> 理论映射 / 假设生成
-> 证据断言 / 反证检查
-> 内容、研究或策略行动
-> 场域反馈
-> 策略、知识、理论映射演进
```

其中“进化”不是简单累积知识，而是包含变异、验证、筛选、保留、降权、遗忘、主动召回和重组。系统可以提出演进建议，但核心理论原则、重大研究结论和高风险发布必须保留人类裁决权。

ArtifactOS 的长期运行采用片场制：年案（YearCase）、半年案（HalfYearCase）、季案（QuarterCase）、月案（MonthCase）、周案（WeekCase）和日案（DayCase）逐层驱动批量产出。人类面对的主入口是总制片秘书（ExecutiveProducerSecretary）；秘书代理日常调度、改稿、复审、发布排期和异常汇报，并在会议中主动召回历史决策、失败教训、强信号和反哺候选。

## 0.1.4 商业化用户画像

ArtifactOS 的早期商业化对象不是所有写作者，而是**有源体系、需要持续对外产出的人或组织**。

优先目标用户：

| 优先级 | 用户类型 | 典型问题 | 购买理由 |
|--------|----------|----------|----------|
| P1 | 理论型 / 方法论型个人 IP | 有思想资产，但难以稳定外化；普通 AI 容易写浅、写散 | 把个人思想资产变成可持续发光的媒体产出系统 |
| P2 | 创始人驱动的 B2B 公司 | 创始人认知、产品方法论和客户洞察无法被市场内容准确表达 | 把创始人认知和产品方法论变成长期内容生产底座 |
| P3 | 专业服务机构 | 专业判断、案例库和客户教育材料产出成本高，难复用 | 把专业判断转成可治理、可审校、可复用的产出链路 |
| P4 | 内容工作室 / 代运营机构 | 客户多、风格多、反馈难沉淀，AI 产出同质化 | 一个客户一个 SourcePack，一套 ArtifactContract，一套 ForgettingSystem |

暂不优先的用户：

```text
只想追热点的泛内容号
没有源体系、只要模板文案的人
短期卖货账号
依赖强互动成交的私域团队
只看爆款概率、不关心长期一致性的内容团队
```

商业化价值主张：

```text
演擎把你的源体系变成可治理、可追溯、可反哺的媒体产出系统。
```

详细用户画像、购买理由和非目标用户边界见 `21.[商业]-用户画像与价值-User-Profile.md`。

商业化证据不由首个自用 7 天影子运行单独证明。商业入口按“内部影子运行 -> 多 SourcePack 干跑 -> 设计伙伴试点 -> 30 天真实发布辅助 -> 付费/续费意愿”推进，详见 `22.[商业]-试点与信任-Pilot-Trust.md`。

第一版以 `D:\_Progs\一元论` 作为自用源体系样板，装载为 `sp_difference_monism`。

## 0.2 解决的核心问题

1. **一个人做不过来**：多账号、多平台、多主题，时间和精力严重不足
2. **AI 辅助写作不可控**：
   - 产出质量波动大，容易出现"AI味"
   - 过程不可追溯：为什么写成这样？用了什么素材？遵循了什么风格？
   - 难回滚：修改一篇文章不知道会影响哪些关联内容
3. **选题靠直觉**：没有系统化的选题方法，追热点凭感觉，常青内容无人维护
4. **素材散落各处**：读书笔记、聊天记录、灵感碎片分散在不同工具里，无法复用
5. **发布效率低**：同一主题适配不同平台需要手动重写，格式适配纯手工
6. **需求过早物化**：一个模糊方向容易被 AI 直接解释成确定契约，导致后续写作、门禁和发布都建立在错误理解上
7. **自动化无法自我校准**：普通内容系统能生成内容，但不能按账号、平台、理论介入方式持续调整策略，也不能把人类矫正转化为流水线能力
8. **知识不能进化**：多数知识库只会保存条目，不会记录判断如何形成、如何被证据支持、如何被反证推翻、如何在新场景中复水
9. **研究循环断裂**：热点观察、理论假设、证据收集、内容表达和反馈校准分散在不同工具中，无法形成可追溯的研究资产
10. **源体系层级会被普通知识库抹平**：母板、解释稿、实践稿、发布记录和归档旧稿若被等价检索，AI 会把旧口径、弱主张或派生表达误当成当前法源
11. **长期系统会被历史噪声污染**：如果把每次反馈、评论、偶然爆文和临时修改都直接注入 AI，上下文会越来越脏，策略会被短期噪声带偏
12. **人类会被多 Agent 管理成本拖垮**：如果人类每天直接管理编剧、主编、理论守门、平台适配等多个 AI 角色，系统越强，人越累

## 0.3 产品目标

- **源体系可装载**：理论、品牌、产品资料、方法论和研究材料必须先装载为 `SourcePack`，保留层级、边界、版本、禁忌和引用优先级
- **高自治运营**：成熟策略单元可以自动追热点、选题、生成、重写、发布和复盘，人类通过抽检和降权控制边界
- **策略可配置**：按 `账号 + 平台 + 内容类型 + 理论介入方式` 建立策略单元，每个单元独立配置评分矩阵、自治等级、抽检率、重写次数和发布权限
- **源体系可驱动**：理论体系、品牌主张、产品资料或方法论不是素材库，而是参与选题、角度、立场、论证路径、表达方式和发布判断的策略引擎
- **选题可量化**：任何选题都能追溯到信号来源、策略单元、理论映射、漏斗筛选和结构化评估依据
- **创作可追溯**：任何一段发布内容都能追到：写作契约、注入素材、质量评分、交互修改记录
- **产出可封存**：通过门禁的定稿、发布物和关键知识条目都有证据包和封存记录
- **错误可召回**：已发布或已注入系统的产出物若证据失效、规则冲突或高风险缺陷暴露，必须能暂停、回滚或召回
- **默认高质量**：用可配置的质量门禁和风格规则，把"AI味"变成可度量、可拒收、可返工的指标
- **低人类打扰**：人类不是固定流程节点，而是抽检者、校准者、降权者和策略裁决者
- **一人可运营**：通过原子化素材、片场制（Studio Operation）、多平台适配，一个人可以维持多个账号的持续输出
- **反馈可训练流水线**：人类的每次矫正都被系统转化为本文级、策略单元级、账号级、平台级或理论层级的训练资产
- **知识可进化**：每次生成、失败、黄灯、反证、召回和人类矫正都形成可追溯的进化事件
- **认知可审计**：关键判断必须留下 `CognitionTrace`，说明系统识别了什么属性、预测了什么趋势、采取了什么介入
- **断言可证伪**：关键事实、理论推导、价值判断和运营假设必须拆成 `EvidenceClaim`，绑定证据、置信度、保鲜期和风险级别
- **研究可生长**：系统能从内容反馈和异常信号中提出研究问题、假设契约和理论修正提案
- **案场可运营**：以案（Case）为一级治理对象，按年案（YearCase）/半年案（HalfYearCase）/季案（QuarterCase）/月案（MonthCase）/周案（WeekCase）/日案（DayCase）逐层约束；片场（Studio）负责固定生成环境，子片场（SubStudio）负责单个产出物（Artifact）
- **会议分层治理**：年计划是战略执行（Strategic Execution），半年计划是战略调整（Strategic Adjustment），季度计划是战略安排（Strategic Arrangement），月度计划是战略落地（Strategic Landing），周计划是战术安排（Tactical Arrangement），日计划是战术落地（Tactical Execution）
- **秘书可代理**：总制片秘书可以在授权范围内代理人类组织会议、调度 AI 岗位、批量改稿、复审、排期和汇报异常
- **遗忘可治理**：所有事件进入全量账本，但遗忘系统在后台做衰减、压缩、降权、归档和候选提纯，保证未来行动只激活少量高价值上下文
- **历史可主动召回**：秘书可以根据当前会议议题主动搜索历史记录，以 `RecallCard` 形式把相关决策、失败教训、强信号和反哺候选放回会议讨论
- **计划可治理变更**：全年可以动态增加计划、减少计划和调整计划，但必须通过机会候选（OpportunityCandidate）、计划变更提案（PlanChangeProposal）和计划变更记录（PlanChangeLog），不得后台静默修改年案（YearCase）

## 0.4 核心概念

### 0.4.0 知识进化对象

ArtifactOS 的核心对象不只是文章，而是“认知行动”。每次系统决定写、不写、重写、发布、暂存、召回或调参，都必须能落到以下对象：

| 对象 | 含义 | 用途 |
|------|------|------|
| `SourcePack` | 可装载源体系 | 记录源根目录、模块、层级、母板、边界、禁忌、发布记录和表达策略 |
| `SourcePackSnapshot` | 某次产出使用的源体系快照 | 冻结生成时刻的源文件版本、引用优先级和治理规则 |
| `CognitionTrace` | 本次判断的认知轨迹 | 记录属性识别、趋势预测、介入动作和反馈验证 |
| `EvidenceClaim` | 可证据化的关键断言 | 绑定来源、依赖边、作用范围、置信度、保鲜期、风险和反证状态 |
| `CognitiveDisturbanceEvent` | 触发系统重新认知的扰动事件 | 黄灯、红灯、反常数据、理论漂移、证据过期 |
| `KnowledgeHydration` | 干知识在当前场景中的复水记录 | 避免把旧规则脱离账号、平台、策略单元直接套用 |
| `TheoryRevisionProposal` | 理论映射或解释模型的修正建议 | 由反证、异常反馈或多次失败触发，需人类确认 |
| `BackfeedCandidate` | 可能反补源体系的反馈候选 | 只记录证据、误读、反例或边界缺口，不自动修改源体系 |
| `CandidateProposal` | 候选提案 | 对计划变更、策略调整、反哺、范本沉淀、边界变更等候选对象的统一信封；具体变更仍由对应提案表承载 |
| `InvestmentTarget` | 投入对象 | 定义被评估是否加码、降频、保持、观察或暂停的场域、平台、账号、主题、案目标、目的组合、产出系列或片场 |
| `AssessmentPolicySeed` | 评估策略种子 | 内置核心战略、平台适配和媒体形态适配的默认策略来源，不直接作为运行时策略 |
| `InvestmentAssessmentPolicy` | 投入评估策略 | 版本化保存投入判断的维度、权重、阈值、否决项、证据要求和缺证处理方式 |
| `InvestmentAssessmentRun` | 投入评估运行 | 记录一次 AI、规则或人类辅助评估的输入证据、模型版本、策略版本、建议、置信度、反证和不确定性 |
| `InvestmentThesisSnapshot` | 投入论点快照 | 冻结“为什么值得加码/降频”的可反驳判断，包括预期结果、成功指标、失败条件、复盘时间和风险 |
| `InvestmentOutcomeReview` | 投入结果复盘 | 对投入论点进行证实、证伪、不确定或噪声过载复盘，并形成后续候选提案 |
| `InvestmentOutcomeBaselineSnapshot` | 投入结果基线快照 | 冻结复盘前的场域、源体系、灯塔目标、目的组合、资源配置、预期指标和基线指标 |
| `InvestmentOutcomeAttributionHypothesis` | 投入结果归因假设 | 保存多种可能归因及其置信度，防止把平台波动、时机、标题、形态或误读强行归为单一原因 |
| `ResourceAllocationDecision` | 资源配置决策 | 记录正式资源加码、降频、暂停或实验的决策痕迹；具体计划修改仍需通过候选提案和计划变更链路 |
| `BoundaryDecision` | 系统知道何时不行动 | `write` / `draft_only` / `wait_human` / `freeze` / `not_write` |
| `EventLedger` | 全量事实账本 | 记录会议、对话、草稿、diff、门禁、批准、发布、反馈和召回证据 |
| `ForgettingRefiner` | 遗忘提炼器 | 从全量事件中提炼可复用模式、降权噪声、压缩上下文和形成候选 |
| `OperationContextPack` | 操作上下文包 | 每次 AI 调用前注入的最小高价值上下文，禁止把全量账本直接塞给模型 |
| `RecallCard` | 主动召回卡 | 秘书在会议中召回历史时使用的结构化证据卡 |
| `ProductionCapabilityRegistry` | 生产能力注册表 | 记录生成、审校、渲染、发布、信号采集和召回等产出链能力，不作为通用 Agent 能力市场 |
| `Case` | 案 | 可授权、可运营、可复盘、可遗忘、可召回的治理单元 |
| `DaySubCase` | 今日子案 | 日案与主题交互后的当天行动案 |
| `Studio` | 片场 | 固定账号、平台、受众、形态与理论显性度的生成环境 |
| `SubStudio` | 子片场 | 只生产一个产出物的执行单元 |
| `PurposeTypeRegistry` | 目的类型注册表 | 管理单篇产出物可执行目的类型及版本，不用数据库硬枚举锁死 |
| `PurposePolicyBinding` | 目的策略绑定 | 将目的类型、平台画像、媒体形态和策略单元解析为蓝图、质量策略与 Amy 动作建议 |
| `ArtifactBlueprint` | 产出物蓝图 | 定义复合媒体成品的部件、门禁、渲染与发布规则 |
| `AssetFile` | 资源文件 | 真实落盘文件及完整性信息 |
| `QualityPolicy` | 质量策略 | 按目的类型、平台、账号、产出物类型和源体系定义硬门禁、软评分与放行条件 |
| `QualityRun` | 质量检查运行 | 记录一次针对产出物版本或发布包的质量检查过程和证据 |
| `QualitySnapshot` | 质量快照 | 固化当前是否合格、是否高质量、是否可发布和是否需人类介入的裁决摘要 |
| `DelegationPolicy` | 授权策略 | 决定秘书可以审批或发布到什么程度 |
| `InterventionPolicy` | 介入策略 | 决定何时需要打扰人类 |
| `HumanAttentionPolicy` | 人类注意力策略 | 由介入策略和人类注意力预算共同决定哪些事项进入 Amy Today Desk |
| `HumanAttentionBudget` | 人类注意力预算 | 控制每天建议人类处理、认真审阅和裁决的数量、耗时和优先级 |
| `DecisionBrief` | 决策简报 | 秘书压缩给人类的一件待决策事项 |

`EvidenceClaim` 的图谱关系首期只做最小预埋：允许记录依赖边和作用范围，但不实现完整图数据库。所有断言依赖默认按 DAG（有向无环图）约束，禁止循环论证。

### 0.4.1 策略单元与认知成熟度

策略单元不仅有自治等级，还要有认知成熟度：

```text
StrategyUnitCognitionScore =
  属性识别能力
+ 趋势预测能力
+ 介入有效能力
+ 证据校准能力
```

一个策略单元不能只因为近期文章分数高就升权。它必须证明自己能识别关键属性、预测内容走势、采取有效介入，并在反馈中修正自己的判断。

### 0.4.2 策略单元与自治权

ArtifactOS 的自治权不按全局授予，也不只按账号授予，而是授予策略单元：

```text
StrategyUnit = 账号 + 平台 + 内容类型 + 理论介入方式
```

每个策略单元独立拥有：

- 自治等级：`AL0` 人类主导 到 `AL4` 系统运营
- 多维评分矩阵：理论、内容、阅读、平台、账号、运营六组维度
- 自动重写策略：低分时重写 N 次，仍不达标则降级
- 发布策略：达标自动发、暂存、等待人类或降级发布
- 抽检策略：随机抽检、风险抽检、新策略加权抽检
- 升降权规则：由质量、风险、运营、人类反馈和红线共同决定
- 实验策略：主策略与实验策略隔离，小流量验证后再晋升

详细设计见 `19.[认知]-证据认知与进化-Evidence-Evolution.md`。

### 0.4.3 双模式创作

写作有两种根本不同的模式，系统必须同时支持：

| 模式 | 作者状态 | 契约角色 | 比喻 |
|------|---------|---------|------|
| **工程模式** | 我知道要说什么，只需要帮我说得好 | 契约是指令，精确驱动 | 建筑图纸 → 施工 |
| **探索模式** | 我有一个模糊的方向，写着才知道 | 契约是罗盘，随时修正 | 航海 → 发现新大陆 |

工程模式用完整契约（full_contract），探索模式用种子契约（seed_contract）起步。探索模式中契约随写作进程演进——这不触发返工闭环，演进是正常的创作行为，不是缺陷。

### 0.4.5 产出物层级

- **选题**（Topic）：一个待写作的主题，经过漏斗筛选后输出
- **需求语义帧**（RequirementFrame）：RSC 输出的澄清结果，记录意图、场景、边界、未知项和验收方向
- **规格快照**（ContentSpecSnapshot）：CTF 输出的可信规格快照，记录内容对象、多投影、证据和审阅状态
- **契约候选**（ContractCandidate）：可升级为写作契约的规格候选，仍可能被阻塞、冻结或退回澄清
- **写作契约**（Contract）：一份结构化的写作指令，可从完整或种子版本开始
- **草稿**（Draft）：AI生成或人机协作的初稿，可能经历多轮交互修改或返工
- **定稿**（Final）：通过全部质量门禁的内容，准备发布
- **渲染版本**（Rendition）：适配到具体平台格式的可预览版本
- **发布包**（PublicationPackage）：交给发布适配器的最终提交材料
- **研究问题**（ResearchQuestion）：从异常、热点或理论空缺中提取出的可研究问题
- **假设契约**（HypothesisContract）：明确假设、适用边界、反证条件和所需证据
- **断言图谱**（ClaimGraph）：由 `EvidenceClaim` 组成的论证网络，支持证据追溯和反证传播
- **理论修正提案**（TheoryRevisionProposal）：当反常证据积累到阈值后，由系统提出、人类裁决的理论演进建议

### 0.4.6 写作契约

写作契约是系统的核心流转单元，但不是"写之前必须完成的铁律"：

- **契约 = 起点**：告诉 AI "做什么"（主题、论点、禁忌、字数、目标平台）
- **上下文 = 素材**：告诉 AI "用什么做"（账号画像、参考素材、爆款模板、平台规则）
- 两者严格分离，不重复
- 契约可以在写作过程中**演进**（不是返工），也可以在定稿后**回填**

### 0.4.7 任务状态机

所有内容在系统中的流转都是**任务**。每个任务有三轴状态：

- **pipeline_status**：管线状态（完整枚举见 `06.[模型]-状态机规范-State-Machine` 和 `24.[数据]-数据库模型与治理-Database`，含 pending / contracting / drafting / reviewing / approved / publishing / published / collecting / completed / publish_failed / frozen / waiting_human / stored / draft_only / not_writing / abandoned）
- **quality_status**：质量状态（完整枚举见 `06.[模型]-状态机规范-State-Machine` 和 `24.[数据]-数据库模型与治理-Database`，含 pending / structure_checking / structure_passed / structure_blocked / es_checking / es_passed / es_failed / ses_checking / ses_passed / ses_warned / strategy_decision / passed / rework / sample_review / waiting_human / stored）
- **publish_status**：发布状态（完整枚举见 `06.[模型]-状态机规范-State-Machine` 和 `24.[数据]-数据库模型与治理-Database`，含 pending / scheduled / publishing / published / failed / recalled / skipped 共 7 态）

加上 flags（checking、ai_working、human_override）叠加在状态之上。

### 0.4.8 ES / 半ES / NES 三级可判定性

- **ES（可实证判定）**：规则引擎执行，零成本——如字数、格式、敏感词
- **半ES（半可判定）**：小模型辅助，低成本——如论点完整性、结构连贯性
- **NES（不可实证判定）**：大模型评分 + 策略矩阵裁决 + 人类抽检——如写得好不好、标题吸引力、理论介入是否自然

### 0.4.9 反馈提炼

人类在抽检、交互修改、策略黄灯协商中的每次反馈都是可学习的信号：

- **最佳实践库**：被验证有效的写作技巧、结构、措辞
- **反例库**：被人类否定的模式、风格、措辞
- **策略校准库**：评分阈值、权重、重写动作、发布动作的调整依据
- 三类资产作为写作引擎和策略引擎的扩展层，持续改善生成质量和自治能力

### 0.4.9a 遗忘系统

ArtifactOS 不把长期能力建立在“记住一切并全部注入”上，而是建立在：

```text
全量记录，有限激活；后台遗忘，前台清明。
```

所有事件原则上进入 `EventLedger`，用于审计、回放和复盘。但未来 AI 行动只能通过 `OperationContextPack` 接收经过筛选的少量上下文。遗忘系统在后台对历史记录做 `decay / mute / compress / candidate / archive / deprecate`，物理删除只用于隐私、安全或人工明确要求。

秘书拥有 `Active Recall` 能力：根据会议议题主动搜索历史账本和保留模式，用 `RecallCard` 把相关历史带回会议讨论。召回不等于采纳，必须带来源、相关理由、生命周期状态和建议动作。

### 0.4.10 ASTO-min / ODD-min 结构治理

ArtifactOS 吸收 ASTO-min 和 ODD-min 的工程部分，但不把强 ASTO 坐标系作为运行时主模型。

- **ASTO-min 五字段**：任何核心流转对象都必须能回答 `state / transition / actor / boundary_condition / exception`
- **ODD-min 五对象**：任何高影响产出物都必须有 `contract / validation / evidence / seal / rollback-recall`

在 ArtifactOS 中，两组语法分别承担不同职责：

| 语法 | 在系统中的作用 | 不做什么 |
|------|---------------|---------|
| ASTO-min | 统一描述对象状态、变迁、行动者、边界和例外 | 不强制标注五态、六阶、七序 |
| ODD-min | 统一治理产出物的契约、验证、证据、封存和召回 | 不替代策略单元授权、理论红线和人类降权权力 |

最小原则：**AI 负责生成和建议，系统负责验证、留痕和自动执行，人类负责抽检、校准、降权和红线裁决。**

### 0.4.11 RSC / CTF 前置层

ArtifactOS 的契约不应从一句模糊话语直接生成，而应经过两层前置处理：

| 层 | 作用 | 关键产出 |
|----|------|---------|
| RSC需求语义澄清 | 问清用户想表达什么、缺什么、哪些不能默认 | `RequirementFrame` |
| CTF可信规格建构 | 把需求、素材、账号边界、平台规则和人类判断建成可追溯规格 | `ContentSpecSnapshot` / `ContractCandidate` |
| ODD契约验证 | 判断契约候选是否可执行、可验证、可封存、可召回 | `ODD Contract` |

最小链条：

```text
raw idea/topic -> RequirementFrame -> ContentSpecSnapshot -> ContractCandidate -> Contract
```

探索模式可以从较弱的 `RequirementFrame` 起步，但发布前必须形成可封存的 `ContentSpecSnapshot` 和 `formal` 契约。

### 0.4.12 ContentSpec 事实源与审阅面

ArtifactOS 吸收 DeepSpec 的最小工程纪律：**事实源和审阅界面分离**。

| 层 | 含义 | 在 ArtifactOS 中的形式 |
|----|------|--------------------------|
| A 原始材料层 | 用户输入、素材、账号画像、平台规则、发布数据、交互反馈 | 原始表、文件、截图、API结果 |
| B 规格事实层 | 系统当前承认的内容规格事实 | `RequirementFrame`、`ContentSpecSnapshot`、`ContentDecision`、`SpecIssue`、证据记录 |
| 审阅呈现层 | 人类看到的预览、报告、面板、图表 | 产出物预览、质量报告、案场面板、发布预览 |

约束：

- 预览、报告和面板不是事实源，不能绕过 B 直接改变契约
- AI 输出先是候选事实，经过 Schema、证据、冲突和人类决策后才能合并进 B
- 人类确认的 `ContentDecision` 优先级高于 AI 推断和旧输入
- A 与 B 冲突时，系统以 B 为当前规格判断，同时标记 A 未同步或证据过期

同时采用 DeepSpec 的正交状态原则：规格对象优先使用 `gen_status` 与 `review_status`，任务执行状态仍交给任务状态机。

```text
gen_status: pending | generated | failed
review_status: pending | accepted | rejected | locked
```

## 0.5 典型运行流程

### 0.5.1 知识进化策略单元流程

1. 策略单元处于 `AL3/AL4`，入口优先级、评分矩阵、重写次数、抽检率和发布权限已经配置
2. 系统从热点入口或理论入口发现候选，自动判断是否值得写；不写也要记录理由
3. 系统完成理论映射、观点推导、RSC/CTF、契约候选和写作契约
4. AI 根据契约和上下文生成草稿，并记录 `TaskObjective` / `AbilityCall` / `AgentResult` / `GovernanceEvent`
5. 质量门禁按硬门禁、底线分、目标分评分
6. 分数不足时自动重写 N 次；仍不达标则按策略降级、暂存、等待人类或放弃
7. 分数达标且无红线时，按策略自动发布、抽检或暂存
8. 发布后数据回收进入进化控制台，影响该策略单元的黄灯建议、实验策略和升降权

### 0.5.2 人类抽检与校准流程

1. 人类在进化控制台看到策略单元灯色：绿、黄、橙、红、蓝、灰
2. 人类可随机抽检，也可点击黄灯/橙灯/红灯查看证据、原因和影响范围
3. 人类用自然语言与 AI 协商策略调整，例如“这个账号理论介入太重，降低显性理论表达”
4. AI 将自然语言转成参数变更草案：权重、阈值、入口优先级、重写动作、抽检率或发布动作
5. 人类确认后生成策略变更事件；若否定，则记录为反例和降权依据
6. 人类可随时对某个策略单元降权、暂停、召回或关闭自动发布

工程模式和探索模式仍然存在，但它们是写作契约的生成方式，不再是整个平台的战略主线。

### 0.5.3 片场秘书与批量总编流程

1. 秘书读取周案（WeekCase）、日案（DayCase）、待处理片场（Studio）、昨日异常和近期强信号
2. 遗忘系统生成与当前会议议题相关的 `RecallCard`
3. 秘书将日案（DayCase）与多个主题（Theme）组织为今日子案（DaySubCase），并生成片场（Studio）和产出计划集（ArtifactPlanSet）草案
4. 日晨会中，人类以今日子案（DaySubCase）为最小授权对象；成熟案（Mature Case）按授权策略（DelegationPolicy）自动推进，需人类判断的事项压缩成决策简报（DecisionBrief）
5. 每个子片场（SubStudio）只生产一个产出物（Artifact）；所有产出物在批量总编台（Artifact Review Desk）中查看部件、版本、diff、门禁和对话
6. 人类可以对单个产出物（Artifact）或整批产出物发出自然语言修改指令；AI 生成 patch/diff，不静默覆盖
7. 通过门禁并符合授权范围的内容生成 `ApprovalRecord`
8. `ApprovalRecord` 才能把内容交给 `media_publish` 发布
9. 发布结果、异常、反馈和人工裁决全部写入 `EventLedger`，等待遗忘系统后台提炼

### 0.5.4 会议体系与计划治理

ArtifactOS 的会议体系按战略/战术层级分工，详见 `20.[治理]-会议体系与计划治理-Meeting-Governance.md`：

| 会议（Meeting） | 输出（Output） | 性质（Nature） | 不能越界 |
|---|---|---|---|
| 年会（Annual Meeting） | 年案（YearCase） | 战略执行（Strategic Execution） | 不排每日稿件 |
| 半年会（Half-Year Meeting） | 半年案（HalfYearCase） | 战略调整（Strategic Adjustment） | 不重开年度北极星，除非 YearCaseReopen |
| 季度会（Quarterly Meeting） | 季案（QuarterCase） | 战略安排（Strategic Arrangement） | 不静默新增主海域 |
| 月会（Monthly Meeting） | 月案（MonthCase） | 战略落地（Strategic Landing） | 不推翻季案（QuarterCase）的战略安排 |
| 周会（Weekly Meeting） | 周案（WeekCase） | 战术安排（Tactical Arrangement） | 不重设月案（MonthCase）的灯塔位置 |
| 日晨会（Daily Meeting） | 日案（DayCase）/今日子案（DaySubCase） | 战术落地（Tactical Execution） | 不重新战略化 |

动态变化通过计划变更机制处理：

```text
机会候选（OpportunityCandidate）
  -> 计划变更提案（PlanChangeProposal）
  -> 对应层级会议审议
  -> 计划变更记录（PlanChangeLog）
  -> 案快照（CaseSnapshot）
```

例如国外媒体（Foreign Media）应先作为机会候选进入观察海域（ObservationField），再通过平台研究案（PlatformResearchCase）和季度平台实验（QuarterPlatformExperiment）逐步验证，最终由半年会决定是否进入年度计划池（AnnualPlanPool）或主海域（PrimaryFields）。

### 0.5.5 首个影子运行流程

首个自用版本不直接接管真实发布，而是先做 7 天影子运行（Shadow Run）。详细规格见 `17.[交互]-前夜审阅与影子运行-Evening-Shadow.md`。

```text
旧系统继续真实发布
ArtifactOS 生成次日候选、前夜审阅、模拟执行和偏差记录
    -> DailyReport / NextDayPlan
    -> ShadowRunDay
    -> ShadowRunObservation
    -> 7 天复盘报告
```

影子运行阶段的重点不是证明某一篇文章更好，而是验证 Amy 工作台、微信摘要入口、前夜审阅、旧系统对照和偏差学习是否形成稳定操作系统。

## 0.6 产品边界与硬约束

- **不以 MVP 方式上线**：ArtifactOS 有旧系统承担真实生产和发布兜底，因此不以残缺可演示版本上线。Phase 只表示开发进度和依赖顺序，不表示功能裁剪、赶时间上线或降低架构标准。
- **按第一接管面进入真实运行**：第一次真实接管不是全局替换旧系统，而是在一个明确接管面内完整接管，例如一个 SourcePack、一个主要平台、一个或少数成熟策略单元。第一接管面必须覆盖源体系装载、产出计划、生成、质量门禁、发布包、Amy 工作台、反馈记录、异常处理、回滚路径和旧系统对照。
- **完整可用不是十年愿景全完成**：完整可用指 ArtifactOS 已能替代旧系统承担一个明确生产面的日常产出、审阅、发布准备、反馈记录和异常处理，并且所有真实发布、源体系反哺、战略调整、高风险动作都有门禁、审计、回滚和人类裁决路径；不要求 Phase 5/6 的长期愿景全部完成。
- **能力闭合度衡量进度**：开发进度以规格闭合、数据闭合、流程闭合、人机闭合、影子闭合、接管闭合、退出闭合等能力状态衡量，不以日期承诺或 MVP 上线衡量。
- **接管面绑定 LegacyStage**：上线不是全局开关，而是某个接管面逐步从 LegacyStage L0 到 L5。达到 `LegacyStage L3` 才表示有限真实接管，达到 `LegacyStage L4` 才表示该接管面的主系统，达到 `LegacyStage L5` 才表示旧系统在该接管面归档。
- **主链优先**：任何新增能力都必须说明它服务于 `SourcePack -> Case -> LighthouseStrategyObjective -> Studio -> ArtifactPlan -> Artifact -> QualitySnapshot -> PublicationPackage -> SignalEvent -> CandidateProposal / BackfeedCandidate -> HumanDecision` 的哪一段。不能映射到主链的能力不得进入核心域。其中 `Case` 是片场治理的一等公民，`LighthouseStrategyObjective` 是战略意图资产层的根节点，`ArtifactPlanSet / ArtifactPlan / SubStudio / SubStudioExecutionTask` 属于内部自动化节点，必须可映射到这条主链的对应位置。核心域。
- **Amy 是复杂治理压缩器**：Amy 不是聊天入口，也不是 AI 管理面板，而是案、会议、门禁、授权、事件账本、遗忘系统和复盘机制的前台压缩器。人类日常面对少量工作卡、日报、异常摘要、准备动作和必须裁决事项。
- **商业信任边界前置**：SourcePack、Manifest、产出物和运行证据属于用户或组织的核心资产。ArtifactOS 可以复用通用软件能力，但不得跨客户复用 SourcePack、表达范本、反馈模式或运行证据。商业客户必须能导出核心产出链资产；隐私或安全删除必须留删除记录。
- **关键边界必须可证明**：系统必须能证明一次产出使用了哪个 SourcePackSnapshot、归档材料没有混入当前口径、AI 没有静默裁决源体系冲突、Shadow Run 没有触发真实发布、Amy 动作在授权范围内、真实发布经过 RealPublishGate、平台反馈没有直接修改源体系/灯塔目标/目的组合、自然语言改稿经过影响预览和确认、事件账本保持追加记录、旧系统接管存在回滚路径。
- **写作契约是起点，不是铁律**：系统基于契约工作，但允许写作过程中契约演进
- **自治权按策略单元授予**：自动发布不是全局开关，必须由策略单元配置、自治等级、质量门禁和风险红线共同决定
- **人类有降权权**：人类不必每篇终审，但可以随时抽检、暂停、降权、召回或关闭某策略单元的自动权限
- **不做爆款预测**：系统辅助选题判断，但不承诺预测哪篇会爆
- **允许条件自动发布**：当策略单元授权、质量分达标、红线未触发、证据链完整时，系统可以自动发布
- **真实发布门（RealPublishGate）统一判定**：真实发布必须同时满足 `run_mode=real`、`legacy_stage_rank >= 3`（有限真实接管或更高）、`SourcePackLoadingDecision.allow_production=true`、`StrategyUnitMaturity` 达到授权等级、`DelegationPolicy` 明确允许、质量门禁通过、无红线、发布包可回滚；Phase 1A 永远 `simulation_only`
- **不做静默调参**：AI 可以提出调参建议，但策略演化必须通过看板灯号可见、可解释、可协商、可追溯
- **不做理论原则漂移**：运营数据可以改变理论表达方式，不能自动改变理论核心原则
- **不把源体系当普通 RAG**：`SourcePack` 必须保留母板、解释、实践、发布和归档层级；归档材料默认不进入当前口径
- **不做自我认证**：AI 输出、AI 评分和 AI 总结不能互相充当最终证据；关键结论必须有外部来源、人工确认或明确标注为假设
- **不做一次到位**：允许"先写再改"，探索模式和工程模式并列
- **不做无证据放行**：质量通过、人工覆盖、发布确认、知识入库都必须留下可回查证据
- **不做不可撤回产出**：任何被系统封存或外发的产出物都必须有回滚、禁用或召回路径
- **不做接引承接**：ArtifactOS 只做媒体产出物、发布痕迹和反馈候选；私域互动、用户接引、咨询承接和成交转化属于其他系统
- **只结构化交接吸引信号**：共鸣、误读、公开追问和高意向可以形成 `AttractionHandoff` 交给外部系统；ArtifactOS 不接管私聊和成交，见 `23.[商业]-外部协议-External-Protocols.md`
- **不把审阅界面当事实源**：草稿预览、质量报告、发布预览只能发起候选决策，最终必须写回规格事实层
- **不让进化静默发生**：策略、知识、理论映射的演进必须通过进化控制台、事件日志和证据链可见；核心理论变更必须人类确认
- **不允许循环论证**：`EvidenceClaim` 之间默认按 DAG 约束，断言不能依赖自身或形成循环支撑链
- **不做全局雪崩传播**：素材证伪、断言反证和平台异常默认隔离在 `strategy_unit + time_window` 内，只有高风险或人类确认后才扩大到账号、平台或全局
- **不让算法反馈绑架理论**：当内部质量高但外部表现异常低时，优先进入灰灯避险，不自动判定理论失败
- **不把平台指标当方向盘**：阅读量、点赞、收藏、转发和评论只能作为 `InvestmentThesisSnapshot / 投入论点快照` 的证据，不能单独触发加码、降频、灯塔调整或源体系反哺
- **不把全量历史直接注入 AI**：历史必须先经过遗忘系统筛选、压缩和召回解释，再形成 `OperationContextPack`
- **不让秘书越过主权边界**：秘书可以代理日常操作，但不能自动改变战略海域、长期账号定位、SourcePack 母板或理论核心
- **不让召回等于采纳**：被召回的历史只进入会议讨论，不能因过去存在就自动变成当前规则
- **不把后台 AI 管控当产品目的**：系统目标是推广源体系、生产合格产出物、提高质量、传播放大并节省人工；所有能力注册、授权、门禁、审计和状态机都只能作为后台保障机制
- **不做通用 Agent 平台**：凡不能映射到 `SourcePack / Case / LighthouseStrategyObjective / Studio / Artifact / PublicationPackage / QualitySnapshot / SignalEvent / CandidateProposal / InvestmentThesisSnapshot` 的能力，不进入 ArtifactOS 核心域
- **不把可发布偷换成高质量**：`Qualified Artifact` 必须通过硬门禁并满足产出计划预声明的 `PurposeFit`；`High Quality Artifact` 才用于重点传播放大和范本沉淀
- **不让反馈改写历史质量**：发布后的公开信号可以形成质量策略或传播计划调整候选，但不得覆盖已经封存的 `QualitySnapshot`

### 0.6.1 系统"不管区"声明

| 维度 | 不管的理由 | 设计含义 |
|------|-----------|---------|
| 读者个人反应 | 同一段文字对不同读者效果不同 | 不做"读者反应预测"功能 |
| 美学偏好 | 什么是"好的文字"没有客观标准 | 系统只检测缺陷（ES），不评判美学（NES由人类裁决） |
| 爆款运气 | 爆款有运气成分，系统不承诺预测 | 选题系统提供评估，不提供预测 |
| 平台算法 | 平台推荐算法不透明且持续变化 | 系统适配已知的格式规则，不猜测算法偏好 |

**功能蔓延防线**：每次有人提"我们是不是应该做 X"，先对照不管区——如果 X 在不管区里，直接拒绝。

## 0.6a 开发约束与设计前提

| 约束 | 含义 |
|------|------|
| **时间不限** | 不设交付死线，每个阶段做到质量达标再推进 |
| **老系统兜底** | 项目已有简单内容生成和发布能力（老系统），ArtifactOS 开发期间老系统持续运行，不要求新系统替代后才可用 |
| **不做 MVP** | 不以残缺可演示版本上线；Phase 是开发进度和依赖顺序，不是功能裁剪或降级上线 |
| **第一接管面** | 先在一个明确 SourcePack、主要平台和少数成熟策略单元上形成完整真实生产面，再逐步扩展接管面 |
| **首版自用** | 第一版以一元论 SourcePack 自用为主，验证复杂源体系装载、产出、反馈候选和人工裁决链路；商业入口预留但不急于交付商业版本 |
| **先影子运行** | 首版先做 7 天 Shadow Run；旧系统真实发布，ArtifactOS 负责生成、前夜审阅、模拟执行、日报和偏差记录 |
| **迁移可退出** | 旧系统从只读影子到归档有明确迁移阶段、接管条件和回滚协议；不允许新系统永久停留在旁路层 |
| **最优设计优先** | 不为赶进度牺牲架构完整性；每一步都不欠债，后续能力都长在正确的结构上 |
| **能力闭合度推进** | 用规格闭合、数据闭合、流程闭合、人机闭合、影子闭合、接管闭合、退出闭合描述进度，不用日期承诺描述上线压力 |
| **Phase 内部分层交付** | Phase 1 内部按依赖顺序分四层逐步交付（数据结构 → 单向流水线 → 自治闭环 → 反馈进化），每层独立可验证 |
| **授权后自动推进** | 内容行动流水线不设置单篇固定审批等待点。人类在年会、半年会、季度会、月会、周会和日晨会中确认对应案（Case）与授权范围后，秘书可在范围内自动改稿、复审、排期和提交发布；但真实发布仍必须通过 RealPublishGate。批量总编台（Artifact Review Desk）支持批量批准、抽检和冻结。系统拉人的强度（抽检率、灯号敏感度、边界决策触发阈值等）是策略单元的可配置参数，由人类按账号成熟度调节 |
| **完整能力最终交付** | 本文档描述的所有功能最终都要完成；Phase 划分是交付顺序，不是功能取舍 |

这些约束影响所有子文档的设计决策：预埋字段不做删减，状态机枚举不做简化，证据化认知骨架不做降级。完整可用的判断以某个接管面能否安全进入 `LegacyStage L3/L4` 为准，而不是以能否展示一个最小功能样品为准。

## 0.6b 第一接管面冻结参数

第一接管面（First Operational Surface）是 ArtifactOS 第一个完整真实生产面。它不替代全部旧系统，只在一个明确定义的范围内完整接管。

| 参数 | 冻结值 | 说明 |
|---|---|---|
| 源体系包 | 一元论 SourcePack（`sp_difference_monism`） | 用最复杂的理论体系验证装载、映射、忠实度和契约化能力 |
| 主平台 | 知乎（Zhihu） | 旧系统已有对照数据、media_publish 已有知乎适配器、文本复杂度高 |
| 首接策略单元 | 旧系统对照数据最丰富者 | 须在 7 天影子运行中确认；至少包含一个知乎主账号 + 长文内容类型 + 可追溯的理论介入方式 |
| 接管完成标志 | 首接策略单元安全进入 `LegacyStage L3` 并保持完整周期无严重事故 | 低风险产出物连续 30 天无红线事故、发布包偏差可解释、回滚验证通过、RealPublishGate 可由数据库事实验证、旧系统仅兜底 |
| 旧系统保留能力 | 完整发布能力作为长期回滚目标 | 高风险案和未接管案继续由旧系统承担；ArtifactOS 故障时可立刻切换回旧系统 |

后续接管面可按相同模式扩展：增加新平台、新账号、新媒体形态或新 SourcePack，但每次只接管一个明确对象，不全体替换。

## 0.7 首期平台范围

项目已有简单内容生成能力，因此首期目标不是证明”AI 能写草稿”，而是搭建单策略单元内容行动流水线的最小可运行骨架，并为证据化认知预埋结构。

- SourcePack：以 `D:\_Progs\一元论` 建立 `SourcePackManifest`、`SourcePackSnapshot`、模块注册、层级标注、归档排除和主张强度策略
- 通用装载：建立 `SourceInventory / SourceReadinessReport / SourceConflictReport / SourcePackLoadingDecision` 和 SPL0-SPL4 装载成熟度
- 策略单元：定义 `账号 + 平台 + 内容类型 + 理论介入方式`，支持独立配置自治等级、评分矩阵、重写次数和发布动作
- 源体系策略引擎：支持热点驱动和源体系驱动双入口，完成理论/品牌/产品映射、观点推导和显性程度配置
- 战略意图资产层：建立 `LighthouseStrategyObjective / 灯塔策略目标`、`CaseObjective / 案目标`、`PurposePortfolio / 目的组合` 和决策谱系，保存“在哪个场域立灯塔、代表谁说话、如何建立信任、各时间案采用什么目的组合”的长期资产
- 选题：热点信号采集 + 理论命题匹配 + 自动判断写/不写
- 契约：支持种子契约和完整契约两种起步方式
- RSC/CTF：最小 RequirementFrame + ContentSpecSnapshot + ContractCandidate
- ContentSpec事实层：最小 ContentDecision + SpecIssue + ContentContextPack
- 案场层级：年案（YearCase）至日案（DayCase）的包含边界、今日子案（DaySubCase）、片场（Studio）和子片场（SubStudio）
- 会议体系：`MeetingProtocol / MeetingRecord / CaseSnapshot / OpportunityCandidate / PlanChangeProposal / PlanChangeLog / CaseChangeControl / BoundaryChangeProposal`
- 片场秘书：多案并行晨会、授权策略（DelegationPolicy）、介入策略（InterventionPolicy）、决策简报（DecisionBrief）和异常汇报
- Amy Today Desk：用人类注意力策略（HumanAttentionPolicy）和人类注意力预算（HumanAttentionBudget）把事项分为必须处理、建议审阅、Amy 可自办、等待结果和异常风险
- 生产能力注册：`ProductionCapabilityRegistry` 记录可调用的生成、审校、渲染、发布、信号采集和召回能力，所有能力必须绑定产出链上下文
- 前夜审阅与影子运行：`DailyReport / NextDayPlan / TomorrowPublishBatch / TomorrowPublishCandidate / ShadowRun / ShadowRunDay / ShadowRunObservation`
- 批量总编台（Artifact Review Desk）：批量生成后的 Artifact 列表、复合部件预览、版本 diff、自然语言批量改稿和发布前批准
- 复合产出物：`Artifact / ArtifactPart / AssetFile / Rendition / PublicationPackage / ArtifactBlueprint / ArtifactPlanSet`
- 写作：自动生成 + 自动重写 N 次 + 交互修改界面（自然语言反馈）
- 质量门禁：硬门禁 + 三组默认评分维度（Phase 1），六组（Phase 3 完整形态）+ 策略矩阵裁决
- 质量事实层：`PurposeTypeRegistry / PurposePolicyBinding / QualityPolicy / QualityRun / QualitySnapshot`；`ArtifactPlan` 必须预声明主目的类型（primary_purpose_type）与策略绑定，吸引/转发/概念种子/传播放大目的才把共鸣潜力纳入合格硬条件；`trust_building / 信任建立` 与 `positioning / 定位占位` 只存在于 `LighthouseStrategyObjective / CaseObjective`，必须编译为具体 `PurposeType` 后才能进入单篇生产
- 发布：知乎单平台条件自动发布，复用 media_publish；自动发布必须受策略单元权限约束
- 进化控制台：以策略单元和认知扰动事件为一级对象，支持绿/黄/橙/红/蓝/灰灯
- 场域状态：`FieldState / 场域状态` 由 `SignalEvent / SignalInterpretation / AttributionDecision` 派生为快照，作为 `PurposePortfolio / 目的组合` 编译输入；灰灯时阻断平台反馈自动改策略
- 证据化认知：最小 `CognitionTrace`、`EvidenceClaim`、`CognitiveDisturbanceEvent`、`BoundaryDecision`；`EvidenceClaim` 必须预留依赖边、作用范围和传播策略
- 源体系忠实度：S08 SourceMapping 必须输出主张、边界、禁忌和场景 profile；理论场景输出结构化因果原语，质量门禁按结构一致性检查 Source Fidelity
- 扰动回灌：连续 `calibration_delta` 超标时生成 `StrategyChangeProposal`，但不得静默调参
- 灰灯避险：平台算法波动或环境噪音过载时进入灰灯，不直接降权或判定理论失败
- 知识与反馈：反馈作用范围分为本文级、策略单元级、账号级、平台级、理论层级；理论层级只能形成 `BackfeedCandidate`，不能自动改源体系
- 吸引信号交接：`ResonanceSignal / ReaderQuestion / MisreadRisk / PublicFollowupCandidate / AttractionHandoff / ExternalDestinationRef`，只交接不承接
- 遗忘系统：`EventLedger` 全量记录、`ForgettingQueue` 后台提炼、`OperationContextPack` 最小注入、`RecallCard` 主动召回
- 实验策略：支持主策略/实验策略隔离
- ODD治理：最小证据链 + 轻封存 + 降权/召回/回滚记录模板
- OCGS桥接：AI生成、反馈解析、知识提取、发布自动化记录 TaskObjective / AbilityCall / AgentResult / GovernanceEvent
- 数据库：PostgreSQL（本机已有实例），充分利用触发器、函数、约束、CTE、JSONB、RLS 等 PG 原生能力，将与下游 media_publish 及其他系统共享 PG 实例
- 多租户预埋：所有核心表预留 `tenant_id` + `created_by` + `updated_by`；建表时写入 RLS 策略骨架；Phase 1 写入固定 tenant_id，后续启用即可
- 代码组织：四个子品牌按包级代码隔离（`signalscope/` / `theoryweave/` / `claimgraph/` / `praxisforge/`），依赖方向单向，接口协议冻结为独立类型文件

## 0.8 里程碑建议

- **Phase 0**：文档对齐与术语冻结
- **Phase 1A**：单策略单元影子运行（理论/热点双入口 + 前夜审阅 + 模拟执行 + 旧系统对照）
- **Phase 1B**：单策略单元内容行动流水线（自动重写 + 条件发布）
- **Phase 1C**：单策略单元认知与进化骨架（CognitionTrace + EvidenceClaim + 灯号 + 反馈作用范围）
- **Phase 2**：进化控制台（灯号、认知扰动、黄灯协商、降权、抽检、实验策略）
- **Phase 3**：多平台策略矩阵（多账号、多平台、多内容类型）
- **Phase 4**：数据回收驱动知识进化（运营数据、反馈晋升、共享学习、证据反证）
- **Phase 5**：PL4 研究型知识进化系统（研究问题、假设契约、反证门禁、理论修正提案）
- **Phase 6**：PL5 个人/组织知识进化 OS（内容、科研、决策、知识管理和理论演化共用一套底座）

## 0.9 主要风险与对策

- **AI 产出同质化**：通过账号画像约束风格 + 缺陷三分法保护生产性偏差 + 遗忘系统提炼保留模式来积累差异化
- **探索模式变成无约束发散**：种子契约仍有最小字段（topic + account + platform），且交互修改的每轮反馈都被记录，可追溯
- **需求过早物化**：在契约前增加 RSC/CTF 前置层，缺少边界、验收和证据时只能生成候选，不能发布
- **选题漏斗不准**：初期手工验证，积累数据后再优化筛选逻辑
- **平台规则变化**：格式适配器解耦，每个平台独立维护规则
- **自动发布失控**：自动发布只在策略单元授权下发生；红线触发立即降权/暂停/召回
- **理论被运营数据带偏**：理论核心原则不可自动修改，运营数据只能调整表达和适配方式
- **反馈提炼不落地**：反馈采集零摩擦——人类只说自然语言，系统自动入账、归类、建议作用范围，并由遗忘系统决定是否激活
- **自我喂养幻觉闭环**：AI 输出不能直接晋升为证据，必须经过来源、门禁、人类确认或场域反馈验证
- **进化方向失控**：策略、知识和理论映射可以演进，但核心理论原则、重大研究结论和高风险发布必须由人类裁决
