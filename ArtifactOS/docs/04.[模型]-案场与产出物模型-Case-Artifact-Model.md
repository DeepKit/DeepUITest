## 一、讨论如何推进到当前设计

### 1.1 源体系与产品边界（Source System and Product Boundary）

讨论从一元论（Difference Monism）及其工程/实践材料开始，确认了以下边界：

1. 一元论（Difference Monism）是首个源体系包（SourcePack），不是产品硬编码内核。
2. 母板（Canonical Mother Text）和治理规则（Governance Rule）必须只读装载，不能被普通检索语料抹平。
3. 反馈（Feedback）可以产生反哺候选（BackfeedCandidate），但不能自动改写源体系包（SourcePack）或母板（Canonical Mother Text）。
4. 产品只负责“找场、立灯塔、发光、吸引人”，不负责接引、私域互动、咨询承接或成交。

### 1.2 产品定位与命名（Positioning and Naming）

产品定位从“媒体文章产出与反馈管理系统”提升为：

```text
源体系驱动的通用媒体产出物操作系统
Source-System-Driven General Media Artifact Operating System
```

正式名称：

| 属性（Property） | 值（Value） |
|---|---|
| 中文名（Chinese Name） | 演擎 |
| 英文名（English Name） | ArtifactOS |
| 首版用户（First-Version User） | 自用（Self Use） |
| 商业策略（Commercial Strategy） | 保留入口，不急于商业交付（Preserve Entry, No Urgent Commercial Delivery） |

### 1.3 旧系统迁移（Legacy Migration）

阅读旧生产/写作系统后确认：

| 旧系统对象（Legacy System Object） | 继承方式（Migration Decision） |
|---|---|
| `article_pipeline.py` | 作为早期产出工厂（ArtifactFactory）继续可用 |
| 写作指南（Writing Guides） | 转为声音包（VoicePack）和表达策略（ExpressionPolicy） |
| 核心读者画像（Reader Profile） | 转为受众假设（AudienceHypothesis） |
| 运营与显影纪律（Operation Discipline） | 转为灯塔策略（LighthouseStrategy） |
| `media_publish` | 作为发布适配器（PublishingAdapter），不重写其发布状态机 |

迁移原则（Migration Principle）：

> 新系统先接管结构、校正、授权、记录、反馈解释和遗忘提炼，再逐步替换生产动作。

### 1.4 批量审片与片场制（Batch Review and Studio Operation）

用户明确要求发布前先写出全部文件，并通过界面与 AI 对话批量纠正。因此，系统不是单篇编辑器，而是批量总编台（Artifact Review Desk）。

随后讨论引入片场制（Studio Operation）：

- 日晨会（Daily Meeting）组织当天输出。
- 周会（Weekly Meeting）、月会（Monthly Meeting）、季会（Quarterly Meeting）、半年会（Half-Year Meeting）、年会（Yearly Meeting）逐层确定边界。
- AI 不是单一聊天助手，而是由总制片秘书（ExecutiveProducerSecretary）协调的专业岗位团队。

### 1.5 秘书、授权与人类介入（Secretary, Delegation and Human Intervention）

最初提出单一“今日授权”，后被修正：一天可以同时有多个主题（Theme）和多个案（Case），每个案可拥有不同授权策略（DelegationPolicy）。

最终确认：

1. 秘书（ExecutiveProducerSecretary）是产品主入口。
2. 审批权绑定于授权策略（DelegationPolicy），不天然绑定于人类。
3. 成熟案（Case）可以授权秘书自动审批和自动发布，人类不再参与过程。
4. 介入策略（InterventionPolicy）与授权策略（DelegationPolicy）分开：前者决定什么时候打扰人类，后者决定秘书可以做什么。
5. 人类不处理原始复杂度，只处理秘书压缩后的决策简报（DecisionBrief）。
6. 日晨会（Daily Meeting）中，人类操作的最小授权对象是今日子案（DaySubCase）；它继承案（Case）的长期授权策略（DelegationPolicy），成熟案不需要每天重复获批。

### 1.6 遗忘与主动召回（Forgetting and Active Recall）

用户把原“记忆系统（Memory System）”纠正为遗忘系统（ForgettingSystem），并明确：

```text
所有信息写入数据库事实账本
遗忘系统在后台进行遗忘、衰减、压缩和提纯
秘书能够按当前会议上下文主动搜索历史并放回讨论
```

因此形成核心原则：

> 全量记录，有限激活；后台遗忘，前台清明。  
> Record Everything, Activate Selectively; Forget in the Background, Keep the Foreground Clear.

### 1.7 案、片场与产出物（Case, Studio and Artifact）

用户进一步确定：

1. 不用项目（Project），使用案（Case）。
2. 案（Case）在时间维度上具有严格包含关系：年案（YearCase）到日案（DayCase）。
3. 日案（DayCase）与多个主题（Theme）交互，形成今日子案（DaySubCase）。
4. 今日子案（DaySubCase）与账号（Account）、平台（Platform）、受众（Audience）等交互，形成片场（Studio）。
5. 一个片场（Studio）对应一个生成环境（Generation Environment）。
6. 一个子片场（SubStudio）对应一个产出物（Artifact）。

### 1.8 复合媒体与统一模型（Composite Media and Unified Model）

以小红书笔记（Xiaohongshu Note）为例，产出物（Artifact）可能同时包含图片、视频、文案和标签，因此不能等同于单个文本文件。

最终确定的抽象包括：

| 中文（Chinese） | 英文（English） | 作用（Purpose） |
|---|---|---|---|
| 产出物 | Artifact | 一个可发布、可治理的媒体成品 |
| 产出物部件 | ArtifactPart | 产出物的语义结构组成件 |
| 资源文件 | AssetFile | 可校验、渲染、发布、归档的真实文件对象 |
| 渲染版本 | Rendition | 为平台适配生成的具体版本 |
| 发布包 | PublicationPackage | 交给发布适配器的提交材料 |
| 产出物蓝图 | ArtifactBlueprint | 一类媒体成品的结构规范 |
| 产出计划集 | ArtifactPlanSet | 某片场准备开启的多个单产出计划 |
| 产出计划 | ArtifactPlan | 一个子片场将生产什么成品的计划 |

### 1.9 门禁、信号与归因（Gate, Signal and Attribution）

复合产出物要求门禁（Gate）分层：

```text
部件门禁（PartGate）
  -> 组装门禁（AssemblyGate）
    -> 产出物门禁（ArtifactGate）
      -> 片场门禁（StudioGate）
        -> 发布包门禁（PackageGate）
```

发布后必须区分：

```text
信号事件（SignalEvent）       # 事实
信号解释（SignalInterpretation） # AI 假设
归因决策（AttributionDecision）  # 受边界约束的后续动作
```

信号不能直接证明理论正确，最多形成策略提案（StrategyChangeProposal）、保留模式候选（RetainedPatternCandidate）或反哺候选（BackfeedCandidate）。

### 1.9a 合格产出物与高质量（Qualified Artifact and High Quality）

围绕质量定义形成以下冻结结论：

1. `QualityRun / 质量检查运行` 与 `QualitySnapshot / 质量快照` 都需要。前者记录检查过程，后者记录当前裁决结论。
2. `Qualified Artifact / 合格产出物` 不等于“阅读量好”，也不等于“AI 评分高”。它必须通过硬门禁，并满足产出计划（ArtifactPlan）中预声明的 `PurposeFit / 目的匹配`。
3. `High Quality Artifact / 高质量产出物` 是合格之上的放大等级，用于判断是否优先传播、建议人类认真审阅、沉淀为范本或提高后续策略权重。
4. `ResonancePotential / 共鸣潜力` 是否是合格硬条件，由 `primary_purpose_type / 主目的类型` 决定。

目的类型规则：

| 主目的类型（primary_purpose_type） | 中文 | 目的族（purpose_family） | 共鸣潜力是否硬门禁 |
|---|---|---|---|
| `attraction` | 吸引同频者 | `propagation / 传播` | 是 |
| `repost_seed` | 转发种子 | `propagation / 传播` | 是 |
| `concept_seed` | 概念种子 | `cognition / 认知` | 是 |
| `amplification` | 传播放大 | `propagation / 传播` | 是 |
| `explanation` | 解释说明 | `expression / 表达` | 否，作为软评分 |
| `foundation` | 铺垫奠基 | `foundation / 奠基` | 否，作为软评分 |
| `evidence_support` | 补证支撑 | `evidence / 证据` | 否，作为软评分 |
| `statement` | 声明澄清 | `defense / 防御` | 否，作为软评分 |
| `boundary_setting` | 边界设定 | `defense / 防御` | 否，作为软评分 |

硬约束：

```text
Qualified Artifact =
  HardGates.pass
+ ArtifactPlan.primary_purpose_type locked before generation
+ PurposeFit.pass
+ QualitySnapshot.sealed
```

系统不得在 `QualityRun / 质量检查运行` 之后临时改写 `primary_purpose_type / 主目的类型`，以规避 `ResonancePotential / 共鸣潜力` 或其他质量要求。

`trust_building / 信任建立` 与 `positioning / 定位占位` 属于上层目标，不作为单篇主目的：

```text
CaseObjective / 案目标
LighthouseStrategyObjective / 灯塔策略目标
  -> PurposePolicyBinding / 目的策略绑定
  -> 一个或多个 PurposeType / 目的类型
  -> ArtifactPlan / 产出计划
```

因此，单篇 `Artifact / 产出物` 可以服务于信任建立或定位占位，但不能把它们作为主 `primary_purpose_type / 主目的类型`。

### 1.10 会议体系与计划治理（Meeting System and Plan Governance）

随后进一步确认：日晨会（Daily Meeting）不是起点，它只是战术落地层。上游必须先定义年会、半年会、季度会、月会、周会的会议协议。各层会议讨论的问题不同：

| 会议（Meeting） | 输出（Output） | 性质（Nature） |
|---|---|---|
| 年会（Annual Meeting） | 年案（YearCase） | 战略执行（Strategic Execution） |
| 半年会（Half-Year Meeting） | 半年案（HalfYearCase） | 战略调整（Strategic Adjustment） |
| 季度会（Quarterly Meeting） | 季案（QuarterCase） | 战略安排（Strategic Arrangement） |
| 月会（Monthly Meeting） | 月案（MonthCase） | 战略落地（Strategic Landing） |
| 周会（Weekly Meeting） | 周案（WeekCase） | 战术安排（Tactical Arrangement） |
| 日晨会（Daily Meeting） | 日案（DayCase）/今日子案（DaySubCase） | 战术落地（Tactical Execution） |

年案（YearCase）不能一次写死全年。全年可以动态增加计划（AddPlan）、减少计划（DropPlan）和调整计划（RebalancePlan），但必须通过机会候选（OpportunityCandidate）、计划变更提案（PlanChangeProposal）和计划变更记录（PlanChangeLog）治理，不能静默修改年案。

国外媒体（Foreign Media）等新方向应进入：

```text
机会候选（OpportunityCandidate）
  -> 平台研究案（PlatformResearchCase）
  -> 观察海域（ObservationField）
  -> 季度平台实验（QuarterPlatformExperiment）
  -> 半年会决定是否进入年度计划池（AnnualPlanPool）/主海域（PrimaryFields）
```

### 1.10a 战略意图资产与目的组合（Strategic Intent Asset and Purpose Portfolio）

新一轮圆桌确认：`trust_building / 信任建立` 与 `positioning / 定位占位` 之所以不能作为单篇主目的，是因为它们属于上层战略意图。系统需要单独沉淀 `StrategicIntentAssetLayer / 战略意图资产层`：

```text
LighthouseStrategyObjective / 灯塔策略目标
  -> CaseObjective / 案目标
    -> PurposePortfolio / 目的组合
      -> PurposePolicyBinding / 目的策略绑定
        -> ArtifactPlan.primary_purpose_type / 产出计划主目的类型
```

主持结论如下：

1. `LighthouseStrategyObjective / 灯塔策略目标` 定义长期要在某个 `Field / 场域` 中成为什么灯塔，包含身份占位、信任建立目标、受众状态路径、边界姿态、平台账号角色和非目标。
2. `CaseObjective / 案目标` 定义某个时间案要推进哪一段战略，包含时间范围、战略任务、目标优先级、约束、成功判据和目的组合。
3. `PurposePortfolio / 目的组合` 定义本案内九类 `PurposeType / 目的类型` 的比例、数量、节奏和优先级；它不是固定模板，而是由灯塔目标、案目标、场域状态和人类注意力预算动态编译。
4. Amy 可以生成 `PurposePortfolioCandidate / 目的组合候选`、排程变体、表达变体和绑定候选，但不能自动改变灯塔策略目标、账号定位、源体系权威版本或大比例目的组合。
5. 年案和半年案的大方向由人类裁决；季案和月案由人类批准后 Amy 拆解；周案和日案可在已批准父组合的 `delegated_within_band / 授权带内派生` 或 `inherited_projection / 继承投影` 模式下自动生成并按注意力策略抽检。
6. `ArtifactMix / 内容形态比例` 不能替代 `PurposePortfolio / 目的组合`；月案必须先确定目的组合，周案拆成 `PurposeSlot / 目的槽位`，日案再锁定单篇 `primary_purpose_type / 主目的类型`。
7. `PurposePolicyBinding / 目的策略绑定` 必须包含 `ExpressionDiversityPolicy / 表达多样性策略`，避免同一目的类型被机械化生成；出现 `FatigueSignal / 疲劳信号` 时，Amy 必须换角度、降频或提交策略调整候选。

六层编译关系：

| 层级（Level） | 对目的组合的职责（PurposePortfolio Responsibility） |
|---|---|
| 年案（YearCase） | 确定全年主叙事、主海域和年度目的组合大比例 |
| 半年案（HalfYearCase） | 根据外部变化增加、减少、调整战略重心和目的组合候选 |
| 季案（QuarterCase） | 确定季度战役、主题群、验证重点和目的组合范围 |
| 月案（MonthCase） | 落成月度灯塔位置、账号节奏、目的组合配额和产能预算 |
| 周案（WeekCase） | 安排主题池、片场候选、具体目的数量和观察指标 |
| 日案（DayCase） | 生成当天 ArtifactPlan，不重新定义战略目标或目的大比例 |

### 1.10b 场域状态（FieldState）

`FieldState / 场域状态` 被定义为某一时间窗口内，对 `Field / 场域`、`Platform / 平台`、`Account / 账号`、`TopicCluster / 主题群`、`AudienceStateHypothesis / 受众状态假设` 的可追溯态势快照。它是 `PurposePortfolio / 目的组合` 的输入变量，不是战略裁决者。

关系链：

```text
SignalEvent / 信号事件
  -> SignalInterpretation / 信号解释
    -> AttributionDecision / 归因决策
      -> FieldStateSnapshot / 场域状态快照
        -> PurposePortfolioCandidate / 目的组合候选
          -> PlanChangeProposal / BoundaryChangeProposal
```

主持结论：

1. `FieldState / 场域状态` 只能记录观察态势、置信度、灯号和有效期，不能直接修改 `SourcePack / 源体系包`、`LighthouseStrategyObjective / 灯塔策略目标`、账号定位或价值边界。
2. 它必须区分 `ObservedSignal / 观察信号`、`InterpretationHypothesis / 解释假设` 和 `ActionImplication / 行动含义`。
3. `AudienceStateDistribution / 受众状态分布`、`ResonanceReason / 共鸣原因`、`AlgorithmPreference / 平台算法偏好` 都只能是假设，不能写成事实。
4. `algorithm_noise_overload / 算法噪声过载` 是灰灯，不是失败灯；灰灯期间平台反馈自动降权，只允许观察、人工审阅或低风险实验。
5. 超出自动调整带的目的组合变化进入 `PlanChangeProposal / 计划变更提案`；影响源体系、灯塔目标、身份占位、边界姿态或非目标的变化进入 `BoundaryChangeProposal / 边界变更提案`。
6. 落在自动调整带内的低风险表达参数（标题句式、钩子排序等）通过 AutoTune 白名单通道自动微调（见 `docs/19.[认知]-证据认知与进化-Evidence-Evolution.md` §6.4）；跨带或禁区的变化才进入候选提案链路。

### 1.10c 表达多样性策略（ExpressionDiversityPolicy）

同目的类型、同账号、同平台连续产出时，Amy 必须避免机械化。表达多样性策略是一组可配置的防重复规则，绑定在 `PurposePolicyBinding / 目的策略绑定` 上。

```yaml
expression_diversity_policy:
  title_pattern_rotation: 3       # 同一句式标题连用上限，超限换句式
  opening_variants_min: 3          # 开头的可选模板数下限
  closing_variants_min: 2          # 结尾的可选模板数下限
  angle_shift_after: 3             # 同角度连续产出上限，超限必须换切入角度
  word_frequency_guard:
    max_repetition: 3              # 同目的下相同核心概念词连续出现上限
    synonym_boost: true            # 超限时自动用近义词替换
  metadata_drift_check: true       # 启用标题/摘要/标签的语义漂移检测
```

当检测到重复度过高时 Amy 的默认动作：

```text
1. 低重复：自动轮换标题句式和开头模板
2. 中重复（连续 3+）：提示 Amy 建议换切入角度
3. 高重复（连续 5+）：暂停同类生成，生成 StrategyChangeProposal 建议拓宽目的组合或换主题
```

### 1.10d 疲劳信号策略（FatigueSignalPolicy）

疲劳信号（FatigueSignal）是由平台反馈和产出频率共同触发的警告。当同主题、同目的或同形态的内容被过度产出时，读者注意力下降、互动质量衰减。

```text
FatigueSignal 触发条件：
  同目的类型产出 > 同周上限（默认 5 篇）+ 互动率连续 3 篇下降
  同主题簇产出 > 同月上限（默认 8 篇）+ 收藏/转发比下降
  同形态产出 > 周上限 + 发布窗口集中度过高（>3 篇同日）
  评论区出现明确疲劳语言信号（"又说这个""没新意""老生常谈"等）
```

触发后的处理链路：

```text
FatigueSignal
  → Amy 工作台：在投资论点卡中显示疲劳风险
  → StrategyChangeProposal：建议降频 / 换目的 / 换角度 / 换形态 / 进入观察
  → PurposePortfolio：建议调整本周或本月目的组合比例
  → 不自动冻结，不直接修改 SourcePack
```

疲劳不等于失败——它说明表达策略需要轮换。连续两个月同一信号不消退才进入橙灯。

### 1.11 产品内核纠偏（Product Kernel Correction）

圆桌曾提出 `AI Action Governance Kernel / AI 行动治理内核` 作为内部命题，随后被用户否决。否决理由已冻结为产品边界：

> 人类使用 ArtifactOS/演擎不是为了治理 AI，而是为了推广理论、品牌或方法论，持续生成合格产出物，达到高质量，并省去大量人工。

因此，撤销 `AI Action Governance Kernel / AI 行动治理内核` 作为产品命题，替换为：

```text
Source-to-Artifact Production and Amplification Kernel
源体系到产出物生产与放大内核
```

该命题的主链是：

```text
SourcePack（源体系包）
  -> Case（案）
  -> LighthouseStrategy（灯塔策略）
  -> Studio（片场）
  -> Artifact（产出物）
  -> QualityGate（质量门禁）
  -> PublicationPackage（发布包）
  -> SignalEvent（信号事件）
  -> CandidateProposal（候选提案）
```

原先讨论中的 AI 治理相关对象不删除，但统一降级为后台保障机制：

| 原命题/对象 | 处理方式 | 新定位 |
|---|---|---|
| `AI Action Governance Kernel` | 撤销 | 不作为产品命题或内核命名 |
| `CapabilityRegistry` | 改名 | `ProductionCapabilityRegistry / 生产能力注册表` |
| `DelegationPolicy` | 保留 | Amy 省人工代理规则 |
| `InterventionPolicy` | 保留 | 必须打扰人类的触发规则 |
| `AttentionBudget` | 改名 | `HumanAttentionBudget / 人类注意力预算` |
| `EventLedger` | 保留 | 产出物生产追溯和复盘事实账本 |
| `AgentRoleContract` | 降级 | 片场岗位能力契约，不是产品中心 |
| `BusinessAdjustmentLoop` | 收窄 | `PropagationPlanAdjustment / 传播计划调整` |

硬边界：凡不能映射到 `SourcePack / Case / Studio / Artifact / PublicationPackage / SignalEvent / CandidateProposal / InvestmentThesisSnapshot` 的能力，不进入 ArtifactOS 核心域。

其中 `CandidateProposal / 候选提案` 采用“统一信封 + 具体提案”结构。统一信封记录来源、证据、作用范围、风险、去重合并、推荐会议、裁决和应用结果；具体对象仍表现为 `OpportunityCandidate / 机会候选`、`PlanChangeProposal / 计划变更提案`、`BoundaryChangeProposal / 边界变更提案`、`StrategyChangeProposal / 策略变更提案`、`BackfeedCandidate / 反哺候选` 或 `CalibrationExample / 校正范本` 等。

### 1.11a 候选提案信封（CandidateProposal Envelope）

圆桌确认：`CandidateProposal / 候选提案` 不是任务池，也不是每条信号的待办列表。它是信号、解释、场域状态和人类观察进入正式变更系统前的隔离层。

```text
SignalEvent / FieldState / HumanFeedback / RecallCard
  -> CandidateProposalEnvelope / 候选提案信封
    -> CandidateDecision / 候选裁决
      -> CandidateApplication / 候选应用
        -> 具体提案或事实对象
```

路由原则：

| 路由目标 | English | 适用变化 |
|---|---|---|
| 机会候选 | OpportunityCandidate | 新平台、新媒体、新受众、新主题、新载体 |
| 计划变更提案 | PlanChangeProposal | 正式计划池、产能、节奏、主题配额、目的组合超自动调整带 |
| 边界变更提案 | BoundaryChangeProposal | 源体系边界、灯塔目标、账号定位、身份占位、非目标 |
| 策略变更提案 | StrategyChangeProposal | 打法、权重、阈值、显影高度、发布策略、抽检率 |
| 反哺候选 | BackfeedCandidate | 源体系可能需要补定义、补边界、补解释或修订 |
| 校正范本 | CalibrationExample | 写作、审校、质量判断或反例训练资产 |

降噪原则：

1. 单个低强度信号不直接生成候选；必须先经过聚合门（Aggregation Gate）、阈值门（Threshold Gate）和目的门（Purpose Gate）。
2. Amy 可以合并重复误读、重复追问、低风险共鸣和过期机会，但合并必须保留来源。
3. 候选被批准不等于已经应用；必须分开记录 `CandidateDecision / 候选裁决` 与 `CandidateApplication / 候选应用`。
4. 未完成裁决和应用记录前，不得修改 `SourcePack / LighthouseStrategyObjective / CaseObjective / PurposePortfolio / plan_pool`。

### 1.11a-1 候选路由决策树

信号从进入系统到分派至具体路由目标的完整路径：

```text
SignalEvent / FieldState / HumanFeedback / RecallCard
    ↓
Aggregation Gate / 聚合门：同类信号计数、同 scope 分组
    ↓
Threshold Gate / 阈值门：信号强度 ≥ 最低阈值、时间窗口内足够样本
    ↓
Purpose Gate / 目的门：映射到具体 business implication，判断是否有行动含义
    ↓
CandidateProposalEnvelope / 候选提案信封：统一记录来源、证据、作用范围、风险
    ↓
RouteDecision / 路由决策：
  ├─ 新平台/新媒体/新受众/新主题/新载体 → OpportunityCandidate
  ├─ 正式计划池/产能/节奏/主题配额变化、目的组合超自动调整带 → PlanChangeProposal
  ├─ 源体系边界/灯塔目标/账号定位/身份占位/非目标 → BoundaryChangeProposal
  ├─ 打法/权重/阈值/显影高度/发布策略/抽检率 → StrategyChangeProposal
  ├─ 源体系补定义/补边界/补解释/修订 → BackfeedCandidate
  └─ 写作/审校/质量判断/反例训练 → CalibrationExample
```

最常见误分派场景的速查：

| 信号类型 | 正确路由 | 常见误路由 |
|----------|----------|------------|
| 连续 3 篇预测偏离 | StrategyChangeProposal | 误认为 BackfeedCandidate |
| 高流量但高误读 | StrategyChangeProposal + CalibrationExample | 误认为 OpportunityCandidate 加码 |
| 评论反复追问同一概念 | BackfeedCandidate | 误认为 CalibrationExample |
| 新平台首次好数据 | OpportunityCandidate + Observe | 误认为直接 StrategyChangeProposal 加码 |
| 同目的连续产出 5 篇 | PlanChangeProposal（调整目的组合） | 误认为 BoundaryChangeProposal |

`algorithm_noise_overload / 算法噪声过载` 期间的信号默认只路由到 `ObserveOnly`，不进入任何正式候选，除非人类手动提升。涉及 `redline / 红线`、`source_boundary / 源边界`、`SourcePack / 源体系包`、`LighthouseStrategyObjective / 灯塔策略目标` 或 `CaseObjective / 案目标` 的候选，Amy 只能准备材料，不得自动裁决。

圆桌确认：ArtifactOS / 演擎不能用平台短期指标直接决定加码或降频。系统需要保存“为什么某个场域、平台、账号、主题、目的组合、产出系列或片场值得投入”的可反驳论点。

```text
SignalEvent / FieldState / QualitySnapshot / PublicationAttempt
  -> InvestmentEvidenceRef / 投入证据引用
  -> InvestmentAssessmentPolicy / 投入评估策略
  -> InvestmentAssessmentRun / 投入评估运行
  -> InvestmentThesisSnapshot / 投入论点快照
  -> CandidateProposal / 候选提案
  -> PlanChangeProposal / StrategyChangeProposal / BoundaryChangeProposal
```

核心原则：

1. `FieldState / 场域状态` 是雷达，`InvestmentThesisSnapshot / 投入论点快照` 是判断资产，`CandidateProposal / 候选提案` 是进入正式变更的信封。
2. 阅读量、点赞、收藏、转发、评论等平台指标只能作为证据之一；不能单独证明方向正确，也不能单独证明源体系、灯塔目标或主题失败。
3. 加码必须同时看 `SourceRelevanceEvidence / 源体系相关度证据`、`LighthouseCoherenceEvidence / 灯塔一致性证据`、`AlignedResonanceSignal / 同频共鸣信号`、`AssetFormationEvidence / 资产沉淀证据` 与 `RiskCostEvidence / 风险成本证据`。
4. 降频不等于放弃；它可能表示换平台、换形态、换显影高度、转观察或等待机会窗口。
5. 每个投入论点必须声明 `ExpectedOutcome / 预期结果`、`SuccessMetricSet / 成功指标集`、`FailureCondition / 失败条件` 与 `ReviewDueAt / 复盘时间`；没有复盘时间的投入判断不能生效。
6. `algorithm_noise_overload / 算法噪声过载` 灰灯期间，不允许自动生成加码决策，只能生成观察、保持、暂停或人工审阅候选。

评估策略（Assessment Policy）必须表化五类判断：

| 判断 | English | 说明 |
|---|---|---|
| 评估维度 | Assessment Dimension | 源体系相关、灯塔一致、同频共鸣、资产沉淀、平台适配、机会窗口、生产成本、人类注意力成本、误读、疲劳、边界风险 |
| 证据要求 | Evidence Requirement | 每个维度需要哪些证据，缺证时失败、降级还是转观察 |
| 推荐阈值 | Recommendation Threshold | increase/decrease/hold/pause/experiment/observe 的分数、风险和缺证门槛 |
| 否决项 | Veto Rule | 红线、源边界、灯塔漂移、算法噪声等一票否决条件 |
| 评分轨迹 | Score Trace | 每次评估各维度得分、证据数、反证、置信度与触发的否决项 |

`AssessmentPolicySeed / 评估策略种子` 采用三层结构：

```text
CoreStrategicSeed / 核心战略种子
  + PlatformAdaptationSeed / 平台适配种子
  + MediaShapeAdaptationSeed / 形态适配种子
  + OverrideSet / 覆盖集
  -> InvestmentAssessmentPolicy / 投入评估策略实例
```

不可覆盖边界：

1. `SourceFit / 源体系匹配`、`LighthouseFit / 灯塔匹配`、`BoundarySafety / 边界安全`、`RiskEnvelope / 风险包络` 和 `HumanDecisionBoundary / 人类裁决边界` 只能收紧，不能被平台或形态适配放松。
2. 平台适配只能调整信号解释、曝光周期、平台原生格式偏好和平台规则限制；不能改变源体系和灯塔判断。
3. 媒体形态适配只能调整生产成本、审阅成本、资产沉淀方式、共鸣表达方式和发布包结构要求。
4. 种子升级不得自动改用户正在使用的策略实例，只能生成 `CandidateProposal / 候选提案`。

### 1.11c 投入结果复盘（Investment Outcome Review）

`OutcomeReview / 结果复盘` 检验的是原始 `InvestmentThesisSnapshot / 投入论点快照`，不是简单判断数据好坏。

```text
InvestmentThesisSnapshot / 投入论点快照
  -> InvestmentOutcomeBaselineSnapshot / 投入结果基线快照
  -> InvestmentOutcomeReview / 投入结果复盘
    -> OutcomeActualMetric / 实际结果指标
    -> OutcomeExpectationComparison / 预期实际比较
    -> OutcomeAttributionHypothesis / 结果归因假设
    -> CandidateProposal / 候选提案
```

复盘结论（Review Result）必须区分：

| 结论 | English | 含义 |
|---|---|---|
| 支持 | supported | 证据支持原投入论点 |
| 部分支持 | partially_supported | 某些维度成立，某些维度不成立 |
| 反驳 | contradicted | 关键假设被明显推翻 |
| 不确定 | uncertain | 信号不足或归因不清 |
| 证据不足 | insufficient_evidence | 样本太少、窗口太短或采集覆盖不足 |
| 归因混杂 | confounded | 无法判断是主题、平台、标题、时机、账号还是形态导致 |
| 过早判断 | premature | 尚未过观察周期 |
| 噪声过载 | noise_overloaded | 算法噪声或平台异常使结论不可用 |
| 风险超限 | risk_exceeded | 热度存在，但误读、边界或身份风险超过可接受范围 |

复盘边界：

1. 复盘只能产生候选、调权建议、计划变更草案、种子校正候选、校正范本或反哺候选，不能直接改 `SourcePack / LighthouseStrategyObjective / PurposePortfolio / AssessmentPolicySeed`。
2. 从初始证据假设升级为稳定策略规则，必须经过多周期复盘、归因不确定性记录和人类裁决。
3. `algorithm_noise_overload / 算法噪声过载` 时，复盘不能判定为确定支持或确定反驳。
4. 低流量高同频不能直接判失败；高流量低同频不能直接判成功。

## 二、规范对象图（Canonical Object Graph）

### 2.1 时间案包含关系（Temporal Case Containment）

```text
年案（YearCase）
  -> 半年案（HalfYearCase）
    -> 季案（QuarterCase）
      -> 月案（MonthCase）
```

### 2.2 上层约束与下层动作（Upper Constraint and Lower Action）

| 层级（Level） | 核心决策（Core Decision） | 禁止越界（Prohibited Override） |
|---|---|---|
| 年案（YearCase） | 北极星、主海域、绝对禁区 | 不安排具体稿件 |
| 半年案（HalfYearCase） | 战略校准、资源重配 | 不改年案北极星 |
| 季案（QuarterCase） | 主题季、验证重点 | 不擅自新增主海域 |
| 月案（MonthCase） | 灯塔位置、账号组合、显影比例 | 不突破季案主题边界 |
| 周案（WeekCase） | 本周战术安排、主题池、观察指标 | 不改变月案灯塔定位 |
| 日案（DayCase） | 今日主题集合、可运行范围 | 不改变周案目标 |
| 今日子案（DaySubCase） | 今日某主题的行动案 | 不突破日案与上层边界 |
| 片场（Studio） | 生成环境 | 不改变账号/平台/受众/形态等固定环境变量 |
| 子片场（SubStudio） | 单产出物执行 | 不产生多个独立产出物 |

每个案（Case）必须记录：

```text
继承约束（inherited_constraints）
本层决策（local_decisions）
边界变更提案引用（boundary_change_proposal_refs）
```

下层若要突破上层约束，只能生成边界变更提案（BoundaryChangeProposal），不能静默改写上层案（Case）。

## 三、案与授权模型（Case and Delegation Model）

### 3.1 案（Case）

案（Case）是可授权、可运营、可复盘、可遗忘、可召回的治理单元。时间案（Temporal Case）通过父案标识（parent_case_id）形成包含关系。

| 属性（Property） | 说明（Description） |
|---|---|
| 案标识（case_id） | 唯一标识 |
| 案类型（case_type） | `year / half_year / quarter / month / week / day / day_sub` |
| 父案标识（parent_case_id） | 上层案 |
| 名称（name） | 案名称 |
| 目的（purpose） | 该案要完成的事情 |
| 状态（status） | `planned / active / reviewing / closed / frozen / archived` |
| 源体系引用（source_pack_refs） | 使用的源体系包 |
| 继承约束（inherited_constraints） | 上层下发的边界 |
| 本层决策（local_decisions） | 本层新增动作与取舍 |
| 授权策略引用（delegation_policy_ref） | 秘书权限 |
| 介入策略引用（intervention_policy_ref） | 人类被打扰条件 |
| 遗忘策略引用（forgetting_policy_ref） | 召回/衰减范围 |

### 3.2 授权策略（DelegationPolicy）

授权策略（DelegationPolicy）决定秘书（ExecutiveProducerSecretary）可以做什么。

| 模式（Mode） | 权限（Permission） |
|---|---|
| 人工审片（manual_review） | 可生产和改稿，发布前必须人类批准 |
| 秘书审片（secretary_review） | 秘书可代审，通过后进入待发布流程 |
| 秘书发布（secretary_publish） | 秘书可代审并发布 |
| 仅汇报（report_only） | 全自动执行，只在摘要中汇报 |
| 冻结（frozen） | 不执行生产或发布 |

策略继承优先级（Policy Precedence）：

```text
全局策略（GlobalPolicy）
  -> 案策略（CasePolicy）
    -> 今日子案策略（DaySubCasePolicy）
      -> 片场策略（StudioPolicy）
        -> 子片场覆盖（SubStudioOverride）
```

越具体的策略优先级越高。

### 3.3 介入策略（InterventionPolicy）

介入策略（InterventionPolicy）决定秘书何时需要把事项交回人类。

| 介入级别（Intervention Level） | 含义（Meaning） |
|---|---|
| 静默记录（silent_record） | 不打扰，只入账 |
| 摘要汇报（digest） | 日报/周报中出现 |
| 待看队列（review_queue） | 可稍后查看，不阻断生产 |
| 下次会议请示（ask_next_meeting） | 下次相关会议中形成决策简报 |
| 立即中断（interrupt_now） | 立即冻结或请求裁决 |

授权策略（DelegationPolicy）与介入策略（InterventionPolicy）必须分离。一个案（Case）可以允许秘书发布，同时只在红线或反哺候选出现时介入人类。

## 四、日案到片场（DayCase to Studio）

### 4.1 今日子案（DaySubCase）

日案（DayCase）包含多个主题（Theme）。每个主题（Theme）与日案（DayCase）交互形成一个今日子案（DaySubCase）：

```text
日案（DayCase） + 主题（Theme） = 今日子案（DaySubCase）
```

今日子案（DaySubCase）确定：

| 属性（Property） | 说明（Description） |
|---|---|
| 主题引用（theme_ref） | 今天处理的主题 |
| 今日目标（daily_goal） | 今日希望完成的显影目标 |
| 核心问题（core_question） | 产出围绕的判断 |
| 允许角度（allowed_angles） | 可采用的表达角度 |
| 禁止角度（forbidden_angles） | 不可采用的表达角度 |
| 上层约束（inherited_constraints） | 来自周/月/季/年案 |
| 当日授权覆盖（daily_delegation_override） | 今日允许秘书生成、改稿、审片、发布或仅产出不发布 |

日晨会（Daily Meeting）的默认授权粒度是今日子案（DaySubCase）：

```text
案（Case）             = 长期目标、边界和默认授权
今日子案（DaySubCase） = 今天是否启动行动及授权到什么程度
片场（Studio）         = 授权后建立的生成环境
产出物（Artifact）     = 批量总编台中检查的具体结果
```

成熟案（Mature Case）若已授予秘书发布权限，可自动形成今日子案并运行；日晨会只显示摘要、异常和撤回/降权入口。出现红线、反哺候选（BackfeedCandidate）、严重归因冲突或上层边界变化时，必须通过决策简报（DecisionBrief）请求人类裁决。

### 4.2 片场（Studio）

片场（Studio）是一个生成环境（Generation Environment），不等于某篇稿件，也不等于多个平台任务的简单分组。

```text
片场（Studio） =
  今日子案（DaySubCase）
+ 账号（Account）
+ 平台（Platform）
+ 受众状态（AudienceState）
+ 内容形态（ArtifactType）
+ 理论显性度（TheoryVisibility）
+ 声音包（VoicePack）
+ 质量画像（QualityProfile）
+ 授权策略（DelegationPolicy）
+ 操作上下文包（OperationContextPack）
```

一个片场（Studio）中的下列环境变量必须固定：

- 账号（account_id）
- 平台（platform_id）
- 受众状态（audience_state）
- 产出物类型（artifact_type）
- 理论显性度（theory_visibility）
- 声音包版本（voice_pack_version）
- 源快照引用（source_snapshot_ref）

其中任一变量变化，必须建立新的片场（Studio）。

### 4.3 子片场（SubStudio）

子片场（SubStudio）是单产出物执行单元（Single-Artifact Execution Unit）：

```text
一个子片场（SubStudio） -> 一个产出物（Artifact）
一个片场（Studio） -> 多个子片场（SubStudio）
```

子片场（SubStudio）接收一个产出计划（ArtifactPlan），执行契约生成、部件生产、组装、门禁、审批、发布打包和结果回收。

## 五、产出物模型（Artifact Model）

### 5.1 产出物（Artifact）

产出物（Artifact）是一个可发布、可审校、可追溯、可复盘、可召回的媒体成品。它可以是单文本，也可以是由多个部件组成的复合媒体。

```text
产出物（Artifact）
  -> 产出物部件（ArtifactPart）
      -> 部件版本（ArtifactPartVersion）
      -> 资源文件（AssetFile）
  -> 产出物版本（ArtifactVersion）
  -> 渲染版本（Rendition）
  -> 发布包（PublicationPackage）
  -> 发布记录（Publication）
```

### 5.2 资源文件（AssetFile）

资源文件（AssetFile）是可被引用、校验、渲染、发布或归档的文件级对象。

| 属性（Property） | 说明（Description） |
|---|---|
| 资源文件标识（asset_file_id） | 文件级唯一标识 |
| 资源文件类型（asset_file_type） | `markdown / image / video / audio / subtitle / pdf / html / json` |
| 文件路径（file_path） | 文件位置 |
| 内容哈希（content_hash） | 完整性与幂等检查 |
| 媒体类型（mime_type） | 文件媒体格式 |
| 文件大小（file_size） | 大小 |
| 尺寸（dimensions） | 图片/视频宽高 |
| 时长（duration） | 视频/音频时长 |
| 语言（language） | 内容语言 |
| 生成来源（generated_by） | AI、人类或导入来源 |

### 5.3 复合媒体示例（Composite Media Example）

```text
产出物（Artifact）：小红书笔记（XiaohongshuNote）
  部件（ArtifactPart）：
    - 封面图（CoverImage）
    - 轮播图（CarouselImage）× N
    - 主视频（MainVideo，可选）
    - 文案（Caption）
    - 标签集（HashtagSet）
  资源文件（AssetFile）：
    - cover_v1.webp
    - slide_01_v1.webp
    - clip_v1.mp4
    - caption_v1.md
    - tags_v1.json
```

## 六、蓝图与计划（Blueprint and Plan）

### 6.1 产出物蓝图（ArtifactBlueprint）

产出物蓝图（ArtifactBlueprint）规定某类媒体产出物由哪些产出物部件（ArtifactPart）组成，以及其门禁和发布打包规则。

| 属性（Property） | 说明（Description） |
|---|---|
| 蓝图标识（blueprint_id） | 唯一标识 |
| 产出物类型（artifact_type） | 如 `zhihu_article / xhs_note / short_video` |
| 平台（platform_id） | 目标平台 |
| 版本（version） | 蓝图版本 |
| 必需部件（required_parts） | 必须存在的部件 |
| 可选部件（optional_parts） | 可选部件 |
| 组装规则（assembly_rules） | 顺序、树结构、时间轴和版面规则 |
| 门禁规则（gate_rules） | 部件和整体门禁 |
| 渲染规则（rendition_rules） | 平台适配规则 |
| 发布包规则（publication_package_rules） | 提交需要的字段 |

产出物部件（ArtifactPart）必须支持：

```text
父部件标识（parent_part_id）
顺序（sequence）
时间轴（timeline）
版面区域（layout_region）
约束（constraints）
资源文件引用（asset_file_refs）
```

### 6.1a 蓝图样例

首版至少锁定三个蓝图样例，即使 Phase 1 只实现知乎，也要先预埋到模型以防止以文章为默认中心：

**知乎文章蓝图（ZhihuArticleBlueprint）v1**

```yaml
blueprint_id: bp_zhihu_article_v1
artifact_type: zhihu_article
platform_id: zhihu
required_parts:
  - part_type: title
  - part_type: body
  - part_type: tags
optional_parts:
  - part_type: cover_image
  - part_type: summary
  - part_type: topic_entry
gate_rules:
  - part_gate: title, body, tags
  - assembly_gate: title 非空，body 段落 >=3，tags >=1
  - artifact_gate: ES + 半ES + NES + SourceFidelity
  - package_gate: 知乎必填字段、幂等键、账号权限
```

**公众号文章蓝图（WeChatArticleBlueprint）v1**

```yaml
blueprint_id: bp_wechat_article_v1
artifact_type: wechat_article
platform_id: wechat
required_parts:
  - part_type: title
  - part_type: body
  - part_type: cover_image
optional_parts:
  - part_type: summary
  - part_type: author_signature
  - part_type: guide_follow
  - part_type: read_original_link
gate_rules:
  - part_gate: title, body, cover_image
  - assembly_gate: title <= 64 字，body 排版合规
  - artifact_gate: ES + 半ES + NES + SourceFidelity + PlatformRisk
  - package_gate: 微信必填字段、图文素材、账号权限
```

知乎 vs 公众号核心差异：知乎用话题体系组织内容；公众号依赖排版风格 + 引导关注 + 阅读原文链接建立信任累积。公众号封面图是必填而非可选。

**小红书笔记蓝图（XiaohongshuNoteBlueprint）v1**

```yaml
blueprint_id: bp_xhs_note_v1
artifact_type: xhs_note
platform_id: xiaohongshu
required_parts:
  - part_type: cover_image
  - part_type: carousel_image    # 1-10 张
  - part_type: caption
  - part_type: hashtag_set
optional_parts:
  - part_type: video
gate_rules:
  - part_gate: cover_image, carousel_image, caption, hashtag_set
  - assembly_gate: 图片 >=1，caption <= 1000 字，hashtag >=1
  - artifact_gate: ES + 半ES + NES + SourceFidelity + VisualCoherence
  - package_gate: 小红书必填字段、图片尺寸、账号权限
```

蓝图建新不修旧的判据：当产出物类型需要不同的 `required_parts` 组合、不同的 `gate_rules` 或不同的 `publication_package_rules` 时，建新蓝图；仅参数差异（如字数范围、标签数量上限）在同一蓝图内通过版本参数化。

PublicationPackage 与 ArtifactBlueprint 的关系为一对一绑定：一个发布包只对应一个蓝图；多平台多账号从同一蓝图产生不同的 Rendition（渲染版本）但同属一个发布包。

### 6.2 产出计划集（ArtifactPlanSet）

产出计划集（ArtifactPlanSet）由秘书（ExecutiveProducerSecretary）组织 AI 岗位，在片场（Studio）的固定环境内生成。

```text
上层案约束（Case Constraints）
+ 今日子案（DaySubCase）
+ 片场环境（Studio Environment）
+ 可用蓝图（ArtifactBlueprint）
+ 召回卡（RecallCard）
+ 信号复盘（SignalReview）
+ 授权策略（DelegationPolicy）
= 产出计划集（ArtifactPlanSet）
```

每个产出计划（ArtifactPlan）对应一个子片场（SubStudio）：

| 属性（Property） | 说明（Description） |
|---|---|
| 产出计划标识（artifact_plan_id） | 唯一标识 |
| 片场标识（studio_id） | 生成环境 |
| 蓝图引用（artifact_blueprint_ref） | 成品结构 |
| 产出意图（artifact_intent） | 为什么做这一件成品 |
| 角度（angle） | 内容切入 |
| 标题种子（title_seed） | 初始题目方向 |
| 预期受众状态假设（expected_audience_state_hypothesis） | 目标 S0-S7 假设；包含证据、置信度、不确定性与替代状态 |
| 预期迁移（expected_shift） | 希望产生的微小认知移动 |
| 风险等级（risk_level） | 门禁与介入输入 |
| 选择理由（selection_reason） | 为什么进入生产 |
| 主目的类型（primary_purpose_type） | 来自 `PurposeTypeRegistry / 目的类型注册表` 的一个 active 版本 |
| 副目的类型（secondary_purpose_types） | 可选 0-2 个辅助目的 |
| 必需硬门禁（required_hard_gates） | 该目的下必须通过的门禁 |
| 最低评分维度（minimum_score_dimensions） | 该目的下不可低于阈值的软评分 |
| 质量放行条件（quality_exit_criteria） | 可发布、暂存、返工、冻结和人工介入的判定条件 |

### 6.3 子片场执行链（SubStudio Execution Chain）

```text
产出计划（ArtifactPlan）
  -> 子片场（SubStudio）
    -> 产出物契约（ArtifactContract）
      -> 部件生产任务（PartProductionTask）
        -> 资源文件（AssetFile）
      -> 组装（Assembly）
      -> 门禁审查（GateReview）
      -> 渲染版本（Rendition）
      -> 发布包（PublicationPackage）
      -> 审批记录（ApprovalRecord）
      -> 发布记录（Publication）
```

## 七、门禁模型（Gate Model）

| 门禁（Gate） | 目标（Target） | 判断内容（Checks） |
|---|---|---|
| 部件门禁（PartGate） | 产出物部件（ArtifactPart） | 文字、图片、视频、字幕、标签等单体合规与质量 |
| 组装门禁（AssemblyGate） | 产出物（Artifact）内部结构 | 顺序、版面、时间轴、部件一致性 |
| 产出物门禁（ArtifactGate） | 完整产出物（Artifact） | 意图、契约、受众、源边界、传播价值 |
| 片场门禁（StudioGate） | 同片场子片场集合 | 环境一致、角度互补、重复与漂移检查 |
| 发布包门禁（PackageGate） | 发布包（PublicationPackage） | 平台必填、文件存在、幂等、账号和发布策略 |

门禁结果（GateResult）必须记录：

```text
门禁类型（gate_type）
目标标识（target_id）
状态（status: pass / warning / fail / blocked）
问题列表（issues）
要求动作（required_actions）
证据引用（evidence_refs）
评审角色（reviewer_role）
```

## 八、信号归因与遗忘（Signal Attribution and Forgetting）

### 8.1 发布前信号预期（SignalExpectation）

每个产出计划（ArtifactPlan）在生产或发布前必须声明信号预期（SignalExpectation）：

| 属性（Property） | 说明（Description） |
|---|---|
| 目标信号（target_signals） | 阅读、收藏、转发、完播、下载等 |
| 观察窗口（observation_window） | 例如发布后 72 小时 |
| 对照基线（comparison_baseline） | 同账号同形态历史基线 |
| 可归因层级（attributable_level） | `artifact / studio / case` |
| 推断边界（inference_limit） | 哪些解释不能从数据直接推出 |

### 8.2 三层信号对象（Three-Layer Signal Objects）

| 层（Layer） | 对象（Object） | 含义（Meaning） |
|---|---|---|
| 事实层（Fact Layer） | 信号事件（SignalEvent） | 平台返回或人工录入的观察事实 |
| 推演层（Inference Layer） | 信号解释（SignalInterpretation） | AI 的原因与受众推测 |
| 决策层（Decision Layer） | 归因决策（AttributionDecision） | 是否进入实验、提案、召回或反哺 |

约束（Constraint）：

> 信号事件（SignalEvent）只能证明发生了什么，不能直接证明为什么发生，更不能直接证明源体系命题为真。

### 8.3 复盘 AI 岗位（Review AI Roles）

| 中文角色（Chinese Role） | 英文角色（English Role） | 负责对象（Output） |
|---|---|---|
| 信号采集 AI | SignalCollectorAI | 信号事件（SignalEvent） |
| 复盘分析 AI | SignalReviewAI | 信号评估（SignalAssessment） |
| 归因 AI | AttributionAI | 信号解释（SignalInterpretation）和归因候选 |
| 受众推断 AI | AudienceInferenceAI | 受众状态推断（AudienceStateInference） |
| 传播种子 AI | PropagationSeedAI | 传播种子候选（PropagationSeedCandidate） |
| 遗忘提炼 AI | ForgettingRefinerAI | 保留/衰减/归档/召回分流 |
| 总制片秘书 | ExecutiveProducerSecretary | 向人类呈现决策简报（DecisionBrief） |

## 九、人类介入与决策压缩（Human Intervention and Decision Compression）

### 9.1 人类只处理什么（Human Decision Boundary）

默认由 AI 和秘书自动处理：

- 数据采集与基线比较。
- 普通信号评估和弱候选分流。
- 已授权案（Case）与片场（Studio）内的改稿、复审和发布。
- 遗忘系统（ForgettingSystem）的衰减、压缩和归档。

需要人类裁决的默认事项：

- 长期授权策略（DelegationPolicy）变化。
- 上层案（Case）边界变更。
- 源体系包（SourcePack）或理论母板相关反哺。
- 红线风险（Redline Event）或高风险发布事故。
- 严重归因冲突（Attribution Conflict）。

具体是否即时打扰，由介入策略（InterventionPolicy）控制。

### 9.2 决策简报（DecisionBrief）

秘书不把原始复杂度直接交给人类，而是压缩成决策简报（DecisionBrief）。

| 属性（Property） | 说明（Description） |
|---|---|
| 简报标识（brief_id） | 唯一标识 |
| 问题（question） | 人类需要判断的一件事 |
| 推荐选项（recommended_option） | 秘书建议 |
| 可选动作（options） | 通常不超过四项 |
| 理由摘要（reasoning_summary） | 为什么建议 |
| 证据引用（evidence_refs） | 门禁、召回卡、数据或边界来源 |
| 风险等级（risk_level） | 风险 |
| 无响应默认动作（default_action_if_no_response） | 不回复时如何处理 |
| 截止时间（deadline） | 需要决定的时间 |

召回卡（RecallCard）负责带回历史；决策简报（DecisionBrief）负责提出当前需要裁决的问题。一个决策简报（DecisionBrief）可以引用多个召回卡（RecallCard）。

## 十一、当前冻结结论（Frozen Decisions）

1. 日常运营一级对象为案（Case），不用项目（Project）。
2. 案（Case）按年案（YearCase）到日案（DayCase）形成包含关系，上层约束下层。
3. 日案（DayCase）与主题（Theme）形成今日子案（DaySubCase）。
4. 片场（Studio）是生成环境（Generation Environment）；子片场（SubStudio）只对应一个产出物（Artifact）。
5. 产出物（Artifact）支持复合媒体，通过产出物部件（ArtifactPart）和资源文件（AssetFile）表达。
6. 新媒体形态通过产出物蓝图（ArtifactBlueprint）扩展，不修改核心流程。
7. 秘书（ExecutiveProducerSecretary）按授权策略（DelegationPolicy）代理审批/发布，按介入策略（InterventionPolicy）决定何时打扰人类。
8. 所有事实进入事件账本（EventLedger）；未来行动仅注入操作上下文包（OperationContextPack）。
9. 秘书可主动召回（Active Recall）历史，但召回卡（RecallCard）不自动成为规则。
10. 信号归因必须区分事实、推演和决策；运营数据不能自动修改源体系包（SourcePack）。
11. 日晨会（Daily Meeting）以今日子案（DaySubCase）为人类最小授权对象；成熟案（Mature Case）在授权范围内默认由秘书自动运行。
12. 六层会议必须分层讨论：年计划是战略执行，半年计划是战略调整，季度计划是战略安排，月度计划是战略落地，周计划是战术安排，日计划是战术落地。
13. 全年可动态增加、减少和调整计划，但必须通过 OpportunityCandidate / PlanChangeProposal / PlanChangeLog，不得静默修改 YearCase。
14. ArtifactOS 的产品目的不是治理 AI，而是围绕 SourcePack 持续生产、审校、发布、复盘高质量 Artifact，用于推广、放大和省人工。
15. 内部核心命题冻结为 `Source-to-Artifact Production and Amplification Kernel / 源体系到产出物生产与放大内核`；`AI Action Governance Kernel / AI 行动治理内核` 不再使用。
16. 生产能力注册、授权、介入、门禁、事件账本、状态机和审计只能服务于产出链主线，不能扩展成通用 Agent 平台。
17. 合格产出物（Qualified Artifact）必须通过硬门禁并满足预声明的目的匹配（PurposeFit）；高质量产出物（High Quality Artifact）才用于重点放大和范本沉淀。
18. 产出计划（ArtifactPlan）的 `primary_purpose_type` 与 `purpose_policy_binding_id` 必须在生成前锁定；质量检查失败后不得临时改口来绕过门禁。
