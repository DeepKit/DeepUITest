# 10 账号矩阵管理系统

> 系统编号：⑥
> 核心职责：管理账号画像、平台差异和策略单元矩阵，为知识进化流水线提供账号/平台/内容类型/理论介入方式配置
> 设计来源：皇包车「1+X+N KOS矩阵」、Rahel Bailie「成熟度五级模型」

---

## 一、设计理念

### 1.1 核心问题

一人运营多账号，最大的风险不是"做不过来"，而是**账号之间互相打架**：

- 同一主题多个账号都写了，自己跟自己竞争
- 各账号风格混乱，读者分不清差异
- 关键词覆盖有盲区，竞品轻松截流

### 1.2 核心原则

1. **分层分工**：不同层级的账号有不同的定位和内容策略
2. **关键词拦截**：每个关键词都有明确的负责账号，不留盲区
3. **风格一致性**：同一账号的所有内容保持统一的品牌调性
4. **策略单元自治**：账号不是最小运营对象，`账号 + 平台 + 内容类型 + 理论介入方式` 才是自治授权对象
5. **成熟度递进**：从烟囱式各自为战，逐步升级到战略驱动的统一运营

## 三、平台账号浏览器会话边界

账号矩阵中的运行态浏览器以 `平台 + 账号` 为最小会话单位，而不是只以账号为单位。

```text
PlatformAccountSession = platform_id + account_id
```

示例：

| 平台 | 账号 | 浏览器/profile |
|---|---|---|
| zhihu | main | `.media_publish/profiles/zhihu/main` |
| wechat | main | `.media_publish/profiles/wechat/main` |
| xiaohongshu | main | `.media_publish/profiles/xiaohongshu/main` |
| zhihu | sub | `.media_publish/profiles/zhihu/sub` |

硬规则：

```text
同一个浏览器/profile 不允许跨平台使用。
同一个 platform+account 同时只能有一个 active publish task。
浏览器任务完成后默认不关闭，保持登录态和页面状态。
只有人类或明确维护操作才能关闭该会话。
```

账号画像描述“这个账号是谁”；平台账号浏览器会话描述“这个账号在某个平台上的真实登录态和页面状态”。二者不能混用。

### 3.2 画像用途

画像在以下环节被使用：

- **选题漏斗**：评估选题与账号定位的匹配度
- **契约生成**：填充契约中的 target_reader、style、taboos
- **写作引擎**：作为上下文 Slot 注入（账号声音和风格要求）
- **质量门禁**：品牌调性一致性检查
- **CTF复审**：账号画像发生重大变更时，相关 `ContentSpecSnapshot` 和契约标记为 `needs_review`
- **知识进化控制台**：生成策略单元，配置自治等级、评分矩阵、抽检率、认知成熟度和发布权限

## 四、策略单元矩阵

### 4.1 策略单元定义

策略单元是自治授权和策略优化的最小对象：

```text
StrategyUnit = account_id + platform + content_type + theory_intervention
```

账号画像描述“这个账号是谁”，策略单元描述“这个账号在某个平台上用某种理论介入方式生产某类内容时，系统能自治到什么程度”。

### 4.2 策略单元字段

```json
{
  "strategy_unit_id": "su_zhihu_sub_hot_long_theory_high",
  "account_id": "sub",
  "platform": "zhihu",
  "content_type": "hotspot_longform",
  "theory_intervention": "high",
  "entry_priority": ["hotspot_driven", "theory_driven"],
  "autonomy_level": "AL3",
  "quality_profile_id": "qp_zhihu_theory_longform_v1",
  "max_rewrite": 3,
  "on_pass": "auto_publish",
  "on_rewrite_exhausted": "downgrade_wait_human",
  "human_intervention_enabled": true,
  "human_unavailable_action": "store_draft",
  "sampling_policy": {
    "random_sample_rate": 0.1,
    "risk_sample_boost": true,
    "new_strategy_sample_rate": 0.5
  },
  "lights": {
    "current": "green",
    "pending_suggestions": []
  },
  "cognition_score": {
    "attribute_recognition": 0.72,
    "trend_prediction": 0.65,
    "intervention_effectiveness": 0.7,
    "evidence_calibration": 0.6
  }
}
```

### 4.3 自治等级与降权

| 等级 | 含义 |
|------|------|
| `AL0` | 人类主导，系统只辅助 |
| `AL1` | 系统生成，人类必审 |
| `AL2` | 系统自动重写，人类裁决发布 |
| `AL3` | 达标自动发布，人类抽检异常 |
| `AL4` | 自动追热点、选题、发布、复盘和提出调参建议 |

策略单元升权不只看近期内容表现，还要看 `cognition_score`。如果系统能写出高分文章，但预测经常失准、EvidenceClaim 经常被反证、理论映射经常漂移，则不能升权。

人类可以随时对策略单元降权：

```text
AL4 -> AL3 -> AL2 -> AL1 -> AL0
```

降权不影响其他策略单元，除非反馈作用范围被提升到账号级、平台级或理论层级。

## 五、关键词拦截表

### 4.1 设计理念

每个关键词都应该有明确的负责账号，不留覆盖盲区。避免：
- 多个账号写同一关键词（内耗）
- 关键词无人覆盖（竞品截流）

### 4.2 拦截表结构

| 关键词 | 负责账号 | 覆盖状态 | 最近覆盖日期 | 竞品覆盖 | 优先级 |
|--------|---------|---------|-------------|---------|--------|
| "编程思维" | sub | ✅ 已覆盖 | 2026-05-22 | — | 高 |
| "写作方法论" | sub | ⚠️ 待更新 | 2026-05-10 | — | 高 |
| "中年转型" | sub | ⚠️ 待覆盖 | — | ✅ 竞品A | 高 |
| "知识管理" | 专家号A | ❌ 未建号 | — | ✅ 竞品B | 中 |
| "软件工程思维" | sub | ❌ 未覆盖 | — | — | 中 |

### 4.3 拦截规则

```
选题漏斗匹配关键词时：
1. 查拦截表 → 找到负责账号
2. 检查覆盖状态 → 已覆盖的降低优先级（避免重复）
3. 检查竞品覆盖 → 竞品已覆盖的提高优先级（抢回流量）
4. 检查账号排期 → 负责账号近期是否有空余档期
```

## 六、成熟度模型

### 5.1 五级成熟度（Rahel Bailie）

| 级别 | 名称 | 特征 | 关键任务 |
|------|------|------|---------|
| **AML1** | 烟囱式 | 各账号独立运营，无协调 | 建立账号注册和基础画像 |
| **AML2** | 战术级 | 有统一术语和品牌规范 | 建立关键词拦截表 |
| **AML3** | 统一呈现 | 读者看到的品牌体验统一 | 统一风格指南和素材库 |
| **AML4** | 受控管理 | 统一创作/发布系统 | 部署 ArtifactOS 全链路 |
| **AML5** | 战略驱动 | 每个账号是整体战略的贡献者 | 数据回收驱动的自动优化 |

### 5.2 当前状态

```
当前：AML1（烟囱式）
  └── 只有1个知乎账号（sub），无矩阵

目标（首期）：AML3（统一呈现）向 AML4（受控管理）过渡
  └── 至少1个账号 + 1个平台 + 1个内容类型形成可运行策略单元
  └── 策略单元可配置自治等级、评分矩阵和发布权限
  └── 进化控制台可显示灯号和降权入口
```

## 七、账号-主题适配

### 6.1 适配评估

给定一个选题，评估它适合哪个账号：

```python
def match_account(topic, accounts):
    scores = {}
    for account in accounts:
        score = 0
        # 主题与账号定位匹配
        score += keyword_overlap(topic.keywords, account.expertise) * 30
        # 近期未覆盖（避免重复）
        if topic not in account.recent_topics:
            score += 20
        # 关键词拦截表匹配
        if topic.keyword in interception_table[account.id]:
            score += 30
        # 账号档期
        if account.has_capacity:
            score += 20
        scores[account.id] = score
    return sorted(scores.items(), key=lambda x: -x[1])
```

实际执行时，账号匹配只是第一步。最终必须匹配到具体策略单元：

```python
def match_strategy_unit(topic, strategy_units):
    scores = {}
    for su in strategy_units:
        score = 0
        score += account_fit(topic, su.account_id) * 20
        score += platform_fit(topic, su.platform) * 20
        score += content_type_fit(topic, su.content_type) * 20
        score += theory_fit(topic, su.theory_intervention) * 25
        score += operation_goal_fit(topic, su.quality_profile_id) * 15
        scores[su.strategy_unit_id] = score
    return sorted(scores.items(), key=lambda x: -x[1])
```

### 6.2 排期约束

- 同一账号两次同主题间隔 ≥ 14天
- 同一账号每周发布不超过频率上限
- 热点选题可以按策略单元配置打破排期；高自治策略单元可自动打破，低自治策略单元要求人类确认
