# 12 质量门禁系统

> 系统编号：⑤
> 核心职责：对产出物部件（ArtifactPart）、产出物（Artifact）、片场（Studio）、发布包（PublicationPackage）、证据断言和认知轨迹进行分层门禁，按策略单元决定自动通过、重写、抽检、降级、发布、冻结或不写
> 设计来源：DeepStory「ES/半ES/NES三级」、DeepStory「缺陷三分法」、Clearscope「多维度评分」

---

## 一、设计理念

### 1.1 核心原则

1. **分级校验，各司其职**：硬门禁保底、半ES防漏、NES评分、策略裁决、人工抽检
2. **不是二元判断**：质量评估的输出不是"好/坏"，而是三分类 + 置信度
3. **返工不等于全盘否定**：缺陷可能是毁灭性的（必须修）、生产性的（应保护）、或中性的（需裁决）
4. **校验成本可控**：ES零成本、半ES低成本、NES有成本但可选
5. **门禁必须留证据**：每次 PASS / FAIL / FREEZE / CONFLICT 都生成可回查的 gate_result 和 evidence
6. **断言必须可证据化**：关键事实、理论推导、价值判断和运营假设必须形成候选 `EvidenceClaim`
7. **源体系忠实度优先于表达流畅**：重写不能为了平台风格破坏 SourcePack 的主张、边界、禁忌；理论场景不得破坏理论原点和核心因果链
8. **边界决策也是质量结果**：当证据不足、源体系映射不稳或风险过高时，最优输出可能是 `not_write` 或 `draft_only`
9. **合格与高质量分离**：`Qualified Artifact / 合格产出物` 判断能否按既定目的进入发布安排；`High Quality Artifact / 高质量产出物` 判断是否值得优先放大和沉淀为范本
10. **目的必须预声明**：每个 `ArtifactPlan / 产出计划` 必须在生成前结构化声明 `primary_purpose_type / 主目的类型` 与质量放行条件，质量失败后不得临时修改目的规避门禁

### 1.1a 合格、高质量与目的匹配

质量判定采用两层结论：

| 结论 | English | 判断问题 | 默认动作 |
|---|---|---|---|
| 合格产出物 | `Qualified Artifact` | 是否通过硬门禁并满足本次预声明的 `PurposeFit / 目的匹配` | 可进入发布安排 |
| 高质量产出物 | `High Quality Artifact` | 是否在合格基础上具有更强表达、传播、差异和长期沉淀价值 | 优先排期、建议审阅、候选范本 |

`PurposeFit / 目的匹配` 不是自由解释，而是由 `ArtifactPlan / 产出计划` 在生成前声明：

| `primary_purpose_type` | 中文目的 | `purpose_family / 目的族` | `ResonancePotential / 共鸣潜力` 处理 |
|---|---|---|---|
| `attraction` | 吸引同频者 | `propagation / 传播` | 进入合格硬条件 |
| `repost_seed` | 转发种子 | `propagation / 传播` | 进入合格硬条件 |
| `concept_seed` | 概念种子 | `cognition / 认知` | 进入合格硬条件 |
| `amplification` | 传播放大 | `propagation / 传播` | 进入合格硬条件 |
| `explanation` | 解释说明 | `expression / 表达` | 作为软评分与排期依据 |
| `foundation` | 铺垫奠基 | `foundation / 奠基` | 作为软评分与排期依据 |
| `evidence_support` | 补证支撑 | `evidence / 证据` | 作为软评分与排期依据 |
| `statement` | 声明澄清 | `defense / 防御` | 作为软评分与排期依据 |
| `boundary_setting` | 边界设定 | `defense / 防御` | 作为软评分与排期依据 |

所有目的类型都必须通过源体系忠实度、边界安全、证据充分度、结构完整度、平台/发布包完整性与授权门禁。平台阅读量、点赞、转发和 AI 自评分不能单独决定合格或高质量。

`trust_building / 信任建立` 与 `positioning / 定位占位` 不是单篇产出物的主目的，而是 `CaseObjective / 案目标` 或 `LighthouseStrategyObjective / 灯塔策略目标`。它们必须通过 `PurposePolicyBinding / 目的策略绑定` 编译为多个具体 `PurposeType / 目的类型` 后，才能进入 `ArtifactPlan / 产出计划`。

### 1.2 结构门禁 + 四层质量门禁总览

```
草稿进入
    │
    ▼
┌────────────────────┐
│ 第零层：结构门禁    │  ← ODD前置，确认规格/契约可判定
│ （不通过FREEZE/退回）│
└────────┬───────────┘
         │ 通过
         ▼
┌────────────────────┐
│ 第一层：ES机械合规  │  ← 零成本，毫秒级
│ （不通过直接FAIL）  │
└────────┬───────────┘
         │ 通过
         ▼
┌────────────────────┐
│ 第二层：半ES语义    │  ← 低成本，秒级
│ （含源体系忠实度/断言风险）│
└────────┬───────────┘
         │ 通过
         ▼
┌────────────────────┐
│ 第三层：NES质量评估 │  ← 多维评分，按策略矩阵输出分数
│ （给出评分+建议）   │
└────────┬───────────┘
         │
         ▼
┌────────────────────┐
│ 第四层：策略裁决    │  ← 读取策略单元，决定自动动作
│ 自动发布/抽检/重写  │
```

人类终审不再是固定必经节点。人类介入由策略单元配置、抽检策略、红线、重写超限或看板灯号触发。

### 1.2a 产出物门禁层级（Artifact Gate Hierarchy）

上面的结构门禁、ES、半ES、NES 和策略裁决是“如何评价内容”的质量判定链。对于复合媒体产出物，还需要一条“对象是否可组成并发布”的组装门禁链；两条链不可混为一谈：

```text
产出物部件（ArtifactPart）
  -> 部件门禁（PartGate）
    -> 组装门禁（AssemblyGate）
      -> 产出物门禁（ArtifactGate）
        -> 片场门禁（StudioGate）
          -> 发布包门禁（PackageGate）
```

| 门禁（Gate） | 目标对象（Target） | 必须判定的事项 | 默认失败动作 |
|-------------|------------------|----------------|-------------|
| 部件门禁（PartGate） | 产出物部件（ArtifactPart） | 文案、图片、视频、音频、字幕、链接、标签单体的格式、风险、来源和版本 | 返工对应部件 |
| 组装门禁（AssemblyGate） | 产出物部件集合 | 必需部件齐全、顺序和引用正确、资源文件（AssetFile）存在且哈希一致 | 阻止产出物封存 |
| 产出物门禁（ArtifactGate） | 产出物（Artifact） | 蓝图符合、理论忠实、整体表达、证据包、可渲染性 | 返工或冻结产出物 |
| 片场门禁（StudioGate） | 片场（Studio）下的产出物集合 | 固定生成环境一致、角度不冲突、重复与策略漂移受控 | 冻结异常子片场 |
| 发布包门禁（PackageGate） | 发布包（PublicationPackage） | 平台必填字段、渲染版本（Rendition）、账号权限、幂等键、排期与发布证据 | 不交给发布适配器 |

规则：

1. 每个子片场（SubStudio）只对应一个产出物（Artifact），其 `ArtifactGate` 可以独立通过或失败。
2. `StudioGate` 不能替代单产出物质量检查，也不能因一个子片场失败而无条件阻断其他已通过子片场。
3. `PackageGate` 通过之前，不得调用发布适配器（PublishingAdapter）或旧版 `media_publish`。
4. 所有门禁结果均写入事件账本（EventLedger），由遗忘系统（ForgettingSystem）决定后续注入与召回。

### 1.3 ODD门禁结果

质量门禁不只输出"通过/不通过"，统一使用 ODD 结果矩阵：

| 结果 | 含义 | 默认去向 |
|------|------|---------|
| `PASS` | 当前门禁通过 | 进入下一状态 |
| `FAIL` | 明确不通过 | 进入返工 |
| `FREEZE` | 风险、信息不足或返工超限，不应自动推进 | 等待人工裁决 |
| `CONFLICT` | 契约、草稿、平台规则或账号边界互相冲突 | 返回契约修订 |

所有门禁结果必须记录 `actor`、`boundary_condition`、`evidence_refs` 和 `next_state`。

### 1.3a QualityRun 与 QualitySnapshot

质量事实必须区分过程与裁决：

| 对象 | 中文 | 作用 |
|---|---|---|
| `QualityPolicy` | 质量策略 | 绑定目的类型、硬门禁、软评分维度和放行条件 |
| `QualityRun` | 质量检查运行 | 记录一次门禁/评分执行所用策略版本、产出物版本、证据和结果 |
| `QualitySnapshot` | 质量快照 | 汇总一个决策时点生效的质量结论，供 Amy、审批和发布使用 |

约束：

1. 一个 `ArtifactVersion / 产出物版本` 可以有多次 `QualityRun`。
2. 每次批准、封存或发布只能引用一个生效的 `QualitySnapshot`。
3. `QualitySnapshot` 必须引用其聚合的 `QualityRun`，不得独立编辑。
4. 发布后的 `SignalEvent / 信号事件` 不得修改历史 `QualitySnapshot`；它只能形成质量策略或传播计划调整候选。
5. 一个 `PublicationPackage / 发布包` 必须绑定 exactly one effective `QualitySnapshot / 生效质量快照`；发布、审批与真实发布门均只能引用该快照。
6. ArtifactVersion、ArtifactPartVersion、Rendition、AssetFile、标题、正文、封面、标签、平台账号、发布时间窗口、QualityPolicy、PlatformConstraint 或 SourcePackSnapshot 任一关键绑定发生变化，原发布包必须作废为 `superseded`，重新构建并重新通过 PackageGate 与 RealPublishGate。

质量门禁额外输出 `BoundaryDecision`：

| 决策 | 含义 |
|------|------|
| `write` | 继续推进 |
| `draft_only` | 只存草稿，不发布 |
| `store_candidate` | 暂存候选 |
| `wait_human` | 等待人类裁决 |
| `freeze` | 冻结 |
| `not_write` | 明确不写 |

### 1.4 第零层：结构门禁（ODD前置）

结构门禁先于 ES 执行，解决的是“这个草稿是否有资格被检查”的问题。它不评价文字好坏，只检查需求、规格、契约、证据是否形成可追溯链。

| 检查项 | 通过条件 | 失败结果 |
|--------|---------|---------|
| `spec_snapshot_id` | 草稿能追到 `ContentSpecSnapshot`，探索临时草稿需明确标记 | `NEEDS_CTF_REVIEW` |
| `contract_candidate_status` | 发布级草稿必须来自 `ready` 候选或 `formal` 契约 | `NEEDS_CTF_REVIEW` |
| `boundary_status` | 账号、平台、素材、禁忌边界均未冲突 | `CONFLICT` |
| `stale_status` | 规格快照、账号画像、平台规则均为 `fresh` 或已人工确认 | `FREEZE` |
| `reversibility` | 本轮失败后能回到契约、草稿或发布前状态 | `ROLLBACK_REQUIRED` |
| `evidence_coverage` | 达到当前阶段阈值，首期发布前默认 >= 0.6 | `NEEDS_CTF_REVIEW` |
| `review_status` | 发布级规格必须为 `accepted` 或 `locked` | `NEEDS_CTF_REVIEW` |
| `spec_issues` | 不存在未关闭 high/critical 规格问题 | `NEEDS_CTF_REVIEW` |
| `agent_result.unresolved` | 未解决项为空，或已进入策略待办/人工待办 | `FREEZE` |

结构门禁返回值映射：

| 返回值 | 任务处理 |
|--------|---------|
| `PASS` | 进入 ES 机械合规 |
| `NEEDS_CTF_REVIEW` | 回到 CTF 规格快照审阅，不自动返工 |
| `FREEZE` | 设置 `flags.frozen=true`，等待人工裁决 |
| `CONFLICT` | 返回契约修订或账号/平台边界修订 |
| `ROLLBACK_REQUIRED` | 进入回滚/召回处理，不继续质量检查 |

## 二、第一层：ES机械合规

### 2.1 校验规则

| 规则ID | 规则名称 | 校验内容 | 失败动作 | 成本 |
|--------|---------|---------|---------|------|
| ES-01 | 字数合规 | word_count ∈ [contract.min, contract.max] | FAIL | 零 |
| ES-02 | 格式合规 | 标题非空、段落≥3、有结尾 | FAIL | 零 |
| ES-03 | must_land覆盖 | 每个must_land在正文中有关键词/近义词匹配 | FAIL | 零 |
| ES-04 | 禁忌词命中 | taboo_list 中无词出现在正文中 | FAIL | 零 |
| ES-05 | 平台敏感词 | 平台敏感词表无命中 | FAIL | 零 |
| ES-06 | 标题非空 | 标题存在且长度 > 0 | FAIL | 零 |
| ES-07 | 理论核心不可违反 | 检查草稿是否与契约 `theory.must_not_violate` 或 S08 `forbidden_relations` 中的结构化谓词冲突 | FAIL（关键词匹配 + LLM 辅助判断；命中即红灯，冻结任务） | 零 |

> Phase 1 保护措辞（核心原则原文不可被改写或覆盖）。Phase 3+ 引入语义保护（检测隐含的语义偏离）。

### 2.2 ES执行方式

```python
def es_check(draft, contract, platform_rules):
    results = []

    # ES-01: 字数
    wc = len(draft.content.body)
    if wc < contract.word_count.min or wc > contract.word_count.max:
        results.append(CheckResult("ES-01", "FAIL", f"字数{wc}，要求{contract.word_count.min}-{contract.word_count.max}"))

    # ES-02: 格式
    paragraphs = draft.content.body.split("\n\n")
    if len(paragraphs) < 3:
        results.append(CheckResult("ES-02", "FAIL", "段落数不足3段"))

    # ES-03: must_land覆盖
    for ml in contract.structure.must_land:
        if not keyword_in_text(ml, draft.content.body):
            results.append(CheckResult("ES-03", "FAIL", f"must_land未覆盖: {ml}"))

    # ES-04: 禁忌词
    for taboo in contract.constraints.taboos:
        if taboo in draft.content.body:
            results.append(CheckResult("ES-04", "FAIL", f"命中禁忌词: {taboo}"))

    # ES-05: 平台敏感词
    for word in platform_rules.sensitive_words:
        if word in draft.content.body:
            results.append(CheckResult("ES-05", "FAIL", f"命中平台敏感词: {word}"))

    return results
```

### 2.3 ES判定

- 任一规则 FAIL → 草稿标记为 `es_failed`，不进入第二层
- 全部通过 → 进入第二层

## 三、第二层：半ES语义校验

### 3.1 校验规则

| 规则ID | 规则名称 | 校验内容 | 模型 | 成本 |
|--------|---------|---------|------|------|
| SES-01 | 论点完整性 | must_land的每个论点是否有≥1个支撑段落 | Haiku | ~50 tokens |
| SES-02 | 结构连贯性 | 段落间逻辑是否衔接（无跳跃） | Haiku | ~100 tokens |
| SES-03 | 标题一致性 | 标题与正文内容是否匹配 | Haiku | ~50 tokens |
| SES-04 | 平台格式适配 | 是否符合目标平台的格式特征 | 规则+Haiku | ~50 tokens |
| SES-05 | 源体系忠实度 | 是否破坏 SourcePack 的主张、边界、禁忌；理论场景检查理论原点、核心因果链、结构化因果原语或核心原则 | 规则+强推理模型 | 可配置 |
| SES-06 | 断言证据风险 | 关键断言是否缺少证据、过期或自我引用 | 规则+小模型 | 低 |

### 3.2 半ES执行方式

```python
async def ses_check(draft, contract):
    results = []

    # SES-01: 论点完整性
    for ml in contract.structure.must_land:
        support = await check_argument_support(ml, draft.content.body)
        if not support.has_support:
            results.append(CheckResult("SES-01", "WARN", f"论点缺乏支撑: {ml}", suggestion=support.suggestion))

    # SES-02: 结构连贯性
    coherence = await check_coherence(draft.content.body)
    if coherence.score < 0.6:
        results.append(CheckResult("SES-02", "WARN", f"结构连贯性不足: { coherence.issues}"))

    # SES-03: 标题一致性
    consistency = await check_title_consistency(draft.content.title, draft.content.body)
    if consistency.score < 0.7:
        results.append(CheckResult("SES-03", "WARN", "标题与正文内容不匹配"))

    return results
```

### 3.3 半ES判定

- 半ES的失败不是硬FAIL，而是**WARN**（警告）
- 警告附加到草稿上，供第三层和人类参考
- 多个WARN可由人类决定是否返工
- `SES-05` 命中理论核心破坏时升级为 `FREEZE`，不得自动发布
- `SES-06` 命中高风险无证据断言时，生成 `EvidenceClaimPatch` 或进入 `draft_only`
- `SES-06` 必须包含自我认证门禁（SelfCertificationGate）：AI 生成断言、AI 摘要、AI 评分和 AI 解释不能互相证明并成为最终证据；若 `source_refs` 只包含 AI 输出，断言只能是 `ai_hypothesis / AI 假设` 或候选断言，必须补充外部来源、SourcePack、人类决策或平台事实后才能晋升

### 3.4 源体系忠实度门禁

源体系忠实度门禁防止多轮重写或跨平台转译破坏 SourcePack 的当前口径。理论场景中，它表现为理论忠实度门禁，防止理论内核被平庸化。

| 检查项 | 失败表现 | 默认动作 |
|--------|----------|----------|
| 理论原点 | 把理论概念误解为普通鸡汤或营销口号 | `FREEZE` |
| 因果链 | 删除关键因果关系，只保留结论 | `rework` |
| 核心原则 | 为追热点改写不可变原则 | `RED_LIGHT` |
| 显性程度 | 理论显性过高或过低，但内核未坏 | 黄灯建议调参 |

该门禁输出 `source_fidelity_score`；理论场景可同步写入 `CognitionTrace.theory_alignment`。

源体系忠实度优先做结构一致性检查，再做语义判断：

| 输入 | 检查方式 | 失败动作 |
|------|----------|----------|
| `causal_primitives` | 检查正文是否保留核心因果算子 | `rework` 或 `FREEZE` |
| `required_relations` | 检查关键阶段、属性、因果或序列关系是否出现 | `rework` |
| `forbidden_relations` | 检查是否生成禁止归因、禁止变迁或理论反向解释 | `FREEZE` |
| `allowed_translations` | 检查平台转译是否在允许范围内 | 黄灯或返工 |
| `non_negotiable_principles` | 检查不可变原则是否被运营目标覆盖 | `RED_LIGHT` |

结构校验输出：

```json
{
  "theory_fidelity": {
    "structure_consistency": "pass | warn | fail",
    "missing_required_relations": [],
    "violated_forbidden_relations": [],
    "translation_out_of_bounds": [],
    "semantic_review_required": false
  }
}
```

只有结构检查无法覆盖的隐性语义漂移，才交给强推理模型判定。

### 3.5 EvidenceClaim 抽取

进入 NES 评分前，系统抽取候选断言：

```json
{
  "claim_id": "ec_20260523_001",
```

- `edge_type=refutes` 的断言不得同时作为同一结论的 `supports`
- `propagation_policy=global_review` 只能进入影响分析，不能自动召回
- 作用范围缺失时，默认 `scope=strategy_unit`，不得默认全局

## 四、第三层：NES质量评估与策略矩阵

### 4.0 评分架构原则

**每个维度独立调用独立LLM，独立prompt、独立上下文、独立评分。** 质量比成本更重要。维度之间不能共用同一次LLM调用，避免评分互相污染——源体系忠实度（Source Fidelity）的评分不应被"标题写得好"所影响；在 theory profile 中才表现为理论准确性。

**评分与裁决分离**：评分层只产出各维度分数和证据，不决定动作。裁决层是独立的三层短路求值引擎。

### 4.1 Phase 1 评估维度（三组）

Phase 1 单平台、少账号，以下维度区分度不足，推迟到 Phase 3：平台适配（PLATFORM-01）、账号一致性（ACCOUNT-01）、运营目标达成（OP-01）。

| 维度ID | 维度名称 | 评估内容 | 分值范围 | 评分方式 |
|--------|---------|---------|---------|---------|
| SOURCE-01 | 源体系忠实度 | 是否保留 SourcePack 的主张、边界、禁忌和表达策略；理论场景下检查理论原点与核心因果链 | 0-100 | 结构化校验优先（S08 SourceMapping 规格比对），规则覆盖不了再独立LLM调用 |
| CONTENT-01 | 内容质量 | 观点力度 + 论证充分性 + 可读性 + 标题与开头 | 0-100 | 独立LLM调用 |
| RISK-01 | 风险校验 | 事实可靠性 + 断言证据完整度 + 反证敏感度 + 禁忌/敏感词残余 | 0-100 | ES/半ES规则引擎兜底，独立LLM只扫残余风险 |

推迟的维度保留在 `quality_profile` schema 中，权重默认为 0，Phase 3 扩展时启用。

### 4.2 各维度独立评分 Prompt

**源体系忠实度评分**：

```
你是源体系审稿人。请评估以下内容的源体系忠实度。若 mapping_kind=theory，请按理论忠实度执行；若为 brand/product/service_methodology/research/founder_voice，请按对应 SourcePack 边界执行。

源体系映射规格（S08 SourceMapping）：
  因果原语：{causal_primitives}
  必需关系：{required_relations}
  禁止关系：{forbidden_relations}
  不可变原则：{invariant_principles}

草稿内容：
标题：{title}
正文：{body}

请评估（0-100）：
1. 理论是否被误用、简化或扭曲
2. required_relations 是否全部保留
3. forbidden_relations 是否被触发
4. 重写/转译后是否保留理论原点与核心因果链
5. 理论显性程度是否符合策略单元要求（{theory_intervention_level}）

输出JSON：{"score": N, "evidence": "...", "violations": [...], "redline_triggered": bool}
```

**内容质量评分**：

```
你是内容质量审稿人。请评估以下内容的整体质量。

写作契约摘要：{contract_summary}
账号画像：{persona_summary}

草稿内容：
标题：{title}
正文：{body}

请评估（0-100）：
1. 观点是否清楚、有力量
2. 论据、案例和反驳是否充分
3. 可读性（概念密度、句子长度、节奏）是否适合目标读者
4. 标题吸引力和开头钩子

输出JSON：{"score": N, "evidence": "...", "weak_aspects": [...]}
```

**风险校验评分**：

```
你是风险审核人。请评估以下内容的风险等级。

已知禁忌：{taboos}
已知敏感词：{sensitive_words}
候选断言：{candidate_claims}

草稿内容：
标题：{title}
正文：{body}

请评估（0-100）：
1. 是否存在未核实的事实断言
2. 关键断言是否有来源、置信度和保鲜期
3. 是否存在可能推翻当前论证的反例（文中是否承认）
4. 是否存在ES/半ES未覆盖的残余敏感风险

输出JSON：{"score": N, "evidence": "...", "risk_items": [...], "falsification_risks": [...]}
```

### 4.3 NES判定

- 硬门禁或红线触发：直接 `FREEZE` / `RED_LIGHT`
- 底线分低于阈值：进入自动重写
- 目标分低于阈值：按策略单元配置重写、降级、暂存或发布
- 分数达标：按策略单元 `on_pass` 执行，可能自动发布、抽检或暂存
- 指标长期偏离：生成黄灯建议，进入进化控制台
- 预测与反馈长期偏离：生成 `CognitiveDisturbanceEvent(type=prediction_miss)`；同一维度连续3次超阈值时生成 `StrategyChangeProposal`
- 内部质量高但外部表现异常低：优先生成 `CognitiveDisturbanceEvent(type=algorithm_noise_overload, light=gray)`，不自动降权或判定理论失败
- 断言被反证挑战：更新 `EvidenceClaim.falsification_status` 并触发召回影响分析

## 五、第四层：策略裁决与人工抽检

### 5.1 三层短路裁决引擎

裁决分三层短路求值，任何一层拦截成功则跳过后续：

**第一层：维度硬底线（veto_rules）**

任意维度低于策略单元配置的 `veto_threshold`，直接强制动作，不看总分：

```json
{
  "veto_rules": [
    {"dimension": "SOURCE-01", "below": 50, "action": "freeze", "reason": "源体系忠实度有硬伤"},
    {"dimension": "RISK-01", "below": 40, "action": "rewrite", "reason": "风险过高"}
  ]
}
```

知乎理论号配 `SOURCE-01 < 50 → freeze`；小红书卡片可降低 Source Fidelity 权重，配 `RISK-01 < 30 → rewrite`。策略单元级可配置。

**第二层：加权总分裁决**

```python
def decide_quality_action(report, strategy):
    # 第一层：veto 短路
    for rule in strategy.veto_rules:
        if report.get_score(rule.dimension) < rule.below:
            return rule.action

    # 第二层：加权总分
    total = sum(w * report.get_score(d) for d, w in strategy.weights.items())

    if report.redline_triggered:
        return "freeze_and_downgrade"
    if report.hard_gate_failed:
        return "rewrite_or_freeze"
    if total < strategy.baseline_threshold:
        return "rewrite"
    if total < strategy.target_threshold:
        return strategy.on_target_underperform

    # 第三层：条件规则
    for cond in strategy.conditional_rules:
        if cond.matches(report):
            return cond.action

    if should_sample(report, strategy.sampling_policy):
        return "sample_review"
    return strategy.on_pass
```

**第三层：条件规则（conditional_rules）**

维度组合的交互毒性，编码为策略单元级可配置规则：

```json
{
  "conditional_rules": [
    {
      "when": "SOURCE-01 < 60 AND CONTENT-01 > 80",
      "action": "rewrite",
      "hint": "内容好看但理论有硬伤，定向重写理论转译",
      "scope": "theory_section"
    },
    {
      "when": "RISK-01 < 60 AND SOURCE-01 > 80",
      "action": "sample_review",
      "hint": "理论扎实但风险可疑，人类判断是否需要撤回断言"
    }
  ]
}
```

执行顺序：`veto_rules → 总分 → conditional_rules → 抽检策略 → 最终动作`。
全部配置存储在 `quality_profile` 中，不同策略单元可配不同规则，不硬编码。

### 5.2 动作集合

| 动作 | 后果 |
|------|------|
| `auto_publish` | 草稿封存后进入发布引擎自动发布 |
| `sample_review` | 进入人工抽检，不阻塞其他策略单元 |
| `rewrite` | 回到写作流水线自动重写 |
| `store_draft` | 存入草稿池 |
| `downgrade` | 降级为低风险内容形态 |
| `wait_human` | 等待人类处理 |
| `abandon` | 废弃任务 |
| `freeze_and_downgrade` | 冻结任务并降低策略单元自治等级 |

人工抽检、人工覆盖和红灯处理必须生成 `ContentDecision` 或 `StrategyChangeEvent`，而不是只更新 UI 状态：

```json
{
  "decision_id": "dec_review_20260522_001",
  "decision_action": "accept | reject | request_changes | lock | unlock | downgrade_strategy",
  "accept_level": "low_risk | provisional | release | accountable",
  "target_objects": ["draft_20260522_001", "ctr_20260522_001"],
  "rationale": "文章符合账号声音，SES-02警告可人工接受",
  "reviewer": "human:sub_owner",
  "status": "accepted",
  "evidence_refs": ["ev_sample_review_001"]
}
```

抽检分层：

| 层级 | 触发条件 | 时间目标 | 输出 |
|------|---------|---------|------|
| Light | 随机抽检、低风险达标稿 | 3分钟 | accept / request_changes |
| Standard | 有半ES警告、重写次数偏高、黄灯建议 | 10分钟 | ContentDecision + StrategyChangeProposal |
| Deep | 红灯、争议话题、理论红线、发布后可能召回 | 20分钟 | accountable 决策 + 降权/召回/完整证据包 |

## 六、缺陷三分法

### 6.1 三种缺陷类型

| 类型 | 含义 | 处理方式 | 示例 |
|------|------|---------|------|
| **毁灭性** | 必须修复的缺陷 | 自动FAIL，强制返工 | 敏感词、事实错误、违规内容、抄袭 |
| **生产性** | 可能是好的偏差 | 自动保护，标记为特色 | 独特的行文节奏、出人意料的论点切入、非常规标题 |
| **中性** | 不确定好坏的偏差 | 标记，攒批给人类裁决 | 偏离了建议结构但效果不确定 |

在证据化认知语境下，缺陷分类还要考虑信息条件：

| 情况 | 分类倾向 |
|------|----------|
| 信息充足仍拒绝修正事实或理论错误 | 毁灭性 |
| 信息不足时提出新隐喻、新解释、新假设 | 生产性 |
| 信息不足且风险高，但可能有价值 | 中性，进入 `draft_only` 或人类裁决 |
| AI 把自身输出当证据 | 毁灭性，必须降级为假设或删除 |

### 6.2 缺陷分类规则

```python
def classify_defect(check_result, draft, contract):
    # 毁灭性：命中敏感词、事实错误、违规
    if check_result.rule_id in ["ES-04", "ES-05"]:
        return "destructive"
    if check_result.rule_id == "ES-03" and check_result.severity == "critical":
        return "destructive"

    # 生产性：偏离建议结构但文字质量高
    if check_result.rule_id == "SES-02":
        if draft.word_count >= contract.word_count.min:
            return "productive"  # 结构不同但内容充分，可能是好的偏差

    # 默认：中性
    return "neutral"
```

## 七、返工闭环

### 7.1 返工流程

```
质量门禁失败（任一层）
    │
    ▼
收集失败原因
    │
    ▼
写入任务的 failure_context
    │
    ▼
rework_count += 1
    │
    ▼
rework_count > strategy.max_rewrite ?
    ├── 是 → 按策略 fallback：等待人类 / 暂存 / 降级 / 发布带风险标记 / 放弃
    └── 否 → 回到写作引擎（契约版本+1，注入S06返工反馈）
```

### 7.2 返工上下文注入

返工时，S06 Slot 注入以下内容：

```
[返工反馈 - 第{N}次返工]
失败原因：
- {failure_context}

具体问题：
- {check_result_details}

修改建议：
- {suggestions}
```

### 7.3 返工次数限制

| 次数 | 处理 |
|------|------|
| 1-3次 | 自动返工，注入S06 |
| >策略上限 | 停止自动返工，按策略 fallback；若策略要求人类则标记 `human_override` |
