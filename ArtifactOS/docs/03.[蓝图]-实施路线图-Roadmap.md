# 03 实施路线图

> ArtifactOS 的分阶段实施计划
> 核心原则：平台已有简单内容生成能力，后续重点不是证明 AI 能写草稿，而是建设源体系驱动、证据化、低人类打扰、可自进化的产出物操作系统；理论驱动是一元论 SourcePack 的首个特化场景。

---

## 一、路线图设计哲学

### 1.1 进化优先原则

ArtifactOS 的长期目标不是单纯 `AL4` 高自治内容行动，而是知识进化：

```text
自动观察现实扰动
-> 自动识别关键属性
-> 自动生成源体系映射和解释假设
-> 自动拆解 EvidenceClaim 并检查反证
-> 自动生成内容、研究或策略行动
-> 自动评分、重写、发布或暂存
-> 自动回收场域反馈
-> 自动提出策略、知识或源体系映射演进建议
```

人类不是每篇内容的固定审核节点，而是抽检者、校准者、降权者、策略裁决者和理论核心裁决者。

### 1.2 策略单元原则

所有自治能力都绑定策略单元：

```text
StrategyUnit = 账号 + 平台 + 内容类型 + 理论介入方式
```

每个策略单元独立配置：

```text
自治等级
评分矩阵
理论介入度
重写次数
发布权限
抽检率
降权规则
实验策略
```

### 1.3 验收标准

验收不再是“能否写出一篇好文章”，而是：

```text
合格质量下的知识进化率
```

核心指标：

- 自动通过率
- 自动重写成功率
- 人类介入率
- 人类平均处理时间
- 草稿积压率
- 红线触发率
- 策略黄灯有效率
- 降权后恢复率
- 发布后召回率
- CognitionTrace 覆盖率
- EvidenceClaim 可验证率
- 预测反馈校准度
- 反馈晋升为知识资产的成功率
- 理论修正提案准确率

## 一A、Phase × 产品层级（Product Level）交叉矩阵

Phase 按能力维度划分（从单策略到多策略到研究型），产品层级（Product Level, PL）按认知深度划分（从工具到操作系统）。两者交叉关系如下：

| Phase | 主要产品层级 | 覆盖的产品层级 | 说明 |
|-------|------------|--------------|------|
| Phase 0 | — | — | 文档对齐，不涉及产品能力 |
| Phase 1 | **PL2** | PL2 主体 + PL3 预埋 | 搭建高自治内容行动流水线（PL2），同时预埋 CognitionTrace / EvidenceClaim / BoundaryDecision 结构（PL3 预埋） |
| Phase 2 | **PL3** | PL3 完成 + PL4 预埋 | 完成证据化认知骨架（PL3），预埋研究问题和假设契约的结构（PL4 预埋） |
| Phase 3 | **PL2-PL3** | PL2-PL3 横向扩展 | 多账号/多平台/多内容类型，不提升认知深度，但扩大 PL2-PL3 能力的覆盖面 |
| Phase 4 | **PL3-PL4** | PL3 深化 + PL4 入场 | 数据回收驱动策略优化（PL3 深化），反馈晋升和分层共享学习开始具备 PL4 特征 |
| Phase 5 | **PL4** | PL4 完成 | 研究型知识进化系统完整实现 |
| Phase 6 | **PL5** | PL5 | 个人/组织知识进化 OS |

关键对齐规则：

1. **每个 Phase 的验收标准必须标注它覆盖的 PL 级别**——"做到什么程度算完成"由 PL 级别决定
2. **PL3 预埋不等于 PL3 完成**——Phase 1 预埋的字段和表结构在 Phase 2 才填充完整逻辑
3. **横向扩展不提升深度**——Phase 3 是 PL2-PL3 的横向扩展，不引入 PL4 能力
4. **PL4 的入场信号**——当系统开始自动提出研究问题和假设契约时，正式进入 PL4

## 一B、开发约束

本路线图遵循以下开发约束（详见 01.[蓝图]-产品蓝图-Blueprint §0.6a）：

| 约束 | 对路线图的影响 |
|------|--------------|
| 时间不限 | 每个 Phase 做到质量达标再推进，不设死线 |
| 老系统兜底 | 新系统开发期间老系统持续运行，Phase 交接不需要功能等价 |
| 不做 MVP | Phase 只表示开发进度和依赖顺序，不是功能裁剪、赶时间上线或降低架构标准 |
| 第一接管面 | 首次真实接管限定在一个明确 SourcePack、一个主要平台和少数成熟策略单元，要求完整闭环、可审计、可回滚 |
| 能力闭合度推进 | 进度按规格闭合、数据闭合、流程闭合、人机闭合、影子闭合、接管闭合、退出闭合判断 |
| LegacyStage 绑定 | 某个接管面进入 `LegacyStage L3` 才表示有限真实接管，进入 `LegacyStage L4` 才表示该接管面的主系统 |
| 最优设计优先 | 预埋字段不做删减，证据化认知骨架不做降级 |
| Phase 内部分层交付 | Phase 1 内部按四层逐步交付（见 §四A） |
| 授权后自动推进 | 年会、半年会、季度会、月会、周会和日晨会确认对应案（Case）与授权范围后自动推进；批量总编台（Artifact Review Desk）支持批量批准、抽检和冻结；拉人强度可配 |
| 完整能力最终交付 | Phase 划分是交付顺序，不是功能取舍 |

```text
输入热点或理论命题

### 4.3 验收标准

1. 至少一个策略单元可从热点或理论命题自动生成文章候选
2. 系统能自动判断 `write_now / store_candidate / experiment / do_not_write`
3. 草稿能按质量矩阵评分，并按低分维度自动重写
4. 重写达到上限后，能按策略执行 `wait_human / store_draft / downgrade / abandon`
5. 达标内容能在策略授权下自动发布到知乎，或按策略进入抽检/暂存
6. 每次自动生成、重写、发布都有证据记录
7. 人类可以对策略单元降权或暂停自动发布
8. 人类反馈能标注作用范围，并至少写入本文级或策略单元级资产
9. 红线触发时自动冻结任务并降低策略单元自治等级
10. 每次写/不写/发布/冻结都生成最小 `CognitionTrace`
11. 关键事实和理论推导至少生成候选 `EvidenceClaim`
12. `EvidenceClaim` 至少记录 `depends_on_claim_ids / edge_type / scope / propagation_policy`，并禁止循环依赖
13. 高理论介入任务的 S08 必须包含结构化因果原语，质量门禁能检查 required/forbidden relations
14. 连续 3 次预测偏离能生成 `StrategyChangeProposal`，并在控制台亮黄灯或橙灯
15. 内部质量高但外部表现异常低时能进入灰灯避险，不自动降权或判定理论失败

### 4A.1 七级能力闭合度（Phase 1-3 全局进度锚点）

Phase 1 内部四层只覆盖数据结构到反馈进化。产品蓝图 §0.6 定义的能力闭合度模型中还有三个高阶闭合度，需要跨 Phase 1/2/3 达成：

| 闭合度 | 含义 | 对应 Phase | 验收锚点 |
|---|---|---|---|
| 规格闭合 | 主链对象、状态、边界、硬约束文档无冲突，表结构完整预埋 | Phase 1 第一层 | 所有核心表 DDL 完成，状态机白名单通过 CK 校验 |

每层完成后进入下一层；上一层的问题可以在下一层开发中修正，但不得跳层。

### 7.3 理论成长子阶段（PL3→PL4 过渡）

Phase 4 内部按能力闭环分三层渐进实现理论成长：

**Phase 4.1 — 理论空缺检测**
- 扫描 EvidenceClaim 图谱中 `falsification_status=untested` 且 `claim_type=theory_inference` 的断言，标记为"待验证理论推导"
- `CognitiveDisturbanceEvent` 新增 `disturbance_type=theory_gap`：当 `calibration_delta` 连续超标且 `theory_fit` 评分高位但实际效果偏离时，识别为"理论覆盖不了此类现象"
- 自动生成 `ResearchQuestion` 候选，人类判断研究价值

**Phase 4.2 — 保护带生长（二级定理）**
- 因果原语池定期聚类分析：找出被映射到不同话题但共享同一段因果原语链的现象集合
- 高频验证的因果原语从"推导结果"升级为 `TheoremCandidate`（系统提议、人类确认、进入理论本体）
- 符合拉卡托斯研究纲领模型：硬核不动，保护带在生长

**Phase 4.3 — 假设检验闭环**
- `ResearchQuestion` → `HypothesisContract`（含 `falsification_conditions` + `required_evidence_types`）
- `FalsificationGate` 自动注册反例监控：后续任何 EvidenceClaim 与假设冲突，自动触发假设置信度下调
- 验证/推翻 → `TheoryRevisionProposal` → 人类确认 → 理论体系更新

**新增总量极小**：一个枚举值（`theory_gap`）+ 因果原语池聚类批处理函数 + 三个已有对象的生命周期实现。核心管道（扰动检测、灯号协商、scope晋升、人类裁决）全部复用。

## 十、风险与应对

| 风险 | 应对 |
|------|------|
| 自动发布失控 | 自动发布只按策略单元授权；红线立即降权/暂停/召回 |
| 理论被热点带偏 | 理论核心原则不可自动修改，运营数据只能影响表达 |
| 策略矩阵过复杂 | 系统提供默认值，首期只启用一个策略单元 |
| 黄灯过多 | 黄灯分级，低优先级合并为周期报告 |
| ClaimGraph 传播雪崩 | EvidenceClaim 默认 DAG，传播隔离在 strategy_unit + time_window，召回先生成影响分析 |
| 源体系忠实度变成主观评分 | S08 必须结构化为主张、边界、禁忌和场景 profile；理论 profile 先做因果原语、必需关系和禁止关系校验 |
| 平台算法绑架策略 | 内部质量高但外部表现异常低时进入灰灯，延长观察，不直接降权 |
| 人类无时间处理 | fallback 支持存草稿、降级、放弃或关闭介入 |
| 微信通道不稳定 | 微信只作为工作汇报接口；失败写入 DeliveryAttempt，并回退到 Amy 总控台 |
| token 过期导致消息丢失 | WeixinContextToken 显式记录 captured_at / expires_at / status，过期进入 rebind_required |
| 微信误当审批源 | 微信回复必须转成 ReplyCommand 和正式决策对象，投递成功不等于批准 |
| 通知通道过早发散 | Phase 1 不做邮件、桌面通知或 Webhook，只做微信摘要入口和 ArtifactOS 详情页 |
| 当天赶稿当天发导致质量不稳 | 默认前夜审明日特别文件，当天发布只走 SameDayException |
| 自治权限扩张过快 | 成熟度绑定 StrategyUnit + Case Constraint，Amy 可降级/冻结但不能自升 StrategyUnitMaturity M3/M4 |
| 策略污染 | 反馈必须标注作用范围，主策略/实验策略隔离 |
| 状态漂移 | 策略状态、任务状态、规格状态分轴记录，事件不可变 |
| 召回困难 | 发布物必须记录 seal、evidence、strategy_unit_id 和依赖关系 |
| 自我喂养幻觉 | AI 输出不能作为自身最终证据，EvidenceClaim 必须区分外部证据、人工确认和 AI 假设 |
| 理论演进失控 | 理论核心原则不可静默修改，TheoryRevisionProposal 必须人工确认 |

## 十A、渐进交付工程实践

### 10A.1 交付子阶段

Phase 1 内部按能力闭环分三步交付，不设工期，每步做到质量达标再推进：

**Phase 1A — 最小闭环（选题→写→影子运行）**

核心模块：简化写作契约 + 命令行选题入口 + 写作流水线（delegate模式） + ES硬门禁 + 知乎发布模拟对接 + Amy 工作台最小骨架 + 前夜审阅节奏 + Amy 微信工作汇报通道技术尖刺 + 7 天影子运行。
数据层：按完整模型建最小表族（Case / MeetingProtocol / MeetingRecord / CaseSnapshot / OpportunityCandidate / PlanChangeProposal / Studio / SubStudio / Artifact / PublicationPackage / contracts / drafts / publications），允许暂时只有一条默认案、一个默认会议协议和一个默认片场。
装载层：建 SourceInventory / SourceReadinessReport / SourceConflictReport / SourcePackManifest / SourcePackSnapshot / SourcePackLoadingDecision，至少支持 `theory_system` 与 `founder_voice` 两类模板。
交互层：建 WorkCard / PreparedActionPanel / PreparedActionOption / HumanReviewChoice / DailyCalibrationReview / CalibrationExample 最小表；固定 `1-8` 常用选项、`9` 重新生成、`0` 我来输入。
通知层：建 NotificationChannel / AmyWeixinChannel / NotificationPolicy / NotificationEvent / WorkReport / WeixinContextToken / DeliveryAttempt / ReplyCommand / DailyReport / DailyReportEntryCard 最小表；验证二维码绑定、首次回复、延迟发送、日报入口、失败留痕和回退 Amy 总控台。
影子运行层：建 ShadowRun / ShadowRunDay / ShadowRunObservation 最小表；旧系统继续真实发布，ArtifactOS 只生成、门禁、前夜审阅、模拟执行和偏差记录。
迁移层：建 LegacyImportBatch / LegacyExternalRef / LegacySnapshot；不修改旧系统，只读导入和对照。
交接层：建 AttractionHandoff 最小对象；只记录公开共鸣、误读和高意向信号，外部承接由其他系统处理。
暂不实现：选题漏斗自动化、半ES/NES、素材库、自动重写、RSC/CTF复杂逻辑、复杂片场批量 UI、国外媒体自动研究、微信完整媒体投递。
验收标准：能完成"人类选题→自动生成→硬规则检查→前夜审明日候选→工作卡确认→旧系统真实发布 + ArtifactOS 模拟执行→ShadowRunObservation 记录偏差→Amy 通过微信汇报结果或失败"的完整流程。

**Phase 1B — 质量闭环 + 素材库**

新增：结构化素材库 + 半ES语义门禁 + NES三维度独立评分 + 三层裁决引擎 + 自动重写闭环 + 上下文组装引擎 + 三轴状态机。
验收标准：系统可自动判定质量、自动重写、自动发布（L3策略单元）。

**Phase 1C — 认知 + 进化**

新增：选题漏斗 + RSC/CTF前置层 + 证据化认知骨架 + 知识进化控制台（命令行版） + 会议治理命令行入口 + 片场制运行 + 多账号 + 数据回收闭环。
验收标准：系统具备完整的L2高自治能力，CognitionTrace和EvidenceClaim最小骨架可用。

### 10A.2 防推翻原则：1A多做10%避免后续重做100%

1. **数据表按完整规格建**，1A不用的字段允许NULL，枚举按完整集合声明（与§一B"最优设计优先"原则一致）
2. **状态机转换表数据驱动**（YAML/JSON规则表），不硬编码if-else，1A即使只实现20条转换，引擎也读取完整规则表
3. **平台适配器从1A就抽象为Interface/Protocol**，哪怕只实现知乎一个适配器，注册表和格式转换接口必须到位
4. **LLM调用层按完整签名设计** `(task, strategy_unit, contract, context_pack) -> GenerationResult`，返回值包含EvidenceClaim和CognitionTrace（1A可返回空列表）

## 十B、设计文档治理

### 10B.1 决策变更记录

每个文档头部维护决策变更记录表：

```

"替代了什么"是防止矛盾扩散的锚点。矛盾内容用删除线标注+链接到新决策记录，不删除旧内容。

每个章节末尾标注实施状态：

```

```

文档始终描述完整设计，标记清楚哪段已落地、哪段还是spec。

### 10B.3 代码反向引用

每个实现模块的注释头写明设计文档来源：

```
// 设计文档: 07_质量门禁 §5.1 | 决策ID: 0523-07s51
```

每个Phase结束时的review，第一项议程是"决策表状态 vs 代码实际"对账。

## 十C、工程开工落点：共享数据库与第一接管面

ArtifactOS 不使用独立物理数据库。ArtifactOS 与后续发布系统共用 PostgreSQL 业务库，通过 schema/table 边界隔离。

| 环境 | Database | Schema |
|---|---|---|
| 开发/正式业务库 | `artifactos` | `artifactos` / `media_publish` / `legacy_bridge` |
| ArtifactOS 独立测试库 | `artifactos_test` | `artifactos` / `media_publish` / `legacy_bridge` |

Phase 1A 默认第一接管面：

```yaml
first_operational_surface:
  source_pack: 一元论
  source_root: D:\_Progs\一元论
  platform: zhihu
  run_mode: shadow
  legacy_stage: L0
  real_publish_allowed: false
  media_publish_mode: manual-review
  audience_stage_scope: [S1, S2, S3]
  theory_visibility: medium
  database:
    main: artifactos
    test: artifactos_test
    schema: artifactos
```

Phase 1A 开工顺序：先在 ArtifactOS 独立测试库 `artifactos_test` 验证 schema 与触发器，再在正式业务库 `artifactos` 建立 `artifactos` / `media_publish` / `legacy_bridge` schema；先生成一元论 SourceInventoryCandidate，不自动晋升 SPL3；发布路径只允许 `manual-review` 或 `simulation_only`。

## 十C、测试策略

### 10C.1 三层分离

**确定性层（单元测试，100%通过率）**：
- ES规则引擎（ES-01~06）：字数、格式、must_land关键词、禁忌词、敏感词
- 状态机转换：枚举合法/非法转换对，表驱动测试
- 策略裁决三层短路逻辑：纯函数，mock输入断言输出
- 结构门禁：spec_snapshot_id存在性、stale_status判断
- 上下文组装版本冻结：快照冻结后拒绝版本变化
- EvidenceClaim DAG校验：循环依赖检测

**不确定性层（eval测试）**：
- 维护golden dataset（20-50组），每组包含完整ContentContextPack + 人工确认的高质量草稿
- 每次改代码后用低随机性重跑golden dataset，用独立LLM做盲比评分
- 退化容忍区间：评分下降>5分标红，1-5分标黄
- 覆盖模块：半ES语义校验、NES三维度评分、自动重写循环

**端到端层（场景测试）**：
- 选3-5个代表性场景（知乎理论长文、小红书卡片、探索模式+交互修改）
- 从选题到定稿走完整流水线，验证轴间协调和策略裁决端到端动作链
- 人工把关

### 10C.2 AI自评校准

AI自评是信号不是数据，需要交叉验证：
- EvidenceClaim置信度映射到离散档位（高/中/低），不做精确数值使用
- NES评分只取序数意义，差20分有意义差3分无意义
- 置信度>90但无外部来源支撑 → 强制标记"待验证"

人类抽检校准闭环（不确定性采样）：抽AI置信度0.5-0.7区间、三维度分数互相矛盾、新策略前5篇全检的样本。校准回灌用prompt级注入（`calibration_offset`写入策略单元），不训练模型不改权重。

## 十D、前沿研究方向

以下三个方向是 PL3-PL5 能力深入所需的额外知识输入，需要在开发过程中持续关注和学习：

### 10D.1 知识图谱构建方法论（支撑 PL3-PL4）

当前 EvidenceClaim DAG 是简单的父子依赖关系，可能不足以支持 PL4 的跨断言推理。需要研究：

- **GoAI**（arXiv 2503.08549）：学术知识图谱支持研究想法生成的具体方法，关注其如何从结构化知识中推导新的研究问题
- **AutoSchemaKG**（arXiv 2505.23628）：无预定义 schema 的自动知识图谱构建——因果原语池可能需要类似的无 schema 演化能力
- **PhilKG**（OpenReview）：从斯坦福哲学百科构建知识图谱的 LLM 方法——最接近我们"从理论文本构建结构化知识"的需求
- **待研究问题**：EvidenceClaim DAG 是否应升级为完整的知识图谱？如果是，用什么图谱引擎（Neo4j / 自建 / 嵌入式）？

### 10D.2 假设生成与检验方法论（支撑 PL4）

当前 HypothesisContract 的 `falsification_conditions` 是文本描述，需要结构化为可自动检验的条件。需要研究：

- **AI Scientist-v2**（Sakana AI, arXiv 2504.08066）：agentic tree search 方法——用树搜索探索假设空间，已实现端到端自动科研（假设→实验→论文）
- **Nature 2025 AI for Science**（Nature d42473-025-00161-3）：数据驱动+模型驱动结合的自动假设验证方法
- **待研究问题**：
  - 假设空间的搜索策略（树搜索 vs 聚类 vs 随机探索）怎么选？
  - `falsification_conditions` 如何从文本描述结构化为可自动检验的规则？
  - 人文社科的"检验"与自然科学的"实验"有何不同？怎么定义"反证"？

### 10D.3 认识论纪律的形式化（支撑 PL2-PL5）

系统口头引用了拉卡托斯研究纲领和波普尔证伪主义，但还没有形式化。需要建立：

- 理论核心/保护带/辅助假设的层级关系的形式定义
- 证伪条件的形式定义（什么算"反证"，什么算"噪音"）
- 进步/退化研究纲领的判定标准（什么时候应该坚持理论、什么时候应该修正）
- **输出物**：一份独立的"认识论纪律"文档，作为系统设计的形式化基础

### 10D.4 对标系统持续跟踪

| 系统/项目 | 方向 | 与我们的关系 | 关注重点 |
|----------|------|------------|---------|
| AI Scientist-v2 (Sakana) | 端到端自动科研 | 我们 PL4 的自然科学对标 | 假设生成和检验的方法论 |
| GoAI (HKUST) | 学术知识图谱+研究想法生成 | 我们 PL3-PL4 的知识图谱对标 | 从结构化知识推导新研究问题 |
| PhilKG (OpenReview) | 哲学知识图谱 | 最接近我们的理论体系结构化 | LLM 从理论文本构建知识图谱的方法 |
| AutoSchemaKG | 无 schema 知识图谱 | 我们因果原语池演化的参考 | 动态 schema 演化的工程实现 |
| Obsidian/Heptabase | Second Brain 工具 | 我们 PL5 的竞品（但无闭环进化） | 知识连接和可视化的 UX 模式 |
