# 24 数据库模型与治理规格

> 文档性质：数据库参考规格（Database Reference）+ 迁移蓝图（Migration Blueprint）
> 适用范围：ArtifactOS Phase 1 到 Phase 3 的 PostgreSQL 数据模型

---

## 一、设计目标

本规格把前面的产品设计落成数据库层可执行的结构。它不是一次性实现清单，而是数据库边界的长期协议：

```text
源体系（SourcePack）
  -> 案（Case）
  -> 会议（Meeting）
  -> 片场（Studio）
  -> 子片场（SubStudio）
  -> 产出物（Artifact）
  -> 发布包（PublicationPackage）
  -> 信号（Signal）
  -> 计划变更 / 反哺候选
```

目标不是把所有字段立刻用起来，而是在 Phase 1 建表时就不留下结构债。

### 1.1 核心原则

1. **统一事实源（Single Source of Truth）**：PostgreSQL `artifactos` schema 是运行事实源，Markdown/HTML/界面只是审阅面。
2. **案表统一（Unified Case Table）**：物理表使用 `case_record`，逻辑上通过 `case_type` 表达 `YearCase / HalfYearCase / QuarterCase / MonthCase / WeekCase / DayCase / DaySubCase`。
3. **快照不可变（Immutable Snapshot）**：会议提交后生成 `CaseSnapshot`，下层案只能引用已提交快照，不能引用会议草案。
4. **计划变更显式化（Explicit Plan Change）**：任何正式计划池的新增、减少、调整，都必须经过 `PlanChangeProposal` 和 `PlanChangeLog`。
5. **事件账本追加写（Append-only Ledger）**：`EventLedger` 只追加，不修改，不删除；修正通过新事件表达。
6. **JSONB 用于弹性，不用于逃避约束**：结构稳定字段必须建列；层级内部差异、AI 输出、证据包可用 `jsonb`。
7. **多租户预埋（Tenant-ready）**：Phase 1 单用户运行，但所有核心表预埋 `tenant_id`、`created_by`、`updated_by`。
8. **数据库承担治理（Database-enforced Governance）**：能用约束、索引、触发器保证的规则，不依赖应用层自觉。
9. **产出链优先（Source-to-Artifact First）**：数据库不为通用 AI 管理平台建模；能力、授权、介入、门禁和事件账本都必须服务于 `SourcePack -> Case -> Studio -> Artifact -> PublicationPackage -> SignalEvent` 主链。

### 1.2 规格边界

本文件完整定义案场治理、会议、授权代理、片场产出、发布信号和遗忘后台所需的核心运行表。以下模块只定义引用边界，不在此重复其内部全文模型：

### 2.1.1 运行时命令边界

ArtifactOS Desk / Agent / Engine 允许直接连接 PostgreSQL，但跨进程协作必须经过 `artifactos.runtime_command`：

```text
Desk / Agent / Amy
  -> artifactos.runtime_command
  -> Engine claim with lease
  -> artifactos.runtime_command_event
  -> Engine result
```

PublishingRuntime 的浏览器执行命令继续使用 `media_publish.runtime_command`。只有 Engine 可以在 L3 发布门禁通过后写入该表；Desk、Agent、Amy 不直接写发布执行命令。

Agent 使用 PostgreSQL `LISTEN/NOTIFY` channel `artifactos_runtime_command` 接收实时通知，并使用 polling 兜底。Engine 默认 command lease 为 5 分钟，默认无 running / pending command 10 分钟后退出。Engine heartbeat 建议 15 秒，Desk / Agent heartbeat 建议 30 秒。

正式 DDL 见：

```text
db/migrations/028_artifactos_runtime_command.sql
```

## 四、案模型

### 4.1 为什么采用统一案表

年案、半年案、季案、月案、周案、日案、今日子案在治理上共享同一组属性：

```text
目标（Goal）
边界（Boundary）
授权（Delegation）
介入（Intervention）
父子关系（Parent-Child）
会议来源（Meeting Source）
快照（Snapshot）
事件（Event）
```

如果物理上建七套表，后续每增加一个治理字段都要改七处，容易制造结构债。因此采用：

```text
case_record.case_type = year / half_year / quarter / month / week / day / day_sub
```

逻辑上仍可创建视图：

```sql
create view year_case as
select * from artifactos.case_record where case_type = 'year';
```

### 4.2 `case_record`

```sql
create table artifactos.case_record (
  id uuid primary key default gen_random_uuid(),
  tenant_id uuid not null,

  case_code text not null,
  case_type text not null check (case_type in (
    'year','half_year','quarter','month','week','day','day_sub'
  )),
  parent_case_id uuid null references artifactos.case_record(id),
  root_case_id uuid null references artifactos.case_record(id),

  title text not null,
  status text not null check (status in (
    'planned','active','reviewing','closed','frozen','archived'
  )),

  planning_nature text not null check (planning_nature in (
    'strategic_execution',
    'strategic_adjustment',
    'strategic_arrangement',
    'strategic_landing',
    'tactical_arrangement',
    'tactical_execution'
  )),

  time_start date null,
  time_end date null,
  source_pack_snapshot_id uuid null,
  delegation_policy_id uuid null,
  intervention_policy_id uuid null,

  goal_summary text null,
  boundary_summary text null,
  artifact_capacity jsonb not null default '{}'::jsonb,
  plan_pool jsonb not null default '[]'::jsonb,
  case_payload jsonb not null default '{}'::jsonb,

  current_snapshot_id uuid null,
  created_by uuid not null,
  updated_by uuid not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  metadata jsonb not null default '{}'::jsonb,

  unique (tenant_id, case_code)
);
```

|------|------|------|
| `case_code` | 案编号 | 人类可读编号，如 `yearcase_2026` |
| `case_type` | 案类型 | 区分年/半年/季/月/周/日/今日子案 |
| `parent_case_id` | 父案 | 下层案必须继承上层案边界 |
| `root_case_id` | 根案 | 便于快速查询同一年案下所有对象 |
| `planning_nature` | 计划性质 | 固化战略/战术层级 |
| `plan_pool` | 计划池 | 当前案内正式计划集合，修改必须受控 |
| `case_payload` | 案内容 | 记录层级特有结构，如年度北极星、月度灯塔、周主题池 |

### 4.3 父子层级约束

数据库触发器必须禁止错误层级：

| 父案（ParentCase） | 允许子案（ChildCase） |
|--------------------|----------------------|
| YearCase | HalfYearCase / QuarterCase |
| HalfYearCase | QuarterCase |
| QuarterCase | MonthCase |
| MonthCase | WeekCase |
| WeekCase | DayCase |
| DayCase | DaySubCase |

规则：

```text
DaySubCase 不能直接挂到 WeekCase。
MonthCase 不能直接挂到 YearCase。
任意下层案不能跨 root_case_id。
```

| `tomorrow_publish_batch` | 明日待发布批次（TomorrowPublishBatch） | `next_day_plan_id / target_date / status / platform_scope / batch_summary` |
| `tomorrow_publish_candidate` | 明日待发布候选（TomorrowPublishCandidate） | `batch_id / artifact_id / planned_publication_window / evening_review_status / overnight_revision_status / morning_confirmation_status` |
| `same_day_exception_proposal` | 当天例外发布提案（SameDayExceptionProposal） | `source_signal_id / opportunity_reason / window_expires_at / status / risk_level / human_override` |
| `fast_gate_result` | 快速门禁结果（FastGateResult） | `same_day_exception_proposal_id / redline_status / fact_risk_status / source_boundary_status / platform_fit_status / package_status` |
| `strategy_unit_maturity` | 策略单元成熟度（StrategyUnitMaturity） | `strategy_unit_id / case_constraint_id / maturity_level / status / evidence_refs` |

### 5D.2 建模约束

- `NextDayPlan` 不是正式 `DayCase`，只能在确认或授权后转成次日 `DayCase`。
- `TomorrowPublishCandidate` 默认前夜审阅，次日早晨只做轻确认。
- `SameDayExceptionProposal` 不能跳过 `FastGateResult`。
- `StrategyUnitMaturity` 绑定 `StrategyUnit + Case Constraint`，不能全局泛化。
- Amy 可以自动降级或冻结成熟度，但不能自升到 StrategyUnitMaturity M3/M4。
- `ShadowRun` 不接管真实发布，只记录模拟调度和偏差。
- `ShadowRunObservation` 是影子运行偏差事实层；不能只把旧系统对照写入自然语言日报。
- 旧系统引用使用 `legacy_ref` 保存路径、报告 ID、发布 URL、截图或旧任务编号；不得假装外部旧系统对象已经属于 ArtifactOS 事实源。

硬约束：

- `InvestmentAssessmentRun / 投入评估运行` 只能产出评估结论和论点快照，不能直接修改 `PurposePortfolio / CaseObjective / LighthouseStrategyObjective / plan_pool`。
- `AssessmentPolicySeed / 评估策略种子` 不能直接运行；运行时必须编译为 `InvestmentAssessmentPolicy / 投入评估策略实例`，并冻结 `seed_version_id / override_set_id / compiled_policy_hash`。
- `CoreStrategicSeed / 核心战略种子` 中的源体系匹配、灯塔匹配、边界安全、风险包络、人类裁决边界和证据强度下限只能收紧，不能被平台或形态适配放松。
- 平台适配种子只能调整信号解释、曝光周期、平台格式偏好和平台规则限制；媒体形态适配种子只能调整生产成本、审阅成本、资产沉淀方式和发布包结构要求。
- 首版平台种子的重点信号只是 `Initial Evidence Hypothesis / 初始证据假设`，不是平台算法事实；无法稳定采集或无法解释归因的信号不得进入加码硬门槛。
- 种子升级、平台规则变化或 AI 能力变化不能自动修改 active 策略实例，只能生成 `CandidateProposal / 候选提案` 或迁移候选。
- `InvestmentAssessmentPolicy / 投入评估策略` 是版本化评分契约；`active` 必须有人类批准，生效后不得原地修改维度、阈值、否决项或模型契约。
- `increase / 加码` 不能只由总分触发；必须通过源体系匹配、灯塔匹配、风险包络和证据强度硬门槛。
- 证据缺失不能当作普通低分吞掉；必须进入 `InvestmentEvidenceGap / 投入证据缺口`，并按策略降级为观察、保持、人工审阅或失败。
- `InvestmentThesisSnapshot / 投入论点快照` 插入后不可更新；复盘、修正和反驳只能追加新快照或 `InvestmentOutcomeReview / 投入结果复盘`。
- `InvestmentOutcomeBaselineSnapshot / 投入结果基线快照` 与 sealed `InvestmentOutcomeReview / 投入结果复盘` 不可更新；历史结论修正必须形成新复盘版本。
- 复盘封存前必须存在基线快照、实际结果指标、预期实际比较、证据引用和归因假设；不能只保存自然语言摘要。
- `algorithm_noise_overload / 算法噪声过载` 灰灯关联的复盘不得给出 `supported / contradicted` 等确定性结论，只能给出 `noise_overloaded / uncertain / insufficient_evidence / confounded`。
- 复盘不能直接修改 `AssessmentPolicySeed / PurposePortfolio / LighthouseStrategyObjective / SourcePack`；种子校正必须形成 `CandidateProposal / 候选提案` 与 `AssessmentSeedCorrectionCandidateDetail / 评估种子校正候选明细`。
- 复盘必须冻结使用的策略版本、种子版本、AI 能力与模型版本；不能用“当前最新策略/模型”解释历史结果。
- `ResourceAllocationDecision / 资源配置决策` 必须引用已批准的 `CandidateDecision / 候选裁决`；当状态进入 `applied` 时，必须已有 `CandidateApplication / 候选应用` 记录输出对象。它记录决策痕迹，不是静默改计划工具。
- `algorithm_noise_overload / 算法噪声过载` 灰灯期间，不允许自动生成 `recommendation='increase'` 的资源加码应用。
- 没有 `review_due_at / 复盘时间`、`failure_condition / 失败条件` 或至少一条 `investment_evidence_ref` 的投入论点不得生效。

- `artifact_version_id`、`rendition_id` 和 `artifact_id` 必须通过触发器校验为同一产出物链路；不能把 A 产出物的渲染包到 B 产出物。
- 真实发布包进入 `queued / submitting / published` 前，必须绑定 `quality_snapshot_id` 和通过的 `real_publish_gate_run_id`。
- `quality_snapshot_id` 必须指向同一 `artifact_id / artifact_version_id / purpose_policy_binding_id`，且 `qualified_status in ('qualified','high_quality')`、`publish_readiness in ('ready','ready_with_warning')`。

### 10.1a Guard DDL 最小规格

以下 Guard 必须作为迁移脚本的一部分落库。实现可以拆分函数，但不能只停留在应用层判断。

```sql
-- 1. 影子运行发布硬隔离
create function artifactos.fn_guard_shadow_publish_isolation()
returns trigger language plpgsql as $$
begin
  if new.run_mode in ('shadow','simulation') or new.simulation_only then
    if new.media_publish_job_id is not null
       or new.published_url is not null
       or new.publish_status in ('queued','submitting','published') then
      raise exception 'shadow/simulation publication_package cannot enter real publish path';
    end if;
  end if;
  return new;
end $$;

create trigger trg_shadow_publish_isolation_guard
before insert or update on artifactos.publication_package
for each row execute function artifactos.fn_guard_shadow_publish_isolation();

-- 2. 模拟发布只能引用 shadow/simulation 发布包
create function artifactos.fn_guard_simulated_attempt_package()
returns trigger language plpgsql as $$
declare pkg record;
begin
  select run_mode, simulation_only into pkg
  from artifactos.publication_package
  where id = new.publication_package_id;
  if pkg.run_mode = 'real' and pkg.simulation_only = false then
    raise exception 'simulated_publication_attempt cannot use real publication_package';
  end if;
  return new;
end $$;

create trigger trg_simulated_attempt_package_guard

-- 5. 产出计划目的必须可解析、可锁定、锁定后不可改
create function artifactos.fn_guard_artifact_plan_purpose_lock()
returns trigger language plpgsql as $$
declare
  primary_code text;
  binding_purpose_type_id uuid;
begin
  select purpose_type_code into primary_code
  from artifactos.purpose_type_registry
  where id = new.primary_purpose_type_id
    and tenant_id = new.tenant_id
    and status = 'active';

  if primary_code is null then
    raise exception 'artifact_plan.primary_purpose_type_id must reference active purpose_type_registry';
  end if;

  if primary_code in ('trust_building','positioning') then
    raise exception 'trust_building/positioning are upper-layer objectives, not artifact primary purpose types';
  end if;

  if cardinality(new.secondary_purpose_type_ids_cache) > 2
     or new.primary_purpose_type_id = any (new.secondary_purpose_type_ids_cache) then
    raise exception 'artifact_plan secondary_purpose_type_ids_cache must be max 2 and exclude primary purpose';
  end if;

  if new.purpose_policy_binding_id is not null then
    select purpose_type_id into binding_purpose_type_id
    from artifactos.purpose_policy_binding
    where id = new.purpose_policy_binding_id
      and tenant_id = new.tenant_id
      and status = 'active';

    if binding_purpose_type_id is null then
      raise exception 'artifact_plan.purpose_policy_binding_id must reference active purpose_policy_binding';
    end if;

    if binding_purpose_type_id <> new.primary_purpose_type_id then
      raise exception 'purpose_policy_binding purpose_type must match artifact_plan primary_purpose_type';
    end if;
  end if;

  if new.status in ('opened','completed')
     and (new.purpose_policy_binding_id is null or new.purpose_locked_at is null) then
    raise exception 'artifact_plan purpose must be bound and locked before opening substudio';
  end if;

  if tg_op = 'UPDATE' and old.purpose_locked_at is not null then
    if new.primary_purpose_type_id is distinct from old.primary_purpose_type_id
       or new.secondary_purpose_type_ids_cache is distinct from old.secondary_purpose_type_ids_cache
       or new.purpose_policy_binding_id is distinct from old.purpose_policy_binding_id
       or new.required_hard_gates is distinct from old.required_hard_gates
       or new.minimum_score_dimensions is distinct from old.minimum_score_dimensions
       or new.quality_exit_criteria is distinct from old.quality_exit_criteria then
      raise exception 'locked artifact_plan purpose fields cannot be changed';
    end if;
  end if;

  return new;
end $$;

create trigger trg_artifact_plan_purpose_lock_guard
before insert or update on artifactos.artifact_plan
for each row execute function artifactos.fn_guard_artifact_plan_purpose_lock();

-- 6. 事件账本只追加
create function artifactos.fn_guard_event_ledger_append_only()
returns trigger language plpgsql as $$
begin
  -- 允许隐私、安全或法律要求的物理删除，但必须附加删除授权记录
  if (tg_op = 'DELETE' and old.metadata->>'deletion_reason' is not null
      and old.metadata->>'deletion_authorized_by' is not null) then
    -- 生成对应的 DeletionRecord 事件写入同一账本（由应用层在事务中先写入再删除）
    return old;
  end if;
  if (tg_op = 'UPDATE') then
    raise exception 'event_ledger rows cannot be updated — corrections must be expressed as new events';
  end if;
  if (tg_op = 'DELETE') then
    raise exception 'event_ledger is append-only — physical deletion only permitted with deletion_reason and deletion_authorized_by in metadata';
  end if;
  return old;
end $$;
```

### 10.3a 租户一致性外键

RLS 不能替代外键的租户一致性。正式迁移必须满足以下规则：

1. 所有租户内引用优先使用复合外键：`(tenant_id, ref_id) references target(tenant_id, id)`。
2. 被引用表必须补 `unique (tenant_id, id)`。
3. 对于外部模块暂未建立复合 FK 的裸 UUID，必须有 `trg_tenant_reference_guard` 校验引用对象租户一致。
4. 单列 `id` 外键只允许跨系统只读引用、外部来源引用或明确标注为延迟外键的字段。

## 十三、首期验收清单

- [ ] 能创建年案、半年案、季案、月案、周案、日案、今日子案，并校验父子层级。
- [ ] 能提交一场会议，生成 `MeetingRecord.status=committed` 和 `CaseSnapshot`。
- [ ] 未提交会议不能驱动下层案创建。
- [ ] 能从任意会议或信号生成 `OpportunityCandidate`。
- [ ] 能把机会候选转为 `PlanChangeProposal`。
- [ ] 未批准的 `PlanChangeProposal` 不能修改 `case_record.plan_pool`。
- [ ] 已批准并应用的 `PlanChangeProposal` 生成 `PlanChangeLog` 和新 `CaseSnapshot`。
- [ ] 日晨会能以 `DaySubCase` 为最小授权对象。
- [ ] 授权策略（DelegationPolicy）与介入策略（InterventionPolicy）分离，成熟案可以在授权范围内自动执行。
- [ ] 生产能力注册表（ProductionCapabilityRegistry）只允许登记能落到产出链对象的能力，未登记能力不得被 Amy 或片场岗位调用。
- [ ] 人类注意力预算（HumanAttentionBudget）能限制 Must Review / Recommended Review 的数量和预计耗时，超预算事项按介入策略降级或延后。
- [ ] 通知策略（NotificationPolicy）可以把需要人类知道的事件转成通知事件（NotificationEvent）。
- [ ] Amy 微信通道（AmyWeixinChannel）只作为工作汇报接口，能记录绑定状态、token 状态和投递尝试。
- [ ] 微信回复必须先形成回复命令（ReplyCommand），再落成正式决策记录或审批记录。
- [ ] 工作卡（WorkCard）能承载今日总览、批量审片、决策简报、异常、召回和每日精选审阅。
- [ ] 准备动作面板（PreparedActionPanel）支持 `1-8` 常用选项、`9` 重新生成、`0` 我来输入。
- [ ] 日报（DailyReport）能渲染日报详情页（DailyReportDetailView），日报入口卡（DailyReportEntryCard）能通过微信发送摘要与动作入口。
- [ ] 明日预案（NextDayPlan）能生成明日待发布批次（TomorrowPublishBatch）和候选（TomorrowPublishCandidate）。
- [ ] 明日预案提升记录（NextDayPlanPromotion）能把 confirmed plan version 提升为正式 DayCase / DaySubCase，并保存父级快照和授权证据。
- [ ] 当天例外发布（SameDayExceptionProposal）必须经过快速门禁（FastGateResult）。
- [ ] 策略单元成熟度（StrategyUnitMaturity）支持 M0-M4，升级、降级、冻结必须留下 MaturityChangeLog。
- [ ] 7 天影子运行（ShadowRun）能记录每日预案、日报、模拟执行和偏差。
- [ ] 影子运行观察（ShadowRunObservation）能逐条记录 ArtifactOS 模拟动作与旧系统真实动作的差异。
- [ ] 模拟发布尝试（SimulatedPublicationAttempt）能验证发布包到提交前一步，且不能触发真实发布。
- [ ] 旧系统导入批次、外部引用和快照能记录路径、hash、mtime、导入时间和授权范围，偏差复盘可复现。
- [ ] 每日精选审阅（DailyCalibrationReview）每天最多推荐一个产出物，且不阻塞发布。
- [ ] 校正范本（CalibrationExample）能记录正向/反向/混合范本和适用范围。

## 十四、硬约束

1. 不建物理表 `case`；统一使用 `case_record`。
2. 不把 `case_payload` 当作逃避建模的垃圾桶；高频查询字段必须升为列。
3. 不允许后台静默修改正式计划池。
4. 不允许会议草案驱动下层生产。
5. 不允许召回卡直接变成规则。
6. 不允许 EventLedger 物理更新来“修正历史”。
7. 不允许 SourcePack 母板被反馈自动修改。
8. 不允许把 `Task` 当产品层对象；产品层使用 `SubStudioExecutionTask`。
9. 不允许一个子片场产出多个产出物。
10. 不允许把多租户字段留到商业化以后再补。
11. 不允许把微信通道当作事实源、审批源或普通个人微信自动化。
12. 不允许明文保存 `context_token` 或在投递失败时静默丢弃通知。
13. 不允许把 `9` 用作重新生成以外的动作，或把 `0` 用作我来输入以外的动作。
14. 不允许将返回上一级、取消当次解释为业务批准、否决、冻结或暂存。
15. 不允许每日精选审阅阻塞发布流程。
16. Phase 1 不引入邮件通道；日报必须采用微信摘要入口与 ArtifactOS 日报详情页。
17. 不允许把当天审当天发作为默认流程；当天发布只能走 SameDayException。
