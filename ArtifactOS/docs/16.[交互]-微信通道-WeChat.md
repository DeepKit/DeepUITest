# 16 Amy 微信通道与主动通知协议

> 核心定位：Amy 微信通道（Amy Weixin Channel）是总制片秘书 Amy 的工作汇报接口（Work Report Interface），不是普通聊天入口，不是个人微信自动化，也不是系统事实源。

---

## 一、战略定位

ArtifactOS 的主要交互面仍然是 Amy 总控台（Amy Cockpit）。微信只承担一个职责：

```text
ArtifactOS 内部事件
  -> 通知策略（NotificationPolicy）
  -> 通知事件（NotificationEvent）
  -> 工作汇报（WorkReport）
  -> Amy 微信通道（Amy Weixin Channel）
  -> 人类确认 / 延后 / 否决 / 要求详情
  -> ArtifactOS 决策记录
```

因此，微信不是新系统的主界面，而是让 Amy 在人类不主动打开系统时可以主动汇报、请示和召回。

### 1.1 核心原则

1. **工作汇报接口（Work Report Interface）**：只发工作状态、日报入口、决策简报、异常、摘要、召回提醒。
2. **不承载社交关系**：不读取、不管理、不代替普通个人微信联系人和群聊。
3. **不做事实源**：微信消息只是投递副本，系统事实源仍是 PostgreSQL 与事件账本（EventLedger）。
4. **不越过 Amy**：人类仍然只和 Amy 交流；微信是 Amy 的一个通道，不暴露多 AI 角色。
5. **可失败设计**：微信投递可能延迟、失败、过期、重复，所有业务流程必须能在 Amy 总控台（Amy Cockpit）继续。
6. **最小泄露**：微信消息默认只发摘要、编号、按钮式选项或短指令，不发送大段源体系、完整草稿或敏感上下文。

### 1.2 技术前提

截至 2026-05-25，腾讯 `openclaw-weixin` 路线提供了可研究的官方微信通道能力：二维码登录（QR Login）、长轮询收消息（getUpdates）、发送消息（sendMessage）、图片/视频/文件等媒体结构，以及基于 `context_token` 的会话回复。

关键约束：

- `sendMessage` 需要目标用户（to_user_id）和上下文令牌（context_token）。
- `context_token` 来自入站消息，必须保存并按有效期管理。
- 长耗时任务可能遇到 `context_token` 过期，导致消息无法送达。
- 因此，ArtifactOS 不能假设微信是稳定、无限期、强保证的主动推送通道。

参考：

- `https://github.com/Tencent/openclaw-weixin`
- `https://github.com/openclaw/openclaw/issues/61174`

## 二、产品边界

### 2.1 它负责什么

| 场景（Scenario） | 微信动作（Weixin Action） | 业务归属（Business Owner） |
|---|---|---|
| 日晨会完成 | 发送今日工作汇报（Daily WorkReport） | 会议系统（Meeting System） |
| 日终汇总完成 | 发送日报入口卡（DailyReportEntryCard） | 日报详情页（DailyReportDetailView） |
| 有决策简报 | 发送决策简报通知（DecisionBriefNotice） | 决策简报（DecisionBrief） |
| 红线/冻结 | 立即发送中断通知（InterruptNotice） | 介入策略（InterventionPolicy） |
| 自动发布完成 | 发送发布结果通知（PublicationResultNotice） | 发布包（PublicationPackage） |
| 发布失败 | 发送失败摘要（DeliveryFailureNotice） | 发布引擎（PublishingAdapter） |
| 主动召回 | 发送召回提醒（RecallNotice） | 召回卡（RecallCard） |
| 周/月复盘 | 发送摘要报告（DigestReport） | 会议记录（MeetingRecord） |

### 2.2 它不负责什么

| 不做（Not Responsible） | 原因（Reason） |
|---|---|
| 不代替个人微信号聊天 | 会污染工作边界，也有隐私和合规风险 |
| 不处理未授权联系人或群聊 | 系统只服务 ArtifactOS 工作汇报 |
| 不承接读者私聊、销售、咨询 | 私域接引是另一个系统 |
| 不直接修改 SourcePack | 理论母板主权必须留在人类与会议体系 |
| 不把微信回复直接当最终决策 | 回复必须解析并落成正式 `MeetingDecisionRecord` 或 `ApprovalRecord` |
| 不长期保存明文 token | `context_token` 必须加密、过期、可撤销 |

## 三、核心对象

| 中文对象 | English Object | 职责 |
|---|---|---|
| 通知通道 | NotificationChannel | 抽象通知通道；Phase 1 仅实现微信 |
| Amy 微信通道 | AmyWeixinChannel | 微信工作汇报接口的绑定、状态和能力边界 |
| 通知策略 | NotificationPolicy | 决定什么事件、何时、通过哪个通道通知人类 |
| 通知事件 | NotificationEvent | 一次待发送或已发送的通知事实 |
| 工作汇报 | WorkReport | 面向人类的短摘要与动作选项 |
| 微信上下文令牌 | WeixinContextToken | 保存 `context_token`、捕获时间、有效期和状态 |
| 投递尝试 | DeliveryAttempt | 每一次实际发送请求和结果 |
| 通知账本 | NotificationLedger | 通知生命周期审计，可由 EventLedger 承载 |
| 回复命令 | ReplyCommand | 人类在微信中的短回复被解析后的命令 |
| 通道绑定 | ChannelBinding | 人类账号与 Amy 微信通道的绑定关系 |
| 日报入口卡 | DailyReportEntryCard | 微信中收到的日报摘要、动作和详情页入口 |
| 日报详情页 | DailyReportDetailView | 适合手机/桌面阅读并可逐项处理的完整日报页面 |

### 3.1 对象关系

```text
NotificationChannel
  -> AmyWeixinChannel
    -> WeixinContextToken
    -> NotificationPolicy
      -> NotificationEvent
        -> WorkReport
        -> DeliveryAttempt
        -> ReplyCommand
```

### 3.2 通知事件与业务事件分离

通知事件（NotificationEvent）只说明“需要通知”和“通知是否送达”。它不能代替业务对象状态。

例如：

```text
Artifact.status = sealed
ApprovalRecord.approval_status = waiting
DecisionBrief.status = waiting
NotificationEvent.status = delivered
```

这只表示决策简报通知已送达微信，不表示人类已经批准。

## 四、通知分级

通知分级必须和介入策略（InterventionPolicy）对齐，但不完全等同。

| 介入级别（Intervention Level） | 默认微信行为（Default Weixin Behavior） |
|---|---|
| `silent_record` 静默记录 | 不发微信，只入账 |
| `digest` 摘要汇报 | 进入日报/周报摘要 |
| `review_queue` 待看队列 | 低频提醒，可合并 |
| `ask_next_meeting` 下次会议请示 | 会议前提醒，附决策编号 |
| `interrupt_now` 立即中断 | 立即发送，必要时重复提醒 |

### 4.1 可发送的消息类型

| 消息类型（Message Type） | 用途（Purpose） | 是否要求回复 |
|---|---|---|
| 摘要报告（DigestReport） | 日报、周报、月报 | 否 |
| 日报入口卡（DailyReportEntryCard） | 每日日终摘要、低风险入口与详情页入口 | 可选 |
| 决策简报通知（DecisionBriefNotice） | 请求批准、否决、延后 | 是 |
| 中断通知（InterruptNotice） | 红线、冻结、发布异常 | 通常是 |
| 召回提醒（RecallNotice） | Amy 发现历史相关记录 | 可选 |
| 发布结果通知（PublicationResultNotice） | 成功、失败、URL、证据 | 否 |
| 重新绑定通知（RebindNotice） | token 失效或通道异常 | 是 |

### 4.2 消息格式

微信消息必须短，默认结构如下：

```text
[ArtifactOS / Amy]
类型：决策简报 DecisionBrief
编号：DB-20260525-003
事项：知乎今日子案 2 是否自动发布
建议：批准发布
理由：质量门禁通过，策略单元为成熟发布案，未命中红线
选项：回复编号或打开详情。高风险动作会回到 Amy 总控台确认
```

要求：

- 每条需要操作的消息必须有可追踪编号。
- 每个选项必须能映射到正式业务动作或低风险导航动作。
- 微信正文不放完整长文，最多放摘要和链接或编号。
- 详情以 Amy 总控台（Amy Cockpit）为准。
- 微信编号必须遵守准备动作协议（Prepared Action Protocol）：`1-8` 是常用选项，`9` 是重新生成，`0` 是我来输入。
- 日报入口卡里的微信选项默认只允许低风险动作：打开详情、稍后提醒、今天跳过、查看异常摘要。发布、返工、冻结、旧系统取舍和校正范本沉淀必须进入日报详情页或 Amy 总控台。

### 4.3 每日日报交付方式

每日日报（Daily Report）的正式交付方式固定为：

```text
日报数据与工作卡（Daily Report Data / Work Cards）
  -> 日报详情页（DailyReportDetailView）
  -> 日报入口卡（DailyReportEntryCard）
  -> Amy 微信通道（Amy Weixin Channel）
```

| 载体（Medium） | 职责（Responsibility） |
|---|---|
| Amy 微信通道（Amy Weixin Channel） | 主动送达摘要、待处理数量、低风险数字选项和详情入口 |
| 日报详情页（DailyReportDetailView） | 阅读完整日报、审阅工作卡、查看详情和执行按钮 |
| Amy 总控台（Amy Cockpit） | 保存完整待处理状态，并能从日报回到全量办公桌 |

Phase 1 不引入邮件通道（Email Channel）。日报、周报和月报均先采用“微信摘要入口 + ArtifactOS 详情页”的方式，未来只有在明确出现归档或外部分发需求时再新增通道。

日报入口卡（DailyReportEntryCard）的默认内容：

```text
今日完成量 / 已发布量 / 已暂存量 / 返工量
待决策数量 / 异常数量 / 每日精选审阅入口
Amy 对明日的建议
低风险直接动作：打开详情 / 稍后提醒 / 今天跳过 / 查看异常摘要
DailyReportDetailView 入口
```

日报入口卡不得在微信内承载完整审稿、发布批准、批量返工、旧系统取舍、每日精选范本沉淀等实质动作。这些动作必须打开日报详情页（DailyReportDetailView）或 Amy 总控台（Amy Cockpit）。

## 五、人类回复协议

人类在微信中可以使用短回复。Amy 负责解析为回复命令（ReplyCommand），但命令不能直接改业务状态，必须进入正式决策流。

微信回复必须复用 Amy 总控台同一个准备动作面板（Prepared Action Panel），不能在微信里另起一套选项。

| 回复（Reply） | 回复命令（ReplyCommand） | 后续落库对象（Persisted Object） |
|---|---|---|
| `1-8` | `prepared_option_selected` | 按 `PreparedActionOption` 映射到正式业务对象 |
| `9` | `regenerate` | 生成新的建议版本（SuggestionVersion），保留旧选项 |
| `0` | `human_input` | 打开上下文绑定输入，等待人类自然语言说明 |
| `返回` | `back` | 回到上一级工作卡或选项面板，不改变业务状态 |
| `取消` | `cancel_current` | 取消当次交互，不改变原业务状态 |
| `详情` | `request_detail` | 发送详情摘要或 Amy 总控台链接 |
| `冻结` / `暂停` | `freeze_request` | 生成冻结请求并回到 Amy 总控台确认 |
| `今天别提醒` | `mute_today` | 临时通知策略覆盖（NotificationPolicyOverride） |
| `停止自动发布` | `pause_auto_publish_request` | 生成策略变更提案草案并回到 Amy 总控台确认 |

### 5.1 解析约束

1. 回复必须绑定最近的可操作通知事件（NotificationEvent），不能凭空执行。
2. 歧义回复必须要求确认，不能猜测。
3. 高风险动作必须二次确认并引导到 Amy 总控台，不在微信内直接完成。
4. 所有回复原文必须写入事件账本（EventLedger）。
5. 解析后的动作必须有 `decision_narrative`。
6. `9` 重新生成必须保留旧建议版本，不能覆盖。
7. `0` 我来输入必须绑定当前工作卡，不能变成无上下文聊天。

### 5.2 微信动作等级

微信消息中的每个可操作项必须显式标注动作等级，避免人类把短回复误认为真实发布或高风险批准已经完成：

| 动作等级 | English Level | 是否可在微信直接生效 | 示例 |
|---|---|---|---|
| 入口 | `entry` | 可以 | 打开详情、请求摘要、查看异常摘要 |
| 低风险 | `low_risk` | 满足幂等和授权时可以 | 稍后提醒、今天跳过、取消当前交互 |
| 需确认 | `needs_confirmation` | 不可以，只生成 ReplyCommand 或 ApprovalRecord 草案 | 发布批准、返工、冻结、旧系统取舍 |
| 回总控台 | `cockpit_required` | 不可以 | SourcePack、灯塔目标、案目标、授权扩权、真实发布确认 |

微信内可直接生效的低风险批准必须同时满足：对应 PreparedActionPanel 当前有效、NotificationEvent 已送达且未过期、选项风险为 `entry/low`、DelegationPolicy 明确允许、不涉及真实发布/高风险返工/冻结/源体系/灯塔/案目标/授权扩权、生成幂等的 ApprovalRecord 或 HumanReviewChoice、决策幂等键未被使用。

发布、返工、冻结、解封、旧系统取舍、策略调参、授权变化、SourcePack 反哺、每日精选范本沉淀和真实发布确认，微信回复只能生成 `ReplyCommand / 回复命令` 或待确认草案，必须回到 Amy 总控台或日报详情页完成正式确认。

## 六、通道绑定与激活

### 6.1 首次绑定流程

```text
1. ArtifactOS 创建 NotificationChannel
2. 用户在本机触发微信二维码登录（QR Login）
3. AmyWeixinChannel.binding_status = qr_pending
4. 用户扫码确认
5. OpenClaw / 插件保存登录凭据
6. 用户向 Amy 会话发送“开始服务”
7. 系统从入站消息捕获 context_token
8. WeixinContextToken.token_status = active
9. Amy 发送验证消息
10. AmyWeixinChannel.binding_status = active
```

### 6.2 令牌生命周期

上下文令牌（context_token）必须以显式生命周期管理：

```text
captured -> active -> stale -> expired -> rebind_required
```

字段要求：

| 字段（Field） | 含义（Meaning） |
|---|---|
| `context_token_ciphertext` | 加密后的上下文令牌 |
| `captured_at` | 从入站消息捕获的时间 |
| `expires_at` | 估算或确认的过期时间 |
| `last_verified_at` | 最近一次验证成功时间 |
| `token_status` | active / stale / expired / revoked |
| `failure_count` | 连续发送失败次数 |

### 6.3 重新绑定

以下情况必须触发重新绑定或重新激活：

- `context_token` 过期且刷新失败。
- 发送连续失败超过阈值。
- 微信端取消授权。
- 本地凭据丢失。
- 人类主动撤销通道。

## 七、投递状态机

### 7.1 NotificationEvent.status

```text
pending
  -> scheduled
  -> sending
  -> delivered
  -> acknowledged
```

异常路径：

```text
sending -> failed -> retrying -> sending
sending -> expired -> rebind_required
delivered -> ignored
pending/scheduled -> canceled
```

### 7.2 DeliveryAttempt.status

```text
queued -> sending -> success
queued -> sending -> failed
failed -> retrying
failed -> abandoned
failed -> rebind_required
```

### 7.3 投递保证

微信通道不能承诺 exactly-once。ArtifactOS 应采用：

- 至少一次投递（At-least-once Delivery）。
- 幂等键（idempotency_key）防重复。
- 每次投递都记录 DeliveryAttempt。
- 同一 NotificationEvent 可多次尝试，但人类动作只能落一次决策。
- 重要决策必须能在 Amy 总控台继续完成。

## 八、安全与隐私

### 8.1 内容最小化

微信只发送：

- 标题、编号、短摘要。
- 关键理由，不发送完整证据链。
- 操作选项，不发送内部链路细节。
- 必要时发送 Amy 总控台链接或本地编号。

默认不发送：

- SourcePack 母板全文。
- 未封存长文全文。
- 全量会议记录。
- token、密钥、账号凭据。
- 用户隐私和外部评论原文。

### 8.2 权限边界

Amy 微信通道（AmyWeixinChannel）只允许：

- 读取自己的通知事件（NotificationEvent）。
- 读取必要的决策简报（DecisionBrief）摘要。
- 写入投递尝试（DeliveryAttempt）。
- 写入回复命令（ReplyCommand）。
- 追加事件账本（EventLedger）。

它不允许直接：

- 修改 SourcePack。
- 修改长期授权策略。
- 越过质量门禁发布。
- 修改历史事件。
- 访问无关案（Case）的全量上下文。

## 九、和 Amy 总控台的关系

| 能力（Capability） | Amy 微信通道（Amy Weixin Channel） | Amy 总控台（Amy Cockpit） |
|---|---|---|
| 接收摘要 | 支持 | 支持 |
| 快速批准/否决 | 仅限非日报入口卡、低风险、已绑定同一 PreparedActionPanel、可幂等回滚的事项 | 支持完整决策 |
| 查看全文/证据链 | 不默认支持 | 支持 |
| 阅读完整日报 | 发送摘要入口 | 支持日报详情页 |
| 批量总编台 | 不支持，只发入口 | 支持 |
| 会议正式提交 | 不支持或只做确认 | 支持 |
| 策略调参 | 只发提醒和短指令 | 支持完整协商 |
| 通道修复 | 提醒重新绑定 | 支持配置 |

结论：微信是 Amy 的外部触达器，Amy 总控台是完整工作台。

## 十、Phase 1 技术验证

在实现微信通道前，必须先做技术尖刺（Technical Spike）：

| 验证项（Spike Item） | 验收（Acceptance） |
|---|---|
| 二维码绑定（QR Binding） | 能完成扫码、保存凭据、显示 active |
| 首次回复（First Reply） | 用户发“开始服务”后 Amy 能回复 |
| 延迟发送（Delayed Send） | 1 小时后仍能发送或明确失败 |
| 重启恢复（Restart Recovery） | 进程重启后能读取通道状态并尝试发送 |
| 跨日发送（Next-Day Send） | 次日能发送或触发 rebind_required |
| token 过期（Token Expiry） | 能识别失败，不静默丢消息 |
| 文本消息（Text） | 可稳定发送短文本 |
| 媒体消息（Media） | 图片/文件仅作为可选验证，不作为 Phase 1 依赖 |
| 投递账本（Delivery Ledger） | 每次尝试都有 DeliveryAttempt |
| 幂等验证（Idempotency） | 重试不造成重复业务决策 |

Phase 1 不要求微信承担全部工作流，只要求它可靠地完成工作汇报、日报摘要入口、请示、失败留痕和回退到 Amy 总控台。

## 十一、硬约束

1. 微信通道不是系统事实源，所有事实必须回写 ArtifactOS。
2. 微信投递成功不等于业务批准。
