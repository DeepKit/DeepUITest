# 05 写作契约规范

> 系统编号：③
> 核心职责：定义写作契约的完整Schema、验证规则、生成流程和演进机制
> 设计来源：DeepStory「契约-产出物分离」、DeepStory「score_json完整规格」

---

## 一、设计理念

### 1.1 什么是写作契约

写作契约（ArtifactContract）是一份**机器可读的结构化产出指令**，是子片场（SubStudio）生产一个产出物（Artifact）时使用的执行约束。它必须绑定策略单元，由策略单元决定自治等级、理论介入方式、评分矩阵、重写次数和发布动作。

> **契约 = 起点**：告诉 AI "做什么"——但不是"写之前必须完成的铁律"
> **上下文 = 素材**：告诉 AI "用什么做"
> 两者严格分离，不重复。
> 契约可以在写作过程中**演进**（不是返工），也可以在定稿后**回填**。

### 1.1a 产出计划与写作契约的边界

产出计划（ArtifactPlan）回答“这个子片场要生产什么产出物”；写作契约（ArtifactContract）回答“这个产出物应如何生成和验收”。两者必须分离：

| 对象 | 英文名 | 归属 | 核心职责 |
|------|--------|------|----------|
| 产出计划 | ArtifactPlan | 片场（Studio）/产出计划集（ArtifactPlanSet） | 决定产出物类型、目标平台、目标受众、蓝图、发布意图和优先级 |
| 写作契约 | ArtifactContract | 子片场（SubStudio）/产出物（Artifact） | 决定论点、边界、结构、证据、质量验收和源体系忠实度 |
| 产出物蓝图 | ArtifactBlueprint | 媒体类型库 | 决定一个媒体产出物由哪些产出物部件（ArtifactPart）组成 |

规则：

1. 一个产出计划（ArtifactPlan）只能开启一个子片场（SubStudio）。
2. 一个子片场（SubStudio）只生产一个产出物（Artifact）。
3. 一个产出物（Artifact）可以由多个产出物部件（ArtifactPart）和资源文件（AssetFile）组成。
4. 写作契约（ArtifactContract）可以演进，但不能改变上层产出计划（ArtifactPlan）设定的目标平台、受众状态和产出物蓝图；需要改变时生成计划变更提案。

### 1.2 双模式：工程契约与种子契约

| 模式 | 契约类型 | 必填字段 | 适用场景 |
|------|---------|---------|---------|
| **工程模式** | `full_contract` | 几乎全部 | 知道要写什么，需要精确驱动 |
| **探索模式** | `seed_contract` | 仅 topic + account + platform | 有方向但不确定具体内容 |

种子契约是完整契约的**子集**——在探索过程中逐步补全为完整契约。这不是降级，而是两种并列的创作方式。

### 1.3 契约在系统中的位置

```
日案（DayCase）+ 主题（Theme）
    -> 今日子案（DaySubCase）
    -> 片场（Studio）
    -> 产出计划集（ArtifactPlanSet）
    -> 产出计划（ArtifactPlan）
    -> 子片场（SubStudio）
    -> 契约草稿（ArtifactContract draft）
    -> 契约验证（本系统）
    -> 正式契约（ArtifactContract formal）
    -> 写作引擎消费
    -> 质量门禁对标
    -> 发布引擎按策略执行
    -> 交互修改中演进
    -> 定稿后回填
```

### 1.4 契约成熟度（ODD）

写作契约不再只有"有/没有"，而是分为三个成熟度：

| 成熟度 | 含义 | 可进入的阶段 |
|--------|------|-------------|
| `draft` | 草案，可包含自然语言和模糊方向 | 探索模式、需求澄清 |
| `agreed` | 人类已确认大致方向、边界和账号 | 写作引擎生成草稿 |
| `formal` | 验收标准、边界条件、例外规则齐全 | 质量门禁、封存、策略化发布 |

工程模式应尽量从 `formal` 起步；探索模式可以从 `draft` 起步。策略单元若拥有自动发布权，发布前必须由系统回填并通过结构门禁升级到可封存的 `formal` 契约；高风险策略单元仍可要求人工确认。

### 2.2 字段详解

#### A. 身份标识区

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `contract_id` | string | 自动 | 唯一ID，格式 `ctr_YYYYMMDD_NNN` |
| `contract_type` | enum | **是** | `full_contract` 或 `seed_contract` |
| `maturity` | enum | 自动/人工 | ODD契约成熟度：`draft` / `agreed` / `formal` |
| `version` | int | 自动 | 契约版本号，演进或返工时递增 |
| `status` | enum | 自动 | 契约生命周期状态 |
| `strategy_unit_id` | string | 是 | 契约所属策略单元，决定自治等级和发布权限 |

#### A2. 策略区（strategy）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `strategy.autonomy_level` | enum | 是 | 当前策略单元授权等级 AL0-AL4 |
| `strategy.generation_mode` | enum | 是 | 写作流水线使用的生成模式 |
| `strategy.entry_mode` | enum | 是 | 热点驱动、理论驱动或混合入口 |
| `strategy.theory_intervention` | enum | 是 | 理论显性介入程度 |
| `strategy.quality_profile_id` | string | 是 | 质量评分矩阵配置 |
| `strategy.max_rewrite` | int | 是 | 自动重写次数上限 |
| `strategy.on_pass` | enum | 是 | 达标后的动作 |
| `strategy.on_rewrite_exhausted` | enum | 是 | 重写耗尽后的动作 |
| `strategy.experiment_id` | string? | 否 | 若使用实验策略，记录实验ID |

#### A3. 源体系映射区（source_mapping）

源体系映射（SourceMapping）是任意 SourcePack 到产出物主张、边界、禁忌和表达策略的结构化映射。理论映射（TheoryMapping）只是 `mapping_kind=theory` 时的特化实现，品牌、产品、课程、服务方法论和研究资料不能被迫伪装成理论。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `source_mapping.mapping_kind` | enum | 是 | `theory / brand / product / service_methodology / research / founder_voice` |
| `source_mapping.source_pack_snapshot_id` | string | 是 | 本契约使用的 SourcePack 快照 |
| `source_mapping.claim_refs` | string[] | 否 | 本次产出要外化的主张、卖点、方法、研究判断或理论命题 |
| `source_mapping.boundary_refs` | string[] | 是 | 不可越过的源体系边界、禁忌和表达红线 |
| `source_mapping.expression_policy` | enum | 是 | 显性表达、隐性转译、平台转译或品牌化表达 |
| `source_mapping.fidelity_profile_id` | string | 是 | 源体系忠实度（Source Fidelity）门禁配置 |

#### A3a. 理论区（theory profile）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `theory.theory_mapping_id` | string | 否 | 本契约采用的理论映射记录 |
| `theory.core_principle_refs` | string[] | 高理论介入必填 | 关联的理论核心原则 |
| `theory.thesis_path` | string[] | 否 | 从理论命题到文章主张的推导路径 |
| `theory.must_not_violate` | string[] | 是 | 不允许被自动改写的理论边界 |
| `theory.expression_policy` | enum | 是 | 显性理论、隐性理论或平台转译 |
| `theory.hypothesis_contract_id` | string | 研究型内容可选 | 关联的假设契约 |
| `theory.theory_revision_proposal_refs` | string[] | 否 | 相关理论修正提案 |
| `theory.causal_primitives` | object[] | 高理论介入必填 | 结构化因果原语，用于 theory profile 的 Source Fidelity 硬校验 |
| `theory.required_relations` | object[] | 高理论介入必填 | 草稿必须保留的阶段、属性、因果或序列关系 |
| `theory.forbidden_relations` | object[] | 是 | 不允许出现的错误转译、错误归因或禁止变迁 |
| `theory.allowed_translations` | object[] | 否 | 平台转译时允许的表达替换 |

S08 源体系映射不得只是一段说明文本。`mapping_kind=theory` 的高理论介入内容必须提供可判定的结构规格：

```json
{
  "causal_primitives": [
    {
      "id": "cp_001",
      "type": "attribute_shift",
      "from": "外部身份驱动",
      "to": "约束条件重组",
      "operator": "causes"
    }
  ],
  "required_relations": [
    {"subject": "中年转型", "relation": "requires", "object": "约束重组"}
  ],
  "forbidden_relations": [
    {"subject": "中年转型", "relation": "equals", "object": "重新燃起热情"}
  ],
  "non_negotiable_principles": ["不能把结构性转型简化成情绪鸡汤"]
}
```

源体系忠实度门禁（Source Fidelity Gate）优先检查这些结构关系；理论场景中表现为理论忠实度门禁，再用强推理模型处理不可机械判定的语义问题。

#### A3b. 认知区（cognition）

| 字段 | 类型 | 必填 | 说明 |

#### C. 核心指令区（directive）

| 字段 | 类型 | 必填 | 说明 |

#### F-H 素材/质量/协作区

质量区必须读取策略单元的质量画像。契约只记录本任务采用的快照，不复制整个策略矩阵。

#### I. ASTO / ODD 治理区

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `asto.state` | string | 是 | 契约当前结构状态，通常与 `status` 对齐 |
| `asto.transition` | string | 是 | 最近一次状态变化原因 |
| `asto.actor` | enum | 是 | 触发契约变化的行动者：human / ai / system |
| `asto.boundary_condition` | string | 是 | 契约成立和可执行的边界条件 |
| `asto.exception` | enum/string | 否 | 常规流程失效时的例外类型 |
| `odd.validation_gates` | string[] | 是 | 契约进入执行前必须经过的门禁 |
| `odd.evidence_refs` | string[] | 否 | 契约审核、人工覆盖、回填等证据ID |
| `odd.seal_required_before_publish` | bool | 是 | 下游定稿/发布前是否必须封存 |
| `odd.rollback_recall_policy` | string | 是 | 契约破坏性变更时下游产物如何处理 |

## 三、契约前置链

正式契约必须从 RSC/CTF 前置对象生成：

```text
RequirementFrame -> ContentSpecSnapshot -> ContractCandidate -> Contract
```

### 3.1 RequirementFrame

`RequirementFrame` 记录用户原始意图和必要澄清槽位：

| 槽位 | 发布前要求 |
|------|-----------|
| `target_account` | confirmed |
| `target_platform` | confirmed |
| `strategy_unit_id` | confirmed |
| `theory_intervention` | confirmed |
| `target_reader` | confirmed 或策略确认可空 |
| `success_result` | candidate 以上 |
| `non_goals` | 至少1条 |
| `ai_human_boundary` | confirmed |
| `acceptance_gate` | candidate 以上 |

### 3.2 ContentSpecSnapshot

`ContentSpecSnapshot` 是内容规格快照，至少记录：

- 语义束：主题、账号、素材、平台规则是否指向同一对象
- 证据引用：信号、素材、账号画像、人工审阅记录
- 正交状态：`gen_status` 与 `review_status`
- stale 状态：需求、素材、账号画像或平台规则变化后是否过期
- 语义束完整性：是否具备意图、结构、账号、平台、素材、证据和人类决策

### 3.3 ContractCandidate

`ContractCandidate` 是可升级为契约的候选对象：

| 状态 | 含义 | 处理 |
|------|------|------|
| `draft` | 候选仍缺边界或证据 | 继续CTF补证据 |
| `ready` | 可生成正式契约 | 进入Schema验证 |
| `blocked` | 有冲突、缺关键槽位或 stale | 返回RSC/CTF |

没有 `source_spec_snapshot_id` 的契约只能用于探索草稿，不能进入发布级封存。

### 3.4 策略决策、人类决策与规格问题

契约生成必须读取策略单元配置、`ContentDecision` 和 `SpecIssue`：

| 对象 | 作用 | 对契约的影响 |
|------|------|-------------|
| `StrategyUnit` | 决定账号、平台、内容类型、理论介入方式和自治等级 | 约束生成模式、评分矩阵、发布权限和抽检率 |
| `ContentDecision` | 人类确认、否定、补口、裁决冲突、锁定规格对象 | accepted 决策覆盖 AI 推断；locked 对象禁止 AI 覆盖 |
| `SpecIssue` | 规格缺口、冲突、低置信、无来源、stale source | 未关闭的 high issue 阻止契约进入 `formal` |

正交状态规则：

```text
gen_status = pending | generated | failed
review_status = pending | accepted | rejected | locked
```

- `generated + pending`：AI 候选，可用于探索，不能发布
- `generated + accepted`：已审阅，可进入 `ContractCandidate`
- `generated + locked`：人工锁定，AI 只能提出 patch proposal，不能直接覆盖
- `failed + locked`：来源变化导致需要再生成，但人类尚未解锁，进入 `FREEZE`

- 定稿后回填 must_land 时，ES-03 仍可执行（验证回填的完整性）

## 五、契约演进

### 5.1 演进 vs 返工

| 维度 | 演进（evolution） | 返工（rework） |
|------|-----------------|---------------|
| 触发 | 探索模式中人类发现新方向 | 质量门禁失败 |
| 性质 | 正常的创作发现 | 质量不达标 |
| 状态路径 | `contract_evolved` | `rework` |
| 计数 | `evolution_count` | `rework_count` |
| 对写作的影响 | 契约更新后继续写作 | 契约更新后重新生成 |

### 5.2 演进触发条件

- 人类在交互修改或策略黄灯协商中说了改变方向的话："角度要换"、"第二段不对，改成XX"
- 人类在交互修改中发现了新的论点："原来我想说的是这个"
- 系统在自动重写中发现当前契约无法满足策略目标，提出契约 patch proposal
- 人类主动修改了契约字段

### 5.3 演进流程

```
人类反馈或策略黄灯协商改变方向
    │
    ▼
系统检测到契约需要演进
    │
    ▼
contract_version += 1
status → evolved → approved（自动）
evolution_count += 1
    │
    ▼
更新后的契约注入写作上下文
    │
    ▼
AI 基于新契约继续生成（不是从头重写，而是调整受影响部分）
```

### 5.4 回填

探索模式定稿后，将写作过程中发现的论点、结构回填到契约中：

```python
def backfill_contract(contract, final_artifact):
    """定稿后回填契约"""
    # 从封存产出物中提取实际论点
    actual_points = extract_key_points(final_artifact.primary_text)

    # 回填 must_land
    if not contract.structure.must_land:
        contract.structure.must_land = actual_points

    # 回填 suggested_structure
    actual_structure = analyze_structure(final_artifact.primary_text)
    contract.structure.suggested_structure = actual_structure

    # 回填 opening_type, closing_type
    contract.structure.opening_type = classify_opening(final_artifact.primary_text)
    contract.structure.closing_type = classify_closing(final_artifact.primary_text)

    # 标记为回填版本
    contract.version += 1
    contract.version_history.append({
        "version": contract.version,
        "change_reason": "backfill_from_final",
        "changed_fields": ["structure.must_land", "structure.suggested_structure"]
    })
```

回填的契约作为历史记录保留，同时成为下次类似主题写作的参考模板。

## 六、契约生成流程

### 6.0 管线模式动态决策

契约生成流程不是按内容类型静态匹配的，而是运行时由多因子组合动态决定。系统在每次生成契约前，计算当前上下文的管线模式：

```python
def resolve_pipeline_mode(context: TaskContext) -> PipelineMode:
    """
    管线模式由以下因子在运行时组合决定，不由内容类型静态映射。
    返回: fast | standard | heavy
    """
    score = 0.0

    # 因子1：时效窗口
    if context.time_window_hours <= 6:
        score -= 3.0
    elif context.time_window_hours <= 48:
        score -= 1.0
    else:
        score += 1.0

    # 因子2：理论介入度
    theory_scores = {"high": 2.0, "medium": 0.5, "low": 0.0, "implicit": -0.5}
    score += theory_scores[context.theory_intervention]

    # 因子3：账号定位风险
    risk_scores = {
        "public_intellectual": 1.5, "niche_expert": 1.0,
        "personal_brand": 0.0, "media_outlet": 0.5,
    }
    score += risk_scores.get(context.account_positioning, 0.0)

    # 因子4：平台特性
    platform_scores = {"zhihu": 1.0, "wechat": 0.5, "xiaohongshu": -0.5, "weibo": -1.0}
    score += platform_scores.get(context.platform, 0.0)

    # 因子5：时事敏感度
    if context.is_breaking_news:
        score -= 2.0
    elif context.has_controversy_risk:
        score += 1.5

    # 因子6：用户输入完整度
    if context.user_input_completeness >= 0.8:
        score -= 1.0
    elif context.user_input_completeness <= 0.3:
        score += 1.0

    # 阈值判定
    if score <= -2.0:
        return PipelineMode.FAST
    elif score >= 2.0:
        return PipelineMode.HEAVY
    else:
        return PipelineMode.STANDARD
```

**策略单元覆盖**：策略单元可设 `pipeline_mode_override = fast | standard | heavy | auto`（默认 `auto`）。非 `auto` 时跳过动态计算，直接使用指定模式。

**权重参数化**：各因子的权重系数不是硬编码常量，而是策略单元级可配置参数，存储在 `strategy_unit.pipeline_mode_weights` 中。系统提供默认值，人类可按账号成熟度调节。

### 6.1 三种管线模式总览

| 模式 | RSC | CTF | Candidate | ODD | 适用场景 |
|------|-----|-----|-----------|-----|---------|
| **fast** | 结构校验（不追问） | 一致性快检（3项布尔） | 跳过 | 跳过，发布后异步追溯 | 热点快评、突发时效、卡片 |
| **standard** | 校验 + 缺失字段追问 | 完整一致性校验 | 正常生成 | 同步执行 | 热点长文、引流文、常规内容 |
| **heavy** | 追问 + 理论立场声明 | 强制论证骨架 + 先行假设清单 | 生成 + 理论评审闸门 | 同步 + 人工确认 | 系列深文、高理论介入、争议话题 |

### 6.2 fast 模式详细流程

```
选题漏斗输出 + 策略单元配置
    │
    ▼
RSC 结构校验（50行校验函数，不调用AI）
    │ 检查必填槽位：topic / target_account / target_platform / strategy_unit_id
    │ 缺失字段标记 unresolved，不追问，直接推进
    │
    ▼
CTF 一致性快检（3项布尔）
    │ account_fit: 账号定位与内容是否匹配
    │ platform_fit: 平台格式要求是否满足
    │ material_fit: 素材是否可用（有则用，无则跳过）
    │ 任一项 false → 升级到 standard 模式
    │
    ▼
直接生成 Contract（跳过 Candidate 层）
    │ 策略绑定由 strategy_unit 配置直推
    │ contract_type = full_contract
    │
    ▼
发布后异步 ODD 追溯
    │ 发布后 30 分钟内后台跑 ODD 事实校验
    │ 严重事实错误 → 自动触发召回
    │ 一般问题 → 记录 SpecIssue，不撤回
```

**风险对冲**：同一策略单元连续 3 次 fast 模式触发 ODD 告警 → 自动升级到 standard。

### 6.3 standard 模式详细流程

```
策略单元选择 + 选题漏斗输出 RequirementFrame + 得分
    │
    ▼
RSC 结构校验 + 缺失字段追问（限1轮AI调用）
    │ 已确认的槽位不追问，只补充缺失项
    │
    ▼
CTF 完整一致性校验
    │ 输入：RequirementFrame + 策略单元 + 账号画像 + 素材匹配 + 爆款参考 + 理论映射
    │ 输出：ContentSpecSnapshot
    ▼
契约候选生成器
    │ 输入：ContentSpecSnapshot
    │ 输出：ContractCandidate
    │
    ▼
契约验证（结构门禁 + Schema校验 + 必填字段检查）
    │
    ▼
策略门禁确认 / 必要时人类抽检确认
    │
    ▼
正式契约（status: approved）
```

### 6.4 heavy 模式详细流程

```
策略单元选择 + 选题漏斗输出 / 理论命题输入
    │
    ▼
RSC 完整追问 + 理论立场声明
    │ 标准追问 + 额外：确认理论核心原则、解释模型、推导路径
    │ 输出：RequirementFrame（含 theory.stance 和 theory.commitment）
    │
    ▼
CTF 增强规格建构
    │ 标准校验 + 强制输出：论证骨架 + 先行假设清单
    │ 输出：ContentSpecSnapshot（含 theory_anchored = true）
    ▼
契约候选生成器 + 理论评审闸门
    │ 标准 Candidate 生成 + 源体系忠实度门禁
    │ 检查 required_relations / forbidden_relations
    │ 人类确认理论核心未被稀释
    │
    ▼
契约验证 + ODD 完整校验 + 人工确认
    │
    ▼
正式契约（status: approved, maturity: formal）
```

### 6.5 探索模式（独立于管线模式）

探索模式不是管线模式的一种，而是另一种起步方式。种子契约在演进为正式契约时，仍需按运行时上下文重新计算管线模式进行验证：

```
人类给出方向或系统从热点/理论入口发现方向
    │
    ▼
创建 RequirementFrame + seed_contract
    │ 必填：topic + target_account + target_platform + strategy_unit_id
    │ 其余字段留空或从账号画像填充默认值
    │
    ▼
按策略单元自治等级进入写作（高风险策略可要求人类确认）
    │
    ▼
在交互修改中逐步演进为完整契约
```

## 七、契约验证

### 7.1 结构门禁（ODD前置）

Schema验证前先执行结构门禁：

| 规则 | 失败结果 |
|------|---------|
| `source.requirement_frame_id` 存在或明确标记为探索临时输入 | NEEDS_CTF_REVIEW |

| 关联 `ContentDecision` 不存在 accepted/locked 冲突 | CONFLICT |
| high 级 `SpecIssue` 已关闭或人工降级 | NEEDS_CTF_REVIEW |
| `odd.rollback_recall_policy` 非空 | CONFLICT |

### 7.2 Schema验证（ES，零成本）

#### 工程契约（full_contract）验证

| directive.target_account 合法 | 必须指向已注册的账号 |

| asto.boundary_condition 非空 | 必须声明契约成立边界 |

#### 种子契约（seed_contract）验证

| 规则 | 说明 |
|------|------|
| directive.topic 不为空 | 必须有方向 |
| directive.target_account 合法 | 必须指向已注册的账号 |

### 7.3 语义验证（半ES，低成本）

仅对 full_contract 执行。

| 规则 | 说明 |
|------|------|
| must_land 与 topic 相关 | 论点必须在主题范围内 |
| taboos 不与 must_land 矛盾 | 禁忌不阻止必须覆盖的论点 |
| material_refs 中的素材存在 | 引用的素材原子必须存在且未过期 |
| material_refs 的 atom_version 存在 | 引用必须锁定版本，不能只引用浮动 atom_id |
| 账号近期无重复主题 | 同账号14天内不重复同主题 |

### 7.4 ODD门禁判定

契约验证结果使用 ODD 门禁结果矩阵：

| 结果 | 含义 | 去向 |
|------|------|------|
| `PASS` | 契约满足当前阶段要求 | 按策略进入下一阶段 |
| `FAIL` | 契约字段或验收条件明确不合格 | 返回契约编辑 |
| `FREEZE` | 信息不足、风险过高或需要人工裁决 | 暂停自动推进 |
| `CONFLICT` | 契约内部边界、禁忌、目标互相冲突 | 进入契约修订 |

`seed_contract` 可以在 `draft/agreed` 成熟度进入探索写作，但不能直接进入发布；发布前必须通过回填、结构门禁和策略门禁形成可封存的 `formal` 契约快照。是否需要人工确认由策略单元决定。

## 十、需求语义澄清（RSC）与规格快照（CTF）转换逻辑

### 10.1 设计来源

RSC（Requirement Semantic Clarification）复用 DeepBase 意图澄清模块（IntentClarification）的设计模型，通过 `IDomainAdapter` 接口适配 ArtifactOS 的写作领域。

对应关系：

| ArtifactOS 对象 | DeepBase 概念 | 说明 |
|---|---|---|
| RSC（需求语义澄清） | IClarificationEngine + IDomainAdapter | 引擎 + 领域适配 |
| RequirementFrame | TSessionState（Slots 填充后） | 澄清结果 |
| CTF（规格快照） | Session Completed 时的输出 | 规则引擎生成 |
| ContractCandidate.status | Session.Status | 状态映射 |
| 工程模式 | RL1 指令型（表单驱动） | Phase 1 实现 |
| 探索模式 | RL2 问题识别型（LLM 辅助） | Phase 2 实现 |

### 10.2 级别与模式映射

| 澄清级别 | 对应写作模式 | 输入方式 | 是否需要 LLM | Phase |
|---|---|---|---|---|
| RL0（背景识别） | 策略单元自动生成 | 策略单元上下文自动填槽 | 否 | Phase 1 |
| RL1（指令型） | 工程模式 | 结构化表单 | 否 | Phase 1 |
| RL2（问题识别型） | 探索模式 | 自然语言 + LLM 澄清 | 是 | Phase 2 |
| RL3（单专家指导） | 理论深度探索 | LLM 专家角色 | 是 | Phase 3+ |
| RL4（多专家圆桌） | 复杂选题决策 | LLM 多角色协商 | 是 | Phase 4+ |

Phase 1 只实现 RL0 和 RL1，不依赖 LLM。

### 10.3 Phase 1 实现方案

**RL0 — 自动填槽**：

当策略单元自治等级达到 AL3+ 且有足够历史数据时，系统自动从策略单元配置和历史契约中推导槽位值，直接生成 RequirementFrame。无需人类输入。

**RL1 — 表单填槽**：

人类填写结构化表单，必填字段包括：

| 槽位（Slot） | 是否必填 | 说明 |
|---|---|---|
| `topic` | 是 | 写作主题 |
| `intent` | 是 | 写作意图（解释热点 / 推导观点 / 知识科普 / 理论评论） |
| `target_platform` | 是 | 目标平台（由策略单元默认值填充） |
| `content_type` | 是 | 内容类型（由策略单元默认值填充） |
| `theory_intervention` | 是 | 理论介入度（由策略单元默认值填充） |
| `argument_direction` | 否 | 论证方向 |
| `taboos` | 否 | 禁忌事项 |
| `word_count_range` | 否 | 字数范围（由策略单元默认值填充） |
| `open_questions` | — | 澄清过程中产生的未解决问题 |

表单字段的默认值从策略单元配置中自动填充，人类只需填写核心意图。

**RSC → CTF 转换**：

```
表单提交 / 自动填槽
→ Slot 全部填充完成（必填字段均有值）
→ 规则引擎生成 RequirementFrame
→ 规则引擎补全默认值，生成 ContentSpecSnapshot
→ 生成 ContractCandidate
```

### 10.4 ContractCandidate status 判定

| status | 判定条件 | 动作 |
|---|---|---|
| `ready` | 所有必填 Slot 已填充，无 open_questions | 可升级为 Contract |
| `draft` | 部分必填 Slot 未填充 | 人类补充后重新判定 |
| `blocked` | 有 blocking issue（理论冲突 / 策略单元冻结 / 证据不足）| 需解决阻塞项 |

判定逻辑对应 DeepBase Property 30：槽位全满触发自动完成。

### 10.5 Phase 2 增强

Phase 2 引入 RL2（问题识别型），支持探索模式：

- 输入：自然语言描述的模糊写作方向
- RSC 使用 LLM 生成假设（Scaffold）供用户确认/否认
- LLM 从自然语言中推导 Slot 值，人类可覆盖
- open_questions 非空时 ContractCandidate 保持 draft 状态
- 复用 DeepBase 的信号检测（Hesitation / Contradiction / Frustration）调整澄清策略
