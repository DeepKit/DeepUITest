## 一、设计哲学

### 核心原则

1. **策略单元驱动** —— 自治权授予 `账号 + 平台 + 内容类型 + 理论介入方式`，不做全局自动化开关
2. **SourcePack 治理** —— 源体系必须按母板、解释、实践、发布、归档等层级装载，不能被压平成普通检索语料
3. **源体系策略引擎** —— 理论、品牌、产品资料或方法论参与选题、解释、论证路径、表达转译和发布判断
4. **契约驱动** —— 写作契约是单篇任务的创作指令源，所有生成和门禁基于契约工作
5. **低人类打扰** —— AI 自动生成、重写、发布和提出策略建议；人类通过抽检、黄灯协商、降权和召回控制边界
6. **状态机管控** —— 任务流转、自动重写、自动发布、抽检、降权和召回靠状态机驱动
7. **质量分级** —— 硬门禁、底线分、目标分分层判定，由策略矩阵决定动作
8. **素材原子化** —— 素材是最小复用单元，通过引用复用而非拷贝复用
9. **自治可降权** —— 自动化能力必须可暂停、可降权、可抽检、可召回
10. **结构编码** —— 核心对象统一回答 ASTO-min 五字段：状态、变迁、行动者、边界、例外
11. **产出物治理** —— 高影响产出物按 ODD-min 留下契约、验证、证据、封存、回滚/召回路径
12. **契约前置** —— 写作契约必须从 RSC 需求语义帧和 CTF 规格快照中生成，不能从模糊输入直接跳到发布级契约
13. **事实源分层** —— 原始材料、规格事实和审阅呈现分离，预览/报告不能直接成为事实源
14. **正交审阅状态** —— 规格对象使用 `gen_status + review_status`，不把生成、审阅和执行状态混在一个字段里
15. **知识进化驱动** —— 任何自动化判断都要能进入“观察、推演、证据、行动、反馈、演进”的闭环
16. **证据化认知** —— 关键判断必须留下 `CognitionTrace` 和 `EvidenceClaim`，不能只保存最终稿
17. **扰动即入口** —— 黄灯、红灯、低分、反常数据、证据过期和理论漂移都建模为 `CognitiveDisturbanceEvent`
18. **边界认知** —— 系统必须会 `not_write`、`draft_only`、`freeze` 和 `wait_human`，高级自治不是盲目推进
19. **不替源体系裁决** —— 反馈可以生成 `BackfeedCandidate`，但修改源体系、尤其是理论母板，必须由人类裁决
20. **不执行接引承接** —— 系统只负责发光产出与反馈信号；互动、接引、成交和服务承接由其他系统负责
21. **最优设计优先** —— 时间不限、老系统兜底的前提下，每个设计决策都追求零欠债；预埋字段不删减，状态枚举不简化
22. **授权后自动推进** —— 内容行动流水线不设置单篇固定审批等待点；人类在年会、半年会、季度会、月会、周会和日晨会中确认对应案（Case）与授权范围后，秘书可在范围内自动改稿、复审、排期和提交发布
23. **片场秘书代理** —— 人类面对总制片秘书，而不是直接管理多个 AI 角色；秘书负责组织会议、调度岗位、压缩决策、汇报异常和主动召回历史
24. **全量记录，有限激活** —— 数据库全量记录会议、对话、草稿、diff、门禁、批准、发布和反馈；AI 调用只通过 `OperationContextPack` 接收被遗忘系统筛选后的最小上下文
25. **主动召回可解释** —— 秘书可以召回历史，但必须生成 `RecallCard`，说明来源、相关理由、生命周期状态和建议动作；召回不等于采纳
26. **会议分层治理** —— 年案（YearCase）管战略执行，半年案（HalfYearCase）管战略调整，季案（QuarterCase）管战略安排，月案（MonthCase）管战略落地，周案（WeekCase）管战术安排，日案（DayCase）管战术落地；越级问题必须生成计划变更提案（PlanChangeProposal）或边界变更提案（BoundaryChangeProposal）
27. **前夜审阅默认** —— 日常发布批次默认在前一晚审阅明日特别文件并确认明日预案（NextDayPlan），次日早晨只做轻确认；当天发布必须进入 `SameDayException`
28. **影子运行先行** —— 首个自用版本先完成连续 7 天影子运行（Shadow Run）；旧系统继续真实发布，ArtifactOS 只做生成、门禁、前夜审阅、模拟执行和偏差记录
29. **通用装载先诊断** —— 任意 SourcePack 进入生产前必须先形成 SourceInventory、SourceReadinessReport、SourceConflictReport 和 SourcePackLoadingDecision；一元论只是首个样板
30. **吸引交接不承接** —— 系统可结构化 ResonanceSignal、MisreadRisk、PublicFollowupCandidate 和 AttractionHandoff，但不接管私聊、销售和服务承接
31. **真实发布门统一判定** —— RealPublishGate 必须同时检查 `run_mode=real`、旧系统迁移阶段、SourcePack 生产许可、策略单元成熟度、授权策略、质量门禁、红线和回滚能力；不能只看 StrategyUnitMaturity M3/M4
32. **产出物生产与放大优先** —— ArtifactOS 的内部核心命题是 `Source-to-Artifact Production and Amplification Kernel / 源体系到产出物生产与放大内核`；AI、状态机、账本、门禁和授权都是合格产出物生产的后台机制，不是产品目的
33. **能力注册受产出链约束** —— `ProductionCapabilityRegistry` 只登记生成、审校、渲染、发布、信号采集和召回等产出链能力；不能把系统扩展成通用 Agent 平台
34. **人类注意力受预算约束** —— `HumanAttentionPolicy` 和 `HumanAttentionBudget` 必须驱动 Amy Today Desk，决定哪些事项必须处理、建议审阅、可由 Amy 自办、等待结果或进入异常风险

### 首个 SourcePack 边界

首版以 `D:\_Progs\一元论` 作为第一个自用 SourcePack。架构上必须把外部源体系和 ArtifactOS 内部运行态分开：

```text
D:\_Progs\一元论
    │  只读装载：README / governance / 01-母板 / 02-学术 / 03-解释 / 04-实践 / 85-发布 / 90-组合
    ▼
SourcePackManifest
    │  固化模块、层级、引用优先级、归档排除、主张强度、禁用边界
    ▼
SourcePackSnapshot
    │  每次产出冻结当时使用的源体系版本
    ▼
ArtifactContract -> Artifact -> Rendition -> PublicationPackage -> SignalLedger
    │
    ▼
BackfeedCandidate -> HumanDecision
```

ArtifactOS 不直接修改一元论源目录。任何可能反补源体系的反馈，只能进入 `BackfeedCandidate`，再由人类裁决是否形成外部源目录的实际修改任务。

## 三、系统间数据流

### 3.1 核心数据流：认知行动与写作契约

写作契约是串联所有系统的核心数据单元：

```
SourcePack ──只读装载──→ SourcePackManifest + SourcePackSnapshot
     │
     ▼
⑨知识进化控制台 ──选择──→ StrategyUnit + StrategyConfig + QualityProfile
①选题漏斗 ──输出──→ RequirementFrame → ContentSpecSnapshot → ContractCandidate
②素材库   ──注入──→ 素材引用（原子ID列表）
③契约规范 ──约束──→ 契约Schema验证 + 结构门禁
④写作引擎 ──消费──→ 契约 → 生成草稿 → 自动重写
⑤质量门禁 ──对标──→ 契约 + 质量画像 + 策略阈值
⑥账号矩阵 ──绑定──→ 契约中的目标账号+平台+策略单元
⑦发布引擎 ──执行──→ 条件自动发布 / 暂存 / 降级 / 等待人类
⑧数据回收 ──回灌──→ 选题信号 + 素材效果 + 知识进化灯号
```

写作契约仍然是内容行动的核心执行单元，但不再是 ArtifactOS 的最高对象。最高对象是一次可追溯的 `CognitionTrace`：它把信号、理论、证据、行动和反馈串成一次知识进化事件。

架构上不得把上述自动化能力解释为“治理 AI”。系统的主链是：

```text
SourcePack -> Case -> LighthouseStrategy -> Studio -> Artifact
  -> QualityGate -> PublicationPackage -> SignalEvent -> CandidateProposal
```

`ProductionCapabilityRegistry`、`DelegationPolicy`、`InterventionPolicy`、`EventLedger` 和状态机只保障这条主链质量、边界、追溯和省人工。任何不能落到该主链的能力，应作为外部系统或未来适配器处理，不进入核心域。

### 3.2 反馈闭环

```
发布后数据（阅读/点赞/收藏/评论/公开追问/共鸣信号/误读风险/高意向信号/AttractionHandoff 状态）
    │
    ▼
⑧数据回收系统
    ├── → ①选题系统：验证选题判断是否准确
    ├── → ②素材库：标记哪些素材类型效果好
    ├── → ⑥账号系统：验证账号-主题适配度
    ├── → ④写作系统：积累爆款模板库
    └── → ⑨知识进化控制台：生成绿/黄/橙/红/蓝/灰灯与调参建议
```

### 3.2a 知识进化闭环

```text
SignalScope 发现扰动
    -> TheoryWeave 生成解释假设
    -> ClaimGraph 拆解 EvidenceClaim 并检查反证
    -> PraxisForge 生成内容/研究/策略行动
    -> 数据回收与人类抽检形成反馈
    -> 进化控制台生成 CognitiveDisturbanceEvent
    -> StrategyChangeProposal / KnowledgeHydration / TheoryRevisionProposal
```

每次闭环至少要记录以下字段（完整定义见 `19.[认知]-证据认知与进化-Evidence-Evolution` §2.1）：

| 字段 | 含义 |
|------|------|
| `cognition_trace_id` | 本次认知行动的主追踪ID |
| `execution_task_id` | 关联的子片场执行任务ID |
| `case_id` | 关联的案（Case） |
| `studio_id` | 关联的片场（Studio） |
| `artifact_id` | 关联的产出物（Artifact） |
| `strategy_unit_id` | 关联的策略单元ID |
| `observed_attributes` | 系统识别出的关键属性 |
| `noise_attributes` | 被过滤的噪音属性 |
| `trend_prediction` | 对内容、平台、理论或研究方向的预测 |
| `intervention_action` | 写、重写、发、暂存、不写、召回、调参等介入 |
| `evidence_claim_refs` | 本次判断关联的断言引用 |
| `boundary_decision` | 本次判断的边界决策 |
| `field_feedback_refs` | 发布数据、人类反馈、反证、门禁失败等反馈来源 |
| `evolution_writeback` | 对策略、知识、理论映射或规格的回写建议 |

### 3.3 案场调度中枢

调度系统不把传统任务（Task）作为产品层一级对象。产品层记录案（Case）、今日子案（DaySubCase）、片场（Studio）、子片场（SubStudio）和产出物（Artifact）；内部自动化才使用子片场执行任务（SubStudioExecutionTask）：

```
子片场执行任务 = {
    execution_task_id: 唯一ID
    case_id: 案ID
    day_sub_case_id: 今日子案ID
    studio_id: 片场ID
    sub_studio_id: 子片场ID
    artifact_plan_id: 产出计划ID
    artifact_id: 产出物ID
    strategy_unit_id: 策略单元ID
    contract_id: 关联的写作契约
    current_state: 任务状态机当前状态
    flags: 叠加标记
    rework_count: 返工次数
    failure_context: 返工原因
    account_id: 目标账号
    platforms: [目标平台列表]
    autonomy_level: 策略单元当前自治等级
    publish_policy: auto_publish | require_review | store_draft | downgrade
}
```

### 3.4 RSC / CTF / ODD 契约前置链

```
raw_topic / human_direction / signal
    │
    ▼
RSC RequirementFrame
    │  澄清：意图、账号、平台、读者、边界、验收方向、未知项
    ▼
CTF ContentSpecSnapshot
    │  建构：多投影、语义束、证据、审阅、stale状态
    ▼
ContractCandidate
    │  判定：ready / draft / blocked
    ▼
ODD Contract
    │  执行：验证、证据、封存、回滚/召回
```

### 3.5 ASTO-min / ODD-min 横切数据流

ASTO-min 与 ODD-min 不新增独立业务系统，而是作为横切治理纪律嵌入所有核心对象。

```
核心对象（topic / contract / draft / final / publication / knowledge）
    │
    ├── ASTO结构卡：state / transition / actor / boundary_condition / exception
    │       └── 用于解释对象当前状态、谁触发了变化、边界何在、例外如何处理
    │
    └── ODD治理记录：contract / validation / evidence / seal / rollback-recall
            └── 用于决定产出物能否放行、如何留痕、何时封存、如何召回
```

落地约束：

- 状态变化必须经过任务调度系统记录 `actor` 与 `transition`
- 契约生成必须能追溯到 `RequirementFrame` 和 `ContentSpecSnapshot`
- 自动门禁、人工覆盖、发布确认都必须生成 `evidence`
- 定稿与发布物进入下一阶段前必须具备最小 `seal`
- 证据损坏、契约破坏性变更、高风险缺陷暴露时必须进入 `rollback/recall` 流程

### 3.6 OCGS 治理事件桥

所有 AI 能力调用都必须形成轻量 `GovernanceEvent`，把能力调用与后续 ODD 证据链连起来：

```
TaskObjective
    → AbilityCall
    → AgentResult
    → gate_state
    → responsibility_subject
    → odd_contract_id
    → validation_result
    → evidence_log / writeback
    → seal_state / rollback_state
```

首期不实现完整 OCGS/TAT，只记录最小字段：本次调用目标、能力、边界条件、门禁状态、责任主体、结果摘要、回写建议、证据引用和回滚状态。

### 3.7 ContentSpec 事实源分层

DeepSpec 的 A/B 分层可以轻量映射到 ArtifactOS：

```text
A 原始材料层
    用户输入 / 素材原子 / 账号画像 / 平台规则 / 发布数据 / 反馈原文
        │
        ▼
B 规格事实层
    RequirementFrame / ContentSpecSnapshot / SemanticBundle
    ContentDecision / SpecIssue / Evidence / AgentResult
        │
        ▼
审阅呈现层
    产出物预览 / 质量报告 / 案场面板 / 发布预览 / 数据看板
```

落地规则：

- PostgreSQL `artifactos` schema 是首期事实源；HTML/Markdown/预览页是可再生成的审阅面
- 人类在审阅面点击“通过/返工/否定/补口/裁决冲突”时，先生成候选 `ContentDecision`
- `ContentDecision.status=accepted` 后才影响规格事实和后续 AI 上下文
- AI 生成的候选规格默认 `gen_status=generated, review_status=pending`
- `review_status=locked` 的规格节点不能被 AI 输出覆盖，除非有人工解锁或 override 证据

### 3.8 片场秘书、遗忘系统与主动召回

片场秘书是人类面对 ArtifactOS 的主入口。她不替代人类主权，而是在授权范围内代理日常操作：

```text
年案（YearCase）
    │
    ▼
半年案（HalfYearCase）
    │
    ▼
季案（QuarterCase）
    │
    ▼
月案（MonthCase）
    │
    ▼
周案（WeekCase）
    │
    ▼
日案（DayCase）
    │
    ▼
ExecutiveProducerSecretary
    │
    ├── 查询 EventLedger + RetainedPatternStore
    │       └── 生成 RecallCard，放回对应层级会议讨论
    │
    ├── 生成今日子案（DaySubCase）与片场（Studio）
    │       └── 按授权策略（DelegationPolicy）自动执行或生成决策简报（DecisionBrief）
    │
    ├── 调度 AI 片场岗位
    │       └── 编剧 / 主编 / 账号导演 / 理论守门 / 证据审校 / 平台适配
    │
    ├── 开启子片场（SubStudio）并产出 Artifact / ArtifactPart / AssetFile
    │       └── 批量总编台（Artifact Review Desk）：复合部件预览 / diff / 对话改稿 / 批量门禁 / 批准
    │
    └── ApprovalRecord
            └── media_publish 发布
```

遗忘系统与传统“记忆系统”的边界：

| 层 | 职责 | 关键对象 |
|----|------|----------|
| 全量事实账本 | 不丢事实，用于审计、回放、追责、复盘 | `EventLedger` |
| 遗忘后台 | 衰减、静音、压缩、候选化、归档、弃用 | `ForgettingQueue` / `ForgettingRefiner` |
| 保留模式库 | 仅保存可复用、可解释、可追溯的行动模式 | `RetainedPatternStore` |
| 主动召回 | 根据当前会议议题把相关历史带回讨论 | `RecallCard` |
| 最小注入 | AI 调用前的有限上下文，不读取全量历史 | `OperationContextPack` |

系统必须坚持：

```text
全量记录，有限激活；后台遗忘，前台清明。
```

`EventLedger` 记录所有会议、对话、草稿、版本、diff、门禁、批准、发布状态和反馈，但这些记录默认不进入 AI 上下文。每次 AI 调用前，秘书和遗忘系统共同生成 `OperationContextPack`，记录注入来源和裁剪理由。

主动召回以 `RecallCard` 进入会议，不直接改变规则。`deprecated/archived/muted` 的历史只有在强相关时才能破例召回，并必须说明原因。

### 3.9 前夜审阅与首个影子运行

首个可验证运行方式不是直接自动发布，而是以旧系统为真实发布方、ArtifactOS 为影子运行方：

```text
D 日白天：ArtifactOS 生成 D+1 候选与发布包草案
    -> D 日晚上：Amy 展示 DailyReport / NextDayPlan / TomorrowPublishReview
    -> D 日夜间：根据人类选择修正、重跑门禁、重建发布包
    -> D+1 早晨：MorningLightConfirmation
    -> D+1 白天：ArtifactOS 模拟执行；旧系统真实发布
    -> D+1 晚上：ShadowRunObservation 记录两侧偏差
```

数据边界：

| 对象（Object） | 作用（Responsibility） |
|---|---|
| `NextDayPlan` | 次日执行草案，不是正式 `DayCase` |
| `TomorrowPublishCandidate` | 前夜审阅与夜间修正的产出候选 |
| `ShadowRun` / `ShadowRunDay` | 运行级与每日级验收事实 |
| `ShadowRunObservation` | ArtifactOS 模拟动作与旧系统真实动作的结构化差异 |
| `DailyReportEntryCard` | 微信中的摘要入口，不承载完整审稿 |

完整可执行规格见 `17.[交互]-前夜审阅与影子运行-Evening-Shadow.md`。

## 四、技术选型

### 4.1 与 media_publish 的关系

`PraxisForge` 是 ArtifactOS 内部负责内容行动和发布执行的子品牌，media_publish 是它的底层发布执行组件：

```
ArtifactOS
    │
    ▼
PraxisForge（内容行动与发布流水线）
    │
    │ 写作契约 + 定稿内容
    ▼
media_publish（发布执行层）
    │
    │ 浏览器自动化
    ▼
各平台（知乎/公众号/小红书/微博）
```

- ArtifactOS 负责：观象 → 论演 → 证链 → 行铸 → 反馈演进
- PraxisForge 负责：契约 → 写作 → 质量门禁 → 适配 → 发布交付
- media_publish 负责：浏览器会话管理 → 格式注入 → 发布 → 截图存证

- 原生支持 RLS 和 schema 隔离，多团队扩展不需要换数据库

### 4.2a PG 触发器与数据库层治理

PG 应承担核心数据治理逻辑，而非仅作为被动存储：

| 触发器/约束 | 用途 | Phase |
|------------|------|-------|
| `trg_validate_state_transition` | 插入前校验状态转换是否在白名单内（§06.[模型]-状态机规范-State-Machine §七A） | 1 |
| `trg_enforce_dag_no_cycle` | EvidenceClaim 插入/更新时检测循环依赖 | 1 |
| `trg_freeze_task_on_redline` | 质量门禁命中红线时自动将任务置为 frozen | 2 |
| `trg_log_governance_event` | 任何 GovernanceEvent 写入时自动追加到事件日志表 | 1 |
| `trg_calibration_delta_check` | calibration_delta 写入时检查连续超标次数 | 2 |
| `CK_scope_vs_propagation` | CHECK 约束：`scope=article` 的断言 `propagation_policy` 只能为 `isolated` | 1 |
| `CK_dag_no_self_ref` | CHECK 约束：`depends_on_claim_ids` 不得包含自身 ID | 1 |
| `CK_valid_state_combo` | CHECK 约束：三轴状态组合必须在白名单内（对照状态机规范） | 1 |

原则：凡可以通过数据库约束、触发器和函数保证的规则，优先在数据库层实现，不依赖应用层代码自觉遵守。

完整表结构、字段、索引、触发器和迁移顺序见 `24.[数据]-数据库模型与治理-Database.md`。架构层只定义存储边界，具体落库以该规格为准。

### 4.2b 多租户预埋

Phase 1 为单用户运营，但数据结构必须预埋多租户字段：

```sql
-- 所有核心业务表统一携带
tenant_id   UUID NOT NULL  -- 团队/组织标识
created_by  UUID NOT NULL  -- 操作人
updated_by  UUID NOT NULL  -- 最后修改人

-- RLS 策略骨架（Phase 1 不启用，但建表时写入）
ALTER TABLE strategy_unit ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON strategy_unit
  USING (tenant_id = current_setting('app.current_tenant_id')::UUID);
```

Phase 1 所有 `tenant_id` 写入固定值（如 `00000000-0000-0000-0000-000000000001`），应用层不感知。Phase 3/4 多团队运营时，仅需切换 `tenant_id` 来源和启用 RLS，不改表结构。

### 4.3 AI 调用

- 通过 Anthropic API / OpenAI API 直接调用 LLM
- 上下文组装在 ArtifactOS 内完成，不依赖外部 RAG 服务
- 半ES校验使用小模型（Haiku / GPT-4o-mini）
- NES评分使用大模型（Sonnet / GPT-4o）

## 六、设计约束

### 6.1 人类参与点（策略触发）

人类不再是每篇内容的固定流程节点。人类参与由策略单元、抽检策略、红线和看板灯号触发。

| 环节 | 人类动作 | 触发条件 |
|------|---------|----------------|
| 策略初始化 | 定义账号、平台、内容类型、理论介入方式和默认权重 | 新策略单元创建 |
| 黄灯协商 | 阅读调参建议，用自然语言与 AI 协商并确认参数 | 系统发现策略优化机会 |
| 会议授权 | 处理秘书生成的 `DecisionBrief`，必要时覆盖 `DelegationPolicy` 或 `InterventionPolicy` | 年/半年/季/月/周/日会议、策略单元权限变化或计划变更提案进入审议 |
| 前夜审阅 | 审阅明日特别文件、确认或修改 `NextDayPlan` | 日常发布批次进入晚上工作页；首个影子运行每日执行 |
| 批量总编台（Artifact Review Desk） | 批量批准、冻结、返工或局部抽检产出物（Artifact） | 发布前批次进入总编台 |
| 抽检 | 阅读草稿或已发布内容，给出矫正反馈 | 随机抽检、风险抽检、新策略抽检 |
| 红灯处理 | 降权、暂停、召回或修订 | 红线、高风险错误、连续失配 |
| 人工覆盖门禁 | 明确覆盖理由和责任承接 | ODD要求 override 必须留证据 |
| 理论核心变更 | 确认理论核心原则、解释模型重大版本变化 | AI 禁止自动改核心理论 |
| 解封/召回决策 | 决定是否撤回、回滚或重新发布 | 普通风险召回；红线级风险可先自动暂停再通知 |

| 理论映射 | 将热点映射到理论命题、解释框架和观点候选 | 全自动，红线抽检 |
| 策略建议 | 发现策略失配并生成黄灯建议 | 自动提出，人类确认 |

| ES校验 | 机械合规检查 | 全自动 |

| 发布执行 | 达标后按策略自动发布、暂存或等待人类 | 策略授权下自动 |

| 遗忘提炼 | 对 EventLedger 后台衰减、压缩、候选化和归档 | 全自动，规则晋升需按边界确认 |
| 影子运行对照 | 把 ArtifactOS 模拟动作与旧系统真实动作写入 `ShadowRunObservation` | 自动记录，人类在 7 天复盘裁决 |
