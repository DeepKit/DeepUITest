# 26. 技术选型与运行时架构 / Stack Decision

> 状态：ArtifactOS 1.0 开发前决策
> 范围：前端、后端、运行时拆分、数据库通讯、DeepBase 复用、AutoFix、Python 诊断层

## 1. 决策摘要

ArtifactOS 1.0 不采用 FastAPI 作为核心后端。本版本所有 ArtifactOS 程序均可以直接读写 PostgreSQL 业务库，但必须遵守 schema、门禁、命令表、状态表和测试库隔离约束。

目标技术栈：

```text
ArtifactOS.Desk   Delphi VCL + DeepBase DeepShell
ArtifactOS.Agent  Delphi VCL/Tray lightweight launcher
ArtifactOS.Engine Delphi on-demand backend worker
ArtifactOS.Core   Delphi shared domain / DB contract / service units
PostgreSQL        DB3 business truth and cross-process contract
DeepBase DB1      local config, layout, MRU, logs, secrets
Python            readiness, tests, migration tooling, diagnostic page, media_publish bridge
media_publish     PublishingRuntime browser automation and platform adapters
```

## 2. 不采用 FastAPI 的原因

本版本不引入 FastAPI core backend：

- ArtifactOS 当前定位是 Delphi / DeepBase 桌面应用生态内的产出物操作系统，不是 API-first Web 服务。
- DeepBase 已提供 ConfigDB、Security、Logging、EventBus、Scheduler、WorkerQueue、Resilience、DeepShell、AutoFix 等基础设施。
- 引入 FastAPI 会增加第二套生命周期、配置、日志、Secret、任务调度、依赖安装、端口管理和服务健康检查。
- Delphi Desk 启动 Python Web server 的运维成本高于启动 Delphi Engine。
- 1.0 重点是发布闭环、证据链、影子运行和桌面工作台，而不是 Web 后端平台化。

FastAPI 可作为未来远程 facade / Web API / 外部集成层评估，但不是 1.0 核心后端。

## 3. 程序拆分

ArtifactOS 仍在一个仓库内开发，但按 Delphi 项目拆分：

| 项目 | 类型 | 职责 |
|---|---|---|
| `ArtifactOS.Core` | Delphi shared units / package | 共享类型、状态枚举、PG contract helper、DB adapter、服务接口 |
| `ArtifactOS.Desk` | Delphi VCL app | 主前端；继承 DeepBase `TDeepMainForm`；人工启动后端；展示工作台和状态 |
| `ArtifactOS.Agent` | Delphi Tray / lightweight app | Desk 未打开时接收 Amy 命令或本地触发，按需启动 Engine |
| `ArtifactOS.Engine` | Delphi worker / console app | 按需启动后端；处理 PG command；生成产出链；写状态和事件 |
| `ArtifactOSTests` | Delphi DUnitX tests | Delphi 单元 / 集成测试 |

现有 `src/ArtifactOS.dproj` 可作为 Engine/console 原型迁移来源，不再作为最终桌面前端形态。

## 4. DeepBase 复用边界

### 4.1 Desk 使用 DeepShell

ArtifactOS Desk 必须从 DeepBase DeepShell 起步：

```pascal
type
  TArtifactOSDeskMainForm = class(TDeepMainForm)
  protected
    procedure RegisterServices; override;
    procedure RegisterCommands; override;
    procedure RegisterProviders; override;
    procedure AfterShellShown; override;
  end;
```

Desk 不从空 `TForm` 重复搭主窗体基础设施。业务内容通过 Provider 注入。

### 4.2 DeepBase 承担基础设施

ArtifactOS 应复用：

- DB1 ConfigDB / `root.txt`
- Security / Secret
- Logger
- FormState / MRU / Layout
- Theme / i18n
- Hotkeys
- EventBus
- Scheduler / WorkerQueue
- Resilience
- DeepShell Command / Provider / Status / Diagnostics
- AutoFix

禁止在下游重复实现 DeepBase 已有基础设施；禁止新增散落 INI / JSON / YAML 配置作为运行时配置源。

### 4.3 数据库分层

| 数据库 | 归属 | 内容 |
|---|---|---|
| DB1 ConfigDB / SQLite | DeepBase | 本地配置、布局、MRU、日志、Secret、Desk 本地状态 |
| DB3 PostgreSQL | ArtifactOS / PublishingRuntime | 业务真相、产出物、发布包、影子运行、runtime command、发布状态 |

ArtifactOS 业务主数据不得塞入 DB1。Secret 不得明文写入 PG 或日志。

## 5. PostgreSQL 直连原则

本版本所有 ArtifactOS 程序可以直接连接 PostgreSQL：

- `ArtifactOS.Desk` 可直接读业务状态、写人工 command / review signal。
- `ArtifactOS.Agent` 可直接读 Amy command / pending command，并写启动状态。
- `ArtifactOS.Engine` 可直接 claim command、写执行状态、写事件账本。
- Python readiness / tests / diagnostic page 可直接读 PG，必要时写诊断或测试数据。

直连不等于绕过契约：

- 必须使用 `artifactos_test` 做测试。
- 必须遵守 `artifactos` / `media_publish` / `legacy_bridge` schema 边界。
- 高风险动作必须经过 RealPublishGate 和人类授权语义。
- 写入发布意图时走 PG command / status contract，不直接控制浏览器。
- 跨程序通讯以 PG 表、状态、租约和事件为准，而不是进程内 direct call。

## 6. 运行时模型

### 6.1 Desk 人工启动

```text
User
  -> ArtifactOS.Desk
  -> write/read PG command/status
  -> start ArtifactOS.Engine when needed
  -> observe Engine heartbeat/status
```

Desk 启动 Engine 后，Engine 在活跃工作期间保持运行；默认无 running / pending command 10 分钟后退出。Engine heartbeat 建议 15 秒一次，Desk / Agent heartbeat 建议 30 秒一次。

### 6.2 Amy 命令启动

```text
Amy command
  -> ArtifactOS.Agent / Tray
  -> write/read PG command/status
  -> start ArtifactOS.Engine when needed
  -> Engine processes command
  -> Desk later observes same PG state
```

如果 Desk 未打开，由 Agent 负责最小常驻和后端启动；Agent 不承担完整业务 UI。

### 6.3 PublishingRuntime

ArtifactOS 不直接控制浏览器。浏览器会话、平台登录、平台 adapter、截图和发布执行属于 PublishingRuntime / media_publish。

ArtifactOS 只负责：

- 生成发布意图。
- 写 runtime command。
- 读 session / task / verification status。
- 执行 RealPublishGate。
- 展示证据和异常。

### 6.4 ArtifactOS runtime command contract

ArtifactOS 内部命令使用：

```text
artifactos.runtime_instance
artifactos.runtime_command
artifactos.runtime_command_event
```

发布执行命令继续使用：

```text
media_publish.runtime_command
```

两层 contract 不混用：Desk / Agent / Amy 写 `artifactos.runtime_command`；Engine claim 并执行 ArtifactOS 命令；只有 Engine 可以在 L3 发布门禁通过后写 `media_publish.runtime_command`。

Agent 使用 PostgreSQL `LISTEN/NOTIFY` channel `artifactos_runtime_command` 接收实时通知，并使用 polling 兜底。Engine claim 使用 lease；默认 lease 为 5 分钟。runtime command 状态和事件账本由 `028_artifactos_runtime_command.sql` 定义。

## 7. Python 定位

Python 保留，但不作为核心后端：

| 模块 | 定位 |
|---|---|
| `check_readiness.py` | 开发前只读自检 |
| `tests/*.py` | 集成测试 / shadow run 验证 |
| `backend/amy_desk.py` | 诊断页面；非主前端 |
| `backend/diagnostics/publishing_runtime_bridge.py` | media_publish 桥接 / 诊断 |
| future migration runner | 开发工具；默认只指向 `artifactos_test` |

`backend/amy_desk.py` 保留为 diagnostic page，不承载正式 Amy Desk 主交互。

## 8. AutoFix 集成

AutoFix 应接入所有相关 Delphi 项目：

- `ArtifactOS.Desk`
- `ArtifactOS.Agent`
- `ArtifactOS.Engine`
- `ArtifactOSTests`

每个可执行项目至少提供 smoke scenario。Desk/Agent 使用 VCL hook；Engine/Tests 使用适合自身类型的 scenario runner。

AutoFix boundary 原则：

- 允许修改 ArtifactOS 源码中的 `.pas` / `.dfm`。
- 默认不允许修改 DeepBase。
- 默认不允许修改数据库迁移。
- `.dpr` / `.dproj` 是否允许修改按接入阶段人工裁决。

## 9. 测试与门禁

开发前：

```bash
python check_readiness.py
```

常规 Python 集成测试：

```bash
python tests/run_all_tests.py
```

Delphi 编译：

```bash
./build.bat
```

后续拆分项目后，应补充：

- Desk build gate。
- Agent build gate。
- Engine build gate。
- AutoFix check / scenarios。
- PG contract tests。
- Engine command roundtrip tests。

## 10. 当前不做

本版本不做：

- FastAPI core backend。
- React / Vue / SPA 主前端。
- Node 构建链。
- Delphi 直接控制浏览器发布。
- Python server-rendered page 作为主前端。
- 客户端直连 DB4。
- 散落 JSON/INI/YAML 运行时配置。
