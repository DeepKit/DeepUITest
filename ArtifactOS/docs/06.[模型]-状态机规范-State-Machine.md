# 06 状态机规范

> ArtifactOS 案场对象与子片场执行任务状态机的完整转换规则表
> 参照 DeepStory 状态机规范风格

---

## 一、对象层级 + 三轴状态机 + 规格前置状态 + 策略状态 + 认知状态

### 1.1 概览

ArtifactOS 的产品层对象是案（Case）、今日子案（DaySubCase）、片场（Studio）、子片场（SubStudio）和产出物（Artifact）。三轴状态机只用于子片场执行任务（SubStudioExecutionTask），不能替代上层案场状态：

```text
MeetingRecord.status:
  draft → prepared → in_review → committed → archived
                     │
                     └── canceled

Case.status:
  planned → active → reviewing → closed
                 │         │
                 └── frozen / archived

Studio.status:
  planning → running → gate_checking → closed
                         │
                         └── frozen

SubStudio.status:
  planned → executing → reviewing → packaged → closed
                           │
                           └── rework / frozen

Artifact.status:
  planned → drafting → assembled → gate_checking → sealed → packaged → published
                                      │             │
                                      └── rework/frozen

PlanChangeProposal.status:
  draft → waiting_meeting → approved → applied
                              │
                              ├── rejected
                              ├── deferred
                              └── superseded

NotificationEvent.status:
  pending → scheduled → sending → delivered → acknowledged
                         │
                         ├── failed → retrying → sending
                         ├── expired → rebind_required
                         └── canceled

WorkCard.status:
  prepared → visible → opened → completed
                         │
                         ├── dismissed
                         └── expired

PreparedActionPanel.status:
  prepared → active → completed
                   │
                   ├── canceled
                   └── superseded

DailyCalibrationReview.status:
  candidate → recommended → reviewing → completed
                         │
                         ├── skipped
                         └── canceled

DailyReport.status:
  draft → prepared → notified → opened → completed → archived

NextDayPlan.status:
  draft → proposed → confirmed → promoted
                      │
                      ├── canceled
                      └── superseded

TomorrowPublishCandidate.status:
  candidate → evening_reviewing → overnight_revising → morning_confirming → approved_for_publish
                    │                     │                     │
                    ├── held              ├── held              ├── held
                    ├── frozen            └── frozen            └── frozen
                    └── canceled

SameDayExceptionProposal.status:
  detected → proposed → fast_gate_checking → waiting_human → approved → published
                                      │             │
                                      ├── stored    ├── stored
                                      ├── rejected  ├── rejected
                                      └── expired   └── expired

ShadowRun.status:
  planned → running → completed
              │
              ├── canceled
              └── aborted

ShadowRunDay.status:
  planned → generated → evening_reviewing → overnight_processing → morning_confirming → simulating → reported → closed
                                │                    │                    │
                                ├── skipped          ├── skipped          └── skipped
                                └── closed           └── closed
```

子片场执行任务（SubStudioExecutionTask）的状态由三条执行轴组成，并带一个轻量规格前置状态、一个策略自治状态和一个认知状态：

```
前置: spec_status     (规格状态) — RSC/CTF/契约候选是否就绪
前置: strategy_status (策略状态) — 策略单元是否允许本任务自动推进
前置: cognition_status (认知状态) — CognitionTrace / EvidenceClaim / BoundaryDecision 是否就绪
轴1: pipeline_status (管线状态) — 任务在管线中的位置
轴2: quality_status  (质量状态) — 质量门禁的检查结果
轴3: publish_status  (发布状态) — 发布执行的结果
```

注意：`RequirementFrame`、`ContentSpecSnapshot`、`SemanticBundle` 自身使用 `gen_status + review_status` 表示“是否生成、是否被审阅”。任务执行状态不得写回这些 CTF 对象，避免把规格形成和执行生命周期混在一起。

三条轴独立演进，但有前置依赖关系：

```
spec_status:
  clarifying → snapshotting → candidate_ready → contracted
       ↑              │                 │
       └──── needs_review/stale ────────┘

pipeline_status:
  pending → contracting → drafting → reviewing → approved → publishing → published → collecting → completed
                                    ↑              │
                                    └─── 返工 ──────┘
  任意非终态 --FREEZE/CONFLICT/REDLINE--> frozen --人工解封--> contracting/drafting/reviewing/publishing/abandoned
  reviewing --策略要求--> waiting_human / stored / abandoned
  pending/contracting/reviewing --边界决策--> not_writing / draft_only

quality_status (仅在 reviewing 期间演进):
  pending → structure_checking → structure_passed → es_checking → es_passed → ses_checking → ses_passed → strategy_decision → passed
                              → structure_blocked               → es_failed                              → rework / sample_review / waiting_human / stored

publish_status (publishing期间及发布后召回时演进):
  pending → scheduled → publishing → published
                       → failed
                       → recalled

strategy_status:
  active → warning → degraded → paused
       ↘ experiment

cognition_status:
  not_started → tracing → evidence_claiming → falsification_checking → cognition_ready
                                      │                   │
                                      └── evidence_gap ───┴── boundary_required
```

### 1.2 轴间约束

| 约束 | 说明 |
|------|------|
| 上层案（Case）处于 `frozen/archived` 时，不得新建片场（Studio） | 上层边界优先于执行便利 |
| 会议记录（MeetingRecord）未 `committed` 时，不得把会议草案作为下层案约束 | 防止草案驱动生产 |
| 计划变更提案（PlanChangeProposal）未 `approved/applied` 时，不得修改正式计划池 | 动态变化必须可治理 |
| 片场（Studio）处于 `closed/frozen` 时，不得新建子片场（SubStudio） | 固定生成环境关闭后不得追加产出 |
| 子片场（SubStudio）只能绑定一个产出物（Artifact） | 防止一个执行单元混出多个发布对象 |
| `pipeline_status` 进入 `reviewing` 前，`quality_status` 必须为 `pending` | 质量检查在 reviewing 阶段开始 |
| `pipeline_status` 从 `contracting` 转到 `drafting` 前，`spec_status` 必须为 `contracted` 或探索模式下明确标记为临时规格 | 防止跳过RSC/CTF直接写作 |
| `quality_status` 从 `pending` 进入 `es_checking` 前，必须通过 `structure_checking` | ES只检查文字，不替代规格/证据检查 |
| `pipeline_status` 从 `reviewing` 转到 `approved` 前，`quality_status` 必须为 `passed` | 质量通过才能发布 |
| `pipeline_status` 从 `approved` 转到 `publishing` 前，`publish_status` 必须为 `pending`，且策略单元允许发布 | 发布状态在 publishing 阶段开始 |
| `pipeline_status` 从 `approved` 转到 `publishing` 前，发布包门禁（PackageGate）必须通过 | 不把缺件、错账号或重复提交交给发布适配器 |
| `pipeline_status` 从 `publishing` 转到 `published` 前，`publish_status` 必须为 `published` | 确认发布成功 |
| 任一门禁返回 `FREEZE` 或 `CONFLICT` 时，`pipeline_status` 必须转入 `frozen` 或设置 `flags.frozen=true` | 自动流转停止 |
| 从 `frozen` 解封时，必须有人工 `decision_narrative` 和下一状态 | ODD要求解封留痕 |
| 策略单元降权到低于自动发布等级时，已批准但未发布任务必须重新走策略裁决 | 防止旧授权继续外发 |
| `pipeline_status` 进入 `approved` 前，`cognition_status` 必须为 `cognition_ready` 或由人类接受 evidence_gap | 防止无认知轨迹放行 |
| `BoundaryDecision=not_write` 时，任务进入 `not_writing` 并生成证据，不再自动转 drafting | 不写也是有效决策 |
| `BoundaryDecision=draft_only` 时，任务可 drafting/reviewing，但不得 publishing | 只草稿不外发 |

## 二、管线状态转换规则

### 2.1 完整转换表

| # | 从 | 到 | 触发条件 | 触发者 | 副作用 |
|---|----|----|---------|--------|--------|
| P1 | `pending` | `contracting` | 策略单元调度或人类确认开始 | 系统/人类 | 绑定strategy_unit_id，生成RequirementFrame，spec_status→clarifying |
| P1a | `contracting` | `contracting` | RSC槽位达到最低要求 | 人类/系统 | spec_status→snapshotting |
| P1b | `contracting` | `contracting` | `ContentSpecSnapshot` 冻结 | CTF | spec_status→candidate_ready |
| P1c | `contracting` | `contracting` | `ContractCandidate` ready | CTF/人类 | 记录contract_candidate_id |
| P2 | `contracting` | `drafting` | 契约审核通过且规格链有效 | 人类 | 契约status→approved, spec_status→contracted |
| P3 | `contracting` | `abandoned` | 人类废弃 | 人类 | — |
| P4 | `drafting` | `reviewing` | 草稿生成完成 | 写作引擎 | quality_status→pending |
| P5 | `reviewing` | `approved` | 质量门禁通过 | 质量门禁 | quality_status→passed |
| P6 | `reviewing` | `drafting` | 返工 | 质量门禁/人类 | rework_count++, quality重置 |
| P6b | `drafting` | `drafting` | 契约演进（探索模式） | 人类反馈 | evolution_count++, contract_version++ |
| P7 | `approved` | `publishing` | 策略允许发布且 final_seal 存在 | 系统/人类 | publish_status→pending |
| P8 | `approved` | `abandoned` | 人类废弃 | 人类 | — |
| P9 | `publishing` | `published` | 发布成功 | 发布引擎 | 记录URL、截图、publication_seal |
| P10 | `publishing` | `publish_failed` | 发布失败 | 发布引擎 | 记录失败原因 |
| P11 | `publish_failed` | `publishing` | 人类重试 | 人类 | — |
| P12 | `publish_failed` | `abandoned` | 人类废弃 | 人类 | — |
| P13 | `published` | `collecting` | 数据回收开始 | 数据回收器 | — |
| P14 | `collecting` | `completed` | 数据回收完成 | 数据回收器 | 更新表现数据 |
| P15 | 任意非终态 | `frozen` | 门禁FREEZE/CONFLICT或证据缺失 | 系统/门禁 | flags.frozen=true, 记录freeze_reason |
| P16 | `frozen` | `contracting`/`drafting`/`reviewing`/`publishing` | 人类解封并指定后续动作 | 人类 | 记录unseal证据 |
| P17 | `published`/`completed` | `frozen` | 发布物召回评估 | 人类/系统 | recall_status=pending |
| P18 | `reviewing` | `waiting_human` | 策略裁决要求人工处理或抽检阻塞 | 策略裁决 | flags.human_override=true |
| P19 | `reviewing` | `stored` | 重写耗尽且策略要求存草稿 | 策略裁决 | publish_status→skipped |
| P20 | `waiting_human` | `approved` | 人类抽检通过 | 人类 | quality_status→passed |
| P21 | `waiting_human` | `drafting` | 人类要求重写 | 人类 | rework_count++ |
| P22 | `approved` | `stored` | 策略或人类决定暂存不发 | 系统/人类 | publish_status→skipped |
| P23 | `pending`/`contracting`/`reviewing` | `not_writing` | BoundaryDecision=not_write | 系统/人类 | 记录 not_write_reason + CognitionTrace |
| P24 | `reviewing`/`approved` | `stored` | BoundaryDecision=draft_only 或 store_candidate | 系统/人类 | publish_status→skipped，保留草稿 |

### 2.2 非法转换

以下转换**不允许**（没有对应规则）：

| 从 | 到 | 原因 |
|----|----|------|
| `completed` | 任何（召回评估除外） | 已完成的任务不可回退；若已发布产出物触发召回，只能进入 `frozen` 评估，不回到普通执行流 |
| `abandoned` | 任何 | 已废弃的任务不可复活 |
| `pending` | `drafting` | 必须先经过 contracting |
| `not_writing` | `drafting` | not_write 是有证据的边界决策，除非新扰动生成新任务 |
| `drafting` | `approved` | 必须先经过 reviewing 和 strategy_decision |
| `contracting` | `drafting` | 若 `spec_status=stale/needs_review`，必须先回到RSC/CTF |
| `frozen` | 任意自动状态 | frozen 只能由人类解封或红线处理策略明确解除 |

## 三、质量状态转换规则

### 3.1 完整转换表

| # | 从 | 到 | 触发条件 | 触发者 |
|---|----|----|---------|--------|
| Q1 | `pending` | `structure_checking` | 进入reviewing阶段 | 系统自动 |
| Q1a | `structure_checking` | `structure_passed` | 结构门禁PASS | 质量门禁 |
| Q1b | `structure_checking` | `structure_blocked` | NEEDS_CTF_REVIEW / FREEZE / CONFLICT / ROLLBACK_REQUIRED | 质量门禁 |

| Q3 | `es_checking` | `es_failed` | 任一ES规则失败 | ES引擎 |
| Q4 | `es_passed` | `ses_checking` | ES通过后自动 | 系统自动 |
| Q5 | `ses_checking` | `ses_passed` | 无严重警告 | 半ES引擎 |
| Q6 | `ses_checking` | `ses_warned` | 有警告但不阻断 | 半ES引擎 |
| Q7 | `ses_passed` | `strategy_decision` | 进入策略裁决 | 系统自动 |
| Q8 | `ses_warned` | `strategy_decision` | 警告也进入策略裁决 | 系统自动 |
| Q9 | `strategy_decision` | `passed` | 策略判定通过且无需抽检 | 策略裁决 |
| Q10 | `strategy_decision` | `rework` | 低分且未超重写上限 | 策略裁决 |
| Q11 | `es_failed` | `pending` | 返工后重新检查 | 系统自动 |
| Q12 | `rework` | `pending` | 返工草稿生成后 | 写作引擎 |
| Q13 | 任意检查中 | `rework` | 门禁FAIL | 质量门禁 |
| Q14 | 任意检查中 | `waiting_human` | 门禁FREEZE/CONFLICT且策略要求人工 | 系统自动 |
| Q15 | `structure_blocked` | `pending` | RSC/CTF复审完成后重新检查 | 系统自动 |
| Q16 | `strategy_decision` | `sample_review` | 命中随机/风险/新策略抽检 | 策略裁决 |
| Q17 | `sample_review` | `passed` | 人类抽检通过 | 人类 |
| Q18 | `sample_review` | `rework` | 人类抽检要求重写 | 人类 |
| Q19 | `strategy_decision` | `waiting_human` | 重写耗尽且 fallback=wait_human | 策略裁决 |
| Q20 | `strategy_decision` | `stored` | 重写耗尽且 fallback=store_draft | 策略裁决 |

说明：`quality_status=waiting_human/stored` 表示质量/策略裁决的局部结果；当该结果需要阻断整个任务时，管线状态必须同步转为 `pipeline_status=waiting_human/stored`。实现时以 `state_combo_seed` 白名单校验两轴组合，不能由单轴状态自由漂移。

## 四A、通知投递状态转换规则

通知投递状态只描述通知事件（NotificationEvent）和投递尝试（DeliveryAttempt）的生命周期，不描述业务对象是否已批准、发布或冻结。

### 4A.1 NotificationEvent.status

| # | 从 | 到 | 触发条件 | 触发者 |
|---|----|----|---------|--------|
| N1 | `pending` | `scheduled` | 通知策略（NotificationPolicy）命中但未到发送窗口 | 通知调度器 |
| N2 | `pending` | `sending` | 立即发送 | 通知调度器 |
| N3 | `scheduled` | `sending` | 到达发送窗口 | 通知调度器 |
| N4 | `sending` | `delivered` | 通道返回发送成功 | 通道适配器 |
| N5 | `delivered` | `acknowledged` | 人类回复被解析并落成正式决策对象 | Amy |
| N6 | `sending` | `failed` | 通道返回错误或超时 | 通道适配器 |
| N7 | `failed` | `retrying` | 未超过重试上限且错误可重试 | 通知调度器 |
| N8 | `retrying` | `sending` | 重新发送 | 通知调度器 |
| N9 | `sending` | `expired` | 上下文令牌（context_token）过期或会话失效 | 通道适配器 |
| N10 | `expired` | `rebind_required` | 刷新 token 失败，需要重新绑定 | 通道适配器 |
| N11 | `pending`/`scheduled` | `canceled` | 业务对象已关闭、撤销或被合并到摘要 | 通知调度器 |
| N12 | `delivered` | `ignored` | 超过响应窗口且不需要强制确认 | 通知调度器 |

### 4A.2 DeliveryAttempt.status

| # | 从 | 到 | 触发条件 | 触发者 |
|---|----|----|---------|--------|
| D1 | `queued` | `sending` | 开始调用通道 API | 通道适配器 |
| D2 | `sending` | `success` | API 返回成功 | 通道适配器 |
| D3 | `sending` | `failed` | API 返回失败或超时 | 通道适配器 |
| D4 | `failed` | `retrying` | 可重试错误 | 通知调度器 |
| D5 | `failed` | `rebind_required` | token 过期、授权失效或登录态失效 | 通道适配器 |
| D6 | `failed` | `abandoned` | 超过重试上限或业务通知已失效 | 通知调度器 |

### 4A.3 通知状态约束

| 约束 | 说明 |
|------|------|
| `NotificationEvent.status=delivered` 不等于业务批准 | 只能说明通知送达 |
| `NotificationEvent.status=acknowledged` 必须引用正式决策对象 | 必须有 `ReplyCommand` 和 `MeetingDecisionRecord` / `ApprovalRecord` |
| `DeliveryAttempt` 必须追加记录 | 失败、重试、成功都必须可审计 |
| 微信通道失败不得丢失业务决策 | 重要事项必须仍在 Amy 总控台和 DecisionBrief Queue 中 |
| 重试必须使用幂等键 | 防止重复微信消息导致重复业务动作 |

## 四C、工作台与准备动作状态转换规则

工作台状态只描述 Amy 办公桌（Amy Desk）上的工作卡（WorkCard）、准备动作面板（PreparedActionPanel）、每日精选审阅（DailyCalibrationReview）和日报（DailyReport），不替代案、产出物、审批或发布状态。

### 4C.1 WorkCard.status

| # | 从 | 到 | 触发条件 | 触发者 |
|---|----|----|---------|--------|
| W1 | `prepared` | `visible` | Amy 将卡片摆上办公桌 | Amy |
| W2 | `visible` | `opened` | 人类打开卡片或查看详情 | 人类 |
| W3 | `opened` | `completed` | 卡片对应事项形成正式决策或处理完成 | 系统 |

### 4C.2 PreparedActionPanel.status

| # | 从 | 到 | 触发条件 | 触发者 |

## 五、返工规则与契约演进

### 5.1 返工 vs 演进

| 维度 | 返工（rework） | 演进（evolution） |
|------|---------------|-----------------|
| 触发 | 质量门禁失败 | 探索模式中人类改变方向 |
| 性质 | 质量不达标（负面） | 创作发现（中性/正面） |
| 计数器 | rework_count++ | evolution_count++ |
| 有上限 | 3次 | 无上限 |
| 触发human_override | 超限且策略 fallback=wait_human 时是 | 否 |
| 上下文注入 | S06（返工反馈） | S07（遗忘系统筛选后的保留模式） |

### 5.2 返工触发条件

| 触发者 | 触发条件 | 返工类型 |
|--------|---------|---------|
| ES引擎 | 任一ES规则FAIL | 自动返工 |
| 策略裁决 | 低分且未超重写上限 | 自动重写 |
| 人类抽检 | 人类选择"返工" | 人工返工 |
| 发布引擎 | 发布失败且可重试 | 发布返工 |

### 5.3 返工处理

```
返工触发
    │
    ▼
rework_count += 1
    │
    ▼
记录 failure_context（返工原因）
    │
    ▼
检查 rework_count 与 strategy.max_rewrite
    │
    ├── ≤ strategy.max_rewrite
    │       │
    │       ▼
    │   contract_version += 1
    │   pipeline_status → drafting
    │   quality_status → pending
    │   注入 S06 返工反馈
    │
    └── > strategy.max_rewrite
            │
            ▼
        按 strategy.fallback_policy 执行
        wait_human 时 flags.human_override = true
```

### 5.4 人类决策选项

当 `human_override=True` 或任务进入 `waiting_human` 时，人类可以选择：

| 选项 | 后果 |
|------|------|
| 继续返工 | 重置 rework_count，允许继续自动返工 |
| 降级处理 | 跳过当前失败的质量检查，强制通过 |
| 废弃任务 | pipeline_status → abandoned |
| 修改契约 | 修改契约后重新开始（重置 rework_count） |
| 解封继续 | 记录解封理由，指定下一状态 |
| 召回发布物 | 对已发布对象进入 recall 流程 |
| 降权策略单元 | 降低当前策略单元自治等级 |
| 调整策略参数 | 通过黄灯协商修改阈值、权重、抽检率或发布动作 |

### 7A.3 Flags 叠加规则

| Flag | 可叠加在哪些 pipeline_status 上 | 阻断性 |
|------|-------------------------------|-------|
| `checking` | `reviewing`（quality_status 为 checking 状态时） | 不阻断，信息性 |
| `ai_working` | `drafting` | 不阻断，信息性 |
| `human_override` | `waiting_human`, `frozen`, `publish_failed` | **阻断**：自动流转停止 |
| `drift_alert` | `reviewing`, `drafting` | 不阻断，信息性 |

| `cognitive_disturbance` | 任意非终态 | 不阻断，触发复盘流程 |
| `evidence_gap` | `reviewing`, `approved` | **阻断自动发布**（`evidence_gap=true` 时不允许进入 `publishing`） |

### 7A.4 组合校验规则

状态机引擎在每次转换前应校验：

1. **目标组合必须在白名单中**
2. **`human_override=true` 时，只允许转到 `waiting_human`、`frozen`、`abandoned`**
3. **`frozen=true` 时，只允许人工解封（触发者必须为 `human`）**
4. **`evidence_gap=true` 时，`pipeline_status` 不得进入 `publishing`**
5. **`algorithm_noise=true` 时，不触发策略降权或红灯**

## 八、跨对象状态联动约束

以下规则为跨对象仲裁说明，实际执行由数据库约束、触发器和状态机引擎强制执行。

### 8.1 Artifact（产出物）→ PublicationPackage（发布包）联动

| 规则 | 约束类型 |
|------|----------|
| Artifact 进入 `sealed` 前，PublicationPackage 不得进入 `queued / submitting / published` | CK / 触发器 |
| Artifact 进入 `frozen` 后，同产出物的所有 active PublicationPackage 强制 `held` | 触发器 |
| Artifact 解封（`sealed` → `rework`）后，旧 PublicationPackage 作废为 `superseded`，必须重建 | 状态机引擎 |

### 8.2 PublicationPackage（发布包）→ QualitySnapshot（质量快照）联动

| 规则 | 约束类型 |
|------|----------|
| PublicationPackage 进入 `queued` 前必已绑定 QualitySnapshot 且 `qualified_status in ('qualified','high_quality')` | CK |
| PublicationPackage 进入 `queued` 前必须已有 RealPublishGateRun.gate_status='passed' | CK |
| ArtifactVersion、Rendition、标题、正文、封面、标签、平台、发布时间或 QualityPolicy 任一变化时原包作废 | 触发器 |

### 8.2a Artifact（产出物）↔ SubStudioExecutionTask（子片场执行任务）状态映射矩阵

```text
Artifact.status                  SubStudioExecutionTask.pipeline_status
─────────────────────────────────────────────────────────────────
planned / drafting               pending / contracting / drafting
assembled / gate_checking        reviewing（quality_status 在 es_checking/ses_checking/strategy_decision 时）
sealed                           approved（quality_status=passed）
packaged                         publishing（publish_status=publishing）
published                        published / completed
frozen                           frozen
rework（从 gate_checking 退回）  rework（pipeline_status=drafting）
recalled（sealed 后召回）       published（再进入 recall 流程或以 swallowed 终态归档）
```

跨表触发器 `trg_task_pipeline_artifact_status_sync` 强制执行关键锚点：
- Artifact 进入 `sealed` 前，SubStudioExecutionTask 必须先进入 `approved`
- SubStudioExecutionTask 进入 `publishing` 前，Artifact 必须先进入 `sealed`
- 任一侧进入 `frozen`，对侧必须在同一个事务内同步进入 `frozen` 或 `held`

### 8.3 发布失败、冻结、解封、召回链路

```text
发布失败：
  Artifact → sealed（保持不退回）
  PublicationPackage → failed
  PublicationAttempt → failed_final
  → 新包重��（新建 PublicationPackage + 重跑门禁）

冻结：
  Artifact → frozen
  PublicationPackage → held
  SubStudio → frozen
  → 等待人工解封

解封：
  Artifact → rework
  ArtifactVersion 递增
  旧 QualitySnapshot → superseded
  旧 PublicationPackage → superseded
  → 重建新包、重跑门禁、重新绑定 QualitySnapshot

召回：
  PublicationPackage → recalled
  Publication → withdrawn
  EvidenceClaim.falsification_status → challenged
  → 受影响的 Artifact 保持 sealed
  → 新包用新的 ArtifactVersion
```

### 8.4 发布重试约束

| 规则 | 约束类型 |
|------|----------|
| 同幂等键下不得存在未完成的 unknown 状态 attempt 同时创建新的 submitted attempt | CK / 触发器 |
| PublicationAttempt.unknown 时不允许自动重试真实发布，必须先执行 recover_status | 状态机引擎 |

## 十、RealPublishGate 单一可执行规格

真实发布门（RealPublishGate）是所有真实发布动作的唯一前置门。任何 `PublicationPackage` 进入真实提交前，必须生成 `RealPublishGateRun`，并由数据库约束或状态机引擎验证通过。

`RealPublishGate = passed` 当且仅当以下条件全部成立：

| 条件 | 必须值 |
|---|---|
| `run_mode` | `real` |
| `legacy_stage_rank` | `>= 3` |
| `source_pack_loading_decision.allow_production` | `true` |
| `strategy_unit_maturity` | `M3/M4`，或存在显式人类发布批准 |
| `delegation_policy.publish_allowed` | `true` |
| `quality_snapshot.qualified_status` | `qualified` / `high_quality` |
| `package_gate_status` | `passed` |
| `redline_status` | `none` |
| `source_boundary_status` | `clean` |
| `rollback_ready` | `true` |
| `idempotency_key` | 非空且唯一 |
| `human_override_required` | 若为 true，必须有关联 `HumanDecision` |

以下情况必须使 RealPublishGate 返回 `blocked`：`run_mode=shadow`、`legacy_stage_rank<3`、`simulation_only=true`、`source_pack_loading_level<SPL3`、`package_gate_status!=passed`、`redline_status!=none`、`source_boundary_status!=clean`、`rollback_ready=false`。

状态机约束：`PublicationPackage.status = queued/submitting` 前必须存在 `RealPublishGateRun.gate_status = passed`；人类按钮授权不能替代 RealPublishGate，只能成为 Gate 的输入证据之一。
