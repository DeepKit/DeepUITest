# 数据库与状态机

## 概述

本文定义 DB2 PostgreSQL 的字段契约、状态机流转规则和事务边界。这不是 SQL migration 文件——DDL 在工程阶段生成，本文是 DDL 的上游规格。

## 数据库总览

| 数据库 | 类型 | 职责 | 禁止 |
|---|---|---|---|
| DB1 | SQLite ConfigDB | DeepBase 框架配置、本地状态、密钥引用 | 业务表、生产任务、资产索引 |
| DB2 | PostgreSQL `DeepFramesData` | 项目、文档版本、任务、资产、质量门控、候选包 | API Key 明文、发布账号、运营数据 |
| DB3 | PostgreSQL | ArtifactOS 交换层、多机共享 | 客户端直连外部系统、支付/账号后端私有库 |

## 通用字段

所有业务主表默认包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT 或 UUID | 稳定主键，不混用语义 ID |
| `created_at` | TIMESTAMPTZ | 创建时间，UTC |
| `updated_at` | TIMESTAMPTZ | 最后更新时间，UTC |
| `created_by_job_id` | BIGINT NULL | 产出该记录的 job，人工导入时为空 |
| `schema_version` | VARCHAR(16) | payload 结构版本，如 `1.0.0` |
| `version_no` | INT | 同一逻辑对象的版本号，递增不可覆盖 |
| `parent_version_id` | BIGINT NULL | 返工或派生时指向上一个版本 |
| `status` | VARCHAR(24) | 见状态机定义 |
| `payload_json` | JSONB | 可扩展 payload，不能代替核心查询字段 |
| `extra_json` | JSONB | 低频扩展信息 |

### 索引策略

- 所有 `*_id` 字段建 B-tree 索引。
- `status` 字段建 B-tree 索引（高频查询条件）。
- `payload_json` 中的高频查询路径建 GIN 索引（如 `variant_kind`、`target_platform`）。
- `created_at` 建降序 B-tree 索引（时间范围查询）。
- 复合索引按实际查询模式在工程阶段建立。

### 字段版本策略

- `schema_version` 只升不降；解析 payload 前必须检查 `schema_version`。
- 新版本字段加到 `payload_json` 或 `extra_json`，不 ALTER 已有列。
- 只有跨版本不兼容时才递增 `schema_version` 主版本号。

### 资产引用保护机制

候选包通过 `source_trace` 引用了特定版本的资产（audio_manifest、video_ir 等）。清理策略执行 `ready → deleted` 时必须遵守以下保护规则：

1. **引用检测**：当 `deepframes_candidate_package` 的 `status = done` 且其 `source_trace` 中包含某个 `asset_id` 时，该资产不得被清理。
2. **`protected_until` 字段**：候选包导出时，将其引用的所有资产的 `protected_until` 设置为 `最大值（9999-12-31）`或显式过期时间。清理策略只删除 `protected_until < NOW()` 且无活跃候选包引用的资产。
3. **级联保护**：如果资产 A 引用了资产 B（如 video_ir 引用 audio_manifest），保护范围必须级联覆盖所有传递引用。
4. **显式解除**：用户删除候选包时，被引用资产的 `protected_until` 回退为 `NULL`，进入正常清理周期。

## 状态机

### 通用状态流转

所有业务任务注册显式状态流转，禁止随意更新状态字符串。

```text
pending -> running -> blocked_review -> running -> done
pending -> running -> failed
pending -> running -> skipped
running -> cancelled
blocked_review -> cancelled
blocked_review -> skipped      ← 人工接受降级/跳过
```

### 状态语义

| 状态 | 语义 |
|---|---|
| `pending` | 已创建，等待执行 |
| `running` | 正在执行 |
| `blocked_review` | 需要人工处理，不等于失败 |
| `done` | 成功完成 |
| `skipped` | 有意跳过（人工接受降级、放弃返工），记录原因但不视为成功或失败 |
| `failed` | 失败，可重试 |
| `cancelled` | 被取消 |

### `done` 完成类型

`done` 状态的 `payload_json` 中增加 `completion_type` 字段，区分不同完成语义：

| `completion_type` | 含义 |
|---|---|
| `full` | 全部 shot 成功完成 |
| `partial_degraded` | 部分 shot 走了降级方案，degraded 比例在 `payload_json.degraded_ratio` 中记录 |
| `partial_skipped` | 部分 shot 被跳过，跳过数量在 `payload_json.skipped_count` 中记录 |

### `blocked_review → running` 重入约束

从 `blocked_review` 回到 `running` 必须满足明确的前置条件。`payload_json` 中必须包含 `review_action` 字段：

| `review_action` | 含义 | 前置条件 |
|---|---|---|
| `rework` | 修改参数后重试 | 必须有至少一个字段被修改（如 prompt 参数、模型选择、shot 文本） |
| `force_retry` | 不修改参数直接重试 | 同一 `review_action: force_retry` 最多允许 2 次，超过后必须选择 `rework` 或 `override_accept` |
| `override_accept` | 人工强制接受当前结果 | 必须有 `reviewer_note` 非空 |

`blocked_review → skipped` 无需 `review_action`，但 `payload_json.skip_reason` 必须非空。

### 质量状态交互

- `warn` / 黄灯：记录并提醒，job 不变为 `blocked_review`，继续生产。
- `fail` / 红灯：job 进入 `blocked_review`，必须返工或人工终止。
- 断点续跑只处理 `pending`、`failed` 和可重试的 `blocked_review`，跳过 `done` 和 `skipped`。
- Job 级别聚合规则：当所有 shot 级 step 均为 `done` 或 `skipped` 时，job 整体可标记为 `done`（`completion_type` 由各 step 状态聚合得出）。

### 资产状态

| 状态 | 语义 |
|---|---|
| `temp` | 临时文件，尚未校验 |
| `ready` | 已校验，可被候选包引用 |
| `failed` | 校验失败或生成异常 |
| `deleted` | 已清理，不可引用 |

`temp -> ready`：校验通过后 atomic rename。`temp -> failed`：校验失败。`ready -> deleted`：清理策略执行。`ready` 不可回退到 `temp`。

### JobQueue 与业务表映射

DeepBase `TJobQueue` 只负责队列领取、去重、心跳和死任务回收；DeepFrames `deepframes_job` / `deepframes_job_step` 负责业务语义。两者通过 `job_queue_task_id` 和 `logical_key` 关联，不混用状态字段。

## 事务边界

### 单表写事务

插入或更新单个业务表记录使用单行事务。Delphi 主程序通过 FireDAC + PostgreSQL 执行。

### 跨表写事务

以下操作必须使用数据库事务确保一致性：

| 操作 | 涉及表 | 事务要求 |
|---|---|---|
| 候选包导出 | `candidate_package` + `asset` + `quality_gate_result` | 原子写入 |
| Job 完成登记 | `job` + `job_step` + `asset` | 原子写入 |
| 版本链更新 | document 表 + `accuracy_report` + `quality_gate_result` | 原子写入 |
| 资产状态变更 | `asset` + 引用该资产的 `job_step` | 原子更新 |

### Worker 结果收集事务

Worker 完成后，主程序读取 result manifest，在一个事务内：
1. 更新 `job_step.status` → `done` / `failed`。
2. 插入或更新 `asset` 记录。
3. 记录 metrics 到 `extra_json`。

如果事务失败，step 保持 `running`，heartbeat 超时后由死任务回收机制处理。

### 幂等性

所有写操作必须幂等：
- 使用 `logical_key` 去重。
- 重复提交同一 `logical_key` 不产生重复记录。
- 版本号递增不可覆盖。
