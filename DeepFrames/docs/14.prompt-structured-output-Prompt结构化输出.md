# Prompt 结构化输出

## 概述

DeepFrames 的 Agent 输出必须结构化可校验。本文定义从 LLM 原始输出到结构化 JSON 的标准化流水线：Extract / Normalize → Schema Validate → Repair / Retry。

## 三层策略

```
LLM 原始输出
  │
  ▼
┌───────────────────────────┐
│ 1. Extract / Normalize    │  从 raw output 提取 JSON，规范化格式
└─────────┬─────────────────┘
          │
          ▼
┌───────────────────────────┐
│ 2. Schema Validate        │  按预期 schema 校验字段和类型
└─────────┬─────────────────┘
          │
     校验通过？──否──▶ 3. Repair / Retry
          │                    │
       是 │                    ├─ 可修复 → Repair → 回到 2
          │                    └─ 不可修复 → Retry（换 prompt/参数）→ 回到 1
          ▼
   规范化 JSON 写入 DB2
```

### 1. Extract / Normalize

LLM 输出常见格式：

| 情况 | 示例 | 提取策略 |
|---|---|---|
| 纯 JSON | `{"shots": [...]}` | 直接解析 |
| Markdown 代码块 | ````json\n{...}\n```` | 提取代码块内容 |
| 前缀文本 + JSON | `这是结果：\n{...}` | 定位第一个 `{` 到最后一个 `}` |
| JSON 嵌套在对话中 | 多轮对话中间出现 JSON | 正则提取 JSON block |
| 空输出或拒绝回答 | `我无法完成` | 标记为提取失败 |

规范化步骤：

1. 去除 BOM、首尾空白。
2. 提取最外层 JSON 对象或数组。
3. 统一编码为 UTF-8。
4. 如果提取成功，记录 `normalized_json`；如果失败，记录 `validation_error`。

### 2. Schema Validate

每个 Agent 输出有对应的 JSON Schema（保存在 `deepframes_prompt_template` 的 `output_schema_json` 字段）。校验维度：

| 校验项 | 规则 |
|---|---|
| 必需字段 | 缺失关键字段（如 `shot_id`、`text`）→ 校验失败 |
| 类型匹配 | 字符串不能是数字，数组不能是对象 |
| 枚举值 | `variant_kind` 只允许 `main/experiment/platform/account` |
| 数值范围 | `score` 只允许 0-1 |
| 数组非空 | `shots` 数组不能为空 |
| 嵌套结构 | `text.style` 必须是对象 |

Schema 版本与 `prompt_template.version_no` 绑定，升级 schema 时递增版本号。

### 3. Repair / Retry

#### 可修复问题

| 问题 | 修复策略 |
|---|---|
| 缺失可选字段 | 填入默认值 |
| 字段类型轻微错误 | 尝试类型转换（如 `"42"` → `42`） |
| 多余字段 | 丢弃，记录到 `extra_json` |
| 数组内元素部分缺失 | 补全可推断的字段 |

修复限制：
- 最多修复 3 次（`repair_count` 上限）。
- 每次修复记录修复动作到 `repair_log`。
- 修复后必须重新通过 Schema Validate。

#### 不可修复问题 → Retry

| 问题 | 重试策略 |
|---|---|
| 核心字段完全缺失 | 重试 1 次，附加 hint 提醒模型补全 |
| JSON 结构损坏 | 重试 1 次，在 prompt 中强调输出格式 |
| 内容语义空洞（如所有 shot 文本相同） | 不重试，标为 fail |
| 连续 2 次重试仍失败 | 不再重试，标为 fail |

重试限制：
- 同一 `logical_key` 最多重试 2 次。
- 重试使用同一 prompt version 和 model binding。
- 重试 token 计入 `deepframes_prompt_run`。

## 记录要求

每次 Agent 调用完整记录到 `deepframes_prompt_run`：

| 字段 | 说明 |
|---|---|
| `raw_output` | LLM 原始输出，不截断 |
| `normalized_json` | 提取并规范化后的 JSON |
| `validation_error` | Schema 校验错误，null 表示通过 |
| `repair_count` | 修复尝试次数，0 表示一次通过 |
| `token_input` / `token_output` | token 消耗 |
| `latency_ms` | 总耗时（含提取、校验、修复） |

## 模板输出声明

每个 `deepframes_prompt_template` 必须声明输出结构：

```json
{
  "output_format": "json",
  "output_schema_json": {
    "type": "object",
    "required": ["shot_id", "text"],
    "properties": {
      "shot_id": { "type": "string" },
      "text": { "type": "string", "minLength": 1 }
    }
  },
  "extraction_hints": {
    "expect_code_block": true,
    "code_block_language": "json"
  }
}
```

`extraction_hints` 帮助 Extract 阶段选择正确的提取策略。

## 工程优先级

- **Phase 1**：fake provider 直接返回合法 JSON，跳过 Extract/Repair。
- **Phase 2**：接入 StepFun 后实现完整的 Extract / Normalize / Validate。
- **Phase 3**：基于 POC 失败样本调优 Repair 规则和重试策略。
