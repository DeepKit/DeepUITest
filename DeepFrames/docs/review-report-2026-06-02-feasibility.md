## 三专家共识问题

### 🔴 共识问题 1：Chromium 逐帧捕获的时序确定性是项目最大技术风险

**发现者**: 全栈集成工程师（主报）、Delphi/DeepBase 工程师（呼应）、生产管线工程师（呼应）

文档的 `timestamp-driven capture` 策略只解决了"在哪一帧截图"的问题，没有解决"CSS 动画如何精确跳转到目标时间点"的核心问题。浏览器是实时系统，CSS 动画绑定到实际时间，在负载下会跳帧。

Replit 在 2026 年 2 月发表了几乎完全相同的技术路线（HTML/CSS/JS → 浏览器帧捕获 → 视频编码），发现必须：
1. 猴子补丁 `performance.now()`、`Date.now()`、`requestAnimationFrame()` 虚拟化浏览器对时间的感知
2. 手动推进 CSS 动画到目标时间点（`seekCSSAnimations`）
3. 运行预热帧保持 Chrome 合成器不失效
4. 单次渲染任务（Chrome 消耗 GB 级 RAM，内存压力导致帧损坏）

**影响**: 如果不实现时间虚拟化，60 秒窗口偏差 ≤ 50ms 的目标几乎不可能达成，音视频同步会肉眼可感知。

**建议**:
- POC 最高优先级验证此问题
- 备选方案：考虑 Remotion 作为 v1.0 默认渲染后端（天然确定性渲染，每帧是独立 React 组件）
- HyperFrames 分块运行：每个 Chromium 会话只处理 300-500 帧（3-5 个 shot），会话间重启防止内存泄漏

### 🔴 共识问题 2：视觉一致性是产出质量的最大瓶颈

**发现者**: 生产管线工程师（主报）、全栈集成工程师（呼应）

三级策略（Reference image/img2img → prompt-only → human review）方向正确，但存在两个核心问题：

1. **StepFun img2img 能否保持跨 shot 风格一致**——`step-image-edit-2` 支持 img2img（已确认 API 存在），但"多张图保持一致画风"是图像编辑的难题，不是简单的 API 能力问题
2. **Style Keeper 的 embedding 余弦相似度精度不足**——中文短文本 Prompt 的 embedding 区分能力有限，"画风从水墨切换到写实"这种语义差异可能余弦相似度很高但视觉差异大

**影响**: 纯 Prompt 驱动的图像一致性上限约"中等偏下"。没有 ControlNet、IP-Adapter、LoRA 等技术手段，同一角色在不同 shot 中的外貌一致性"极低"。

**建议**:
- 视觉策略需要务实化：放弃"每 shot 一张 AI 生成图"的目标，改为"模板化布局 + 精选 AI 配图 + 字幕为主"
- Style Keeper 增加颜色直方图比对或 CLIP 空间比对等视觉层面度量
- 降级方案（纯色背景+字幕）在 B站环境下可接受度很低，需要重新考虑

### 🔴 共识问题 3：Shot 密度估算偏差导致视觉单调

**发现者**: 生产管线工程师

端到端实例（`11.e2e`）中的 `word_count: 126`，切了 9 个 shot。但文档说原文约 3800 字。3800 字按 TTS 语速约 15-16 分钟音频，按平均 5 秒/shot 需要 180-200 个 shot，不是 9-11 个。

如果 3800 字只切 9-11 个 shot，每个 shot 平均 345-420 字 = 85-105 秒静态画面——视觉上极其单调。即使按 60-80 个 shot（每 shot 10-20 秒），每个 shot 一张静态图持续 10-20 秒也是观感下限。

**影响**: 端到端实例有误导性，shot 数量估算需要修正。

**建议**:
- 在 `11.e2e` 中明确 9 个 shot 只覆盖 126 字节选，给出全文级别的数量估算
- 引入"视觉变化"策略：同一 shot 内做图片切换、缩放、平移等简单动画
- HyperFrames 的 HTML/CSS 架构天然支持 Ken Burns 效果，可以在不增加 shot 数量的情况下增加视觉变化

### 🟡 共识问题 4：开发路线图工作量被低估

**发现者**: 三位专家一致

| 阶段 | 文档估算 | 专家合理估算 | 低估程度 |
|---|---|---|---|
| Phase 3: Agent 生产链 | 4-6 周 | 8-12 周 | **显著**（Prompt 调优 + 结构化输出稳定化是迭代过程） |
| Phase 5: 视频生产线 | 5-8 周 | 10-16 周 | **显著**（HyperFrames worker 是独立的中型项目） |
| **Phase 1-6 总计** | **16-27 周** | **30-46 周（7-11 个月）** | **约 2 倍** |

**建议**:
- Phase 3 拆分为 3a（fake provider 链路固化）和 3b（StepFun 真实接入）
- Phase 5 拆分为 5a（静默预览，不依赖音频）和 5b（带声成片，依赖 Phase 4）
- Phase 3 和 Phase 4 可以部分并行
- Phase 5 的 HyperFrames worker 可以在 Phase 3 期间用 fake data 提前开发

### 🟡 共识问题 5：单次生产的 API 调用量和失败叠加

**发现者**: 全栈集成工程师（主报）

一篇 5000 字文章转 15 分钟视频，约需 932 次 API 调用（LLM 152 + TTS 150 + ASR 150 + Image 330），预计失败约 80 次。修复/重试机制能捕获大部分失败，但每次重试增加 token/API 成本。

**影响**: 每次完整端到端生产的净成功率约 60-70%，几乎所有生产都需要多次重试。

**建议**: 在成本/用量文档（`15.cost-usage`）中补充真实 API 调用量估算和 token 消耗预估。

## 各专家独有发现

### Delphi/DeepBase 工程师独有发现

| # | 严重度 | 发现 | 影响 |
|---|---|---|---|
| 1 | 🔴 | DeepBase.Speech `ITTSBackend` 设计为实时播放接口，不满足"批量文件生成 + 返回时长"的需求 | 需新增 `ITTSFileBackend` 接口，3-5 天 |
| 2 | 🔴 | DeepBase 没有 Image Edit（img2img）接口和 Embedding API 接口 | 需新增两个 adapter，8-12 天 |
| 3 | 🟡 | Delphi 没有 JSON Schema 校验库 | 需手写或引入第三方，增加 Phase 3 工作量 |
| 4 | 🟡 | 全局时间轴量化算法的浮点数精度问题——`round(start_sec * fps)` 在 27000 帧时可能累积 1-2 帧偏差 | 建议使用整数帧号运算，避免中间浮点数 |
| 5 | 🟡 | `TerminateProcess` 杀掉 Node.js worker 后，其子进程（Chromium）可能变成孤儿 | HyperFrames worker 必须自己管理 Chromium 生命周期 |
| 6 | 🟡 | 估算 Delphi 主程序代码量 22,000-35,000 行 | 一个人 7-11 个月 |

**关键洞察**: DeepBase 覆盖了 70-80% 的非业务需求，但 Speech（TTS 文件生成）、Image Edit、Embedding 三个接口有缺口，需要在对应 Phase 开始前补齐。

### 全栈集成工程师独有发现

| # | 严重度 | 发现 | 影响 |
|---|---|---|---|
| 1 | 🔴 | 15 分钟 30fps = 27,000 帧，单次 Chromium 会话可能泄漏 2-5 GB 内存 | 必须分块渲染，每 300-500 帧重启 Chromium |
| 2 | 🟡 | FFmpeg `loudnorm` 单次通过精度 ±1-2 LUFS，文档要求 ±1 LUFS 需要两次通过 | 需更新 `05.audio` |
| 3 | 🟡 | FFmpeg H.264 编码参数（profile/level/preset/GOP/B帧/像素格式）完全缺失 | 需补充到 `07.platform` |
| 4 | 🟡 | 帧序列中间存储：PNG 格式 85-140 GB，JPEG 格式 18-32 GB | 建议使用 JPEG 中间格式（对最终 H.264 编码视频影响可忽略） |
| 5 | 🟡 | 一次完整生产的磁盘占用（含中间文件）约 18-140 GB | 需要积极的清理策略 |
| 6 | 🟡 | 全部生产步骤都需要网络连接，离线时只能做 FFmpeg 编码和本地 QA | 可接受的限制 |

**关键洞察**: `step-image-edit-2` **确实支持 img2img**（API 端点 `POST /images/edits`，需 image + prompt），但跨 shot 风格一致性仍然是未验证的能力。

### 生产管线工程师独有发现

| # | 严重度 | 发现 | 影响 |
|---|---|---|---|
| 1 | 🔴 | 降级方案（纯色背景+字幕）在 B站环境下可接受度很低 | 需要重新设计降级方案，建议改为"模板化布局+字幕" |
| 2 | 🟡 | 15 分钟视频实际生产耗时 25-65 分钟（非文档估算的 19-35 分钟） | 文档估算未包含 Agent 推理和图像生成耗时 |
| 3 | 🟡 | Splitter 的 4-6 秒目标与实际不符——短对话 5-10 字无法拉到 4 秒以上，长描写 40-60 字自然超过 6 秒 | 弹性范围 3-8 秒比 4-6 秒更贴近实际 |
| 4 | 🟡 | QA Agent（deepseek-v4-pro）与 Worker（stepfun-flash-3.5）能力不对称会导致系统性低分 | 0.60 fail 阈值需要 POC 标定 |
| 5 | 🟡 | TTS emotion 只有 6 个离散值（calm/tense/sad/happy/angry/mysterious），无法覆盖叙事内容的细腻情感 | 可接受但需要 POC 验证 instruction 自由文本的补充效果 |

**关键洞察**: DeepFrames 产出的视频质量大约是 B站"小说推文"类视频的**中等水平**——"AI 配音 + AI 配图 + 字幕"级别。与手动制作的视频差距主要在视觉一致性和节奏感。

## 实施可行性判断

### 可行的部分（直接开工）

1. **Phase 1（桌面骨架）** — DeepBase 已有框架，主要是 DB2 migration + UI 布局，2-3 周
2. **Phase 2（文档链）** — 版本链、Repository、job 表，标准 CRUD + 状态机，3-4 周
3. **Phase 4（音频线）** — TTS + ASR + FFmpeg 拼接 + 响度标准化，技术最成熟，3-5 周
4. **Phase 6（候选包导出）** — 相对简单，2-3 周

### 需要验证才能投入的部分

1. **Phase 3（Agent 生产链）** — 依赖 StepFun LLM 的结构化输出能力
2. **Phase 5（视频生产线）** — 依赖 Chromium 帧捕获的时序确定性

### 推荐的 POC 计划（2-3 周，4 项并行）

| # | POC 项目 | 时间 | 通过标准 | 失败后方案 |
|---|---|---|---|---|
| 1 | Chromium 帧捕获 + 时间虚拟化 | 3-5 天 | 60 秒窗口音视频偏差 ≤ 50ms | 切换到 Remotion 作为 v1.0 默认后端 |
| 2 | stepfun-flash-3.5 结构化 JSON | 2-3 天 | 首次通过率 ≥ 80%（20 次调用） | 简化输出 schema 或升级到 Pro 模型 |
| 3 | step-image-edit-2 img2img 一致性 | 2-3 天 | 5 张编辑图中 ≥ 3 张风格基本一致 | 简化视觉策略为模板化布局 |
| 4 | StepFun TTS 对玄幻内容的 451 触发率 | 1-2 天 | 触发率 < 30%（5 篇文章） | 文本预处理 + 备选 TTS provider |

### 推荐的开发顺序调整

```
Phase 1 (骨架) + Phase 2 (文档链) — 5-7 周
                    ↓
              POC 验证（4 项并行）— 2-3 周
                    ↓
   ┌────────────────┴────────────────┐
   ↓                                  ↓
Phase 3 (Agent链)              Phase 4 (音频线)
8-12 周                         3-5 周（可提前开工）
   ↓                                  ↓
   └────────────────┬─────────────────┘
                    ↓
         Phase 5 (视频线) — 10-16 周
                    ↓
         Phase 6 (候选包) — 2-3 周
```

音频线可以提前开工：TTS/ASR 不依赖 Agent 链的完成，可以在 Phase 2 结束后直接开始。
