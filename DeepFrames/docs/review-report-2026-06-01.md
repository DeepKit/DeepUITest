## Expert 1: 系统架构师 — 评分 7/10

### 总体评价

DeepFrames 的架构在核心分解上表现出色。音视频双线独立、Video IR 中间表示、DB1/DB2/DB3 三层数据库边界、以及 `content_unit` 对 `chapter` 的抽象升级，都是经过深思熟虑的架构决策。文档链（source → script → accuracy → variant → shot → manifest/IR → package）提供了完整的可追溯性。与 ArtifactOS 通过 `integration.*` 表交换的边界契约清晰且可执行。

然而，系统在可扩展性、容错性和技术栈选择上存在几个根本性问题。

### 发现

#### CRITICAL

**C1. 单机架构无容错机制**
- **位置**: `01.arch` 战略基线、"使用规模假设"章节；`09.engineer` 任务编排
- **问题**: 整个系统设计为"单人单机桌面生产工具"。JobQueue、StatusMachine、所有状态均在本地 SQLite。如果机器在 30 分钟渲染过程中崩溃，所有中间状态丢失。文档未提及状态复制、故障转移或灾难恢复。
- **建议**: 至少为 DB2 增加自动备份策略；为长时间运行任务增加外部心跳/进度持久化到 DB2 而非仅内存；考虑为关键任务步骤增加"至少一次"投递保证。

**C2. Delphi VCL 作为唯一 UI 框架的战略风险**
- **位置**: `01.arch` DeepBase 集成基线；`09.engineer` 桌面 UI
- **问题**: VCL 是 Windows-only 的遗留技术。文档提及 FMX 作为"未来跨平台扩展"仅一句话带过，无具体计划。如果产品未来要销售（战略基线明确提到），Windows-only 会严重限制市场规模。且 Delphi 开发���池在缩小，长期维护成本上升。
- **建议**: 明确 FMX 迁移的时间表和触发条件；或至少将核心业务逻辑与 UI 框架彻底解耦，使未来换 UI 框架的成本可控。

#### HIGH

**H1. DeepBase 框架的全量耦合**
- **位置**: 全文档，尤其是 `01.arch` 和 `09.engineer`
- **问题**: 系统对 DeepBase 的依赖是全方位的——配置、密钥、日志、数据访问、任务编排、LLM/Speech 适配。这导致 bus factor 极高，代码不可移植。如果 DeepBase 框架停止维护或方向变更，DeepFrames 将无法独立生存。
- **建议**: 为核心接口（ILogger, IConfigStore, ISecretStore, IJobQueue）定义抽象层，使 DeepBase 成为可替换的实现。短期不替换，但架构上保留替换能力。

**H2. Worker 取消机制不可靠**
- **位置**: `09.engineer` Worker 协议 v0
- **问题**: 取消信号通过文件系统 (`cancel_file`) 传递。文件轮询在跨进程场景下不可靠——worker 可能在检查间隔内已经完成了大量不可逆工作。没有进程信号或 IPC 机制作为主要取消通道。
- **建议**: 增加进程信号（SIGTERM/CTRL-BREAK）作为主要取消通道；`cancel_file` 作为辅助信号；定义取消的 SLA（worker 必须在 N 秒内响应）。

**H3. logical_key 格式脆弱**
- **位置**: `09.engineer` job 与 JobQueue 映射
- **问题**: `logical_key` 格式如 `agent:{project_id}:{content_unit_id}:{variant_id}:{prompt_version}:{model_binding}` 将参数直接编码进 key。任何参数变更（如 prompt 版本升级）会改变 key，导致无法识别为"同一任务的新版本"。这破坏了幂等性的实际效用。
- **建议**: 分离"业务身份"（用于去重）和"参数快照"（用于版本追踪）。logical_key 只包含业务身份，参数变更通过 version 字段管理。

#### MEDIUM

**M1. TypeScript 接口与 Delphi 实现的文档断层**
- 文档中大量使用 TypeScript 接口描述设计，但实际系统是 Delphi。这会造成设计与实现之间的认知偏差，尤其当 TypeScript 的类型系统表达能力远超 Delphi 时。

**M2. 事件溯源缺失**
- 系统有复杂的状态机和审计需求（版本链、返工、质量门控），但没有采用事件溯源或 CQRS。当前设计依赖状态字段的直接更新，可能导致审计信息丢失。

#### LOW

**L1. 命名约定**
- `deepframes_` 表前缀冗余但可接受。建议在 DB2 内去掉前缀（因为 DB2 本身就是 DeepFrames 专用），只在 DB3 的 `integration.*` 中保留前缀以区分边界。

## Expert 2: AI/ML 管线工程师 — 评分 6/10

### 总体评价

Multi-Agent 架构（Splitter → Worker → Assembler → QA → Style Keeper）在概念上是合理的，prompt registry 版本化、few-shot 示例管理、以及降级机制都是良好的工程实践。使用强模型做 QA 把关是成本效率的明智选择。

但整个 Agent 管线缺乏系统性的评估框架，Style Keeper 的核心机制严重欠规范，Worker 的独立并行生成模式与跨镜头一致性需求之间存在根本矛盾。

### 发现

#### CRITICAL

**C1. 缺乏系统性评估框架**
- **位置**: `03.agent` Prompt Registry；`08.quality` QA Agent
- **问题**: 系统有 `deepframes_eval_result` 表但完全没有评估方法论。如何判断 Splitter 的切分质量？QA Agent 的评分准确率是多少？没有 golden dataset、没有基准测试、没有 A/B 对比框架。整个 Agent 管线的质量是未经验证的。
- **建议**: 在 Phase 3 之前建立评估框架：① 手工标注 20-50 篇文章的 golden shot_document；② 定义自动化指标（切分边界 F1、画面描述相关性 BLEU/CLIP score、情感标注准确率）；③ 每次 prompt 变更必须通过回归评估。

**C2. Style Keeper 核心机制严重欠规范**
- **位置**: `03.agent` Style Keeper Agent；`08.quality` Style Keeper
- **问题**: Style Keeper 被描述为"建立章节级风格指纹，逐 shot 比对偏差"，但以下关键问题无答案：风格指纹的具体数据结构是什么？用何种算法度量偏差（embedding cosine similarity？CLIP score？LLM-as-judge？）？偏差阈值如何确定？这是整个管线中最难的问题（跨独立生成的镜头保持视觉一致性），而设计文档对此几乎完全手摇。
- **建议**: 明确风格指纹的量化方案（建议使用 CLIP image embedding + 文本 embedding 的联合空间）。定义偏差度量的具体算法和阈值。考虑在 Phase 2 就做 Style Keeper 的概念验证，而不是等到 Phase 3。

#### HIGH

**H1. Worker 独立并行与跨镜头连贯性的矛盾**
- **位置**: `03.agent` Worker Agent
- **问题**: 每个 Worker 接收前后各 1 个 shot 的摘要，但独立生成自己的 shot。Worker A 不知道 Worker B 正在生成什么。`group_style` 只约束视觉参数，不约束叙事流。这意味着即使每个 shot 单独质量高，拼接后可能出现叙事断裂、视觉跳跃、或情感弧线不连贯。
- **建议**: 考虑两阶段生成：第一阶段所有 Worker 先输出"意图草图"（轻量级），第二阶段 Assembler 汇总后做全局一致性调整，再分发回 Worker 完成详细生成。或在 Worker 之间引入轻量级的共享上下文（如角色状态追踪）。

**H2. QA 评分阈值缺乏校准依据**
- **位置**: `08.quality` Gate 2
- **问题**: `score >= 0.80 = pass`、`0.60-0.80 = warn`、`< 0.60 = fail` 这些阈值完全是任意的。没有校准实验、没有与人工判断的相关性分析、没有 ROC 曲线。QA 的评分可能系统性地偏高或偏低，导致要么漏过问题，要么过度阻塞。
- **建议**: 在 Phase 3 之前进行校准研究：收集 100+ 个 shot 的 QA 评分和人工评分，计算评分者间信度（IRR），调整阈值使 F1 最大化。

**H3. TTS 451 自动改写风险**
- **位置**: `03.agent` 错误处理；`05.audio` 批量 TTS
- **问题**: TTS 451 内容审查触发时"自动改写文本重试 1 次"。自动改写可能引入事实错误或改变语义，而系统没有对改写后文本的准确性校验。这直接违反了"表达准确优先于传播效果"的战略原则。
- **建议**: 改写后文本必须经过原文对比校验（diff-based 或 QA Agent 快速检查），标记改写部分供人工复核。不允许静默改写。

#### MEDIUM

**M1. QA 回流重做范围不明确**
- QA 标记某个 shot 失败后，回流 Worker 重做。但重做后是否需要重新跑 Assembler？需要重新跑 QA？文档未明确。

**M2. 并行度缺乏基准**
- Worker 并行数 5-8、TTS 并行 5 路、图像生成 10 路并行——这些数字看起来合理但缺乏 API 延迟基准数据支撑。

#### LOW

**L1. prompt 缓存策略缺失**
- 未提及对 StepFun API 的 prompt 缓存利用，对于包含大量 system prompt 的 Agent 调用，这可能显著影响成本和延迟。

## Expert 3: 媒体制作工程师 — 评分 8/10

### 总体评价

DeepFrames 在音频/视频制作工程方面展现了扎实的专业功底。WAV/PCM 中间格式策略、EBU R128 响度标准化、全局时间轴量化算法、双时间戳坐标系、三种渲染模式解耦——这些都是生产级音视频系统的正确设计。60 秒滑动窗口 ≤50ms 的同步检查标准是专业广播级的要求。

但视觉质量保证、图像生成一致性、和字幕精度方面存在关键缺口。

### 发现

#### CRITICAL

**C1. 缺乏视觉感知质量指标**
- **位置**: `08.quality` Gate 3b；`04.video` 视频流水线
- **问题**: Gate 3b 检查空白帧、元素越界、字幕遮挡等结构化问题，但完全没有感知质量指标（PSNR, SSIM, VMAF）。一个视频可以通过所有结构化检查但仍然看起来糟糕——模糊的背景图、压缩伪影、色彩失真。对于声称"表达准确优先"的系统，缺少视觉质量保证是矛盾的。
- **建议**: 至少增加 SSIM 作为自动检查项（对比渲染输出与预期参考帧）。在 snapshot QA 中增加人工可读的质量评分维度。

**C2. AI 图像生成一致性无技术保障**
- **位置**: `04.video` 素材准备；`03.agent` Worker Agent visual 输出
- **问题**: 系统依赖 `group_style` 字符串 prompt 来保证同组镜头的视觉一致性。但 AI 图像生成器（StepFun image model）对相同 prompt 的不同调用会产生不同结果。没有 img2img、ControlNet、reference image、seed 固定、或 style transfer 等一致性技术。`group_style` 是 prompt 级约束，不是视觉一致性保证。
- **建议**: 为每个 group 生成一张"风格参考图"作为 img2img 的 init_image；或使用固定 seed + 渐进式 prompt 变化；或在 Phase 5 之前评估 ControlNet/IP-Adapter 等一致性方案的可行性。

#### HIGH

**H1. ASR 逐字时间戳精度不足以支撑卡拉 OK 字幕**
- **位置**: `05.audio` ASR 逐字时间戳；`04.video` 音频-视频时间轴同步
- **问题**: ASR 逐字时间戳的固有噪声约 ±50-100ms/词。直接用于卡拉 OK 字幕会导致可见的抖动。文档未提及任何平滑或后处理策略。
- **建议**: 对 ASR 时间戳施加平滑约束（如保证相邻词之间无时间倒退、词间间隔不低于音素最小持续时长）。或使用 forced alignment（强制对齐）技术替代纯 ASR 时间戳。

**H2. 性能估算偏乐观**
- **位置**: `04.video` 性能估算
- **问题**: 5 分钟视频预估 10-18 分钟总耗时。按 4-6 秒/shot 计算约 50-75 个 shot，每个 shot 2-3 个比例的背景图 = 100-225 张图。StepFun 图像 API 限流 60 req/min，仅图像生成就需要 2-4 分钟。加上渲染 8-15 分钟，总计 10-19 分钟——在理想情况下勉强可行，但未计入 retry、API 限流退避、ASR 回传等额外耗时。实际耗时可能接近 20-30 分钟。
- **建议**: 将性能估算更新为包含 p50/p95/p99 的分位数估算，而非单点估计。在 Phase 5 进行实际基准测试。

**H3. 视频编码专利风险未评估**
- **位置**: `04.video` 多版本渲染（H.264）；`01.arch` 关键约束
- **问题**: H.264 编码涉及专利授权（MPEG LA）。文档提到"Remotion 商业许可需复核"但未提及 H.264 专利。对于商业产品这是必须提前解决的法律问题。
- **建议**: 增加 H.264/H.265 专利评估到 Phase 5 前置条件；评估 VP9/AV1 作为免专利替代方案。

#### MEDIUM

**M1. 转场类型有限**
- 仅支持 fade/cut/slide/zoom 四种转场。对于特定内容类型（如对话场景的硬切节奏、动作场景的快速摇镜），可能需要更多转场选项。

**M2. FFmpeg 版本未锁定**
- FFmpeg 作为外部工具但无版本兼容性矩阵。不同 FFmpeg 版本的编码器行为和参数可能不同，导致渲染结果不可复现。

**M3. 视觉演进路径不清晰**
- v1 采用"简单表意"视觉路线是正确的，但架构未说明如何从简单背景图升级到更丰富的视觉表达（如角色动画、场景合成、粒子效果）。

## Expert 4: 平台/DevOps 工程师 — 评分 5/10

### 总体评价

这是五个维度中评分最低的。DeepFrames 在 DevOps 基础设施方面几乎是空白。文档描述了"做什么"（构建、测试、部署）但没有"怎么做"。对于一个包含 Delphi + Node.js + FFmpeg + Chromium 四个技术栈的项目，缺乏 CI/CD、监控、资源管理是严重的工程风险。

### 发现

#### CRITICAL

**C1. 完全没有 CI/CD 管线**
- **位置**: `09.engineer` 测试策略；`10.dev-roadmap` 全阶段
- **问题**: 项目包含 Delphi 编译、Node.js worker 构建、数据库 migration、DUnitX 测试、集成测试。测试策略提到 PowerShell 脚本但无 CI 系统集成（GitHub Actions、Jenkins 等）。没有自动化构建、没有自动化测试门禁、没有制品管理。
- **建议**: 在 Phase 1 就建立 CI 管线：① Delphi 编译 + DUnitX 单元测试；② Node.js worker lint + 单元测试；③ DB migration 干运行；④ 制品归档。

**C2. 零可观测性设计**
- **位置**: `09.engineer` 日志与诊断；`01.arch` DeepBase 集成基线
- **问题**: 系统依赖 DeepBase.Logging 做日志，但完全没有 metrics、tracing、alerting。30 分钟渲染任务在后台运行时，如果性能下降或卡住，用户没有任何途径知道。Worker heartbeat 仅用于进程存活检测，不用于性能监控。
- **建议**: 至少增加：① 任务级耗时 metrics（p50/p95/p99）；② API 调用延迟和错误率；③ 资源使用（CPU/内存/磁盘）；④ 任务状态变更的事件通知。

**C3. SQLite 并发写入冲突风险**
- **位置**: `09.engineer` DB2 核心表；`03.agent` 并行 Worker
- **问题**: DB2 使用 SQLite，但系统设计了大量并行写入场景——5-8 个 Worker 并行写入 job_step，10 路并行图像生成写入 asset，TTS 并行写入。SQLite 在 WAL 模式下支持并发读但写是串行的。高并发写入会导致频繁的 SQLITE_BUSY 和性能退化。
- **建议**: 评估 SQLite 在目标并发写入负载下的表现。如果 SQLITE_BUSY 频繁出现，考虑：① 写入批量化；② 内存队列 + 异步批量写入；③ 或为 DB2 使用 PostgreSQL（即使在单机场景下）。

#### HIGH

**H1. Worker 生命周期管理不完整**
- **位置**: `09.engineer` Worker 协议 v0
- **问题**: "Delphi 主程序启动、监控、取消和收集结果"——但如何处理 worker 崩溃？僵尸进程？Chromium 内存泄漏？长时间运行后 worker 性能退化？没有健康检查、没有自动重启策略、没有资源泄漏检测。
- **建议**: 增加 worker 健康检查端点（非仅 heartbeat）；定义崩溃后的重启策略（最大重试次数、退避间隔）；增加 Chromium worker 的定期重启机制（处理内存泄漏）。

**H2. 缺乏系统级资源管理**
- **位置**: `04.video` 性能估算；`09.engineer` Worker 协议
- **问题**: Chromium 渲染是内存密集型（单个实例可能占用 500MB-2GB），FFmpeg 编码是 CPU 密集型。文档提到 `max_memory_mb` 和 `max_parallelism` 但没有全局资源预算管理。如果用户同时运行多个渲染任务，系统可能耗尽内存导致 OS 级 OOM。
- **建议**: 实现全局资源管理器：启动前检查可用内存/CPU；为每类 worker 定义资源配额；渲染任务排队等待资源，而非直接启动。

**H3. 数据库备份策略缺失**
- **位置**: `09.engineer` 运行目录与数据库
- **问题**: DB2 包含所有业务数据（项目、文档版本、任务、资产、质量门控），但没有备份策略。SQLite 文件损坏（如写入时断电）可能导致全部数据丢失。
- **建议**: 至少实现：① 定期自动备份 DB2 到独立目录；② 关键操作前（如 migration）强制备份；③ 备份文件保留策略。

#### MEDIUM

**M1. Migration 工具和回滚策略未明确**
- 文档说"DB2 schema 变更必须走 migration"但未指定 migration 工具（自定义 Delphi 框架？Flyway？）。也未说明 migration 失败时如何回滚。

## Expert 5: 产品/UX 策略师 — 评分 7/10

### 总体评价

DeepFrames 的战略基线是这份文档中最出色的部分之一——清晰、诚实、有原则。"表达准确优先于传播效果"、"自用版优先，商业化后置"、"不按 MVP 砍功能"——这些决策在技术文档中罕见地明确。质量门控的默认策略（全自动，红灯停，黄灯提醒）也是对用户注意力的尊重。

但产品设计缺乏用户验证，UI 设计停留在 IDE 布局层面，且"不做 MVP"的策略在没有用户反馈循环的情况下存在风险。

### 发现

#### CRITICAL

**C1. 零用户研究或工作流验证**
- **位置**: `01.arch` 战略基线；`10.dev-roadmap` 全阶段
- **问题**: 整个设计基于作者自身的用例（小说→音频/B站视频）。没有证据表明目标工作流匹配实际内容创作者的需求。文章→音频→视频的假设链路是否适合其他类型的内容（知识分享、教程、新闻评论）？"准确优先、简单表意"的视觉策略是否被目标受众接受？这些都没有验证。
- **建议**: 在 Phase 2 完成后，用最小可用链路（文章→shot_document→音频）做 3-5 个真实案例的 walkthrough 并收集外部反馈。这不违反"不砍功能"原则——完整架构保留，但验证假设。

**C2. "不做 MVP"策略在无反馈循环下的风险**
- **位置**: `10.dev-roadmap` 开发路线图；`01.arch` 战略基线
- **问题**: Phase 1-7 是一个漫长的开发路线，在 Phase 5（B站视频）完成之前没有任何可交付的用户价值。延迟所有用户反馈直到完整系统建成，风险是花了 6 个 phase 构建了错误的东西。战略基线说"功能可按依赖顺序实现"，但并未定义中间反馈点。
- **建议**: 在每个 Phase 结束时定义可演示的中间产物和反馈收集点。Phase 1（骨架）→ 内部架构评审；Phase 2（文档链）→ 导入真实文章验证；Phase 3（Agent）→ 人工评审 shot_document 质量；Phase 4（音频）→ 交付音频候选包给真实听众试听。

#### HIGH

**H1. UI 设计是 IDE 布局而非创作工具**
- **位置**: `09.engineer` 桌面 UI
- **问题**: 描述的 UI 布局（左侧树、中央预览、右侧属性、底部任务）是通用 IDE 布局。对于内容创作工具，核心 UX 应该是：时间轴视图（shot-by-shot 预览+波形）、对比视图（主版本 vs 实验版本）、问题导航（按严重程度排序的质量问题列表）、一键修复入口。当前设计围绕数据结构组织，而非围绕创作流程组织。
- **建议**: 在 Phase 1 就定义核心用户旅程地图：① 导入→审核→确认的线性流程；② 发现问题→定位 shot→编辑→重新渲染的修复流程；③ 多版本对比→选择→导出的决策流程。UI 布局应服务于这些流程。

**H2. 零协作能力**
- **位置**: `01.arch` 使用规模假设；`09.engineer` 全文档
- **问题**: 系统设计为严格的单人单机。但即使是"自用"，内容制作通常涉及他人审阅（编辑、原作者、运营）。作者制作完音频/视频后如何分享给他人审阅？审阅意见如何回流到系统？当前设计完全排除了这个场景。
- **建议**: 至少增加候选包的审阅模式：导出包含质量快照的审阅包 → 审阅者标注问题 → 回流到 DeepFrames 的 quality_gate_result 表。不需要实时协作，但需要异步审阅循环。

**H3. 黄灯累积效应被忽略**
- **位置**: `08.quality` 控制点策略
- **问题**: 默认策略"黄灯只提醒并继续"。但如果有 50 个 shot 都有黄灯警告，系统仍然静默继续。用户可能忽略大量黄灯，导致最终输出质量下降。没有累积阈值或升级机制。
- **建议**: 增加黄灯累积阈值：当黄灯数量超过 shot 总数的 N%（如 30%）时，自动升级为红灯阻塞。或按黄灯类型（风格不一致、时长偏差、情感不匹配）分组展示，帮助用户批量处理。

#### MEDIUM

**M1. 多版本对比 UX 缺失**
- 文档提到主版本+实验版本（默认 1+1），但未描述如何比较和选择版本。这需要并排预览、diff 高亮、质量评分对比等 UX 支持。

**M2. 撤销/重做未提及**
- 片段级编辑（`deepframes edit --shot`）是一个强大的功能，但没有撤销/重做机制。用户改错了一个 shot 的参数后如何恢复？

#### LOW

**L1. 预设体系的国际化局限**
- 内置预设（xuanhuan, dushi, lishi 等）完全基于中国网文分类。如果产品未来面向国际市场，需要重新设计预设体系。

### 设计优势（值得保留和推广）

1. **音视频双线独立架构** — 这是整个设计的核心亮点，解耦干净，边界清晰
2. **Video IR 中间表示** — 后端无关的渲染契约，隔离了渲染技术变更
3. **文档链可追溯性** — 从 source 到 package 的完整版本链，支持返工和回滚

5. **全局时间轴量化算法** — 防止帧累计漂移的正确方案
6. **质量门控的分级策略** — pass/warn/fail 三级 + 可配置人工控制点，灵活且实用
7. **DB1/DB2/DB3 三层数据库边界** — 配置、业务、集成的清晰分离
8. **与 ArtifactOS 的 integration.* 契约** — 系统间边界设计典范
9. **候选包概念** — 将生产与发布解耦的良好抽象
10. **降级策略** — 保证时间轴完整的实用兜底机制
