# 工程化基础

## 概述

DeepFrames 的工程基础设施以 **Delphi VCL 桌面主程序 + DeepBase** 为中心。本文定义项目结构、数据库分层、配置与密钥、任务状态、外部 worker、测试和开发门槛。

DeepFrames 不是 Web 控制台，不以 TypeScript/Node 作为主程序。Node、Chromium、HyperFrames、Remotion、FFmpeg 可以存在，但它们只是被桌面主程序调度的外部 worker 或工具进程。

## 工程原则

- 不按“砍功能做 MVP”的方式设计；功能可以按依赖顺序慢慢实现，但数据契约和架构边界从一开始按完整软件设计。
- 主控、状态、配置、日志、密钥、任务编排、人工审核全部接入 DeepBase。
- DeepFrames 只负责生产候选包，不负责发布、运营、排期、账号、数据复盘。
- 业务数据不得混入 DB1 ConfigDB；DB1 只放 DeepBase 框架配置和本地状态。
- JSON 文件只作为资产快照、worker payload 或导出格式；断点续跑、任务状态和质量门控以数据库为准。
- 渲染和媒体处理不强行 Delphi 化；复杂媒体能力通过可替换 worker 执行。

## 当前战略决策

| 决策项 | 当前选择 | 架构影响 |
|---|---|---|
| 第一条完整生产链路 | 文章 -> 音频候选包 + B站视频候选包 | 默认平台规格、候选包 schema、验收样例先围绕 B站和音频输出落地 |
| 视频表达路线 | 简单表意优先 | 视觉资产先保证语义准确、字幕清晰和节奏稳定，不把强插画一致性作为首阶段阻塞项 |
| BGM | 默认不加 | audio manifest 记录 BGM 关闭状态；混音接口保留，但第一条链路不要求音乐库 |
| 渲染后端 | HyperFrames 优先，Remotion 后续 | Video IR 仍保持后端无关；首个 worker 和验收用 HyperFrames |
| 控制点策略 | 多个控制点可由参数设定，默认全自动跑到候选包 | 只有红灯停止；黄灯记录并提醒，不阻塞继续生产 |
| 商业化 | 后置 | 不设计收费体系、license server、多租户、云账户；用量记录作为基础保留 |

| `DeepBasePersistence.dpk` | 必选 | FireDAC storage、DoQry、DB Factory、migrations、JobQueue、StatusMachine |
| `DeepBaseFeatures.dpk` | 必选 | LLM、Speech、网络 transport、AutoUpdate 等可选能力入口 |
| `DeepBaseVCL.dpk` | 必选 | VCL 适配、DeepShell、FormState Helper |

## 启动模板

```delphi
program DeepFrames;

uses
  Vcl.Forms,
  DeepBase.Manager,
  DeepBase.Persistence.Manager.FireDAC,
  DeepFrames.App.Bootstrap,
  DeepFrames.UI.MainForm in 'UI\DeepFrames.UI.MainForm.pas' {MainForm};

begin
  Application.Initialize;
  Application.MainFormOnTaskbar := True;

  DeepBase.InitializeOrRaise;
  try
    TDeepFramesBootstrap.RegisterServices;
    Application.CreateForm(TMainForm, MainForm);
    DeepBase.FireReadyCallbacks;
    Application.Run;
  finally
    TDeepFramesBootstrap.Shutdown;
    DeepBase.Finalize;
  end;
end.
```

## 运行目录与数据库

DeepFrames 使用 DeepBase 标准 `root.txt + DB1 + DB2 + DB3` 布局。

```text
{RootPath}/
├── DeepFramesConfig.db                # DB1，DeepBase ConfigDB
├── assets/
├── output/
├── cache/
├── logs/
└── workers/
```

| 数据库 | 位置 | 内容 | 禁止 |
|---|---|---|---|
| DB1 | `{RootPath}\DeepFramesConfig.db` | DeepBase Settings、Logs、I18n、FormStates、MRU、Hotkeys、LLM 配置、Secrets 引用 | DeepFrames 业务表、生产任务、资产索引 |
| DB2 | PostgreSQL `DeepFramesData` | 项目、文档版本、任务、资产、质量门控、候选包 | API Key 明文、发布账号、运营数据 |
| DB3 | PostgreSQL | ArtifactOS 交换层、多机共享、团队协作 | 客户端直连 DB4、支付/账号后端私有库 |

DB2 PostgreSQL 连接参数写入 DB1：

```text
DB2.Type = PostgreSQL
DB2.Host = 127.0.0.1
DB2.Port = 5432
DB2.Database = DeepFramesData
DB2.User = deepframes
DB2.PasswordSecretRef = secret://deepframes/db2
```

## 配置与密钥

优先级：

```text
代码默认值 < DeepBase.Config < 本次任务参数
```

规则：

- 不使用 `.env`、INI、Registry 或散落 JSON 保存配置。
- StepFun、图像、语音、worker token 等密钥统一走 `DeepBase.Security.SaveSecret/LoadSecret`。
- 普通业务配置写入 DB1 `Settings`，例如并发、默认平台、输出目录、质量门控策略。
- 平台规格、模板、音色、prompt、生产配方等长期业务配置写入 DB2 业务表。
- 命令参数只影响当前任务，不自动回写为全局配置。

### 生产控制点配置

控制点由 DeepBase.Config 保存默认值，并允许单次 job 参数覆盖。

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `Gate1.HumanStop` | false | 结构校验后是否等待人工确认 |
| `Gate2.HumanStop` | false | Agent 输出后是否等待人工确认 |
| `Gate3a.HumanStop` | false | 音频成品校验后是否等待人工确认 |
| `Gate3b.HumanStop` | false | 视频成品校验后是否等待人工确认 |
| `Package.HumanStopBeforeExport` | false | 候选包导出前是否等待人工确认 |
| `WarnPolicy` | `continue_with_notice` | 黄灯只提醒并继续 |
| `FailPolicy` | `stop_for_review` | 红灯停止并进入人工处理 |

默认生产模式是全自动跑到候选包，只有红灯停止，黄灯只提醒。需要人工把关时，在任务参数或全局设置中打开对应控制点。

### 运维与并发配置

借鉴 Y2A-Auto 的运维与分离限流设计，适配 DeepFrames 的桌面单机生产规模。配置写入 DB1 `Settings`，允许单次 job 参数覆盖。

#### 运维配置

| 配置项 | 默认 | 说明 |
|---|---|---|
| `FFMPEG_LOCATION` | 空 | 自定义 FFmpeg 路径，空则用项目内 `ffmpeg/` |
| `FFMPEG_AUTO_DOWNLOAD` | true | Windows 缺失时自动补齐 FFmpeg |
| `LOG_CLEANUP_ENABLED` | true | 日志自动清理 |
| `LOG_CLEANUP_HOURS` | 168 | 日志保留时长（小时） |
| `LOG_CLEANUP_INTERVAL` | 24 | 清理扫描间隔（小时） |
| `DOWNLOAD_CLEANUP_ENABLED` | true | 下载/中间资产自动清理 |
| `DOWNLOAD_CLEANUP_HOURS` | 168 | 中间资产保留时长（小时） |
| `DOWNLOAD_CLEANUP_INTERVAL` | 24 | 清理扫描间隔（小时） |

`DOWNLOAD_CLEANUP_*` 与 `06.dist` 的 **102C 策略**衔接：清理只作用于 C3（可复现中间资产）与 C4（临时/失败资产），C1/C2 受保护白名单保护，不被这些参数清理。清理扫描由 DeepBase Scheduler 调度。

#### 下载配置（`external_video_import` adapter 专用）

yt-dlp 作为外部工具，与 FFmpeg 同级管理（项目内 `yt-dlp` 二进制或自动补齐）。下载配置服务于 `external_video_import` adapter（见 `01.arch`），用于导入自有/授权外部视频供文案/配音分析与再生产。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `YOUTUBE_DOWNLOAD_THREADS` | 4 | yt-dlp 下载线程数 |
| `YOUTUBE_THROTTLED_RATE` | 空 | 下载限速（如 `5M`），空则不限速 |
| `YOUTUBE_PROXY_ENABLED` | false | 是否启用下载代理 |
| `YOUTUBE_PROXY_URL` | 空 | 代理地址（`http://host:port` 或 `socks5://host:port`） |
| `DOWNLOAD_DIR` | `downloads/` | 下载产物目录（见运行目录） |

- 下载并发纳入 `MAX_CONCURRENT_TASKS`，不单列——搬运任务是完整生产任务，下载是其 step，与 TTS/渲染/转码共享生产并发额度。
- 下载产物落 `downloads/`，ASR 转写后按 102C 策略清理（C3 中间资产）。
- yt-dlp 全站支持（不止 YouTube），本地文件直接读取不走 yt-dlp。

#### 并发分离限流

生产任务与上传是两类资源占用差异极大的工作，**两条限流独立**，互不挤占：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `MAX_CONCURRENT_TASKS` | 2 | 生产任务（Agent / TTS / 渲染 / 转码）最大并发 |
| `MAX_CONCURRENT_UPLOADS` | 1 | 平台上传最大并发 |

借鉴 Y2A 的「下载/上传分离限流」思路：上传通常受平台限速与登录态约束，与生产并发解耦，避免上传阻塞生产或反向拖累。

#### 内存压力降并发

单机生产时内存是硬约束。`MAX_CONCURRENT_TASKS` 是上限，运行时按内存压力**自动降并发**：

- 监控本机内存占用百分比（`_get_memory_usage_percent`）。
- 超过阈值（`_should_reduce_concurrency`，默认 85%）时，新任务排队等待，不立即抢占，直到内存回落。
- 降并发事件写入日志与用量记录，便于调参。

此机制保证桌面主程序在跑大视频渲染时不把整机打满，影响用户其他操作��

## 领域文档链

DeepFrames 不直接从文章生成镜头，必须保留中间语义层，便于复核、返工和多版本生产。

```text
source_document
  -> script_document
  -> accuracy_report
  -> variant_document
  -> shot_document
  -> audio_manifest / video_ir
  -> candidate_package
```

| 文档 | 作用 | 典型内容 |
|---|---|---|
| `source_document` | 输入原文和来源快照 | Markdown、网页正文、转录稿、手工输入 |
| `script_document` | 可生产脚本 | 段落、旁白、引用、术语、表达约束 |
| `accuracy_report` | 脚本级准确性核对 | `build_script` 阶段核对 `script_document` 是否忠实于来源，记录遗漏、歪曲、证据引用和人工意见；Agent 输出后的 Gate 2 结果另写 `deepframes_quality_gate_result` |
| `variant_document` | 多版本表达 | 主版本、实验版本、平台版本、账号定位版本 |
| `shot_document` | 音视频共享镜头契约 | 文本、音频指令、视觉意图、资产引用 |
| `audio_manifest` | 音频线输出快照 | WAV/PCM 中间文件、MP3/AAC 成品、timestamps、duration |
| `video_ir` | 视频线稳定契约 | 场景、时间轴、布局、安全区、模板、音轨引用 |
| `candidate_package` | 可交付候选包 | 文件路径、封面、元数据、质量快照、平台规格 |

`content_unit` 是底层生产单位。`chapter` 是首个文章工作流的显示名称，不是数据库和架构的唯一模型。

## DB2 migration v0 字段契约

DB2 第一版 migration 必须先落地这些字段，避免 UI、Workflow、Agent 和 worker 各自猜数据结构。

### 通用字段

所有业务主表默认包含：

| 字段 | 说明 |
|---|---|
| `id` | 稳定主键，PostgreSQL 使用 UUID 或明确的 BIGINT 主键，不能混用语义 ID |
| `created_at` / `updated_at` | TIMESTAMPTZ，统一使用 UTC；UI 层按本地时区显示 |
| `created_by_job_id` | 产出该记录的 job，可为空表示人工导入或初始化 |
| `schema_version` | payload 或文档结构版本 |
| `version_no` | 同一逻辑对象的版本号，递增不可覆盖 |
| `parent_version_id` | 返工、派生、平台改写时指向上一版本 |
| `status` | `pending/running/blocked_review/done/skipped/failed/cancelled` |
| `payload_json` | 可扩展 payload，不能代替核心查询字段 |
| `extra_json` | 低频扩展信息 |

### content_unit

| 字段 | 说明 |
|---|---|
| `content_unit_id` | 稳定业务 ID |
| `project_id` | 所属项目 |
| `unit_type` | `chapter/topic/segment/platform_variant/account_variant` |
| `parent_unit_id` | 层级父节点 |
| `derived_from_unit_id` | 派生来源，例如平台浓缩版来自原章节 |
| `display_label` | UI 显示名，如“第 1 章” |
| `order_index` | 同一父节点下排序 |
| `source_range_json` | 原文段落、字符范围、时间码或引用范围 |
| `target_duration_sec` | 目标时长，默认 900，作为生产策略门控 |
| `platform_scope_json` | 目标平台或账号定位约束 |

底层统一用 `content_unit`；首个文章工作流的 UI 可以继续显示“章节”。

### document 表

`source_document`、`script_document`、`variant_document`、`shot_document` 使用同一版本策略：

| 字段 | 说明 |
|---|---|
| `document_id` | 文档版本 ID |
| `project_id` / `content_unit_id` | 所属范围 |
| `document_kind` | source/script/variant/shot |
| `version_no` | 不可覆盖版本号 |
| `parent_document_id` | 返工或派生来源 |
| `source_document_id` | 对应原文版本 |
| `prompt_template_id` / `prompt_version_no` | 生成该文档使用的 prompt |
| `model_binding_id` | 使用的模型绑定 |
| `quality_summary_json` | gate 摘要 |
| `payload_json` | 文档主体 |
| `content_hash` | payload hash，用于去重和复现 |

`accuracy_report` 必须至少包含：`source_document_id`、`script_document_id`、`coverage_score`、`distortion_score`、`result`、`issues_json`、`human_review_status`、`reviewer_note`。

`variant_document` 必须至少包含：`variant_kind`（`main/experiment/platform/account`）、`variant_label`、`target_platform`、`account_profile`、`parent_variant_id`、`expression_policy_json`、`payload_json`。

`candidate_package` 必须至少包含：`package_id`、`project_id`、`content_unit_id`、`variant_document_id`、`target_platform`、`delivery_type`、`manifest_asset_id`、`cover_asset_id`、`metadata_json`、`quality_snapshot_json`、`export_status`、`output_root_uri`。

### asset 表

| 字段 | 说明 |
|---|---|
| `asset_id` | 稳定资产 ID |
| `asset_type` | source/audio/video/image/subtitle/manifest/snapshot/package |
| `uri` | 相对 RootPath 或 asset store 的 URI |
| `sha256` | 文件校验 |
| `byte_size` | 文件大小 |
| `mime_type` | MIME |
| `duration_sec` | 音视频时长，可为空 |
| `sample_rate` / `channels` / `codec` | 音视频技术参数 |
| `width` / `height` / `fps` / `frame_count` | 视频技术参数 |
| `producer` / `producer_version` | 生成者和版本 |
| `anchor_asset_id` / `reference_asset_id` | img2img anchor 或参考图资产 |
| `image_generation_mode` | img2img/text2img/prompt_only |
| `retention_class` | 102C 分类：C1/C2/C3/C4 |
| `protected_until` | 引用保护截止时间 |
| `cleanup_eligible_at` | 最早可清理时间 |
| `status` | temp/ready/failed/deleted |

资产写入必须先进入临时路径，校验通过后 atomic rename 或登记为 `ready`。失败的 partial asset 不允许被候选包引用。

### job 与 JobQueue 映射

DeepBase `TJobQueue` 只负责队列领取、去重、心跳和死任务回收；DeepFrames `deepframes_job` / `deepframes_job_step` 负责业务语义和 UI 展示。两者通过 `job_queue_task_id` 和 `logical_key` 关联，不混用状态字段。

`logical_key` 必须由业务输入确定，例如：

```text
preprocess:{project_id}:{content_unit_id}:{source_document_id}:{script_policy_hash}
agent:{project_id}:{content_unit_id}:{variant_id}:{prompt_version}:{model_binding}
audio:{shot_document_id}:{voice_profile_version}:{audio_policy_hash}
video:{shot_document_id}:{platform}:{render_backend}:{template_version}:{audio_manifest_id}
package:{content_unit_id}:{platform}:{candidate_package_profile}
```

## Worker 协议 v0

外部 worker 的请求、进度和结果必须版本化。Delphi 主程序负责创建工作目录、写入请求、启动进程、监听退出、读取结果并登记资产。视频 render worker 的 `input_manifest_uri` 指向主程序已编译的版本化 `video_ir` 快照；worker 不直接读取 `shot_document` 或 DB2 业务表。

### request

`cancel_file` 是辅助取消信号；主取消通道是主程序向 worker 发送 `CTRL-BREAK` 并在超时后强制终止。

```json
{
  "schema_version": "1.0.0",
  "job_id": "...",
  "step_id": "...",
  "logical_key": "...",
  "work_dir": "...",
  "input_manifest_uri": "...",
  "output_dir": "...",
  "cancel_file": "...",
  "heartbeat_interval_sec": 5,
  "timeout_sec": 7200,
  "limits": {
    "max_memory_mb": 4096,
    "max_parallelism": 4
  },
  "params": {}
}
```

### progress

```json
{
  "schema_version": "1.0.0",
  "job_id": "...",
  "step_id": "...",
  "percent": 42,
  "message": "rendering frames",
  "heartbeat_at": "2026-06-01T00:00:00Z"
}
```

### result

```json
{
  "schema_version": "1.0.0",
  "job_id": "...",
  "step_id": "...",
  "status": "done",
  "exit_code": 0,
  "assets": [],
  "metrics": {},
  "stdout_tail": "",
  "stderr_tail": "",
  "error": null,
  "worker": {
    "name": "render-hyperframes",
    "version": "0.1.0"
  }
}
```

取消协议：主程序先向 worker 进程发送 `CTRL-BREAK`，worker 捕获信号后清理临时文件并退出；若 5 秒内未退出，主程序调用 `TerminateProcess` 强制终止。`cancel_file` 保留为辅助信号，供 worker 在正常轮询周期内提前感知取消意图。强制终止后的 partial asset 不得登记为 `ready`，step 按实际情况标为 `cancelled` 或 `failed`。
## 任务编排

DeepFrames 使用两层任务模型：

1. `DeepBase.DB.JobQueue` 负责领取、幂等、心跳、死任务回收。
2. DeepFrames DB2 业务表记录生产语义、阶段状态、质量门控和资产结果。

队列建议：

| 队列 | 任务 |
|---|---|
| `deepframes.preprocess` | source -> script -> accuracy_report |
| `deepframes.agent` | variant -> shot |
| `deepframes.audio` | TTS、ASR、混音、音频 manifest |
| `deepframes.image` | 背景图、封面图、素材变体 |
| `deepframes.video` | Video IR、lint、snapshot、render |
| `deepframes.package` | 平台候选包、元数据、质量快照 |

所有 job 必须有 deterministic logical key，避免重复点击或重试生成重复任务。外部 worker 每个阶段必须定期 heartbeat，并把 stdout/stderr 摘要写回日志和事件表。

## 状态机

每类业务任务都要注册显式状态流转，禁止随意更新状态字符串。

```text
pending -> running -> blocked_review -> running -> done
pending -> running -> failed
pending -> running -> skipped
running -> cancelled
blocked_review -> cancelled
blocked_review -> skipped
```

典型规则：

- `blocked_review` 表示需要人处理，不等于失败。
- `skipped` 表示用户有意跳过或接受降级，不视为执行成功。
- `warn` 质量结果标为黄灯，只提醒人类，不把 job 改为 `blocked_review`。
- `fail` 质量结果进入红灯和 `blocked_review`，必须返工或人工强制终止。
- 断点续跑只处理 `pending`、`failed`、可重试的 `blocked_review`，跳过 `done` 和 `skipped`。

## Agent 与 Prompt Registry

Prompt 不写死在代码里。所有 Agent prompt、输出结构说明、few-shot 示例、评估 rubric 都进入 DB2 的 prompt registry。

| Agent | 默认模型绑定 | 输出 |
|---|---|---|
| Splitter | `stepfun-flash-3.5` | `content_unit` 内的结构和镜头组 |
| Worker | `stepfun-flash-3.5` | 单 shot 音频指令和视觉意图 |
| Assembler | `stepfun-flash-3.5` | 数据补全、编号、时间轴初算 |
| QA | `deepseek-v4-pro` | 准确性、语义匹配、表达风险、黄灯/红灯 |
| Style Keeper | 无（确定性规则引擎） | 跨 shot 风格一致性报告 |

模型选择由 `deepframes_model_binding` 和 DeepBase.LLM 配置决定。DeepFrames 不实现自动模型路由；生产前由用户或配置明确指定。Style Keeper 不进入 LLM 模型绑定，只读取规则阈值和 embedding 模型配置。

## 外部 Worker 协议

外部 worker 只能通过受控协议和主程序交互，不直接改 DeepFrames 内部状态。

| worker | 输入 | 输出 | 主程序责任 |
|---|---|---|---|
| FFmpeg / ffprobe | manifest、源文件路径、编码参数 | 音频/视频文件、probe JSON | 启动、取消、超时、日志、校验 |
| HyperFrames worker | Video IR、模板、平台规格 | HTML composition、snapshot、preview/final video | 写入任务、读取结果、Gate 3b |
| Remotion worker | Video IR、模板、平台规格 | composition、snapshot、preview/final video | 同上 |
| Chromium capture | HTML composition、帧范围 | frame sequence、snapshot | 沙箱目录、清理、错误映射 |

worker 输出必须包含：

```json
{
  "schema_version": "1.0.0",
  "job_id": "...",
  "step_id": "...",
  "status": "done | failed",
  "assets": [],
  "metrics": {},
  "error": null
}
```

## 数据契约

Delphi 领域对象是主契约，JSON 是序列化形式。所有 JSON payload 必须写入 `schema_version`，并在进入下一阶段前校验。

通用约定：

- 时间单位统一为秒，帧号只在 Video IR / render step 内使用。
- 音频中间格式优先 WAV/PCM，最终平台包再转 MP3/AAC，避免 MP3 padding 造成同步漂移。
- 音频 manifest 同时记录 shot-local timestamps 和 global timestamps。
- 文件 URI 必须通过 asset store 记录，不在业务表里散落绝对路径。
- 生成结果不可原地覆盖；返工产生新 version，旧 version 保留用于复核和回滚。

## 桌面 UI

DeepFrames UI 基于 DeepShell，不从空白 `TForm` 重建工具壳。

核心交互模型：**参数调整 → AI 流水化生成 → A/B 并行 → 人类选优或加工优化**。

DeepShell 五区分工：

| 区域 | DeepShell 承载 | DeepFrames 用途 |
|------|---------------|----------------|
| 左悬浮窗 | `StructureWindow` | 项目/文章树 + 版本配置参数面板（风格预设、A/B prompt 模板、目标平台、高级参数折叠区） |
| TopPanel | `TopPanel` | 快捷命令栏：[开始生成] [暂停] [导出 A 版] [导出 B 版]，生成中显示进度摘要 |
| 中间主区 | `MiddleHost` | 视频预览与结果对比。三种状态：空 → 生成中（进度摘要 + 预估时间）→ 完成（A/B 并排播放 + 差异标注列表） |
| 右悬浮窗 | `InspectorWindow` | 选中 shot 的参数编辑器：background_prompt、voice、emotion 等字段 + [重新生成此 shot] [对比 A/B 版此 shot] |
| BottomPanel | `BottomPanel` | 任务日志 + 历史生成记录，默认折叠 |

**设计原则**：意图区和结果区分离。意图=左窗（配完参数点生成），结果=中央（看机产出了什么）。不满意则点击结果中的问题点 → 右窗编辑参数 → 重跑 → 回到结果区。不设计"浏览数据结构"的多视图 IDE 布局，不设计向导式流程。

UI 只调用 application service，不直接访问 FireDAC query，不直接写业务表。

## 生产入口

自用版第一条完整生产链路：

```text
导入已写好的文章
  -> 生成 script_document
  -> 准确性检查
  -> 生成主版本 + 实验版本，默认 1+1
  -> 生成 shot_document
  -> 生成音频 manifest
  -> 生成 15 分钟以内 B站视频候选包
  -> 导出音频候选包 + B站候选包
```

超过目标时长时，系统按配置拆分或浓缩，并保留依据引用。默认 `target_duration_sec = 900` 是生产策略门控，不只是 UI 默认值。

## 发布与回滚

- DB2 schema 变更必须走 migration，禁止手工改生产库。
- 每次候选包生成保留 manifest、quality snapshot、prompt version、model binding、worker version。
- 外部 worker 升级要记录版本；渲染结果异常时可回滚到上一 worker 版本和上一模板版本。
- 输出目录清理只清理可再生中间文件，不删除已登记的候选包资产。
- 资产保留策略默认为“最终候选包 + 关键快照长期保留，中间大文件按策略清理”。关键快照包括 manifest、quality snapshot、prompt/model/worker 版本、Video IR、audio manifest、timestamps 和封面。
