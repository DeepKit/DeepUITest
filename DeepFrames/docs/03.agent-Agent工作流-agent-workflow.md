# Agent 工作流

## 概述

DeepFrames 采用 Multi-Agent 架构，将输入内容按语义切分后分配给多个 Agent 并行处理。Agent 链路包含 4 种 LLM 角色：Splitter → Worker → Assembler → QA；Style Keeper 是链路中的确定性规则引擎，不调用 LLM。

本文档中的章节、角色和叙事镜头是首个生产配方，不是产品边界。通用内容可以按章节、主题或观点单元进入同一条 Agent 链路，并通过模板注册表选择讲解、问答、案例、观点冲突等表达模板。

**职责边界原则**：Assembler 只做数据层面的补全（时间轴间隙、时长匹配、格式校验），所有语义层面的质量判断统一收归 QA Agent。

**准确性边界**：`accuracy_report` 是上游 `build_script(source_document)` 阶段产出的脚本级准确性报告，用于核对 `script_document` 是否忠实于来源。本文档中的 QA Agent 评审的是 Agent 输出后的 `shot_document`，结果写入 `deepframes_quality_gate_result` / `deepframes_eval_result`，不覆盖脚本级 `accuracy_report`。

## 生产模式：Accuracy Mode 与 Expressive Mode

DeepFrames 支持两类任务级表达模式，默认使用 `Accuracy Mode`。

| 模式 | 目标 | 约束 |
|---|---|---|
| `Accuracy Mode` / 准确模式 | 忠实原文，适合有声书、长文朗读和严肃内容 | 不静默改写核心文本；TTS 451 改写必须经 QA 对照；`accuracy_report` 是硬参考；QA 对遗漏、歪曲和私自补充更敏感 |
| `Expressive Mode` / 表达增强模式 | 提升观感和传播效果，适合实验版、B 版、短视频预告或用户主动选择的增强表达 | 允许轻度口语化、压缩和场景渲染；必须保留 source reference；不允许伪造关键事实；增强范围写入 quality snapshot |

A/B 版本的“保守准确 / 大胆演绎”是版本标签或差异维度，不替代正式模式名。`expression_policy_json` 必须显式记录当前模式。

## fake provider 工程主线 + StepFun prompt POC

Agent 生产链采用两条并行验证路径：

1. **工程主线**：fake provider 返回固定结构化 JSON，用于固化 schema、DB、状态机、UI、版本链和回归测试。
2. **AI 验证支线**：StepFun prompt POC 使用 1-2 篇真实文章验证 JSON 成功率、字段稳定性、QA 可用性、token/耗时和失败样本。

两条线在真实 StepFun adapter 接入前汇合：fake provider 跑通文档链，StepFun POC 的失败样本用于修正 prompt、schema 和修复策略。

## 工作流阶段

```
script_document (预处理与脚本化输出)
  │
  ▼
┌─────────────┐
│  Splitter    │  语义+时长双约束切分
│  Agent       │  生成章节风格摘要 + 镜头组
└──────┬──────┘
       │ shots[] + style_anchor + chapter_summary + shot_groups
       ▼
┌─────────────────────────────────┐
│     并行 Worker Agents (5-8路)   │
│                                │
│  每个 Worker 输入:              │
│  · 当前 shot 文本              │
│  · 全局风格锚点 (style_anchor)  │
│  · 章节摘要 (chapter_summary)  │
│  · group 共享风格 (group_style) │
│  · 前后各 1 shot (上下文)      │
│  · Few-shot 示例               │
│                                │
│  ┌─────┐ ┌─────┐ ┌─────┐     │
│  │Shot1│ │Shot2│ │Shot3│ ... │
│  └──┬──┘ └──┬──┘ └──┬──┘     │
└─────┼───────┼───────┼────────┘
      │       │       │
      ▼       ▼       ▼
┌─────────────┐
│  Assembler   │  数据层补全：时间轴、时长匹配、格式校验
│  Agent       │  （不做语义质量判断）
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  QA Agent    │  语义质量审核（默认 deepseek-v4-pro）
│  (强模型)    │  不合格 shot → 展示给用户 → 用户决定回流重做
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  Style Keeper│  跨 shot 风格一致性校验
│  规则引擎     │
└──────┬──────┘
       │
       ▼
  完整镜头脚本 (`shot_document`，可导出 shots.json 快照)
  → 进入 Gate 2 审核
```

## Agent 定义

### 1. Splitter Agent（切片器）

**职责**: 将章节文本按语义+时长双约束切分为镜头单元，生成章节级风格摘要和镜头组。

**切分优先级**（从高到低）：
1. 场景切换（地点/时间变化）
2. 角色切换（对话轮转）
3. 情感转折（氛围突变）
4. 时长阈值（4-6 秒，弹性范围 3-8 秒）

**镜头组(group)概念**:
- 3-5 个语义相近的 shot 组成一个 group
- group 内共享视觉风格参数（`group_style`），减少背景图重新生成
- 跨 group 才做明显的风格/背景切换
- group 边界处额外注入首尾 shot 摘要，防止长章节（50+ shots）跨 group 风格漂移

**输入**:
```json
{
  "chapter_id": 1,
  "title": "第一章 初入江湖",
  "segments": [...],
  "characters": [
    {"name": "张三", "voice_id": "voice_a", "description": "年轻侠客"}
  ],
  "preset_id": "xuanhuan"
}
```

**输出**:
```json
{
  "style_anchor": {
    "art_style": "中国水墨画与奇幻风格融合",
    "color_palette": ["深蓝", "金色", "紫色"],
    "tone": "大气磅礴，略带神秘"
  },
  "chapter_summary": "张三初入江湖，在客栈遇到神秘老者，获得一本武功秘籍。基调：好奇+紧张。场景：客栈、街道、山间小路。",
  "shot_groups": [
    {
      "id": "group_01",
      "shot_ids": ["shot_001", "shot_002", "shot_003"],
      "group_style": "客栈内景，暖黄灯光，木质结构，江湖气息",
      "boundary_summary": "张三推开客栈大门 → 落座饮酒，氛围从紧张转为好奇"
    }
  ],
  "shots": [...]
}
```

### 2. Worker Agent（Per-Shot）

**职责**: 为单个镜头生成完整的音视频指令。

**输入（包含 group 上下文）**:
```json
{
  "current_shot": { "text": "...", "type": "narration" },
  "context": {
    "style_anchor": { "art_style": "...", "color_palette": [...], "tone": "..." },
    "chapter_summary": "...",
    "group_style": "客栈内景，暖黄灯光，木质结构，江湖气息",
    "prev_shot": { "...summary..." },
    "next_shot": { "...summary..." }
  },
  "few_shot_examples": ["...2-3个高质量shot示例..."]
}
```

`group_style` 由 Splitter 在切分阶段生成，作为同组所有 Worker 的共享视觉参数。Worker 在 `background_prompt` 中必须延续 group_style 的视觉基调。

**结构化输出**:
```json
{
  "shot_id": "shot_001",
  "group_id": "group_01",
  "audio": {
    "text": "夜色笼罩着古城，远处传来悠扬的笛声。",
    "voice": "cixingnansheng",
    "emotion": "mysterious",
    "pace": "slow",
    "pitch": "low",
    "instruction": "神秘低沉，语速偏慢"
  },
  "visual": {
    "background_prompt": "[中国水墨画风] + [古城墙远景，月光下城墙轮廓，灯笼微光] + [远景低角度] + [月光冷色调] + [深蓝与金色]",
    "target_aspect_ratios": ["16:9", "9:16"],
    "layers": {
      "subject": null,
      "text": {
        "content": "夜色笼罩着古城，远处传来悠扬的笛声。",
        "position": "bottom",
        "style": "fade-in"
      }
    },
    "transition": {
      "type": "fade",
      "duration": 0.5
    }
  }
}
```

**画面描述 Prompt 模板**: `[画风] + [主体] + [构图] + [光影] + [色调]`，从 `style_anchor` + `group_style` 自动填充画风和色调部分。

### 3. Assembler Agent（汇总器）

**职责**: 数据层面的补全和校验（不做语义质量判断）

**处理范围**:
- 补全 shot 间的时间轴间隙
- 校验音频时长与视频时长在数值上匹配
- 修正格式错误（字段缺失、类型不匹配）
- 编号连续性检查

**不做**:
- 画面质量判断 → QA Agent
- 风格一致性检查 → Style Keeper
- 转场语义自然度 → QA Agent

**新增：叙事连贯性规则检测**

Assembler 在汇总所有 shot 后，运行确定性规则检测叙事连贯性问题，不调用 LLM：

| 规则 | 检测方式 | 标记 |
|------|---------|------|
| 情感跨度 | 相邻 shot 的 `emotion` 值跨度 > 2 级（如 calm→angry 跨 calm/tense/angry = 3 级） | 黄灯 |

Emotion 枚举的序数值：`calm=0, tense=1, sad=2, happy=3, angry=4, mysterious=5`。相邻 shot 的 emotion 差值 ≥ 3 且中间无过渡 shot 时标黄灯。不阻塞生产，在结果区差异标注中展示。

**输出**: 初版 `shot_document`，必要时导出 `shots.json` 调试快照

### 4. QA Agent（质量审核）

**职责**: 独立语义质量把关，默认使用 `deepseek-v4-pro`；其他 Agent 默认使用 `stepfun-flash-3.5`。最终模型分配由生产前配置确定，DeepFrames 不内置 LLM 自动路由策略。

**检查维度**:

| 维度 | 规则 | 不合格处理 |
|---|---|---|
| 文本完整性 | 字幕文本与原文覆盖率 ≥ 95% | 标记遗漏段落 |
| 画面匹配度 | 画面描述与文本语义相关 | 标记 |
| 情感一致性 | emotion 标注与语境匹配 | 标记 |
| 风格统一性 | 同 group 内画风一致 | 标记 |
| 转场连贯性 | 相邻 shot 转场自然 | 标记 |
| 时长合理性 | 单 shot 3-8 秒，无异常值 | 标记 |

**输出**:
```json
{
  "gate_result": "pass | warn | fail",
  "score": 0.85,
  "issues": [
    {
      "shot_id": "shot_023",
      "type": "style_inconsistency",
      "severity": "warn",
      "description": "画风从水墨切换到写实",
      "suggestion": "统一为中国水墨画风"
    }
  ]
}
```

**Gate 2 审核流程**:
- QA 结果为 `pass` → 自动通过
- QA 结果为 `warn` → **展示给用户**，由用户决定是接受还是重做
- QA 结果为 `fail` → 标记问题 shot，展示给用户，用户确认后回流 Worker 重做（最多 2 轮）
- 仍不合格则标记 `degraded: true` 走降级方案

### 5. Style Keeper（风格一致性）— 确定性规则引擎

**职责**: 横跨所有 shot 的全局风格一致性校验。**不调用 LLM**，作为确定性规则引擎运行。

**工作方式**:
1. 从 Splitter 输出的 `style_anchor` 和每个 group 的 `group_style` 中提取**期望约束**：主色调、画风关键词、构图偏好
2. 从每个 Worker 输出的 `visual.background_prompt` 中提取**实际值**
3. 逐 shot 比对：规则引擎检查实际值是否遵循了期望约束

**规则定义**:

| 规则 | 检查方式 | 偏差阈值 | 标记 |
|------|---------|---------|------|
| 主色调一致性 | 从 `background_prompt` 提取颜色描述词 → 与 `style_anchor.color_palette` 做字符串匹配或颜色空间距离 | 无一匹配 = 偏差 | 黄灯 |
| 画风关键词一致性 | 从 `background_prompt` 提取画风关键词 → 与 `style_anchor.art_style` 做 embedding 余弦相似度 | cosine < 0.7 = 偏差 | 黄灯 |
| Group 内一致性 | 同一 group 内所有 shot 的 `background_prompt` 两两对比 embedding 余弦相似度 | 任意 pair cosine < 0.8 = 偏差 | 黄灯 |
| Group 间过渡平滑性 | 相邻 group 的 `group_style` embedding 余弦相似度 | cosine < 0.5 = 风格突变 | 黄灯提醒（不做红灯——跨 group 风格变化可能是设计意图） |

Embedding 可选用轻量中文模型（如 text2vec-base-chinese，本地运行），不调用云端 LLM API。

**输出**: 风格一致性报告（JSON），列出所有偏差 shot 及其偏差类型、偏差值和建议。报告写入 `deepframes_eval_result`，结果区差异标注按风格类别分组展示。

## Prompt Registry

所有 Agent 的 prompt 必须以版本化模板管理，不能只写在代码里。Prompt 输出采用 `Extract / Normalize → Schema Validate → Repair / Retry` 三层结构化输出策略；完整规范见 `14.prompt-structured-output-Prompt结构化输出.md`。

| Agent | 默认模型 | Prompt 模板要求 |
|---|---|---|
| Splitter | `stepfun-flash-3.5` | system prompt、切分规则、输出 JSON schema、1 个完整章节切分示例 |
| Worker | `stepfun-flash-3.5` | system prompt、画面描述模板、音频指令模板、2-3 个 shot few-shot 示例 |
| Assembler | `stepfun-flash-3.5` | 只允许数据补全与格式修复，不做语义判断 |
| QA | `deepseek-v4-pro` | 质量评分 rubric、hard/soft issue 定义、pass/warn/fail 阈值 |
| Style Keeper | 无（确定性规则引擎） | embedding 模型配置、余弦相似度阈值、偏差分类规则 |

Prompt 文件需包含 `prompt_version`，并与 `schema_version` 一起写入 job metadata，便于复现同一次生产结果。生产前用户可修改 Agent 到模型的映射，但 DeepFrames 不实现自动模型路由。
### DeepBase 持久化约束

Prompt Registry 是 DB2 中的真实业务模块，不是代码目录里的 prompt 文件集合：

| 表 | 用途 |
|---|---|
| `deepframes_prompt_template` | prompt 模板、版本、输出结构和 few-shot 示例 |
| `deepframes_prompt_run` | 每次调用的模板版本、模型、原始输出、规范化 JSON、校验错误、repair 次数、token、耗时和错误 |
| `deepframes_model_binding` | Agent 角色到 DeepBase.LLM provider/model 的明确绑定 |
| `deepframes_eval_result` | QA、人工复核和评估结果 |

StepFun Chat 调用通过 DeepBase.LLM adapter 执行，API Key 通过 DeepBase.Security 保存。Agent 不在 VCL UI 线程同步调用远程 API。

## 编排策略

### Agent 运行期间的用户交互

Agent 阶段（LLM 推理 + 图像生成）可能持续 5-15 分钟。在此期间，用户不得面对黑箱等待。

**最小交互承诺**：

| 用户能力 | 实现要求 |
|---------|---------|
| 查看实时进度 | 按 Agent 阶段展示进度（Splitter / Worker 5/9 / Assembler / QA / Style Keeper）；Worker 阶段显示已完成/总 shot 数 |
| 预览已完成 shot | 每个 Worker 完成后立即展示该 shot 的结构化输出（文本、情感标注、画面描述），不需等全部完成 |
| 任意时刻取消 | 取消操作立即停止所有 pending 和 running 的 API 调用；已完成的 shot 保留为 checkpoint |
| 查看耗时估算 | 基于已完成 shot 的平均耗时，估算剩余时间 |

**进度信息来源**：
- Splitter / Assembler / QA / Style Keeper：`deepframes_job_step.status` 变更触发 UI 更新
- Worker 阶段：每个 `deepframes_job_step` 完成（status → `done`）时触发增量更新
- 令牌桶队列深度可从内存状态读取，用于估算排队时间

**取消后的恢复**：`cancelled` 是终端状态，原 step 不得原地改回 `running`。断点续跑时，`done` / `skipped` / `cancelled` 状态的 step 被跳过；如需继续未完成工作，Workflow application service 为同一 logical key 创建新的 `pending` step，并通过 `parent_step_id` 或 `retry_of_step_id` 追溯原取消记录。

### 并行度控制

- Worker Agent 并行数：配置化（默认 5-8）
- Splitter、Assembler、QA、Style Keeper 串行执行
- 采用令牌桶 + 自适应并发：监控 API 响应延迟，动态调整窗口

### 错误处理（按类型分级）

| 失败类型 | 处理策略 |
|---|---|
| TTS 451 审查 | 音频线生成 `tts_text_variant`，不改写 `shot_document`；由 Gate 3a 按语义相似度判定 pass/warn/fail |
| API 限流 (429) | 指数退避重试，最多 3 次 |
| 网络超时 | 固定间隔重试，最多 3 次 |
| Agent 推理异常 | 降级为简化模板 |
| Worker 失败 | 重试 3 次，标记 degraded |

### 重试/时间约束

- 全局最大重试轮次：2 轮（QA 回流）
- 单 shot 最大重试次数：3 次
- Agent 阶段默认超时：30 分钟（可配置）
- StepFun 文字模型按包月使用，DeepFrames 当前不做 token/次数预算拦截；但必须记录 token、latency、retry 和错误，详见 `15.cost-usage-成本与用量-cost-usage.md`

### 降级 Agent

当 shot 无法正常生成时，输出简化版本保证时间轴完整：

```json
{
  "shot_id": "shot_023",
  "metadata": {
    "degraded": true,
    "degraded_reason": "image_generation_failed",
    "fallback": "solid_color_background + subtitle_only"
  }
}
```

批量降级修复命令：
```bash
deepframes repair --chapter 1 --degraded-only
```

## 数据格式约定

Agent 阶段以 Delphi 领域对象和 DB2 版本化文档为主契约；JSON 仅用于模型结构化输出、worker payload 和导出快照。每个 payload 必须带 `schema_version`，进入下一阶段前由 Delphi 校验。

核心数据：
- **script document**: 预处理与脚本化输出，Splitter 的输入，写入 `deepframes_script_document`
- **shot document**: Agent 工作流最终输出，音频和视频流水线各自的输入，写入 `deepframes_shot_document`
- **job/step tables**: 任务状态（shot 级别 checkpoint），写入 `deepframes_job`、`deepframes_job_step` 和音视频阶段表，支持断点续跑

shot_id 规则：章节内唯一，格式 `shot_{三位序号}`（如 `shot_001`, `shot_002`）。

Schema 变更时需通过快照测试验证向后兼容。

生产内反馈（用户选择、人工确认、手动编辑、warning 处理）只用于记录和人工复盘，不自动改 prompt、不训练模型、不自动调阈值；详细规则见 `08.quality-质量门控-quality-gate.md`。
