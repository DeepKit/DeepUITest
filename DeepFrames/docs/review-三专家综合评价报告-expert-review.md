## 二、三位专家公认的核心优势

以下优势被至少两位专家独立确认：

### 1. 文档版本链的完整性与可返工性（三位一致确认）

`source → script → accuracy → variant → shot → manifest/IR → package` 的 7 阶段链路，配合 `version_no` 单调递增、`parent_version_id` 回溯、`schema_version` 兼容性检查，构成了一套坚实的不可变版本模型。用户可以在任意阶段停下来审查、返工、对比，而不是"全量重来"的黑箱。

### 2. 音视频双 Pipeline 真正解耦（三位一致确认）

两条流水线通过 asset manifest 和只读快照关联，不共享内部状态。缺失音频只阻塞 `final-with-audio` 模式，不阻塞图片生成、模板检查和静默预览。`visual-preview / timed-preview / final-with-audio` 三种视频运行模式让用户可以渐进式验证。

### 3. Worker 协议的最小化设计（三位一致确认）

request.json / progress.json / result.json 三文件协议简洁、可测试、跨语言友好。Worker 不直接访问 DB、不持有密钥、不拥有业务状态。取消策略的三级设计（CTRL-BREAK → cancel_file → TerminateProcess）覆盖了 Windows 进程管理的主要场景。

### 4. 质量门控的参数化策略（专家 2 + 专家 3 确认）

默认绿灯/黄灯自动通过、红灯才停止，同时允许在任意 Gate 设置人工停顿点。"放弃信号"和"不适合生产的内容信号"两张表避免了"无限重试"陷阱。degraded 阈值（>20% 最高 warn，>40% 必须 fail）有实际指导价值。

### 5. 11.e2e 用真实数据验证 schema（专家 1 + 专家 3 确认）

用 3800 字玄幻小说走通完整链路是文档体系中最有价值的部分。这种"用实例验证设计"的做法极大降低了 schema 与实际生产之间的 gap。

### 6. 全局时间轴量化策略（专家 1 + 专家 2 确认）

意识到逐 shot 做 `round(duration * fps)` 会导致长视频累计漂移，采用全局秒级时间轴后统一量化的方案，是处理 A/V 同步的正确工程实践。

## 三、阻塞级问题汇总（必须修复后才能进入工程阶段）

按影响范围排序，共 8 个阻塞级问题：

### 🔴 A1. ASR API 协议与文档假设不匹配（技术可行性）

**发现者**: 专家 2
**严重性**: 高 — 工程实现时需重写 ASR 调用层

文档 `05.audio` 假设 ASR 返回简单的 word-level timestamp JSON，但 StepFun ASR 实际行为是：
- 端点是 `POST /v1/audio/asr/sse`（SSE 流式，不是一次性 JSON）
- 时间戳需设置 `enable_timestamp=true`
- 时间戳在 Delta 事件中增量返回，非 Done 事件一次性返回
- 音频需 Base64 编码

**修复建议**: 工程启动前先做 ASR SSE POC，确认 Delta 事件格式后更新 `02.api` 和 `05.audio`。

### 🔴 A2. StepFun 双 Base URL 问题（技术可行性）

**发现者**: 专家 2
**严重性**: 高 — 会导致 ASR 调用 401 错误

文档 `02.api` 将 Base URL 统一定义为 `/step_plan/v1`，但 ASR SSE 端点实际走 `/v1`（标准端点）。Step Plan 和标准端点使用不同 API Key。

**修复建议**: 在 DeepBase 配置中同时管理两个 API Key（Step Plan Key + 标准 Key），按 capability 路由到正确端点。在 `02.api` 中补充双端点说明。

### 🔴 A3. TTS voice_label 与 instruction 参数限制（技术可行性）

**发现者**: 专家 2
**严重性**: 中 — 影响情感控制方案

`stepaudio-2.5-tts` 不支持 `voice_label`，只支持 `instruction`（限 200 字符）。文档中 `VoiceConfig` 的枚举映射为中文 instruction 的思路正确，但需确保不传入 `voice_label`。另外 `input` 中括号 `()` 有特殊语义（内联指令），原文含括号需转义。

**修复建议**: 在 `02.api` 中补充 `stepaudio-2.5-tts` 的参数限制说明，在 `05.audio` 中增加括号转义逻辑。

### 🔴 A4. 状态机缺少 `skipped` 状态和 `partial_done` 语义（架构）

**发现者**: 专家 1
**严重性**: 中 — 影响返工和降级场景的状态准确性

12.db-state 的状态流转未覆盖：
- 用户在 Gate 2 后决定接受降级的 shot 应进入什么状态？`done` 不准确，`failed` 不准确，`cancelled` 语义不对
- 9 个 shot 中 7 个 done、2 个 degraded 时，job 整体状态应如何聚合？

**修复建议**: 增加 `skipped` 状态或在 `done` 的 `payload_json` 中增加 `completion_type` 枚举，并定义 job 级别聚合规则。

### 🔴 A5. `blocked_review → running` 的重入缺少条件约束（架构）

**发现者**: 专家 1
**严重性**: 中 — 可能导致同一任务被多次错误推回 running

当前没有定义 `blocked_review` 回到 `running` 的前置条件（人工确认？参数修改？自动超时？）。

**修复建议**: 为 `blocked_review → running` 增加前置条件字段（如 `review_action: rework | force_retry | override_accept`）。

### 🔴 A6. 候选包引用的资产清理保护缺失（架构）

**发现者**: 专家 1
**严重性**: 中 — 可能导致已导出候选包的引用资产被删除

`asset` 状态允许 `ready → deleted` 清理，但"清理任务不得删除被候选包引用的资产"只是文字约束，DB 层面无引用计数或保护标记。

**修复建议**: 在 `deepframes_asset` 中增加 `protected_until` 时间戳，或建立候选包与资产之间的引用关系表。

### 🔴 A7. 缺少用户操作流文档（产品体验）

**发现者**: 专家 3
**严重性**: 中 — 影响可操作性和长期可维护性

15 份文档全部是从"系统内部"向外看的架构师视角，缺少从"用户操作"向内看的产品视角。没有一份文档描述"用户第一次坐下来想生产一条视频"的完整操作步骤。

**修复建议**: 增加一份 `00.quickstart-快速上手.md`，用 2-3 页描述从打开程序到导出第一个候选包的完整操作流。

### 🔴 A8. Agent 运行期间的用户交互未定义（产品体验）

**发现者**: 专家 3
**严重性**: 中 — 5-15 分钟黑箱等待影响体验

Agent 阶段（LLM 推理 + 图像生成）可能需要 5-15 分钟，但文档没有定义用户在此期间能看到什么（进度？预览？能否取消？）。

**修复建议**: 明确 Agent 工作流的流式输出策略：(1) 逐 shot 进度展示；(2) 任意时刻取消；(3) 已完成 shot 的预览。

## 九、综合结论

### 当前设计是否最优？

**在架构与数据契约层面接近最优，在 StepFun API 集成精度和用户操作体验层面还有明确缺口。**

三位专家一致认为以下核心设计是正确且可落地的：
- 7 阶段文档版本链
- 音视频双 pipeline 解耦
- Worker 文件契约协议
- 质量门控参数化策略
- Agent 职责分离 + Style Keeper 确定性检查
- 全局时间轴量化

需要修正的 8 个阻塞级问题中：
- 3 个是 StepFun API 集成偏差（A1-A3），通过 POC 验证后更新文档即可解决
- 3 个是状态机/资产保护的 schema 补全（A4-A6），在 DDL migration 阶段解决
- 2 个是文档视角缺口（A7-A8），补充一份操作流文档即可

**最终判断：解决 8 个阻塞级问题后，可进入工程阶段。无需架构重构。**
