# 开发路线图

## 目标

DeepFrames 不采用“先砍功能做 MVP”的产品策略。开发按依赖顺序推进，但每一层的接口、数据契约、版本策略和回滚能力都按完整软件设计。

当前自用版第一条完整生产链路：

```text
已写好的文章
  -> source_document
  -> script_document
  -> accuracy_report
  -> variant_document
  -> shot_document
  -> audio_manifest
  -> video_ir
  -> 音频候选包 + B站视频候选包
```

默认策略：

| 项 | 默认值 |
|---|---|
| 目标时长 | 单条视频通常不超过 15 分钟，`target_duration_sec = 900` |
| 版本策略 | 主版本 + 实验版本，默认 1+1 |
| 视频平台 | B站优先 |
| 视觉路线 | 简单表意，表达准确优先 |
| BGM | 默认关闭 |
| 渲染后端 | HyperFrames 优先，Remotion 后续 |
| 控制点 | 多个控制点可由参数设定，默认全自动跑到候选包 |
| 黄灯 / 红灯 | 黄灯只提醒并继续；红灯阻塞并要求返工或人工处理 |
| 资产保留 | 最终候选包 + 关键快照长期保留，中间大文件按策略清理 |

## 阶段 1：DeepBase 桌面骨架

目标：建立 Delphi VCL + DeepBase 原生桌面程序基础。

范围：

- `DeepFrames.dpr` 初始化 DeepBase。
- 接入 `DeepBase.Persistence.Manager.FireDAC`。
- 使用 DeepShell 建立主窗体、设置页、任务面板和日志面板。
- 初始化 DB1 `DeepFramesConfig.db` 与 DB2 PostgreSQL `DeepFramesData`。
- 固化 RootPath、输出目录、worker 目录和日志目录。

验收：

- 程序可启动、关闭、恢复窗口状态。
- DB1 只保存 DeepBase 配置和本地状态。
- DB2 由 PostgreSQL migration 创建，业务表不写入 DB1。
- 日志、配置、密钥入口全部通过 DeepBase。

## 阶段 2：文档链与业务库

目标：让文章能进入稳定、可返工、可追踪的生产链。

范围：

- 落地 `deepframes_project`、`deepframes_content_unit`、document 表、asset 表、job 表。
- 实现 `source_document -> script_document -> accuracy_report -> variant_document -> shot_document` 的版本链。
- 建立 Repository 和 application service。
- UI 可查看每个 content unit 的文档版本、质量标记和派生关系。

验收：

- 导入文章后生成 `source_document`。
- 所有后续文档只新增版本，不覆盖旧版本。
- 黄灯、红灯、人工备注可写入并在 UI 显示。
- `content_unit` 支持章节、段落、平台版本和账号版本。

## 阶段 3：Agent 生产链

目标：让 Agent 产出可校验的脚本、版本和镜头文档。

范围：

- 建立 prompt registry、model binding、prompt run 记录。
- 先用 fake provider 固化结构，再接 StepFun adapter。
- Splitter、Worker、Assembler、QA 通过同一 LLM service 调用；Style Keeper 使用确定性规则引擎，不调用 LLM。
- QA 输出 Gate 2 质量门控结果，并区分黄灯与红灯；脚本级 `accuracy_report` 由上游 `build_script` 阶段产出。

验收：

- 同一输入、同一 prompt version、同一 model binding 可复现调用记录。
- Agent 输出进入结构化 JSON payload，并通过 schema 校验。
- 黄灯继续生产并提醒；红灯进入阻塞状态。
- 失败任务可重试，重试不产生重复业务对象。

## 阶段 4：音频生产线

目标：生成可独立使用、也可供视频线绑定的音频候选包。

范围：

- TTS shot 级合成、checkpoint、资产登记。
- ASR 逐字时间戳，保存 local/global 双坐标。
- WAV/PCM 中间链路、FFmpeg 拼接、响度标准化。
- 生成 `audio_manifest`，记录采样率、声道、编码、duration、timestamps、BGM 关闭状态。

验收：

- 每个 shot 音频可断点续跑。
- 合并后实际时长与预期时长偏差在 Gate 3a 阈值内。
- `audio_manifest` 可被视频线只读消费。
- 不启用 BGM 时不依赖音乐库。

## 阶段 5：B站视频生产线

目标：基于 `shot_document` 和 `audio_manifest` 生成 B站可发视频候选包。

> **渲染后端许可证决策点**：Phase 5 默认使用 HyperFrames。若 Phase 5 过程中需要引入 Remotion，必须先完成 Remotion 商业许可复核；否则 Remotion 许可证复核 deadline 固定在 Phase 5 结束、Phase 7 扩展能力开始之前。HyperFrames 依赖许可证也在 Phase 5 结束前复核一次，确保后续产品化无阻塞。

范围：

- 编译后端无关的 `video_ir`。
- 平台规格先落地 B站：1920x1080、30fps、H.264、AAC。
- 实现 HyperFrames worker：lint、snapshot、preview、render。
- 生成字幕、安全区、简单表意背景图或画面素材。
- Gate 3b 校验时长、字幕同步、黑屏、文本遮挡和基础画面可读性。

验收：

- 15 分钟以内视频可从文章链路完整生成。
- 全局时间轴量化不产生累计漂移。
- snapshot 和最终 mp4 登记为 asset。
- B站候选包包含视频、封面、标题、简介、标签、quality snapshot 和 manifest。

## 阶段 6：候选包与导出

目标：把生产结果整理为下游发布系统可选择的候选包。

范围：

- 定义 `candidate_package` schema。
- 支持音频候选包和 B站视频候选包。
- 默认采用 102C 资产策略：保留最终包和关键快照，中间大文件按策略清理。
- 写入平台、账号定位、多版本标注、质量快照和资产清单。
- 导出目录保持独立，不与程序目录和数据库目录混在一起。

验收：

- 下游系统无需理解内部任务表即可读取候选包 manifest。
- DeepFrames 不写发布状态、运营数据、账号排期和平台分析。
- 每个候选包可回溯到 source、prompt、model、worker、quality gate 和资产版本。

## 阶段 7：扩展能力

目标：在第一条完整链路稳定后扩展，不反向破坏核心契约。

范围：

- Remotion worker。
- 更多平台规格和多比例视频。
- BGM 与音乐库。
- ArtifactOS 深度联动。
- DB3 多机协作。
- 商业化、授权、销售包装。

验收：

- 扩展能力只新增配置、worker 或平台 profile，不改破已有候选包契约。
- 旧候选包和旧任务可继续查看、复核和回滚。
