# Coach 基于协议的实现规范

> 状态：开发收敛版
> 协议依赖：DeepGuide Journey Protocol v1.0

---

## 1. 协议消费方式

Coach 是 Journey Package 的执行端。它只消费 `published` 状态的旅程包，严格按照协议状态机播放，不自由生成业务规则。

Coach 可以使用 AI 做多轮意图澄清、旅程候选生成、专业意见提示和卡点解释，但不得把推测当结论，不得自动替员工结束澄清或进入旅程，不得跳过 Gate、RiskPolicy、LostRecovery 或 Trace。

---

## 1.1 双悬浮面板规则

- Coach 只采用独立悬浮窗口形态，不介入浏览器和其它业务系统，不做浏览器插件、系统内嵌 SDK 或业务系统覆盖层。
- 独立悬浮窗口内采用两个悬浮面板：A 意图澄清对话框，B 图卡展示区。
- 默认只显示轻量悬浮入口，不遮挡主业务系统。
- 员工点击悬浮入口后展开 A 面板。
- A 面板必须支持文字输入；语音输入为可选增强能力，不得阻塞 MVP 主链路。
- A 面板负责员工提问、多轮澄清、专业意见和旅程候选。
- B 面板在员工确认进入旅程后出现，负责 GuideCard 展示、数字候选、风险提示、完成验证和 LostRecovery 入口。
- A 面板和 B 面板职责不得混用：A 不播放执行图卡，B 不做自由聊天。
- A 面板和 B 面板都必须提供展开、收缩、钉住控件；展开、收缩、钉住由员工决定，AI 不得强制固定面板。
- Coach 不根据屏幕状态主动猜测员工意图；入口必须来自员工文字提问、可选语音提问，或员工明确点击继续已有旅程。
- 员工可随时用 `0` 返回、取消、收起 A 面板或退出当前 B 面板上下文。

---

## 1.2 面板状态

```text
collapsed：只显示悬浮入口
clarifying：A 面板展开，进行意图澄清
ready_to_enter：A 面板显示专业意见和旅程候选，等待人类确认
playing：B 面板展开，播放当前 GuideCard
playing_pinned：B 面板被员工钉住，跟随旅程步骤更新但不自动收起
playing_with_clarify：B 面板保持当前图卡，A 面板展开处理卡点、9 重生成或呼叫专家
completed：B 面板显示完成验证，用户可 0 收起
```

状态切换必须由员工动作或协议状态机驱动。AI 不得自行打开 B 面板并进入旅程。

---

## 1.3 B 图卡视觉渲染规则

- B 图卡仅作为参考导航图，不得作为真实业务系统的覆盖操作层。
- B 图卡应尽量与员工正在操作的业务界面结构一致，优先使用线框图作为参考导航图。
- B 图卡必须支持视觉锚点：目标区域、目标字段、目标按钮、风险区域、完成状态。
- 当前目标使用聚焦化展示；非当前区域可以模糊化、灰化或弱化。
- 必须支持色框：当前主焦点、候选目标、场域、风险区、成功状态。
- 必须支持导航线：把图卡说明、数字候选与界面目标区域连接起来。
- 色框和导航线只画在 B 参考图中，用于导航提示，不代表自动点击、自动填写或证据链采集。
- 员工正在操作的真实系统仍是业务执行主界面，B 面板只是线框参考导航层。

---

## 2. 进入旅程前检查

进入旅程前必须检查：

- `boundary_set.not_applicable_when`：当前场景是否不适用。
- `ability_set.abilities` 中 `required=true` 的能力项：用户、系统、材料、外部服务是否满足。
- `status`：只能新进入 `published` 包。
- `version`：默认使用最新 published 版本；进行中的 session 继续绑定进入时版本。

任一 MUST 检查失败，不得进入旅程执行。

---

## 3. 执行状态机

Coach 必须实现协议状态机：

```text
idle -> intent_matched -> journey_selected -> playing -> completed
                                     |          |       |
                                     |          |       -> aborted
                                     |          -> lost -> playing
                                     -> risk_confirm -> playing
```

每次状态转换必须产生 TraceEvent。

---

## 4. 数字候选规则

- 所有一线候选项使用 0-9 编号。
- 1-8 用于业务候选；9 保留为重新生成/重组选项；0 保留为返回、取消或退出。
- 必须支持键盘和点击；语音说数字为可选增强能力。
- 超过 8 个业务候选必须分页或先分类。
- 所有前台候选界面必须提供 0；AI 生成或澄清候选必须提供 9。
- 用户自由文本必须进入 A 面板；语音转文字为可选入口。Coach 必须通过多轮澄清把意图缩小到可匹配旅程的程度。
- 澄清是否足够、是否进入某个旅程，必须由人类通过数字选择确认。
- 用户自由文本只能触发意图澄清、意图匹配、反馈或 LostRecovery，不得直接替代高风险确认。

---

## 5. 风险确认规则

- L2/L3 必须暂停执行并等待人类确认。
- L3 必须二次确认，并提供人工升级或回退路径；Trace 只记录导航状态，不承担证据链职责。
- 风险确认、拒绝、回退都要写 TraceEvent。
- Coach 不得自动替用户点击“确认”。

---

## 6. TraceEvent 要求

每次状态转换、Gate 决策、风险确认、迷路恢复、完成验证都要产生 TraceEvent。

最小字段：

```text
event_id, event_type, package_key, package_version, journey_session_id,
from_state, to_state, gate_key, card_key, route_key, actor_ref,
trigger, timestamp, context_hash, context_refs
```

Trace 必须持久化，支持按 session 回放。

### 6.1 Trace 边界

Trace 只用于旅程复盘和产品改进，不用于证据链和追责。

Trace 应记录：package/version/session、Gate/Card/Route、数字候选选择、风险确认、迷路恢复、呼叫专家、退出或完成。

Trace 不应记录：发票原图、客户/员工/供应商隐私原文、真实业务系统截图、员工在真实系统里的实际点击证据、报销审批证据链或责任裁判材料。

---

## 7. LostRecovery

触发条件：

- 用户长时间无响应。
- 用户明确表示困惑或迷失。
- 状态机无法匹配下一条 Route。
- 当前 Gate 配置了异常恢复路径。

交互方式：

- 告诉用户当前所在 Gate/Card。
- 提供 0-9 数字恢复候选，并保留 0 作为返回、取消或退出。
- 支持返回上一步、重试当前步骤、转人工或退出。
- 恢复动作写 TraceEvent。

## 7.1 呼叫专家摘要

Coach 只生成脱敏问题摘要，由员工或客户流程转交专家。摘要不得包含原始票据、真实系统截图、隐私原文或点击证据。

触发条件：

- 用户在 L2/L3 节点选择“我不确定”或“需要问专家”。
- 两轮澄清后仍无法匹配已发布分支。
- 规则来源冲突或规则缺失。
- 进入疑似假票、重复报销、税务合法性、资金不可逆、法律责任等 L3 场景。
- LostRecovery 重试后仍无法继续。

摘要字段：

```text
业务、旅程包、当前节点、风险级别、员工想解决的问题、已确认事实（脱敏）、
未确认/冲突、已走节点、员工已选候选、请专家判断的数字选项
```

专家回复后，员工仍通过 0-9 候选继续旅程；Coach 不替专家做结论。

---

## 8. 完成验证

到达 CompletionGate 时：

- 验证 Output.final_state 是否满足。
- 若不满足，提示差距并引导补充。
- 若满足，进入 completed 并写 TraceEvent。

---

## 9. 反馈回流

Coach 必须支持按 `remediation_set.feedback_channel` 提交反馈。

反馈至少绑定：

- package_key
- package_version
- journey_session_id
- gate_key/card_key
- feedback_type
- description
- submitted_by
- submitted_at

---

## 10. 版本和召回

- 新 session 使用最新 `published` 版本。
- 已开始 session 继续绑定进入时版本。
- `recalled` 包不可新进入。
- 如果正在执行的包被召回，Coach 完成本 session 后提示版本已更新或转人工。

---

## 10.1 离线与多语言

- 第一版不要求离线模式。
- 第二版支持离线模式：在无外网环境下播放本地已缓存的 `published` 旅程包。
- 外网受限客户可配置甲方内部 AI；Coach 不强依赖公有云 AI。
- 离线模式下若无法访问 AI，只允许使用本地缓存旅程、规则候选和已发布话术，不自由生成业务规则。
- 多语言能力不阻塞 MVP；后续接 DeepBase i18n，界面文案、图卡文案、候选项和系统提示应可国际化。
---

## 10.2 桌面环境与遗留系统兼容

- 第一版目标运行环境为 Windows 10/11 普通企业桌面。
- Delphi 13.1 已适配高 DPI、多屏和现代 Windows 桌面，Coach 首版验收应覆盖常见缩放比例、主副屏切换和悬浮窗口置顶/收起/钉住。
- Win7 不作为第一版承诺，不进入 MVP 阻塞项。
- 对仍使用 Win7 的客户，只按项目制做遗留兼容评估：功能以文字输入、已发布旅程包播放、基础图卡和本地缓存为主；语音、现代 WebView、完整高 DPI/多屏体验和外部 AI 访问不做默认承诺。
- Win7 项目必须现场验证客户运行时、补丁、显卡驱动、字体和安全策略；验收以客户实际环境可运行为准。
- 为兼容 Win7 不得牺牲 Windows 10/11 主线体验，也不得把 DeepAssist 的自动点击、证据链能力提前混入 DeepGuide。
