# Journey Protocol 设计补充：DueSet 完整覆盖

> 状态：设计沿革，关键内容已并入 `06.DeepGuide-Journey-Protocol-v1.0.md`
> 用途：解释为什么 Journey Package 必须包含 Boundary、Ability、Accountability、Seal 和 Remediation

---

## 1. 为什么需要 DueSet

早期 Journey Schema 只覆盖了 Output、Gate、Card、Route、RiskPolicy 等执行对象，但对 OCGS 的 Due 层覆盖不够。仅能播放流程，不代表治理闭合。

DueSet 补齐五类对象：

| 对象 | 解决的问题 |
|---|---|
| BoundarySet | 这个旅程适用什么，不适用什么 |
| AbilitySet | 运行旅程需要哪些前置能力 |
| AccountabilitySet | 谁创建、审核、发布、配置结果负责人、召回 |
| SealSet | 发布后是否不可原地修改 |
| RemediationSet | 错误、召回、回滚、反馈如何处理 |

---

## 2. BoundarySet

旅程包必须声明适用范围和不适用条件。边界不是说明文字，而是 Coach 进入旅程前的检查依据。

最低规则：

- MUST：每个包必须有 `scope_declaration`。
- SHOULD：高风险包应有 `not_applicable_when`。
- SHOULD：边界应覆盖地域、主体类型、业务类型。

---

## 3. AbilitySet

当前协议采用扁平数组结构，使用 `category` 区分能力类型。

```json
{
  "ability_set": {
    "abilities": [
      {
        "ability_key": "ability.invoice_system_access",
        "category": "system_permission",
        "description": "报销系统查询权限",
        "required": true,
        "if_not_met": "请联系管理员开通权限"
      }
    ]
  }
}
```

能力类别：

- `system_permission`
- `hardware`
- `customer_material`
- `personnel_qualification`
- `external_service`

规则：

- MUST：每个包必须声明 `ability_set`。
- MUST：每项能力必须标注 `required`。
- MUST：`required=true` 的能力必须说明 `if_not_met`。
- SHOULD：Coach 进入旅程前检查 required 能力。

---

## 4. AccountabilitySet

发布包必须有完整发布治理信息。

```json
{
  "accountability_set": {
    "created_by": { "name": "string", "role": "business_expert" },
    "reviewed_by": [{ "name": "string", "role": "reviewer", "reviewed_at": "datetime" }],
    "published_by": { "name": "string", "role": "admin" },
    "outcome_owner": { "name": "string", "role": "manager", "scope": "业务结果" },
    "recall_owner": { "name": "string", "role": "manager", "scope": "旅程包召回" }
  }
}
```

规则：

- MUST：`created_by` 不可为空。
- MUST：`published` 包必须有 `reviewed_by`、`published_by`、`outcome_owner`。
- SHOULD：L2/L3 包应有 `recall_owner`。

---

## 5. SealSet

发布后的旅程包不可原地修改。任何修改必须产生新版本。

```json
{
  "seal_set": {
    "immutable_after_publish": true
  }
}
```

规则：

- MUST：`published` 包不可修改任何协议字段。
- MUST：修改已发布包必须创建新版本。
- MUST：Trace 绑定 `package_key + version`，不可事后改绑。

---

## 6. RemediationSet

补救不是可选装饰，而是治理闭合的一部分。

最低包含：

- `recall_policy`：包内容错误或过期时如何召回。
- `rollback_policy`：已执行结果错误时如何标记和补救。
- `feedback_channel`：一线卡点如何回流 Studio。

规则：

- MUST：已发布包必须有召回策略。
- MUST：召回时必须提供替代包或人工 fallback。
- MUST：正在执行中的旅程不因召回被强制中断。
- SHOULD：L2/L3 包应有 rollback_policy。
- MUST：所有包必须支持 feedback_channel。

---

## 7. 风险-治理强度映射

| 风险 | 典型含义 | MUST |
|---|---|---|
| L0 | 只读/浏览 | 基础进入退出 Trace |
| L1 | 低风险可撤回 | Gate Trace |
| L2 | 影响业务记录/客户结果 | 用户确认、Trace、outcome_owner |
| L3 | 不可逆/法律/资金 | 二次确认、人工升级、禁止自动放行 |

Validator 必须把 L2/L3 缺失治理对象判为 Red。
