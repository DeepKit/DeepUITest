# DeepGuide 开发落地总纲

> 状态：开发收敛版
> 日期：2026-05-13
> 目的：把愿景文档压实成开发可以执行的边界、顺序和验收标准。

---

## 1. 产品本质

DeepGuide 不是“让 AI 自由指导业务”，而是“让 AI、专家和一线人员都受同一个旅程协议约束”。

核心资产：`Journey Package`。
核心能力：`Validator + Runtime + Trace`。
核心分工：

```text
Studio   写入端：创建、校验、审核、发布旅程包
Coach    执行端：播放已发布旅程包，执行状态机，产生 Trace
Showcase 解释端：只读展示旅程结构，不产生业务执行
Platform 协议底座：定义包结构、校验规则、状态机和治理边界
```

---

## 2. 不可妥协的开发约束

1. 协议先于界面。任何 UI 功能都必须能落到 Journey Protocol 对象上。
2. Validator 先于 Studio 完整编辑体验。没有 Validator，Studio 只是表单生成器。
3. Coach 不自由生成业务结论，只能消费已发布旅程包。
4. L2/L3 风险步骤必须暂停并等待人类确认。
5. Trace 必须绑定 `package_key + version + journey_session_id`。
6. `published` 包不可原地修改，只能召回、废弃或新建版本。
7. 行业差异通过配置包和扩展字段表达，不修改底座状态机。
8. AI 不主动猜员工需要什么帮助；入口采用独立悬浮窗口点击展开，来自员工文字提问，语音为可选增强。Coach 不介入浏览器和其它业务系统。AI 只主持多轮澄清、生成候选、提供专业意见和辅助分析，是否进入旅程由人类决定，不替业务责任人做最终决策。
9. 首版运行环境承诺 Windows 10/11 普通桌面，覆盖常见高 DPI 和多屏场景；Win7 不进入首版承诺，只作为遗留客户项目制兼容评估，不得反向牵制主架构。

## 3. MVP 切线

P0 必须先完成：

- JSON Schema 可被自动校验。
- Validator 规则可执行，至少覆盖引用完整性、路径可达、风险治理、发布门槛。
- 一个财税/会计实操正向样例旅程包和三个反例包。
- Coach 状态机最小实现设计。

P1 再做 Studio：

- Output 定义器
- Gate/Card/Route 编辑
- RiskPolicy 与 LostRecovery 编辑
- Validator 红黄绿反馈
- 审核发布

P2 再做 Coach：

- 读取最新 published 包
- 双悬浮面板：A 意图澄清对话框、B 图卡展示区
- A 面板：文字提问、可选语音、多轮意图澄清、意图候选、人类确认与数字选择
- B 面板：播放 Gate/Card/Route、线框参考图、模糊/聚焦、色框导航线、风险提示、完成验证
- 风险确认
- LostRecovery
- TraceEvent 输出

P3 再做反馈和版本治理。

V2 再做受限网络增强：离线播放已缓存 published 旅程包、甲方内部 AI 配置、DeepBase i18n。Win7 等遗留环境仅作为单独项目兼容项评估，不阻塞 P0-P3。

## 3.1 首个样板决策

首个参考行业定为财税/会计实操，首个样板业务定为发票报销材料检查。

样板角色：新入职财务助理 / 报销初审员。

样板边界：只验证员工能否按已发布旅程检查材料是否齐全、是否需要补充、是否需要专家确认。DeepGuide 不做税务结论裁判，不替单位承担合规责任，不采集证据链，不替员工点击或提交。

规则来源分三层：通用规则、单位规则、专家规则。MVP 优先单位规则和专家规则，通用规则只做背景提示。

Trace 只记录旅程过程：包版本、Gate/Card/Route、数字选择、风险确认、迷路恢复、呼叫专家、退出或完成；不记录发票原图、隐私原文、真实系统截图、员工实际点击证据或追责材料。
---


## 3.2 首条旅程开发锚点

首条旅程以 `platform/10.财税发票报销材料检查旅程规格.md` 为准。

开发锚点：

- 11 个 Gate 跑通：意图澄清、范围确认、材料接收、发票基本要素、材料形态、报销类别、附件清单、单位规则、异常扫描、结果准备、专家呼叫/完成。
- 风险分级跑通：L1 普通材料核对，L2 单位规则/后续审批影响，L3 税务合法性/资金不可逆/疑似假票或重复报销。
- 专家呼叫跑通：只生成脱敏摘要，不带原始票据、真实截图、隐私原文或点击证据。
- 样例包跑通：1 个正向闭环，3 个 Validator 反例。
- 图卡跑通：第一版只用通用线框图，后续再考虑脱敏仿真界面。

## 5. 后续讨论主题

愿景和开发之间的张力主要集中在四处：

1. “AI 主持式倒推”的理想体验 vs Validator 能否约束生成结果。
2. 行业配置包的扩张愿景 vs 底座 Schema 的稳定性。
3. 员工主动自然语言表达与多轮澄清体验 vs 受控旅程、不自由生成的安全边界。
4. DeepGuide 产品矩阵的完整愿景 vs MVP 必须只验证一个闭环。

本轮文档优化先把开发锚点钉住，后续再讨论这些张力如何分阶段释放。

## 6. DeepGuide / DeepAssist 分层

DeepGuide 当前开发只做到导航层：播放旅程、提示风险、提供迷路恢复。它不帮点击，不承诺业务证据链，不做责任裁判。

DeepAssist 是后续高级层：在红绿灯协议约束下，经用户授权后辅助点击、填写和记录辅助操作证据。

因此 P0-P3 的工程实现必须先把 DeepGuide 导航闭环做稳；ActionRun、EvidenceRecord、自动点击、截图留证等能力进入 DeepAssist 设计，不混入 DeepGuide 核心协议。
