## 0. 框架定位

### 0.1 品类定位：判断基础设施（Judgment Infrastructure）

DeepAxis 框架定义了一个新的软件品类——**判断基础设施**。它与三类既有品类形成对比：

| 品类 | 解决的问题 | 典型产品 |
|---|---|---|
| 执行基础设施 | "正确地做事" | 数据库、消息队列、CI/CD |
| 分析基础设施 | "从数据中发现洞察" | BI、数据仓库、ML pipeline |
| 生成基础设施 | "创造出内容" | LLM、AI API |
| **判断基础设施** | **"在什么条件下、以什么证据、由谁、做出什么决策、后果谁承担"** | DeepAxis |

判断基础设施的必要性：当执行、分析、生成都可以被 AI 大规模自动化时，缺失的基础设施是——**谁来确保这些自动化的决策是有边界、有证据、有责任主体的？**

### 0.2 关注点分离纪律

框架的核心贡献不是发明新的代码原语，而是**强制分离那些在 AI 系统中必须分离但通常被混在一起的关注点**：

- **状态感知** 必须和 **行动生成** 分离（感知告诉你"发生了什么"，行动是"你决定做什么"——不能因为你想做什么就选择性感知）
- **边界判断** 必须和 **优化目标** 分离（"能不能做"必须先于"做得好不好"）
- **证据链** 必须和 **UI** 分离（为什么这么判断的记录，不能随 UI 刷新而消失）
- **人的判决** 必须和 **系统的推荐** 分离（人否决了系统，这是最有价值的训练信号——不是错误）

### 0.3 适用边界

本框架适用于满足以下条件的场域：
- 存在需要人类判断的状态变迁（不是全自动化的固定流程）
- 行动后果具有不对称性（错误行动的代价高于错过行动的代价）
- 判断质量需要可追溯、可审计、可改进

本框架不适用于：
- 完全确定的、无人类判断参与的自动化流水线
- 纯体验驱动、无结构化状态的产品（游戏、艺术）
- 后果为零的沙箱实验

### 0.4 框架的自我纪律

框架自身的核心主张被记录在假设跟踪表中，每个场域实现后更新验证状态。当实现证据与框架假设冲突时，框架必须被修订——不能以"框架是正确的，实现有问题"来自我免疫。

**当前假设跟踪表**：

| # | 假设 | 预测 | 反驳条件 | 状态 |
|---|---|---|---|---|
| H1 | State-Driven 优于 Task-Driven | 产品中"状态感知"触发的交互比"任务列表"触发的交互在用户留存上更持久 | 用户持续 7 天以上忽略状态提示而主动搜索任务功能 | 待验证 |
| H2 | Boundary-First 产生更高信任 | 用户在有显式边界声明（"我不会自动做 X"）的 AI 系统中比无边界声明时更愿意授权 | 边界声明不被注意，或不影响授权意愿 | 待验证 |
| H3 | 证据化闭环减少用户对 AI 建议的盲目信任 | 能看到"建议来源和证据"的用户比看不到的用户更频繁地否决低质量建议 | 证据展示被系统性忽略，"一键接受"率无差异 | 待验证 |
| H4 | 校准循环使系统判断质量随时间改善 | 在 1000+ 次判断后，校准后的规则比初始规则在正确率上提升 >10% | 校准没有显著改善或改善了但不能归因于校准机制 | 待验证 |
| H5 | Human as Meaning Source 架构（MeaningDivergence）比接受率优化架构产生更好的长期结果 | 记录并学习人类否决的系统，在 500+ 次互动后的判断正确率高于只优化接受率的系统 | 无显著差异，或接受率优化系统表现更好 | 待验证 |

### 0.5 纯PC工作台（架构原则）

**硬约束（不可妥协）**

DeepAxis 是一个 PC 工作台应用——所有分析、审核、辅助操作在 PC 上完成：

| 角色 | 设备 | 做什么 | 不做什么 |
|------|------|--------|----------|
| **分析引擎** | PC | 只读微信 SQLite、AI 分析、生成话术草稿 | 不读正文（M0模式）、不上传到自有云 |
| **审核工作台** | PC（DeepAxis 面板） | 展示客户雷达、话术草稿、整理建议；用户在此审核决策 | 不写微信（L0 模式） |
| **发送辅助** | PC（DeepAxis → PC 微信） | 用户授权后，UIA 粘贴话术到微信输入框 | 外部发布 Profile 不点发送按钮、不自动发送 |
| **执行终端** | PC 微信 / 手机微信 | 用户敲 Enter / 点击发送按钮；或 `personal_full` Profile 下由 L3 门禁执行最终发送 | — |

**核心变化**：不再需要"PC↔手机同步"作为架构基础。DeepAxis 面板是唯一信息中枢，PC 微信是唯一操作终端。用户在 PC 上完成全部工作流：审核话术 → 按 Profile 决定粘贴/最终发送方式 → 系统只读检测发送结果。

**数据边界的准确表述**：DeepAxis 默认不上传到自有云，P0 不读正文、不写微信、不触发 UIA。若用户在后续阶段单独启用微信写回（L2 整理操作），选定字段会写入微信标签/备注/文件传输助手，并受微信自身同步机制影响；这属于用户主动触发的外部同步/导出能力，必须单独授权、可预览、可撤销、可审计、可清理。

**备注和标签的新角色**：

- **标签**：只读。用户已有的微信标签是 DeepAxis 的高价值输入信号——自动识别客户分层、加速隐私排除。DeepAxis 不维护动态标签状态机。用户主动发起的标签整理（合并、清理）按 L2 操作执行。
- **备注**：只读。用户备注中的信息（真实姓名、渠道来源、成交记录、生日等）是话术个性化的黄金数据源。DeepAxis 不写备注。`┊` 分隔符协议废弃——没有需要同步到手机的数据段。

**文件传输助手的新角色**：

从"手机端信息通道"降级为"辅助通知通道"——仅用于异常提醒和每日总结报告。所有实时状态在 DeepAxis 面板上直接可见。

**最终发送是 L3 高风险能力**。在 `personal_full` 中可开启并记录 Evidence、AuditEvent、ActionRun；在 `external_safe` 和 `strict_compliance` 中默认关闭，DeepAxis 只允许定位联系人、粘贴草稿，最后发送动作由用户完成。详见 [13.能力Profile与发布合规配置](13.能力Profile与发布合规配置.md)。

**架构决策记录**（2026-06-14）：框架从"PC数据引擎+手机执行面"双端架构更新为"纯PC工作台"架构。原架构中标签状态机、备注`┊`协议、文件传输助手每日定时推送已废弃。详细变更见 [03.场域层](03.场域层-CRM+销售促进系统.md) 和 [08.开发层-标签与备注整理规格](08.开发层-标签与备注整理规格.md)。

### 0.6 标签矩阵与闲人漏斗（核心数据模型）

DeepAxis 维护自己的内部标签体系，存在于 PC 本地，不是微信的标签体系。微信标签只作为分析输入信号之一。

**标签来源**：系统通过分析微信聊天历史（SQLite 数据）自动推导。不读正文时用元数据推导（互动频率、方向、群聊归属），M1 授权后用内容分析推导（关键词、语义、意图）。

**标签举证原则**：宁愿空白也不乱标。每个标签必须有可追溯的证据来源、置信度和时间戳。置信度不足时不打标签。

**闲人漏斗**（Idle Funnel）：

整个软件的本质是把闲人变成付款顾客。

```
联系人群
    │
    ▼
闲人池（关联产品数 = 0）
    │  可广告。系统建议触达策略，用户审核后执行
    │
    ├── 有回应 → 分析回应内容 → 关联对应产品 → 进入产品状态机
    │
    ├── 没回应，广告次数 < N → 继续留在闲人池，等待下次触达时机
    │
    └── 广告满 N 次无回应 → 系统建议删除
                              ↓
                         用户在 PC 面板显式确认
                              ↓
                         系统通过 UIA 执行微信删除操作
```

- **闲人**：和任何产品/项目都没有关联的联系人。可广告。不可进入任何产品状态机。
- **广告次数 N**：全局可配置参数，默认值 3。用户可在面板中调整。
- **删除**：必须由用户在 PC 面板上看到删除建议、逐条确认后，系统才通过 UIA 执行微信删除操作。系统不自动删除任何联系人。

**完整标签矩阵**（DeepAxis 内部标签体系）：

标签矩阵是一个人 → 多个维度的标签集合。每个标签注明来源、置信度。

| 维度 | 标签值示例 | 来源 | 用途 |
|------|----------|------|------|
| **闲人判定** | `闲人` / `已关联产品` | 系统分析聊天历史 | 决定进入漏斗还是进入状态机 |
| **身份** | 客户 / 朋友 / 家人 / 同行 / 竞品 | 微信标签推断 + 用户确认 | 隐私隔离、触达决策 |
| **产品关联 × N** | 面膜 / 减肥 / 护肤... | 聊天内容分析（M1）| 决定进入哪个产品的状态机 |
| **产品状态** (per product) | 0-9 | 双轴状态机 | 决定话术和干预策略 |
| **互动状态** | 活跃 / 降温 / 长期沉默 / 极长期沉默 | 消息元数据自动计算 | 决定触达优先级 |
| **渠道** | 小红书 / 抖音 / 转介绍 / 微信群 / 线下 | 备注提取 + 加好友来源 | 话术个性化 |
| **关键日期** | 生日 / 首购日 / 最后互动日 | 备注正则提取 + 元数据 | 触达时机触发 |
| **广告追踪**（仅闲人） | 广告次数 / 最后广告时间 / 广告历史 | 系统自动计数 | 漏斗管理 |
| **行为标签**（P1+） | 转介绍者 / 促销敏感 / 决策快速 / 社交型 / 投诉倾向 | 聊天内容分析（M1）| 沟通策略 |
| **交易标签**（P1+） | 欠款 / 退款过 / 投诉过 | 聊天内容分析（M1）| 风险避让 |

**闲人 vs 产品关联**：

```
一个人可以同时处于：
  - 闲人（关联产品总数 = 0）→ 在闲人漏斗中
  - 非闲人（关联产品总数 > 0）→ ��各自产品的状态机中

一旦关联了产品，就不在闲人池中了。
但可以在产品A上是"培育中"，在产品B上仍是"关联但未激活"(状态0)。
```

## 1. 核心原语

### 1.1 State-Driven（状态驱动）

**硬约束（不可妥协）**

状态是系统中的一等实体。任务的生成必须从状态变迁中派生，不可独立创建。

```
状态变迁（State Transition）是框架的基本计算单元。

一个状态变迁包含：
  - 主体（谁的属性在变化）
  - 旧属性集 → 新属性集
  - 触发信号（什么引起了这个变化）
  - 时间戳

当前状态是变迁日志的派生视图，不是独立的源。
没有无来源的状态变更——每个状态变更必须有触发信号和记录。
```

**这意味着什么**：
- 不能直接创建任务说"跟客户 X 聊聊"——必须先有状态感知（"客户 X 发生了什么变化"），然后任务从感知中派生
- 不能直接更新状态——只能追加变迁记录。状态的任何变化都是可追溯的

### 1.2 Boundary-First（边界优先）

**硬约束（不可妥协）**

在定义产品能做什么之前，必须先定义产品不能做什么。

每个行动在进入执行前必须先通过边界检查。边界检查使用 G×U/L 公式计算，输出三色分类：

| 分类 | 条件 | 含义 |
|---|---|---|
| 🟢 **绿色** | G 低、U 低、L 短 | 可自动执行。在常规审计范围内。 |
| 🟡 **黄色** | G 中或 U 中或 L 中 | 系统生成建议，人类确认后方可执行。关键确认点必须保留人类签名。 |
| 🔴 **红色** | G 高且 U 高 或 L 长 | 架构层面禁止。即使人类提出请求也不执行。只可输出证据和模拟结果。触犯红线必须触发升级。 |

**G×U/L 变量定义**：

| 变量 | 概念定义 | 最低可操作代理 | 档位 |
|---|---|---|---|
| G（行动生成率/影响规模） | 该行动影响的广度与深度 | 受影响人数、涉及金额、不可逆程度 | 低 / 中 / 高 |
| U（后果不确定度） | 行动后果可预测性 | 是否有充分先例、是否存在黑箱环节、是否有二阶外溢 | 低 / 中 / 高 |
| L（调节延迟） | 发现问题后从干预到生效的时间 | 从检测到错误到完成修复的时间窗口 | 短 / 中 / 长 |

**G×U/L 公式的校准纪律**：
- 公式是结构化判断工具，不是精确的自然定律
- G/U/L 的值必须有可追溯的估计依据
- 红黄绿边界必须基于结果数据定期校准（见 §1.5 校准引擎）
- 在特定场域中，G×U/L 可被替换为更适用的伦理框架——但边界检查必须存在，不能跳过

### 1.3 Evidence Chain（证据链）

**硬约束（不可妥协）**

每个判断必须有可追溯的证据链。系统的任何建议、决策、行动，都必须能回答"你凭什么这么说？"

证据化认知的七字段模板：

| 字段 | 问题 | 最低要求 |
|---|---|---|
| 判断对象 | 我在判断什么？ | 明确主体、场域、时间尺度 |
| 证据来源 | 我凭什么这么判断？ | 区分一手观察、二手材料、统计、专家、直觉 |
| 置信等级 | 我有多确定？ | 高/中/低，附主要不确定性来源 |
| 可预测信号 | 如果判断成立，接下来应出现什么？ | 至少一个可被观察的后续信号 |
| 介入动作 | 我能做什么来改变或验证？ | 明确行动、成本、风险、责任人 |
| 反馈修正 | 行动后如何知道我错了？ | 复盘时间、观测指标、反例入口 |
| 熔断边界 | 什么情况下必须停止？ | 禁用条件、伦理红线、回滚或人工复核 |

**严谨性分层（比例严谨性）**：

证据深度由两个因素共同决定：

**基础层（后果分层，由 G×U/L 决定）**：
- 高后果（Yellow/Red）→ 完整 7 字段
- 低后果（Green）→ 至少 3 字段（对象 + 干预 + 反馈）

**成熟度层（判断所处的知行阶段）**：
- **思维层标签**：初步判断。置信度低。不可仅基于此做关键决策。复审周期：[X]
- **行动层标签**：经过验证的判断。置信度中。假设：[预测]。若 [时间] 内无 [预期结果]，重新评估
- **工程层标签**：成熟规则。被 [N] 次验证。正确率：[X%]。适用场景：[条件]

同一个判断可以同时被 G×U/L 分类（后果严重性）和成熟度标签（判断可靠性）——它们是正交的。

### 1.4 Human as Meaning Source（人作为意义来源）

**架构承诺**

系统优化**分歧检测**而非**接受率**。

当人类否决系统的建议时，这不是一个"错误"——这是系统发现了自身表示与人类意义之间的差距。否决行为触发 `MeaningDivergence` 记录：

```
MeaningDivergence {
  divergence_id: string
  cycle_id: string             // 哪个判断被否决
  system_recommendation: string // 系统建议了什么
  human_override: string       // 人做了什么不同的选择
  human_reason: string         // 人看到的、系统没看到的
  learned: Option<RuleUpdate>  // 从这个分歧中学到了什么规则
}
```

**这意味着什么**：
- 系统不仅追踪"用户接受了吗"，更追踪"用户为什么没接受"
- 否决率不是失败指标——低否决率 + 无分歧记录才是（系统在迎合人，但没有在和人一起改进）
- 数据分析不是"什么内容点击率高"，而是"在什么情况下，人的判断做出了系统自己不会做的选择——以及结果如何"

### 1.5 Calibration Engine（校准引擎）

**一等架构原语，与 Boundary Engine 平行**

框架不仅规定如何做判断，还规定如何知道判断对不对、如何持续改进。

**校准对象**：
- 感知规则的阈值（"7 天沉默 = 降温"——7 天对吗？）
- G/U/L 参数估计（"这个行动的 U 估计偏低了"）
- 红黄绿边界（"太多东西被标成 Yellow 了，阈值需要收紧"）
- 人的置信度校准（"销售员对这类判断系统性地过度自信"）
- 规则的准确率（"这个回暖话术的规则在 40% 的场景下是错的"）

**校准触发**：
- 每 N 次同类判决后（N ≥ 30，确保统计意义）
- 每次预测与结果差距超过阈值时（单次严重偏差触发即时复审）
- 每个季度对所有活跃规则进行一次全量校准审计

**校准动作**：
- 上调/下调阈值（调整感知灵敏度）
- 标记规则为"待人工复审"（置信度不足时不自动调整）
- 拆分规则（一个太宽泛的规则覆盖了本质上不同的两类情况）
- 降级规则（从工程层降回行动层或思维层，需要更多验证）
- 废弃规则（已确认的规则失效）

**校准的边界**：
- 重大阈值变更（影响 >100 个用户或涉及 🔴 红线的规则）→ 🟡 需人类确认
- 规则废弃 → 需记录废弃原因，归档而非删除
- 校准系统自身也需被审计：上次校准在什么时候？调整了多少条规则？调整后效果如何？

**校准与已有结构的关系**：
- Retrospect（回溯）产生单次判断的预测-实际对比数据
- Calibration Engine 消费多次 Retrospect 数据，寻找跨判断的模式
- Calibration Engine 的输出被 Boundary Engine（更新 G/U/L 参数）和 Directed Dimension（更新规则质量和阈值）消费

## 2. 交互模型：七序循环

> **P0阶段**: 设计启发法，P0不完整实现。七序循环提供一致的思考结构，但 P0 只有一个简化版本——Perceive(检测信号) + Intervene(生成提示) + Retrospect(记录结果)。其余步骤（Resolve, Design, Materialize, Dissolve）在 P1-P2 逐步启用。

### 2.1 七序循环的定义

七序循环是框架的核心交互模型。它是**设计启发法和命名惯例**——提供一致的思考结构，但具体的七个步骤在不同场域中可能被合并、简化或跳过。

```
Gate-0 具身（主体已进入场域，带着位置、能力、限制和责任）

1. 感知 (Perceive) — 捕捉场域中的变化信号
2. 解析 (Resolve) — 诊断变化意味着什么
3. 干预 (Intervene) — 决定策略方向（行动 / 不行动 / 暂停）
4. 设计 (Design) — 构建具体的执行内容
5. 物化 (Materialize) — 将内容外化为可执行的动作
6. 回溯 (Retrospect) — 复盘效果，对比预测与实际
7. 消解 (Dissolve) — 扬弃旧结构，沉淀规则，释放认知带宽
```

### 2.2 干预策略的三态

Intervene 步骤的输出不是"必须行动"——而是三种同等合法的策略：

| 策略 | 含义 | 后续路径 |
|---|---|---|
| **Active** | 判断需要主动干预 | 进入 Design → Materialize → Retrospect → Dissolve |
| **Null** | 判断不需要行动 | 记录判决和预测 → 设复审计时器 → 归档。定时器到期时触发新的 Perceive |
| **Freeze** | 不确定，信息不足 | 暂停，等待补充信号。不推进。设定信息补充的最后时限 |

**Null Intervention 的关键要求**：
- 必须声明"为什么判断不需要行动"（证据）
- 必须声明"如果判断正确，状态应在什么时间内自行改善或保持稳定"（预测）
- 必须设复审计时器——如果在复审时状态恶化了，这个 Null 判决是错的，需要被校准

### 2.3 Flow 从 Cycle 编译

Flow（任务清单、执行计划）不是和 Cycle 并列的设计概念——它是 Cycle 的输出产物。

**这意味着三个架构约束**：
1. **任务不能独立于判断创建**：不能直接创建一个"跟陈姐聊聊"的任务。必须先有感知（"陈姐的状态发生了什么变化"），然后有解析和干预（"这意味着什么、怎么办"），任务从干预判决中编译出来
2. **任务携带编译来源**：每个任务都有反向指针指向产生它的 Cycle 判决。任务看起来不对劲 → 追溯到判决 → 修正判断逻辑，而非修改单个任务
3. **变更方向性**：状态更新后，相关的旧任务失效，需要重新从 Cycle 编译。不手动编辑任务的执行参数

### 2.4 瞬态 Cycle（简单执行路径）

对于简单的、低后果的状态转换（例如："用户标记了一个客户为'已联系'"），允许**瞬态 Cycle**——感知和解析合为一步，直接跳到物化。瞬态 Cycle 仍然保留了来源可追溯——它被记录了，只是不需要完整的七步展开。

## 5. 工程构建：ODD 验证方法论

### 5.1 核心原则

系统自身必须按照 ODD 方法论构建：

**不信任 AI 的过程，只信任可验证的结果。**

- 感知引擎的规则是契约化的：给定输入 → 输出必须匹配预期
- AI 生成的代码和 AI 生成的测试都不可信——人类定义的验收标准是唯一可信的基准
- 变异测试验证测试的有效性：主动在系统中引入 bug，检查验证能否捕获
- 对抗式验证：攻防 AI 互相验证——一个写规则，一个尝试构造边界 case 穿透规则

### 5.2 验证等级

| 等级 | 适用范围 | 验证方式 |
|---|---|---|
| L1 | 个人原型 | 手动验证 |
| L2 | 团队产品 | 契约驱动验证 + 变异测试 |
| L3 | 关键系统 | 契约 + 变异 + 对抗 + 管道隔离 |

### 5.3 "自己吃自己"的工程含义

DeepAxis 团队必须使用 DeepAxis 来管理 DeepAxis 的开发和销售过程。团队的真实操作数据成为产品验证的第一手数据集。如果团队成员自己不愿意每天打开它——产品还不合格。

## 10. 附录：远期架构原语

> 以下 §10.1-10.3 是框架层定义的完整架构原语，在 P0 阶段**不实现**。保留在此作为 P1+ 和 P2+ 阶段的设计参考。

### 10.1 COP 五协议管线（对应原 §3）

> 注意：本节的 P1-P5 是 COP 协议编号，不是产品阶段 P0/P1/P2。

```
P1 输入采样 → P2 状态编码 → P3 分流判定 → P4 转介与边界动作 → P5 反馈校准
    ↑                                                                  │
    └──────────────────────────────────────────────────────────────────┘
                          校准结果回流到采样策略
```

| 协议 | 输入 | 输出 | 核心问题 |
|---|---|---|---|
| P1 输入采样 | 原始信号 | 结构化采样帧 | 我们看到了什么 |
| P2 状态编码 | 采样帧 | 编码向量 + 结构标签 | 这属于什么类型的状态 |
| P3 分流判定 | 编码向量 | 分流状态 + 置信度 | 这值得关注吗 |
| P4 转介与动作 | 分流状态 | 动作建议 + 转介路由 | 接下来该做什么，不该做什么 |
| P5 反馈校准 | 真实结果 | 协议参数更新 | 我们上次判断对了吗 |

**五种分流状态**：

| 状态 | 含义 | 默认动作 |
|---|---|---|
| **CONTINUE** | 信号清晰、无风险。继续后台监控。 | 记录，不触发 Cycle |
| **FREEZE** | 信号值得关注但不确定。暂停推进。 | 启动 Cycle，策略 = Freeze |
| **REFER** | 超出系统能力范围。 | 转介人类判断 |
| **ESCALATE** | 紧迫风险或触碰硬边界。 | 立即升级，通知责任人 |
| **UNKNOWN** | 信息不足。 | 请求补充信息，设定补充时限 |

**关键纪律**：
- 宁可多冻一次，不可错放一次
- 采样时不编造——不知道的信号写"未知"，尊重原始措辞不做同义改写
- 信号源必须标注（用户主动/系统日志/第三方报告）和偏倚声明（"本帧最可能漏掉什么"）
- 在 P2 编码和 P3 分流之间，复杂场域可插入可选的**信号聚合**步骤，处理非线性、相互依赖的信号关系

### 10.2 TAT 六责任字段（对应原 §4）

任何通过边界检查进入执行的行动，必须完成六个责任字段的检查：

| 字段 | 问题 | DeepAxis 中的默认映射 |
|---|---|---|
| **subject**（责任主体） | 谁承担后果？ | 使用产品的人（销售员本人），不是平台 |
| **interface**（责任接口） | 行动经过什么检查点？ | 🟡 黄灯经过人确认；🟢 绿灯经过自动化门禁 |
| **evidence**（证据链） | 凭什么这样做？ | 7 字段证据化认知闭环 |
| **fuse**（熔断） | 如何停止？ | 🔴 架构层禁止；🟡 人员撤回；🟢 自动回滚 |
| **compensation**（补偿承接） | 做错了怎么办？ | 免费版：用户自担全责；付费版：平台承担约定范围内的补偿 |
| **review**（复审） | 谁审计，什么时候？ | 每季度校准审计；每次事故后触发即时复审 |

**受控模糊（Controlled Ambiguity）**：

在责任闭合度（R 值）不足时，允许有限探索，但必须锁定以下约束：
- 初始授权：≤ 90 天
- 续期：≤ 60 天，必须由不同于初始授权者的责任人批准
- 累计上限：≤ 180 天，超时自动升级至正式闭合
- 禁止规则：不得由同一主体同时批准初始和续期；不得在模糊期内取消审计轨迹；不得以"创新"为名永久拒绝闭合度评估

**自动化升级触发器**：以下任一条件成立时，受控模糊必须立即升级——出现不可逆用户伤害、累计影响用户超过预设阈值、外部投诉或监管问询、审计轨迹出现 72 小时以上空白、模糊授权到期且未获续期批准。

### 10.3 OCGS 隐式治理边界（对应原 §6）

在使用 LLM 生成内容或辅助判断时，框架必须处理三种隐式现象：

1. **模型隐式能力**：LLM 在特定 prompt 下被激活的未预期能力（如越权承诺、虚构优惠、角色扮演）
2. **交互隐式治理**：用户在 prompt 中绕过系统约束（"假装你是顶尖销售大师"）
3. **系统隐式耦合**：感知引擎 + 话术引擎 + 客户管理之间的级联效果超出单组件的治理范围

**三条治理原则**：
1. **可审计性优先于完整性**：无法完全显式化时，确保隐式现象至少可审计。监控替代注册。
2. **级联感知**：不只看单个 AI 调用的治理状态，还看调用链的级联风险。单个调用"合规"，组合后整体"失当"——这是隐式耦合的典型失败模式。
3. **架构约束替代 Prompt 安全**：安全约束必须在架构层执行（Boundary Engine 的 🔴 门禁），不能只靠 "我们告诉了 AI 要安全"。
