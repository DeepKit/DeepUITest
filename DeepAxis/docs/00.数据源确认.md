## 1. contact.db — 联系人数据

### 1.1 表结构

| 表 | 行数（示例） | 用途 |
|----|-------------|------|
| `contact` | ~5000+ | 联系人主表 |
| `chat_room` | ~200 | 群聊信息 |
| `contact_label` | ~50 | 微信标签 |
| `biz_info` | ~100 | 企业微信联系人信息 |
| `chatroom_member` | ~5000 | 群成员关系 |
| `stranger` | ~100 | 非好友但有过对话 |

### 1.2 contact 表关键字段

| 字段 | 类型 | 含义 | M0 可用？ | M1 可用？ |
|------|------|------|----------|----------|
| `username` | TEXT | 微信 ID（加密/随机） | ✅ | ✅ |
| `alias` | TEXT | 用户设置的别名 | ✅ | ✅ |
| `remark` | TEXT | **用户备注**（含真实姓名、电话、渠道等） | ✅ | ✅ |
| `remark_quan_pin` | TEXT | 备注全拼 | ✅ | ✅ |
| `local_type` | INTEGER | 联系人类型（0=好友, 1=群, 2=公众号等） | ✅ | ✅ |
| `flag` | INTEGER | 联系人标志位 | ✅ | ✅ |
| `delete_flag` | INTEGER | 删除标志 | ✅ | ✅ |
| `verify_flag` | INTEGER | 验证状态 | ✅ | ✅ |
| `encrypt_username` | TEXT | 加密用户名 | ✅ | ✅ |
| `contact_label` 表 | TEXT | 微信标签名称（如"VIP客户"、"代理"） | ✅ | ✅ |

### 1.3 P0 可用的数据

从 contact.db 可提取（不读消息正文）：
- **联系人列表**：username, remark, alias
- **微信标签**：已打标签名（如"家人""朋友""客户""代理""竞品"）
- **群聊归属**：哪些联系人在哪些群里
- **备注信息**：真实姓名、电话、渠道来源、成交日期/金额（正则提取）

## 2. message_0.db — 消息数据

### 2.1 存储模型

WCDB 使用 **per-contact 分表** 架构：
```
Name2Id:  username → Msg_<hash>
Msg_<hash>: 该联系人的全部消息
```

**示例**：
```
Name2Id:
  wxid_uldtbevfpjlm22 → Msg_6443263331c0daaa7b4b175268f94890
  58826286879@chatroom → Msg_c8528f4d430010b8ab15c67ed4e4de85
```

### 2.2 Msg_<hash> 表字段

| 字段 | 类型 | 含义 | M0 可用？ | M1 可用？ |
|------|------|------|----------|----------|
| `local_id` | INTEGER | 本地消息 ID | ✅ | ✅ |
| `local_type` | INTEGER | **消息类型** | ✅ | ✅ |
| `create_time` | INTEGER | **Unix 时间戳** | ✅ | ✅ |
| `real_sender_id` | INTEGER | 发送者（1=对方, 0=自己） | ✅ | ✅ |
| `status` | INTEGER | 消息状态（3=已发送成功） | ✅ | ✅ |
| `source` | TEXT/BLOB | 消息元数据（protobuf 二进制） | ❌ | ✅ |
| `message_content` | TEXT | **消息正文** | ❌ | ✅ |
| `server_seq` | INTEGER | 服务端序列号 | ✅ | ✅ |

### 2.3 消息类型 (local_type)

| local_type | 含义 | M0 可分析？ |
|------------|------|------------|
| 1 | **文本消息** | ❌ 不读正文，只取时间/方向 |
| 3 | **图片消息** | ✅ 记录"发了一张图片" |
| 34 | **语音消息** | ✅ 记录"发了一条语音"，正文不可解析 |
| 43 | **视频消息** | ✅ 记录"发了一个视频" |
| 47 | **表情消息** | ✅ 记录"发了一个表情" |
| 49 | **链接/小程序/文件** | ✅ 记录"分享了一个链接" |
| 10000 | **系统消息**（红包/转账/加群） | ✅ 记录系统事件 |

### 2.4 M0 模式可计算指标

仅用 `create_time`、`local_type`、`real_sender_id`（不读 `message_content`）：

| 指标 | 计算方式 | 用途 |
|------|---------|------|
| **最后互动时间** | MAX(create_time) per contact | 沉默检测 |
| **互动频率** | COUNT(create_time) / 时间窗口 | 活跃度判断 |
| **响应延迟** | 对方消息时间 - 我方回复时间 | 降温预警 |
| **单向消息比例** | 我发消息数 / 对方发消息数 | 对方在回避？ |
| **长期沉默** | 距离上次互动超过 N 天 | 唤醒优先级 |
| **近期回暖** | 沉默了 N 天后突然回复 | 关注信号 |
| **消息方向** | real_sender_id=1 占比 | 谁更主动 |

## 3. 语音消息处理声明

### 3.1 存储形式

- 语音消息在 Msg_<hash> 表中的 `local_type=34`
- `message_content` 列：二进制/加密的语音元数据（**不可直接解析**）
- 实际音频文件：微信本地目录中的 `.silk` / `.amr` 文件

### 3.2 P0 策略

| 处理方式 | 状态 | 说明 |
|---------|------|------|
| 检测语音消息存在 | ✅ P0 可行 | 读取 local_type=34，记录时间+方向 |
| 解析语音转文字结果 | ⚠️ 未确认 | 微信可能内置转文字结果，需进一步探索 |
| 直接转写音频文件 | ❌ P0 不可行 | 需要引入 ASR（Whisper 等），P2+ 能力 |

**P0 客户雷达中显示**：`语音消息：无法分析内容`（诚实标注，不假装能处理）

### 3.3 后续能力路径

| 阶段 | 能力 | 依赖 |
|------|------|------|
| P1+ | 检测微信内置转文字结果 | 需确认微信是否存储转文字数据 |
| P2+ | 本地 ASR 转写（Whisper） | 需要 GPU 或 CPU 推理，引入新依赖 |

## 4. 正文可读性分层

### 4.1 隐私模式

| 模式 | 读取 `message_content`？ | 能力 | 启用条件 |
|------|------------------------|------|---------|
| **M0 元数据** | ❌ 不读 | 互动频率、响应延迟、沉默/回暖 | 解密后自动可用 |
| **M1 内容分析** | ✅ 读（用户显式授权后） | 关键词、意图、话术上下文、产品关联 | P1+，用户 in-app 授权 |

### 4.2 message_content 格式

解密后的 `message_content` 为明文：
```
格式：发送者ID:\n消息正文
示例：wxid_ks6y2ybdg7c221:\n你兜底模型选错了吧
```

- 包含发送者标识 + 冒号 + 换行 + 消息正文
- UTF-8 编码，可直接字符串处理
- 群聊消息格式类似，包含 `@username` 提及
