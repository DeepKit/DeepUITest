# DeepAxis 序枢的由来

  ASTO Business Orchestration Layer
  = 持续感知客户业务状态，并按七序循环调度 Agent / App / 人类的业务智能体运行层

  不是 Workflow Engine，不是 Agent Router，也不是 SaaS 自动化工具。

  核心判断
  当前最优中心应该是 Cycle Runtime，不是 Flow。

  旧中心：Workflow / Flow / Step
  新中心：Business State / ASTO Cycle / Intervention

  Flow 只适合作为“执行图”，不适合作为“业务大脑”的本体。因为 Flow 假设流程已知，而你要做的是持续发现问题、判断问题、设计干预、执行、复盘、沉淀
  客户定向维。

  七个核心模块

  1. Connector Fabric
     连接多个 App 和多个 Agent。每个能力必须声明输入输出、副作用、风险、幂等、可逆性、补偿方式。

  2. Business State Layer
     这是业务大脑的感知层。不要只存事件，要形成客户业务状态：客户、线索、项目、合同、任务、内容、风险、承诺、待办、异常。

  3. ASTO Cycle Runtime
     系统主循环。每次不是“跑一个流程”，而是启动一个 CycleInstance：

  Perceive → Resolve → Intervene → Design → Materialize → Retrospect → Dissolve

  4. Directed Dimension Store
     这是护城河资产。存客户的约束集、映射规则、自检机制、红线、审批规则、业务偏好、历史干预效果。

  5. Boundary Engine
     负责判断某动作能不能自动化：

  绿灯：自动执行
  黄灯：人机协同，需确认
  红灯：只给证据和模拟，不允许自动裁决

  6. Execution Runtime
     只负责执行，不负责决定。它接收 ASTO Runtime 编译出来的 ExecutionGraph，然后调用 App、Agent、人工审批、等待回调、重试、补偿。

  7. Evidence & Audit Ledger
     所有判断都必须留下证据：为什么感知到问题，为什么这样解析，为什么选择这个干预，谁授权，结果如何，是否消解。

  关键数据模型

  BusinessSignal        外部系统来的原始业务信号
  BusinessState         客户当前业务状态
  StateDelta            状态变化
  CycleInstance         一次 ASTO 七序循环
  ProblemFrame          被解析出的真实问题
  EvidenceBundle        证据包
  InterventionPlan      干预方案
  BoundaryDecision      自动/确认/阻断/冻结
  ExecutionGraph        可执行动作图
  ExecutionRun          一次执行记录
  RetrospectiveReport   回溯报告
  DirectedDimension     客户定向维资产

  历史最小闭环假设（已被当前 P0 技术门禁取代）

  注：本节保留为产品由来，不再作为当前开发范围。当前 P0 唯一开发入口是 `docs/07.开发层-P0技术验证规格.md`。

  先不要做通用 Flow 编辑器，也不要先做 Agent 市场。

  当时的最小闭环假设是：

  1. 接 3 个系统：CRM、邮件、IM。
  2. 做 BusinessState 和 DirectedDimension。
  3. 跑一个高价值场景：线索转化/客户跟进/内容销售自动化。
  4. 实现七序循环的最小闭环。
  5. 加红黄绿边界和人工确认。
  6. 所有动作进入证据链和回溯报告。

  一句话
  当前最优架构是：
  以 BusinessState 为感知对象，以 ASTO Cycle Runtime 为中枢，以 DirectedDimension 为客户资产，以 Boundary Engine 管住自动化边界，以 Connector
  Fabric 调用外部 App 和 Agent。Flow 不做中心，只做被编译出来的执行图。



 这是一个智能体框架吗? 它的准确定义是什么?


• 是，但不能简单叫“智能体框架”。

  如果“智能体框架”指 LangChain / AutoGen 那类：帮你创建 Agent、接工具、做多 Agent 协作的开发框架，那它不是这个层级。

  它的准确定义应该是：

  > 一个以业务状态变迁为核心对象、以 ASTO 七序循环为控制模型、以定向维和边界引擎为治理约束，持续调度 Agent、App 和人类完成业务干预的状态化业
  > 务智能体运行层。

  更短一点：

  > ASTO 驱动的业务智能体编排运行时。

  或者产品化表达：

  > 持续在线的业务大脑运行框架。

  它的计算单元不是 Agent，也不是 Workflow，而是：

  Business State → Problem Frame → Intervention → Execution → Retrospect → Dissolve

  所以它和普通 Agent Framework 的区别是：

  普通智能体框架：
  用户任务 → Agent 规划 → 工具调用 → 输出结果

  你的架构：
  业务状态 → 七序循环 → 业务干预 → 多 App / 多 Agent 执行 → 证据回溯 → 定向维沉淀

  因此它包含智能体框架，但高于智能体框架。

  更准确的分类是：

  Business Agent Runtime
  业务智能体运行时
  跨系统编排层

  + Governance Runtime
  + Business Memory Layer
  客户定向维沉淀层

  我会避免把它叫成“Agent Framework”，因为这个词会让人误解成“又一个造 Agent 的工具包”。

  最准确的定义是：

  > ASTO Business Agent Runtime：一种面向客户业务状态的长期运行智能体系统。它通过持续感知业务场域、解析状态张力、设计干预路径、调度能力 Agent
  > 与外部 App 执行、回溯效果并沉淀客户定向维，形成可审计、可中断、可演化的业务智能循环。

  一句话定位：

  > 它不是做 Agent 的框架，而是让 Agent 在真实业务中持续负责地工作的运行层。

 DeepAxis for Customer Success
  最终定位：

  > 序枢 DeepAxis：有边界的业务智能体运行时。

，第一款落地产品可以非常像：

  > CRM + 销售促进 + 微信/企微业务大脑

  但准确定义不是“再做一个 CRM”，而是：

  > 以微信/企微客户互动为主要业务场域，持续感知客户状态、推动销售跟进、沉淀客户规则的销售增长运行中枢。

  关键区分
  CRM 记录的是：

  客户是谁
  阶段是什么
  负责人是谁
  预计成交多少
  下一步动作是什么

  序枢 DeepAxis 要做的是：

  这个客户现在真实状态如何
  为什么停滞
  该不该跟进
  用什么方式跟
  谁来确认
  跟完有没有推进
  哪些规则以后要记住

  所以它不是替代 CRM，而是站在 CRM 和微信/企微之上，持续跑销售七序循环。

  微信是不是中心？
  在中国中小企业场景，答案基本是：是，但更准确说是企微/微信生态为业务场域中心，CRM 是结构化账本。

  推荐架构是：

  微信/企微/群聊/私聊/朋友圈/公众号/小程序

  客户互动信号层
          ↓
  Business State 客户状态层

          ↓

  第一版产品形态
  我建议叫：

  > 序枢 DeepAxis for Sales
  > 微信/企微中心的客户增长运行中枢

  它的第一屏不是流程编辑器，而是：

  今日该跟进客户
  停滞商机
  高意向客户
  风险客户
  待确认发送
  销售动作复盘

  核心能力

  1. 从微信/企微互动中感知客户状态。
  2. 识别客户升温、沉默、异议、流失风险。
  3. 生成跟进建议和话术草稿。
  4. 需要销售确认后再发送关键消息。
  5. 自动补全 CRM/SCRM 记录。
  6. 每周回溯：哪些动作有效，哪些客户推进了。
  7. 沉淀客户定向维：行业话术、禁区、节奏、成交信号、风险规则。

  重要边界
  不要把个人微信外挂、自动群控、私聊爬取作为核心能力。这类方式商业风险和平台风险都高。

  企业微信优先
  SCRM/CRM 接入
  人工授权导入

  一句话定位
  > 我们不是给你装一个 CRM，而是给你的销售团队放一个持续在线的客户跟进大脑。它每天从微信/企微和 CRM 里看客户状态，告诉你该跟谁、怎么跟、谁要
  > 确认、跟完有没有结果。
