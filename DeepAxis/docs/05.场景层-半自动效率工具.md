## 0. 设计动机

DeepAxis 不是"帮你分类客户"的工具。分类只是手段。用户真正的需求是：

- "我该跟谁聊？"
- "我该说什么？"
- "能不能一次跟好几个人聊但又不显得像群发？"

半自动效率工具是用户**每天打开 DeepAxis 的价值锚点**。如果一个用户打开系统，看到的是一张分类好的表格，她可能会觉得"很整齐，但有什么用？"如果她打开系统，看到的是三条可以一键准备并由自己最终发送的个性化消息，每条对应一个她正在丢掉的客户，她就会说"这值得。"

## 1. 设计红线（必须先声明）

| 红线 | 内容 |
|---|---|
| 🔴 | 最终发送是 L3 能力。`personal_full` 可开启；外部发布 Profile 默认关闭，必须由用户完成最后发送 |
| 🔴 | 回复建议只能做口吻适配，不能伪造身份、关系、事实或承诺 |
| 🔴 | 群发不能使用相同的文案。每个接收人看到的必须是基于个人上下文的变体 |
| 🔴 | 私人联系人不能收到任何营销信息建议 |
| 🔴 | 不能在一个群发批次中选择超过该联系人状态匹配的接收人 |
| 🔴 | DeepAxis 绝不代替用户承诺价格、优惠、交付时间或售后条件 |

**架构约定**（与框架层 0.5 节一致）：
- DeepAxis 的本地面板是唯一交付渠道；微信写回属于外部同步/导出能力，必须单独授权
- 备注整理按 L2 操作执行（用户主动发起、预览确认后追加写入），不承载话术
- 发送动作有两种模式（辅助/手动），辅助模式为默认
- 辅助模式中的 UIA 操作仅负责"定位联系人 + 粘贴话术"，不负责"按回车"

## 2. 半自动回复（1:1 私聊）

### 2.1 触发时机

当用户打开 DeepAxis 的"需要关注"面板时，系统不是只显示一个名单，而是为每个需要关注的客户**附带一条可以直接发送的消息草稿**：

```
┌──────────────────────────────────────────────────┐
│  🔥 正在降温 — 47 人                                │
│                                                  │
│  这些人最近回复变慢了。趁他们还热，发一条消息。            │
│                                                  │
│  ┌──────────────────────────────────────────────┐│
│  │ 👤 张伟                                       ││
│  │   上次活跃: 5 天前                              ││
│  │   回复速度: 30分钟 → 2小时 → 1天 (↓)            ││
│  │   上次对话: "这个面膜效果怎么样？"                  ││
│  │                                              ││
│  │   💬 建议消息:                                 ││
│  │   ┌────────────────────────────────────┐     ││
│  │   │ 伟哥，上次你问的那个面膜，我这边刚补了一批  │     ││
│  │   │ 现货。你要不要我把活动信息发你看下？       │     ││
│  │   └────────────────────────────────────┘     ││
│  │   [ 编辑 ]  [ 准备发送 ]  [ 换一条建议 ]        ││
│  └──────────────────────────────────────────────┘│
│                                                  │
│  💰 M1 授权后：高意向待确认 — 23 人                   │
│  ...                                             │
└──────────────────────────────────────────────────┘
```

### 2.2 消息生成逻辑

每条建议消息由三个要素拼合：

```
消息 = 称呼 + 上下文引用 + 目的引导

称呼:   备注名/昵称
上下文: 引用上次对话中的具体内容
目的:   根据当前状态推断的行动建议
```

| 客户状态 | 上下文引用 | 目的引导 |
|---|---|---|
| 降温 (7) | 上次对话主题 | "最近怎么样，上次聊的那个你还用吗？" |
| 有兴趣未成交 (3) | "你上次问的XX" | "最近有活动/有新货/想了解一下吗？" |
| 洽谈中 (4) | 最后的异议 | "上次你说价格的问题……" |
| 培育中 (2) | 之前聊过的非商业话题 | 关心型："最近忙不忙？" |
| 已首购+沉默 (5+7) | 购买的产品 | "上次买的XX用完了吗？感受如何？" |

### 2.3 消息变体

同一个客户不应每次都收到相同风格的消息。系统生成 3 条变体让用户选择：

```
💬 变体 1（直接型）
"伟哥，上次那个面膜效果特别好，又到货了。要不要再试试？"

💬 变体 2（关心型）  
"伟哥最近皮肤状态怎么样？上次你用的那个面膜，很多人反馈说保湿效果特别好。"

💬 变体 3（分享型）
"伟哥，我刚看到一篇关于春季保湿的文章，想起你上次说皮肤干。发你看看？[链接]"
```

三种变体对应三种销售风格——用户选择最像自己说话的。

### 2.4 用户操作流程

```
看到建议 → [编辑] 修改文案 → [发送] 确认发送
              ↓                    ↓
         自由修改，保留          按所选发送模式
         上下文引用              交付给用户
              ↓                    ↓
         [换一条]              消息发送后：
         换一个风格              系统更新联系人状态
         或重新生成              记录"已跟进"
```

这里的 `[发送]` 是用户授权进入发送流程。辅助模式定位并粘贴到输入框；是否由系统执行最终发送取决于 Profile。外部发布 Profile 中最终发送动作始终由用户完成。

### 2.5 消息历史 + 避免重复

系统记录已发送的消息摘要：
- 防止 7 天内给同一个人发相同内容的建议
- "你 3 天前刚推荐过面膜给张伟。确定还要推荐吗？"
- 保护用户不被自己的工具搞成"骚扰式销售"

### 3.1 核心概念

**群发 ≠ 群消息。** 群发是给多个联系人各发一条**不同的**消息。每条消息基于该联系人的上下文个性化生成。接收人看不出这是群发。

### 3.3 发送节流

| 参数 | 默认值 | 说明 |
|---|---|---|
| 消息间隔 | 3-8 秒随机 | 保护用户处理节奏，降低骚扰感 |
| 单批上限 | 50 条 | 超过 50 条分批次发送 |
| 每日上限 | 动态 | 按账号使用习惯、用户回复处理能力、近期异常动态收紧 |
| 时间段限制 | 禁止 22:00-08:00 | 不在休息时间发送 |

这些参数用户可调但系统有明确的安全上限（不能设为 0 间隔、不能设为不限制）。节流目标是反骚扰、保护用户处理能力和降低误触风险，不以规避平台识别为设计目标。

### 3.4 "这不是群发，是批量 1:1 跟进"

系统在营销伦理层面的定位：这不是"群发广告"。这是**给每一个需要关注的人，发一条基于你们之间真实对话的个性化消息。**

这是 DeepAxis 与微信批量助手/第三方群发工具的本质区别：

| | DeepAxis 半自动群发 | 传统群发工具 |
|---|---|---|
| 消息内容 | 基于个人聊天上下文生成 | 统一模板 |
| 接触理由 | "你上次问的面膜..." | "新品上架！" |
| 接收人感受 | 像被单独想起 | 像被群发轰炸 |
| 发送节奏风险 | 受用户处理能力和平台规则约束 | 高 |

### 4.2 群信号映射到个人联系人

群聊中的价格询问、效果咨询等信号，不仅触发群回复建议，也同时更新相关群友的个人状态：

```
群内信号: "@小美 问"这个套装多少？""
  ↓
群回复建议: 在群里公开回复
  ↓
同时更新: 小美 的 护肤维度 → 状态 3（有兴趣）← 这是跨群聊→1:1 的信号流转
  ↓
下次 1:1 跟进: 系统提醒"小美在群聊中问过价格，可以私聊跟进"
```

这就是群聊分析和 1:1 私聊分析最终汇合的地方——它们不是两条独立数据流，而是同一张客户关系图的两种信号来源。

## 5. 效率工具全局参数

| 参数 | 默认值 | 可调范围 | 说明 |
|---|---|---|---|
| 单次群发人数上限 | 50 | 10-200 | 建议 ≤50，超过需要用户主动调高 |
| 发送间隔 | 3-8 秒随机 | 2-15 秒 | 不得设为 0 |
| 每日发送上限 | 200 条 | 50-500 | 不得设为不限制 |

| 同客户最小消息间隔 | 3 天 | 1-7 天 | 防止频繁骚扰 |
| 消息变体数 | 3 | 1-5 | 每个客户生成几条变体供选择 |
| 消息风格默认 | 直接型 | 直接/关心/分享 | 新用户默认直接型，系统可根据用户选择频率调整 |

## 6. 校准循环（嵌入效率工具使用）

日常使用中的校准比导入阶段的批处理校准更有价值，因为它捕获的是真实工作流的偏差：

```
用户行为           →  校准信号
────────────────────────────────────
选择"换一条"       →  当前风格/内容质量低
大量编辑消息       →  用户口吻与 AI 生成的差距
从不使用某风格      →  该风格不适应此用户
群发后退回编辑      →  生成质量触发重新生成
发送后客户回复      →  消息质量正面信号
发送后客户不理      →  消息质量负面信号（弱信号）
```

### 6.1 口吻适配

系统记录用户编辑后的文本 vs 原始建议文本，提取差异模式：
- 用户把"您"改成"你" → 偏口语
- 用户删掉了表情符号 → 不喜表情
- 用户加了"哈哈哈" → 语气偏活泼
- 用户每次都缩短消息 → 偏好简洁

口吻适配只调整表达偏好，不复制用户身份、私人关系、事实断言或承诺边界。30 天后，系统对用户表达偏好的适配应当更稳定；新用户可以使用默认模板。

## 7. 边界规则

| 场景 | 边界 | 理由 |
|---|---|---|
| 系统自动发送消息 | 🔴 L3 / Profile 控制 | `personal_full` 可开；外部发布关闭，用户最终确认 |
| 向私人联系人推荐消息 | 🔴 禁止 | 隐私红线 |
| 建议中包含错误的产品信息 | 🟡 检测 | 交叉验证产品维度状态 |
| 7 天内向同一人重复推荐相同内容 | 🟡 检测 | 提醒用户但不禁止 |
| 营销群发超过每日上限 | 🔴 禁止 | 遵循预定义上限 |
| 在禁发时间段发送 | 🔴 禁止 | 阻止发送 |
| AI 以用户身份承诺或伪造关系（如"保证有效""我跟你很熟"） | 🔴 禁止 | 系统绝不生成疗效、效果保证或虚假关系语句 |
| 用户编辑消息加入红线内容 | 🟡/🔴 检测 | 只要仍通过 DeepAxis 队列、粘贴或审计，系统至少警告；功效/治疗/价格承诺等严重红线可阻断 |
| 群聊中 @ 多人询问的回复 | 🟢 自动建议 | 低风险，用户确认后发送 |

## 8. 数据安全

| 风险 | 缓解 |
|---|---|
| 建议消息包含联系人隐私信息 | 生成时过滤：不引用私人关系、不透露第三方信息 |
| 群发消息造成骚扰或触发平台风险 | 分波发送、动态上限、禁发时段、Profile 控制、异常时熔断 |
| 消息模板被外泄 | 所有处理在本地，不经过云端 |
| AI 生成有歧义或不适当的措辞 | 用户始终是最后一道防线（必须手动确认） |

## 9. 与框架层关系

半自动效率工具是框架层的直接实例化：

| 框架原语 | 效率工具实现 |
|---|---|
| 感知 (P1) | 检测降温信号、活跃度变化、群内产品提及 |
| 解析 (P2) | 判断状态 → 决定干预策略（降温→重新激活 还是 沉默→放弃） |
| 干预 (P3) | 生成回复建议、群公告草稿、群发消息 |
| 设计 (P4) | 用户选择风格、编辑消息——人类设计最终版本 |
| 物化 (P5) | 发送消息、记录结果 |
| 回溯 (P6) | 发送后客户响应 → 更新信心 → 校准模型 |
| 消解 (P7) | 客户回复 → 降温状态解除；客户不理 → 升级告警 |

## 10. 后续阶段

- **P1.5 事实底座**：产品事实卡、轻量订单信号、禁用承诺、素材和 FAQ。没有事实底座时，复购、物流、售后类建议不能进入稳定绿灯
- **P3 朋友圈轻量运营**：基于产品事实和用户确认素材，生成朋友圈内容草稿、发布时间建议和互动回顾
- **定时消息**：用户写好草稿，设置"明天上午 10 点发送"（仍需到时手动确认）
- **跟进序列**：预设 3-5 步的跟进流程（"第 1 天发问候 → 第 3 天发产品介绍 → 第 7 天发促销"），系统在每一步到期时提醒
- **客户回复后的自动状态更新**：客户回复 → 降温状态自动解除 → 更新互动时间线
