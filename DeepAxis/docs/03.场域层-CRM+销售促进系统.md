## 0. 场域定义

### 0.1 一句话定义

**CRM + 销售促进系统**：以客户状态变迁为感知对象，以销售员为判断主体，以多渠道信号为输入，以 CRM 为下游记录系统的**客户增长运行中枢**。

### 0.2 场域边界声明

本场域中：
- **CRM 是抽象的**——下游记录系统，不是 DeepAxis
- **渠道是抽象的**——微信、企微、邮件、电话、面谈都是信号来源，不在场域层绑定
- DeepAxis 站在渠道和 CRM 之间——做"感知和推动"层

### 0.3 与框架层的约束对齐

本场域层遵守框架层的三个硬约束：
1. **State-Driven**：状态变迁是一等实体，任务从状态派生
2. **Boundary-First**：边界检查（G×U/L → 绿/黄/红）先于所有行动
3. **Evidence Chain**：所有判断有可追溯证据链

### 0.4 开发阶段说明

本文定义场域语义和长期目标，不定义当前 P0 开发范围。

架构已从"PC分析+手机执行"更新为"纯PC工作台"：
- 标签状态机（§2.3 旧版）已废弃。标签现在是只读信号输入源，不再承载工作流状态。
- 备注`┊`协议（§2.4 旧版）已废弃。备注现在是只读信号输入源，不再承载 DeepAxis 数据段。
- 发送模式由 Profile 控制：辅助模式、手动模式、以及 `personal_full` 下可启用的最终发送模式。外部发布 Profile 默认关闭最终发送。
- 标签/备注整理按 L0-L3 分级体系执行，详见 `08.开发层-标签与备注整理规格.md`。

当前 P0 只验证本地只读数据接入、元数据互动分析、隐私排除和证据链，范围以 [07.开发层-P0技术验证规格](07.开发层-P0技术验证规格.md) 为准。

冷启动阶段（P0/P1）不自动推进核心客户状态，只生成候选提示和客户雷达项。正式状态推进必须在用户确认、规则成熟、证据链完整后逐步启用。

## 1. 行动者模型

| 行动者 | 角色 | 责任 |
|---|---|---|
| **销售员 (Salesperson)** | 唯一的判断主体 + 行动的后果承担者 | 信号的最终解释者、干预策略的决定者、否决系统建议 → 否决即训练信号 |
| **系统 (DeepAxis)** | 辅助感知者 + 建议引擎 | 检测状态变化、建议干预策略、生成执行初稿、追踪判断质量。不可自动执行高于 🟢 门槛的动作 |
| **客户 (Client)** | 感知对象（非行动者） | 不登录 DeepAxis，不直接与系统交互。状态完全通过信号间接推断 |

**没有第四类行动者（如销售经理）**——第一个场域聚焦单销售员场景。

## 2. 信号模型

### 2.1 信号分类

| 信号类型 | 来源 | 可靠性 | 示例 |
|---|---|---|---|
| **行为信号** | 客户做的，通过渠道观察到的 | 高 | 客户回复了消息、点击了链接、评论了内容、打开了文件、参加了通话 |
| **状态信号** | 外部系统记录的客观事实 | 高 | 购买日期、支付金额、合同截止日期、产品使用数据 |
| **感知信号** | 销售员的主观判断 | 中-低 | "我觉得她其实想买但预算不够"、"他对我有点不信任" |

每种信号必须标注：来源、采集方式（自动/手动/同步）、可靠性评估（高/中/低/未知）、本帧偏倚声明。

### 2.2 关键纪律

- **被动信号优先权**：行为信号和状态信号比感知信号在模型中权重更高。它们是免疫于选择性记录的
- **缺失作为信号**："销售员 N 天未更新此客户"本身是统计上有信息量的——记录模式本身是行为信号
- **冷启动策略**：首日仅 #5 复购机会和 #3 成交窗口（结构化部分）完全运行。所有其他事件进入静默日志模式——收集数据、建立基线、穿越置信阈值前显示"数据不足"
- **按人类接收者的人均告警节流**：告警总量受操作者注意力预算约束。精度优先于召回率

### 2.3 DeepAxis 内部标签体系

DeepAxis 维护自己的内部标签矩阵，存在 PC 本地数据库。微信标签仅作为分析参考输入之一，不是 DeepAxis 标签本身。

**标签来源与举证原则**：
- 所有标签由系统通过分析聊天历史自动推导
- M0 模式下：仅用元数据推导（互动频率、方向、群聊归属、微信标签名）
- M1 模式下：扩展至内容分析（关键词、语义、意图识别）
- 每个标签必须附带：来源证据、置信度（0-1）、推导时间、失效条件
- **宁愿空白也不乱标**：置信度低于阈值时，标签维度留空，不猜测

**标签矩阵维度定义**（详见 02.框架层 §0.6）：

| 维度 | P0 可用 | P1+ 扩展 |
|------|--------|---------|
| 闲人判定 | ✅ 元数据可判 | — |
| 身份标签 | ✅ 微信标签推断 + 用户确认 | — |
| 产品关联 | ⚠️ 仅群聊名推断，置信度低 | ✅ M1 语义分析 |
| 互动状态 | ✅ 全自动计算 | — |
| 渠道标签 | ✅ 备注正则提取 | — |
| 关键日期 | ✅ 备注正则提取 | — |
| 广告追踪 | ✅ 系统自计数 | — |
| 行为标签 | ❌ 需 M1 | ✅ M1 语义分析 |
| 交易标签 | ❌ 需 M1 | ✅ M1 语义分析 |

### 2.4 备注作为客户信息源（只读）

DeepAxis 只读用户备注中的信息，提取结构化数据用于话术个性化。

**备注的输入价值**：
- 称呼方式：备注名"张总"vs"伟哥"决定话术口吻
- 事实信息：真实姓名、公司、渠道来源、成交日期/金额、生日、兴趣偏好
- 上下文钩子：用户手动记录的个人信息是关系维护的最高质量素材

**备注提取分层**：
- L1 正则提取（日期/金额/电话，M0模式即可做）
- L2 关键词+模板提取（渠道来源、成交记录，M1授权后）
- L3 AI提取（复杂语义，M1授权后+用户确认）

**`┊` 分隔符协议已废弃**。不再在备注中维护 DeepAxis 数据段。话术在 DeepAxis 面板上展示，不需要通过备注传输。

**备注整理**：用户可以通过 DeepAxis 面板发起备注追加写入操作（在备注末尾追加标准化信息如 `┊渠道:小红书`）。按 L2 操作执行——用户预览→确认→系统通过 UIA 逐条追加。绝不修改用户原文。

### 2.5 文件传输助手作为辅助通知通道

纯PC工作台下，文件传输助手从"主通道"降级为"辅助通知通道"。

**保留的场景**：
- **异常提醒**：发送失败、微信数据库异常、联系人冲突
- **每日总结报告**：当日发送统计、话术效果排行

**不再做的**：
- 定时推送（清晨/午间/晚间简报）——这些信息在 DeepAxis 面板上实时可见
- 作为状态同步通道——用户不需要在手机上看跟进状态

文件传输助手消息属于微信写回操作，必须单独授权。DeepAxis 粘贴消息到文件传输助手输入框，由用户手动发送。

### 2.6 闲人漏斗

**定义**：闲人 = 关联产品数为 0 的联系人。可广告。不进入任何产品状态机。

**广告触达**：
- 系统建议广告时机和话术，用户在面板审核后执行
- 广告次数由系统自动追踪（从雷达/群发中选中该联系人即+1）
- 广告后有回应 → 分析回应内容，关联对应产品 → 移出闲人池，进入对应产品状态机
- 广告后无回应 → 继续留在闲人池

**N 次无回应处理**：
- 全局参数 `idle_max_ad_count`，默认值 3，用户可在面板配置
- 广告次数达到 N 且最后广告时间 > 7天 → 系统生成"建议删除"清单
- 删除必须经过两个步骤：
  1. 用户在 PC 面板看到删除建议清单（含联系人信息、广告历史、删除原因）
  2. 用户逐条勾选确认 → 系统通过 UIA 执行微信删除操作
- 系统不自动删除任何联系人
- 用户可为特定联系人标记"保留"——该联系人不进入删除建议

**闲人池的生命周期**：
```
未知联系人（新导入，尚未分析）
    │
    ▼ 系统分析
闲人（关联产品数=0，可广告）
    │
    ├── 广告有回应 → 关联产品 → 离开闲人池
    ├── 广告<3次未回 → 留在闲人池
    └── 广告满3次未回 → 建议删除 → 用户确认 → 微信删除
```

## 3. 客户状态模型（双轴）

### 3.1 Axis 1：客户事实状态（事实层）

状态使用 0-9 数字编码，Per-Project×Product 维度。一个联系人在不同产品维度上可以有不同的状态。

| 数字 | 中文名称 | 含义 | 典型信号 |
|---|---|---|---|
| **0** | 关联未激活 | 此人在本产品维度上已关联（提及/询问/被推荐过此产品），但尚未开始培育 | 首次产品关联信号 |
| **1** | 知道 | 首次接触。知道此产品/项目存在 | 首次提及产品名 |
| **2** | 培育中 | 正在建设关系。有持续对话 | 多轮非交易对话 |
| **3** | 有意向 | 明确表达兴趣 | "这个多少钱""怎么买""有效果吗" |
| **4** | 洽谈中 | 正在议价、对比、决策 | "太贵了""再想想""对比一下" |
| **5** | 首单 | 第一次成交 | 首次购买记录 |
| **6** | 复购 | 多次购买。稳定客户 | 第二次以上购买 |
| **7** | 降温中 | 原活跃、在衰退 | 响应延迟 > 阈值，互动频率大幅下降 |
| **8** | 已流失 | 确认已失联或明确拒绝 | 极长期不回复 or 删好友/拉黑/退群 |
| **9** | 不适用 | 此维度不适用此人 | 男性对女性护肤品；竞品方人员等 |

数字通路可学习：0→1→2→3→4→5→6 是漏斗推进线，7-8 是衰退线，9 是正交排除。

**辅助维度**（非二元补充指标）：

| 指标 | 含义 | 用途 |
|---|---|---|
| 响应延迟趋势 | 从 30 分钟 → 2 小时 → 1 天 → 零 | 触发降温检测（7）早于静默阈值 |
| 回复质量 | 多句回复 → 一句话 → 纯表情 → 零 | 参与深度在衰减 |
| 参与度比率 | 客户对你朋友圈的参与 / 客户总朋友圈活动 | 检测不可见的疏远 |
| 购买-互动比率 | 只买不聊 → 交易型高流失风险；只聊不买 → 还在维持关系 | 指导干预策略 |

### 3.2 Axis 2：变迁事件（判断层）

系统检测的事件——带有证据、置信度、分流推荐。

#### 可行事件层级

**🟢 第 1 层：第 1 天可用，基于规则**

| # | 事件 | 触发信号 | 冷启动置信度 | 默认分流 |
|---|---|---|---|---|
| 5 | **复购机会** | 距上次成交超过产品消耗周期 + 客户仍在活跃 | 0.80 | FREEZE → 提示时机 |
| 3 | **成交窗口**（部分）| 管道阶段推进 + 文档参与度信号 | 0.65 | FREEZE → 提示时机 |

**🟡 第 2 层：数周后可用，需要基线**

| # | 事件 | 触发信号 | 冷启动置信度 | 默认分流 |
|---|---|---|---|---|
| 1 | **升温信号** | 互动频率较客户基线显著上升 | 0.30 → 增长 | CONTINUE（提升监测频率）|
| 2 | **降温预警**（行为）| 互动频率下降 + 响应延迟上升 | 0.25 → 增长 | FREEZE |
| 6 | **流失风险** | 降温 + 多层负面信号叠加 | 0.15 → 增长 | ESCALATE |

**🔴 第 3 层：数月后可用，需要 ML/标注数据**

| # | 事件 | 触发信号 | 冷启动置信度 | 默认分流 |
|---|---|---|---|---|
| 4 | **异议信号** | NLP 从对话中检测到"太贵""再想想""对比" | 0.10 → 增长 | FREEZE |
| 8 | **异常行为** | 偏离个体和群组基线（突然大量购买/突然问竞品）| 0.05 → 增长 | FREEZE |

**⚫ 第 4 层：有志向的 / 需要外部数据**

| # | 事件 | 触发信号 | 冷启动置信度 | 默认分流 |
|---|---|---|---|---|
| 7 | **转介绍机会** | 成交 + 满意 + 社交影响力 | 0.05 | CONTINUE |
| 9 | **销售员偏误信号** | 销售员判断与行为数据存在系统性分叉 | 0.00（不活跃）| 仅仪表盘 |

### 3.3 两个轴的交互协议

**P1.5/P2+：高置信状态应用 + 撤销**

> 阶段限定：本协议只适用于 P1.5/P2 以后规则成熟的状态变迁。P0/P1 只生成 `RadarHint` / 候选提示，不自动推进 Axis 1。

- 事件置信度 ≥ 0.80 → 应用 Axis 1 状态变更，通知销售员，可一键撤销
- 事件置信度 0.50–0.80 → 生成待审查变更，由销售员确认后应用
- 事件置信度 < 0.50 → 仅通知，不应用状态。标记为"待审查"
- 销售员随时可以通过撤销按钮覆盖任何系统状态变更
- 撤销是训练信号——触发 MeaningDivergence 记录

**理由**（来自多专家共识）：人更可能纠正错误（"不对，她没降温——她在出差"）而非主动创建记录。高置信状态应用尊重操作者注意力预算，撤销保护准确性。

**状态变更来源**：
- 事件来源（系统检测 + 用户确认或高置信应用）— 大多数轴 1 的变更
- 人工来源（销售员手动推进）— 销售员覆盖系统时
- 外生来源（从外部系统同步：交易记录、合同状态）— 无可争议的事实

### 3.4 互动丰富度（补充维度）

轴 1 的二元状态（活跃/沉默）对检测衰退来说太粗糙。系统追踪：

- **响应延迟趋势**（不是"回应了"，而是"从 30 分钟变成 2 小时变成 1 天"）
- **回复质量**（多句话 → 一句话 → 仅表情符号 → 没有）
- **参与度比率**：客户与操作者朋友圈内容的互动 / 客户的总朋友圈可见活动
- **购买-互动比率**：购买但不交流 = 高流失风险的交易型客户；交流但不购买 = 尚在维持关系

## 4. 干预模型

### 4.1 干预策略三态

| 策略 | 含义 | 后续 |
|---|---|---|
| **Active** | 判断需要干预 | 设计 → 物化 → 回溯 → 消解 |
| **Null** | 判断不需要行动 | 记录判决 + 预测 + 设复审计时器 |
| **Freeze** | 不确定，信息不够 | 暂停，设信息补充时限 |

### 4.2 场域特有的行动类型（需经边界检查）

所有干预动作必须先经过 Boundary Engine 的绿/黄/红分类：

| 动作 | 分类 | 含义 |
|---|---|---|
| 向销售员推送感知通知 | 🟢 | "陈姐可能降温了"——系统通知，不涉及客户 |
| 生成跟进建议 + 话术草稿 | 🟢 | "建议回暖，话术如下"——销售员决定发不发 |
| 建议跟进时机和优先级 | 🟡 | "今天优先跟这 3 个高意向客户"——需销售员确认 |
| 建议修改客户状态标签 | 🟡 | 系统建议从"活跃"改为"降温中"——需审查 |
| 代替销售员承诺价格、优惠 | 🔴 | 架构层禁止——无论什么情况 |
| 代替销售员发送任何消息 | 🔴 | 架构层禁止——无论什么情况 |
| 自动同步 CRM 状态更新 | 🟢 | 已确认的变迁同步到下游 CRM |

### 4.3 告警节流

按人类操作者的注意力预算对所有事件通知进行节流：
- 系统产出事件量必须 ≤ 操作者每周可行动的干预数量
- 当事件产生 > 容量时，按（置信度 × 后果严重性）排序
- 低优先级事件静默归档，定期总结而非逐条通知

### 4.4 行动空间：发送模式与 Profile

> **P2+ 完整行动层。** P0/P1/P2 是内部开发阶段，不是对外发布版本。发送能力最终完整实现，并由 [13.能力Profile与发布合规配置](13.能力Profile与发布合规配置.md) 控制个人使用和外部发布差异。

发送动作是 DeepAxis 中最核心的操作。框架规定两种发送模式：

**唯一语义**：客户消息的最终发送动作属于 L3 高风险能力。`personal_full` 可启用自动最终发送；`external_safe` 和 `strict_compliance` 默认关闭，必须由用户在微信中完成最终发送。

| 模式 | 含义 | UI 行为 | 适用场景 | 边界级别 |
|------|------|---------|---------|---------|
| **辅助模式**（默认） | 系统生成话术 → 在 PC 微信中定位联系人、粘贴话术 → 用户按 Enter 发送 | 用户在 DeepAxis 面板审核话术，按空格键触发粘贴。DeepAxis 通过 UIA 打开 PC 微信会话、粘贴话术到输入框。用户敲 Enter 完成发送 | 日常跟进的主要模式 | 🟢（人按发送键）|
| **手动模式** | 用户自行撰写话术、自行发送 | DeepAxis 不参与发送过程。仅事后通过聊天记录检测发送结果 | 高价值客户、需高度定制话术的场景 | 🟢（完全人工）|
| **最终发送模式** | 系统在 `personal_full` 下执行最终发送动作 | 必须经过 Command/Gate、证据记录、目标确认、熔断检查 | 作者个人全功能使用 | 🔴 L3 |

**辅助模式的工作流**：
```
DeepAxis 面板展示话术 → 用户审核（扫一眼，2-3秒）
  → 用户按空格键 → 系统 UIA 粘贴话术到 PC 微信输入框
  → 系统自动切换窗口焦点到微信 → 用户敲 Enter 发送，或在 `personal_full` 下由最终发送模式执行
  → 系统只读检测发送结果 → 自动加载下一条话术到面板
```

**辅助模式的安全约束**：
- 🔴 **Profile 约束**：外部发布 Profile 禁止自动最终发送；`personal_full` 下最终发送必须走 L3 Gate
- 🟢 **粘贴前可修改**：用户在面板上可以随时编辑话术草稿
- 🟢 **发送后可检测**：系统通过只读 SQLite 检测新的 outbound 消息，确认发送成功

**为什么废弃安全模式**：
- 安全模式依赖备注作为话术传输通道——用户需要在手机上看到备注、手动打字发送
- 在纯PC工作台架构下，用户在 PC 上直接操作，不需要通过备注传到手机
- 对外发布时，辅助模式（粘贴+用户Enter）是默认合规平衡：效率提升 + 用户最终控制发送

## 5. 场域特有的边界

除框架层的通用边界外，本场域增加：

1. **不可代替销售员承诺任何客户信息**——包括价格、优惠、交付时间、售后承诺
2. **不可自动分析跨客户隐私数据来生成建议**——"你和陈姐成交了，那王姐作为陈姐的朋友可能也想要" ← 如果王姐没有主动询问，这是隐私侵犯
3. **销售员的否决权无条件优先于系统判断**——系统不能绕过销售员直接修改客户状态。销售员覆盖系统 → MeaningDivergence 记录 → 校准输入
