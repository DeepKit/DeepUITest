# 04. 场景层 — 首次使用与持续使用

> **版本**: v2.1（基于四专家开发评审修正）
> **核心变更**: P0 首屏收敛为 M0 客户雷达；首次流程改为信任预检 → 兼容性扫描 → 小规模隐私分流 → 结果

---

## 0. 设计原则（重写依据）

原 v1 设计有三大问题（三专家一致确认）：

1. **价值悬崖**：用户在看到任何有用信息之前，必须投入 1-2 小时的元数据录入工作。流失率不可接受。
2. **三轮结构暴露**：Round A/B/C 是系统内部架构，不应暴露为用户的认知负担。用户只想看到结果。
3. **校准与使用割裂**：校准是一次性事件（Round C 抽查），而非嵌入日常使用的持续过程。

**v2 核心原则**：

| 原则 | 含义 |
|---|---|
| **价值前置** | 连接数据库后 5 分钟内，用户必须看到可行动的信息 |
| **导入可选** | 标签映射、批量分类、矩阵定义——全部可选。不做系统也能工作 |
| **一轮持续流** | 用户只看到：连接 → 隐私确认 → 结果。其余全部后台处理 |
| **校准嵌入使用** | 每一次用户纠正都是一份训练数据。没有单独的"校准阶段" |
| **本地优先** | 默认本地处理，DeepAxis 不上传到自有云。后续若启用微信写回，选定字段会写入微信并受微信同步机制影响 |

**当前开发口径**：本文描述目标体验，不定义 P0 范围。P0 只实现 `M0 元数据模式`（联系人、群聊、消息时间、方向、类型、数量），不读取消息正文；涉及关键词、摘要、意图、话术上下文的能力属于 `M1 内容分析模式`，必须在后续阶段由用户显式授权。当前 P0 范围以 [07.开发层-P0技术验证规格](07.开发层-P0技术验证规格.md) 为准。

**P0 首屏纪律**：P0 只能展示元数据可证明的客户雷达提示，不展示“表达兴趣”“价格”“购买”“成交”“摘要”“话术”等 M1/M2 以后能力。

## 1. 用户流（唯一暴露给用户的路径）

### 第一步：信任预检（~30 秒）

```
┌────────────────────────────────────────────┐
│  DeepAxis — 本地只读预检                   │
│                                            │
│  P0 只会读取：联系人、群聊、消息时间、方向、类型、数量 │
│  P0 不会读取：消息正文、图片、语音、文件内容        │
│  P0 不会做：写微信、发消息、粘贴消息、上传云端      │
│                                            │
│  [ 开始兼容性扫描 ]                          │
│                                            │
│  🔒 所有处理在本机完成，可随时删除本地 P0 数据      │
└────────────────────────────────────────────┘
```

用户在这里先看到字段边界，再授权 P0 扫描。系统不得在用户同意前读取消息时间线。

### 第二步：兼容性扫描（~30-120 秒）

```
正在扫描...
  ✓ 检测到微信数据源：1 个
  ✓ 只读打开成功
  ✓ Schema 已识别：WeChat vX / adapter-2026-06
  ✓ 正文列存在但未读取
  ✓ 写入次数：0
  ⏳ 正在构建 90 天互动时间线...
```

**显示进度**：
```
正在读取...
  ✓ 联系人数据：4,872 人
  ✓ 群聊数据：186 个群
  ✓ 消息时间线：最近 90 天
  ⏳ 正在分析互动模式...
```

**错误处理**（E2 Critical 8.4）：
- 解密失败 → "无法读取微信数据。可能原因：微信版本不兼容、数据库已损坏。[重试] [手动选择路径] [查看帮助]"
- Schema 不兼容 → "检测到不支持的微信版本。DeepAxis 目前支持微信 v3.9.x — v4.x。[提交版本信息以加快适配]"
- 数据库不完整 → "只读取到部分数据（已读 2,341/4,872 个联系人）。[继续使用] [重新扫描]"

### 第三步：小规模隐私分流（~60 秒，唯一必须步骤）

```
┌────────────────────────────────────────────┐
│  确认首屏隐私边界                             │
│                                            │
│  这些联系人可能进入首屏雷达，需先确认身份。       │
│  标记为「私人」的联系人：                       │
│  • 元数据不参与客户雷达                         │
│  • 不参与任何状态追踪                          │
│  • 不显示在任何客户列表中                      │
│                                            │
│  ┌──────────────────────────────────────┐  │
│  │ 👤 老婆         私人 ✅ | 改→客户      │  │
│  │ 👤 老妈         私人 ✅ | 改→客户      │  │
│  │ 👤 张三(同事)    私人 ✅ | 改→客户      │  │
│  │ 👤 李四         私人 ✅ | 改→客户      │  │
│  │ 👤 大学同学群主   私人 ✅ | 改→客户      │  │
│  │ ... (共 23 人已标记，5 人待确认)        │  │
│  └──────────────────────────────────────┘  │
│                                            │
│  AI 自动识别依据：称呼模式、标签、对话频率        │
│  （商业关键词需开启内容分析模式）                 │
│                                            │
│  [ 确认并查看客户雷达 ] [ 我有更多人要标记 ]       │
└────────────────────────────────────────────┘
```

P0 不要求用户一次性确认全部联系人。只处理会影响首屏结果的少量高风险联系人；其余 `UNKNOWN` 默认不进入客户雷达。

**增量隐私边界**（E2 Critical 6.4 — 双向可逆）：

用户可以在任何时间重新分类任何人：
- 私人 → 客户："此联系人之前的对话数据未被保留。重新分类后将从头开始追踪。AI 无历史辅助，需手动标注初始状态。"
- 客户 → 私人："此联系人的已有状态标签将被删除。对话摘要和提取事实将被清除。此操作不可撤销。"

### 第四步：首个价值屏幕（连接后 ~5 分钟）

这是用户见到的第一个信息画面——不是表格，不是状态数字，而是可行动的洞察：

```
┌──────────────────────────────────────────────────┐
│  DeepAxis                                        │
│                                                  │
│  🔥 今日客户雷达（仅基于元数据）                       │
│  ┌──────────────────────────────────────────────┐│
│  │ ⚠️ 互动明显下降                  17 人            ││
│  │   近 30 天回复频率下降，建议看一眼                 ││
│  │                                              ││
│  │ 🕒 长期未联系                    36 人            ││
│  │   90 天内曾互动，最近 30 天无互动                  ││
│  │                                              ││
│  │ 🆕 最近重新活跃                  8 人             ││
│  │   沉默后重新出现互动信号                         ││
│  │                                              ││
│  │ 📤 我发多、对方回少              14 人            ││
│  │   单向触达比例偏高，可能需要调整节奏                ││
│  └──────────────────────────────────────────────┘│
│                                                  │
│  证据样例：                                       │
│  张伟 · 互动下降 · 30天内 12次 → 2次 · 置信度中       │
│  李娜 · 长期未联系 · 最后互动 78 天前 · 数据质量高      │
│                                                  │
│  [ 查看今日 10 人 ] [ 标记不准 ] [ 删除本地 P0 数据 ] │
└──────────────────────────────────────────────────┘
```

**这不依赖用户做任何分类工作。** 在 `M0 元数据模式` 下，系统只基于互动频率、响应延迟、时间分布等元数据生成“互动下降”“长期未联系”“近期重新活跃”“数据不足”等提示。涉及“表达过兴趣”“上次对话摘要”“价格/效果/购买关键词”的状态，需要进入 `M1 内容分析模式` 后才可启用。

用户可以立即：
- 点进"互动明显下降"列表，看到具体是谁、消息频率下降了多少
- 点进"长期未联系"或"近期重新活跃"列表，查看元数据证据
- 对每条提示标记“有用 / 不准 / 私人 / 不是客户 / 以后提醒”
- 在后续授权内容分析后，开始使用半自动回复功能（见 05.场景层）

### 2.1 标签映射（可选）

入口：设置 → 标签映射

```

─────────────────────────────────────────────────────────
 VIP                              高价值客户                 高
 意向客户                          潜在客户                   中
 老客户                            已成交客户                 高
 家人                              私人（已排除）             高
 健身                              兴趣标签：健身             中
 同事                              私人（已排除）？            低 ⚠️

```

API 默认行为：**不使用标签**。标签映射是一个提升——如果用户做了，AI 分类会更准确。如果用户不做，P0 只用元数据互动模式做推断；M1 授权后才允许使用对话模式。

不再要求所有标签必须映射后才能继续。**标签映射不是门槛。**

## 3. 状态系统（用户视角）

### 3.1 用户看到的状态标签

内部用 0-9 数字（用于批量操作和 API），但日常界面用自然语言 + 颜色：

| 内部 | 用户标签 | 颜色 | 含义 |
|---|---|---|---|
| 0 | 未激活 | 灰色 | 还没开始发展关系 |
| 1 | 初步接触 | 浅蓝 | 刚认识，刚提到产品 |
| 2 | 培育中 | 蓝色 | 正在建立关系 |
| 3 | 有兴趣 | 绿色 | 表达过兴趣 |
| 4 | 洽谈中 | 黄色 | 正在议价/比较 |
| 5 | 已首购 | 深绿 | 第一次购买 |
| 6 | 老客户 | 金色 | 多次购买 |
| 7 | 在降温 | 橙色 | 活跃度在下降 |
| 8 | 已流失 | 红色 | 确认失联 |
| 9 | 不适用 | 灰色 | 此维度不适用此人 |

### 3.2 AI 自动分类的依据

本节描述 `M1 内容分析模式` 及后续能力。P0 的 `M0 元数据模式` 不读取消息正文，因此只能使用互动频率、响应延迟、时间分布等元数据；关键词、摘要、意图识别必须在用户显式授权内容分析后启用。

| 信号 | 来源 | 影响的状态 |
|---|---|---|
| 首次提及产品名 | 关键词匹配 | 1 |
| 多轮对话 + 无产品关键词 | 对话模式 | 2 |
| "多少钱""怎么买""有效果吗" | 意图识别 | 3 |
| "太贵了""再想想""对比" | 意图识别 | 4 |
| 支付/收款记录 | 微信支付 | 5, 6 |
| 回复延迟趋势上升 | 时间分析 | 7 |
| 长期不回复 + 删除/拉黑 | 系统事件 | 8 |

### 3.3 用户纠正即校准

每一次用户纠正都是质量信号：

```
用户纠正过程：
1. 用户把"李娜"从"3(有兴趣)"改为"5(已首购)"
2. 系统：记录 (预测=3, 实际=5, 时间, 联系人特征)
3. 系统：如果同类型错误累计 >=30 次，自动调整推断阈值
4. 系统：如果同类型错误累计 >=100 次，提示用户"我发现你对XX类联系人经常纠正我的分类。要帮我调整规则吗？"
```

这是持续校准——不存在单独的"C 轮抽查"环节。校准嵌入每一次使用动作。

## 4. 隐私与数据保留

### 4.1 P0 数据保留

P0 只保存元数据指标、隐私决策、雷达提示、证据摘要和审计日志，不保存消息正文，不生成内容事实。

| 数据类型 | 默认保留 | 说明 |
|---|---|---|
| M0 元数据指标 | 90-180 天滚动 | 只保存派生指标，不保存正文 |
| 隐私决策 | 用户删除前，默认每 365 天复核 | 用于避免重复误分析私人联系人；只保存必要分类和审计时间 |
| 雷达提示和证据摘要 | 180 天 | 不含正文，可用于复核判断 |
| P0 审计日志 | 180 天 | 最小化保留，记录 body-zero 和删除动作 |
| `PRIVATE` 派生数据 | 立即级联删除 | 只保留最小删除审计 |
| `UNKNOWN` 业务画像 | 不持久化 | 不进入指标、报告、雷达提示 |

### 4.2 M1+ 数据保留

M1+ 允许在用户显式授权后短期读取业务联系人正文，但不继承 v1 的“无限期保留”策略。默认保留规则如下：

| 数据类型 | 保留时间 | 说明 |
|---|---|---|
| 联系人姓名/备注 | 用户删除前，默认每 365 天复核 | 基础元数据；删除联系人时级联清理 |
| 状态标签 | 180-365 天滚动 | 保留状态历史用于校准，不做永久画像 |
| 事件摘要 | 180 天（可配置 90/180/365） | 只保存必要业务事件，不保存原文 |
| 提取事实 | 180-365 天滚动 | 只保留用户确认或高置信业务事实，到期复核或删除 |
| 业务对话原始文本 | 7/30/90 天可配置，默认 30 天 | 仅限业务联系人；到期自动删除 |
| 审计日志 | 180 天 | 记录授权、读取、删除、写回，不含正文 |
| `PRIVATE` 派生数据 | 立即级联删除 | 只保留最小删除审计 |
| `UNKNOWN` 业务画像 | 不持久化 | 不进入指标、报告、雷达提示 |
| 私人联系人的任何正文数据 | 从不持久化 | 读取后立即丢弃；如误入必须级联删除 |

新增：到期前提醒：
- 第 80 天："你的对话数据将在 10 天后自动删除。[延长至 180 天] [保持不变] [立即删除]"
- 支持手动触发立即删除。（E2, E1 修复）

## 5. 数据模型

### 5.1 Contact 核心表

```
Contact {
  contact_id: UUID
  wechat_id: string          // 微信内部 ID
  display_name: string       // 备注名 > 昵称 > 微信ID
  privacy: enum { BUSINESS, PRIVATE, UNKNOWN }
  wechat_tags: string[]
  group_ids: UUID[]
  first_seen: datetime
  last_updated: datetime
}
```

### 5.2 ContactDimensionState（Per-Project×Product）

```
ContactDimensionState {
  contact_id: UUID
  dimension_id: UUID
  state: 0-9
  confidence: 0.0-1.0        // AI 对当前状态分类的确信度
  last_auto_classified: datetime  // AI 最后一次自动分类时间
  last_human_corrected: datetime // 用户最后一次纠正时间（null = 从未）
  source: enum { AI_INFERRED | HUMAN_CORRECTED | TAG_DERIVED | MANUAL_IMPORT }
}
```

**确认标记 ✓ 被移除**（E2 Critical 4.7 + E1 一致）。取而代之的是 `last_human_corrected` 时间戳。空值 = AI 未经人核的分类，有值 = 用户最后纠正过。系统可以据此知道哪些状态有更强的人类背书。

### 5.3 状态变迁记录（满足框架 Evidence Chain）

每次状态变化——无论是系统建议、成熟规则下的高置信应用，还是用户手动修改——都留下变迁记录：

```
StateTransition {
  transition_id: UUID
  contact_id: UUID
  dimension_id: UUID
  from_state: 0-9 | null      // null = 初始分配
  to_state: 0-9
  trigger: string              // "ai_inference:v3.2:signal=keyword_purchase_intent"
  confidence: 0.0-1.0
  source_evidence: string      // 引用具体信号（如 "msg_uuid:abc123"）
  operator: enum { AI | HUMAN }
  created_at: datetime
}
```

这满足框架的硬约束："不能直接更新状态——只能追加变迁记录。"

### 5.4 CorrectionLog（校准数据）

```
CorrectionLog {
  correction_id: UUID
  transition_id: UUID          // 被纠正的变迁记录
  original_prediction: 0-9
  human_label: 0-9
  contact_features: JSON       // 联系人特征快照（用于模型训练）
  corrected_at: datetime
}
```

## 6. 自动化级别（简化）

v1 的六档 L0-L5 过于复杂。v2 采用三档感知式自动化。阶段限定：P0/P1 只启用“协助”，不启用自动状态应用；后两档必须等 P1.5/P2 规则、事实底座和审计闭环成熟后再开放。

| 级别 | 名称 | 行为 | 适用场景 |
|---|---|---|---|
| **协助** | AI 建议，用户决定 | AI 标记为"可能 X"，用户确认或修改 | 默认级别。新用户前 2 周 |
| **审查应用** | 高信心应用，低信心建议 | ≥80% 信心应用状态，其余建议 | 系统使用 2 周后、纠正率 <10% 时自动推荐升级 |
| **审计应用** | 规则应用 + 审计日志 | 成熟规则内的推断自动应用，用户收到每周摘要 | 用户主动开启。始终可退回 |

**不再需要用户理解 6 个级别**。新用户默认"协助"，系统根据纠正率（纠正次数/总推断次数）自动推荐升级或降级。

## 7. COP Pipeline 映射

> 注意：本节的 P1-P5 是 COP 协议编号，不是产品阶段 P0/P1/P2。

| COP 协议 | 实现 | 位置 |
|---|---|---|
| P1 采样 | 信号提取：对话关键词、互动频率、回复延迟 | 本地 NLP 管线 |
| P2 编码 | 信号 → 0-9 状态推断 | 本地分类模型 |
| P3 分流 | 红灯（隐私/边界冻结）/黄灯（低信心需人工）/绿灯（自动通过） | Boundary Engine |
| P4 转介 | 绿灯→半自动回复建议；黄灯→用户通知；红灯→拦截 | 动作路由 |
| P5 校准 | CorrectionLog 积累 → 定期模型调整 | 持续后台任务 |

## 8. 边界规则

| 场景 | 判定 | 理由 |
|---|---|---|
| AI 自动修改用户手动设置的状态 | 🔴 禁止 | 人类判断优先 |
| AI 建议"这个人可能该跟进一下" | 🟢 自动 | 低风险，通知级别 |
| AI 生成回复建议 | 🟡 确认 | 用户必须确认后发送 |
| AI 自动发送消息 | 🔴 禁止 | 不可自动发送 |
| 跨联系人隐私数据关联分析 | 🔴 禁止 | 隐私红线 |
| 降级自动化级别 | 🟢 自动 | 系统发现纠正率上升时自动降级 |

## 9. 与 v1 的关键差异

| v1 | v2 |
|---|---|
| 3 轮暴露给用户 | 1 轮持续流，3 轮在后台 |
| 导入是必经流程 | 导入是可选工具 |
| 标签映射是前置门槛 | 标签映射是可选提升 |
| 1-2 小时才能看到价值 | 5 分钟看到第一个价值屏幕 |
| C 轮抽查校准 | 每一次纠正都是校准 |
| 6 档手动滑块 | 3 档感知式自动化 |
| ✓ 确认标记（误导） | last_human_corrected 时间戳 |
| 群聊默认不分析 | AI 预分类 + 提示（群主力用户） |
| 恢复无保证 | 批原子提交 + 随时退出不丢数据 |
