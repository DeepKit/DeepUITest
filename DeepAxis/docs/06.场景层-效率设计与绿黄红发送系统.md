## 1. 核心设计哲学

### 1.1 用户审核的是系统的判断，不是消息内容

> **[强共识，E1+E2+E3]** 用户的任务是确认"系统做对了"，而不是重新做一遍系统做过的事。把用户的注意力从"读消息内容"转移到"验证系统判断是否可信"，是从"半自动"到"真正的效率工具"的关键跃迁。

**E3的实战验证**（确信度：高）："我自己打字时，脑子里有每个客户的脸，话是我自己想的。看系统写的消息，我需要**反向推导**系统为什么这么写——这是一个'阅读理解'过程，比'创作'累。"

**设计响应**：系统必须主动展示"为什么这么写"的推理依据，把审核从"推理题"变成"验证题"。

### 1.2 分级不是锦上添花，是生死攸关

> **[强共识，E1+E2+E3]** 200条消息全量平铺 = 认知酷刑。E3："不分级的话，这个产品的审核体验会让用户在第三天放弃使用。"

当前设计（05.场景层 §3.2）的问题——把所有消息平等展示——是本设计的核心修正目标。

### 1.3 "过脑的条数"是比"总审核时间"更好的效率指标

> **[强共识，E3提出并经E1+E2确认]**

目标是：200条消息中，用户真正需要"过脑子"的不超过 30 条（15%）。其余 170 条通过抽查和系统信任清单快速放行。

### 1.4 发送语义的唯一口径

本文所有“一键”“确认”“通过”表示**用户授权消息进入发送队列或辅助队列**。是否自动执行最终发送动作由 Profile 决定。

发送链路分两层：

| 层 | 含义 | 责任主体 |
|---|---|---|
| 审核授权 | 用户批准某条或某组消息可以被准备 | 用户 |
| 物理发送 | 在微信中按发送键、回车或手机发送按钮 | 用户；或 `personal_full` 下由 L3 Gate 控制的最终发送能力 |

DeepAxis 可以准备草稿、写备注、定位联系人、粘贴到输入框、记录发送后的状态变化。最终发送动作按 [13.能力Profile与发布合规配置](13.能力Profile与发布合规配置.md) 执行：`personal_full` 可开启，外部发布 Profile 默认关闭。

## 2. 绿/黄/红三级分类系统

### 2.1 分类架构：场景硬约束 + 算法评分

> **[强共识]** E2的五维评分是正确的技术方案，但需要E3定义的场景分类作为前置约束。算法在安全护栏内运行。

```
                    场景硬约束层
                  ┌───────────────┐
                  │ E3 实战分类    │
                  │ 红灯黑名单     │  → 直接标记 🔴
                  │ 绿灯白名单     │  → 直接标记 🟢
                  │ 其余→进入评分  │
                  └───────┬───────┘
                          │
                    算法评分层
                  ┌───────────────┐
                  │ E2 五维评分    │
                  │ [0.0, 1.0]    │
                  │ ≥0.70 → 🟢    │
                  │ 0.45~0.70→🟡 │
                  │ <0.45 → 🔴    │
                  └───────────────┘
```

#### 2.1.1 绿灯场景白名单（硬编码，不受算法评分覆盖）

| 编号 | 场景 | 条件 | 来源 |
|---|---|---|---|
| G1 | 售后回访 | 有轻量订单事实：已成交，距上次成交 7/30 天，且无投诉/售后中状态 | E3-F |
| G2 | 复购提醒 | 有产品事实卡 + 订单事实：消耗周期已到或即将到期 | E3-F |
| G3 | 物流/付款确认 | 有进行中的订单，状态为待付款/待发货/已发货 | E3-F |
| G4 | 稳定老客常规触达 | 连续复购 ≥ 5 次，沟通模式固化，近 30 天无负面信号 | E3-I |

> 阶段限定：绿灯白名单依赖 P1.5 的产品事实卡和轻量订单信号。没有事实底座前，上述场景不得作为稳定绿灯。

#### 2.1.2 红灯场景黑名单（硬编码，不受算法评分覆盖）

| 编号 | 场景 | 触发条件 | 来源 |
|---|---|---|---|
| R1 | 新客首触 | 加好友 ≤ 24 小时 | E3-F |
| R2 | 投诉处理 | 客户最近消息包含投诉/不满情绪 | E3-F |
| R3 | 议价中 | 客户最近对话包含议价/讲价内容 | E3-F |
| R4 | 长沉默激活 | 客户 ≥ 90 天无互动 | E3-F |
| R5 | 流失客户 | 客户状态 = 已流失（8）— 任何消息 | E2-F |
| R6 | 隐私未确认 | `privacy = UNKNOWN` — 不确定是客户还是私人 | E2-F |
| R7 | 投诉/售后中 | 订单或对话处于投诉、退换、过敏、质量问题 | E3-F |
| R8 | 功效/治疗承诺 | 消息包含保证有效、治疗、无副作用等风险表述 | E2+E3 |

> **E3-F**："首次触达——第一印象决定生死。系统可能理解错了加好友的场景，搞错了第一句话客户直接拉黑。"

#### 2.1.3 其余场景：五维加权评分

消息置信度由五个维度加权计算：

```
confidence_score = w1 * state_clarity          (0.30)
                 + w2 * context_richness        (0.30)
                 + w3 * voice_alignment         (0.15)
                 - w4 * sensitivity_penalty     (0.20)
                 - w5 * edit_history_penalty    (0.05)
                 - w6 * recency_conflict_penalty(0.10)  ← E3补充
```

> 注：权重总和 > 1.0 以容纳 E3 补充的 recency_conflict_penalty。归一化到 [0, 1]。

**维度详解：**

| 维度 | 说明 | 来源 |
|---|---|---|
| `state_clarity` | 读取 `ContactDimensionState.confidence`。AI 对联系人当前状态的置信度 | E2 |
| `context_richness` | 上次对话中可用的具体信息量——产品名、意图信号、对话轮次 | E2 |
| `voice_alignment` | 生成消息与用户历史发送消息的风格相似度（称呼方式、语气词、emoji、句子长度） | E2 |
| `sensitivity_penalty` | 价格承诺(扣0.50)、功效描述(扣0.35)、时间承诺(扣0.20)、风格偏差(扣0.10) | E2 |
| `edit_history_penalty` | 该联系人/状态/产品维度的历史编辑频率 | E2 |
| `recency_conflict_penalty` | **[E3补充]** 消息内容和客户最近交易/对话的冲突检测 | E3 |

**`recency_conflict_penalty`（最近行为冲突惩罚）详解：**

> **E3-F（高确信度）**："客户刚买了面膜，系统告诉他'补货了'——他会觉得你根本没记住他。这是信任杀手。"

| 触发条件 | 惩罚值 |
|---|---|
| 消息推荐的产品 = 客户 7 天内已购买的产品 | 0.50 |
| 消息假设"你可能感兴趣"的产品 = 客户 30 天内明确拒绝过的产品 | 0.40 |
| 消息的跟进话术与客户最后一条消息明确矛盾（客户说"不考虑"，消息说"上次聊得很开心"） | 0.60 |
| 无冲突 | 0.00 |

#### 2.1.4 分类阈值

| 级别 | 条件 | 确信度 | 依据 |
|---|---|---|---|
| 🟢 绿色 | `confidence_score >= 0.70` | 高 | 信号检测理论 d'=1 平衡点 |
| 🟡 黄色 | `0.45 <= confidence_score < 0.70` | 高 | 黄色区间宽度 0.25 足够分类 |
| 🔴 红色 | `confidence_score < 0.45` | 高 | 低于 0.45 的人类判断准确率显著下降 |

**特殊情况——红线直降**（无论 score 多高）：
- `sensitivity_penalty >= 0.35`（价格承诺或功效描述）
- 联系人状态 = 已流失（8）
- `privacy = UNKNOWN`

### 2.2 冷启动策略

| 阶段 | 条件 | 行为 |
|---|---|---|
| 冷启动期 | 用户累计发送 < 30 条 | **全部强制黄色**。绿/红不启用。UI 标注"学习期——所有消息由你审核" |
| 过渡期 | 30-100 条 | 启用绿/红，但阈值收紧：绿 ≥ 0.75，红 < 0.50 |
| 稳定期 | > 100 条 | 标准阈值：绿 ≥ 0.70，红 < 0.45 |

> **[强共识]** E2："30 条是统计显著性最小样本 + voice 样本需求。100 条触发首次 Calibration。" E3："第一天看到一堆绿灯我不敢点——先让我实际看过 30 条，我自己心里有数了，绿灯才有意义。"

**冷启动结束后的校准报告**：系统生成"过去 30 条中，系统预估绿 X 条 / 黄 Y 条 / 红 Z 条，实际你编辑了 A 条 / 直接发送了 B 条 / 跳过了 C 条"。**E3**："这种数据比任何说明书都管用。"

### 2.3 自适应演化

#### 2.3.1 时间维度的分布预期

| 时间点 | 绿色 | 黄色 | 红色 | 驱动因素 |
|---|---|---|---|---|
| Day 0 | 0% | 100% | 0% | 冷启动 |
| Day 3 (~50条) | 15% | 70% | 15% | 冷启动结束 |
| Day 7 | 25% | 60% | 15% | voice 初具雏形 |
| Day 14 | 40% | 48% | 12% | voice 基本稳定 |
| Day 30 | 55% | 37% | 8% | voice 成熟，edit 模式清晰 |
| Day 90+ | 72% | 23% | 5% | 稳定态 |

> **E2**："这些不是目标值，而是合理预期。如果用户极其挑剔，绿色可能永远不超过 30%——这不是系统失败，而是系统正确校准。"

#### 2.3.2 用户行为反馈

| 用户行为 | 系统响应 |
|---|---|
| 绿灯区频繁编辑（30 条中 ≥ 30% 被编辑） | 绿灯阈值从 0.70 自动提升到 0.75，UI 提示变化原因 |
| 绿灯区极少编辑（< 10% 被编辑，持续 2 个窗口） | 阈值回降 0.05 |
| 编辑后发送 | VoiceProfile 增量更新 |
| "换一条"选择 | 该风格权重 -0.05 |
| 发送后客户回复 | 该消息类型 trust_boost +0.02 |
| 发送后客户投诉/负面 | Escalation 记录，触发人工复核 |

> **E1**："系统自动调整 + 告知变化原因，比让用户手动调参数滑块好。用户不应该理解'阈值'这个概念。"

## 3. 审核交互设计

### 3.1 三层金字塔

```
        ┌──────┐
        │ 红灯  │  ~10条   逐一审核      ~3-5分钟
        │      │           (每条约15-20秒)
       ┌┴──────┴┐
       │  黄灯   │  ~60条   分组抽查      ~2-3分钟
       │        │           (4-6组，抽查8-12条)
      ┌┴────────┴┐
      │   绿灯    │  ~130条  矩阵确认+     ~30-60秒
      │          │          3条样本抽查
      └──────────┘

      用户过脑消息：~30条 / 200条
      总审核时间：  ~6-8分钟 / 200条
```

> **[多数共识，E1+E3调和]** E1 最初估计 2 分钟过于乐观。E3 估计 12-15 分钟是上限。E1 修正后目标约 6-8 分钟是合理的设计目标（不是产品承诺，是交互优化方向）。

### 3.2 绿灯交互：确认矩阵

> **[强共识]** 绿灯消息不应展示全文。用户审查的是"系统决策依据"，不是每条消息的全文。

```
┌─────────────────────────────────────────────┐
│ 🟢 绿灯消息 · 93 条                           │
│                                              │
│ 为什么可以放心？                               │
│  ✓ 4 种绿灯场景：售后回访 32 · 复购提醒 28 ·    │
│    节日问候 18 · 物流确认 15                     │
│  ✓ 所有客户已成交 ≥ 1 次                       │
│  ✓ 所有消息使用已验证话术模板                        │
│                                              │
│ 抽查确认（3条样本）：                            │
│ ┌──────┬──────────┬──────────┬──────┐        │
│ │ 客户  │ 场景     │ 产品     │ 称呼 │        │
│ ├──────┼──────────┼──────────┼──────┤        │
│ │ 张伟  │ 售后30天  │ XX面膜   │ 张哥✓│        │
│ │ 李娜  │ 复购提醒  │ YY精华   │ 李姐✓│        │
│ │ 王芳  │ 节日问候  │ —       │ 王姐✓│        │
│ └──────┴──────────┴──────────┴──────┘        │
│                                              │
│ [批准 93 条进入发送队列]  [查看全部 ▼]           │
│                                              │
│ ⚠️ 抽查不通过 → [降级全部绿灯为需审核，重新生成]   │
└─────────────────────────────────────────────┘
```

**设计要点：**
- 展示"**为什么可以放心**"（场景类型 + 客户条件 + 模板来源）比展示消息全文更重要
- 抽查样本选取最能代表绿灯判断逻辑的 3 条（不同场景类型各 1 条）
- "抽查不通过"不是逐条修改，而是**整批降级为黄灯重新审核** — 这也产生校准记录
- E2 架构提醒：绿灯隐藏全文 = 减少校准信号。解决方案：每天随机抽取 5% 的已发送绿灯消息做"事后审计"展示给用户

### 3.3 黄灯交互：按风险维度分组

> **[强共识，E1+E2+E3]** 不分组的黄灯就是另一种形式的"全量审核"。用户审的是"系统为什么不确定"，而不是"87条消息逐条读"。

```
┌─────────────────────────────────────────────┐
│ 🟡 需审核 · 87 条消息                         │
│                                              │
│ 不确定原因分组：                                │
│                                              │
│ ▸ 口吻可能不一致 · 12条                        │
│   voice_alignment < 0.5                     │
│   你习惯用"哥/姐"，这批消息语气偏正式             │
│   [抽查 2 条代表性消息]  [批准这 12 条进入队列]   │
│                                              │
│ ▸ 客户近30天无互动 · 34条                      │
│   系统对客户当前状态不确定                       │
│   ⚠️ 含排除名单检查结果：2人标记为"不联系"       │
│   [抽查 2 条代表性消息]  [批准这 32 条进入队列]   │
│                                              │
│ ▸ 上下文信息不足 · 28条                        │
│   上次对话内容模糊，无明确产品/意图关键词          │
│   [抽查 2 条代表性消息]  [批准这 28 条进入队列]   │
│                                              │
│ ▸ 模板匹配度中等 · 13条                        │
│   客户画像和话术模板不完全匹配                   │
│   [抽查 2 条代表性消息]  [批准这 13 条进入队列]   │
│                                              │
│ 全部抽查通过 → [批准全部 87 条进入队列]          │
└─────────────────────────────────────────────┘
```

**E3 的安全网要求**：黄灯分组"批量批准整组"前，自动跑排除清单 — 用户手动标记过"不联系"的人、近期有负面交互的人。如果检测到，高亮提醒"此组有 X 人已被你标记为不联系，已自动移除"。

**E1 的关键补充**：每个分组旁边展示"不确定原因"（源自 E2 的五维信号）比展示消息全文更重要。`voice_alignment < 0.5` 变成 UX 语言就是"口吻可能不一致"。

### 3.4 红灯交互：逐一审核 + 升级出口

```
┌─────────────────────────────────────────────┐
│ 🔴 需逐一确认 · 8 条消息                        │
│                                              │
│ ┌── 1/8 ─────────────────────────────────┐  │
│ │                                          │  │
│ │ 客户：刘强                          │  │
│ │ 风险：新客首触（加好友 18 小时前） + 隐私未确认  │  │
│ │                                          │  │
│ │ 建议消息：                                 │  │
│ │ 刘总好，那天在群里看到您对XX比较感兴趣，      │  │
│ │ 方便的话可以聊一下？                         │  │
│ │                                          │  │
│ │ ℹ️ 为什么这么写 [展开 ▼]                   │  │
│ │   ├─ 加好友来源: XX行业群                  │  │
│ │   ├─ 群内关键词: "面膜"、"效果"、"多少钱"   │  │
│ │   ├─ 称呼"刘总": 从群名片推断              │  │
│ │   └─ 当前状态: AI推断为"有兴趣(3)" 置信度0.62│  │
│ │                                          │  │
│ │ [编辑消息]  [确认发送]  [不发了]  [换成通用版本]│  │
│ └──────────────────────────────────────────┘  │
│                                              │
│ 进度：■□□□□□□□ 1/8  键盘：Enter=确认 E=编辑    │
│                                        S=跳过 │
└─────────────────────────────────────────────┘
```

**红灯硬上限：20 条。** 超限时系统提示拆分批次，或引导用户"以下 X 条可通过补充标签后降级为黄灯"。

**升级出口（E3补充）**：
- **"换成通用版本"**：系统重新生成一条不含价格承诺/功效描述的安全版本，自动降级为黄灯。E3："80% 的红灯是因为带了个承诺/风险表述，换成安全版就能发。"
- **"不发了"**：从本次群发中移除，不回退到任何分组。

### 3.5 万能操作：批量修正

> **[强共识，E1]** 如果用户抽查后发现风格/内容有问题，不应逐条修改。应提供批量修正入口："调整所有消息的语气 → 更亲切/更正式" 或 "给所有消息追加一句提醒"。

## 4. 客户回复感知系统

### 4.1 回复检测

系统通过**轮询微信本地 SQLite 数据库**检测回复（已有架构，04.场景层 §1）。

**回复分类逻辑**：

```
新消息到达
  │
  ├─ 时间窗口 ≤ 24h（距离我方最近发送）→ 进入内容匹配
  │   ├─ 含微信引用标记（quote_msg_id）→ DIRECT_REPLY
  │   ├─ 语义相似度 ≥ 0.4 → DIRECT_REPLY
  │   ├─ 纯社交信号（"好的""谢谢""嗯"）→ ACKNOWLEDGMENT
  │   └─ 相似度 < 0.4 且非社交信号 → UNRELATED
  │
  └─ 时间窗口 > 24h → INDIRECT_ENGAGEMENT
```

### 4.2 回复紧急度分类

> **[强共识，E1+E2+E3调剂]** E2 的 ESCALATE/FREEZE/CONTINUE 路由与 E3 的"立即/中等/低"完全吻合。唯一修正：将"购买信号"从 FREEZE 提升到 ESCALATE。

| 类型 | 示例 | 路由 | 延迟目标 | 来源 |
|---|---|---|---|---|
| `ESCALATE` | "多少钱"、"我要下单"、"过敏了怎么办" | 立即推送 | < 60s | E3-F |
| `FREEZE` | "有什么区别"、"还有别的颜色吗"、"用了有点干" | 15分钟聚合 | < 15min | E2 |
| `CONTINUE_HIGH` | "好的我看看"、"听起来不错" | 30分钟聚合 | < 30min | E2 |
| `CONTINUE_NORMAL` | 一般正面互动 | 60分钟聚合或每日摘要 | < 60min | E2 |
| `ACKNOWLEDGMENT` | "好的"、"谢谢"、表情包 | 每日摘要（20:00） | 同日 | E2+E3 |

> **E3-F**："意向客户问价，你 30 秒内不回，客户就走了。这不是夸张。" E2 原方案将 DIRECT_REPLY_QUESTION 归为 FREEZE（15分钟），**修正后拆分为**：购买信号（询价/下单）→ ESCALATE，信息询问（"有什么区别"）→ FREEZE。

### 4.3 多回复优先级排序

```
排序权重 = 优先级分(A) + 时间分(B) + 客户价值分(C)

A. 优先级分:  ESCALATE = 100, FREEZE = 60, CONTINUE_HIGH = 40, CONTINUE_NORMAL = 20, ACK = 5
B. 时间分:    max(0, 50 - 等待分钟数)
C. 客户价值:  老客户(6) +15, 已首购(5) +10, 洽谈中(4) +8, 有兴趣(3) +5
```

### 4.4 通知形式：渐进式两级

**第一级：聚合通知（非侵入式）**

```
┌─────────────────────────────────────────────┐
│ 🔔 群发"新品推荐"有 5 条新回复                 │
│                                              │
│ 🔴 需要立即处理 (2)                           │
│  · 李娜 问了价格                              │
│  · 张伟 要下单                               │
│                                              │
│ 🟡 可以稍后 (2)                              │
│  · 王芳 问有什么区别                          │
│  · 赵六 说用了有点干                          │
│                                              │
│ ✅ 客套回复 (1) — 已折叠                      │
│                                              │
│ [查看全部回复]                                 │
└─────────────────────────────────────────────┘
```

出现在：系统托盘弹窗、界面内顶部横幅、左侧客户列表角标。

**第二级：客户详情（点击后）**

展示回复原文、系统建议跟进动作、跳转到对话窗口。

### 4.5 回复 → 状态更新 → 跟进闭环

绿/黄/红审批通过并完成发送后，系统只读检测发送结果，在 DeepAxis 面板上更新各联系人的跟进状态（已发送待回复 / 已回复 / 待跟进）。用户可在面板上实时查看进度。

```
客户回复
  │
  ├─ 高意向（"多少钱"→ 询价）
  │   → 系统建议回复模板 → 用户确认发送
  │   → 加入"已处理"队列
  │   → 面板状态: 已回复
  │
  ├─ 中意向（"考虑一下"→ 犹豫）
  │   → 系统建议 2h 后跟进 → 加入待跟进队列
  │   → 面板状态: 待跟进
  │
  ├─ 低意向（"不需要"→ 拒绝）
  │   → 标记"已拒绝" → 移出跟进
  │   → 面板状态: 已关闭
  │
  └─ 其他 → 用户手动处理
```

> **E3-F**："发送后的 4-48 小时才是真正的工作量。我需要一个**待跟进队列**——不是只通知我谁回了，而是帮我记住要对谁做什么。"
>
> **状态追踪的设计意图**：DeepAxis 面板是用户的状态中枢。用户发送后看着面板的变化——谁已发送、谁回了、谁没回、谁需要立即行动。不需要离开 DeepAxis 去其他设备查看。

### 4.6 系统节流（注意力预算）

| 参数 | 标准值（默认） | 确信度 |
|---|---|---|
| ESCALATE | 无聚合，立即推送，不计入配额 | 高 |
| FREEZE 聚合窗口 | 15 分钟，窗口内 ≥ 2 条才推送（不足则延至 30 分钟，仍不足则直接推送） | 中 |
| CONTINUE_HIGH 聚合窗口 | 30 分钟 | 中 |
| CONTINUE_NORMAL 聚合窗口 | 60 分钟 | 中 |
| 每小时最大推送次数 | 3 次（ESCALATE 不计入） | 中 |
| 单日最大推送次数 | 15 次（不含每日摘要） | 中 |
| 免打扰时段 | 22:00-08:00（仅 ESCALATE 突破） | 中 |

> **E3 对聚合窗口的修正**：不是 timer 到了就推，而是 timer 到了且队列 ≥ N 条。避免"空等 14 分钟然后收到 1 条通知"。

## 5. 效率量化

### 5.1 全流程时间预算（200 人）

| 步骤 | 操作 | 目标耗时 | 过脑条数 |
|---|---|---|---|
| 1. 选人 | 筛选条件组合 + 预设加载 | 1-2 分钟 | — |
| 2. 生成预览 | 系统生成 + 三色分类 | 后台完成 | — |
| 3. 🟢 绿灯审核 | 确认矩阵 + 抽查 3 条 + 批准进入发送队列 | 30-60 秒 | 3 条 |
| 4. 🟡 黄灯审核 | 4-6 组 × 每组抽查 2 条 | 2-3 分钟 | 8-12 条 |
| 5. 🔴 红灯审核 | 逐一确认（上限 20 条） | 3-5 分钟 | 全部（最多20条） |
| 6. 最终确认 | 发送队列准备完成 | 3 秒 | — |
| **决策与准备总计** | | **约 6-8 分钟** | **约 25-35 条** |

### 5.2 效率提升倍数

| 对比基准 | 手动耗时 | DeepAxis | 提升 |
|---|---|---|---|
| 编写消息 | 200 × 30s = 100min | 0（系统生成） | ∞ |
| 审核确认 | 200 × 5s = 17min | 6-8min | 2-3x |
| 回复追踪 | 持续 1-2h（碎片化） | 系统自动追踪（面板状态: 待回复 → 已回复）+ 分级通知 | 大幅减少 |
| **决策与准备** | **~120min** | **~8min（面板审核）+ 异步通知** | **显著减少** |

注意：以上不包含物理发送耗时。DeepAxis 的目标是 5-8 分钟完成今日跟进决策、草稿审核和队列准备；最终发送由 Profile 决定，外部发布版默认由用户分波完成。

> 状态追踪的详细信息参见 [03.场域层 §4.4 发送双模式](./03.场域层-CRM+销售促进系统.md)。

### 5.3 效率价值锚定

> **"5分钟不浪费" —— 用户每天打开 DeepAxis 的 5 分钟内：**
> 1. 看到今天该跟进谁（优先级排序）
> 2. 审核完当天所有需要半自动准备的消息
> 3. 看到昨天发送的消息中有谁需要立即回复
> 4. 完成发送队列准备，随后由用户按节奏分波发送

## 7. E3 补充的实战需求

### 7.1 分波发送

> **E3-F**："我很少一次发 200 条。先发 30-50 个最活跃的看回复，调整话术后再发第二批。"

系统应支持：
- "先发送绿灯中 state ≥ 5 的客户" → 剩余暂存
- 分波之间的回复数据作为话术调整依据
- 默认每波 30-50 人；每日上限按账号使用习惯、历史发送量、近期异常、用户回复处理能力动态收紧

### 7.2 一键排除

> **E3-F**："审核时最频繁的操作不是'确认发送'，而是'这个人不发了——跳过'。"

消息卡片上右滑或点 X → 从本次群发移除。

### 7.3 发送节奏控制

> **E3-F**："200 条消息在 2 分钟内全发出，用户也处理不过来。"

- 可配置发送时段（工作日 9:00-21:00）
- 发送间隔保护处理节奏：5-15 秒随机（非等间隔）
- 跨时段分批发：≥ N 条自动跨上下午
- **面板状态追踪**：用户每发送完一条，系统只读检测发送结果后自动更新面板状态

### 7.4 可撤回性

> **E3-F**："消息发出去了，突然发现发错了，需要撤回。"

发送后展示最近 2 分钟内发送的消息列表，高亮可撤回（带撤回按钮）。超过 2 分钟的标灰不可撤回但可标记"待补救"。

### 7.5 多微信号统一管理

> **E3-F**："大多数工具只支持一个微信号。5 个号 = 5 次登录、5 个界面。没有任何工具把它们汇总到一个地方。" **这是硬需求。**

**分阶段方案**：
- **1.0（分号管理）**：每个微信号独立管理，P1 采样管线附加 `source_wechat_id` 标签，前端按号筛选或汇总展示。不做跨号去重。
- **2.0（跨号合并）**：基于昵称/备注/共同群聊的启发式匹配，识别"A 号张伟" = "B 号张伟"。

## 8. 信任建立机制

### 8.1 主动的、数据驱动的信任

> **[强共识，E1+E3]** E2 的理论框架正确，但需要主动的可视化信任建立，而非被动等待算法收敛。

**三个信任触点：**

1. **发送后结果报告**（前 10 次绿灯发送后展示）：
   "上周绿灯发送的 32 条消息：28 条已收到回复（87.5%），0 条被投诉，4 条未回复。"

2. **编辑差异解释**（每次编辑后展示）：
   "你修改了张伟的称呼从'张总'到'张哥'。已学习：对状态为'老客户'的联系人，使用亲密称呼。下次会自动使用。"

3. **进步导向的校准报告**（100 条消息后首次，之后每 200 条一次）：
   "系统越来越懂你了：你的编辑率从最初的 40% 下降到现在的 12%。你直接发送的消息中，89% 收到了客户回复。"

### 8.2 产品事实与订单事实前置

绿灯和批量准备依赖事实底座。进入 P2 前必须至少具备：

- 产品事实卡：价格区间、库存/活动、卖点、禁用承诺、FAQ、素材。
- 轻量订单信号：已买、待付款、待发货、已发货、售后中、复购周期。

没有事实底座时，复购提醒、物流确认、售后回访、最近行为冲突检测只能作为黄灯或红灯候选，不能作为绿灯低风险批量准备。

### 8.3 异步审计（应对"信任悖论"）

> **[E2识别的新风险]** "系统的可靠性越高，用户的监督越少，未发现的系统性偏差越可能积累。"

每天在用户空闲时段，随机抽取当天已发送的 5% 的绿灯消息展示给用户做"事后审计"：
   "今天你通过绿灯队列发送了 130 条消息。随机抽查 6 条：" — 用户可标记有问题 → 触发校准。

## 9. 边界规则

### 9.1 不可突破的约束

- 🔴 最终发送是 L3 能力，必须由 Profile 和 Governance 控制；外部发布 Profile 默认关闭
- 🔴 用户**必须**对每条消息或批次做出授权动作（绿灯=批量授权进入队列，黄灯=分组授权进入队列，红灯=逐条确认；最终物理发送按 Profile 执行）
- 🔴 消息内容**必须**基于个人上下文（框架层 §1）
- 🔴 DeepAxis 默认本地处理，不上传到自有云；微信写回属于单独授权的外部同步能力（04.场景层 §0）

### 9.2 绿灯的信任边界

- 绿灯 ≠ "系统不会出错"，绿灯 = "出错概率低到不值得你花时间逐条看"
- 绿灯的用户确认动作从"逐条确认"变为"抽查 + 批量授权进入队列" — 仍然是用户确认，只是确认的粒度变了
- 如果用户通过"抽查不通过"将绿灯整批降级，系统记录否决事件，用于校准

### 9.3 规模边界

- **回复容量预警**：系统根据历史回复率估算本批次预计回复量。如果 > 用户历史日处理能力，提示但不阻止。
- **红灯硬上限 20 条**：超过则强制拆分批次或引导数据治理。
