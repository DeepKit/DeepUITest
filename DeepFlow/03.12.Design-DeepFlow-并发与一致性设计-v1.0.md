## 1. 概述

本文档作为`03.02.Design-DeepFlow-CoreModelAndPrinciples-1.0` 的补充，详细定义 deepFlow 在多客户端、多系统并发访问场景下的一致性保证机制。

### 1.1 设计目标

- **事件顺序一致性***：同一 FlowInstance 的事件序列全局有序
- **写入原子性***：事件写入要么完全成功，要么完全失败
- **读取一致性***：读取操作返回一致的快照视图
- **冲突可检测***：并发写入冲突可被检测并合理处理

### 1.2 适用场景

## 2. 版本号与乐观锁机制

### 2.1 FlowInstance 版本控制

每个 FlowInstance 维护一个单调递增的版本号。

```ts
interface FlowInstance {
  flowId: UniFlowId;
  version: number;           // 当前版本号，从 0 开始
  expectedVersion?: number;  // 写入时的期望版本（乐观锁字段）
  status: UniFlowStatus;
  // ...
}
```

**版本递增规则**：
- 每次成功写入事件，version += 1
- 快照创建时记录对应的 version
- 版本号永不回退（即使回滚操作也产生新版本）

### 2.2 乐观并发控制（OCC）

```ts
interface WriteEventRequest {
  flowId: UniFlowId;
  expectedVersion: number;  // 客户端认为的当前版本
  event: UniFlowEvent;
}

interface WriteEventResponse {
  success: boolean;
  newVersion?: number;      // 写入成功后的新版本
  error?: {
    code: 'VERSION_CONFLICT' | 'INVALID_STATE' | 'WRITE_FAILED';
    currentVersion?: number;  // 冲突时返回实际版本
    message: string;
  };
}
```

**冲突检测流程**：

```
    ▶                           ▶                               ▶
     │                           │                               │
     │ 读取 Flow (version=5)     │                               │
     │◄───────────────────────────│                               │
     │                           │     读取 Flow (version=5)     │
     │                           │───────────────────────────────►│
     │                           │                               │
     │ 写入事件 (expect=5)       │                               │
     │───────────────────────────►│                                │
     │                           │ 检│ 5==5 │                 │
     │ 成功 (newVersion=6)       │ 写入成功                      │
     │◄───────────────────────────│                               │
     │                           │                               │
     │                           │     写入事件 (expect=5)       │
     │                           │◄───────────────────────────────│
     │                           │ 检│ 5!=6 │                 │
     │                           │     VERSION_CONFLICT          │
     客户端                          │───────────────────────────────►│
```

### 2.3 冲突解决策略

客户端收到 VERSION_CONFLICT 时的处理方式:

```ts
async function writeEventWithRetry(
  request: WriteEventRequest,
  maxRetries: number = 3
): Promise<WriteEventResponse> {
  for (let i = 0; i < maxRetries; i++) {
    const response = await writeEvent(request);
    
    if (response.success) {
      return response;
    }
    
    if (response.error?.code === 'VERSION_CONFLICT') {
      // 策略1: 重新读取最新状态，重新生成事件
      const latestFlow = await getFlow(request.flowId);
      request.expectedVersion = latestFlow.version;
      
      // 策略2: 根据业务逻辑决定是否需要重新计算 payload
      if (needsPayloadRecalculation(request.event, latestFlow)) {
        request.event = await recalculateEvent(request.event, latestFlow);
      }
      
      continue;
    }
    
    // 其他错误直接返回
    return response;
  }
  
  return {
    success: false,
    error: {
      code: 'WRITE_FAILED',
      message: `写入失败，已重试 ${maxRetries} 次`
    }
  };
}
```

## 3. 事件写入原子性

### 3.1 单事件写入

单个事件写入使用数据库事务保证原子性：

```sql
BEGIN TRANSACTION;

-- 1. 检查版本号
SELECT version FROM flow_instances WHERE flow_id = ? FOR UPDATE;

-- 2. 验证版本匹配
-- (应用层检查)

-- 3. 插入事件
INSERT INTO uni_flow_events (
  id, flow_id, type, step, source, status, timestamp, payload, error_code
) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?);

-- 4. 更新版本号
UPDATE flow_instances SET version = version + 1 WHERE flow_id = ?;

COMMIT;
```

### 3.2 批量事件写入

某些场景需要原子写入多个相关事件：

```ts
interface BatchWriteRequest {
  flowId: UniFlowId;
  expectedVersion: number;
  events: UniFlowEvent[];  // 按顺序写入
  createSnapshot?: boolean; // 写入后是否创建快照
}
```

批量写入的约束：
- 所有事件必须属于同一个 FlowInstance
- 事件按数组顺序写入，每个事件递增版本号
- 任一事件写入失败，整批回滚

### 3.3 事件 ID 生成

事件 ID 必须全局唯一且可排序。

```ts
// 推荐格式: {timestamp}-{flowId_suffix}-{random}
// 示例: 20251204T103045Z-abc123-x7k9m

function generateEventId(flowId: UniFlowId): string {
  const timestamp = new Date().toISOString()
    .replace(/[-:]/g, '')
    .replace(/\.\d{3}/, '');
  const flowSuffix = flowId.slice(-6);
  const random = crypto.randomBytes(4).toString('base36');
  return `${timestamp}-${flowSuffix}-${random}`;
}
```

## 4. 快照隔离与管理

### 4.1 快照隔离级别

deepFlow 支持两种快照读取模式：

```ts
type SnapshotIsolation = 
  | 'READ_COMMITTED'    // 读取最近已提交的快照
  | 'SNAPSHOT'          // 读取指定版本的快照
  | 'LINEARIZABLE';     // 读取最新状态（可能需等待进行中的写入）
```

**默认隔离级别**: `READ_COMMITTED`

### 4.2 快照创建策略

```ts
interface SnapshotPolicy {
  // 自动快照条件
  autoSnapshot: {
    everyNEvents: number;      // 每 N 个事件创建快照，默认 10
    onStatusChange: boolean;   // 状态变更时创建快照，默认为 true
    onUserConfirm: boolean;    // 用户确认步骤后创建快照，默认 true
  };
  
  // 快照保留策略
  retention: {
    keepLatestN: number;       // 保留最近 N 个快照，默认 5
    keepSucceeded: boolean;    // 始终保留成功结束的快照，默认 true
    maxAgeHours: number;       // 最大保留时长（小时），默认 720（30天）
  };
}
```

### 4.3 快照重建

当请求的快照不存在时，从事件序列重建快照。

```ts
async function getOrRebuildSnapshot(
  flowId: UniFlowId,
  targetVersion: number
): Promise<UniFlowSnapshot> {
  // 1. 尝试直接获取
  const existing = await getSnapshot(flowId, targetVersion);
  if (existing) return existing;
  
  // 2. 找到最近的基础快照
  const baseSnapshot = await getNearestSnapshot(flowId, targetVersion);
  const startVersion = baseSnapshot?.version ?? 0;
  
  // 3. 获取需要重放的事件
  const events = await getEvents(flowId, {
    versionFrom: startVersion,
    versionTo: targetVersion
  });
  
  // 4. 重放事件构建状态。
  let state = baseSnapshot?.stateJson ?? {};
  for (const event of events) {
    state = applyEvent(state, event);
  }
  
  // 5. 可选：持久化重建的快照
  const snapshot: UniFlowSnapshot = {
    flowId,
    version: targetVersion,
    stateJson: state
  };
  
  await saveSnapshot(snapshot);
  return snapshot;
}
```

## 6. 错误码定义。

### 6.1 并发相关错误码。

```ts
const ConcurrencyErrorCodes = {
  // 版本冲突
  VERSION_CONFLICT: 'DEEPFLOW/CONCURRENCY/VERSION_CONFLICT',
  
  // 写入超时
  WRITE_TIMEOUT: 'DEEPFLOW/CONCURRENCY/WRITE_TIMEOUT',
  
  // 锁获取失败
  LOCK_ACQUISITION_FAILED: 'DEEPFLOW/CONCURRENCY/LOCK_FAILED',
  
  // 快照重建失败
  SNAPSHOT_REBUILD_FAILED: 'DEEPFLOW/CONCURRENCY/SNAPSHOT_REBUILD_FAILED',
  
  // 事务回滚
  TRANSACTION_ROLLBACK: 'DEEPFLOW/CONCURRENCY/TX_ROLLBACK',
} as const;
```

### 6.2 错误处理建议

| 错误码 | 客户端处理建议 |
|--------|---------------|
| VERSION_CONFLICT | 重新读取状态，合并后重试。|
| WRITE_TIMEOUT | 检查网络，延迟后重试。|
| LOCK_ACQUISITION_FAILED | 等待后重试，最多3次。|
| SNAPSHOT_REBUILD_FAILED | 报告错误，需人工介入 |
| TRANSACTION_ROLLBACK | 检查数据完整性，重新发起流程 |

## 7. 性能优化建议

### 7.1 读写分离

- 读操作优先使用缓存。
- 热点 Flow 的快照可缓存在内存。
- 写操作总是走主存储

### 7.2 批量操作

- 支持批量事件写入减少事务开销
- 快照清理使用后台任务批量处理

### 7.3 索引策略

```sql
-- 事件查询优化
CREATE INDEX idx_events_flow_version ON uni_flow_events(flow_id, version);
CREATE INDEX idx_events_flow_timestamp ON uni_flow_events(flow_id, timestamp);
CREATE INDEX idx_events_source ON uni_flow_events(source);

-- 快照查询优化
CREATE INDEX idx_snapshots_flow_version ON uni_flow_snapshots(flow_id, version DESC);
```

## 8. 测试要点

### 8.1 并发测试场景

1. **乐观锁冲突**：两个客户端同时写入同一 Flow
2. **快照一致性**：写入过程中读取快照
3. **事务回滚**：写入中途失败的回滚验证
4. **重放一致性**：删除快照后重建，验证状态一致。

### 8.2 压力测试指标

- KafkaFlow 写入 TPS > 100
- 并发冲突重试成功率 > 99%
- 快照重建延迟 < 500ms·s 事件清单。
