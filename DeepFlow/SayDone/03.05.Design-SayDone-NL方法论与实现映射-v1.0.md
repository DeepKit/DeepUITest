# SayDone NL 方法论与实现映射（DevDirector 内嵌版）

> 本文档作为桥接文档：

> - 上接 `SayDone-设计原则.md` / `SayDone-方法论.md` 中的理念与架构；

## 1. 方法论回顾：我们到底在做什么？

### 1.1 核心公式

来自 SayDone 顶层设计者

> **结构化抽取 = 领域识别 + 模板激活 + 增量修改 + 超模型AI 补充**

其中DevDirector 内嵌 NL MVP 中，我们聚焦在其中一条最细的一支：

- 聚焦 **UI 表单页面** 这一单一领域（登录页、注册页、联系页等）。
- 通过 LLM 生成结构化JSON，再映射到`TNLParseResult` / `TUIScreen`。
- 只做很薄的一层「增量修改」（用户通过 NL 预览中手动调标题、字段文案等）。

### 1.2 三层转换引擎与当前覆盖面

在`SayDone-设计原则.md` 中，自然语言交互被拆成三层：

1. **语义捕获器** 即捕获用户说的每一句话、每一个点选，提取动作+目标+属性；
2. **需求累积层** 它把一次次输入累积成稳定的需求状态，而不是“一次性聊天”；
3. **显影触发层** 它在恰当时机，把当前状态以弹窗/代码的形式显影给用户。

当前 DevDirector 中的 NL 组件，大致对应：

- 语义捕获层：
  - 由UI（`UI.Panels.NLInput` / SoIs 侧面板）负责，把文本输入和场景类型封装成 `Input + SceneType`。
- 需求累积层：
  - 目前*极简*：NL 本身按"一次输入，一次解析"工作，状态累积更多在 SoIs SessionService / DevDirector 域模型里完成了：
- 显影触发层：
-   `NL.Parser.Parse(解析(
      返回TNLParseResult
      得到ToUIScreen
      触发DevDirector 画布刷新`;
- 执行`ApplyNLParseResult`修复SoIs SVG 草图刷新

可以理解为：**当前 NL 组件是"转换层→结构化数据"这一步的 MVP 实现。**

## 2. 后台角色到当前组件的映射

SayDone 方法论中有一系列"后台角色"（总导演/监工/AI代理/守卫/自检/记忆/回滚员）等）
不过DevDirector 内嵌版中，并没有把这些角色全部拆成独立服务，而是在职责上已经部分落实**

下表是一个“概念→实现”的对照表（只列 NL 相关部分）：

| 方法论角度概念 | 当前实现中的承载结构 | 说明 |
|----------------|--------------------|------|
| AI代理 (AI Agent) | `ILLMService` + `TLiteLLMService` / `TMockLLMService` | 统一封装了 LiteLLM/OpenAI 的调用；负责“生成内容”但不做质量判断 |
| 守卫者 (Guardian) | `NL.Validator` + `TNLParseResult.FromJSON` | 前者做 Schema+业务规则校验，后者在 JSON 不合法时直接抛异常，相当于格式守护者 |
| 自检者 (Self-Checker) | 当前**未独立拆分**，部分逻辑体现在测试和重试策略中 | 将来可以在 Parser 与 Validator 之间插一层“AI 自审者” |
| 记忆者(Memory Keeper) | `Infra.Sqlite.NLCacheRepository` + Prompt 库 | 通过输入+场景 的Hash 的方式做 NL 级缓存，相当于记住"同样的话之前怎么解析过"；Prompt 仓库则是"长期记忆库" |
| 调度者/总导演(Director/Orchestrator) | `TAppServices.InitializeAppServices` + UI 按钮事件 | 决定什么时候调用NL、用哪种 LLM 服务、是否启用重试等；逻辑目前是静态的过程式代码 |
| 回滚者(Rollback Agent) | DevDirector/SoIs 各自的快照/HiDeepDeepDeepDeepDeepStoryEvent 机制 | NL 只负责"生成结构化结果"，真正的回滚通过 HiDeepDeepDeepDeepDeepStoryEvent/快照来做 |

**结论**：

- 方法论里提出的大部分职责，在 DevDirector 里都有对应的“落地点”；
- 只是目前**没有强制拆成 9 个服务接口**，而是内嵌在具体类中；
- 后续如要演进为独立 SayDone 引擎，可以以这些类为"雏形"向外抽象出来。

## 3. 一次解析从用户到结构化的"方法论视角"。

以用户在 DevDirector 述成 Tab 输入“做个登录页”为例：

### 3.1 用户视角 4。

1. **输入愿望**：在"自然语言输入框"中输入一句话（可选选择场景类型 `FormPage`）。
2. **等待显影**：点击"解析"，看到进度指示/等待状态。
3. **查看结果**：右侧列表出现"用户名 / 密码 / 登录按钮"等结构化字段信息。
4. **确认/调整**：满意则"确认使用"生成 UIScreen，不满意则修改标签字段文案，或重新解析。

### 3.2 系统内部 7 步（映射方法论阶段）

1. **意图归档（语义捕获层）**
   - UI 收集：`InputText = "做个登录页"`，`SceneType = 'FormPage'`。
   - 由 App.Services/SoIs SessionService 记录当前上下文（FeatureId/ProjectId 等）。

2. **Prompt 构建（模板激活 + 领域约束）**
   - `TNLPromptBuilder.Build(InputText, SceneType)`。
      - 在 `prompts` 表加入 `Category='nl_system'`、`SceneType='FormPage'` System Prompt。
      - 组装成固定结构（System Prompt + 分隔符 + 用户输入）。
- 这一步相当于方法论中的"模板激活"+ 上下文注入。

3. **调用 LLM（AI代理执行）**
   - `ILLMService.Chat('', Prompt)');
     - 通过 `TLiteLLMService` 调用 LiteLLM/OpenAI 兼容接口。
     - 要求模型输出一个包含`type/title/fields/submitButton` 的JSON 对象（规范体现在 Prompt 与测试中）。

4. **JSON 提取与解析（守卫员第一道关卡）**
   - `TNLParser.ExtractJSON(ResponseText)`;
     - 尝试从  代码块/  代码块/ 原文中的 `{...}` 中提取JSON。
   - `TNLParseResult.FromJSON(JSONText)`;
     - 不符合预期结构时抛异常，相当于硬编码 Schema 关卡的一部分。

5. **验证（守卫员第二道关卡）**
   - 若注入了 `NL.Validator`;
     - `ValidateSchema`：检查标签字段数量/字段名唯一性等。
     - `ValidateLogic`：登录注册/联系等场景的业务规则（登录必须有密码，注册建议有邮箱/手机等）。
   - 不通过时：
     - `ParseAsync` : 直接通过 `OnError('验证失败: ...')` 告知 UI。
     - `ParseWithRetryAsync` : 把错误信息当作"提示块"追加到下一个Prompt 中，让 LLM 带着反馈重试。

6. **缓存与记忆（记忆官轻量版）**
   - 若有 `INLCacheRepository`，
      - **无验证提示** 的情况下，
        - 解析前：尝试缓存`InputText + SceneType` 的Hash 命中缓存
- 解析后：写入 `TNLCacheRecord`（Input/SceneType/OutputJSON + 时间戳、命中次数）缓存
    - 这提供了"同一句话不用每次都跑一遍LLM"的记忆能力

7. **显影与落地（显影触发层）**
- DevDirector模式
      - 在NL 预览面板中展示`TNLParseResult.Fields` 列表中的项。
- 用户确认后调用`ToUIScreen(ProjectId, FeatureId)`，写入UI 仓储 + HiDeepDeepDeepDeepDeepStoryEvent
 - SoIs错
      - 通过 `ApplyNLParseResult` 把字段映射为 TVizUIScreen 结构，重新生成 SVG 草图

这条链路，可以看成是"方法论 SayDone 引擎"的一个最小闭环实现。

## 4. 当前实现的“边界条件”与设计约束

为了保证简单可靠，当前内嵌 NL 有一些刻意收紧的边界，在扩展时需要注意不要随便打破边界

### 4.1 场景类型边界

- 当前实现只正式支持少数几个`SceneType`，尤其是
  - `FormPage`（表单页面）
  - 其他诸如 `ListPage` / `DetailPage` / `Dashboard` 更多是预留常量；
- `TNLParseResult.ToUIScreen` 默认按"对话框型Form"去映射控件

**扩展建议**：

- 如要引入新场景类型（例如 `SearchPage`、`WizardPage`）：
  1. 先在 SayDone 方法论层定义这个场景的"信息结构"（有哪些区域、典型字段、最小可用版本）：
2. 再在 Prompt 中写清楚期望 JSON 结构的？
3. 最后才是扩展到 `ToUIScreen` 的映射逻辑？

### 4.2 字段类型边界

- `TNLFieldType` 目前是八个固定值，已经覆盖了大部分表单场景了？
- `NL.Validator` 的逻辑验证默认依赖这套字段类型（比如通过 `HasPasswordField/HasTextareaField`）了？

**扩展建议！**

- 新增字段类型前，先问三件事：
   1. **用户会怎么自然表达？***（Prompt 里要能引导出这种字段）；
2. **在UI 里对应什么组件？**（`TUIScreen` 上有没有合适的 CanonicalKind/DialectType）；
3. **验证规则如何设计？**（Schema/业务层面要不要特殊校验）吗？

- 确认之后再依次扩展：
  - `TNLFieldType` 枚举 + `FieldTypeStr/StrToFieldType`枚举定义？
  - `ToUIScreen` 中的控件映射实现方式？
  - （可选）`NL.Validator` 中专门针对该类型的规则注册。

### 4.3 输出结构约束与"只输出JSON"理想状态。

- 方法论层面，希望 LLM 输出**严格符合Schema约束的JSON**。
- 当前实现采用"容忍提取"的方式。
  - 容忍 LLM 外层有解释文字，只要能在其中找到 `{...}`即可
  - 优先提取  代码块中的内容即可

**扩展建议（迈向严密的Schema约束）?**

1. 在Prompt 中更明确地要求"只输出一个JSON 对象，不要多余文字"；
2. 在`TLiteLLMService` 上游增加一层"Schema 验证服务"：
   - 将`TNLParseResult` 的JSON Schema 显式化；
   - 在送入 `FromJSON` 之前进行 Schema 校验，不合法时要要求LLM 重写输出即可
3. 如未来有需要，可以把"守卫员"从 `NL.Validator + FromJSON` 中抽成独立单元，形成真正的"格式关卡"即可

## 5. 如何在不违背方法论的前提下扩展NL

下面是几个常见扩展方向及**推荐做法**（"先方法论，再实现"）即可

### 5.1 增加新的业务场景（例如：注册页、密码重置页的细分）

1. **先写好DSL / JSON 结构**即可
   - 在方法论/设计文档中描述这个场景的“字段模板”；
   - 确认哪些是必备字段、哪些是可选字段、哪些由系统推断即可
2. **补充 Prompt**即可
   - 在`Infra.Sqlite.PromptInit` 或配置脚本中，为`SceneType` 写一个System Prompt
   - Prompt 中要明确输出字段的语义与约束即可
3. **调整 Validator**即可
    - 如果该场景有特殊业务规则（例如密码重置必须验证邮箱、手机），把规则写到`NL.Validator`里？
4. **最后才做 UI？**
    - DevDirector/SoIs 做 UI 可以继续消费 `TNLParseResult`，只需要在文案/图形上做个性化呈现吗？

### 5.2 把"澄清过程"拉长（多轮问答？）

当前内嵌 NL 是"一轮自然语言输入一次解析"，多轮澄清主要由 SoIs 负责？

如果要把"多轮澄清"能力部分下沉到 NL 层，建议如下：

- 把"澄清问答"留给 SoIs（或上层 UI），NL 层关注：
  - **在 Prompt 中注入澄清结果*（例如当前已确认的数据字段、业务约束）；
  - **在 Validator 的错误信息中给出"下一步澄清建议？"*？

这样可以保持职责清晰吗？

- SoIs：负责“问什么、如何问”；
- SayDone/NL：负责"在给定的已知条件下，生成一个结构化表单 + 校验它是否合理"？

### 5.3 与更完整的 SayDone 引擎对接

当未来独立的 SayDone 服务上线时，本地 NL 可以演进为：

- **本地轻量模式（当前实现）**：
  - 使用嵌入式轻量 LLM（或 Mock）；
  - 适合离线/开发环境；
- **远程重载模式（未来）**：
  - `TLiteLLMService` 不再直接调 OpenAI，而是连独立 SayDone 服务？
  - 上游 `TNLParser` / `NL.Validator` 可以逐步薄化，把更多逻辑下沉到SayDone。
  - 但对 DevDirector/SoIs 来说，`INLParser` 接口尽量保持稳定。

这种演进路径保证平滑过渡。

- **当前代码立即可用**。
- 同时不锁死未来的独立服务化方案。

## 6. 与其他文档的关系与阅读顺序建议。

如果你是第一次接触该 NL 子系统，推荐的阅读顺序：

1. `docs/SayDone/README.md`
   - 了解 SayDone 的定位、三层架构、三个后台角色等。
2. `docs/SayDone/SayDone-设计原则.md`
   - 理解自然语言交互的体验目标与质量保障理念。
3. `docs/SayDone/SayDone-NL-方法论与实现映射.md`（本文）
   - 搞清楚方法论概念如何落在 DevDirector 内嵌 NL 中"落在了哪里"；
4. `docs/SayDone/SayDone-NL-组件实现说明.md`
   - 查看具体单元（`Domain.NL`、`NL.Parser`、`NL.Validator`、`NL.PromptBuilder`、`NL.LiteLLMService`）的接口与代码细节；

   - 通过单元测试案例理解典型输入/输出与错误场景。

这样可以**愿景 → 方法 → 当前实现 → 测试案例**形成一条完整链路。
