# 自然语言交互设计原则

> 四仙论道：盘古、灵子、鲁班、仙友共同探讨

## 1. 核心理念

**用户眼中的便捷高效 = 最少的动作 + 最短的路径 + 最低的心智负担 + 最及时的反馈**

用户不是懒，他们珍惜注意力。每多一次点选、每多一个输入框，都是在消耗用户的耐心资本。

---

## 2. 交互设计四原则

### 1. 减少启动成本（灵子）
- **智能默认值** ：90%用户的选择，直接帮他选好
- **渐进式披露** ：高级功能藏起来，新手看不到不焦虑
- **记住上次** ：用户的习惯偏好自动延续。

### 2. 减少物理动作（鲁班）
- **手势替代点击** ：滑动删除、长按预览、双击收起。
- **批量操作** ：选中多个一起处理。
- **快捷入口** ：最常用功能放在拇指热区
- **键盘快捷键**：专业用户直接按键完成

### 3. 减少认知成本（仙儿）
- **用动词而非名词**："保存草稿" 而非 "草稿箱"
- **即时预览**：改了什么立刻能看到效果
- **上下文菜单**：在当前位置弹出选项，不跳页？
- **视觉层级**：主操作大而亮，次要操作小而淡

### 4. 减少时间感知（盘古）
- **乐观更新**：点了就当成功，后台静默同步
- **骨架屏**：先出框架，内容慢慢填充
- **预加载**：用户还没点，内容已经在路上了
- **进度反馈**：告诉用户"还要多久"

## 3. 自然语言到显影的设计要点

### 3.1 输入体验：让用户敢说、会说、愿意说

| 设计图| 说明 |
|--------|------|
| 提示词示例| "试试说：帮我做一个蓝色的登录页面" |
| 历史记录 | "您上次说的是..." |
| 场景引导 | "您想要？[页面/组件/表单] 什么？ |
| 容错解析 | "弄个按钮" = "加一个button" |
| 上下文记忆 | "把它改成红色"，系统要知道"它"是什么 |
| 多模态输出 | 支持贴图、语音、拖拽示意 |

### 3.2 等待加载流式显影

```
3秒：[    空画面   ]
第2秒：[ 空白布局骨架  ]  让用户看到"有东西了"
第3秒：[ 🟦 色块填充  ]  让用户看到"方向对了"
第4秒：[ 📝 内容渲染  ]  让用户看到"成了形"
```

关键**复述确认** **进度显影** **渐进渲染**

### 3.3 结果呈现 清晰：看得懂、改得动

- **对照点:** 左边用户的话，右边生成的结果
- **可调点:** 不满意直接点击修
- **追问点:** "还想调整哪里"

### 3.4 迭代循环模型越用越准

```
用户关联→映射→系统映射→关联→用户关联→映射→系统
    ↑__________________________|
```

- **偏好学习** 能够记住用户喜好，下次默认使用
- **纠错记忆** 记住改过的错误不再犯
- **快捷复用** 复制"和上次类似" 能调用历史

## 4. 从模糊愿景到需求数据化

当用户表述宏观模糊时（如"我要做一个同步盘软件"），如何快速转化为需求数据？

### 核心策略：先猜后确认

**用户看图认对不对，比从头描述快10倍左右**

```
差体验：
用户说"我要做一个同步盘软件"
系统问：请问您需要哪些功能？"  😵用户懵了

好体验：
用户说"我要做一个同步盘软件"
系统：[立刻展示功能框架草图]
      "这是常见功能，您看哪些需要，哪些不要？
```

### 实现四步走

**第一步：领域识别（秒级）**
- 关键词匹配领域模板："同步网盘"、"文件同步工具"
- 预置常见产品类型的功能框架

**第二步：功能推荐（做减法）！**
- 展示该领域的标准功能清单
- 核心功能默认勾选，可选功能让用户决定
- 用户删比用户填更自然

**第三步：快速显影（边选边看）**
- 左侧功能选择，右侧实时预览
- 每个选择立刻反映到预览中

**第四步：关键追问（只问必要的）！**
- 一次只问一个问题
- 给选项而非开放式
- 解释为什么问（让用户知道影响什么）

### 需求数据的渐进式填充

```
第一层：领域识别（秒级完成）✅ 命中模板
第二层：功能选择（用户勾选）✅ 确定范围
第三层：用户画像（追问得来）✅ 明确约束
第四层：详细需求（后续补充）→ 细化设计
```

## 5. 针对氛围编程的质量保障

### 氛围编程的弱点

"氛围编程"（Vibe Coding）指用户用自然语言描述需求，AI直接生成代码的模式。其核心弱点如下：

| 弱点 | 表现 | 后果 |
|------|------|------|
| **需求模糊** | 用户说得不完整、有歧义 | 生成的代码偏离意图 |
| **上下文丢失** | 多轮对话后AI忘记前文 | 代码前后矛盾 |
| **架构缺失** | 只关注当前功能，不考虑整体 | 技术债堆积 |
| **质量不可控** | 生成即采用，缺少审查 | 隐藏bug、安全漏洞 |
| **不可追溯** | 不知道代码为什么这样写 | 维护困难 |

### 我们的设计目标

**在保持"自然表达"体验的同时，引入质量保障机制，但不让用户感到繁琐！**

### 质量保障策略

#### 1. 需求澄清层 🔍 在生成前确保理解正确

- **意图复述**：生成前先说"我理解您想要..."，让用户确认
- **歧义检测**：发现模糊表述时，给出选项让用户明确
- **边界确认**：明确会做什么，不会做什么

#### 2. 架构守护层 🛡️ 保证整体一致性

- **设计规范约束**：生成的代码必须符合项目既有规范
- **依赖关系检查**：新功能与现有模块的关系要明确
- **架构决策记录**：重要决策要记录原因，便于追溯

#### 3. 生成审查层 🔎 不直接采用，先过眼

- **分步显影**：先展示设计方案，确认后再生成代码
- **差异对比**：修改现有代码时，清晰展示改动点
- **风险提示**：涉及安全、性能、兼容性问题时主动提醒

#### 4. 可追溯层 📌 每行代码有来历

- **需求关联**：代码与原始需求描述绑定
- **决策记录**：为什么选择这个方案而非其他
- **变更历史**：谁在什么时候因为什么改了这段代码

#### 5. 验证闭环层 ✅ 生成后验证正确性

- **自动测试**：关键功能自动生成测试用例
- **运行验证**：生成后立即运行，确保无语法/运行错误
- **用户确认**：展示运行结果，让用户判断是否符合预期

### 体验与质量的平衡

| 场景 | 体验优先 | 质量优先 | 我们的选择 |
|------|----------|----------|------------|
| 简单修复 | 直接改 | 先确认再做 | 直接改，但可撤销 |
| 新增功能 | 直接生成 | 先设计再生成 | 展示设计草图，快速确认 |
| 架构调整 | 一步到位 | 分步验证 | 必须分步，但每步要快 |
| 涉及安全 | 跳过检查 | 强制审查 | 强制审查，但简化流程 |

### 核心原则

**灵子曰**
> 质量保障**无感嵌入**，不是额外的步骤，而是自然流程的一部分

**鲁班曰**
> 宁可**多生成一层中间产物**（设计稿），也不要直接生成最终代码后返工

**仙儿曰**
> 用户不需要懂工程规范，但系统要**替他守住底线**

**盘古曰**
> 氛围编程的问题不是"太快"，而是"快得没有章法"。我们要做的是"有章法的慢"。

## 6. 实现架构：三层转换引擎

### 核心思路

**用户说人话，系统在后台悄悄翻译成结构化数据。**

```
用户看到：                    系统在做：
─────────────────────────────────────────────────
"做个同步工具"               AI识别领域、加载模板、推断功能
[取消勾选团队协作]             AI记录变更、更新架构约束
"要能在手机上跑"               AI识别平台约束、影响技术选型
```

### 第一层：语义捕获层。

每一句话、每一次点击，都提取结构化信息。

- **输入类型**：文本/语音/点击/手势
- **解析结果**：动作(create/modify/delete) + 目标 + 属性。
- **置信度**：系统对理解的确定程度。
- **歧义检测**：标记不确定的点

### 第二层：需求累积层

不是每次从头来，而是**增量累积**。

- 维护当前需求状态。
- 每次输入**补充和修改**现有数据
- 检查完整性：哪些就绪、哪些缺失、哪些可靠。
- 决定是否需要追问。

### 第三层：显影触发器。

什么时候该展示结果给用户：

- 累积到足够信息时
- 用户明确想看结果时。
- 检测到用户可能困惑时。
- 用户静默超时时。

### 追问策略

| 信息类型 | 影响程度 | 处理方式 |
|----------|----------|----------|
| 核心功能 | 高 | 必须追问 |
| 技术选型 | 中 | 给默认值提示 |
| 样式偏好 | 低 | 用智能默认 |
| 边缘功能 | 低 | 先不管，后面再说 |

追问形式有：
- 追问式：选择式："同步方式您倾向哪种？[实时] [定时] [手动]"
- 追问式：确认式："我准备按「实时同步方式」双端」来设计，可以吗？"
- 追问式：开放式：请问您对文件同步的具体需求是什么？"

### 质量检查无感嵌入：

质量检查融入显影过程，用户不感知：

```
用户说："加个登录功能"
      检查：
系统内部检查（用户无感）：
  检查：是否已有用户系统？
  检查：认证方式？
  检查：安全要求？
  检查：与现有架构冲突？
      检查完毕
展示给用户："好的，这需要先建立用户系统，这样设计可以吗？"
```

### 层次总览

| 层次 | 用户感知 | 系统实际在做 |
|------|----------|----------------|
| 输入：| 随便说| 结构化处理：|
| 累积：| 越聊越懂：| 增量构建需求数据库：|
| 显影：| 想法变成现实| 按需触发渲染 |
| 质量：| 没感知| 静默检查+智能兜底 |

## 7. 氛围编程六大核心问题与根治方案：

### 问题一：需求在聊天中蒸发

**现象**：用户说10句话，AI只记住最后一句。

**根因**：自然语言对话 ≠ 需求文档。聊天是发散的，需求是收敛的。

**根治方案：需求状态机**
- 不存对话历史，存**结构化的需求状态**
- 项目级：整体在做什么？
- 功能级：功能清单是什么（树状结构）？
- 焦点级：当前在讨论/修改什么？
- 每次输入更新状态，而非追加对话

### 问题二：没有设计直接编码

**现象**：需求？？？？？代码出来了（设计在哪里？）

**根因**：跳过设计阶段，不知道架构、模块关系、数据流动。

**根治方案：强制设计层**
- 在生成代码前，必须经过设计层
- 自动生成设计稿：功能边界、数据结构、接口定义、依赖关系
- 用户只需确认，不需要自己画
- 确认后再生成代码

### 问题三：代码生成后无法追溯

**现象**：一个月后看代码，不知道为什么这样写、能不能改、改了影响什么？

**根因**：代码与需求脱钩。

**根治方案：代码需求双向绑定**
- 每段代码带溯源元信息
- 记录：来自哪个需求、哪个设计决策、为什么这样写
- 记录：依赖哪些代码、被哪些代码依赖

### 问题四：改了A坏了B

**现象**：用户改个按钮颜色，结果登录功能挂了。

**根因**：没有影响范围分析。

**根治方案：变更影响分析系统**
- 执行变更前，先分析影响
- 展示：直接影响的文件/元素、间接影响的功能、风险评级
- 提供回滚方案

### 问题五：技术债无形积累

**现象**：每次都"能跑就行"，代码越来越乱。

**根因**：只管当前功能，不管代码质量。

**根治方案：技术债可视化 + 主动重构建议**
- 持续监控：重复代码、复杂度、架构违规、过时模块
- 在合适时机提醒用户重构
- 不每次都提醒，找空档时机

### 问题六：用户不知道自己不知道什么？

**现象**：用户说"做个登录"，不知道要考虑密码强度、失败锁定、多因素认证...

**根因**：领域知识缺失，系统不引导就全漏了。

**根治方案：领域知识主动引导？**
- 建立领域知识库
- 用户提到某领域概念时，主动展示相关考量
- 渐进式引导：先展示关键的，确认后再展示可选的

### 总览？

| 核心问题 | 根本原因 | 根治方案 |
|----------|----------|----------|
| 需求蒸发 | 对话≠需求 | 需求状态机 |
| 跳过设计 | 直接生成代码 | 强制设计评审 |
| 无法追溯 | 代码与需求脱节 | 双向绑定 |
| 改A害B | 无影响分析 | 影响分析系统 |
| 技术栈 | 只管能跑 | 债务监控+重构建议 |
| 盲区漏需 | 用户不知情 | 领域知识引导 |

### 本质

**在自然语言交互的外表下，偷偷建立工程化的内核的？**

用户感受到的只是随便说说，系统在做的是严格工程"

## 8. 以人为本的交互设计

### 核心认知

人类与系统交互的本质？

```
👁️眼睛，获取信息（输入）
🖐️手操作，发出指令（输出）—🤐未来用嘴
👁️眼确认，验证结果（反馈）
```

系统设计围绕这三点：让人**看得到、看得明白、操作简单、还喜欢**？

### 维度一：看得到

一切操作都要有可视反馈，不能有"空白时刻"！

| 用户动作 | 系统反馈 |
|----------|----------|
| 说了一句话 | 显示气泡，表"示"我听到了" |
| 系统在理"解" | 显示"正在理解..."状"态" |
| 理解完成 | 高亮显示识别出的关键"词" |
| 开始生"成" | 骨架屏渐进显"示" |
| 生成完成 | 新内容有入场动画 |
| 发生变化 | 变化部分闪烁/高亮 |

**始终可见的状态栏**：用户任何时候看屏幕，都知道现在是什么状态！

### 维度二：看得明白

**用用户的语言，不用系统的语言**

```
"系统语言"：创建 UserModel 实例，配"置" bcrypt 加密算法"
"用户语言"：建立用户数据存储，密码会安全加密保存"
                [展开详情] "想看技术细节再"看看
```

**复杂信息分层展示**
- 第一眼（0.5秒）：知道大概是什"么"？
- 第二眼（2秒）：知道包含什"么"？
- 第三眼（需要时）：知道细节

**用对比让变化显而易"见"**：修改前/修改后并排展示，明确标注改了什么？

### 维度三：操作简"单"？

**最常用的操作，最少的动作**

| 操作频率 | 操作方式 |
|----------|----------|
| 高频（每分钟"一次" | 单击/单词语音 |
| 中频（每小时"一次" | 右键菜单/短句语音 |
| 低频（每天） | 顶部菜单/完整对话 |
| 罕见（偶尔） | 设置面板 |

**设计原则**：
- 智能预判，减少操作（推荐下一步）
- 就近操作，不要跳转（原地弹出小面板）
- 语音和点击协同（点击选中 + 语音指令？）

### 维度四：确认结果

**即时反馈，所见即所得**？

用户说话的同时，预览区实时变化。说完即完成，不需要等待！

**给用户后悔的权利**

始终可撤销，用户才敢大胆尝试！

**正向确认，给用户信心**

完成后展示：做了什么、包含哪些、下一步可以做什么？

### 维度五：喜欢（情感设计）

用户喜欢用，来自情感体验感？

| 情感 | 来源 |
|------|------|
| 成就感？| 说了一句话，出来这么好的东西？|
| 掌控感？| 我能控制它，它听我的 |
| 安全感？| 不怕出错，随时可以回退 |
| 惊喜感？| 它居然想到了我没想到？|
| 流畅感？| 整个过程没有卡顿、没有打错？|

**设计原则**：
- 让用户感受到"系统懂我"
- 适度的小惊喜（完成时的仪式感？）
- 温柔的错误处理（不是冷冰冰的 Error 提示？）

### 人本设计检查表

| 维度 | 核心问题 | 设计目标 |
|------|----------|----------|
| 看得清？| 系统在干什么？ | 一切操作有反馈，没有空白状态？|
| 看得明白 | 这是什么意思？ | 用人话，分层展示，对比变化？|
| 操作简单？| 怎么才能完成？| 最少动作，智能预判，就近操作？|
| 确认结果 | 对不对？ | 即时反馈，可撤销，正向确认？|
| 喜欢 | 想不想用？| 懂我、小惊喜、有温度 |

### 本质

## 12. 落地保障机制

```typescript
async function validateAIOutput(output: any, schema: Schema): ValidationResult {

    return { valid: false, errors, needsRegeneration: true };

}
```

```typescript
interface UsabilityCheck {
  // 生成的设计是否可预览
  previewable: boolean;
  
  // 生成的代码是否可运行
  runnable: boolean;

function ensureUsability(output: AIOutput): UsabilityCheck {

    runnable: canRun(output.code),

    editable: output.editPoints.length > 0,
    reversible: snapshotCreated()

}
```

```typescript
  private renderer: UIRenderer;

  async processStream(stream: AsyncIterable<string>) {
    for await (const chunk of stream) {
      this.buffer += chunk;
      
      // 尝试解析并渲染
      const parsed = this.tryParse(this.buffer);
      if (parsed.renderable) {
        await this.renderer.update(parsed.content);
      }
    }
  }
  
  // 增量解析，尽早显示
  private tryParse(buffer: string): ParseResult {
    // 即使不完整也尝试渲染部分内容
    return incrementalParse(buffer);
  }
}
```

### 总导演的约束机制

**核心问题**：谁来监督监督者？如何确保总导演优秀履行职责？

#### 约束原则：制度约束 + 透明执行 + 事后审计

```
┌─────────────────────────────────────────────────────────────────┐
│                  总导演约束体系                                 │
│             Director Constraint System                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                │
│ 【制度约束 / Institutional Constraints】                       │
│   · 流程剧本不可篡改 — 总导演只能按剧本执行，不能改剧本          │
│   · 必经关卡不可跳过 — 守卫员检查是硬编码的，总导演无权绕过     │
│   · 权限边界硬隔离 — 总导演只能协调，不能直接操作数据            │
│                                                                │
│ 【透明执行 / Transparent Execution】                           │
│   · 每个决策都记录 — 为什么走这条路、为什么调用这个角色         │
│   · 执行轨迹可追溯 — 完整的执行日志，任何人可审查               │
· 状态实时可见——用户和系统都能看到当前在哪个节点

【事后审计/ Post-Audit】
· 监工独立监控 ——监工不受总导演指挥，直接观察执行状态
· 异常自动上报 ——流程异常时自动记录，供事后分析
· 用户最终裁决——用户可以否决任何结果，要求重做

└─────────────────────────────────────────────────────────────────
```

#### 约束一：流程剧本不可篡改(Immutable Playbook)

总导演只是剧本的执行者，不是编写者：

```pascal
// 流程剧本 —设计时固化，运行时只读
type
  T流程剧本 = class
  private
    F节点列表: TArray<T流程节点>;  // 设计时定义，运行时不可修改。
    F转换规则: TArray<T状态转换>;
  public
    // 总导演只能查询，不能修改
    function 获取当前节点(const 状态 T流程状态): T流程节点;
    function 获取下一节点(const 状态 T流程状态, const 事件: T事件): T流程节点;
    // 没有任何Set方法。
  end;
```

**关键**：流程定义是**编译时常量**，不是运行时变量。

#### 约束二：必经关卡不可跳过 (Mandatory Checkpoints)

守卫员检查是硬编码在流程中的，总导演无权决定是否执行：


```
└─────────────────────────────────────────────────────────────────顺
```

**传统工具思维** vs **"懂我"思维**顺

| 传统工具思维 | “懂我”思维 |
|----------------|------------|
| 用户来是为了完成任务 | 用户来是为了被理解顺|
| 成功 = 任务完成 | 成功 = 用户舒服 |
| 效率第一 | 共鸣第一 |
| 流程要闭环顺| 情绪要闭环顺|
| 用户中断 = 失败 | 用户中断 = 需要休息顺|

### 原则一：容忍中断，保证可恢复顺(Tolerate Interruption)

人类会半途而废，这不是缺点，是人性。系统要适应人，不是人适应系统顺

```
传统思维模式                         人性化思维模式
────────────────────────────────────────────────────────
开步问号必须完成 问号结束            开步问号可以暂停 问号随时回来 问号继续
      流                                  任
     用户走了 = 失败                    用户走了 = 保存草稿，下次见
```

**具体策略**示例

| 用户行为 | 传统处理 | 人性化处理 |
|----------|----------|------------|
| 生成到一半不想要了| 强制完成或放弃| “我先保存着，您随时回来续|
 | 确认等待超时 | 错误/失败 | "已保存为草稿，下次打开继续了|
用户忘了这件事| 资源浪费 | "您上次做到了这步..呢|
| 反复修改 | 禁止或限制？| "慢慢来，我都记着呢？|

**超时处理示例**：

```pascal
procedure T总导览等待用户确认(const 内容: T内容);
begin
  case 等待响应(超时30秒) of
    用户确认: 
      应用变更(内容);
    用户调整: 
      返回调整流程;
    超时:  // 用户走了，没关系
      begin
         保存为草稿内容);
         显示提示('已保存，您可以随时回来继续😊');
         会话状态:= 暂停;
      end;
  end;
end;
```

### 原则二：懂我优先，结果其次(Understanding First, Results Second)

用户要的不是"你帮我做了什么"，而是"你懂了我要什么"啊？

```
                    用户的真实需求层次？

                         被理解
                             清晰
                          ┏┻┓
                           最小值 中位数 最大值最渴望的："你懂我呗
                           ┗┳━
                           ┌┼─
                          │  │  ← 其次：“你在乎我”
                          └┬┘
                         ┌──┼──┐
                         │   │ │然后："你能帮我吗"
                        └──┬──┘
                       ┌────┼────？
                      │      │  ← 最后：“拿到结果”
                       └─────────┘
```

**「懂我」的三个层次**

| 层次 | 表现 | 系统实现 |
|------|------|----------|
| **听懂你** | 准确复述用户意图 | "我理解您想..." |
| **记住你** | 用户不用重复 | "您之前说过..." |
| **理解你** | 知道用户没说的部分 | "您可能还需要..." |

**具体策略**

#### 1. 先共鸣，再做方案。

```
差体验：
用户说："我想做个简单的网站"
系统：[直接开始生成代码...]

好体验：
用户说："我想做个简单的网站"
系统："简单的网站，让人感觉清爽不累对吧？您是想展示什么呢？"
        [个人作品集] [公司介绍] [卖东西] [先随便看看]
```

#### 2. 允许发泪，不急着解决

```
用户说："这个功能太复杂了，我不知道怎么处理"

差体验：
系统说："我来帮您做，第一步骤..." 急着解决问题

好体验：
系统说："复杂的功能确实让人头疼。您先告诉我哪里卡住了？"
        或者我们慢慢来，一点一点拆开看？" 先共情，再解决。
```

#### 3. 记住用户的偏好，不要每次都问

```pascal
// 记忆官不只记事实，也记偏好。
type
  T用户偏好 = record
喜欢的风格: string;       // "简约"
常用的配色: string;       // "蓝白"

    工作时段: string;         // "晚上"

  end;

// 用户第五次说"简单点"，系统应该记住了
记忆模块:学习偏好('简单点', +1);
// 下次默认就用简约风格
```

#### 4. 感知用户情绪，调整交互方式

```
情绪信号                          系统调整
────────────────────────────────────────────────────
输入很短、有错别字      短语    用户可能着急，别追问太多。
夜里还在聊               夜聊    用户可能很累，简化流程。
连续删除重来              重做    用户可能不满意，主动问问原因。
长时间没操作              等待    用户可能在想，别打断
```

```pascal
Result.标记('可能着急');
```

### 原则三：软硬关卡分层 (Soft/Hard Checkpoint Layers)

不是所有关卡都要强制，区分"底线"和"锦上添花"的差别。

| 关卡类型 | 能否跳过 | 跳过后果 | 示例 |
|----------|----------|----------|------|
| **硬关卡** | 绝对不可 | - | 安全检查、Schema验证 |
| **软关卡** | 可跳过 | 记录风险、后续提醒 | 预览确认、影响分析 |

```pascal
// 软关卡：允许跳过，但温柔提醒
procedure T总导航.预览确认(const 内容: T内容);
begin
  显示预览(内容);
  
  case 等待用户响应 of
    确认: 
      继续流程;
    跳过: 
      begin
        记录日志('用户跳过预览');
添加后续提醒('您跳过了预览，如果有问题随时说');
        继续流程;  // 允许跳过
      end;
  end;
end;

// 硬关卡：绝对不能跳过
procedure T总引导.守卫检查(const 内容: T内容);
begin
  // 没有跳过选项，代码结构强制执行
  守卫结果 := 守卫员.验证(内容);
  if not 守卫结果.通过 then
    raise E质量不达标.Create(守卫结果.原因);
end;
```

### 原则四：温度表达，不要冰凉 (Warm Expression)

同样的信息，不同的表达，感受完全不同。

| 场景 | 冰冷表达 │ | 温暖表达 │ |
|------|-------------|-------------|
| 等待 | "请稍等.." | "正在为您准备..." |
| 错误 | "Error: Invalid input" | "我没太理解，您是..? |
| 完成 | "操作完成" | "搞定吧.." |
| 中断 | "Session timeout" | "我先保存着，您随时回来 😊" |
| 失败 | "操作失败" | "没成功，要不试试别的方式？" |
| 重复 | "您已说过该内容" | "您说的跟之前那个有点像，是想调整还是新做一个？" |

### 原则五：情绪闭环，不只是任务闭环 (Emotional Closure)

任务完成不等于用户满意。要让用户的情绪也"闭环"。

```
任务闭环│                         情绪闭环│
───────────────────────────────────────────────────────
开始 → 执行 → 完成              困惑 → 被理解 → 有进展 → 成就感
                                      │        │       │
                                   认同情绪   小步前进   庆祝时刻
```

**具体实现**：

```
1. 认同困惑
   用户："这个好难啊"
   系统："确实有点绕，我们一起拆开看看"

2. 小步前进
   系统："这部分完成了 ✔，接下来简单了..."

3. 庆祝时刻
    系统真太棒了！整个功能都做完了 🎉"
```

```

│                  人性化设计五原则                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                │
│ 1. 容忍中断   —用户随时可走，系统自动保存                       │
│    Tolerate Interruption                                       │
│                                                                │
│ 2. 懂我优先   —先共鸣再做事，记住偏好                           │

│                                                                │
│ 3. 软硬分层   —底线不退，锦上添花可有                           │
│    Soft/Hard Layers                                            │
│                                                                │
│ 4. 温度表达   —同样的信息，温暖的语言                          │
```

**不变的底线**
- 安全 —绝对不妥协
- 可恢复 —绝对保证

**可灵活的部分**
- 流程 —可中断
- 确认 —可超时
- 预览 —可跳过
- 节奏 —可调整

## 16. 所说即所见的核心设计

> 四仙论道：盘古、灵子、鲁班、轩辕

### 核心问题

```
用户觉得简单 + 所说即所意 + 系统能抽取结构化数据
```

这三者看似矛盾，实则是系统成败的关键。

### 灵子（用户体验）的观点

用户要的"简单"，是**心理上的简单***，不是功能上的简单。

```
用户说："我要做个简单的登录页面"

复
  系统：请选择认证方式、数据库类型、密码加密算法？..
  
简
  系统：好的，登录页面。这样可以吗？
  [直接显示一个登录页面的样子]
  用户：嗯，但是要蓝色,
  系统：[页面变成蓝色]
```

**核心洞察**：
> **用户不是来做选择题的，是来看结果的。**
> 
> 让用户挑毛病比让用户"出主意"容易100倍。

### 鲁班（技术实现）的观察

要实现所说即所得，需要在后台做大量结构化工作。关键是**什么时候做、怎么做，用户不知道**。

```
用户看到的                       系统在做
─────────────────────────────────────────────────────────────
"做个登录页面"                系统识别意图：创建页面
                               系统识别类型：登录页
                               系统调用模板：login_page
                               系统填充默认值：标准配色、标准布局
                              
[看到一个登录页面]            系统渲染预览
                              
"蓝色！"                      系统解析：修改配色
                               系统定位：主题色
                               系统值：blue
                               系统更新状态
                              
[页面变蓝]                    系统重新渲染
```

**核心洞察**：
> **用户只管说，系统偷偷翻译成结构化数据。**
> 
> 这个"翻译"过程要快到用户感觉不到。

### 仙儿（界面表现）的观察

"所说即所得"的关键是**即时反馈**。用户说完话后0.5秒内必须有响应吗

```
时间线：
───────────────────────────────────────────────────────
0ms     用户说完"蓝色登录页"
100ms   系统显示"正在变蓝..."（哪怕还没真的变蓝）
300ms   页面开始变色（渐变动画中）
500ms   变色完成
1000ms  系统显示"这是蓝色的登录页，还要调整什么？"
```

**核心洞察**点:
> **宁可先展现"即时反馈，也不能让用户等"真的"结果。
> 
> 人对时间的感知是主观的，有反馈就不觉得慢。

**未来优化（待AI API速度提升后）:**

仙儿提出了一个更激进的想法—"边听边做"，即用户还在说话时就开始渲染。但由于当前AI API速度限制，暂不实现，作为未来优化方向记录。

```

用户正在输入'做个登录...'
0.1秒：系统已经猜到可能是"登录页面"
       [立刻展示一个模糊的页面轮廓]

0.3秒：[轮廓变成登录页面的样子]

1秒：用户说完
     [完整的蓝色登录页面已经显示]
```

#### 温柔纠错机制

当AI理解错误时，不要让用户觉得是系统的错，而是给选项让用户轻松纠正：

```
场景：AI理解错了

✗ 差体验：
用户说"变蓝色"
系统：[把文字变成蓝色]  ✗ 理解错了
用户：不是这个意思！😠

✓ 好体验：
用户说"变蓝色"
系统：[把整个页面变成蓝色主题]
      "把主题色改成蓝色了，是这个意思吗？"
      [是] [不是，我要改文字颜色] [不是，我想……]
```

```pascal
// 每次理解都带置信度
type
  T理解结果 = record
    意图: string;
    置信度: Double;  // 0-1
    备选理解: TArray<string>;  // 其他可能的理解
  end;

// 置信度低时，主动确认
procedure T总导览.处理用户输入(const 输入: string);
var
  理解: T理解结果;
begin
  理解 := AI代理.理解意图(输入);
  
  if 理解.置信度 < 0.8 then
    // 不确定时，先做最可能的，同时展示备选
    执行并展示备选(理解)
  else
    // 确定时，直接执行
    执行(理解);
end;
```

#### 核心本质

> **用户只管"说人话"，系统在背后"做翻译"。"
> 
> 用户看到的是魔法，系统做的是工程。
> 
> 翻译的结果就是结构化数据——用户不需要知道它存在。

> 四仙论道。

#### 问题：用户改变主意时怎么办？

```
用户说"做个登录页面"

系统：[变蓝]
```

#### 解决方案：草稿箱机制

**1. 草稿保留策略**

| 策略 | 说明 |
|--------|------|
| **默认保留** | 推翻时自动存为草稿，不丢失 |
| **用户主动删除** | 用户说"把那个删掉"才删除 |
| **超时自动清理** | 默认1个月无交互则清理（可配置） |

```

      [替换成商品列表]      ◆ 这个项目只做商品列表
```

```
用户说"还是做登录吧"
```

```pascal
    ID: string;
    标题: string;           // "登录问题"
    摘要: string;           // "蓝色+微信登录"
    创建时间: TDateTime;
    最后修改时间: TDateTime;
    需求状态: T需求状态;   // 完整的结构化数据
    对话历史: TArray<T消息>;  // 可选，保留对话上下文
  end;

  T草稿箱 = class
    草稿列表: TArray<T草稿>;
    超时天数: Integer = 30;  // 默认1个月
    
    procedure 保存草稿(const 草稿: T草稿);
    procedure 删除草稿(const ID: string);
    function 恢复草稿(const ID: string): T需求状态;
    procedure 清理过期草稿;  // 定期执行
  end;
```

#### 设计原则

> **不丢弃用户的任何努力，哪怕他自己"算了"?**
> 
> 用户的"算了"可能只是一时的想法，系统要帮他留后路。

## 17. 核心目标与质量监督

### 核心目标

```
核心目标三角形

            自然表达
概览
             / \
            /   \
可靠转换
          /       \
          ▼─────────◆
      可用结果    用户掌控
```

- **自然表达**：随便说、随便指、随便画
- **可用结果**：能看、能用、可用
- **用户掌控**：知道系统在干什么、可确认、可控制
- **可靠转换**：在“自然”和“精确”之间建立可靠的桥梁

### 质量监督三方模型

交互过程中的质量由三方协同监督：

| 监督角色 | 负责什么 | 怎么负责 | 特点 |
|--------|----------|----------|------|
| **AI监督者** | 内容质量 | 自检Prompt，发现问题自我修复 | 柔性、智能、可能漏检 |
| **系统守卫** | 格式/安全 | 程序化验证，不通过则拒绝 | 硬性、可靠、不可绕过 |
| **用户裁判** | 最终满意度 | 确认界面，决定是否接受| 最终权威、不过度打扰 |

### 质量监督工作流程

```
用户输入
     粘贴
     复制
┌─────────────────────────┐
│  AI生成 + AI自检         │
│ ┌──────────────────┐   │
│ │ 自我检查完整性、正确性 │
│ │ 发现问题则自我修复   │
└────────────┬────────────┘
             │
              。
┌─────────────────────────┐
│ 系统守卫检查             │
错误Schema验证 失败不通过 重生门
错误代码验证 失败不通过 自动修复
安全检查项不通过 拒绝
└────────────┬─────────────
            ✓全部通过
            
┌─────────────────────────┐
│用户确认                 │
│展示AI理解（复述）       │
│展示生成结果（预览）     │
│用户决定：确认/调整/重来 │
└─────────────────────────┘
```

### 质量监督关键原则

1. **AI不信任自检**：AI生成后必须自检，不能盲目自信
2. **系统不信任AI**：即使AI说"我检查过了"，系统也要再验证。
3. **用户不需要懂技术**：质量问题在到达用户之前就应该被拦截
4. **宁可降级不可出错**：检查不通过时降级处理，而非展示错误结果
