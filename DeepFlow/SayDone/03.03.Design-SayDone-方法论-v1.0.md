# 方法论：需求到结构化数据

> 从DevDirector 自然语言交互系统设计中提炼的通用方法论
> 
> 核心目标：让用户"说人话"，系统懂意图，结果看得见

---

## 1. 核心公式

```
结构化抽取 = 领域识别 + 模板激活 + 增量修改 + 超模板AI补充
```

### 公式解读

| 步骤 | 做什么| 用户感知 |
|------|--------|---------|
| **领域识别** | 从用户输入识别这是什么类型的东西" | 无感 |
| **模板激活** | 加载该类型的默认结构和默认值| "系统好像懂我" |
| **增量修改** | 用户每句话映射到字段变更 | "说什么变什么" |
| **超模板补充**? | 模板没有的，AI推断+用户确认 | "它还想到了我没想到的" |

## 3. 领域模板设计（通用结构）

### 3.1 模板定义结构

```typescript
interface DomainTemplate {
  // 模板标识
  id: string;                    // "page.login", "api.crud", "table.user"
  domain: string;                // 所属领域 "ui", "api", "database", "workflow"
  type: string;                  // 具体类型: "login", "crud", "user"
  
  // 识别规则
  keywords: string[];            // 触发关键词 ["登录", "login", "sign in"]
  patterns: RegExp[];            // 正则模式
  
  // 结构定义
  schema: FieldDefinition[];     // 字段定义列表
  
  // 默认值
  defaults: Record<string, any>; // 90%用户会选的项
  
  // 约束规则
  constraints: Constraint[];     // 字段间约束关系
  
  // 关联模板
  related: string[];             // 可能一起用的模板
}

interface FieldDefinition {
  name: string;                  // 字段名
  type: FieldType;               // 类型: string, number, enum, object, array
  required: boolean;             // 是否必填
   default?: any;                 // 默认值
  options?: any[];               // 枚举选项
   description: string;           // 用于AI理解的内容
   mappingKeywords: string[];     // 什么词会触发修改这个字段
}
```

## 4. 字段映射机制

### 4.1 映射规则

用户说一句话，系统需要判断：

1. **操作类型**：添加(add) / 修改(modify) / 删除(remove) / 查询(query)
2. **目标字段**：改的是哪个字段
3. **目标值**：改成什么值

```typescript
interface MappingResult {
  operation: 'add' | 'modify' | 'remove' | 'query';
  field: string;
  value: any;
  confidence: number;  // 0-1
}

// 示例
用户说"蓝色"
返回{ operation: 'modify', field: 'theme', value: 'blue', confidence: 0.95 }

用户说"加个微信登录"
返回{ operation: 'add', field: 'authMethods', value: 'wechat', confidence: 0.92 }

用户说"不要忘记密码"
返回{ operation: 'remove', field: 'forgotPassword', value: false, confidence: 0.88 }
```

### 4.2 映射策略

| 策略 | 说明 | 示例 |
|------|------|------|
| **关键词直接匹配** | 字段有明确关键词 | "蓝色"→theme=blue |
| **同义词扩展** | 预置同义词表 | "简洁"="简单"="清爽"→style=minimal |
| **上下文推理** | 结合前文理解 | "把它变大"→根据上文确定它是什么|
| **AI补充** | 超出模板的，问AI | "要高大上"→AI推断具体配置 |

### 4.3 置信度处理

```
置信度≥0.9  →直接执行，无需确认
置信度0.7-0.9 →执行但展示备选："我理解为...，对吗？[是] [不是，我不确定..]"
置信度< 0.7  →展示选项让用户选："您是说..？[选项A] [选项B] [其他]"
```

## 5. 需求状态管理

### 5.1 状态结构

```typescript
interface RequirementState {
  // 基本信息
  id: string;
  templateId: string;           // 使用的模板
  
  // 三类字段
  确定的: Record<string, any>;  // 用户明确说过的
  默认的: Record<string, any>;  // 模板默认值（用户未改动的）
  删除的: string[];             // 用户明确表示"不要"的
  
  // 元信息
  completeness: number;         // 完整度(0-1)
  missingRequired: string[];    // 缺少的必填项
}
```

### 5.2 状态更新流程

```
用户输入
    →
领域识别 状态是否切换模板状态
     ---         ---
字段映射      新建状态保存旧状态为草稿
     ---
更新状态
     ---
检查完整度
     可以状态           不可以状态
可以生成/渲染    追问缺失状态
```

## 6. 交互设计原则

### 6.1 核心原则

| 原则 | 说明 | 实现 |
|------|------|------|
| **先猜后确认** | 给用户看结果，而非让用户描述| 立刻展示默认模板 |
| **即时反馈** | 0.5秒内必须有响应| 流式渲染、骨架屏 |
| **渐进显影** | 先出轮廓，再填细节| 分阶段渲染|
| **温柔纠错** | 理解错了提供选项，不让用户尴尬| 备选理解列表|
| **不丢弃努力** | 用户"算了"时自动保存草稿| 草稿箱机制|

### 6.2 反馈时机

| 时机 | 反馈内容 | 时限 |
|------|---------|------|
| 用户输入时| 关键词高亮| <100ms |
| 意图理解完成 | "我理解您想要..." | <500ms |
| 开始生成| 骨架屏出现| 即时 |
| 生成过程 | 流式填充内容 | 实时 |
| 生成完成 | 完成动画 + 下一步引导| <100ms |

## 7. 适用场景判断

### 7.1 适用的场景特点

- ✅领域可枚举 ✅能识别出"这是什么类型的东西"
- ✅有模板可套 ✅该类型有标准化的结构/套路
- ✅增量可映射 ✅用户的每句话能对应到具体字段变更
- ✅默认值合适 ✅90%用户的选择是相似的

### 7.2 适用场景列表

| 场景 | 领域识别 | 模板化程度 | 增量映射 |
|------|----------|-----------|---------|
| UI/页面设计 | ✅页面类型有限 | 适中 | ✅容易 |
| API设计 | ✅CRUD模式 | 适中 | ✅容易 |
| 数据库设计 | ✅实体类型 | 中高 | ✅容易 |
| 工作流设计 | ✅流程类型 | 适中 | ✅中等 |
| 报表设计 | ✅报表类型 | 适中 | ✅容易 |
| 测试用例 | ✅测试类型 | 适中 | ✅容易 |
| 配置管理 | ✅配置类型 | 适中 | ✅容易 |
| 文档生成 | ✅文档类型 | 适中 | ⚠️ 中等 |
| 智能表单 | ✅字段类型 | 适中 | ✅容易 |

### 7.3 不太适用的场景

| 场景 | 原因 |
|------|------|
| 创意写作 | "纯模板"，内容完全开放 |
| 自由绘画 | 结构化程度低 |
| 策略决策 | 需要推理而非模板匹配 |
| 复杂算法 | 逻辑难以模板匹配 |

## 8. 实现路径

### 8.1 最小可行版本(MVP)

1. **选一个垂直领域**（如：UI页面设计）
2. **5-10个核心模板**（登录/注册/列表/详情/表单等）
3. **实现基础映射**（颜色/布局/组件增删改）
4. **简单的即时渲染**（静态预览）

### 8.2 逐步扩展

```
MVP (1个领域)
    ↓
多领用(UI + API + DB)
错误
领域联动 (设计API自动影响DB)
错误
AI增强 (超模板能力)
    功能
学习系统 (用户偏好)
```

## 10. 连接器层（效用最大化）

> **结构化数据本身不产生价值，连接到行动才产生价值**

### 10.1 数据的五种效用出口

| 出口类型 | 说明 | 示例 |
|----------|------|------|
| **生成** | 数据→代码/文档/配置 | 登录页结构→React代码 |
| **调用** | 数据→API/服务 | 请假结构→OA系统API |
| **存储** | 数据→数据库/知识库| 客户信息→CRM |
| **展示** | 数据→可视化/报表 | 销售数据→Dashboard |
| **流转** | 数据→下一个系统→| 需求结构→Jira工单 |

### 10.2 连接器架构

```
用户说话 →  结构化数据 →  连接器层 → 实际效用
                        完成
         ┌───────────────┼────────────────说明
         名称              类型               描述
         组件            接口               功能
   [代码生成器]    [API调用器]    [存储适配器]
   [可视化器]      [工作流引擎]   [导出器]
         代码              工单               数据
         代码             工单               数据
     React           Jira           MySQL
      代码             工单           数据
```

### 10.3 连接器接口定义

```typescript
interface StructuredOutput {
  // 元信息结构
  domain: string;        // "meeting", "leave", "page.login"
  templateId: string;    // 用了哪个模板
  confidence: number;    // 置信度
  
  // 数据本体
  data: Record<string, any>;
  
  // 声明支持的输出
  supportedOutputs: OutputType[];
}

type OutputType = 
  | 'code'        // 可生成代码
  | 'api'         // 可调用API  
  | 'storage'     // 可存储
  | 'visual'      // 可可视化
  | 'export'      // 可导出(JSON/CSV/PDF)
  | 'workflow';   // 可触发工作流

interface Connector {
  id: string;
  name: string;
  supportedDomains: string[];   // 支持哪些领域
  outputType: OutputType;
  
  // 执行连接
  execute(data: StructuredOutput): Promise<ConnectorResult>;
}

interface ConnectorResult {
  success: boolean;
  output: any;           // 生成的代码、返回的结果
  error?: string;
  nextActions?: string[];  // 建议的下一步操作
}
```

### 10.4 三层效用策略

| 层级 | 策略 | 成本 | 覆盖率|
|------|--------|------|--------|
| **Layer 1** | 即时可用 ?导出JSON/Markdown/复制到剪贴板 | 0 | 100% |
| **Layer 2** | 领域适配 ?每个领域2-3个推荐输出| ?| 80% |
| **Layer 3** | 深度集成 ?定制连接器对接用户系统| ?| 20% |

| 领域 | 首选输出 | 次选输出 |

### 11.2 GUI模板编辑器（元方法论。）

用这套方法论来配置方法论本身吗？

```
用户：帮我建个模板，用来做菜谱"
系统：好的，菜谱通常包括：[食材] [步骤] [时间] [难度]，还要加什么？"
用户：加个口味，比如麻辣、清单
系统：[自动识别为枚举类型，填充选项]
系统模板创建完成！触发词：'做菜''食谱''菜谱'可以吗？"
```

### 11.3 AI渲染器（分级策略）

| Level | 策略 | 速度 | 可靠 | 适用场景 |
|-------|--------|------|--------|----------|
| **1** | 模板渲染 | 最快 | 最准 | 标准化场景 |
| **2** | 规则渲染 | 最快 | 最快 | 结构固定内容变化 |
| **3** | AI渲染 | 慢 | 慢 | 特殊需求 |
| **4** | AI+人工 | 最快 | 最灵活 | 高价值低频场景 |

> **底线原则：能用模板就用模板，模板不够才用AI。AI生成的必须经过验证。**

## 12. 核心洞察

> **凡是"有套路"的工作，都可以用这套方法论。**

> **让用户挑毛病比让用户出主意容易100倍。**

> **系统的智能不在于"猜得准"，而在于"猜错了能优雅地让用户纠正"。**
