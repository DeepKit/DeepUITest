# DeepFlow 落地实施策略与避坑指南

> **版本**: 1.0 | **更新日期**: 2025-12-04
> **定位**: 本文档作为《MVP 定义与实现指南》的补充，专注于"怎么做才不翻车"，提供工程化落地的实战建议。

## 1. 核心实施策略：曳光弹开局(Tracer Bullet)

不要试图一次性构建完美的 11 角色系统。应采用**曳光弹**策略，优先打通一条"从用户输入到AI 执行再返回"的全链路。

### 1.1 推荐的开发顺序

1.  **Phase 0: 连通性(The Bridge)**
    - 目标：Delphi 点击按钮 -> 调用本地 Python FastAPI -> Python 调用 LiteLLM -> 返回 "Hello World"。
    - 关键点：解决 Python 环境打包、端口管理、进程保活。不要涉及任何业务逻辑。

2.  **Phase 1: 线性硬编码 (Hardcoded Chain)**
    - 目标：实现一个写死在代码里的 Workflow（如：输入->意图识别->执行天气查询->输出）？
    - 关键点：验证 Commander -> Dispatcher -> Skill 的接口契约。此阶段**不要**使用 YAML 解析器，直接使用 Delphi 代码构建对象树？

3.  **Phase 2: 状态持久化 (The Memory)**
    - 目标：在 Phase 1 的基础上，每一步执行完都能存入 SQLite，且重启 App 后能从中断点继续？
    - 关键点：设计 `TWorkflowInstance` 以及 `TStepCursor` 表结构？

4.  **Phase 3: 动态化 (The Engine)**
    - 目标：引入 YAML/JSON 定义文件，替代 Phase 1 的硬编码？
    - 关键点：此时才需要写 Parser？

## 2. 避坑指南：常见的工程陷阱

### 2.1 陷阱一：过度设计 Workflow 引擎

**现象**：试图实现一个兼容 BPMN 2.0、支持复杂网状拓扑、回退、分支预测的通用引擎？
**后果**：开发周期由 2 周拖延 2 个月，Bug 频出。
**对策**：
- **MVP 原则**：只实现**有向无环图(DAG)**，甚至只实现**线性链路。**
- **状态机简化。**
  - 不要把状态逻辑分散在各 Node 里。
  - 维护一个全局的 `CurrentStepId` 指针即可。
  - 复杂的循环分支逻辑，尽量通过"子 Workflow"或"Python 侧逻辑"规避，保持 Core 引擎愚蠢而健壮。

### 2.2 陷阱二：JSON 处理的性能与类型地狱

**现象**：在 Delphi 中手动拼接 JSON 字符串，或者使用性能极差的 Variant 转换。
**后果**：代码极其脆弱，特殊字符导致 Crash，内存泄漏。
**对策**：
- 严禁手动拼接 string。
- 统一使用 `System.JSON` 或 `SuperObject`。
- 定义明确的**DTO (Data Transfer Object)** 记录(Record)，并编写自动化的 `Record <-> JSON` 转换助手函数。

### 2.3 陷阱三：Python 环境依赖地狱

**现象**：依赖用户系统安装的 Python，版本不兼容，缺少 pip 包。
**后果**：在开发机上能跑，发给测试/用户直接报错。
**对策**：
- **Embeddable Python**: 必须把Python 嵌入式包随应用分发。
- **Vendor Dependencies**: 将所有依赖包（`site-packages`）打包在 `bin/python/Lib` 下，不要依赖 `pip install`。
- **相对路径**: 所有调用都基于 `ExtractFilePath(ParamStr(0))` 动态计算，严禁硬编码`C:\Python`。

### 2.4 陷阱四：IPC 通讯卡顿

**现象**：UI 界面在等待 AI 响应时假死。
**后果**：用户体验极差。
**对策**：
- **异步到底**: Delphi 侧所有HTTP 请求必须在独立线程（`TTask.Run`）中执行。
- **UI 响应**: 主线程只负责显示"正在思考".."动画，通过 `TThread.Queue` 更新 UI。
- **超时控制**: 必须设置连接超时（如 2s）和读取超时（如 60s），避免永久挂起。

## 3. 关键技术模式 (Patterns)

### 3.1 状态机模式 (State Machine for Workflow)

不要用复杂的递归函数来执行Workflow。使用状态机循环。

```pascal
procedure TDispatcher.ExecuteLoop;
var
  Step: IWorkflowStep;
begin
  while FStatus = wsRunning do
  begin
    Step := GetStep(FCurrentStepId);
    try
      // 执行步骤
      ExecuteStep(Step);
      // 移动指针
      FCurrentStepId := Step.NextStepId;
       // 持久化
      SaveState;
    except
      on E: Exception do
      begin
        HandleError(E);
        Break; // 退出循环等待人工或重试
      end;
    end;
    
    // 响应中断
    if CheckPauseSignal then Break;
  end;
end;
```

### 3.2 混合开发调试模式

为了提高开发效率，建议支持 **"Mock Mode"**。

- **Config.json**: 增加 `"UseMockAI": true`
- **Mock 实现**: 当开启时，Advisor 不调用Python，而是直接返回预设的JSON 响应。
- **价值**: 为Delphi 开发者在不启用Python 服务的情况下，快速调用UI 到Workflow 逻辑。

## 4. 落地检查清单(Checklist)

- [ ] **Python 环境包**：是否已制作包含 FastAPI/LiteLLM 的独立zip 包？
- [ ] **接口定义**：Delphi 与 Record 结构体是否与 Python Pydantic 模型字段完全一致？
- [ ] **日志链路**：Python 与 `print` 输出能否被 Delphi 捕获并存入SQLite？
- [ ] **错误码？**：是否定义了统一的ErrorCode（如 `E_LLM_TIMEOUT`, `E_SKILL_NOT_FOUND`）？
- [ ] **配置分离**：API Key、BaseURL 是否提取到了配置文件，未硬编码？
- [ ] **Mock AI 模式**：`advisor.use_mock=true` 可跑通端到端流程，且不会产生外部 LLM 请求
- [ ] **消息版本控制**：`TRoleMessage.Version` 已实现并记录到日志审计
- [ ] **黄金数据源**：已定义至少 5 个黄金用例并纳入 CI
- [ ] **骨架项目**：最小骨架可编译运行（含 Echo Skill 示例与单测）
- [ ] **Python 服务管理**：启动健康检查自动重启链路正常
- [ ] **可观测性**：全链路 `traceId` 打通，关键指标可观测
