> 本文档源于五位AI角色（盘古架构师、灵狐产品经理、鲁班开发者、仙剑安全专家、李耳QA）的深度讨论，凝练了Skill 动态增强系统底座功能的核心认知。

## 第一部分：Skill 的本源

### 1.1 为什么需要Skill

DeepFlow 核心能力"流程编排"，不追求什么都会做"。读写数据库、调用API、处理文件，这些是专业能力，应该由专业组件提供支持"

**Skill 存在的三个根本原因？**

| 原因 | 说明 |
|------|------|
| 能力边界 | 核心专注编排，专业能力外包 |
| 演进速度 | 外部世界变化快，核心应该稳定 |
| 定制化| 每个企业需求不同，需要扩展机制|

### 1.2 Skill 是扩展机制

Skill 本质是"扩展机制"，而非"能力单元"。核心需求是

1. **隔离**：扩展出问题不影响核心
2. **标准化**：扩展有统一的接入方式
3. **可扩展**：能找到需要的扩展
4. **可信机制**：知道扩展是否可靠

**如果用其他方式能更好地满足这四个需求，可以不用"Skill"这个形式**。

### 1.3 能力是条件性的

Skill 不应该声明"能做 X"，而应该声明"在条件 Y 下，能做 X"。

**例子**：发送邮件 Skill
- 它只是调用了 SMTP 服务
- 如果 SMTP 服务挂了，它会"不能"。
- 如果邮件内容太大，它会"不能"。
- 如果收件人不存在，它会"不能"。

**条件 Y 包括**：
- 前置条件（输入满足什么）
- 环境条件（依赖服务可用）
- 资源条件（有足够资源）。

## 第二部分：Skill 生态分析

### 2.1 四层信任体系

| 层级 | 来源 | 信任级别 | 运行时隔离 | 能力天花板 |
|------|------|----------|------------|------------|
| Core Skills | 内置 | 完全信任 | 无隔离（原生执行）| 最高，可做系统级操作 |
| Official Extensions | 官方/认证伙伴 | 有限信任 | 进程隔离 | 中等，可访问用户数据和外部API |
| Community Skills | 社区 | 低信任 | 沙箱隔离（WASM/容器）| 较低，只能在沙箱内操作 |
| User Skills | 用户自建 | 最低信任 | 严格沙箱 + 网络隔离 | 最低，几乎只能做纯计算 |

### 2.2 分层信任原则

即使 Skill 声明需要更高权限，如果它的信任等级不够，也会被拒绝或降级。

**信任不是"是"或"否"的二元选择，而是"多大程度"的连续光谱。**
- 对高可靠 Skill：高信任，低检查。
- 对新 Skill：低信任，高检验
- 对用户自定义 Skill：最低信任，最高检验

### 2.3 核心 vs 外围

**核心能力（应该内置）**：
- 流程编排本身（调度、分支、循环、异常处理）
- 与用户的交互（人工任务、通知、确认）
- AI 协调（智囊的调度、质量把控）
- 安全控制（权限、审计）

**外围能力（应该是 Skill）**：
- 特定数据源的读写
- 特定外部服务的调用
- 特定格式的处理
- 特定行业的业务逻辑

**判断标准**：
- 如果没有这个能力，DeepFlow 还是 DeepFlow 吗？是核心
- 如果这个能力只有部分用户需要，才是 Skill
- 如果这个能力变化很快，才是 Skill
- 如果这个能力有多种实现选择，才是 Skill

## 第三部分：Skill 对用户不可见

### 3.1 产品悖论

我们想要丰富的 Skill 生态，用户想要简单的解决方案

**Skill 多了反而可能是负担**：
- 选择困难：哪个 Skill 适合我？
- 质量参差：哪个 Skill 可靠？
- 学习成本：每个 Skill 怎么用？

### 3.2 解决思路

**用户只看'功能'，看不到"Skill**

系统自动选择合适的 Skill 来实现功能。Skill 是开发者的概念，不是用户的概念。

```
用户：每天把新订单发到邮箱。
系统：（内部选择 CronTrigger + DBQuery + EmailSend）
用户：（只看到任务完成了。）
```

### 3.3 智能路由。

```
用户意图 → AI 路由 → 选择 Skill → 执行 → 结果
```

路由层需要：
- 理解用户意图
- 知道每个 Skill 能做什么。
- 匹配意图与 Skill
- 处理多个 Skill 都能满足的情形

**注意**：Skill 增多，路由更复杂，需要更强的 AI 应对更多不确定性。这里复杂性转化，而非"复杂性消失"。

### 3.4 透明度 vs 简洁度

**平衡点：可选的透明度**

默认简洁，但用户可以查看详情：
- "高级视图"显示 Skill 选择和执行过程
- 重要操作时主动披露："我将使用 XX 能力来完成这个任务，继续吗？"

## 第四部分：Skill 抽象层次

### 4.1 四层抽象

```
用户层：业务动作如发送日报，
译
语义层：意图组合模块、查询数据 + 格式转换 + 发送邮件…
         …
执行层：Skill 调用（DBQuery + Template + Email）
         …
基础层：具体实现（SQL 执行 + 字符串处理 + SMTP 发送）
```

### 4.2 每层的复用含义

| 层级 | 复用含义 | 复用对象 |
|------|----------|--------|
| 业务用户 | 业务动作模板 | 业务用户 |
| 语义层 | 意图组合模式 | 高级用户/业务分析师 |
| 执行层 | Skill 组件 | 开发者 |
| 基础层 | 基础能力库 | 平台开发者 |

### 4.3 两层 Skill 体系

**底层：技术原理 Skill**
- HTTP 调用、数据库查询、文件操作…
- 给开发者用

**上层：业务语义 Skill**
- 发送钉钉消息、获取天气、创建 Jira 工单…
- 给业务用户用

上层 Skill 由底层 Skill 组合而成，但用户不需要知道。

## 第五部分：Skill 组合

### 5.1 组合的价值？

Skill 的价值在于封装（把复杂性藏起来），也在于组合（多个 Skill 组合成更强大的能力）？

### 5.2 组合的极限？

Skill 组合存在极限？

| 极限类型 | 原因 | 后果 |
|----------|------|------|
| 理解极限 | AI 理解复杂组合的能力有限？| 5 个 Skill 能理解，50 个可能理解偏颇？|
| 调试极限 | 组合越复杂，出错越难定位 | 复杂网络中的错误难以追踪 |
| 性能极限 | 每个 Skill 都有调用开销 | 100 个 Skill × 100ms = 10 秒？|
| 可靠性极限？| 串联越多，总体可靠性越低？| 10 个 99% 可靠的 Skill 串联 = 90% 可靠 |

**设计原则：追求能力密度，不追求数量。用最少的 Skill 完成任务？**

### 5.3 封装 vs 组合的矛盾？

封装越彻底，内部细节越隐藏，组合越困难。因为组合需要理解 Skill 内部状态、错误模式、资源需求？

**解法：引入"组合协议"？**

- Skill 接口层：简单的输入输出
- 组合协议层：批量处理策略、错误处理策略、资源协调？

组合不是直接调用 Skill 串起来，而是通过组合协议层协调？

### 5.4 AI 动态组合？

用户说："发消息到钉钉"

AI 需要：
1. 理解"钉钉"指的是哪个 API
2. 理解"发消息"指的是哪种消息？
3. 理解"到钉钉"指的是发给谁
 4. 找到合适的底层 Skill 并正确组合
 5. 填充所有必要参数

**每一步都可能出错***

**原则：AI 动态组合是"增强"，不要替代**

主流程还是靠预定义的业务 Skill。AI 动态组合处理长尾场景，但要有人工确认环节。

## 第六部分：Skill 组合安全

 ### 6.1 组合创造新攻击链

单个 Skill 安全不代表组合安全：

| Skill A | Skill B | A + B |
|---------|---------|-------|
| 读取用户数据（安全） | 发出HTTP 请求（安全） | 读取用户数据并发送出去（危险！） |

**这是"混淆代理攻击"与权限聚合攻击**

### 6.2 组合安全分析

**Workflow 保存***
- 计算"等效权限"（所有 Skill 权限的组合）
- 如果等效权限超过用户本身的权限，拒绝保存
- 数据流分析，检测敏感数据流。
- 高风险组合需要额外审核或警告

 ### 6.3 数据流追踪

。Workflow 层面做数据流分析。
- 标记敏感数据
 - 追踪敏感数据在各 Skill 之间的流转
- 检测敏感数据是否流向不安全的目的地

### 6.4 意图与行动的鸿沟

。AI 根据用户自然语言动态组合 Skill 时，用户实际上是在"编程"，但他们不知道自己在编程。

**风险**：
- 用户说了一句模糊的情况
- AI 理解成了高风险操作？
- Skill 组合执行了敏感操作？
- 用户事后说：我没让你这么做？

**安全对策**：

| 对策 | 说明 |
|------|------|
| 意图确认 | AI 组合后告诉用户："我理解你想做 X、Y、Z，对吗？" |
| 行动预览 | 执行前展示这个操作会做什么？ |
| 分级执行 | 低风险直接执行，高风险需要明确确认？|
| 行动可追溯？| 尽可能支持撤销，或至少完整记录 |

**根本原则：AI 不能单方面决定执行高风险操作**

## 第七部分：状态管理？

### 7.1 无状态理想？vs 有状态现实？

Skill 理想是无状态：每次调用独立，输入决定输出。

但现实需要状态：
- 认证令牌（需要保存和刷新。
- 分页游标（需要记住上次位置）
- 速率限制状态（需要记住调用频率）
- 事务状态（需要记住操作历史以便回滚）

### 7.2 状态管理层

**状态放在专门的状态管理层**，而非 Skill 内部。Workflow 引擎？

状态管理协议定义：
- 状态生命周期：会话级、用户级、全局。
- 状态存取接口：统一的读写方式？
- 状态持久化策略：何时保存、如何恢复？
- 状态隔离边界：Skill 间状态不互通？

### 7.3 状态安全？

**状态是攻击目标？**
- 认证令牌被窃取，身份冒充
- 事务状态被篡改，数据不一致？
- 速率限制状态被绕过，资源耗尽？

**状态隔离原则？**
1. Skill 只能访问自己创建的状态？
2. 共享通过显式接口、状态传递机制
3. 传递的是值，不是引用
4. 所有状态访问都记录

## 第八部分：设计时 vs 运行时？

### 8.1 设计时能力？

| 能力 | 说明 |
|------|------|
| Skill 发现 | 搜索、推荐、分类浏览？|
| 兼容性检查？| 依赖分析、冲突检查？|
| 安全审核 | 静态分析、权限验证？|
| 组合预览 | 可视化 Skill 编排 |
| AI 辅助配置 | 自然语言描述 可自动配置 |

### 8.2 运行时能力

| 能力 | 说明 |
|------|------|
| 热加载卸载 | 不重启系统更新 Skill |
| 沙箱隔离 | 限制 Skill 的能力边界 |
| 资源配额 | CPU、内存、网络限制 |
| 健康监控 | 实时检查 Skill 状态 |
| 动态降级 | 失败时自动切换备选方案 |

### 8.3 用户体验差异

| 阶段 | 用户体验 |
|------|----------|
| 设计阶段 | 显式浏览和选择，配置和参数化，组合安全分析 |
| 运行阶段 | 透明执行，用户无感知 Skill 边界，故障隔离和降级 |

### 8.4 智能默认 + 渐进披露

**智能默认**：
- 大多数配置有合理的默认值
- 根据上下文推断配置

**渐进披露**：
- 第一次使用：只问必要的几个问题
- 出问题时：再引导用户调整配置
- 高级用户：可以主动进入详细配置

**这不是隐藏复杂性，而是"适时暴露复杂性"**

## 第九部分：质量保证

### 9.1 分层测试

| 层级 | 目的 | 方法 |
|------|------|------|
| 基础层 | 实现正确 | 单元测试，高覆盖 |
| 执行层 | 接口兼容 | 契约测试 |
| 语义层 | 理解准确 | 意图识别测试 |
| 用户层 | 体验符合预期 | 端到端场景测试 |

### 9.2 组合测试策略

Skill 组合可能性是爆炸的（N 个 Skill 理论上有 N! 种组合），不可能穷举

**分层策略：**
1. 每个 Skill 测试：必须 100% 通过
2. 契约兼容性测试：对可能连接的 Skill 对测试
3. 常见组合模式测试：管道、并行、条件等模式
4. 真实 Workflow 回归测试：生产环境的真实 Workflow
5. 模糊测试：随机生成组合，测试是否崩溃

### 9.3 状态测试

有状态的系统比无状态的难测 100 倍

**策略：**
- 状态注入：测试时设置任意状态
- 状态观察：测试时查看当前状态
- 状态重置：测试后清理状态
- 状态抽象：测试状态类别之间的转换，而非具体状态值。

### 9.4 质量信号体系

建立透明的质量信号，让市场机制发挥作用：

| 信号类型 | 内容 |
|----------|------|
| 自动化指标 | 测试覆盖率、错误率、响应时间 |
| 社区信号 | 使用量、评分、评价 |
| 官方背书 | 审核状态、认证标准 |

### 9.5 质量分级

不同场景对质量要求不同：

| 等级 | 标准 | 适用场景 |
|------|------|----------|
| 企业级 | 严格标准，严格审核 | 金融、医疗等高风险场景 |
| 标准级 | 基本标准，基本审核 | 一般业务场景 |
| 实验级 | 最低标准，用户自担风险 | 个人自动化、测试 |

## 第十部分：Skill 生态

### 10.1 生态冷启动

**死循环**：用户少 →没人愿意开发 Skill → Skill 少 → 用户觉得平台没用

**解法**?
1. 官方先提供足够多的官方 Skill"覆盖主流场景
2. 选择性投资几个明星 Skill"开发者。
3. ?Skill 开发足够简单，降低门槛

### 10.2 开发者体验

**简化开发的方向**?

| 方向 | 说明 |
|------|------|
| 代码推导契约 | 从代码自动分析输入输出类型、权限使用|
| Skill 模板 | 常见场景下Skill 提供模板，填配置即可 |
| AI 辅助开发 | 自然语言描述即可生成 Skill 脚手架 |

**正确的演进路径：**
1. 内置 5-10 个核心Skill，代码实现
2. 发现它们的共同模式
3. 提取 Skill SDK
4. 用 SDK 重构已有 Skill
5. 开放 SDK 给第三方

**避免**：一开始就设计"完美的"Skill SDK"，然后发现设计有缺陷推翻重来

### 10.3 生态熵增

生态成熟后会发生：
- 大量相似 Skill
- 质量参差不齐
- 维护状态混乱
- 依赖关系复杂

**对策**：
1. 积极策展（Curation）：编辑推荐、官方精选
2. 淘汰机制：长期无维护、使用量极低质量Skill 降低曝光
3. 合并/替代建议：功能重叠时引导用户使用更好的
4. 健康度仪表盘：整个生态的健康状态可见

### 10.4 治理模式

**平台定规则，社区选精品*：**
- 平台负责底线（安全、稳定性）
- 社区负责上限（推荐、评价）

## 第十一部分：战略考量

### 11.1 产品 vs 平台

| 阶段 | 定位 | 重点 |
|------|------|------|
| 第一阶段（当下） | 产品 | 用户体验、端到端可控 |
| 第二阶段（验证后）| 开放平台| 开发者体验、API 稳定性|
| 第三阶段（成熟后）| 生态主导| 生态繁荣、平台治理|

**不要在第一阶段就按第三阶段设计**

### 11.2 DeepFlow 的核心价值

**担忧**：如果所有真正的"能力"都在 Skill 里，DeepFlow 本身剩下什么？

**回答**：DeepFlow 是"大脑"，不是"胶水"

调度谁都能做。但 DeepFlow 独特的是什么？
- AI 驱动的智能决策（什么时候该做什么）
- 人机协作的决策框架（什么事 AI 决定，什么事人决定）
- 还有 Skill 的状态管理和事务保证

**Skill 是手脚，DeepFlow 是大脑。Skill 越丰富，DeepFlow 越有价值**

### 11.3 用户分层

| 用户类型 | 占比 | 需求 | 不需要 |
|----------|------|------|--------|
| 简单用户| 80% | 可靠 Skill 执行 + 简单触发| AI 决策、复杂编排|
| 复杂用户 | 20% | 智能决策、动态适配、人机协作| - |

"大脑"能力是差异化，但不能是门槛的？

**策略：简单入口，深度可配置**

比如 80% 的用户用最简单的方式完成任务（甚至不暴露"Workflow"概念）
比如 20% 的用户能挖掘 DeepFlow 的全部能力

### 11.4 护城河

| 护城河| 说明 |
|--------|------|
| Skill 生态| 开发者和用户的网络效应|
| 数据飞轮 | 使用越多，AI 表现越好 |
| 行业深耕| 特定行业的专业知识和 Skill |

## 第十二部分：核心洞察

1. **Skill 是扩展机制，不是能力单元**——核心需求是隔离、标准化、可发现、可信任
2. **能力是条件性的**——条件往往隐含，需要显式声明
3. **Skill 应该对用户不可见**——用户看功能，系统看 Skill
4. **追求能力密度，不追求数量**——用最少的 Skill 完成任务
5. **组合创造新的攻击面**——需做 Workflow 级别的安全分析
6. **AI 动态组合是增强不是替代**——高风险操作必须人类确认
7. **状态管理是隐藏的复杂度***——需要专门的状态管理层
8. **先做对，再做抽象**——从具体 Skill 提炼 SDK，而非反过来
9. **DeepFlow 是大脑不是胶水**——核心价值是智能决策和协同
