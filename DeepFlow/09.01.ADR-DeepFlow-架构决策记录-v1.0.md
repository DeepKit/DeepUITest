# DeepFlow 架构决策记录 (ADR)

---

## 概述

本文档采用ADR (Architecture Decision Record) 格式，记录DeepFlow项目中做出的重要架构决策。每个决策包含：

- **状态**：提议| 已接受| 已废弃| 已取代
- **背景**：做出决策的上下文
- **决策**：选择的方案
- **理由**：为什么选择这个方案
- **后果**：决策带来的影响

## ADR-001：采用11 角色架构

### 状态
已接受（2025-12-03）

### 背景
设计 AI Agent 系统时，需要确定系统的模块化程度：
- 传统方案：单个Agent 处理所有职责
- 另一极端：细粒度微服务，每个功能独立
- 需要平衡：可维护性、性能、复杂度

### 决策
采用 11 角色设计，使用"军事指挥"隐喻组织职责

| 角色 | 职责 | 类比 |
|------|------|------|
| Engine | 角色生命周期 | 总参谋部 |
| Inspector | 调试监控 | 督察 |
| Commander | 请求入口 | 司令 |
| Dispatcher | 任务编排 | 参谋 |
| Executor | 任务执行 | 前线指挥官|
| Advisor | AI 推理 | 智囊团|
| Guard | 安全审核 | 宪兵 |
| Quartermaster | 资源管理 | 军需官|
| Logistics | 基础设施 | 后勤官|
| Chronicler | 日志审计 | 书记员|
| SignalOfficer | 外部通信 | 通信官|

### 理由

**为何不是更少（如 5 个角色）**？
- 职责不够清晰，单个角色过于臃肿
- 难以独立测试和替代
- 安全、审计等横切关注点难以分离

**为何不是更多（如 20 个角色）**？
- 通信开销过大
- 理解和维护成本过高
- 很多角色会过于单薄

**为何选择军事隐喻**？
- 职责边界天然清晰
- 指挥链概念直观
- 与 AI Agent "代理执行"语义契合
- 团队沟通时容易达成共识

### 后果

**正面**？
- 职责单一，每个角色可独立测试
- 新成员容易理解角色分工
- 支持渐进式实现（可先实现核心角色）?

**负面**？
- 消息传递开销（需优化路由策略）
- 初期学习曲线较陡
- 文档维护量较大

**需要关注**？
- 角色交互矩阵的约束（已在消息协议中定义）
- 消息路由性能（Engine 需要优化）

## ADR-002：MVP 选择 Delphi 而非 Electron

### 状态
已接受（2025-12-03）

### 背景
DeepFlow 需要集成到洞见（DeepInsight）桌面应用中
- 洞见现有技术栈：Delphi
- 考虑的替代方案：Electron、Tauri、.NET MAUI

### 决策
MVP 阶段使用 Delphi 实现核心框架，Python 实现 AI Skills。

### 理由

**选择 Delphi**。
| 因素 | Delphi | Electron | 说明 |
|------|--------|----------|------|
| 现有代码复用 | ✓ | ⚠️ 需重写 | 洞见已有大量 Delphi 代码 |
| 启动速度 | ✓✓ | ⚠️⚠️ | 原生编译 vs Node.js 启动 |
| 内存占用 | ✓✓ | ⚠️⚠️ | ~50MB vs ~200MB+ |
| 团队熟悉度 | ✓✓ | ⚠️ 需学习 | 现有团队技术栈 |
| 生态系 | ⚠️ 较小 | ✓丰富 | npm 包远多于 Delphi 组件 |

**为何 Python 用 AI Skills**？
- LLM 生态主要在 Python（LangChain、LiteLLM）
- 数据处理库丰富（pandas、numpy等
- 快速迭代 AI 逻辑
- 通过 HTTP 桥接，与主程序解耦

### 后果

**正面**：
- 快速交付 MVP（复用现有代码）
- 桌面应用性能优秀
- 单文件部署简单

**负面**：
- 需要管理 Python 子进程
- 跨语言调试较复杂
- Delphi 社区较小，招聘难度高

**缓解措施**：
- 详细规划 Python 服务生命周期管理（见风险 R7）
- 统一的日志和追踪（traceId）
- 考虑未来迁移到跨平台方案（V2.0）

## ADR-003：Python Skills 使用 FastAPI 而非 gRPC

### 状态
已接受（2025-12-03）

### 背景
Delphi 主程序需要调用 Python AI Skills，需选择通信协议。
- gRPC：高性能、强类型
- FastAPI/HTTP：简单、调试友好
- 进程内嵌入（Python4Delphi）：紧耦合

### 决策
使用 FastAPI 提供 HTTP/JSON API接口

### 理由

| 因素 | FastAPI | gRPC | Python4Delphi |
|------|---------|------|---------------|
| 调试便利 | ✓ 浏览器/curl 可测 | ⚠️ 需专用工具 | ✓ 难以单独调试 |
| Delphi 集成 | ✓ HTTP 客户端组成 | ⚠️ 需额外组件 | ✓ 直接调用 |
| 性能 | ⚠️ 中等 | ✅ 快 | ✅ 最快 |
| 部署独立性 | ✓ 可独立部署 | ✓ 可独立 | ✓ 紧耦合 |
| 流式支持 | ✓ SSE | ✅ Stream | ⚠️ 复杂 |

**FastAPI 优势**。
- 自动生成 OpenAPI 文档
- 原生 async/await 支持
- 类型提示和校验
- 社区活跃，文档丰富

### 后果

**正面**：
- 开发和调试效率高
- Python 服务可独立测试
- 未来可轻松暴露为外部 API

**负面**：
- HTTP 开销略高于 gRPC
- JSON 序列化不如 Protobuf

**性能优化**建议？
- 使用 msgpack 替代 JSON（可选）
- 连接池复用？
- 批量请求合并

## ADR-004：Workflow 引擎自研而非使用现成方案

### 状态？
已接受（2025-12-03）？

### 背景
需要一套Workflow 引擎来编排多步骤任务？
- 现成方案：Temporal、Camunda、Airflow
- 自研轻量方案

### 决策
自研轻量 Workflow 引擎，参考Temporal 设计理念？

### 理由

**为何不用 Temporal**？
- 需要额外的服务端部署（Temporal Server）？
- 对于桌面应用过于重量级？
- 学习曲线陡峭

**为何不用 Camunda**？
- Java 生态，与Delphi/Python 集成困难
- BPMN 对简单场景过于复杂？

**自研方案设计**？
```
核心概念？
- WorkflowDefinition：静态定义？
- WorkflowInstance：运行时实例
- Step：执行单元（SkillTask、AITask、HumanTask、SubWorkflow）？
- State：持久化状态

关键特性：
- 轻量：无需额外服务
- 可持久化：SQLite 存储状态
- 可恢复：应用重启后继续执行
- 支持人工任务：HumanTask 等待
```

### 后果

**正面**：
- 完全控制，可针对场景优化
- 无外部依赖，部署简单
- GPT 11 角色架构深度集成

**负面**：
- 需要自行实现持久化、恢复、重试
- 缺少成熟方案的生态

**风险缓解**：
- 详细的状态持久化设计（见风险 R1的
- 充分的测试覆盖

## ADR-005：使用置信度三档而非连续值路由

### 状态
已接受（2025-12-03）

### 背景
- 方案 A：使用连续置信度值（0-1）精细路由。
- 方案 A：使用连续置信度值（0-1）精细路由。
- 方案 B：离散化为高/中/低三档。

### 决策
使用三档置信度（High/Medium/Low）驱动路由决策。

```
High (≥0.9)   → 自动采用
Medium (0.7-0.9) → 人工确认
Low (<0.7)    → 重新生成或拒绝
```

### 理由

**为何不用连续置信度？**
✓ LLM 置信度天然不精确，0.85 vs 0.87 无实际区分意义
- 连续值需要复杂的路由规则
- 用户难以理解"0.823 置信度"

**三档的好处**
- 决策逻辑简单明了
- 容易向用户解释
- 阈值可配置调整

### 后果

**正面**：
- 实现简单
- 行为可预测
- 易于监控和调节

**负面**影响
- 精度有损失
- 边界情况需要调整

## ADR-006：消息协议使用JSON 而非二进制格式

### 状态
已接受（2025-12-03）

### 背景
11 角色之间通过消息通信，需选择序列化格式：
- JSON：可读性好
- MessagePack：紧凑高效
- Protocol Buffers：强类型、高性能

### 决策
MVP 使用 JSON，后续可选支持MessagePack）。

### 理由

| 因素 | JSON | MessagePack | Protobuf |
|------|------|-------------|----------|
| 可读性| 纯人类可读 | 纯二进制| 纯二进制|
| 调试便利 | 可日志直接可看 | ⚠️ 需解码 | ⚠️ 需解码 |
| Delphi 支持 | 均内置 | ⚠️ 需三方库| ⚠️ 需生成代码 |
| 性能 | ⚠️ 中等 | 相对较高 | 相对最高|
| 灵活性 | 强动态类 | 主行动态 | 无需预定义 |

**JSON 的现实考量因素**
- 本地单进程场景，性能不是瓶颈
- 开发效率优先
- 调试友好

### 后果

**正面**
- 开发调试效率高
- 日志可读
- 跨语言兼容性好

**负面**？
- 大消息序列化较慢
- 体积比二进制大？

**优化路径**？
- V1.1 可选支持 MessagePack
- 大对象（>1MB）使用 URI 引用而非内联

## ADR-007：日志使用结构化 JSON 而非纯文本

### 状态
已接受（2025-12-03）

### 背景
系统日志格式选择方案
- 纯文本：简单直观
- 结构化JSON：可查询、可分析

### 决策
使用结构化JSON 日志格式。

```json
{
  "timestamp": "2025-12-04T10:30:15.123Z",
  "level": "info",
  "traceId": "abc123",
  "role": "Commander",
  "action": "REQUEST_RECEIVED",
  "message": "接收用户请求",
  "data": {
    "userId": "u-001",
    "requestType": "analyze"
  }
}
```

### 理由

- **可查询*：可用jq、grep 过滤
- **可聚合*：便于统计分析
- **可追溯*：traceId 贯穿完整请求链
- **工具友好**：支持日志查看工具

### 后果

**正面**的？
- 问题定位效率高？
- 支持自动化监控？
- 审计合规友好

**负面**的？
- 日志体积略大
- 直接阅读略繁琐？

## ADR-008：MVP 不实现分布式部署

### 状态？
已接受（2025-12-03）？

### 背景
是否支持？MVP 阶段支持分布式部署：
- 单机部署：简单但扩展性有限？
- 分布式部署：复杂但可扩展

### 决策
MVP 仅支持单机部署，V2.0 再考虑分布式部署？

### 理由

**单机部署的**MVP 阶段足够**？**
- 洞见是桌面应用，单机场景为主
- 减少 MVP 复杂度？
- 避免分布式一致性问题？

**分布式需要解决的问题**（V2.0）：
- Workflow 实例化？
- 角色主从选举
- 状态同步？

### 后果

**正面**的？
- MVP 交付更快
- 架构简单可靠

**负面**：
- 单机性能上限
- 无法水平扩展
