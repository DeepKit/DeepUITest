## 1. 概述

本清单将 "DeepFlow Core / Flow 引擎框架" 拆解为四个模块的可执行任务：

1. `UniFlow.Types` — 基础类型与核心模块
2. `UniFlow.FlowStore` — Flow / Event / Snapshot 的持久化（SQLite 数据库）
3. `UniFlow.FlowEngine` — Flow 状态机与对接 API
4. `UniFlow.FlowService` — 面向 SoIs / SayDone / DevDirector 的高层服务

以及：

- 一个最小端到端用例（Build + Maintain 框架）
- 一组基础测试与验收标准

> 注：架构与模型定义以 `03.01.Design-DeepFlow-CoreModelAndPrinciples-1.0.md` 和 `04.01.Data-DeepFlow数据模型-v1.0.md` 为准，本清单仅给出工程实现视角的任务拆解。

## 3. 模块一：UniFlow.Types（核心类型）

> 目标：将 Flow / Event / Snapshot / Node 等核心模型抽象为统一的 Delphi 类型，供全系统复用。

### 3.1 设计要点

- Flow 类型与状态：`TUniFlowType` / `TUniFlowStatus`
- 事件状态：`TUniFlowEventStatus`
- 字符串别名：`TUniFlowId` / `TUniNodeId` / `TUniNodePath`
- 事件结构：`TUniFlowEvent`
- 快照结构：`TUniFlowSnapshot`
- Node 结构：`TUniFlowNode`

### 3.2 开发任务

- 定义 `UniFlow.Types.pas` 单元文件
  - [ ] 定义 `TUniFlowType = (uftBuild, uftMaintain, uftNlConvert, uftSceneChange, uftCodeChange)`。
  - [ ] 定义 `TUniFlowStatus = (ufsCreated, ufsRunning, ufsWaitingUser, ufsSucceeded, ufsFailed, ufsCancelled)`。
  - [ ] 定义 `TUniFlowEventStatus = (ufeStarted, ufeSucceeded, ufeFailed)`。
  - [ ] 定义 `TUniFlowId`/`TUniNodeId`/`TUniNodePath` `type string`。
  - [ ] 定义 `TUniFlowEvent` 结构，包含Id/FlowId/FlowType/Step/Source/Status/Timestamp/PayloadJson/ErrorCode。
  - [ ] 定义 `TUniFlowSnapshot` 结构，包含FlowId/Version/StateJson/CreatedAt。
  - [ ] 定义 `TUniFlowNode` 结构，包含NodeId/NodeType/ParentId/AttributesJson。

- 约定与样例：
  - [ ] 在注释中明确约定如下
    - Failed 事件必须携带非空 `ErrorCode`。
    - `PayloadJson` 一律使用 UTF-8 JSON 字符串，不在类型层解析；
    - `NodeType` 建议使用固定枚举字符串，如 `Project`/`Scene`/`Step`/`Feature`/`CodeBlock`。

## 4. 模块二：UniFlow.FlowStore（SQLite 存储模块）

> 目标：提供 IUniFlowStore 接口，屏蔽 SQLite 细节，负责 Flow / Event / Snapshot 的可靠持久化与查询接口。

### 4.1 表结构（参见 04.01 & 06.03）

最简MVP 需要的表（建议）：

- `flow_instances` 表/Flow 实例表
  - `id TEXT PRIMARY KEY`
  - `type TEXT NOT NULL`    // 映射 TUniFlowType
  - `status TEXT NOT NULL`  // 映射 TUniFlowStatus
  - `created_at TIMESTAMP`
  - `updated_at TIMESTAMP`

- `flow_events` 表/事件表
  - `id TEXT PRIMARY KEY`
  - `flow_id TEXT NOT NULL`
  - `type TEXT NOT NULL`
  - `step TEXT NOT NULL`
  - `source TEXT NOT NULL`
  - `status TEXT NOT NULL`
  - `timestamp TIMESTAMP NOT NULL`
  - `payload_json TEXT`
  - `error_code TEXT`

- `flow_snapshots` 表/快照表
  - `flow_id TEXT NOT NULL`
  - `version INTEGER NOT NULL`
  - `state_json TEXT NOT NULL`
  - `created_at TIMESTAMP NOT NULL`
  - `PRIMARY KEY (flow_id, version)`

### 4.2 接口定义

在`UniFlow.FlowStore.pas` 中：

- [ ] 定义 `TUniFlowInstance`（Id/FlowType/Status/CreatedAt/UpdatedAt）；
- [ ] 定义 `IUniFlowStore` 接口，至少包含：
  - `CreateFlowInstance(AFlowType, AInitialSnapshotJson): TUniFlowId`;
  - `UpdateFlowStatus(AFlowId, AStatus)`;
  - `GetFlowInstance(AFlowId, out AInstance)`;
  - `AppendEvent(AEvent)`;
  - `GetEvents(AFlowId): TArray<TUniFlowEvent>`;
  - `SaveSnapshot(ASnapshot)`;
  - `GetLatestSnapshot(AFlowId, out ASnapshot)`;

### 4.3 实现任务

- [ ] 实现 `TUniFlowStoreSqlite = class(TInterfacedObject, IUniFlowStore)`;
  - 构造函数接 SQLite 连接（或连接工厂）；
  - 使用事务保证 `AppendEvent` + `UpdateFlowStatus` + `SaveSnapshot` 的原子性（视调用点需求）;

- [ ] 在`TUniFlowType` / `TUniFlowStatus` 与数据库中的 TEXT 映射写成统一的转换函数，避免魔法字符串散落代码：
  - `function FlowTypeToStr(AType: TUniFlowType): string;`
  - `function StrToFlowType(const S: string): TUniFlowType;`
  - `function FlowStatusToStr(AStatus: TUniFlowStatus): string;` 等等

- [ ] 编写最小单元测试：
  - CreateFlowInstance / GetFlowInstance /
  - AppendEvent / GetEvents /
  - SaveSnapshot / GetLatestSnapshot /

## 5. 模块三：UniFlow.FlowEngine（状态机）API）

> 目标：在 IUniFlowStore 之上实现 Flow 状态机与基础 API，统一管理 Flow 的创建、事件追加与状态变更。

### 5.1 接口定义

> `UniFlow.FlowEngine.pas` 中：

- [ ] 定义 `TUniFlowTransitionResult`：FlowId/NewStatus/SnapshotJson）
- [ ] 定义 `IUniFlowEngine` 接口）
  - `CreateFlow(AFlowType, AInitialSnapshotJson): TUniFlowId）
  - `AppendEventAndAdvance(AEvent, AUpdateSnapshotJson): TUniFlowTransitionResult）
  - `GetFlowStatus(AFlowId): TUniFlowStatus）
  - `GetFlowEvents(AFlowId): TArray<TUniFlowEvent>`）
  - `RebuildSnapshot(AFlowId): string`（通过事件重放构建 StateJson）

- [ ] 提供一个默认实现类 `TUniFlowEngine = class(TInterfacedObject, IUniFlowEngine)`
  - 持有 `FStore: IUniFlowStore`
  - 内部函数 `NextStatus(ACurrentStatus, AEvent): TUniFlowStatus` 实现状态机方法

### 5.2 状态机 MVP 规则

建议先实现一套简单规则（后续可配置化）：

- 初始状态：
  - 新建 Flow：`ufsCreated`
- 事件驱动迁移（示意）：
  - `ufsCreated + (任何事件)` → `ufsRunning`
  - `ufsRunning + Failed 事件` → `ufsFailed`
  - `ufsRunning + Succeeded 事件 & Step in {终结步骤集合}` → `ufsSucceeded`
  - （可选）当业务显式写入 Cancel 事件 → `ufsCancelled`
  - `ufsWaitingUser` 用于需要用户确认的步骤，可由上层决定何时进入/退出

实现任务流程？

- [ ] FStore 获取当前 Flow 状态（若不存在则视为`ufsCreated`）；
- [ ] `AppendEventAndAdvance` 中：
  - 调用 `FStore.AppendEvent(AEvent)`；
  - 计算新状态`NewStatus := NextStatus(CurrentStatus, AEvent)`；
  - 调用 `FStore.UpdateFlowStatus(FlowId, NewStatus)`；
  - 若`AUpdateSnapshotJson` 非空，写入Snapshot；
  - 返回 `TUniFlowTransitionResult`；
- [ ] 对非法迁移（例如：`ufsSucceeded` 再写事件）抛出统一错误：
  - 使用 `EUniFlowError` 或等价异常类型；
  - `ErrorCode` 推荐统一为`WORKFLOW_INVALID_TRANSITION`：

### 5.3 快照重建

- [ ] ：`RebuildSnapshot(AFlowId)` 中：
  - 获取所有事件；
  - 从初始 Snapshot 开始（可为`{}`）；
  - 按时间顺序应用业务侧提供的"状态变更函数"（MVP 阶段可以先不实现复杂合并，只做占位或复用现有逻辑）：

> 说明：MVP 阶段可以先只依赖最简 Snapshot，不从事件完全重放；但接口签名建议按最终目标设计好：

> 目标：为 SoIs / SayDone / DevDirector 提供高层友好的服务接口，避免它们直接操作 Store/Engine：

### 6.1 接口定义

`UniFlow.FlowService.pas` 中：

  - `StartBuildFlow(AInitialStateJson): TUniFlowId`：
  - `StartMaintainFlow(ASourceFlowId, ATargetNodePath, AInitialStateJson): TUniFlowId`：
  - `AddBusinessEvent(AFlowId, AFlowType, AStep, ASource, AStatus, APayloadJson, AErrorCode): TUniFlowTransitionResult`：

- [ ] 实现 `TUniFlowService = class(TInterfacedObject, IUniFlowService)`，内部组装`IUniFlowEngine`：
  - `StartBuildFlow`：`CreateFlow(uftBuild, AInitialStateJson)`：
  - `StartMaintainFlow`：可从 Snapshot 或 Payload 中记`source_flow_id`/`target_node_path`：

### 6.2 SoIs / SayDone 接入改造任务

## 7. 最小端到端用例（验收用例）

> 目标：通过一条简单的 Build Flow + Maintain Flow，验证Types / Store / Engine / Service 整链路是否正常工作。

### 7.1 Build Flow 用例

场景（简化）：

1. SoIs：用户输入需要触发`ClarifyRequirement`事件。
2. SoIs：生成草稿 → `GenerateSketch` 事件→
3. 用户确认草图 → `ConfirmSketch` 事件→
4. SayDone：NL→结构化 → `NlConvertToStructure` 事件→
5. DevDirector：导入场景树 → `ImportToSceneTree` 事件→
6. Flow 最终状态= `ufsSucceeded`，有一个最新 Snapshot。

任务：

- [ ] 使用 `IUniFlowService.StartBuildFlow` 创建 Flow。
- [ ] 依次调用 `AddBusinessEvent` 模拟上述步骤（可以先在测试代码中硬编码）：
- [ ] 验证结果
  - `GetFlowStatus` 返回 `ufsSucceeded`.
  - `GetFlowEvents` 中按顺序包含 5 个步骤；
  - `GetLatestSnapshot` 非空.

### 7.2 Maintain Flow 用例

场景（简化）：

1. DevDirector：用户在界面上选中<Node>，点击"修改"；
2. FlowService：`StartMaintainFlow(源FlowId, NodePath)`.`
3. SoIs：澄清修改`ClarifyChange` 事件.
4. SayDone：计算补丁`ComputePatch` 事件.
5. DevDirector：应用Patch触发`ApplyPatch`事件。
6. Maintain Flow 状态= `ufsSucceeded`，Snapshot 中记录新结构/新版本引用记。

任务清单

- [ ] 在测试或 Demo 程序中模拟这条链路；
- [ ] 确认 Flow 与原来Build Flow 之间的关联（可在Payload 和Snapshot 中记录）。
- [ ] 为后续UI提供可视化基础。

## 8. 测试与验收标准（Flow 引擎线）

### 8.1 单元测试建议

- `UniFlow.Types`
  - [ ] 测试枚举与字符串转换（如有实现`ToStr/FromStr`）；
- `UniFlow.FlowStore`
  - [ ] 创建 Flow 、查询 Flow。
  - [ ] 写入多条 Event 、按时间顺序读取；
  - [ ] 多版本Snapshot 写入 、读取最新版本；
- `UniFlow.FlowEngine`
  - [ ] `CreateFlow` 后状态为 `ufsCreated`。
  - [ ] 第一条事件追加后状态为 `ufsRunning`。
  - [ ] Failed 事件使状态变为`ufsFailed`。
  - [ ] 非法迁移抛出异常（如`ufsSucceeded` 再次写入运行事件）。

### 8.2 集成测试建议

- [ ] 建一个最小子系统：`FlowStore + FlowEngine + FlowService`。
- [ ] 按第 7 章的 Build/Maintain 用例执行，检查状态与事件数量。
- [ ] 在SoIs / SayDone 中各增加一条代码路径，真正调用 `IUniFlowService` 处理Flow 事件，跑一遍真实UI/交互场景。

### 8.3 验收标准

当满足以下条件，可认为"DeepFlow Core / Flow 引擎线（MVP 阶段）基本完成"。

1. `UniFlow.Types` / `UniFlow.FlowStore` / `UniFlow.FlowEngine` / `UniFlow.FlowService` 四个模块均存在且编译通过。
2. SQLite 中 `flow_instances` / `flow_events` / `flow_snapshots` 表结构与 04.01 文档一致；
3. 能通过测试代码跑通一组 Build Flow 与一组 Maintain Flow，状态、事件顺序与 Snapshot 符合预期。
4. 至少有一次 SoIs 中 SayDone 的实际用户操作，会在 Flow 历史中留下完整可追溯的 `UniFlowEvent` 序列。
5. 相关单元/集成测试可稳定通过，且后续改动 Flow 引擎时，可用这些测试辅助回归。
