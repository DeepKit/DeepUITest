# UpFlow 与deepFlow 关系说明

> 厘清 11 角色协作架构（UpFlow）与事件溯源核心模型（deepFlow）的关系、定位和适用场景。

创建日期: 2025-12-04  版本: 1.0

---

## 1. 为何有两套设计？

DeepBase 文档集中存在两套看似独立的架构设计，这并非冗余，而是服务于不同层次的需求：

| 设计 | 文档 | 关注点 | 服务对象 |
|------|------|--------|----------|
| **UpFlow** | `03.01.Arch-DeepFlow架构设计` | 角色协作、AI 能力编排 | 洞见、AI Agent 应用 |
| **deepFlow** | `03.02.Design-DeepFlow-CoreModelAndPrinciples` | 流程追溯、事件记录 | SayDone、SoIs、DevDirector |

### 2.2 核心区别

| 维度 | UpFlow (角色协作) | deepFlow (事件溯源) |
|------|-------------------|-------------------|
| **核心抽象** | Role（角色）、Message（消息） | Flow（流程）、Event（事件） |
| **设计模式** | 多代理Agent 协作模式 | 事件溯源 (Event Sourcing) |
| **主要目标** | AI 能力的安全、可控编排 | 流程的可追溯、可回放 |
| **状态管理** | 角色内部状态 + 消息传递 | 事件序列 + 快照重建 |
| **适用场景** | AI 推理、Skill 执行、安全审计 | 构建循环、维护循环、版本管理 |

## 3. 典型使用场景

### 3.1 洞见（DeepInsight）使用 UpFlow

洞见是 AI 决策辅助产品，侧重于 **AI 能力的安全编辑**。

```
用户请求 "分析这个决策"
    │?
[UpFlow 角色协作]
├── Commander: 接收请求，权限校验?
├── Guard: 检测?Prompt 注入
├── Advisor: 调用 LLM 分析
├── Executor: 执行 decision_coach Skill
├── Guard: 审核输出，检测幻觉?
└── Commander: 返回结果

核心价值 安全、可控、可审计的?AI 调用
```

### 3.2 SayDone 使用 deepFlow

SayDone 是自然语言转结构化引擎，侧重于 **流程的完整记录**??

```
用户输入 "创建一个登录页面?"
    │?
[deepFlow 事件记录]
├── Event: ClarifyRequirement (Started →?Succeeded)
├── Event: GenerateSketch (Started →?Succeeded)
├── Event: ConfirmSketch (Started →?WaitingUser →?Succeeded)
├── Event: NlConvertToStructure (Started →?Succeeded)
└── Snapshot: 最终结构化数据

核心价值 可追溯、可回放、可分叉的流程历史?
```

### 3.3 混合使用场景

某些复杂场景可能同时使用两套机制。

```
SoIs 意图澄清流程
    │?
    ├── [deepFlow] 记录流程事件
    │?  └── Event: ClarifyIntent (Succeeded)
     终了
    └── [UpFlow] 执行 AI 能力
        ├── Commander: 分发任务
        ├── Advisor: 理解用户意图
        └── Guard: 校验澄清结果
```

## 4. 设计原则对比

### 4.1 共同原则

两套设计共享以下核心原则：

| 原则 | UpFlow 体现 | deepFlow 体现 |
|------|-------------|-------------|
| **AI 用 AI，程序归程序** | Guard 是纯程序，Advisor 用 AI | 状态机是纯程序，payload 可含 AI |
| **单一事实源** | 消息是角色间唯一通信方式 | Event 是状态变化的唯一来源 |
| **可审计** | Chronicler 记录所有操作 | Event 序列完整可查 |
| **向后兼容** | 消息协议版本化 | Event 结构可扩展 |

### 4.2 侧重点差异

| UpFlow 强调 | deepFlow 强调 |
|-------------|-------------|
| 角色职责清晰、边界明确 | 事件完整、无幽灵状态 |
| 消息路由、交互约定 | 时间线追溯、版本分发 |
| 安全守卫、信任层 | 快照重建、状态恢复 |
| 实时响应、流式输出 | 历史回放、可视化调试 |

## 5. 何时使用哪套方案

### 5.1 选择 UpFlow 的场景

- 需要调用 AI/LLM 能力
- 需要多步骤 Skill 编排
- 需要严格的安全审核（输入/输出校验）
- 或需要实时响应或流式输出
- 或面向终端用户的智能交互

### 5.2 选择 deepFlow 的场景

- 或需要完整的操作历史
- 或需要从任意历史点回退/分叉
- 或需要向用户展示"经历了哪些步骤"
- 或需要支持撤销/重做
- 或构建/维护循环的流程管理

### 5.3 同时使用的场景

- 或AI 辅助的构建/维护循环（如 SoIS）
- 或需要既安全又可追溯的复杂流程
- 或需要将 AI 能力嵌入事件驱动流程

## 6. 集成指南

### 6.1 UpFlow 调用 deepFlow

或UpFlow 与Workflow 需要记录到 deepFlow 时：

```pascal
// 在 Dispatcher 中创建 deepFlow Event
procedure TDispatcher.OnWorkflowStepCompleted(AStep: TWorkflowStep);
begin
  // 将记录到UpFlow 的Chronicler
  Chronicler.Log('STEP_COMPLETED', AStep.ToJSON);
  
  // 同时记录向 deepFlow 的事件系统（如果启用）
  if FUniFlowEnabled then
    UniFlowEngine.WriteEvent(TUniFlowEvent.Create(
      FCurrentFlowId,
      'WorkflowStep',
      AStep.Name,
      'Dispatcher',
      'Succeeded',
      AStep.OutputPayload
    ));
end;
```

### 6.2 deepFlow 触发 UpFlow

当deepFlow 的某个步骤需要AI 能力时：

```pascal
// 当deepFlow 步骤中调用UpFlow
function TUniFlowStep.ExecuteAITask(APayload: TJSONObject): TJSONObject;
var
  LMessage: TUniFlowMessage;
  LResponse: TUniFlowMessage;
begin
  // 通过 UpFlow 向Commander 发起 AI 请求
  LMessage := TMessageBuilder.Create
    .WithAction('EXECUTE_AI_TASK')
    .From(rtDispatcher)
    .To([rtCommander])
    .WithPayload(APayload)
    .Build;
  
  LResponse := FUniFlowEngine.SendAndWait(LMessage);
  Result := LResponse.Body.Payload;
end;
```

## 8. 常见问题

### Q1: 能否只用一套？

**可以**，但会牺牲部分能力：
- 只用 UpFlow：缺少完整的历史追溯和回放能力：
 - 只用 deepFlow：缺少 AI 能力的安全编码

### Q2: 两套会不会增加复杂度吗？

**会增加学习成本*，但是**
 - 职责分离使单个系统更简单
 - 可以根据产品需求选择性使用
- 文档明确划分了适用场景

### Q3: 两套的数据如何关联？

 - UpFlow 的 `traceId` 可以关联到 deepFlow 的 `flowId`
- Chronicler 的日志可以作为两者的桥接审计
 - 建议在 deepFlow Event 的 payload 中记录相关的 UpFlow traceId
