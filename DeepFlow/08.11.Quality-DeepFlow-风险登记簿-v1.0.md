## 风险 1：Workflow 状态持久化

### 风险描述

🔴 **风险等级：高**

Workflow 执行过程中需要保存状态以支持断点续传。
- 长时间运行的 HumanTask（可能数小时甚至数天等）
- 应用重启后的 Workflow 恢复
- 分布式场景下的状态同步

**核心挑战**：
1. 状态结构复杂（嵌套步骤、变量、循环上下文等）
2. 检查点（checkpoint）粒度难以平衡（太频繁影响性能，太稀疏丢失状态）
3. 版本升级时旧状态的兼容性

### 影响评估

| 维度 | 影响 |
|------|------|
| 功能 | HumanTask 超时后无法恢复；Workflow 中断后无法续跑|
| 性能 | 频繁持久化导致延迟增加50-100ms/步骤 |
| 运维 | 状态损坏导致需要人工干预|

### 缓解措施

**短期（MVP阶段）**

```pascal
// 使用 SQLite 简单实现
TWorkflowState = class
  WorkflowInstanceId: string;
  CurrentStepId: string;
  Status: TWorkflowStatus;
  Variables: TJSONObject;
  StepStates: TJSONArray;     // 每个步骤的状态快照
  CreatedAt: TDateTime;
  UpdatedAt: TDateTime;
  Version: Integer;           // 乐观锁版本号
end;

// 持久化时机
// 1. 每个步骤完成时
// 2. HumanTask 开始等待时
// 3. 重要变量变更时
```

**中期（V1.1阶段）**
- 引入 WAL（Write-Ahead Log）模式，先写日志再更新状态
- 实现增量状态更新，减少序列化开销
- 添加状态压缩（对长期运行的 Workflow）

**长期（V2.0阶段）**
- 考虑使用专门的 Workflow 引擎存储（如 Temporal 的方案）
- 实现状态分片，支持大规模并发

### 监控指标

| 指标 | 阈值 | 告警 |
|------|------|------|
| 状态持久化延迟 | P99 < 50ms | > 100ms |
| 状态恢复成功率 | > 99.9% | < 99% |
| 状态大小 | < 1MB | > 5MB |
| 检查点频率 | 1-10/步骤 | > 50 |

### 验收标准

- [ ] 应用重启后，所有进行中的 Workflow 能正确恢复
- [ ] HumanTask 等待 24 小时后，Workflow 能继续执行
- [ ] Workflow 定义升级后，旧实例能兼容运行或优雅失败

## 风险 2：LLM 调用抽象

### 风险描述

🟡 **风险等级：中**

智囊角色需要调用不同的 LLM 服务（OpenAI、Claude、本地模型等），面临挑战
1. API 差异（请求格式、响应结构、错误码映射）
2. 流式响应处理方式不同
3. Token 计数和费用计算差异
4. 速率限制和配额管理

**核心挑战**：
1. 抽象层设计需要平衡通用性和特定模型能力
2. 置信度提取方式因模型而异（有的支持 logprobs，有的不支持）
3. 模型切换时的行为一致性

### 影响评估

| 维度 | 影响 |
|------|------|
| 功能 | 切换模型时输出格式不兼容；置信度不可靠 |
| 成本 | 无法准确预估和控制 API 费用 |
| 可靠性 | 单一模型故障导致整体不可用 |

### 缓解措施

**短期（MVP）**：

```pascal
// MVP 只支持 OpenAI 兼容 API
TLLMClient = class
private
  FBaseUrl: string;           // 可配置，支持代理
  FApiKey: string;
  FModel: string;
  FTimeout: Integer;
public
  function Complete(const APrompt: string; AParams: TLLMParams): TLLMResponse;
  function CompleteStream(const APrompt: string; AParams: TLLMParams;
    AOnChunk: TProc<string>): TLLMResponse;
end;

// 参数统一
TLLMParams = record
  Temperature: Double;
  MaxTokens: Integer;
  StopSequences: TArray<string>;
  ResponseFormat: TLLMResponseFormat;  // text | json_object
end;
```

**中期（V1.1）**：
- 引入 Provider 抽象层

```pascal
ILLMProvider = interface
  function GetName: string;
  function GetCapabilities: TLLMCapabilities;
  function Complete(ARequest: TLLMRequest): TLLMResponse;
  function SupportsStreaming: Boolean;
  function SupportsLogprobs: Boolean;
end;

// 实现多个 Provider
TOpenAIProvider = class(TInterfacedObject, ILLMProvider)
TClaudeProvider = class(TInterfacedObject, ILLMProvider)
TOllamaProvider = class(TInterfacedObject, ILLMProvider)
```

**长期（V2.0）**：
- 实现模型路由（根据任务类型选择最佳模型）
- 实现自动降级（主模型失败切换备用模型）
- 实现成本预算控制

### 监控指标

| 指标 | 阈值 | 告警 |
|------|------|------|
| LLM 请求延迟 | P99 < 30s | > 60s |
| LLM 错误率 | < 1% | > 5% |
| Token 消耗/请求 | < 2000 | > 5000 |
| API 费用/请求 | 预算内 | 超预算+20% |

### 验收标准

- [ ] 能成功调用 OpenAI 兼容 API（包括代理）
- [ ] 流式响应能正确处理
- [ ] 超时和错误能正确处理和重试
- [ ] Token 使用量能正确统计

## 风险 3：角色间消息序列化

### 风险描述

🟡 **风险等级：中**

设计文档使用 TypeScript 定义消息类型，但 MVP 使用 Delphi 实现，存在：
1. 类型系统差异（TypeScript 结构类型 vs Delphi 名义类型）
2. JSON 序列化/反序列化的边界情况处理
3. 泛型和联合类型的映射困难
4. 版本兼容性管理

**核心挑战**：
1. 确保 Delphi 实现与TypeScript 规范保持一致
2. 处理复杂嵌套结构和可选字段
3. 保持序列化性能

### 影响评估

| 维度 | 影响 |
|------|------|
| 开销| 手动维护两套类型定义，易出错 |
| 调试 | 序列化错误难以定位 |
| 扩展 | 新增消息类型需要修改多处 |

### 缓解措施

**短期（MVP阶段）

```pascal
// 使用 RTTI 和泛型简化序列化
TMessageSerializer = class
public
  class function ToJSON<T: class>(AObj: T): TJSONObject;
  class function FromJSON<T: class>(AJSON: TJSONObject): T;
  
  // 验证消息格式
  class function Validate(AJSON: TJSONObject; const ASchemaName: string): TValidationResult;
end;

// 消息基类使用属性标签
TBaseMessage = class

  [JSONName('id')]
  FId: string;
  
  [JSONName('type')]
  FType: TMessageType;
  
  [JSONName('timestamp')]
  [JSONFormat('yyyy-MM-dd''T''HH:mm:ss.sss''Z''')]
  FTimestamp: TDateTime;
public
  // ...
end;
```

**中期（V1.1版本）目标**
- 基于 TypeScript 定义自动生成 Delphi 类型（代码生成器）
- 引入 JSON Schema 验证
- 实现消息版本自动协商

```pascal

  FSchemas: TDictionary<string, TJSONObject>;

  procedure LoadSchema(const AName, APath: string);
```

**长期（V2.0阶段）里程碑**
- 考虑使用 Protocol Buffers 或FlatBuffers 提升性能
- 实现消息压缩（对大消息）

### 监控指标

| 指标 | 阈值| 告警 |
|------|------|------|
| 序列化耗时 | < 1ms | > 10ms |
| 反序列化错误率| < 0.1% | > 1% |
| Schema 验证失败率| < 0.1% | > 1% |
| 消息大小 | < 64KB | > 256KB |

### 验收标准

- [ ] 所有消息类型能正确序列化/反序列化
- [ ] 未知字段能被忽略（向前兼容）
- [ ] 缺失可选字段能使用默认值
- [ ] 错误消息能明确指出问题位置

## 风险 4：AI 置信度校验

### 风险描述

🟡 **风险等级：中**

置信度路由机制依赖于准确的置信度评估，但仍有局限
1. LLM 自报告的置信度往往过度自信
2. 不同任务类型的置信度基线不同
3. 校准需要足够的历史数据

### 影响评估

| 维度 | 影响 |
|------|------|
| 准确性 | 高置信度结果可能错误；低置信度结果可能正确 |
| 效率 | 错误路由导致不必要的人工介入 |
| 成本 | 重复生成浪费 API 调用 |

### 缓解措施

**短期（MVP版本）？
- 使用保守的阈值设置（high >= 0.95, medium >= 0.85?
- 记录所有置信度和实际结果，积累校准数据

**中期（V1.1版）**
- 实现 Platt Scaling 和Temperature Scaling 校准
- 基于历史数据动态调整阈值

**长期（V2.0版）**
- 训练任务特定的置信度预测模型
- 实现多模型集成投稿

### 监控指标

| 指标 | 阈值 | 告警 |
|------|------|------|
| 高置信度准确率 | > 95% | < 90% |
| 中置信度准确率 | > 80% | < 70% |
| 人工修正率 | < 20% | > 30% |

## 风险 5：分布式一致性（V2.0版

### 风险描述

🔴 **风险等级：高**（仅分布式模式）

分布式部署时，有状态角色（调度员、军械官）需要保证一致性：
1. Workflow 实例不能被多个调度员同时执行
2. 配置更新需要原子性传递
3. 节点故障时的状态接管

### 影响评估

| 维度 | 影响 |
|------|------|
| 数据 | 同一 Workflow 被重复执行或状态丢失？|
| 可用性？| 脑裂导致服务不可用？|
| 复杂度？| 大幅增加开发和运维难度 |

### 缓解措施

**MVP 策略：不实现分布式？**

MVP 阶段仅支持单机部署，完全避免分布式一致性问题。

**V2.0 策略**。
- 使用 Redis 分布式锁保护 Workflow 实例
- 使用 etcd/ZooKeeper 进行主从选举
- 实现幂等性处理，容忍重复消息

### 监控指标

| 指标 | 阈值？| 告警 |
|------|------|------|
| 锁竞争率 | < 5% | > 20% |
| 主从切换时间 | < 30s | > 60s |
| 重复执行率？| 0% | > 0.1% |

## 风险 6.1 角色通信复杂性

### 风险描述

🟡 **风险等级：中**

11 角色设计带来高度模块化的同时，也引入了通信复杂性：
1. **交互路径数**：理论上最多 110 种两两交互，约束管理复杂
2. **调试困难**：消息在多角色间流转，问题定位慢
3. **性能开销**：每次跳转都有序列化/反序列化成本
4. **学习曲线**：新开发者理解 11 角色分工需要耗时

### 影响评估

| 维度 | 影响 |
|------|------|
| 开发 | 调试一个请求可能需要跟进 5+ 角色的日志 |
| 性能 | 简单请求可能经历4-6 次角色跳转|
| 维护 | 修改一个角色可能影响多个上下游 |

### 缓解措施

**短期（MVP阶段）

1. **统一跟踪 ID**：每个请求携带`traceId`，所有角色日志包含此 ID

```pascal
// 日志格式
[2025-12-04 10:30:15.123] [TRACE:abc123] [Commander] 接收请求
[2025-12-04 10:30:15.125] [TRACE:abc123] [Dispatcher] 创建 Workflow
[2025-12-04 10:30:15.130] [TRACE:abc123] [Executor] 执行 Skill:echo
```

2. **可视化跟踪工具**：Inspector 提供消息流可视化

3. **交互矩阵校验**：Engine 在路由时验证交互合法性？

**中期（V1.1规划）：**
- 集成 OpenTelemetry 分布式追踪
- 实现消息流端到端延迟分析
- 提供角色依赖关系图

### 监控指标

| 指标 | 阈值 | 告警 |
|------|------|------|
| 平均角色跳转次数 | < 6 | > 10 |
| 单次跳转延迟 | < 2ms | > 10ms |
| 违规交互次数 | 0 | > 0 |

## 风险 7：Python 服务生命周期管理

### 风险描述

🔴 **风险等级：高**

Delphi 主程序需要管理 Python Skill 服务进程？
1. **启动管理**：DeepFlow 启动时需同时启动 Python 服务
2. **健康检查**：Python 进程崩溃时需自动重启
3. **优雅停止**：主程序退出时需清理 Python 进程
4. **资源隔离**：Python 内存泄漏不应影响主程序？
5. **版本兼容**：不同用户可能有不同 Python 环境

### 影响评估

| 维度 | 影响 |
|------|------|
| 可靠性 | Python 崩溃导致 AI 功能不可用？ |
| 部署 | 需要处理 Python 环境配置复杂？ |
| 调试 | 跨进程调试困难？ |
| 安全 | 进程权限需要正确隔离？ |

### 缓解措施

**短期（MVP阶段）：**

## 风险 8：LLM 成本控制

### 风险描述

🟡 **风险等级：中**

LLM API 调用有直接费用，且费用可能快速增长：
1. **费用不可预测**：用户输入长度不可控
2. **无意中的循环**：错误重试可能产生大量调用
3. **Token 浪费**：Prompt 设计不当导致 token 使用过多
4. **没有预算控制**：可能产生超预期费用

### 影响评估

| 维度 | 影响 |
|------|------|
| 财务 | 月度费用可能超预算数额|
| 可用配额| 达到配额后服务中断|
| 用户体验 | 限流影响正常使用 |

### 缓解措施

**短期（MVP阶段）?

```pascal
// 费用跟踪代码
TCostTracker = class
private
  FDailyLimit: Double;      // 美元

    const AModel: string): Double;
public
  procedure RecordUsage(AUsage: TTokenUsage; const AModel: string);
  function CanProceed(AEstimatedTokens: Integer): Boolean;
  function GetRemainingBudget: Double;
  
   property OnBudgetWarning: TNotifyEvent;  // 80% 时触发

   raise EBudgetExceeded.Create('今日 AI 调用额度已用完');
```

**中期（V1.1版）：**
- 实现用户级别的配额管理
- Prompt 缓存减少重复调用
- 智能模型选择（简单任务用便宜模型）:
- 批量请求合并减少开销

### 监控指标

| 指标 | 阈值 | 告警 |
|------|------|------|
| 日均费用 | < 预算 | 超预算80% |
| 单次调用费用 | < $0.10 | > $0.50 |
| Token 浪费率 | < 10% | > 30% |
| 重试导致的额外费用 | < 5% | > 20% |

### 验收标准

- [ ] 每次 LLM 调用都记录 token 使用费用
- [ ] 达到日度预算 80% 时发出警告
- [ ] 超出预算时能优雅降级而非崩溃

## 风险 9：文档维护负担

### 风险描述

🟢 **风险等级：低**（但长期影响显著：）

当前已有 38+ 份详细文档，维护成本高：
1. **同步成本**：代码变更需同步更新文档
2. **一致性风险**：文档间可能产生矛盾
3. **发现性低**：新成员难以快速定位所需文档
4. **过时风险**：未更新的文档可能误导

### 影响评估

| 维度 | 影响 |
|------|------|
| 开发效率 | 文档维护占用开发时间 |
| 新成员上手 | 文档与代码不一致导致困惑 |
| 质量 | 过时文档可能导致实现错误 |

### 缓解措施

**短期（MVP 版）：**

1. **文档分级**：
   - 🟢 稳定：架构设计、核心模型（变更少）
    - 🟡 活跃：API 规范、开发指南（需跟随代码更新）
   - 🔴 临时：实验性方案（可删除）

2. **变更关联**：在代码 PR 中标记受影响的文档

3. **文档导航**：已使用`00.03.Product-DeepFlow-文档导航总览` 作为入口

**中期（V1.1*目标*）
- 文档源码化，与代码一起版本控制
- 自动化文档统计（最后更新时间、作者）
- 从代码注释自动生成部分文档

### 监控指标

| 指标 | 阈值 | 告警 |
|------|------|------|
