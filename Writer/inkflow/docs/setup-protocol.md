# InkFlow 交互式 Init / Setup 协议 v1.4

> 记录于 2026-06-19。v1.2：2026-06-25 增加叙事分析师审查角色；v1.3：2026-06-26 将 `init` 定义为全书启动，将 `setup --chapter` 定义为单章生产前校准；v1.4：2026-06-29 增加 contract-first 章前事实清单和资格门禁口径；v1.5：2026-06-29 增加 `confirm-contract` 契约审计师两轮复审。

## 核心规则

### 0-9 对话格式

| 数字 | 含义 |
|------|------|
| 1-7 | AI 生成的 7 个差异性选项，由人类选择 |
| 8 | 进入下一级 / 生成 Shot 级子契约 |
| 9 | 重新生成 1-7 选项 |
| 0 | 返回上一级 / 退出当前层级 |
| 人类直接输入文字 | 交付内容（不选数字，直接写文字） |

### 对话规则

1. **每次只聊一个问题。** 不批量提问。
2. **先战略后战术。** L1 世界观 → L2 角色弧线 → L3 章节结构 → L4 Shot+风格。
3. **选项必须互斥且有实质差异。** 不是连续打分，是 7 个不同的具体方案。
4. **每个选项一句话说清楚。** 不啰嗦。

## L1 世界观核心原则：系统偏差的三层来源

鱼嘴不是一个"恶意系统"，它的代价来自三层结构性偏差，每一层都不是故意的：

1. **建模者偏差** — 参数定义者以自己的世界为默认值。"社交活跃度"=微信群数量+活动报名，茶社里四十年的老茶友不算"社交"。"业态效率"=人流密度，白英用手背试杯壁的温度不可量化，因此不存在。"外江适应指数"由 23 楼的人定义，他们认为的"适应"是有社保、有学历——阿坤送了 8794 单，不算。

2. **传感器/采集系统盲区** — 能被传感器捕捉的才进入系统。阿坤的膝盖没有传感器 → "系统未记录"。老张的杯子底磕了又粘四十年的那层水垢 → 没有传感器。茶社后厨的泡菜坛子坛沿水干了白英又加了一点 → 没有传感器。系统不撒谎，但它的"真实"是传感器能看见的那一部分真实。

3. **AI 运行后的放大** — 目标函数在无人值守时自动向效率倾斜。苏然三年前写的代码把"配送效率"当作最高权重，她没想过骑手的膝盖。三年后，外江边界每年外推 6%。没有人按下"外推"按钮——是系统在自动优化。偏差一旦进入算法，会被规模化。

**写作原则**：系统不恶意、建模者不恶意、评估团不恶意。代价来自结构，不来自反派。

## 架构师 4 级（同时存在，各守其层）

| 级别 | 名称 | 上下文 | 管什么 |
|------|------|--------|--------|
| L1 | 世界观架构师 | 全书 | 系统规则、时空设定、硬边界——什么能发生、什么不能 |
| L2 | 角色弧线架构师 | 全书 | 每个 POV 角色从哪来、到哪去、转变路径 |
| L3 | 章节结构架构师 | 单卷 | 本章在卷中的位置、核心情绪、各线配比 |
| L4 | Shot+风格架构师 | 单章 | 每个 Shot 的 must_land 事件、POV 分配、风格执行 |

## Init 阶段流程

```
L1 世界观 → 确认(8) → L2 角色弧线 → 确认(8) → L3 章节结构 → 确认(8) → L4 Shot事件 → 确认(8) → 生成 contract-draft.yaml
```

`ink init <project>` 用于全书启动和章以上层级交互初始化。每级只问一个问题，给 1-7 个选项。人类选 8 进入下一级，选 9 换一批选项，选 0 回到上一级，直接输入文字交给架构师吸收。Init 完成后生成 `contract-draft.yaml`，但主流程不是让普通用户直接编辑 YAML；人类和架构师继续讨论，由架构师修订契约草案，然后运行 `ink confirm-contract <project>`。

`ink confirm-contract <project>` 必须触发契约审计师两轮复审：

1. 结构完整性复审：检查必需段落、角色弧线、`chapter_N_events`、占位符。
2. 生产就绪复审：检查 shot 编号、POV 声明、must_land 事件、提示词残留、章末 hook 提示。

两轮复审都通过，契约才能入库为 `confirmed`。任何一轮不通过，都写 contract audit report 和 `contract_conflict` 审计事件，并打回架构师和人类继续讨论。

## Chapter Setup 阶段流程

```
读取 confirmed/locked 元契约
  → 抽取本章 chapter_N_events
  → 读取前一章 review 结论
  → 编译 fact manifest / hard fact pack
  → 生成 .inkflow/chapter-setups/<chapter>.yaml
  → 人类确认本章 shot、POV、类型职责、章末钩子、禁止议论规则、硬事实与禁扩写范围
  → run --chapter 执行生产
```

`ink setup <project> --chapter <key>` 只校准某一章，不创建全书项目、不改写元契约、不生成正文。人类只在生产前编辑/确认 setup 包；生产中不插手；生产后用 `ink review --chapter` 记录验收结论。

### 契约问题 vs 软件规则问题

每章生成前必须重新 `setup --chapter`，因为契约里的章节事件、上一章人工 review、类型职责和章末钩子都可能变化。若契约仍含“只生成第 N 章”这类旧范围限制，或仍保留旧段落锁（如 `500-800 字/段落，3-4 段/shot`），这是契约未校准，必须先更新契约并重新 confirm/setup。

软件规则负责防呆和判定边界：`run --chapter` 必须拒绝缺失/过期/章节不匹配的 setup 包；硬规则裁判只清零硬事实、POV、must_land、禁写、提前揭示、提示词残留、空文/重复等问题。段落长度、方言点缀、感官密度和身体时刻开场属于风格或文学质量问题，不能直接导致 `eligible=False`。

### Contract-first setup 输出

`setup --chapter` 必须把人类可审的章节计划编译成机器可检查的 `fact_manifest`。第一版已经包含废弃角色名、禁词、未授权医疗/请假类扩写标记、hook 要求、每 shot must_land / POV / authorized corpus；完整目标字段如下：

| 字段 | 说明 |
|------|------|
| `allowed_facts` | 本章允许出现和推进的事实、机构、地点、人物关系 |
| `forbidden_expansions` | 未经授权不得新增的医疗、制度、国际、系统、履历等高影响事实 |
| `must_land_anchors` | 可定位动作/台词/物件/信息变化，不接受散文化愿望句 |
| `pov_known_unknown` | POV 角色知道/不知道的信息边界 |
| `contract_numbers` | 必须保真或不得新增同类替代的数字 |
| `hook_requirements` | 仅对有职责的 shot 标记悬疑、留白、章末钩子 |
| `format_rules` | 正文标题、分隔符、管线元数据、提示词残留等排版规则 |
| `editorial_intent` | 本章编辑意图：该推进什么、压住什么、读者应带着什么问题离开 |

run 阶段必须先用 `fact_manifest` 审大纲，再审草稿。第一版已做到：大纲不合格不得进入正文写作；Gate1 通过稿还要先过 hard fact gate，不合格草稿不得进入文学 jury。setup linter 也已在 run 前执行，能拦截 `must_land` 同时命中 `forbidden_phrases`、POV 与契约/fact_manifest 不一致、未知类型职责、章节 hook 缺失等问题，并归因为 `contract_conflict`；数字锁与 POV known/unknown 的细粒度校验仍需后续增强。

## 叙事分析师（审查角色）

> 规范文档：`narrative-analyst.md`

架构师每完成一个级别的编译后，人类可选是否触发叙事分析师审查。叙事分析师**不修改契约**——只输出诊断报告，由人类 + 架构师决定如何行动。

```
架构师编译完成 → 人类收到通知
                         ↓
              人类选择：直接确认 / 请求叙事分析师审查
                         ↓
              叙事分析师审查（输出诊断报告）
                         ↓
              人类 + 架构师决定：
                - 接受报告 → 修改 → 重新编译 → 再审查（循环）
                - 部分接受 → 只改 P0/P1
                - 跳过 → 直接确认
                         ↓
              人类确认 → 进入下一级
```

### 审查触发规则

| 场景 | 是否触发 |
|------|---------|
| 架构师完成 L1-L4 编译 | 人类可选 |
| 人类修改后重新编译 | 人类可选 |
| 人类主动要求 | 是 |
| run 阶段 | 不触发 |
| 全书 Chisel 校准 | 不触发 |

### 审查输出格式

叙事分析师每次审查输出结构化诊断报告，包含：
- **总体判断**：通过 / 需要调整 / 结构性问题
- **问题列表**：类型、位置、严重程度（P0/P1/P2）、框架依据、修正建议
- **优势**：至少指出 1 条做得好的地方
- **修正优先级**：1-2-3 排序

### 与架构师的分工

| | 架构师 | 叙事分析师 |
|---|---|---|
| 编译契约 | ✅ | ❌ |
| 修改契约 | ✅（根据人类指令） | ❌（只提建议） |
| 发现结构问题 | 自检 | ✅（专业审查） |
| 输出修正建议 | ✅ | ✅ |
| 最终决策 | ❌ | ❌（人类决定） |

## 生产阶段：级联 Gate

### 规则

**下级全部封版，才触发上级 Gate。** 不是每个 Shot 都过 4 级，而是攒够一批才升一级。

```
Shot 1 → L4 → 封版
Shot 2 → L4 → 封版
...
Shot N → L4 → 封版
           ↓ (最后一个 Shot 封版后)
         L3 唤醒 → 检查整章 → 封版
           ↓ (最后一章封版后)
         L2 唤醒 → 检查全卷角色弧线 → 封版
           ↓ (最后一卷封版后)
         L1 唤醒 → 检查全书世界观 → 封版
```

### 为什么这样设计

- L4 写得再好，也可能在 L2 翻车（角色弧线走偏）或 L1 翻车（违反世界观硬边界）
- 写得越好越要检查高层级，因为低层级的"好"会掩盖高层级的"偏"
- 级联不是"选一个级别检查"，是**逐级必过**

### 各层 Gate 检查内容

| Gate | 触发条件 | 检查什么 | 失败动作 |
|------|---------|---------|---------|
| L4 | 每个 Shot 完成 Gate2 | must_land 事件落地、风格合规、反模式避免 | 标记 Shot 需 repair |
| L3 | 一章全部 Shot 通过 L4 | POV 配比、章节弧线、节奏、钩子质量 | 标记具体 Shot 需 repair |
| L2 | 一卷全部章通过 L3 | 每个 POV 角色弧线是否在轨道上 | 标记具体章需 repair |
| L1 | 全书全部卷通过 L2 | 世界观硬边界、系统规则一致性 | 标记需 repair 的章，严重时触发契约修订 |

### P0 实现范围

P0 已实现 L4 和 L3 单章运行。第 2 章已完成真实链路验证；后续章节按 `setup --chapter → run --chapter → review --chapter` 推进。L2 和 L1 是 P1 多章/多卷运行时的功能。
