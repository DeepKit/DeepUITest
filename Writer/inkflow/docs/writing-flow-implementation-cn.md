# InkFlow 写作流程实现说明

日期：2026-06-29
编码：UTF-8 中文
用途：说明当前软件流程中已经实现的写作思路，方便人工检查是否符合正确的创作生产逻辑。

## 1. 当前产品定位

InkFlow 现在不是“一次性直接生成整本小说”的工具。

当前实现的核心思路是：

1. 全书启动前，由人确认全书级别的创作意图。
2. 每一章生产前，由人校准本章契约和关键事实。
3. 软件在章节生产过程中自动执行，不再中途向人要判断。
4. 章节生成后，由人审阅。
5. 只有人工接受的章节，才会成为正式版本。

也就是说，模型生成的正文默认只是候选稿。只有通过软件门禁并且被人工接受后，才算正式正文。

## 2. 人类介入边界

人类只应该在两个阶段介入：

1. 生产前：
   - `init`：初始化全书级别、章以上级别的契约。
   - `confirm-contract`：契约审计师两轮复审，通过后才把契约确认为可生产版本。
   - `setup`：在某一章生产前，校准这一章的写作准备。

2. 生产后：
   - `review`：接受、修改或拒绝这一章的生成结果。

在 `run` 执行期间，软件不应该反复询问人类。它应该自动完成，或者失败并留下可审计的原因，或者留下可以恢复的 session。

## 3. 主命令流程

当前公开的生产流程是：

```text
init -> confirm-contract -> setup --chapter -> run --chapter -> review -> export
```

批量生产时：

```text
run-book -> 逐章 setup/run -> book-report -> 人工逐章 review
```

`run-book` 只是编排层。它不改变基本原则：章节仍然是一章一章生产，生产后仍然要由人审稿。

## 4. init 的职责

`init` 用于全书启动。

它应该做这些事情：

1. 创建或打开项目数据库。
2. 如果有人类样稿，则导入样稿。
3. 读取模型配置。
4. 生成契约草稿。
5. 由人类和架构师讨论高创意、高风险字段。
6. 由架构师修订契约草案，而不是要求普通用户直接编辑 YAML。

`init` 不负责某一章续写前的准备。这个职责属于 `setup`。

## 4.1 confirm-contract 的职责

`confirm-contract` 不是“人工点头即入库”。

它现在应该做这些事情：

1. 读取架构师输出的 `contract-draft.yaml`。
2. 做基础格式校验。
3. 执行契约审计师第一轮复审：结构完整性。
4. 执行契约审计师第二轮复审：生产就绪性。
5. 两轮全部通过后，才创建 confirmed 元契约。
6. 如果任何一轮不通过，则写审计报告和失败归因，打回架构师和人类继续讨论。

契约审计师第一轮主要检查：

1. 必需契约段落是否齐全。
2. 角色弧线是否存在。
3. `chapter_N_events` 是否存在。
4. 是否还有 `<<请填写>>`、TODO、TBD 等占位符。

契约审计师第二轮主要检查：

1. shot 编号是否重复或异常。
2. 每个 shot 是否有明确 POV。
3. POV 是否在 `identity.pov_characters` 中声明。
4. 每个 shot 是否有可落地的 `event`。
5. 契约事件中是否混入 `### 场景`、`brilliance=`、`badsmell=`、`POV=` 等管线提示词残留。
6. 章末 hook 是否有明确提示，缺失时至少给出警告。

## 5. setup 的职责

`setup` 用于某一章生产前的校准。

它应该做这些事情：

1. 读取已经确认或锁定的元契约。
2. 提取目标章节的 `chapter_N_events`。
3. 读取上一章的人工审阅状态，如果有的话。
4. 生成本章 setup 包。
5. 生成机器可检查的 `fact_manifest`。
6. 保存 setup YAML。
7. 把 setup 快照写入审计数据库。

setup 包同时面向两类对象：

1. 人类可以读懂，用来确认这一章是不是准备正确。
2. 软件可以检查，用来防止后续写作跑偏。

当前第一版 `fact_manifest` 包含：

1. 废弃人物别名。
2. 禁用短语。
3. 提示词残留标记。
4. 议论性文字标记。
5. 未授权的医疗、请假等扩写标记。
6. 章末钩子要求。
7. 每个 shot 的标题、POV、必达内容、硬事实、类型职责、授权语料。

## 6. setup 预检

在 `run` 创建生产 session 之前，软件会先检查 setup 包是否和契约矛盾。

当前预检可以拦截：

1. 缺少 `fact_manifest`。
2. setup 中的 shot 数量和契约不一致。
3. `fact_manifest` 中的 shot 数量和契约不一致。
4. `must_land` 命中了禁用短语。
5. setup 的 POV 和契约 POV 不一致。
6. setup 的 POV 和 `fact_manifest` POV 不一致。
7. POV 没有在契约中声明。
8. 出现未知类型职责。
9. 章节要求钩子，但最后一个 shot 没有 hook 职责。
10. `must_land` 为空。
11. shot 编号重复或越界。

如果预检失败，失败会被归因为 `contract_conflict`。

## 7. run 的职责

`run` 是正式生产执行器。

它应该按顺序做这些事情：

1. 读取当前契约和 setup。
2. 执行 setup 预检。
3. 创建或恢复 session。
4. 创建本次 run 的快照。
5. 创建 run-attempt shot ID。
6. 编译 shot 级契约。
7. 为不同写手 persona 构建提示词。
8. 调用写手模型。
9. 在进入评审前先做候选稿硬门禁。
10. 只对合格候选稿执行评审打分。
11. 通过 Gate2 和 L4 后，才能封存某个 shot。
12. 通过 L3 后，才能完成整章。
13. 章节门禁通过后，才导出当前 run 的草稿正文。
14. 全程写入审计事件和失败归因。

## 8. 契约优先的写作逻辑

当前最重要的写作原则是：

```text
硬性合格先于文学赛马。
```

具体含义是：

1. 如果一篇候选稿违反硬契约，不能因为文笔好就被选为 winner。
2. 文学评审只能比较已经合格的候选稿。
3. 文风强不能覆盖事实错误。
4. 如果所有候选稿都违反硬规则，系统应该重写或失败，并留下原因，而不是把“最不差”的稿子当成合格稿。

这是第三章审阅暴露问题之后，软件流程做出的主要修正。

## 9. 大纲门禁

每个 shot 会先生成或读取 shot 大纲，然后执行大纲事实门禁。

大纲事实门禁会拦截：

1. 空大纲。
2. 大纲没有包含任何可识别的契约信号。
3. 使用废弃人物别名。
4. 命中禁用短语。
5. 出现未授权事实扩写。

如果大纲门禁失败，正文写作不会开始。

这个机制的目的，是在写手模型消耗 token 前，先拦住错误计划。

## 10. shot 任务卡

大纲通过后，软件会编译 `shot_task_card`。

任务卡包含：

1. 章节。
2. shot 编号。
3. 标题。
4. POV。
5. 必达内容。
6. 硬事实。
7. 类型职责。
8. 是否要求钩子。
9. 禁用短语。
10. 大纲。
11. 大纲评分。
12. 大纲是否通过。

任务卡会被同时写入：

1. 写手提示词。
2. 审计事件。
3. 后续硬门禁。

它的目的，是让写手提示词、硬规则检查、审计记录都使用同一份结构化任务，避免各处自然语言摘要互相漂移。

## 11. 任务卡完整性门禁

写作继续前，软件会检查任务卡是否完整。

它会拦截：

1. 缺少 `must_land`。
2. 缺少 POV。
3. `fact_manifest` 有硬事实，但任务卡缺少硬事实。
4. `fact_manifest` 要求钩子，但任务卡缺少 hook 职责。
5. 缺少大纲。

如果失败，归因为 `task_card_gap`。

## 12. 写手逻辑

当前实现中有多个写手 persona：

1. 意象写手。
2. 节奏写手。
3. 对话写手。
4. 结构写手。

如果 API 并发受限，它们可以串行执行。逻辑上仍然是“多个差异化写手赛马”，只是执行方式可以是串行。

每个写手会收到：

1. 全书级静态前缀。
2. 硬边界。
3. 风格锁。
4. 世界观知识。
5. 如果配置了悬疑职责，则加入悬疑指令。
6. shot 任务上下文。
7. 已接受正文或当前 run 的上下文。
8. 事实锚点。
9. 母题任务。
10. 章节 setup 指令。
11. `shot_task_card`。

写手必须只输出正文，不应该输出分析、解释、小标题或给编辑看的标记。

## 13. 候选稿合格门禁

候选稿会先过 Gate1，再过硬事实门禁，然后才进入评审。

Gate1 检查机械问题：

1. 空文本。
2. 篇幅过短。
3. 重复过多。

硬事实门禁检查：

1. 废弃人物别名。
2. 禁用短语。
3. 未授权事实扩写。
4. 章末钩子被议论性文字提前说死。

只有通过这些检查的候选稿，才有资格进入评审打分。

## 14. 评审逻辑

评审是分层的：

1. 硬规则层。
2. 类型职责层。
3. 文学层。

类型职责只在 shot 有对应类型时启用。例如：

1. 悬疑。
2. 留白。
3. 钩子。

文学层使用九个文学维度打分。当前设计思想是：

1. 硬规则决定是否有资格。
2. 类型职责决定是否完成指定功能。
3. 文学分用于在合格稿之间排序。

## 15. winner 选择逻辑

winner 只能从合格候选稿中选择。

评审还会检查超过配置分数线的稿件数量是否足够。如果数量不够，系统应该重写，而不是封存一个低信心 winner。

这用于避免“只有一个勉强可用的稿子”被系统误判为高质量结果。

## 16. L4 和 L3 门禁

L4 是 shot 级架构门禁。

它判断某个 shot 是否可以封存。主要用于捕捉局部问题，例如：

1. 废弃人物名。
2. 未授权高影响事实。
3. 过多议论性叙述。
4. 契约边界问题。

L3 是章节级架构门禁。

它判断整章是否可以完成和导出。主要用于捕捉章节级问题，例如：

1. 章末钩子太弱。
2. shot 没有完成。
3. 某些有标题的 shot 过薄。
4. 连续性或章节整体不匹配。

如果 L3 不通过，章节不应该被完成，也不应该被正式导出。

## 17. review 与正式正文

`review` 是人类最终决策点。

`review --accept` 要求：

1. run 已完成。
2. 所有 shot 已封存。
3. L3 已通过。
4. 然后把这个 run 标记为本章正式 canonical 版本。

`review --revise` 或 `review --reject` 会：

1. 记录人工决策。
2. 阻止这个 run 被当成正式正文。
3. 让章节回到 setup/run 修订流程。

正式导出默认使用已接受章节。

草稿导出必须显式使用 `--draft`。

## 18. 审计逻辑

当前审计思想是：

```text
每个关键阶段都必须留下数据库记录。
```

审计记录包括：

1. setup 快照。
2. prompt 和上下文快照。
3. 模型提示词和响应正文。
4. 写手候选稿事件。
5. 大纲门禁事件。
6. 候选稿合格性。
7. 评审 verdict。
8. gate 失败。
9. 失败归因。
10. 人工 review 决策。
11. export 事件。

`audit-report` 命令可以汇总：

1. setup 快照。
2. 模型调用。
3. 阶段事件。
4. 候选稿合格性。
5. 失败归因。
6. 最近审计事件。

## 19. 失败归因逻辑

当前失败归因类别：

1. `contract_conflict`：契约或 setup 自相矛盾。
2. `outline_gap`：大纲缺失或大纲没有承接契约。
3. `task_card_gap`：任务卡缺失关键信息。
4. `writer_drift`：写手正文跑偏。
5. `gate_false_positive`：门禁误杀，暂时预留。
6. `model_failure`：模型调用或 JSON 解析失败。
7. `jury_failure`：评审不可用或评审失败。
8. `unknown`：未知原因。

当前映射关系：

1. setup 预检失败 -> `contract_conflict`。
2. 大纲事实门禁失败 -> `outline_gap`。
3. 任务卡完整性失败 -> `task_card_gap`。
4. 正文硬事实失败 -> `writer_drift`。
5. 模型调用或 JSON 解析失败 -> `model_failure`。
6. 评审不可用 -> `jury_failure`。

`gate_false_positive` 暂时保留，等真实失败样本证明“规则拦错了有效稿”之后，再做自动识别。

## 20. 当前投产判断

软件流程已经更接近正确的写作生产思路，但还不应该宣布完全正式投产。

原因：

1. 契约优先的第一版已经实现。
2. 全流程审计已经实现。
3. setup lint 和任务卡失败归因已经实现。
4. 完整测试已经通过。
5. 但新流程还需要用真实第三章重写、第四章首跑来验证。

下一步最有意义的验证是：

1. 重新对第三章执行 setup。
2. 用新门禁重新跑第三章。
3. 检查 `audit-report`。
4. 人工审阅导出的第三章。
5. 确认旧问题是否在进入文学评审前就被拦住。

## 21. 人工重点检查问题

你需要重点判断这些设计是否正确：

1. 人类是否只应该在 `init/setup` 和 `review` 两端介入？
2. `fact_manifest` 是否应该作为硬边界的核心来源？
3. 大纲没有承接契约信号时，是否应该直接停止写作？
4. `shot_task_card` 是否必须成为写作前的强制结构？
5. 正文硬门禁现在是太严，还是还不够严？
6. 悬疑、留白、钩子等类型职责是否应该按 shot 可选启用？
7. 人工接受后的 canonical 正文，是否应该作为唯一正式真相来源？
8. `run-book` 能不能使用未人工接受的草稿作为后续上下文，还是必须只依赖 accepted 章节？
9. 当前失败归因是否足够帮助定位质量问题？
10. `gate_false_positive` 是否应该先人工标记，再考虑自动识别？

## 22. 一句话总结

当前实现的写作思路是：

```text
人类定方向和审最终稿，软件负责在中间生产阶段用契约、硬规则、任务卡、评审和审计来约束模型，防止它写得像但写错。
```
